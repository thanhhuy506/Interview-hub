1. How do you log before and after entering a Controller, besides Spring AOP?

Core idea
Spring MVC
Production
Easy explanation: A request passes through several layers. A Filter is close to the HTTP layer. A HandlerInterceptor is inside Spring MVC and knows about the selected handler/controller. AOP works at method level. For request tracing, Filter or Interceptor is often cleaner than putting logging logic into every controller.
How it works in real life: When a request arrives, the Filter can create a correlation ID and record the start time. The Interceptor can identify the Spring MVC handler. After the controller finishes, the interceptor/filter records the status and latency.

Concrete example — trace one request

POST /api/orders
X-Correlation-ID: req-123

Filter:
  requestId=req-123, start=10:00:00.000
        ↓
Interceptor:
  handler=OrderController.createOrder()
        ↓
Controller
        ↓
Service
        ↓
Database
        ↓
Interceptor:
  status=201
        ↓
Filter:
  duration=152ms

When I use it: For production troubleshooting, latency measurement, request tracing and audit metadata. I would not log the full request body by default because it can contain passwords, tokens, payment data or personal information.

Real production example: A customer reports that checkout is slow. I search for req-123 and can follow the request through Order Service, Payment Service and database logs instead of searching thousands of unrelated log lines.
Client
  ↓
Filter
  ↓
DispatcherServlet
  ↓
Interceptor.preHandle()
  ↓
Controller
  ↓
Interceptor.afterCompletion()
  ↓
Response

Option A — HandlerInterceptor

@Component
public class LoggingInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler) {

        log.info("Before Controller: {} {}",
                request.getMethod(),
                request.getRequestURI());
        return true;
    }

    @Override
    public void afterCompletion(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler,
            Exception ex) {

        log.info("After Controller: status={}",
                response.getStatus());
    }
}

Option B — OncePerRequestFilter

@Component
public class LoggingFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain chain)
            throws ServletException, IOException {

        long start = System.currentTimeMillis();

        log.info("Before request");

        try {
            chain.doFilter(request, response);
        } finally {
            log.info("After request: status={}, time={}ms",
                    response.getStatus(),
                    System.currentTimeMillis() - start);
        }
    }
}
Production tip: Add a correlation/request ID and put it into MDC. Then Controller → Service → Repository logs can be connected using the same ID. Avoid logging passwords, tokens, card data, or sensitive personal information.
Senior answer:
“Besides AOP, I can use a HandlerInterceptor for Spring MVC controller-level logging, or a OncePerRequestFilter for lower-level HTTP logging. In production, I usually add a correlation ID and MDC so that one request can be traced across Controller, Service, database calls, and downstream services. I also log latency and status code, but avoid sensitive data.”

2. What is the difference between Interceptor and Filter?

Easy explanation: Filter belongs to the Servlet/HTTP layer. Interceptor belongs to Spring MVC. Therefore Filter can run before Spring MVC starts, while Interceptor works around the selected controller handler.

Concrete example — which one should I choose?

Need correlation ID for EVERY HTTP request?
        → Filter

Need to know which Spring Controller/handler was selected?
        → HandlerInterceptor

Need to intercept a service method?
        → Spring AOP

Need raw HTTP request/response handling?
        → Filter
Production example: I would put correlation-ID initialization in a Filter because it should exist before Spring MVC starts. I might use an Interceptor to record which controller method handled the request. I would use AOP for service-level audit or metrics.
FilterHandlerInterceptor
Servlet / HTTP levelSpring MVC level
Can run before DispatcherServletRuns around Spring MVC handler execution
Good for request ID, security-related preprocessing, CORS, raw request/response concernsGood for controller-specific checks, timing, handler information
Does not naturally know which controller handler was selectedReceives the handler object
Interview answer:
“A Filter is lower-level and works at the Servlet layer, while a HandlerInterceptor is part of Spring MVC. I would use a Filter for cross-cutting HTTP concerns such as correlation IDs or request preprocessing, and an Interceptor when I need Spring MVC handler information or controller-level behavior.”

3. How do you coordinate microservices? Order → Process → Payment

Easy explanation: Do not assume one database transaction can safely cover multiple independent microservices. A transaction normally belongs to one resource/transaction boundary. For distributed workflows, use patterns such as Saga, orchestration/choreography, events, idempotency, outbox, retries and compensation.

Concrete example — Order → Inventory → Payment

1. Order Service
   INSERT order(status = PENDING)
   COMMIT

2. Inventory Service
   Reserve 2 items
   COMMIT

3. Payment Service
   Charge $100
   FAIL

Now what?
We cannot simply execute ROLLBACK in Payment Service
and expect Order/Inventory databases to rollback.

Saga compensation:
   → Cancel Order
   → Release Inventory

Why this matters: Imagine the payment provider accepted the payment but the network response was lost. The client retries. Without idempotency, the customer could be charged twice. Therefore Saga, idempotency, retry policy, timeout and event delivery must be designed together.

Concrete Outbox example

Order DB transaction:
  UPDATE orders SET status='CONFIRMED'
  INSERT outbox_event(type='OrderConfirmed', orderId=123)
  COMMIT

Outbox publisher:
  reads event
  → Kafka
  → Inventory Service

If Kafka is temporarily down:
  event stays in outbox
  → retry later
Senior thinking: The goal is not “never have partial failure.” Distributed systems cannot guarantee that simply. The goal is to make partial failure recoverable, observable and idempotent.

Example

Order Service
    ↓
Process Service
    ↓
Payment Service
    ↓
Payment fails
Important: If A commits and B commits, then C fails, a normal local database rollback in C cannot magically undo A and B. You need a distributed transaction strategy or business compensation.

Recommended production approach — Saga

Create Order
    ↓
Reserve / Process Order
    ↓
Payment
    ↓
FAIL
    ↓
Compensating actions
    ├── Cancel Order
    └── Release reserved resources

Two common styles:

  • Orchestration: a Saga Orchestrator tells each service what to do and decides the next step.
  • Choreography: services publish events and react to events without one central coordinator.

Outbox pattern

When a service updates its database and publishes an event, there is a dual-write problem. The service can update the DB successfully but fail before publishing the event. The Outbox pattern stores the business change and an event record in the same local DB transaction. A publisher then sends the outbox event to Kafka/RabbitMQ and marks it as published.
BEGIN TX
  update orders
  insert outbox_event
COMMIT
      ↓
Outbox Publisher
      ↓
Kafka
      ↓
Payment Service

Idempotency

Retries can send the same request more than once. Payment and order operations should have an idempotency key or unique business key so the same command is not applied twice.

Senior answer:
“I would not try to use one local @Transactional boundary across independent microservices. For an Order → Process → Payment workflow, I would use a Saga with either orchestration or choreography. Each service commits its own local transaction. If a later step fails, the workflow executes compensating actions, for example canceling the order or releasing a reservation. I would combine this with an Outbox pattern for reliable event publishing and idempotency for safe retries. This gives eventual consistency rather than pretending we have one ACID transaction across all services.”

4. How does @Transactional work? What if C fails but I only want B rolled back?

Easy explanation: @Transactional creates a transaction boundary through Spring's transaction infrastructure, commonly via a proxy. A single transaction normally means A, B and C share the same commit/rollback decision.

Concrete example — partial rollback

Requirement:
A = create audit record
B = update temporary data
C = update final business data

C fails.
Need:
A = keep
B = rollback
C = rollback

One big transaction:
A + B + C
   ↓
C fails
   ↓
Everything rolls back

Nested/savepoint concept:
BEGIN
  A
  SAVEPOINT before_B
  B
  C
  if B must be undone:
      ROLLBACK TO SAVEPOINT before_B
  continue
COMMIT

Important: A savepoint only works inside the transaction and its exact support depends on the database/transaction manager. If B is placed in REQUIRES_NEW and commits, a later C failure cannot undo B.

Concrete REQUIRES_NEW example

Outer T1:
  A

Suspend T1
  Inner T2:
    B
    COMMIT T2

Resume T1:
  C → FAIL
  ROLLBACK T1

Final:
  A = rollback
  B = committed
  C = rollback
Interview trap: If the interviewer says “C fails, rollback only B, but keep A and C”, first ask whether B and C are in the same transaction and whether “rollback B” means database rollback or a business compensation. That clarification shows senior-level thinking.
@Transactional
public void process() {
    A();
    B();
    C();
}

If C throws a rollback-triggering exception:

BEGIN
 ↓
A
 ↓
B
 ↓
C → exception
 ↓
ROLLBACK
 ↓
A + B + C are rolled back

By default, Spring rolls back for unchecked RuntimeException and Error. Checked exceptions normally do not trigger rollback unless configured, for example rollbackFor = SomeCheckedException.class.

Propagation options

PropagationMeaning
REQUIREDJoin the current transaction, or create one.
REQUIRES_NEWSuspend the current transaction and create an independent transaction.
NESTEDUse a nested transaction concept/savepoint when supported, allowing rollback to a savepoint.

If the requirement is “A stays, B rolls back, C continues”

BEGIN T1
  A
  SAVEPOINT
  B
  B fails
  ROLLBACK TO SAVEPOINT
  C
COMMIT T1

This is conceptually a NESTED/savepoint use case, subject to the transaction manager/database support.

If B must be completely independent

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void executeB() {
    B();
}
Critical interview point: REQUIRES_NEW commits B independently. Once B commits, a later failure in C cannot roll B back. Use REQUIRES_NEW when independence is the requirement, not when you need a later step to undo B.
Self-invocation trap: Calling another @Transactional method from the same class may bypass the Spring proxy, so propagation behavior may not be applied as expected. A separate bean/service is a common solution.
Senior answer:
“@Transactional defines a transaction boundary. With A, B and C in the same transaction, an exception in C normally rolls back the whole transaction. If I need partial rollback while keeping the same transaction, I can use a nested transaction/savepoint where supported. If I need B to be completely independent, I use REQUIRES_NEW, but then B commits independently and cannot be rolled back by a later C failure. For distributed microservices, I would use Saga and compensation rather than trying to stretch a local transaction across services.”

5. How many ways can you connect to a database?

Interview note: There is no single fixed number. The answer depends on the language, framework and database. For Java/Spring, explain the major access styles and their trade-offs.

Concrete example — JDBC vs JPA vs MyBatis

Simple CRUD:
  Spring Data JPA
  → less SQL boilerplate

Complex reporting query:
  MyBatis / JDBC
  → precise SQL control

Reactive end-to-end application:
  R2DBC
  → non-blocking database access where supported

All can use connection pooling:
  Application
      ↓
  DataSource / HikariCP
      ↓
  DB connections
      ↓
  Database
Production example: If 20 application instances each open 100 DB connections, the database could face up to roughly 2,000 connections. Increasing the pool size is not automatically a performance improvement. The DB has finite CPU, memory and connection capacity.
ApproachExampleUse case
JDBCDataSource / Connection / PreparedStatementLow-level control
JdbcTemplateSpring JDBCSQL with less boilerplate

Also distinguish connection pooling from the database access technology. HikariCP, for example, manages a pool of JDBC connections; it is not a separate database API.

“In Java, the main choices are JDBC, Spring JdbcTemplate, JPA/Hibernate, MyBatis, and R2DBC for reactive access where supported. My choice depends on the workload. I prefer JPA for standard CRUD and domain relationships, JDBC/MyBatis when I need precise SQL control or complex queries, and R2DBC when the application is truly reactive end-to-end.”

6. How do you improve SQL performance?

Easy explanation: Do not start by adding indexes blindly. First measure the slow query and inspect its execution plan.

Concrete example — finding a slow query

Problem:
GET /orders takes 4 seconds

Step 1:
Find the SQL in APM/database slow-query logs.

Step 2:
Run EXPLAIN / EXPLAIN ANALYZE.

Suppose we discover:
  full table scan
  10 million rows examined
  only 20 rows returned

Step 3:
Check WHERE/JOIN columns and add an appropriate index.

Step 4:
Run the query again and compare:
  rows scanned
  execution time
  CPU / I/O

Step 5:
Verify the improvement under realistic data volume.

Another real example: OFFSET 1000000 LIMIT 20 may become expensive because the database still has to walk through many rows. For very large datasets, keyset/cursor pagination can be a better design.

  1. Identify the slow query using application/APM/database monitoring.
  2. Run EXPLAIN / EXPLAIN ANALYZE where supported.
  3. Check indexes and whether the query actually uses them.
  4. Reduce unnecessary columns and rows.
  5. Review joins, filters and sorting.
  6. Check statistics and data distribution.
  7. Review pagination strategy for large datasets.
  8. Check locking, connection pool size and transaction duration.
  9. Consider caching, read replicas or partitioning if the workload requires it.
Bad:
SELECT * FROM orders
WHERE DATE(created_at) = '2026-08-15';

Better:
SELECT id, status, created_at
FROM orders
WHERE created_at >= '2026-08-15'
  AND created_at <  '2026-08-16';
Why? Applying a function to an indexed column can prevent a normal index from being used efficiently. The exact optimizer behavior depends on the database and available indexes.
Senior answer:
“I start with measurement, not assumptions. I check the execution plan, scan type, join strategy, estimated versus actual rows, indexes, locks and I/O. Then I optimize the query, index design, pagination, schema or workload. For large-scale systems I may add caching, read replicas or partitioning, but only after identifying the actual bottleneck.”

7. Explain database indexes

Easy explanation: An index is an additional data structure that helps the database find rows without scanning the entire table. A common implementation is a B-tree/B+tree family structure, depending on the database.

Concrete example — why an index helps

orders = 10,000,000 rows

Query:
SELECT *
FROM orders
WHERE customer_id = 123;

Without suitable index:
  potentially inspect many rows

With:
CREATE INDEX idx_orders_customer
ON orders(customer_id);

Database can use the index
to find rows for customer 123 much faster.

Composite index example

CREATE INDEX idx_order_customer_status
ON orders(customer_id, status);

Good candidate:
WHERE customer_id = ?
  AND status = ?

Also potentially useful:
WHERE customer_id = ?

Not automatically ideal:
WHERE status = ?
Senior point: The exact result depends on the optimizer, database engine, statistics and query. Always verify with the execution plan instead of memorizing a rule.
Without index:
Table → scan row 1 → row 2 → ... → row N

With index:
Index → locate matching key → fetch required row(s)

Trade-off

BenefitCost
Faster readsExtra storage
Faster filtering/joining/sorting for suitable queriesINSERT/UPDATE/DELETE may become more expensive
Can enforce uniqueness with unique indexesToo many indexes increase maintenance cost

Composite index

CREATE INDEX idx_order_customer_status
ON orders(customer_id, status);

Column order matters. For a B-tree composite index, queries filtering by the leading column(s) can generally benefit more than queries that only use a later column. This is often described using the leftmost prefix concept, although exact optimizer behavior depends on the database.

Senior answer:
“An index is a data structure that reduces the amount of data the database must scan. I design indexes based on real query patterns, especially WHERE, JOIN, ORDER BY and uniqueness requirements. I also consider write overhead, storage, selectivity and column order for composite indexes. I validate the result using the execution plan rather than assuming an index is always beneficial.”

8. How do you design a database?

Easy explanation: Start from business requirements and access patterns, not from tables alone.

Concrete example — Order database

customers
  id PK
  name
     |
     | 1:N
     ↓
orders
  id PK
  customer_id FK
  status
  created_at
     |
     | 1:N
     ↓
order_items
  id PK
  order_id FK
  product_id
  quantity
  price

payments
  id PK
  order_id
  status

Why separate order_items? An order can contain many products. Storing multiple products in one column makes querying, constraints and updates difficult.

Production example: If the order table reaches hundreds of millions of rows, I would not immediately shard it. First measure workload, then consider indexing, partitioning, archiving old orders, read replicas and query optimization. Sharding is a larger operational and consistency decision.
  1. Understand business entities and relationships.
  2. Define data ownership and service boundaries.
  3. Choose relational or NoSQL based on access patterns and consistency needs.
  4. Normalize to reduce unnecessary duplication for transactional data.
  5. Define primary keys and foreign keys where appropriate.
  6. Define constraints: NOT NULL, UNIQUE, CHECK, referential integrity.
  7. Design indexes from expected queries.
  8. Define transaction boundaries and isolation requirements.
  9. Plan growth: partitioning, archiving, sharding, read replicas if necessary.
  10. Plan backup, recovery, migration and observability.

Example — Order system

customers
  |
  +--- orders
          |
          +--- order_items --- products
          |
          +--- payments
Senior point: In microservices, avoid creating one giant shared database schema owned by every service. Prefer clear ownership. If another service needs data, expose an API/event or replicate the needed read model rather than directly changing another service's tables.
Senior answer:
“I start from domain requirements, data ownership and read/write patterns. I choose the database based on consistency, query patterns, scale and operational requirements. For relational systems I define keys, constraints, normalization and indexes, then validate the design against expected queries. In microservices, I also define database ownership per service and avoid uncontrolled cross-service table access.”

9. How do you implement a REST API?

Easy explanation: A production REST API is more than a Controller method. Think about contract, validation, security, service logic, persistence, errors, observability and backward compatibility.

Concrete example — POST /orders

POST /api/orders
Authorization: Bearer ...
Idempotency-Key: payment-order-123

{
  "customerId": 10,
  "items": [
    {"productId": 100, "quantity": 2}
  ]
}

→ Authentication
→ Authorization
→ Validation
→ Controller
→ Order Service
→ Transaction
→ Repository
→ DB
→ 201 Created

Response:
{
  "orderId": 123,
  "status": "PENDING"
}

Why return DTO? If the JPA entity contains internal fields such as database IDs, audit columns or internal status flags, exposing the entity directly can accidentally expose implementation details and make API changes harder.

Production example: For a payment/order endpoint, idempotency is important because a client may retry after a timeout. The API should not create two orders or charge twice simply because the network response was lost.
Client
 ↓
Controller
 ↓ validation
Service
 ↓
Repository
 ↓
Database

Implementation steps

  1. Define the resource and API contract.
  2. Choose HTTP method and URI.
  3. Define request/response DTOs.
  4. Validate input.
  5. Authenticate and authorize.
  6. Execute business logic in the service layer.
  7. Use a transaction where required.
  8. Persist through repository/data access layer.
  9. Map domain result to DTO.
  10. Define consistent error responses.
  11. Add logging, metrics, tracing and tests.
  12. Document with OpenAPI/Swagger.
@PostMapping("/orders")
public ResponseEntity<OrderResponse> create(
        @Valid @RequestBody CreateOrderRequest request) {

    return ResponseEntity
        .status(HttpStatus.CREATED)
        .body(orderService.create(request));
}
HTTP basics: GET reads, POST commonly creates/actions, PUT replaces a resource, PATCH partially updates it, DELETE removes it. Use status codes consistently: 200/201 for success, 400 for invalid input, 401 unauthenticated, 403 forbidden, 404 not found, 409 conflict, 500 for unexpected server failure.
Senior answer:
“I first define the API contract and resource model, then implement Controller → Service → Repository separation. I use DTOs rather than exposing persistence entities directly, validate input, apply authentication and authorization, define consistent error responses, and make transaction boundaries explicit. For production I also add observability, idempotency where needed, OpenAPI documentation and automated tests.”

10. How do Docker containers communicate with each other?

Easy explanation: Containers normally communicate through a Docker network. On a user-defined Docker network, containers can resolve each other by container/service name using Docker's built-in DNS.

Concrete example — Docker Compose

services:
  order:
    ...
  payment:
    ...

Both are on app-net.

Inside order container:
curl http://payment:8080/health

NOT:
curl http://localhost:8080/health

Because:
localhost = current order container
payment = another container resolved by Docker DNS
Production mindset: Do not hard-code container IPs. Containers can be recreated. Use service discovery/DNS. In Kubernetes, use a Kubernetes Service such as payment-service and let cluster DNS resolve it.
docker network create app-net

docker run --network app-net --name order-service ...
docker run --network app-net --name payment-service ...

Then Order Service can call:

http://payment-service:8080/api/payments
Common mistake: Inside a container, localhost means that same container. It does not mean another container or the host machine.

Docker Compose example

services:
  order:
    build: .
    depends_on:
      - payment
    networks:
      - app-net

  payment:
    build: ./payment
    networks:
      - app-net

networks:
  app-net:

For Kubernetes, the equivalent concept is normally a Service and cluster DNS rather than directly addressing a container IP.

Senior answer:
“In Docker, I normally put related containers on the same user-defined network and communicate using service/container DNS names rather than hard-coded IP addresses. For example, order-service can call payment-service:8080. In Kubernetes, I would use a Kubernetes Service and service discovery. I also separate internal ports from published host ports and apply network/security policies as needed.”

11. Redis vs Database — what happens when Redis stores a large amount of data?

Easy explanation: Redis is primarily an in-memory data store. A relational database is usually the system of record for durable transactional business data. Redis is often used for cache, session, counters, locks, rate limiting, queues/streams and fast key-value access.

Concrete example — Redis cache-aside

GET product:100
      ↓
Redis HIT?
  ├─ Yes → return product
  └─ No
       ↓
     Query DB
       ↓
     SET product:100 TTL=300
       ↓
     return product

What if Redis is full?

If maxmemory is configured, Redis follows its configured eviction policy for eligible keys. For example, a cache-oriented policy may remove keys to make room. If the policy does not allow eviction for the operation/data involved, writes can fail because Redis cannot allocate enough memory.

Concrete promotion example — 1 million requests

1,000,000 users
      ↓
same product key
      ↓
TTL expires
      ↓
1,000,000 cache misses
      ↓
DB receives huge traffic
      ↓
DB becomes bottleneck

Protection:
  TTL jitter
  single-flight / request coalescing
  distributed lock for regeneration
  cache warming
  rate limiting
  DB connection limits
  fallback / degraded response
Important distinction: Redis can scale by replication and sharding/Redis Cluster, but that does not solve every problem. Large values, hot keys, memory fragmentation, network bandwidth and uneven key distribution can still become bottlenecks.
Production example: During a promotion, I would pre-warm popular products, avoid synchronized TTLs, monitor hit ratio and evictions, protect the DB from cache stampede, and make sure the application can degrade gracefully if Redis becomes temporarily unavailable.
RedisRelational Database
Memory-first, very low latencyDisk-backed durable storage with database-specific caching
Key-value/data-structure orientedRelational model, SQL, joins and constraints
Great for cache and fast accessGreat for system-of-record transactional data
Memory is expensive and limitedUsually more economical for very large durable datasets

What if Redis becomes very large?

  • Eviction policies: if configured with a maxmemory limit, Redis can evict keys according to the configured policy.
  • TTL: cache entries can expire automatically.
  • Data modeling: avoid storing unnecessarily large values; use appropriate structures and key design.
  • Replication: replicas can improve availability and read scaling depending on the architecture.
  • Redis Cluster: shard data across nodes using hash slots.
  • Monitoring: monitor memory usage, hit ratio, evictions, latency and fragmentation.

Important production case — cache stampede

1,000,000 requests
       ↓
same product key
       ↓
TTL expires
       ↓
all requests miss Redis
       ↓
all requests hit DB
       ↓
DB overload

Mitigations include cache-aside with controlled repopulation, distributed locking/single-flight, TTL jitter, pre-warming popular keys, request coalescing and rate limiting.

Important: Do not treat Redis as an automatic replacement for a database just because it is faster. Decide what data can be regenerated and what data must remain durable and strongly consistent.
Senior answer:
“Redis and a relational database solve different problems. I normally keep durable business data in the database and use Redis for low-latency access such as caching, sessions, counters or distributed coordination. If Redis grows too large, I control memory with TTL and eviction policies, optimize the data model, monitor memory and latency, and use replication or Redis Cluster for scale and availability. For high-traffic cache keys, I also design against cache stampede when TTLs expire at the same time.”

Final Senior Interview Framework

Do not answer only with definitions. For a 9-year Senior Engineer interview, show that you can make decisions under production constraints.
1. What is the problem?
2. Why does it happen?
3. What are the options?
4. Which option would I choose?
5. Why?
6. What are the trade-offs?
7. What happens under failure / peak traffic?
8. How do I monitor it?
9. Give a real production example.

Example: Instead of saying “I use Redis for caching”, say: “I use Redis to reduce DB load and latency. However, I consider cache stampede, stale data, eviction, memory limits, failure fallback and invalidation strategy. For a promotion event, I may pre-warm hot keys, add TTL jitter and protect the database with rate limiting or request coalescing.”
