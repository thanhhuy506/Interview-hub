2. Java Sorting Internals - Concept Only

2.1. What sorting means in Java

Sorting means arranging elements based on a comparison rule. In Java, the comparison rule usually comes from either Comparable or Comparator.

class Employee implements Comparable<Employee> {
    private String name;
    private int age;

    @Override
    public int compareTo(Employee other) {
        return Integer.compare(this.age, other.age);
    }
}
employees.sort(Comparator.comparing(Employee::getName));

2.2. Comparable vs Comparator

Concept Meaning Use case
Comparable Natural ordering defined inside the class. User sorted by ID, Money sorted by amount, Date sorted by time.
Comparator External ordering rule. Sort employees by salary, then by name, then by department.

2.3. Stable vs unstable sort

A stable sort keeps the original order of equal elements.

Before sorting by department: 1. Alice - IT 2. Bob - HR 3. John - IT 4. Mary - HR After stable sorting by department: 2. Bob - HR 4. Mary - HR 1. Alice - IT 3. John - IT Bob stays before Mary. Alice stays before John.
Stability matters when you sort by multiple criteria in multiple steps. For example, sort by name first, then stable-sort by department.

2.4. Arrays.sort for primitives

For primitive arrays such as int[], long[], and char[], Java documentation describes a Dual-Pivot Quicksort implementation. Conceptually, quicksort partitions data around pivots and recursively sorts partitions.

Dual-Pivot Quicksort concept: Array ↓ Choose two pivots ↓ Split data into three regions: values < pivot1 pivot1 <= values <= pivot2 values > pivot2 ↓ Sort each region

Why use quicksort-like algorithm for primitives?

  • No object identity to preserve.
  • No need for stability because primitive values have no attached business identity.
  • Good memory locality.
  • Usually low extra memory overhead.

2.5. Arrays.sort for objects

For object arrays, Java sort is required to be stable. Modern JDK documentation describes it as a stable adaptive iterative mergesort adapted from TimSort ideas.

TimSort / adaptive merge sort concept: Detect already sorted runs ↓ Sort or extend small runs if needed ↓ Merge runs efficiently ↓ Very good for partially sorted real-world data

2.6. parallelSort

Arrays.parallelSort() can split sorting work into multiple tasks. It may help for large arrays on multi-core machines, but it is not always faster for small arrays due to thread/task overhead.

Interview points

  • Do not say every Java sort uses the same algorithm.
  • Primitive arrays and object arrays may use different strategies.
  • Object sorting must be stable.
  • Comparator cost matters. If comparator calls DB/API or heavy logic, sorting becomes expensive.
  • For database-backed data, prefer sorting in DB when pagination/filtering is involved.
Short answer: Java sorting depends on data type. Primitive array sorting is optimized for raw values, while object sorting is stable and optimized for real-world partially sorted data. For business objects, the correctness of comparator logic is often more important than the algorithm name.

3. Java HashMap Internals - Concept Only

3.1. What HashMap is trying to optimize

HashMap is designed for fast key-value lookup. Conceptually, it converts a key into a hash value, maps that hash to a bucket, and stores the entry in that bucket.

put(key, value) ↓ hash = hash(key) ↓ index = hash mapped to bucket position ↓ store Node(hash, key, value, next) in bucket

3.2. Basic internal structure

table[index] → Node(key, value, hash, next)
             → Node(key, value, hash, next)
             → Node(key, value, hash, next)

A bucket may contain one entry, multiple entries in a linked list, or in heavy collision cases, a tree structure.

3.3. How get works

get(key) ↓ Calculate hash ↓ Find bucket index ↓ Check first node ↓ If key matches by hash and equals() → return value ↓ Otherwise traverse linked list or tree ↓ If not found → return null

3.4. Why equals() and hashCode() must be consistent

If two objects are equal by equals(), they must have the same hashCode(). Otherwise, HashMap may search in the wrong bucket.

Map<User, String> map = new HashMap<>();

User u1 = new User(1, "John");
User u2 = new User(1, "John");

map.put(u1, "A");
System.out.println(map.get(u2));

If equals() says u1 and u2 are same but hashCode() is different, get(u2) may fail.

3.5. Collision

A collision happens when different keys map to the same bucket.

Bucket 5: Node("Aa", value1) Node("BB", value2) Node("Xy", value3)

3.6. Collision handling

  • Initially, entries in the same bucket are linked together.
  • If a bucket becomes too large and the table is large enough, Java can convert that bucket into a tree.
  • This protects worst-case lookup from degrading too badly when many keys collide.

3.7. Load factor and resize

Load factor controls how full the table can become before resizing. Default load factor is commonly 0.75.

capacity = 16 load factor = 0.75 threshold = 16 * 0.75 = 12 When size > 12: resize table redistribute entries

3.8. Why resizing is expensive

Resize is expensive because HashMap needs to allocate a larger table and redistribute existing entries into new buckets.

If you know the approximate number of entries, initialize HashMap with a suitable capacity to reduce resize operations.

3.9. HashMap vs LinkedHashMap vs TreeMap

Map Ordering Typical performance Use case
HashMap No guaranteed order Average O(1) Fast lookup by key.
LinkedHashMap Insertion/access order Average O(1) Cache-like behavior, predictable iteration.
TreeMap Sorted by key O(log n) Range query, sorted keys.

Interview points

  • HashMap uses hashCode to locate bucket, then equals to confirm key identity.
  • Good hash distribution gives near constant-time lookup.
  • Bad hashCode causes many collisions and slower lookup.
  • HashMap is not synchronized. Use ConcurrentHashMap for concurrent access.
  • Do not use mutable fields in hashCode/equals for keys after insertion.

4. B-tree and Database Indexes

4.1. Why indexes exist

Without an index, the database may need to scan many rows to find matching data. An index is a separate data structure that helps the database find rows faster.

Without index: Read table rows one by one ↓ Check condition ↓ Return matching rows With index: Search index tree ↓ Find row pointers ↓ Fetch matching table rows

4.2. B-tree concept

A B-tree index is a balanced tree structure. It keeps keys sorted and allows efficient equality search, range search, and ordered traversal.

Root page ├── Internal page │ ├── Leaf page: key → row pointer │ └── Leaf page: key → row pointer └── Internal page ├── Leaf page: key → row pointer └── Leaf page: key → row pointer

4.3. Why B-tree is good for databases

  • Balanced height means predictable lookup.
  • Each node/page contains many keys, reducing disk I/O.
  • Keys are sorted, so range queries are efficient.
  • Can support ORDER BY when index order matches query needs.

4.4. Common queries that benefit from B-tree index

WHERE user_id = ?
WHERE created_at >= ? AND created_at < ?
ORDER BY created_at DESC
WHERE status = ? AND created_at >= ?

4.5. Index is not free

Benefit Cost
Faster reads for matching queries. Slower writes because index must be updated.
Faster range queries and sorting. More disk storage.
Can reduce table scans. Too many indexes can confuse maintenance and increase write cost.
Short answer: A B-tree index is like a sorted tree of keys pointing to table rows. It helps the database avoid scanning the whole table, especially for equality, range, and ordering queries.

5. Index Design and Performance

5.1. Single-column index

CREATE INDEX idx_users_email ON users(email);

Good for:

SELECT * FROM users WHERE email = ?;

5.2. Composite index

CREATE INDEX idx_orders_customer_created
ON orders(customer_id, created_at DESC);

Good for:

SELECT *
FROM orders
WHERE customer_id = ?
ORDER BY created_at DESC;

5.3. Leftmost prefix rule - concept

For an index on (customer_id, created_at, status), the database can efficiently use the prefix from the left side.

Query condition Can use index well? Reason
WHERE customer_id = ? Yes Uses first column.
WHERE customer_id = ? AND created_at > ? Yes Uses left prefix.
WHERE created_at > ? Usually not well Skips first column.

5.4. Selectivity

Selectivity means how well a condition filters data. High selectivity means the condition returns a small percentage of rows.

Column Selectivity Index usefulness
email High Very useful.
gender Low Often less useful alone.
status Depends Useful if combined with date/customer or if distribution is skewed.

5.5. Covering index / index-only scan concept

If the index contains all columns needed by the query, the database may answer from the index without reading table rows.

CREATE INDEX idx_orders_customer_created_total
ON orders(customer_id, created_at, total_amount);
SELECT created_at, total_amount
FROM orders
WHERE customer_id = ?
ORDER BY created_at DESC;

5.6. Index pitfalls

Function on indexed column

WHERE DATE(created_at) = '2026-07-01'

May prevent normal index usage.

Leading wildcard

WHERE name LIKE '%abc'

B-tree index cannot efficiently start from unknown prefix.

Too many indexes

Read may improve, but insert/update/delete become slower.

Wrong column order

Composite index order should match query pattern.

Better date range query

WHERE created_at >= '2026-07-01'
  AND created_at <  '2026-07-02'

6. Database Isolation Levels

6.1. ACID reminder

ACID Meaning
AtomicityAll operations succeed or all are rolled back.
ConsistencyData moves from one valid state to another valid state.
IsolationConcurrent transactions should not corrupt each other.
DurabilityCommitted data survives crash/restart.

6.2. Common concurrency anomalies

Anomaly Meaning Example
Dirty read Read uncommitted data from another transaction. Read payment status before the payment transaction commits.
Non-repeatable read Same row read twice gives different values because another transaction updated it. Read balance = 100, later read balance = 50 in same transaction.
Phantom read Same query returns different set of rows because another transaction inserted/deleted rows. Count orders twice; second count sees new rows.
Lost update Two transactions update same data and one update overwrites the other. Two users update same inventory quantity.

6.3. Isolation levels

Level Concept Use case
Read Uncommitted Weakest isolation. Dirty reads may be possible depending on DB. Rarely used in business systems.
Read Committed Only committed data is visible. Common default in many DBs. Most normal OLTP workloads.
Repeatable Read Rows read earlier should remain consistent inside transaction. Reports or logic needing stable reads.
Serializable Strongest isolation. Result should be as if transactions ran one by one. Critical consistency, but may have higher contention/retry cost.

6.4. MVCC concept

MVCC means Multi-Version Concurrency Control. Instead of blocking every reader when a writer changes data, the database can keep multiple versions of rows so readers see a consistent snapshot.

Transaction A starts ↓ Sees snapshot version 1 Transaction B updates row ↓ Creates version 2 and commits Transaction A may still see version 1 depending on isolation level
Senior mindset: Isolation is a trade-off. Stronger isolation gives stronger consistency but can increase blocking, serialization failures, retries, or lower throughput.

7. Database Locking Mechanism

7.1. Why locks exist

Locks coordinate concurrent access so that two transactions do not modify the same data in unsafe ways.

7.2. Common lock types - concept

Lock Meaning Example
Row lock Locks specific rows. Update one order.
Table lock Locks table-level operations. DDL, bulk operation, explicit lock.
Shared lock Allows reads but prevents conflicting writes. Read lock concept.
Exclusive lock Prevents other conflicting reads/writes depending on DB. Update/delete lock concept.

7.3. SELECT FOR UPDATE

BEGIN;

SELECT quantity
FROM inventory
WHERE product_id = 100
FOR UPDATE;

UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = 100;

COMMIT;

FOR UPDATE locks selected rows so other transactions cannot update them until the current transaction completes.

7.4. Pessimistic locking

Pessimistic locking assumes conflict is likely, so it locks data before update.

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p from Product p where p.id = :id")
Product findByIdForUpdate(Long id);

7.5. Optimistic locking

Optimistic locking assumes conflict is not common. It does not lock first. Instead, it checks a version when updating.

@Entity
public class Product {
    @Id
    private Long id;

    private int quantity;

    @Version
    private Long version;
}
Transaction A reads product version = 1 Transaction B reads product version = 1 A updates product where version = 1 → success, version becomes 2 B updates product where version = 1 → fails because version is now 2

7.6. Deadlock

Transaction A locks row 1, waits for row 2 Transaction B locks row 2, waits for row 1 Database detects deadlock and aborts one transaction

How to reduce deadlock risk

  • Access tables and rows in consistent order.
  • Keep transactions short.
  • Avoid user interaction inside transaction.
  • Add proper indexes so updates lock fewer rows.
  • Retry safely when deadlock or serialization failure occurs.

8. Synchronous vs Asynchronous Programming

8.1. Synchronous programming

In synchronous programming, the caller waits until the operation completes.

Order order = orderService.getOrder(orderId);
Payment payment = paymentService.getPayment(order.getPaymentId());
return buildResponse(order, payment);
Request thread ↓ Call DB ↓ wait Call payment API ↓ wait Return response

Best use cases

  • Simple CRUD APIs.
  • Short DB operations.
  • Business flow requires immediate result.
  • Team prefers simpler debugging and stack traces.

8.2. Asynchronous programming

In asynchronous programming, the caller does not block waiting for the operation to finish. The result may come later through Future, callback, message, or event.

CompletableFuture<User> userFuture =
        CompletableFuture.supplyAsync(() -> userClient.getUser(userId));

CompletableFuture<Orders> ordersFuture =
        CompletableFuture.supplyAsync(() -> orderClient.getOrders(userId));

CompletableFuture.allOf(userFuture, ordersFuture).join();

User user = userFuture.join();
Orders orders = ordersFuture.join();

Best use cases

  • Independent external API calls.
  • Sending email/notification after main transaction.
  • Background jobs.
  • Message-driven workflows.
  • High-latency I/O operations.

Sync vs Async comparison

Point Sync Async
Thread Often blocked while waiting. Can free caller thread or process later.
Complexity Simple. More complex error handling and tracing.
Use case CRUD, simple request-response. Independent I/O, background processing, event workflows.
Failure handling Direct exception flow. Needs callback/Future/message retry handling.
Async does not automatically mean faster. It helps when waiting time can be overlapped or moved out of the request path.

9. Reactive Programming and WebFlux

9.1. What reactive means

Reactive programming is a programming model for asynchronous, non-blocking data streams with backpressure support.

Asynchronous Non-blocking Stream-based Backpressure Event-driven

9.2. Blocking vs non-blocking

Blocking: Thread calls external API Thread waits Thread cannot serve other work Non-blocking: Thread starts I/O Thread is released When data is ready, callback/event continues processing

9.3. Mono and Flux concept

Type Meaning Example
Mono<T> 0 or 1 item. Find user by ID.
Flux<T> 0 to many items. Stream orders, events, messages.

9.4. Example

public Mono<OrderResponse> getOrder(Long orderId) {
    return orderRepository.findById(orderId)
            .flatMap(order ->
                    paymentClient.getPayment(order.getPaymentId())
                            .map(payment -> buildResponse(order, payment))
            );
}

9.5. When reactive is a good fit

  • High-concurrency I/O-bound services.
  • Many slow external API calls.
  • Streaming data.
  • WebSocket/SSE/event stream.
  • Need backpressure-aware processing.

9.6. When reactive may not be a good fit

  • Simple CRUD service with normal traffic.
  • Team is not comfortable with reactive debugging.
  • Most dependencies are blocking JDBC or blocking SDKs.
  • CPU-bound computation.
  • Project needs simplicity more than maximum concurrency.
Mixing blocking calls inside reactive pipelines can destroy the benefit of WebFlux. If blocking is unavoidable, isolate it using appropriate bounded schedulers and understand the trade-off.

9.7. WebMVC vs WebFlux concept

Point Spring MVC Spring WebFlux
Programming model Blocking request-response. Reactive non-blocking.
Thread usage One request usually occupies a request thread while waiting. Small number of event-loop threads can handle many I/O operations.
Return type Object, ResponseEntity, List. Mono, Flux.
Best for Most CRUD/business apps. High concurrency, streaming, non-blocking I/O.

10. Loose Coupling Design

10.1. What loose coupling means

Loose coupling means one component depends as little as possible on the concrete implementation details of another component.

Short version: Depend on abstraction, not concrete implementation.

Tight coupling example

public class OrderService {
    private final EmailSender emailSender = new EmailSender();

    public void createOrder() {
        // create order
        emailSender.send("Order created");
    }
}

Problems:

  • OrderService directly creates EmailSender.
  • Hard to replace with SMS, push notification, or event publisher.
  • Hard to unit test.

Loose coupling with interface

public interface NotificationPort {
    void notify(String message);
}

@Service
public class EmailNotificationAdapter implements NotificationPort {
    public void notify(String message) {
        // send email
    }
}

@Service
public class OrderService {
    private final NotificationPort notificationPort;

    public OrderService(NotificationPort notificationPort) {
        this.notificationPort = notificationPort;
    }
}

10.2. Dependency Inversion Principle

High-level business logic should not depend on low-level infrastructure details. Both should depend on abstractions.

Bad: OrderService → MySqlOrderRepository OrderService → SmtpEmailSender Better: OrderService → OrderRepository interface OrderService → NotificationPort interface Infrastructure implements the interfaces.

10.3. Ports and Adapters / Hexagonal Architecture

Domain / Application Core ├── Use cases ├── Domain services └── Ports / Interfaces Adapters ├── REST Controller ├── JPA Repository ├── Kafka Producer ├── External API Client └── Email Sender

Benefits

  • Business logic is easier to test.
  • Infrastructure can be replaced.
  • Code becomes easier to maintain.
  • Supports modular monolith and microservice architecture.

11. Loose Coupling in Microservices

11.1. What loose coupling means between services

In microservices, loose coupling means each service owns its domain logic and data, and communicates with other services through stable contracts.

Order Service owns order data Payment Service owns payment data Inventory Service owns stock data They communicate through APIs or events, not by directly sharing database tables.

11.2. Bad coupling between microservices

  • Service A directly reads Service B database.
  • Services require synchronized deployment.
  • One service knows too much about another service internal schema.
  • Shared domain model library becomes a hidden monolith.
  • Synchronous call chain becomes too long.

11.3. Better coupling

  • Use stable API contracts.
  • Use events for state changes.
  • Each service owns its database.
  • Use backward-compatible API changes.
  • Use idempotency for retries.
  • Use contract testing between services.

11.4. Synchronous communication

Order Service → Payment Service REST API

Good when:

  • Immediate response is required.
  • User cannot continue without the result.
  • Failure should be returned directly to caller.

Risk:

  • Increases latency.
  • Creates runtime dependency.
  • Can create cascading failure.

11.5. Asynchronous/event-driven communication

Order Created Event
        ↓
Payment Service consumes event
        ↓
Inventory Service consumes event
        ↓
Notification Service consumes event

Good when:

  • Work can happen after main request.
  • Multiple services react to same business event.
  • System needs better resilience and decoupling.

Trade-off:

  • Eventual consistency.
  • Harder debugging.
  • Need retry and idempotency.

12. Advanced Backend Patterns

12.1. Idempotency

An operation is idempotent if calling it multiple times has the same effect as calling it once.

POST /payments
Idempotency-Key: abc-123

Use case:

  • Payment API retry.
  • Order creation retry.
  • Message consumer retry.

12.2. Outbox Pattern

Outbox pattern solves the problem of updating database and publishing event atomically.

Within same DB transaction: 1. Save order 2. Save event to outbox table 3. Commit Background publisher: 4. Read outbox event 5. Publish to Kafka/RabbitMQ 6. Mark event as published

12.3. Saga Pattern

Saga manages distributed transactions using multiple local transactions and compensating actions.

Create Order ↓ Reserve Inventory ↓ Charge Payment ↓ Confirm Order If payment fails: ↓ Release Inventory ↓ Cancel Order

12.4. Circuit Breaker

Circuit breaker protects a service from repeatedly calling a failing dependency.

Closed: calls dependency normally Open: dependency failing, fail fast Half-open: allow small test traffic to check recovery

12.5. Bulkhead

Bulkhead isolates resources so one failing dependency does not consume all threads/connections.

Payment client thread pool Inventory client thread pool Notification client thread pool If notification is slow, payment is still protected.

12.6. Retry with backoff

Retry can help with transient failures, but retry without limit can make outage worse.

Retry 1: after 100ms
Retry 2: after 300ms
Retry 3: after 900ms
Then fail or send to DLQ

12.7. DLQ - Dead Letter Queue

Messages that cannot be processed after retries can be moved to a DLQ for investigation or manual recovery.

13. Interview Summary

Java sorting

Java sorting implementation depends on the data type. Primitive arrays are optimized differently from object arrays. Object sorting must be stable, while primitive sorting focuses on fast raw value sorting. For business code, comparator correctness and cost are very important.

HashMap

HashMap uses hashCode to find a bucket and equals to confirm the exact key. With good hash distribution, get and put are near O(1). Collisions are handled inside buckets, and heavy collision buckets can be treeified. Resizing is expensive, so proper capacity matters for large maps.

B-tree index

A B-tree index is a balanced sorted structure that helps the database find rows efficiently. It is especially useful for equality search, range conditions, and ordering. However, indexes cost storage and slow writes, so they should match real query patterns.

Isolation and locking

Isolation controls what one transaction can see from other concurrent transactions. Locking prevents unsafe concurrent modification. Stronger isolation improves correctness but can reduce throughput or require retries. In production, we choose isolation and locking based on business consistency requirements.

Sync, async, reactive

Synchronous programming is simple and good for normal CRUD flows. Async programming helps when tasks are independent or can run in background. Reactive programming is useful for high-concurrency non-blocking I/O and streaming, but it adds complexity and should not be mixed carelessly with blocking calls.

Loose coupling and microservices

Loose coupling means depending on stable abstractions and contracts, not concrete implementation details. In microservices, each service should own its data and communicate through APIs or events. Event-driven design improves decoupling but introduces eventual consistency and retry/idempotency requirements.

2. Java Sorting Internals - Concept Only

2.1. Sorting trong Java là gì?

Sorting nghĩa là sắp xếp elements dựa trên một rule so sánh. Trong Java, rule này thường đến từ Comparable hoặc Comparator.

class Employee implements Comparable<Employee> {
    private String name;
    private int age;

    @Override
    public int compareTo(Employee other) {
        return Integer.compare(this.age, other.age);
    }
}
employees.sort(Comparator.comparing(Employee::getName));

2.2. Comparable vs Comparator

Concept Ý nghĩa Use case
Comparable Natural ordering được định nghĩa bên trong class. User sort theo ID, Money sort theo amount, Date sort theo time.
Comparator Rule so sánh nằm bên ngoài class. Sort employee theo salary, rồi name, rồi department.

2.3. Stable vs unstable sort

Stable sort giữ nguyên thứ tự ban đầu của các phần tử được xem là bằng nhau.

Trước khi sort theo department: 1. Alice - IT 2. Bob - HR 3. John - IT 4. Mary - HR Sau khi stable sort theo department: 2. Bob - HR 4. Mary - HR 1. Alice - IT 3. John - IT Bob vẫn đứng trước Mary. Alice vẫn đứng trước John.
Stability quan trọng khi sort nhiều tiêu chí theo nhiều bước. Ví dụ sort theo name trước, sau đó stable-sort theo department.

2.4. Arrays.sort cho primitive arrays

Với primitive arrays như int[], long[], char[], Java documentation mô tả implementation là Dual-Pivot Quicksort. Về concept, quicksort chia data theo pivot và sort các partition.

Dual-Pivot Quicksort concept: Array ↓ Chọn hai pivots ↓ Chia data thành ba vùng: values < pivot1 pivot1 <= values <= pivot2 values > pivot2 ↓ Sort từng vùng

Vì sao primitive dùng quicksort-like algorithm?

  • Primitive không có object identity cần giữ.
  • Không cần stability vì primitive value không mang business identity riêng.
  • Memory locality tốt.
  • Thường dùng ít extra memory.

2.5. Arrays.sort cho objects

Với object arrays, Java sort phải stable. Modern JDK documentation mô tả nó là stable adaptive iterative mergesort, được adapt từ ý tưởng TimSort.

TimSort / adaptive merge sort concept: Detect các đoạn đã sort sẵn ↓ Sort hoặc extend small runs nếu cần ↓ Merge runs hiệu quả ↓ Rất tốt với real-world data đã gần sorted

2.6. parallelSort

Arrays.parallelSort() có thể chia việc sort thành nhiều task. Nó có thể hữu ích với array lớn trên máy nhiều core, nhưng không chắc nhanh hơn với array nhỏ do overhead.

Điểm phỏng vấn

  • Không nên nói mọi Java sort đều dùng cùng một algorithm.
  • Primitive arrays và object arrays có thể dùng strategy khác nhau.
  • Object sorting phải stable.
  • Comparator cost rất quan trọng. Nếu comparator gọi DB/API hoặc logic nặng, sort sẽ rất tốn.
  • Với data từ database, nên sort ở DB khi có pagination/filtering.
Trả lời ngắn: Java sorting phụ thuộc vào data type. Primitive array sorting tối ưu cho raw values, còn object sorting stable và tối ưu cho real-world partially sorted data. Với business objects, comparator correctness và cost thường quan trọng hơn tên algorithm.

3. Java HashMap Internals - Concept Only

3.1. HashMap tối ưu cái gì?

HashMap được thiết kế để lookup key-value nhanh. Về concept, nó convert key thành hash value, map hash đó vào bucket, rồi lưu entry trong bucket.

put(key, value) ↓ hash = hash(key) ↓ index = hash mapped to bucket position ↓ store Node(hash, key, value, next) in bucket

3.2. Cấu trúc internal cơ bản

table[index] → Node(key, value, hash, next)
             → Node(key, value, hash, next)
             → Node(key, value, hash, next)

Một bucket có thể chứa một entry, nhiều entries dạng linked list, hoặc trong case collision nặng có thể chuyển thành tree.

3.3. get hoạt động thế nào?

get(key) ↓ Calculate hash ↓ Find bucket index ↓ Check first node ↓ If key matches by hash and equals() → return value ↓ Otherwise traverse linked list or tree ↓ If not found → return null

3.4. Vì sao equals() phải đi với hashCode()?

Nếu hai object bằng nhau theo equals(), chúng bắt buộc phải có cùng hashCode(). Nếu không, HashMap có thể tìm sai bucket.

Map<User, String> map = new HashMap<>();

User u1 = new User(1, "John");
User u2 = new User(1, "John");

map.put(u1, "A");
System.out.println(map.get(u2));

Nếu equals() nói u1 và u2 giống nhau nhưng hashCode() khác nhau, get(u2) có thể fail.

3.5. Collision

Collision xảy ra khi nhiều key khác nhau map vào cùng một bucket.

Bucket 5: Node("Aa", value1) Node("BB", value2) Node("Xy", value3)

3.6. Cách xử lý collision

  • Ban đầu, entries cùng bucket được nối với nhau dạng linked list.
  • Nếu bucket quá lớn và table đủ lớn, Java có thể chuyển bucket đó thành tree.
  • Việc này giúp worst-case lookup không bị degrade quá nặng khi collision nhiều.

3.7. Load factor và resize

Load factor quyết định table được phép đầy tới mức nào trước khi resize. Default load factor thường là 0.75.

capacity = 16 load factor = 0.75 threshold = 16 * 0.75 = 12 Khi size > 12: resize table redistribute entries

3.8. Vì sao resize expensive?

Resize tốn kém vì HashMap phải allocate table lớn hơn và redistribute existing entries vào bucket mới.

Nếu biết gần đúng số lượng entries, nên khởi tạo HashMap với capacity phù hợp để giảm resize.

3.9. HashMap vs LinkedHashMap vs TreeMap

Map Ordering Typical performance Use case
HashMap Không guarantee order Average O(1) Lookup nhanh theo key.
LinkedHashMap Insertion/access order Average O(1) Cache-like behavior, predictable iteration.
TreeMap Sorted by key O(log n) Range query, sorted keys.

Điểm phỏng vấn

  • HashMap dùng hashCode để tìm bucket, sau đó dùng equals để xác nhận đúng key.
  • Hash distribution tốt thì lookup gần O(1).
  • hashCode xấu gây nhiều collision và lookup chậm hơn.
  • HashMap không synchronized. Dùng ConcurrentHashMap khi concurrent access.
  • Không dùng field mutable trong hashCode/equals của key sau khi insert.

4. B-tree và Database Index

4.1. Vì sao cần index?

Nếu không có index, database có thể phải scan rất nhiều rows để tìm data. Index là data structure riêng giúp database tìm rows nhanh hơn.

Không có index: Read table rows one by one ↓ Check condition ↓ Return matching rows Có index: Search index tree ↓ Find row pointers ↓ Fetch matching table rows

4.2. Concept B-tree

B-tree index là balanced tree structure. Nó giữ keys theo thứ tự sorted và hỗ trợ equality search, range search và ordered traversal hiệu quả.

Root page ├── Internal page │ ├── Leaf page: key → row pointer │ └── Leaf page: key → row pointer └── Internal page ├── Leaf page: key → row pointer └── Leaf page: key → row pointer

4.3. Vì sao B-tree phù hợp với database?

  • Balanced height giúp lookup ổn định.
  • Mỗi node/page chứa nhiều keys, giảm disk I/O.
  • Keys được sorted nên range query hiệu quả.
  • Có thể hỗ trợ ORDER BY nếu index order match query.

4.4. Query thường hưởng lợi từ B-tree index

WHERE user_id = ?
WHERE created_at >= ? AND created_at < ?
ORDER BY created_at DESC
WHERE status = ? AND created_at >= ?

4.5. Index không miễn phí

Lợi ích Chi phí
Read nhanh hơn cho query phù hợp. Write chậm hơn vì index cũng phải update.
Range query và sorting nhanh hơn. Tốn thêm disk storage.
Giảm table scan. Quá nhiều index làm maintenance khó và tăng write cost.
Trả lời ngắn: B-tree index giống một cây sorted các key trỏ tới table rows. Nó giúp database tránh scan toàn bộ table, đặc biệt với equality, range và ordering queries.

5. Thiết kế Index và Performance

5.1. Single-column index

CREATE INDEX idx_users_email ON users(email);

Tốt cho:

SELECT * FROM users WHERE email = ?;

5.2. Composite index

CREATE INDEX idx_orders_customer_created
ON orders(customer_id, created_at DESC);

Tốt cho:

SELECT *
FROM orders
WHERE customer_id = ?
ORDER BY created_at DESC;

5.3. Leftmost prefix rule - concept

Với index (customer_id, created_at, status), database thường dùng hiệu quả prefix từ bên trái.

Query condition Dùng index tốt? Lý do
WHERE customer_id = ? Có Dùng column đầu tiên.
WHERE customer_id = ? AND created_at > ? Có Dùng left prefix.
WHERE created_at > ? Thường không tốt Skip column đầu tiên.

5.4. Selectivity

Selectivity nghĩa là condition lọc data tốt tới đâu. High selectivity nghĩa là condition chỉ trả về phần nhỏ rows.

Column Selectivity Index usefulness
email High Rất hữu ích.
gender Low Thường ít hữu ích nếu đứng một mình.
status Tùy case Hữu ích nếu combine với date/customer hoặc data distribution lệch.

5.5. Covering index / index-only scan concept

Nếu index chứa đủ columns query cần, database có thể trả kết quả từ index mà không cần đọc table rows.

CREATE INDEX idx_orders_customer_created_total
ON orders(customer_id, created_at, total_amount);
SELECT created_at, total_amount
FROM orders
WHERE customer_id = ?
ORDER BY created_at DESC;

5.6. Index pitfalls

Function trên indexed column

WHERE DATE(created_at) = '2026-07-01'

Có thể làm index không được dùng tốt.

Leading wildcard

WHERE name LIKE '%abc'

B-tree index khó dùng vì không biết prefix bắt đầu.

Quá nhiều indexes

Read có thể nhanh hơn, nhưng insert/update/delete chậm hơn.

Sai thứ tự column

Composite index order nên match query pattern.

Date range query tốt hơn

WHERE created_at >= '2026-07-01'
  AND created_at <  '2026-07-02'

6. Database Isolation Levels

6.1. Nhắc lại ACID

ACID Ý nghĩa
AtomicityTất cả operations thành công hoặc rollback hết.
ConsistencyData chuyển từ trạng thái hợp lệ này sang trạng thái hợp lệ khác.
IsolationCác transaction chạy đồng thời không được làm hỏng data của nhau.
DurabilityData đã commit phải tồn tại sau crash/restart.

6.2. Các anomaly phổ biến

Anomaly Ý nghĩa Ví dụ
Dirty read Đọc data chưa commit từ transaction khác. Đọc payment status trước khi payment transaction commit.
Non-repeatable read Đọc cùng một row hai lần nhưng ra value khác vì transaction khác update. Lần đầu đọc balance = 100, sau đó đọc balance = 50 trong cùng transaction.
Phantom read Cùng một query nhưng trả về tập rows khác vì transaction khác insert/delete. Count orders hai lần, lần hai thấy rows mới.
Lost update Hai transaction update cùng data và một update ghi đè update kia. Hai user cùng update inventory quantity.

6.3. Isolation levels

Level Concept Use case
Read Uncommitted Yếu nhất. Dirty read có thể xảy ra tùy DB. Hiếm dùng trong business systems.
Read Committed Chỉ thấy data đã commit. Là default phổ biến trong nhiều DB. Phần lớn OLTP workloads bình thường.
Repeatable Read Rows đã đọc nên ổn định trong transaction. Report hoặc logic cần stable reads.
Serializable Mạnh nhất. Kết quả như thể transactions chạy lần lượt. Consistency critical, nhưng có thể tăng contention/retry cost.

6.4. MVCC concept

MVCC là Multi-Version Concurrency Control. Thay vì block mọi reader khi writer thay đổi data, database giữ nhiều version của row để reader thấy consistent snapshot.

Transaction A starts ↓ Sees snapshot version 1 Transaction B updates row ↓ Creates version 2 and commits Transaction A may still see version 1 depending on isolation level
Senior mindset: Isolation là trade-off. Isolation mạnh hơn cho consistency tốt hơn nhưng có thể tăng blocking, serialization failures, retries hoặc giảm throughput.

7. Database Locking Mechanism

7.1. Vì sao cần lock?

Locks điều phối concurrent access để hai transaction không modify cùng data một cách unsafe.

7.2. Các loại lock phổ biến - concept

Lock Ý nghĩa Ví dụ
Row lock Lock các row cụ thể. Update một order.
Table lock Lock ở mức table. DDL, bulk operation, explicit lock.
Shared lock Cho đọc nhưng ngăn conflicting writes. Read lock concept.
Exclusive lock Ngăn các conflicting reads/writes tùy DB. Update/delete lock concept.

7.3. SELECT FOR UPDATE

BEGIN;

SELECT quantity
FROM inventory
WHERE product_id = 100
FOR UPDATE;

UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = 100;

COMMIT;

FOR UPDATE lock selected rows để transaction khác không update chúng cho tới khi transaction hiện tại kết thúc.

7.4. Pessimistic locking

Pessimistic locking giả định conflict dễ xảy ra, nên lock data trước khi update.

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p from Product p where p.id = :id")
Product findByIdForUpdate(Long id);

7.5. Optimistic locking

Optimistic locking giả định conflict không quá thường xuyên. Nó không lock trước, mà check version khi update.

@Entity
public class Product {
    @Id
    private Long id;

    private int quantity;

    @Version
    private Long version;
}
Transaction A reads product version = 1 Transaction B reads product version = 1 A updates product where version = 1 → success, version becomes 2 B updates product where version = 1 → fails because version is now 2

7.6. Deadlock

Transaction A locks row 1, waits for row 2 Transaction B locks row 2, waits for row 1 Database detects deadlock and aborts one transaction

Cách giảm deadlock

  • Access tables và rows theo cùng thứ tự.
  • Giữ transaction ngắn.
  • Không có user interaction trong transaction.
  • Thêm index phù hợp để update lock ít rows hơn.
  • Retry an toàn khi deadlock hoặc serialization failure.

8. Synchronous vs Asynchronous Programming

8.1. Synchronous programming

Trong synchronous programming, caller chờ operation hoàn thành rồi mới đi tiếp.

Order order = orderService.getOrder(orderId);
Payment payment = paymentService.getPayment(order.getPaymentId());
return buildResponse(order, payment);
Request thread ↓ Call DB ↓ wait Call payment API ↓ wait Return response

Use case tốt

  • Simple CRUD APIs.
  • DB operations ngắn.
  • Business flow cần immediate result.
  • Team muốn debugging và stack trace đơn giản.

8.2. Asynchronous programming

Trong asynchronous programming, caller không block để chờ operation xong. Kết quả có thể đến sau qua Future, callback, message hoặc event.

CompletableFuture<User> userFuture =
        CompletableFuture.supplyAsync(() -> userClient.getUser(userId));

CompletableFuture<Orders> ordersFuture =
        CompletableFuture.supplyAsync(() -> orderClient.getOrders(userId));

CompletableFuture.allOf(userFuture, ordersFuture).join();

User user = userFuture.join();
Orders orders = ordersFuture.join();

Use case tốt

  • Các external API calls độc lập.
  • Gửi email/notification sau main transaction.
  • Background jobs.
  • Message-driven workflows.
  • High-latency I/O operations.

Sync vs Async comparison

Điểm Sync Async
Thread Thường bị block khi chờ. Có thể giải phóng caller thread hoặc xử lý sau.
Complexity Đơn giản. Error handling và tracing phức tạp hơn.
Use case CRUD, simple request-response. Independent I/O, background processing, event workflows.
Failure handling Exception flow trực tiếp. Cần callback/Future/message retry handling.
Async không tự động nhanh hơn. Nó hữu ích khi waiting time có thể overlap hoặc chuyển ra khỏi request path.

9. Reactive Programming và WebFlux

9.1. Reactive nghĩa là gì?

Reactive programming là programming model cho asynchronous, non-blocking data streams có backpressure support.

Asynchronous Non-blocking Stream-based Backpressure Event-driven

9.2. Blocking vs non-blocking

Blocking: Thread calls external API Thread waits Thread cannot serve other work Non-blocking: Thread starts I/O Thread is released When data is ready, callback/event continues processing

9.3. Mono và Flux concept

Type Ý nghĩa Ví dụ
Mono<T> 0 hoặc 1 item. Find user by ID.
Flux<T> 0 đến nhiều items. Stream orders, events, messages.

9.4. Ví dụ

public Mono<OrderResponse> getOrder(Long orderId) {
    return orderRepository.findById(orderId)
            .flatMap(order ->
                    paymentClient.getPayment(order.getPaymentId())
                            .map(payment -> buildResponse(order, payment))
            );
}

9.5. Khi nào reactive phù hợp?

  • High-concurrency I/O-bound services.
  • Nhiều slow external API calls.
  • Streaming data.
  • WebSocket/SSE/event stream.
  • Cần backpressure-aware processing.

9.6. Khi nào reactive có thể không phù hợp?

  • Simple CRUD service với traffic bình thường.
  • Team chưa quen reactive debugging.
  • Phần lớn dependencies là blocking JDBC hoặc blocking SDKs.
  • CPU-bound computation.
  • Project cần simplicity hơn maximum concurrency.
Mix blocking calls trong reactive pipeline có thể phá lợi ích của WebFlux. Nếu bắt buộc dùng blocking, cần isolate bằng bounded scheduler phù hợp và hiểu trade-off.

9.7. WebMVC vs WebFlux concept

Điểm Spring MVC Spring WebFlux
Programming model Blocking request-response. Reactive non-blocking.
Thread usage Một request thường giữ request thread trong lúc chờ. Số ít event-loop threads có thể xử lý nhiều I/O operations.
Return type Object, ResponseEntity, List. Mono, Flux.
Best for Phần lớn CRUD/business apps. High concurrency, streaming, non-blocking I/O.

10. Loose Coupling Design

10.1. Loose coupling nghĩa là gì?

Loose coupling nghĩa là một component phụ thuộc ít nhất có thể vào implementation detail cụ thể của component khác.

Câu ngắn: Depend on abstraction, not concrete implementation.

Ví dụ tight coupling

public class OrderService {
    private final EmailSender emailSender = new EmailSender();

    public void createOrder() {
        // create order
        emailSender.send("Order created");
    }
}

Vấn đề:

  • OrderService tự tạo EmailSender.
  • Khó thay bằng SMS, push notification hoặc event publisher.
  • Khó unit test.

Loose coupling với interface

public interface NotificationPort {
    void notify(String message);
}

@Service
public class EmailNotificationAdapter implements NotificationPort {
    public void notify(String message) {
        // send email
    }
}

@Service
public class OrderService {
    private final NotificationPort notificationPort;

    public OrderService(NotificationPort notificationPort) {
        this.notificationPort = notificationPort;
    }
}

10.2. Dependency Inversion Principle

High-level business logic không nên phụ thuộc trực tiếp vào low-level infrastructure details. Cả hai nên phụ thuộc vào abstraction.

Bad: OrderService → MySqlOrderRepository OrderService → SmtpEmailSender Better: OrderService → OrderRepository interface OrderService → NotificationPort interface Infrastructure implements the interfaces.

10.3. Ports and Adapters / Hexagonal Architecture

Domain / Application Core ├── Use cases ├── Domain services └── Ports / Interfaces Adapters ├── REST Controller ├── JPA Repository ├── Kafka Producer ├── External API Client └── Email Sender

Lợi ích

  • Business logic dễ test hơn.
  • Infrastructure dễ thay thế hơn.
  • Code dễ maintain hơn.
  • Hỗ trợ modular monolith và microservice architecture.

11. Loose Coupling trong Microservices

11.1. Loose coupling giữa services nghĩa là gì?

Trong microservices, loose coupling nghĩa là mỗi service own domain logic và data của nó, giao tiếp với service khác qua stable contracts.

Order Service owns order data Payment Service owns payment data Inventory Service owns stock data They communicate through APIs or events, not by directly sharing database tables.

11.2. Coupling xấu giữa microservices

  • Service A đọc trực tiếp database của Service B.
  • Các service bắt buộc deploy cùng lúc.
  • Một service biết quá nhiều về internal schema của service khác.
  • Shared domain model library biến thành hidden monolith.
  • Synchronous call chain quá dài.

11.3. Coupling tốt hơn

  • Dùng stable API contracts.
  • Dùng events cho state changes.
  • Mỗi service own database của nó.
  • Thay đổi API theo hướng backward-compatible.
  • Dùng idempotency cho retry.
  • Dùng contract testing giữa services.

11.4. Synchronous communication

Order Service → Payment Service REST API

Tốt khi:

  • Cần immediate response.
  • User không thể tiếp tục nếu không có result.
  • Failure cần trả trực tiếp cho caller.

Rủi ro:

  • Tăng latency.
  • Tạo runtime dependency.
  • Có thể gây cascading failure.

11.5. Asynchronous/event-driven communication

Order Created Event
        ↓
Payment Service consumes event
        ↓
Inventory Service consumes event
        ↓
Notification Service consumes event

Tốt khi:

  • Work có thể chạy sau main request.
  • Nhiều service cùng react với một business event.
  • System cần resilience và decoupling tốt hơn.

Trade-off:

  • Eventual consistency.
  • Debug khó hơn.
  • Cần retry và idempotency.

12. Advanced Backend Patterns

12.1. Idempotency

Một operation là idempotent nếu gọi nhiều lần vẫn có effect giống như gọi một lần.

POST /payments
Idempotency-Key: abc-123

Use case:

  • Payment API retry.
  • Order creation retry.
  • Message consumer retry.

12.2. Outbox Pattern

Outbox pattern giải quyết bài toán update database và publish event một cách atomic.

Trong cùng DB transaction: 1. Save order 2. Save event vào outbox table 3. Commit Background publisher: 4. Read outbox event 5. Publish to Kafka/RabbitMQ 6. Mark event as published

12.3. Saga Pattern

Saga quản lý distributed transaction bằng nhiều local transactions và compensating actions.

Create Order ↓ Reserve Inventory ↓ Charge Payment ↓ Confirm Order Nếu payment fail: ↓ Release Inventory ↓ Cancel Order

12.4. Circuit Breaker

Circuit breaker bảo vệ service khỏi việc liên tục gọi một dependency đang fail.

Closed: gọi dependency bình thường Open: dependency fail, fail fast Half-open: cho một ít traffic test để kiểm tra dependency đã recover chưa

12.5. Bulkhead

Bulkhead isolate resources để một dependency fail không ăn hết threads/connections.

Payment client thread pool Inventory client thread pool Notification client thread pool Nếu notification chậm, payment vẫn được bảo vệ.

12.6. Retry with backoff

Retry giúp xử lý transient failures, nhưng retry không giới hạn có thể làm outage nặng hơn.

Retry 1: after 100ms
Retry 2: after 300ms
Retry 3: after 900ms
Then fail or send to DLQ

12.7. DLQ - Dead Letter Queue

Messages không process được sau nhiều lần retry có thể được đưa vào DLQ để investigate hoặc recover thủ công.

13. Tóm tắt phỏng vấn

Java sorting

Java sorting implementation phụ thuộc data type. Primitive arrays được optimize khác với object arrays. Object sorting phải stable, còn primitive sorting tập trung sort raw value nhanh. Với business code, comparator correctness và cost rất quan trọng.

HashMap

HashMap dùng hashCode để tìm bucket và equals để xác nhận đúng key. Nếu hash distribution tốt, get và put gần O(1). Collision được xử lý trong bucket, và bucket collision nặng có thể chuyển thành tree. Resize tốn kém, nên capacity phù hợp rất quan trọng với map lớn.

B-tree index

B-tree index là balanced sorted structure giúp database tìm rows hiệu quả. Nó đặc biệt hữu ích cho equality search, range condition và ordering. Tuy nhiên index tốn storage và làm write chậm hơn, nên index phải match query pattern thực tế.

Isolation và locking

Isolation kiểm soát một transaction nhìn thấy gì từ transaction khác. Locking ngăn concurrent modification unsafe. Isolation mạnh hơn giúp correctness tốt hơn nhưng có thể giảm throughput hoặc cần retry. Trong production, chọn isolation và locking dựa trên business consistency requirement.

Sync, async, reactive

Synchronous programming đơn giản và phù hợp với CRUD flow bình thường. Async programming hữu ích khi tasks độc lập hoặc có thể chạy background. Reactive programming phù hợp với high-concurrency non-blocking I/O và streaming, nhưng tăng complexity và không nên mix bừa với blocking calls.

Loose coupling và microservices

Loose coupling nghĩa là phụ thuộc vào abstraction và stable contract, không phụ thuộc implementation detail. Trong microservices, mỗi service nên own data của nó và giao tiếp qua API hoặc events. Event-driven design tăng decoupling nhưng kéo theo eventual consistency, retry và idempotency requirements.
