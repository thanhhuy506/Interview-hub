Amazon-Scale E-commerce: How Inventory Stays Correct Under Massive Concurrency

What happens when one item has only 1 unit left and 50,000 customers press Buy at the same time? What if an admin changes price while thousands of users are viewing and ordering the product? What if payment succeeds but the network times out? This page explains how to design an Amazon-like commerce system that keeps the customer experience fast while the commit path remains correct.

The key idea: browsing can be fast and slightly stale; committing money, inventory, and order state cannot be casual. We separate the high-volume read path from the authoritative reservation/checkout path.

0. Amazon Public Facts vs Amazon-like Design

AMAZON PUBLIC HISTORY

Dynamo + shopping cart

Amazon's 2007 Dynamo paper says the Shopping Cart Service was designed to stay readable and writable during failures. It accepted weaker consistency and resolved conflicts for a better customer experience.

AMAZON PUBLIC HISTORY

99.9th percentile focus

The Dynamo paper explains that Amazon measured service SLAs at the 99.9th percentile instead of optimizing only for averages.

AWS OFFICIAL PRIMITIVE

DynamoDB conditional writes

A single UpdateItem is atomic and can include a condition such as “quantity must be at least requested quantity”. This is a direct primitive for preventing an inventory counter from going below zero.

AWS OFFICIAL PRIMITIVE

DynamoDB transactions

DynamoDB supports ACID transactional reads/writes and serializable isolation for transactional operations with individual reads/writes.

DESIGN INFERENCE

Amazon.com inventory internals

Amazon does not publish the exact current implementation of Amazon.com inventory checkout. The architecture below combines Amazon public lessons with AWS-supported concurrency patterns.

DESIGN INFERENCE

Price quote + reservation model

Versioned price quotes, short inventory reservations, escrow-style regional quotas, and the exact state machine below are recommended designs, not claims about private Amazon retail code.

Do not make this interview mistake: Amazon used eventual consistency for shopping carts because losing cart availability is a bad experience. That does not mean inventory can be eventually decremented with no protection. Different business data needs different consistency.

3. The Core Inventory Race: 1 Item, Thousands of Buyers

3.1 The broken read-then-write design

inventory = 1

Request A: READ inventory -> 1
Request B: READ inventory -> 1

A: inventory = 1 - 1 -> 0
B: inventory = 1 - 1 -> 0

Both customers think they bought it.
Actual stock = 1.
Orders = 2.

OVERSOLD.

The bug is not the speed of the database. The bug is the application performs a non-atomic read-modify-write sequence.

3.2 Correct relational database pattern: one atomic statement

UPDATE inventory
SET
  available = available - :qty,
  reserved  = reserved  + :qty,
  version   = version + 1
WHERE sku_id = :sku
  AND available >= :qty;

if affected_rows == 1:
    reservation succeeded
else:
    out of stock

The database serializes the conflicting row update internally. Only a request that still satisfies available >= qty wins.

3.3 DynamoDB equivalent

UpdateItem(
  Key = { sku_id },
  UpdateExpression =
      "SET available = available - :qty,
           reserved  = reserved + :qty",
  ConditionExpression =
      "available >= :qty"
)

AWS documentation states that individual UpdateItem operations are atomic and operate on the most recent version of an item. Conditional updates only succeed when the condition is true. This gives a natural “winner” under concurrency.

3.4 Timeline with one item left

available = 1

t0  A -> conditional decrement
t0  B -> conditional decrement
t0  C -> conditional decrement

Database order:

A: condition 1 >= 1 -> TRUE
   update available = 0
   SUCCESS

B: condition 0 >= 1 -> FALSE
   OUT_OF_STOCK

C: condition 0 >= 1 -> FALSE
   OUT_OF_STOCK

Exactly one reservation wins.
Most important inventory principle: never do “read stock, calculate in application, then write absolute new value” for a contested item. Move the constraint into the atomic database write.

4.4 Why reserve before final payment?

Because you do not want to successfully charge the customer and then discover that inventory disappeared. A common design is:

1. validate product/price
2. reserve inventory for a short window
3. authorize payment
4. commit order
5. finalize reservation

if payment fails:
  release reservation

4.5 But reservation creates another problem: hoarding

An attacker can reserve all scarce stock and never pay. Therefore a reservation needs:

  • Short expiry.
  • Per-user/account/device limits.
  • Bot and abuse checks before scarce-stock reservation.
  • Reliable release/reconciliation if a workflow dies.
Do not depend only on database TTL deletion for exact reservation expiry. Expiration is a business event. A sweeper/scheduler or explicit expiry index should release inventory predictably; native storage TTL can be too delayed for scarce inventory.

5. Admin Updates Product While Thousands of Users Are Buying

This is not one problem. Price, content, product status, and inventory need different rules.

5.1 Product versioning

product:
  product_id = P100
  title      = "Laptop"
  price      = 1000
  status     = ACTIVE
  version    = 42

User loads the page and sees version 42. An admin changes the price:

price   = 1100
version = 43

The old product page may still show version 42 from cache for a short period. That can be acceptable for browsing. Checkout must decide the business rule.

5.2 Strategy A — always use the newest price at checkout

client checkout request:
  product_id = P100
  seen_version = 42
  seen_price = 1000

checkout reads authority:
  current_version = 43
  current_price = 1100

42 != 43

return:
  PRICE_CHANGED
  new_price = 1100

UX: show “Price changed from $1000 to $1100. Please review before placing your order.”

5.3 Strategy B — short price guarantee / quote

For a better experience, Pricing Service can issue a short-lived quote:

price_quote:
  quote_id
  product_id
  unit_price = 1000
  currency
  quantity_limit
  expires_at = now + 10 minutes
  pricing_version = 42
  signature / server record

Then an admin can update the public price to $1100, but a valid quote can still honor $1000 until expiry. This is a business decision, not a database accident.

5.4 Product disable during checkout

If an admin changes:

status: ACTIVE -> BLOCKED
version: 42 -> 43

checkout should revalidate the sellability state before commitment. Do not trust the old cached product page.

5.5 Admin inventory adjustment: never overwrite blindly

Dangerous:

Admin sees available = 100

Meanwhile:
customer reserves 2
available becomes 98

Admin writes:
SET available = 120

The reservation can be lost in the calculation.

Better: update the physical quantity as a delta or use a version check:

receive shipment:
  on_hand += 20

customer reservation:
  reserved += 2

available_to_promise =
  on_hand - reserved - safety_stock

For a physical stock count correction, use optimistic version control or a short transaction so the reconciliation cannot silently overwrite concurrent reservations.

6.1 Why optimistic locking can collapse under extreme contention

1000 writers:

read version 50
read version 50
read version 50
...

one writes version 51

999 fail
999 re-read
999 retry

one writes version 52

998 fail again
...

AWS's official resource-counter guidance warns that this read-modify-retry loop can become self-destructive at high concurrency. For a hot inventory counter, prefer a single atomic conditional decrement or redesign the ownership model instead of creating an OCC retry storm.

7. Flash Sale: One SKU Receives Millions of Requests

Critical insight: If there are only 100 items, you do not want one million successful writes to the inventory database. You want at most roughly 100 successful reservations and to reject/shed the rest as cheaply as possible.

7.1 Layered protection

1,000,000 Buy Requests
→
Edge Rate Limit
→
Bot / Eligibility
→
Admission Gate
→
Inventory Reservation
→
100 Winners

7.2 “Sold out” fast flag

When authoritative inventory reaches zero, publish a fast regional/cache signal:

sku:P100:likely_sold_out = true

This flag is only an optimization. It can reject obvious losers before the database, but the authoritative conditional write remains the correctness guard.

7.3 Single hot key has a physical throughput limit

A single exact inventory item cannot scale infinitely because conflicting mutations must be ordered somehow. DynamoDB documentation also explains that a single hot partition/item has finite write throughput even with adaptive capacity.

7.4 Scale by dividing ownership, not by duplicating one counter

For extremely hot inventory, pre-allocate disjoint stock budgets:

Total stock = 1,000

Bucket 0 -> 50
Bucket 1 -> 50
...
Bucket 19 -> 50

sum(all bucket budgets) = 1,000

Requests hash across buckets. Each bucket uses its own atomic conditional decrement. Because the inventory tokens are disjoint, global oversell is still impossible.

7.5 This is an escrow / token ownership model

Global stock
   |
   +-- APAC quota: 300
   +-- US quota:   400
   +-- EU quota:   300

Each region can sell only its owned quota.

No region can spend another region's tokens
without a quota-transfer operation.

This removes a global write on every purchase. The trade-off is that one region can temporarily show sold out while another still owns unused quota. A background/control-plane process can rebalance quotas.

7.6 Alternative: one token per unit

stock-token-0001 FREE
stock-token-0002 FREE
...
stock-token-1000 FREE

reservation:
conditional claim one FREE token

FREE -> RESERVED -> SOLD
             \
              -> FREE on release

This makes the invariant very explicit: one physical sellable unit corresponds to one claimable token. It costs more storage and token-selection logic, but it avoids a single global counter hotspot.

7.7 Should we serialize all orders with a queue?

Usually no.

per-SKU FIFO queue:
  request 1
  request 2
  request 3
  ...

A queue gives easy ordering but introduces waiting and creates a hot queue partition for a hot SKU. It can be useful for limited launches, lotteries, background reconciliation, or as an admission system, but a normal checkout path is often better with direct conditional writes.

8. Double Click, Timeout and Retry: Idempotency Is Mandatory

8.1 The ambiguous timeout problem

User clicks Buy

Client -> Order Service
           |
           | creates order O123
           | reserves stock
           v

Response is LOST.

Client sees timeout.

Question:
Did the order happen?

If the client retries with a new identity, we may create order O124 and reserve again.

8.2 Idempotency key

POST /checkout

Idempotency-Key:
  9ca5c0bf-...

same user intention
=
same key on every retry

The server stores:

idempotency_key -> order_id -> final/result state

Retry:

same key found
    |
    +-- request still processing -> return processing/reconcile
    |
    +-- completed -> return same order/result
    |
    +-- conflicting payload -> reject

Amazon's Builders' Library explicitly describes idempotent API design as a way to make retries safe and avoid duplicate side effects.

8.3 Transactional idempotency marker

TRANSACTION:

1. condition:
   idempotency marker does not exist

2. reserve inventory

3. create order

4. create marker:
   key -> order_id

COMMIT ALL OR NOTHING

AWS's DynamoDB counter guidance describes this marker pattern and DynamoDB transactions also support client request tokens for idempotent transactional requests.

There is always a propagation window. Therefore correctness cannot depend on every cache being updated immediately.

10.2 Versioned cached objects

cache key:
product:P100:v43

or cached value:
{
  product_id: P100,
  version: 43,
  ...
}

10.3 DAX lesson

AWS documents that DAX cached reads are eventually consistent. Strongly consistent reads are passed through to DynamoDB instead of being served from cache. This is exactly the kind of distinction a checkout design should understand: cache for speed, source-of-truth read/write for strong decisions.

10.4 Cache outage protection

Amazon's Builders' Library warns that blindly falling back from a failed cache to a dependency can overload the dependency and cause a brownout. Protect the authoritative database with:

  • Rate limits.
  • Request coalescing.
  • Load shedding.
  • Bounded concurrency.
  • Warm/cold-cache recovery plans.

11. Multi-Region Inventory: The Hardest Version of the Problem

11.1 Dangerous design

stock = 1

US region sees 1
APAC region sees 1

US sells 1
APAC sells 1

eventual replication later merges state

too late:
2 customers were promised
1 unit.

For exact inventory, multi-active eventual consistency on one shared counter is dangerous.

11.2 Option A — single write authority per inventory pool

SKU + warehouse
      |
      v
home write region
      |
      +---- replicas for read

All reservations for that inventory pool go to one authoritative region. Correct and simpler, but users far from the authority pay WAN latency.

11.3 Option B — multi-region strong consistency

DynamoDB now documents a multi-Region strong consistency mode for global tables, where writes are synchronously replicated before returning and strong reads can see the latest version. The trade-off is higher cross-region coordination cost/latency and stricter region topology constraints.

11.4 Option C — escrow quotas by region

Total sellable = 100

US   owns 40 tokens
APAC owns 35 tokens
EU   owns 25 tokens

Each region makes local exact reservations.

40 + 35 + 25 = 100
=> global oversell impossible.

This is often the most scalable conceptual model for scarce globally sold resources. Rebalancing tokens is much less frequent than customer purchases.

Consistency lesson: “global active-active database” is not automatically correct for inventory. You need to know the database's conflict model and decide who owns the right to spend each unit.

12. Inventory Ledger: Make Every Change Explainable

A single current counter is useful, but a ledger makes reconciliation possible.

inventory_events

event_id    sku   location   type        qty    reference
E1          A     WH1        RECEIVE     +100   shipment-10
E2          A     WH1        RESERVE       -2   order-501
E3          A     WH1        RELEASE       +2   order-501
E4          A     WH1        RESERVE       -1   order-502
E5          A     WH1        SHIP           0   order-502
E6          A     WH1        ADJUST        -3   cycle-count

The exact sign semantics depend on whether the ledger represents available, on-hand, reserved, or several dimensions. The key value is auditability:

  • Why did stock change?
  • Which order owns a reservation?
  • Was an event processed twice?
  • Can current counters be rebuilt/reconciled?

12.1 Counter + ledger hybrid

Fast path:
  update current inventory counters atomically

Same transaction / durable event:
  write inventory event

Async:
  analytics
  audit
  reconciliation
  warehouse projections

AWS's resource-counter guidance describes item-collection/event-sourcing approaches as an alternative for accurate, idempotent counter changes, with the trade-off that reads become more expensive if the value must be summed.

13. Concurrency Cases You Should Be Ready to Explain

Case 1 — Two users buy the last item

Use one atomic conditional reservation. One succeeds; the later condition sees zero and fails. Never separate check and decrement.

Case 2 — 100,000 users buy 100 flash-sale units

Use edge admission, bot protection, rate limiting, a fast sold-out hint, and an authoritative reservation. If a single inventory key cannot handle the mutation rate, pre-partition ownership into disjoint inventory token buckets.

Case 3 — User double-clicks “Place Order”

Both requests carry the same idempotency key. Order creation + inventory reservation + marker are designed so only one logical order can be created.

Case 4 — Server committed order but response timed out

The retry uses the same idempotency key. The server returns the existing order rather than making a second reservation.

Case 5 — Inventory reserved, payment declines

Saga compensates: release reservation and mark order failed. Release must itself be idempotent.

Case 6 — Payment authorized, Order Service crashes

Recovery process queries durable workflow/payment state using stable request IDs, then either continues confirmation or voids/refunds depending on the business state machine.

Case 7 — Admin changes price while user is on checkout page

Checkout compares product/price version or validates a price-quote token. Business rule either asks the customer to accept the new price or honors the old quote until expiry.

Case 8 — Admin blocks product while thousands are ordering

Browse caches may briefly stay stale. Commit path checks authoritative sellability/version and rejects new commitments after the effective boundary.

Case 9 — Warehouse receives 500 units while orders reserve stock

Use additive on-hand adjustment, not an absolute overwrite of available inventory. Keep on-hand and reserved dimensions separate.

Case 10 — Physical stock count discovers 10 missing units

Record a versioned adjustment event. If reserved exceeds new physical availability, set available-to-promise to zero and start shortage reconciliation according to business priority; do not erase confirmed reservations silently.

Case 11 — Customer cancels while fulfillment allocates the item

Use an order/fulfillment state machine with conditional transitions. For example, cancellation can move RESERVED → RELEASED, but cannot overwrite SHIPPED. State transition must include expected current state/version.

Case 12 — Same event is delivered twice from the queue

Use event ID / inbox marker. Consumer checks if it has processed the event before applying side effects.

Case 13 — Cache still shows stock after product is sold out

This is acceptable only for the browse label. Checkout's conditional reservation rejects the purchase and UI immediately refreshes the product state.

Case 14 — One region loses network access

If inventory has a home region, fail closed for new reservations that cannot reach authority, or switch only after controlled authority transfer. If regional quotas are used, each healthy region can keep selling only its locally owned tokens.

Case 15 — Retry storm after a database slowdown

Use bounded retries, exponential backoff with jitter, idempotency, admission control, and load shedding. Never let every client retry immediately and multiply the original overload.

Case 16 — Hot optimistic-lock row causes endless conflicts

Stop using a read-version-write retry loop for the hot path. Use atomic condition, serialize a bounded subset, or split inventory ownership into disjoint buckets.

Case 17 — Promotion starts at exactly midnight during active carts

Store promotion/version/effective_at. Browsing can update asynchronously; checkout resolves the price according to server time and the quote/promotion policy, not client clock.

Case 18 — Return arrives while a replacement order is being created

Return is a distinct inventory event. Decide when the returned unit becomes sellable—received, inspected, or restocked—rather than immediately adding it when the refund begins.

16. What Amazon's Dynamo Shopping-Cart Story Teaches Us

Amazon's Dynamo paper is useful because it shows that consistency is a business decision. The shopping cart had a strong “always writeable” requirement: customers should still add/remove items during failures. Dynamo therefore used partitioning, replication, object versioning, quorum-like techniques, and application conflict resolution. The cart application could merge conflicting versions instead of rejecting customer actions.

But inventory is different. If two replicas independently promise the same last physical unit, “merge later” cannot undo the customer promise. Therefore a modern Amazon-like design should give inventory reservation a stronger invariant than cart editing.

17. Principal Engineer Interview Answer

“I would not make the entire e-commerce system strongly consistent. I would separate the browse/read model from the order commitment model. Catalog and search can be cached and eventually consistent.
