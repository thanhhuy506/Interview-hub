Caching Patterns & Anti-Stampede

A senior-level interview and production guide: cache fundamentals, common caching patterns, Redis architecture, TTL behavior, and how to protect a database when 10,000 concurrent requests arrive after the same cache entry expires.

1. Caching Fundamentals

What is caching?

A cache stores frequently accessed data in a faster storage layer so that future requests can avoid an expensive operation such as a database query, remote API call, disk read, or computation.

Client → Application → Cache → (hit) return data
Client → Application → Cache → (miss) Database → Cache → return data

The important senior-level idea is that a cache is normally an optimization, not the source of truth. The database or another authoritative system owns correctness unless the architecture explicitly defines otherwise.

Cache Hit

The requested key exists and the cached value is usable. The application avoids the expensive backend operation.

Cache Miss

The key is absent, expired, or unusable. The application needs another source, usually the database.

TTL

Time To Live defines how long an entry is considered valid. TTL is useful for controlling staleness and memory usage.

Eviction

Eviction removes entries because of memory pressure or an eviction policy such as LRU/LFU. Eviction is different from TTL expiration.

2. Basic Caching Patterns

2.1 Cache-Aside / Lazy Loading

The application explicitly checks the cache. On a miss, it loads data from the database and then populates the cache.

public Product getProduct(long id) {
    String key = "product:" + id;

    Product cached = redis.get(key);
    if (cached != null) {
        return cached;
    }

    Product product = productRepository.findById(id);

    if (product != null) {
        redis.set(key, product, Duration.ofMinutes(10));
    }

    return product;
}

Advantages: simple, flexible, only requested data is cached.

Risks: cache miss storms, stale data, race conditions, and cache/database inconsistency.

Typical use: product details, user profiles, configuration, reference data, read-heavy APIs.

Interview point: Cache-aside is usually the default choice in application-level caching because the application controls what is cached and when. But a senior engineer must immediately think about stampede protection and invalidation.

2.2 Read-Through Cache

The application asks the cache layer for data. The cache itself loads missing data from the backend through a configured loader.

Application → Cache → hit: return
Application → Cache → miss: Cache Loader → DB → Cache → Application

This reduces cache-loading logic in business code, but it couples the cache layer to the backend and can make failure behavior more complex.

2.3 Write-Through Cache

Writes go through the cache, and the cache synchronously writes to the backing store before the operation is considered successful.

Application → Cache → Database
↓
success

Benefit: cache is less likely to contain stale data after writes.

Cost: write latency increases because the backend write is part of the request path.

2.4 Write-Behind / Write-Back

The application writes to the cache first. The cache asynchronously persists changes to the database.

Application → Cache → immediate response
↓ async
Queue/Worker → Database

This can provide extremely high write throughput but introduces durability and consistency risks. It requires careful handling of retries, ordering, duplicate events, and process failure.

2.5 Refresh-Ahead

The system refreshes an entry before it expires, usually when the entry is close to its TTL. This reduces the probability that a hot key becomes unavailable at exactly the expiration time.

It is especially useful for predictable, frequently accessed data such as product catalogs, exchange rates, or configuration.

2.6 Multi-Level Cache: L1 + L2

Application
↓
L1: Local Caffeine / in-process cache
↓ miss
L2: Redis
↓ miss
Database

L1 avoids network calls for extremely hot keys. Redis provides shared caching across application instances. The trade-off is invalidation complexity because multiple cache copies exist.

3. TTL, Expiration and Eviction

Why use TTL?

  • Limit how long stale data remains cached.
  • Automatically remove data that should no longer be used.
  • Control memory consumption.
  • Reduce the need for explicit invalidation for data that can tolerate bounded staleness.
Important: TTL does not prevent a stampede. In fact, synchronized TTLs can create a stampede.

Fixed TTL vs TTL Jitter

Suppose 100,000 product keys are loaded at 12:00:00 and all receive exactly a 10-minute TTL. They may expire around 12:10:00, creating a synchronized burst of cache misses.

Instead, add random jitter:

baseTtl = 10 minutes
jitter = random(0..120 seconds)

actualTtl = baseTtl + jitter

Expiration is distributed over time instead of synchronized.

4. The 10,000-Request Cache Stampede

The production problem

Assume:

  • Redis contains product:123.
  • TTL = 10 minutes.
  • At 10:00:00 the key expires.
  • 10,000 requests arrive almost simultaneously.
  • All 10,000 requests check Redis.
  • All receive a miss.
  • All execute SELECT ... FROM product WHERE id = 123.
10,000 requests
↓
10,000 Redis MISS
↓
10,000 DB queries
↓
DB connection pool exhausted
↓
DB CPU / I/O increases
↓
timeouts → retries
↓
even MORE requests
↓
cascading failure

This is called a cache stampede, cache avalanche in broader cases, or thundering herd.

Why can retries make it worse?

Suppose the DB can safely handle 500 expensive queries/second but 10,000 requests arrive. The first wave overloads the DB. Requests time out. Clients or upstream services retry. Now the DB receives the original requests plus retries.

A senior engineer should recognize this as a positive feedback loop:

Cache miss → DB overload → latency → timeout → retry → more DB load → higher latency → more timeout

5. Anti-Stampede Techniques

Technique 1 — Distributed Lock / Single Flight

The most important technique for a hot key is to allow only one request to rebuild the cache while the others wait or use an alternative response.

Request A → Redis MISS → acquire lock product:123:lock → DB → Redis SET
Request B → Redis MISS → lock exists → wait/retry Redis
Request C → Redis MISS → lock exists → wait/retry Redis
...
Request 10,000 → Redis MISS → lock exists → wait/retry Redis

After A populates Redis, B–10,000 read the newly cached value.

Goal: convert 10,000 DB reads into approximately 1 DB read.

The lock must have a TTL so that a crashed lock holder does not block the key forever.

Senior warning: A distributed lock is not automatically safe just because Redis supports SET NX. You must consider lock expiration, ownership, retries, process crashes, and whether the protected operation can outlive the lock.

Technique 2 — Request Coalescing / SingleFlight

Inside one application instance, requests for the same key can share one in-flight computation.

Concurrent requests:
product:123
product:123
product:123
        ↓
one in-flight load
        ↓
DB
        ↓
shared result
        ↓
all callers

This is excellent for reducing duplicate work locally. However, if there are 50 application instances, each instance could still perform one DB request. A distributed coordination mechanism may be required for globally hot keys.

Technique 3 — Stale-While-Revalidate

Do not immediately discard a hot value when it reaches its freshness boundary. Serve the stale value for a short grace period while one background process refreshes it.

Request → stale-but-acceptable value → return immediately
↓
background refresh → DB → Redis

This is often one of the best approaches for read-heavy systems where slightly stale data is acceptable.

Example policy:

  • Fresh for 5 minutes.
  • Stale-but-servable for another 2 minutes.
  • Only one refresh is allowed during the stale window.

Technique 4 — TTL Jitter

Add randomness to TTL values so large numbers of keys do not expire simultaneously.

TTL = 600 + random(0, 120) seconds

This is simple and cheap, but it does not solve a single extremely hot key that expires. Combine it with locking or stale-while-revalidate.

Technique 5 — Background Refresh / Pre-Warming

For known hot keys, refresh the cache before expiration.

Scheduler / event / background worker
↓
Redis TTL low
↓
load DB
↓
update Redis TTL

This works particularly well for predictable traffic, promotions, flash sales, and popular product pages.

Technique 6 — L1 Local Cache + L2 Redis

Put very hot data in an in-process cache such as Caffeine, with Redis as the distributed second-level cache.

For 10,000 requests hitting the same application instance, many requests never reach Redis. Redis itself also avoids unnecessary network traffic.

The challenge is invalidation: every application instance may hold its own copy. Pub/Sub, events, versioning, or short local TTLs can help.

Technique 7 — Rate Limiting / Concurrency Limiting

Even with stampede protection, backend load should be bounded. Limit the number of concurrent cache rebuilds or database calls.

For example, allow at most 20 expensive product loads concurrently. Other requests wait, receive stale data, or fail fast depending on business requirements.

Key idea: protecting the DB is more important than making every request succeed immediately.

Technique 8 — Circuit Breaker + Fallback

If the database becomes unhealthy, stop sending unlimited traffic to it. A circuit breaker can temporarily reject or short-circuit expensive operations.

Possible fallbacks include:

  • Serve stale cached data.
  • Return a degraded response.
  • Return a controlled 503.
  • Use a secondary read source if the architecture supports it.

Technique 9 — Negative Caching

If a key does not exist in the database, cache the negative result for a short TTL.

product:999999 = NOT_FOUND, TTL 30 seconds

This protects the database from repeated requests for invalid IDs. Use a short TTL because the entity may be created later.

6. Recommended Production Architecture

For a very hot product key

Client ↓ API / Load Balancer ↓ Application ↓ L1 Caffeine ↓ miss Redis ↓ miss / stale Single-flight or distributed lock ↓ DB concurrency limit ↓ Database ↓ Redis SET with jittered TTL ↓ L1 update

For a high-traffic production system, combine mechanisms rather than expecting one mechanism to solve everything.

Example request algorithm

1. Check L1.
2. If fresh → return.
3. Check Redis.
4. If fresh → populate L1 and return.
5. If stale value is available → return stale value.
6. Trigger one background refresh.
7. If no usable value exists:
      acquire distributed lock
      double-check Redis
      if another request already refreshed:
          return Redis value
      otherwise:
          load DB
          write Redis
          populate L1
          release lock
8. Apply timeout and concurrency limits to DB.
9. Never allow unlimited retries.

8. Senior-Level Interview Questions & Answers

Q1. What happens if 10,000 requests hit the same Redis key exactly when its TTL expires?

Senior answer: If the application uses naive cache-aside, all 10,000 requests can observe a cache miss and independently query the database. That creates a thundering-herd problem and can exhaust the DB connection pool, CPU, I/O, or downstream capacity. Timeouts can then trigger retries and cause a cascading failure.

I would prevent this with a combination of single-flight or a distributed lock, stale-while-revalidate for data that can tolerate bounded staleness, TTL jitter for large populations of keys, and database concurrency limits. For predictable hot keys, I would also pre-warm or refresh them before expiration.

Q2. Is a distributed lock enough?

No. A lock reduces duplicate rebuilds, but it does not automatically solve every failure mode. I need a lock TTL, ownership semantics, timeout handling, and a strategy for a lock holder that crashes. I also need to avoid making every waiting request hammer Redis with aggressive polling.

For example, waiting requests can use exponential backoff with jitter and then re-check the cache. If stale data is acceptable, I would prefer stale-while-revalidate because it avoids making thousands of requests wait behind a lock.

Q3. Distributed lock vs stale-while-revalidate — which would you choose?

It depends on the consistency requirement. If the value must be fresh before responding, a lock or request coalescing mechanism is appropriate. If bounded staleness is acceptable, stale-while-revalidate is usually better for user-facing high-read traffic because most requests can return immediately while one worker refreshes the value.

Q4. Why is TTL jitter useful?

Without jitter, many entries created at approximately the same time can expire at approximately the same time. That creates synchronized cache misses. Jitter spreads expiration across a time window. However, jitter does not solve a single hot key. For a hot key I still need single-flight, locking, refresh-ahead, or stale-while-revalidate.

Q5. What if Redis itself goes down?

I would assume the cache can fail and design the system so Redis is not the only protection. A local L1 cache can absorb some traffic. The application should also use database concurrency limits, timeouts, circuit breakers, and controlled degradation. The key principle is: a cache failure must not automatically become a database outage.

Q6. What metrics would you monitor?
  • Cache hit ratio by key/category.
  • Redis latency and error rate.
  • Cache miss rate and miss bursts.
  • Number of cache rebuilds per key.
  • Lock acquisition success/failure/wait time.
  • Database connection pool utilization.
  • Database QPS, CPU, I/O, latency and slow queries.
  • Application request latency and timeout rate.
  • Retry rate.
  • Evictions and memory usage.

A particularly useful metric is load amplification: how many backend requests are generated per logical cache miss. A healthy single-flight design should keep this close to one for a hot key.

Q7. How would you explain the design in an interview?

Recommended answer: “I normally use cache-aside with Redis for read-heavy data. The application first checks cache and falls back to the database on a miss. The main issue is that cache-aside alone is unsafe for hot keys because a synchronized expiration can cause a thundering herd. If 10,000 requests miss simultaneously, I don't want 10,000 DB queries. I would use request coalescing locally and distributed single-flight or locking across instances. If the business can tolerate bounded staleness, I prefer stale-while-revalidate so requests continue serving the previous value while one refresh happens in the background. I would also add TTL jitter, pre-warming for predictable hot keys, database concurrency limits, timeouts, and circuit breakers. Finally, I would monitor cache misses, rebuild counts, Redis latency, DB load, lock contention, and retry rates.”

9. Senior Design Checklist

  • Define the source of truth.
  • Choose the caching pattern based on consistency and workload.
  • Define TTL and acceptable staleness.
  • Prevent synchronized expiration with TTL jitter.
  • Protect hot keys with single-flight / distributed coordination.
  • Use stale-while-revalidate when business rules allow it.
  • Consider L1 local cache for extremely hot reads.
  • Pre-warm predictable traffic.
  • Limit database concurrency.
  • Use timeouts and circuit breakers.
  • Control retries with exponential backoff and jitter.
  • Monitor cache and database amplification.
  • Design for Redis failure instead of assuming the cache is always available.

Core takeaway

The senior-level answer is not “use Redis.” Redis only reduces normal read latency. The real design question is what happens when the cache is empty, expired, unavailable, or overloaded.

For the 10,000-request scenario, the key objective is:

10,000 requests → ideally 1 cache rebuild → 1 DB load → Redis → 10,000 cache responses

Then add stale serving, jitter, pre-warming, concurrency limits, timeouts, and circuit breakers according to the consistency and availability requirements.

10. Important Caching Cases Often Missed in Interviews

10.1 Cache Penetration — Requests for Data That Does Not Exist

This is different from cache stampede. The requested key does not exist in the database, so every request misses Redis and then hits the database.

Request product:999999
↓
Redis MISS
↓
DB MISS
↓
Do NOT cache result
↓
Next request repeats the same DB query

Protection: negative caching with a short TTL, Bloom filter for very large key spaces, request validation, and rate limiting.

// Example
product:999999 = NOT_FOUND
TTL = 30 seconds

Typical attack: a client generates millions of random IDs. Redis hit ratio remains low and the database receives most of the traffic.

10.2 Cache Avalanche — Many Keys Expire Together

Cache stampede usually focuses on one hot key. Cache avalanche is broader: a large number of cached keys become unavailable at approximately the same time.

100,000 keys created together
↓
All TTL = 10 minutes
↓
10 minutes later
↓
Huge number of cache misses
↓
Huge DB traffic

Protection: TTL jitter, staggered expiration, refresh-ahead, pre-warming, multiple cache tiers, and backend load protection.

10.3 Hot Key Problem

A hot key is one key receiving a disproportionate amount of traffic. Even if Redis can handle the requests, one logical key can become a bottleneck at the application, network, or Redis shard level.

Examples include:

  • A product during a flash sale.
  • A viral article.
  • A celebrity profile.
  • A global configuration object.
  • A promotion page.

Protection: L1 local cache, replication/read scaling where appropriate, request coalescing, pre-warming, stale-while-revalidate, and sometimes key replication/sharding strategies.

Interview distinction: A hot key is a traffic-distribution problem. A cache stampede is a synchronized-miss problem. They can happen together, but they are not the same thing.

10.4 Cache Inconsistency After a Database Update

Suppose the application updates the database but Redis still contains the old value.

DB = Product price $100
Redis = $100
↓
Update DB → $120
↓
Redis still = $100
↓
Users read stale value

Common strategies include:

  • Cache invalidation after DB update.
  • Update cache after DB update.
  • Transactional Outbox + event-driven cache invalidation.
  • Short TTL when bounded staleness is acceptable.
  • Versioned cache values.

A senior engineer should explicitly define whether stale data is acceptable and for how long.

10.5 The Double-Delete / Race Condition

A classic race can occur when cache invalidation and DB updates happen concurrently.

Request A: update DB
Request B: read DB
Request A: delete cache
Request B: reads old DB value
Request B: writes old value to cache
↓
Cache becomes stale again

Possible solutions include delayed double-delete, versioning, serialized updates, transactional event processing, or an architecture where cache updates are driven from committed database events.

Important: “Delete Redis after UPDATE” is not automatically race-free.

10.6 Cache-Aside Failure Between DB Write and Cache Update

Consider:

1. UPDATE database succeeds
2. Redis SET fails
3. Request returns success

The next request may read stale data from Redis until expiration.

Possible policies:

  • Delete cache after a successful DB write.
  • Retry cache invalidation asynchronously.
  • Publish an invalidation event.
  • Use an outbox so the invalidation event is not lost.

For critical systems, cache invalidation should be treated as a reliable asynchronous operation rather than an optional best-effort side effect.

10.7 Cache-Aside Failure Between Cache Write and Response

The DB request succeeds, but Redis is unavailable. The application should usually still be able to return the DB result.

Redis GET → timeout
↓
Fallback to DB
↓
DB succeeds
↓
Redis SET fails
↓
Return DB result

A cache failure should normally degrade performance, not destroy correctness.

10.8 Redis Failure / Cache Outage

If Redis becomes unavailable, a naive application can send all traffic directly to the database. This can turn a Redis outage into a database outage.

Protection:

  • L1 local cache.
  • Connection and command timeouts.
  • Circuit breaker around Redis.
  • Database concurrency limits.
  • Load shedding.
  • Stale local data where acceptable.
  • Graceful degradation.
Senior principle: Never design “Redis down → every request goes to DB” without checking whether the DB can survive the resulting traffic.

10.9 Cache Serialization / Deserialization Problems

Objects stored in Redis may become incompatible after a deployment.

Example:

Version 1:
Product { id, name, price }

Version 2:
Product { id, name, price, currency }

Problems can occur when old cached payloads are read by new application code.

Protection: versioned cache keys, backward-compatible serialization, explicit schema/version fields, and safe cache invalidation during incompatible releases.

10.10 Cache Key Collision / Poor Key Design

Bad key naming can cause different business objects to share the same key.

user:123
order:123
product:123

Using only 123 would be dangerous. Use namespaces and include important dimensions:

user:v2:123
order:v1:123
product:v3:123

For multi-tenant systems, tenant identity must usually be part of the key:

tenant:{tenantId}:product:{productId}

10.11 Multi-Tenant Cache Isolation

A particularly dangerous production bug occurs when tenant-specific data is cached without tenant identity in the key.

Tenant A → product:123 → cache
Tenant B → product:123 → receives Tenant A data

This is not just a cache performance issue. It can become a serious data-isolation/security problem.

Rule: Every dimension that affects the result must be represented in the cache key or otherwise guaranteed by the cache boundary.

10.12 Cache Memory Pressure / Eviction Storm

Redis can evict keys when memory is exhausted depending on its configured policy. A large eviction event can suddenly reduce the hit ratio and send traffic to the database.

Monitor:

  • Used memory.
  • Evicted keys.
  • Expired keys.
  • Hit/miss ratio.
  • Fragmentation.
  • Memory growth rate.

Do not assume that “Redis has a TTL” means memory usage is automatically safe.

10.13 Large Object / Large Value Problem

Putting very large payloads into Redis can create memory pressure, network latency, serialization overhead, and replication cost.

Instead of caching a 5 MB object for every request, consider:

  • Cache only required fields.
  • Split the object into smaller independently cached parts.
  • Use pagination.
  • Store large blobs in object storage and cache metadata.

10.14 Cache Warming After Restart

After Redis restart, deployment, cluster migration, or mass eviction, the cache can become cold.

If millions of requests arrive immediately, the database can receive a sudden load spike.

Protection: controlled warm-up, background preloading, request rate limiting, and gradual traffic ramp-up.

10.15 Deployment / Cache Versioning

When the cache representation changes, old entries may no longer be valid.

Instead of deleting millions of keys synchronously, use versioned namespaces:

product:v1:123
product:v2:123

Deploy the new version, gradually populate v2, and remove v1 later. This can reduce deployment-time cache storms.

10.16 Negative Cache Becoming Too Sticky

Negative caching protects the DB, but a long negative TTL can hide newly created data.

10:00 → product does not exist
10:00 → cache NOT_FOUND for 10 minutes
10:01 → product is created
10:02 → users still receive NOT_FOUND

Use short TTLs for negative entries and explicitly invalidate them when the entity is created.

10.17 Cache Poisoning / Untrusted Cache Inputs

Never blindly cache data based on untrusted user-controlled input or cache responses that should not be shared.

Be careful with:

  • Authorization-dependent responses.
  • User-specific data.
  • Headers and locale.
  • Query parameters.
  • Permissions and roles.

A cache key must represent all inputs that change the response. Otherwise one user's response can accidentally be served to another user.

10.18 Cache Stampede Caused by Application Restart

Even if Redis is healthy, restarting all application instances can destroy L1 local caches simultaneously.

50 application instances restart
↓
All L1 caches become empty
↓
All instances query Redis
↓
Redis load spikes

If Redis is also cold, the load can propagate to the DB.

Protection: rolling deployments, gradual instance replacement, warm-up, L2 caching, and traffic ramp-up.

10.19 Distributed Cache Lock Contention

A distributed lock can prevent a DB stampede but create a different bottleneck if many requests wait for the same lock.

For a hot key:

10,000 requests
↓
1 request owns lock
↓
9,999 requests waiting
↓
lock holder is slow
↓
large queue / latency

This is why stale-while-revalidate can be preferable when stale data is acceptable. Do not simply replace DB overload with lock contention.

10.20 Lock Expiration While the Owner Is Still Working

Suppose a lock has a 5-second TTL but the DB operation takes 8 seconds. The lock can expire while the first worker is still running. Another worker may acquire the lock and start the same rebuild.

This creates duplicate work and can cause correctness problems.

Production approaches include safe lock ownership, lease renewal where appropriate, fencing/version tokens, or choosing a design that does not require long-held distributed locks.

10.21 Retry Storm

Cache misses, Redis timeouts, DB timeouts, and client retries can multiply traffic.

For example:

10,000 original requests
× 3 automatic retries
≈ 40,000 attempts

Protection: bounded retries, exponential backoff, jitter, retry budgets, deadlines, circuit breakers, and avoiding retries for non-transient failures.

10.22 Cache + Database Transaction Boundary

Redis normally does not participate in the same ACID transaction as the relational database.

Therefore, avoid pretending that:

BEGIN DB TX
UPDATE DB
UPDATE Redis
COMMIT

is one atomic transaction. The cache update can fail independently.

For reliable propagation, transactional outbox + asynchronous cache invalidation is often a better architecture.

10.23 Cache Invalidation Ordering

With asynchronous events, events can arrive out of order.

Update v2 → event v2
Update v3 → event v3
Consumer receives v3 first
Consumer receives v2 later
↓
Cache can accidentally move backward

Use version numbers, timestamps with care, sequence numbers, or idempotent consumers that reject older versions.

10.24 Partial Cache Failure in a Redis Cluster

In a distributed Redis cluster, one shard can have problems while other shards remain healthy. The application may see partial failures rather than a complete outage.

Design for:

  • Timeouts.
  • Retry only when safe.
  • Cluster failover behavior.
  • Hot-key concentration on a shard.
  • Memory imbalance.
  • Monitoring per node/shard.

10.25 When NOT to Cache

Senior engineers should also know when caching is a bad idea.

  • Data is rarely read and expensive to invalidate.
  • Data must always be strongly consistent.
  • Data is extremely large and rarely reused.
  • The backend is already faster than the cache path after serialization/network overhead.
  • Cache complexity is greater than the performance benefit.

A cache adds another failure mode and another consistency boundary. It should solve a measured performance/scalability problem, not be added automatically.

13. Deep-Dive: Production Caching Failure Cases

13.1 Cache Penetration — Detailed Design

Problem: A request asks for a key that does not exist. Because there is no cached value, every request queries the database. If attackers or buggy clients generate random IDs, the cache provides almost no protection.

GET product:ABC123
↓
Redis MISS
↓
DB MISS
↓
No positive cache entry
↓
Next request repeats the same DB query

Solution A — Negative Caching

Cache the fact that the entity does not exist for a short period.

product:ABC123 = NOT_FOUND
TTL = 10–60 seconds

Trade-off: If the product is created immediately after the negative cache is written, users may temporarily receive NOT_FOUND. Therefore the TTL should usually be short, and entity creation can explicitly invalidate the negative key.

Solution B — Bloom Filter

A Bloom filter can quickly answer “this ID definitely does not exist” without querying the database. It is memory-efficient but probabilistic: a false positive is possible, while a false negative should not occur with a correctly maintained filter.

Solution C — Request Validation / Rate Limiting

Reject obviously invalid IDs before reaching Redis or the database. Rate-limit clients that generate abnormal numbers of random IDs.

Senior choice: For normal invalid requests, use short negative caching. For very large key spaces or abuse-prone APIs, combine negative caching with a Bloom filter and rate limiting.

13.2 Cache Avalanche — Detailed Design

Problem: A large population of keys expires at nearly the same time, causing a sudden cache miss wave.

100,000 keys
TTL = exactly 10 minutes
↓
all created around 12:00
↓
12:10
↓
many keys expire together
↓
DB QPS suddenly increases

Solution A — TTL Jitter

baseTTL = 600 seconds
jitter = random(0, 120)

actualTTL = baseTTL + jitter

This spreads expiration over a window instead of synchronizing it.

Solution B — Refresh-Ahead

Refresh frequently used keys before their expiration time. For example, if TTL is 10 minutes, refresh at 8–9 minutes when the key is known to be hot.

Solution C — Pre-Warming

Before a known promotion, preload predictable hot data. This is useful for flash sales, campaign pages, scheduled events, and morning traffic peaks.

Solution D — Backend Protection

Even if the cache becomes cold, the DB must not receive unlimited requests. Use a concurrency semaphore, connection-pool limits, timeouts, circuit breakers, and load shedding.

Senior point: TTL jitter reduces synchronized expiration; it does not protect one extremely hot key. For hot keys, combine it with single-flight or stale-while-revalidate.

13.3 Hot Key — Detailed Design

Problem: One key receives a huge percentage of traffic. Example: a product page receives 500,000 requests/second during a flash sale.

Even if Redis can process high throughput, the same key can become concentrated on one shard or create unnecessary network traffic from every application instance.

Solution A — L1 Local Cache

Application
↓
Caffeine L1
↓ miss
Redis L2
↓ miss
DB

Frequently accessed values can be served directly from application memory. This reduces network latency and Redis QPS.

Solution B — Request Coalescing

If the value is missing locally, only one request should rebuild it while concurrent requests share the result.

Solution C — Pre-Warming

Load predictable hot data before traffic arrives.

Solution D — Hot-Key Replication

In architectures that support it, extremely hot values can be replicated across cache nodes or read replicas to distribute read pressure. This adds operational complexity and invalidation cost.

Senior distinction: Hot key = uneven traffic distribution. Stampede = many requests rebuilding after a miss. A hot key can exist without expiration, and a stampede can happen without a single permanent hot key.

13.4 Cache Consistency — DB and Cache Race Conditions

Consider this common sequence:

T1: update DB → price = $120
T2: read DB → old price = $100
T1: delete Redis
T2: SET Redis = $100
↓
Redis contains stale data again

The problem is not simply “forgot to invalidate.” The real issue is concurrent read/write ordering.

Solution A — Versioned Values

Redis:
product:123 = {
    version: 42,
    price: 120
}

When updating the cache, reject an older version if a newer version is already present.

Solution B — Transactional Outbox

Update the DB and write an outbox event in the same database transaction. A background publisher sends the committed event to a cache-invalidation consumer.

DB transaction
├── update product
└── insert ProductUpdated event
↓ commit
Outbox publisher
↓
Cache invalidation consumer
↓
Redis DEL / SET

This avoids losing the invalidation event if the application crashes after the DB commit.

Solution C — Short TTL

Useful as a safety net, but TTL should not be treated as the primary consistency mechanism when freshness matters.

13.5 Delayed Double Delete

A commonly discussed technique is:

1. Delete cache
2. Update DB
3. Wait briefly
4. Delete cache again

The second delete attempts to remove a stale value that may have been written by a concurrent reader.

However, the delay is heuristic. It does not provide a formal transactional guarantee. The correct delay depends on system latency and concurrency and can still fail in unusual schedules.

Interview answer: Mention delayed double-delete as a practical technique, but do not present it as a perfect consistency guarantee. For stronger guarantees, discuss versioning, serialized updates, transactional outbox, or CDC.

13.6 Redis Failure — Preventing DB Fallback Storm

The dangerous design is:

try Redis
catch RedisException:
    query DB

If 10,000 requests arrive while Redis is down, this can generate 10,000 DB queries.

Better design

Redis timeout
↓
Fast failure / circuit breaker
↓
L1 stale cache?
├─ YES → return stale
└─ NO → bounded DB concurrency
↓
DB timeout
↓
controlled 503

The application should define a maximum number of concurrent fallback DB requests. Excess traffic should wait briefly, use stale data, or fail fast.

Important Configuration

  • Redis connection timeout.
  • Redis command timeout.
  • Bounded connection pools.
  • Circuit breaker.
  • Bulkhead/concurrency isolation.
  • Fallback policy.
  • Observability and alerting.

13.7 Distributed Lock — Correctness Details

A simple Redis pattern is conceptually:

SET product:123:lock requestId NX EX 10

NX means only create the lock if it does not already exist. EX prevents an abandoned lock from remaining forever.

But the lock must be released only by its owner. Never blindly execute:

DEL product:123:lock

because the original lease might have expired and another worker may now own the lock.

A safe release checks ownership using a unique token.

Long-running operation problem

Worker A gets lock for 5 sec
DB operation takes 8 sec
↓
lock expires
↓
Worker B gets lock
↓
A and B both rebuild cache

Possible approaches include lease renewal, fencing tokens, or avoiding long lock ownership entirely through stale-while-revalidate.

Senior answer: A distributed lock is a coordination mechanism, not a magic correctness guarantee. Always discuss ownership, lease expiry, crashes, contention, and bounded waiting.

13.8 Stale-While-Revalidate — Why It Is Often Better

For read-heavy data where a few seconds of staleness is acceptable, do not make thousands of requests wait for a rebuild.

Fresh value
↓
return immediately

Stale but acceptable
↓
return stale immediately
↓
ONE background refresh
↓
DB → Redis

Too old / unavailable
↓
controlled synchronous rebuild

This gives excellent latency and protects the database. The key requirement is a clearly defined freshness policy.

StateAction
FreshReturn immediately.
Stale but within grace periodReturn stale; trigger one refresh.
Expired beyond graceSingle-flight rebuild.
DB unavailable but stale existsServe stale if business rules allow.
No cache and DB unavailableFail gracefully.

13.9 Retry Storm — Detailed Protection

Retries can multiply traffic dramatically.

10,000 original requests
↓
each retries 3 times
↓
up to ~40,000 attempts

Use:

  • Exponential backoff.
  • Random jitter.
  • Maximum retry count.
  • Retry budgets.
  • Request deadlines.
  • Circuit breakers.
  • Do not retry non-transient errors.
delay = min(maxDelay, baseDelay * 2^attempt)
actualDelay = random(0, delay)

The important idea is that retries must be treated as additional traffic. They are not free.

13.10 Multi-Tenant / Authorization-Sensitive Caching

Suppose an endpoint returns data based on tenant and user permissions. A cache key containing only the resource ID can accidentally share data between users.

BAD:
document:123

BETTER:
tenant:42:document:123

Possibly required:
tenant:42:user:88:document:123

The correct key depends on whether the response is tenant-wide, user-specific, role-specific, locale-specific, or permission-specific.

Security rule: Every input that can change the authorization or response must be represented in the cache boundary. A cache hit must never bypass authorization semantics.

13.11 Memory Pressure and Eviction Storm

When Redis reaches its memory limit, keys may be evicted according to the configured policy. A sudden eviction increase can reduce cache hit ratio and amplify DB traffic.

Memory reaches limit
↓
Redis evicts keys
↓
Hit ratio drops
↓
DB traffic increases
↓
DB latency increases
↓
application latency increases

Solutions

  • Set an appropriate maxmemory policy.
  • Monitor memory headroom.
  • Monitor evicted_keys and hit ratio.
  • Control object size.
  • Set TTL for disposable data.
  • Separate critical and disposable cache workloads where appropriate.
  • Scale Redis capacity before sustained memory pressure becomes an outage.

13.12 Large Cache Values

A cache hit is not automatically cheap. A 5 MB Redis value still requires network transfer and deserialization.

Large values can cause:

  • Network bandwidth pressure.
  • Higher Redis latency.
  • Higher JVM allocation and GC pressure.
  • Longer replication time.
  • Higher memory fragmentation.

Prefer smaller payloads, partial objects, pagination, or storing large blobs outside Redis and caching only metadata or references.

13.13 Serialization and Cache Schema Versioning

Deployments can change object structure while old entries remain in Redis.

A robust strategy is versioned cache keys:

product:v1:123
product:v2:123

Deploy the new application version using v2. Old v1 entries can expire naturally or be removed later. This avoids requiring an enormous synchronous cache flush during deployment.

For Java systems, also consider compatibility of JSON, Java serialization, protobuf, or other formats. Avoid native Java serialization for long-lived distributed cache contracts when safer schema-controlled formats are available.

13.14 Cache Warm-Up and Cold Start

A cold cache after Redis restart or deployment can create a sudden backend spike.

Controlled warm-up

  1. Start a small number of application instances.
  2. Warm the most important keys.
  3. Gradually increase traffic.
  4. Monitor DB utilization.
  5. Continue warming less important data asynchronously.

For predictable workloads, maintain a list of top keys based on historical traffic and pre-warm them.

13.15 Cache Invalidation Event Ordering

Suppose two updates happen:

v2 event
v3 event

If the consumer receives v3 first and v2 later, blindly applying events can make the cache move backward.

Solution

if incomingVersion < cachedVersion:
    ignore event
else:
    update cache

This requires the domain event to carry a reliable version or sequence number. Consumers should also be idempotent because duplicate event delivery is common.

13.16 Application Restart and L1 Cache Stampede

With Caffeine L1 + Redis L2, restarting all application instances simultaneously empties every L1 cache.

Even if Redis remains healthy, Redis QPS can suddenly increase. If Redis is also cold, the load propagates further to the DB.

Solution: rolling deployment, gradual instance replacement, startup warm-up, L1 TTL jitter, and controlled traffic ramp-up.

13.17 When NOT to Cache

A senior engineer should challenge unnecessary caching.

Do not automatically cache data when:

  • It is rarely read.
  • It changes extremely frequently.
  • Strong consistency is required.
  • Invalidation is harder than the original DB query.
  • The object is too large.
  • The database query is already cheap and well-indexed.
  • The cache introduces more operational complexity than performance benefit.
Senior principle: Cache only when measured latency, throughput, cost, or scalability requirements justify the additional consistency and failure complexity.

What I would say in a Senior Interview

“I would start with cache-aside because it is simple and gives the application control over caching. But I would not stop there. The failure modes are more important than the happy path. For a hot key, synchronized expiration can create a thundering herd where thousands of requests hit the database simultaneously. If bounded staleness is acceptable, I prefer stale-while-revalidate so requests continue serving a previous value while only one refresh happens. If freshness is mandatory, I use request coalescing or a distributed lease with bounded concurrency.

I also use TTL jitter to prevent mass expiration, negative caching for nonexistent objects, and pre-warming for predictable hot keys. Redis failure must not cause an uncontrolled DB fallback, so I add timeouts, circuit breakers, bulkheads, and a hard DB concurrency limit. For cache consistency, I consider invalidation races, versioned values, and transactional outbox or CDC for reliable propagation. Finally, I monitor cache hit ratio, miss bursts, rebuild amplification, Redis latency, eviction rate, lock contention, DB connection utilization, retries, and end-to-end latency.

The key principle is that a cache is not just a performance layer. It is another distributed-system component with its own consistency, availability, failure, and concurrency problems.”

12. Extra Senior Interview Questions

Q8. What is cache penetration vs cache stampede vs cache avalanche?

Cache penetration: requests repeatedly ask for data that does not exist, so every request can hit the DB.

Cache stampede: many requests miss the same hot cache entry at the same time and all rebuild it.

Cache avalanche: a large population of cache entries becomes unavailable around the same time, creating a broad backend load spike.

Q9. What happens if Redis is healthy but the DB is down?

If the requested data is still cached and acceptable to serve, the application can continue serving cache hits. But cache misses must not blindly retry the unavailable DB. Timeouts, circuit breakers, stale fallback, and controlled degradation are important.

Q10. What is the most dangerous cache bug?

From a security perspective, serving one user's or tenant's data to another because of an incorrect cache key is extremely serious. From a reliability perspective, a cache failure that causes an uncontrolled DB flood is also dangerous. A senior engineer should consider correctness, security, and availability—not only hit ratio.

Q11. Why can adding a cache make a system less reliable?

Because the system now has another dependency, another consistency boundary, serialization overhead, invalidation logic, memory management, and failure modes. If the fallback path is not protected, a cache outage can overload the database. Therefore caching improves performance only when its failure behavior is designed properly.

Q12. How would you design caching for a flash-sale product?

I would treat the product as a hot-key scenario. I would pre-warm the product data, use L1/L2 caching, avoid synchronized TTL expiration, use stale-while-revalidate where acceptable, coalesce rebuilds, and strictly limit DB access. I would also consider whether inventory should be cached at all because inventory correctness and concurrency requirements are different from read-only product metadata. The inventory reservation path should have its own consistency design.

Senior Mental Model

When you see a caching problem, ask these questions in order:

  1. What is the source of truth?
  2. How stale can the data be?
  3. What happens on a cache miss?
  4. What happens when 10,000 requests miss together?
  5. What happens if Redis is down?
  6. What happens if the DB is down?
  7. Can invalidation race with reads/writes?
  8. Can different users/tenants receive the wrong cached response?
  9. Can retries multiply the traffic?
  10. How do we observe and measure the behavior?

This mental model is usually more valuable in a senior interview than memorizing individual caching patterns.

15. Real Production Patterns Used by Large-Scale Companies

15.1 Facebook/Meta — Request Coalescing for Massive Fan-Out

At Meta scale, the cache is not treated as a simple key-value store. Facebook has described using request coalescing to prevent a large number of requests for the same uncached object from reaching the origin simultaneously. In a live-video scenario, the first request can fetch the object while subsequent requests wait and are served after the object reaches the edge cache.

1st request → origin fetch
next 999,999 requests → wait/coalesce
origin response → edge cache
all waiting requests → cache hit

Production lesson: when one object can suddenly become extremely popular, “just add Redis” is insufficient. The cache layer needs to understand duplicate in-flight work.

Interview takeaway: “For a hot object, I would use request coalescing so one request performs the expensive fill while concurrent requests share the result.”

15.2 Facebook/Meta — Multi-Level Caching

Meta has described cache architectures with multiple cache layers for high-scale workloads. For example, its photo infrastructure used cache layers between the user-facing edge and the underlying storage system.

User
↓
Edge cache
↓ miss
Origin cache
↓ miss
Storage

This is a powerful production pattern because the cache hierarchy prevents every request from travelling all the way to the source of truth.

Use case: CDN → application cache → Redis → database/object storage.

Trade-off: every additional layer increases consistency and invalidation complexity.

15.3 Facebook/Meta — Cache Routing and Sharding

At very large scale, cache infrastructure itself becomes a distributed system. Meta built mcrouter to route traffic across many memcached servers and clusters. This illustrates an important production transition: the cache eventually needs its own routing, failure isolation, reconfiguration, and observability layer.

Production lesson: consistent hashing, shard distribution, failure isolation, and online reconfiguration become important when one cache cluster is no longer enough.

Senior interview question: “What happens if one Redis node becomes hot?”

Answer: inspect key distribution and hot keys, because increasing the number of nodes does not automatically solve a single hot key concentrated on one shard.

15.4 Facebook/Meta — Cache Consistency Is a Distributed-Systems Problem

Meta has publicly described cache consistency as a major engineering problem. One important lesson is that cache fill and cache invalidation can race with each other, creating stale values even when the application appears to follow a simple “update DB then invalidate cache” rule.

Reader fills old value
↘
cache ← stale value
↗
Writer invalidates cache

Production lesson: invalidation ordering, versions, race detection, and reliable propagation matter much more than simply choosing Redis versus Memcached.

15.5 Facebook/Meta — Delete Holds to Protect Against Stale Sets

Meta has described a production technique where a delete can temporarily prevent a stale set from repopulating a key. This addresses a subtle race in which an old cache fill arrives after an invalidation.

Old reader starts
↓
Writer deletes cache
↓
Old reader finishes
↓
old value tries SET
↓
delete hold-off blocks stale SET

Why this matters: cache invalidation races can exist even when every individual operation is technically successful.

Interview takeaway: “I would reason about the ordering of cache fill and invalidation, not just the individual commands.”

15.6 Facebook/Meta — Observability at Cache Scale

Meta has described dedicated cache monitoring because diagnosing whether an incident originates in the cache or backend is difficult at scale.

Useful production dashboards include:

  • Hit ratio by cache cluster and key class.
  • Miss rate and miss burst.
  • p50/p95/p99 cache latency.
  • Backend load generated by misses.
  • Eviction rate.
  • Hot-key concentration.
  • Connection utilization.
  • Error and timeout rate.
  • Cache fill latency.

Important metric: cache miss amplification — how much backend work one cache miss creates.

15.7 Facebook/Meta — Flash-Crowd / “Everyone Arrives at Once” Events

Meta has described handling events where millions of users may request the same content simultaneously. This is not the same workload as normal traffic because the arrival rate is synchronized.

Examples in other companies include:

  • Flash sales.
  • Concert ticket releases.
  • Sports finals.
  • Product launches.
  • Breaking news.
  • Limited inventory drops.

Production response: pre-warm important data, use CDN/edge caching, coalesce requests, protect origins with concurrency limits, and gradually admit traffic when necessary.

15.8 Karrot — Probabilistic Early Expiration

Karrot's feature-serving platform, described in an AWS Architecture Blog case study, uses probabilistic early expiration to proactively refresh data likely to be requested again. The system also combines soft and hard TTL concepts, jitter, negative caching, and locking to address cache misses, consistency, stampede, and penetration.

This is a useful real-world example because it demonstrates that mature caching systems often use multiple defenses simultaneously, not one universal pattern.

Normal TTL
↓
probabilistic early refresh
↓
soft TTL
↓
hard TTL
↓
jitter + lock + negative cache

Interview takeaway: “For very high-scale feature serving, I can use probabilistic early refresh instead of waiting for every key to reach exactly the same expiration boundary.”

15.9 AWS / ElastiCache — Monitor TTL Population for Stampede Risk

AWS documentation and architecture guidance highlight that TTL configuration and the population of expiring items are useful signals for identifying potential cache stampedes. If many volatile keys exist and hit ratio suddenly drops, the cache may be entering a synchronized-expiration pattern.

Production lesson: do not monitor only Redis CPU and memory. Monitor the shape of expiration and cache-miss behavior.

15.10 CDN / Edge Caching — Origin Protection

Large-scale video and web systems often put caches close to users. The purpose is not only latency reduction; it is also origin protection.

Millions of clients
↓
Edge cache
↓ only on miss
Origin
↓
Storage

Without the edge layer, a viral object can turn into millions of origin requests. With request coalescing, only a small number of requests need to fetch the object from the origin.

Senior insight: cache architecture should be designed around protecting the slowest and most expensive dependency, not merely making individual requests faster.

15.11 Real-World Pattern — Separate Freshness From Availability

A mature cache design often defines two limits instead of one TTL:

  • Soft TTL: data is preferred to be fresh, but stale data may still be served.
  • Hard TTL: data is too old and cannot be served normally.
0 ───────── 5 min ───────── 10 min ────────→
Fresh Soft-expired Hard-expired
return serve + refresh rebuild/fail

This separation is particularly useful for recommendation systems, product metadata, configuration, and other read-heavy workloads where a few seconds of staleness is much cheaper than a database outage.

15.12 Real-World Pattern — Protect the Database Even When Cache Is Correct

A common mistake is to calculate capacity from cache hit ratio alone.

Example:

1,000,000 requests/sec
99.9% cache hit ratio

Misses = 1,000 requests/sec

That may sound safe. But if each miss causes five downstream queries, the database actually receives:

1,000 × 5 = 5,000 queries/sec

If each query also triggers a remote call, the real amplification is even higher.

Production rule: measure the entire miss path, not just the cache hit ratio.

16. Real Production Scenarios — What Would You Do?

Scenario A — Flash Sale Product

Situation: 500,000 users request the same product page in 2 seconds.

Design:

  1. CDN/edge cache static and cacheable content.
  2. L1 local cache for application-level hot metadata.
  3. Redis for shared product data.
  4. Pre-warm the product before the event.
  5. Use stale-while-revalidate.
  6. Single-flight cache rebuild.
  7. Hard DB concurrency limit.
  8. Keep inventory reservation separate from read-only product metadata.

Why separate inventory? Product description can tolerate staleness. Inventory usually has stricter correctness and concurrency requirements. Treating both as the same cache problem is a design mistake.

Scenario B — Celebrity / Viral Content

Situation: one post suddenly receives millions of reads.

Solution: hot-key detection, edge caching, L1 cache, request coalescing, pre-warming if the event is predictable, and stale serving if acceptable.

The key question is not “Can Redis handle millions of GETs?” It is “What happens when this object is unavailable or changes, and where does the load concentrate?”

Scenario C — Redis Cluster Loses One Shard

Situation: one shard is unavailable while other shards continue serving.

Solution: failover, bounded client timeouts, avoid aggressive retries, detect affected key ranges, use L1/stale fallback, and protect the database from sudden fallback traffic.

Do not assume “cluster = no failure.” A distributed cache can fail partially.

Scenario D — Deployment Changes Cache Schema

Situation: Java service v1 stores one JSON structure. v2 expects a different structure.

Solution: version the cache key, support compatible reads during migration, gradually warm v2, and allow v1 to expire naturally.

Scenario E — Database Is Healthy but Cache Hit Ratio Suddenly Drops

Possible causes:

  • Mass expiration.
  • Eviction storm.
  • Changed key format after deployment.
  • Hot-key workload shift.
  • Cache node failure.
  • TTL changed accidentally.
  • Serialization failures causing cache writes to fail.

Senior debugging sequence: check hit ratio → miss rate → key distribution → eviction → TTL population → Redis latency/errors → application deployment changes → DB QPS.

17. Production Design Rules to Remember

  1. Never assume cache hit ratio alone proves the design is safe.
  2. Protect the origin/DB from cache failure.
  3. Hot keys and stampedes are different problems.
  4. TTL jitter prevents synchronization; it does not solve a single hot key.
  5. Request coalescing is one of the most powerful anti-stampede techniques.
  6. Serve stale data when business requirements allow it.
  7. Use hard limits on backend concurrency.
  8. Cache invalidation is a distributed concurrency problem.
  9. Every response-changing dimension belongs in the cache key.
  10. Version cache schemas when deployments change representations.
  11. Monitor cache misses as a source of backend load amplification.
  12. Pre-warm predictable traffic.
  13. Do not cache by default; cache when the workload justifies the complexity.
