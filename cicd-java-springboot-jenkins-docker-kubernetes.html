1. CI/CD Architecture for a Spring Boot Microservice

This tutorial builds one complete path from a Git commit to a verified Kubernetes rollout. The example uses Java 21, Spring Boot 3.5.16, Maven, Jenkins Pipeline, Docker, and Kubernetes.

What

CI/CD automates integration, validation, packaging, release, deployment, and verification.

Why

Manual deployment is slow, inconsistent, difficult to audit, and easy to break.

When

Use it when a service is released repeatedly, has multiple environments, or needs reliable rollback.

How

Store pipeline and deployment configuration as code, then promote immutable artifacts.

Impact

Faster feedback, smaller releases, repeatable environments, and lower recovery time.

Real case

A bad image fails its readiness probe, the rollout stops, and Jenkins triggers rollback.

Baseline choice
Spring Boot 4.x is the newest major line, but this tutorial uses Spring Boot 3.5.x because it remains a practical migration-friendly baseline for many enterprise systems. Keep your exact versions pinned and upgrade them deliberately.

2. Jenkins, Docker, and Kubernetes: Responsibilities

ComponentMain responsibilityIt should not doFailure impact
JenkinsOrchestrate pipeline stages, credentials, approvals, reports, and deployment commands.Store business data or become a manually configured snowflake.No new release can be built or promoted.
DockerPackage the application and runtime dependencies into an immutable image.Manage a production cluster or application replicas.Images cannot be built, pulled, or started.
RegistryStore versioned images such as order-service:a1b2c3d4.Decide whether an image is safe to deploy.Cluster image pulls fail.
KubernetesSchedule containers, maintain replicas, expose networking, probe health, scale, and roll out changes.Compile source code or replace application-level resilience.Service availability or rollout is affected.

CI versus CD

Continuous Integration validates every change: compile, unit test, integration test, static analysis, and package. Continuous Delivery keeps a releasable artifact ready and usually requires approval for production. Continuous Deployment automatically releases every change that passes all controls.

6. Prepare the Spring Boot Microservice

The downloadable starter contains a small order service, Actuator health endpoints, a unit/integration-style controller test, graceful shutdown, and Prometheus metrics.

Key application settings

spring:
  application:
    name: order-service
  lifecycle:
    timeout-per-shutdown-phase: 25s

server:
  port: ${SERVER_PORT:8080}
  shutdown: graceful

management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  endpoint:
    health:
      probes:
        enabled: true
      show-details: never
  health:
    livenessstate:
      enabled: true
    readinessstate:
      enabled: true

Build and run locally

cd cicd-microservice-starter
mvn clean verify
java -jar target/order-service-0.0.1-SNAPSHOT.jar

curl http://localhost:8080/api/orders/ping
curl http://localhost:8080/actuator/health/liveness
curl http://localhost:8080/actuator/health/readiness

Why probes must be different

  • Startup probe: gives a slow-starting JVM enough time before liveness checks begin.
  • Liveness probe: answers whether the process is irrecoverably unhealthy and should be restarted.
  • Readiness probe: answers whether the Pod should receive traffic now.
Common production mistake
Do not put every external dependency into liveness. A temporary database outage should normally make the Pod unready, not create an endless restart loop.

7. Install Docker Engine on Ubuntu

Use Docker's official APT repository rather than an unofficial distribution package.

# Remove conflicting packages if they exist.
for pkg in docker.io docker-doc docker-compose podman-docker containerd runc; do
  sudo apt-get remove -y "$pkg" 2>/dev/null || true
done

sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings

sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg   -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

. /etc/os-release
echo   "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc]   https://download.docker.com/linux/ubuntu ${UBUNTU_CODENAME:-$VERSION_CODENAME} stable" |
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update
sudo apt-get install -y   docker-ce docker-ce-cli containerd.io   docker-buildx-plugin docker-compose-plugin

sudo systemctl enable --now docker
sudo docker run --rm hello-world

Allow a non-root build agent to use Docker

sudo usermod -aG docker jenkins
sudo systemctl restart jenkins

# Log out/in before testing an interactive user.
docker version
docker info
Security impact
Membership in the docker group is effectively root-level access to the host. It is acceptable for a controlled lab, but production should prefer isolated agents, rootless builders, BuildKit, Kaniko, or another hardened build model.
DOCKER

8. Create a Production-Oriented Dockerfile

# syntax=docker/dockerfile:1.7

FROM maven:3.9.11-eclipse-temurin-21 AS builder
WORKDIR /workspace

COPY pom.xml .
RUN --mount=type=cache,target=/root/.m2     mvn -B -q dependency:go-offline

COPY src src
RUN --mount=type=cache,target=/root/.m2     mvn -B clean verify

FROM eclipse-temurin:21-jre-jammy AS runtime
WORKDIR /app

RUN groupadd --system --gid 10001 appgroup     && useradd --system --uid 10001 --gid appgroup --create-home appuser

COPY --from=builder /workspace/target/*.jar /app/app.jar

USER 10001:10001
EXPOSE 8080

ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75.0 -XX:+ExitOnOutOfMemoryError"

ENTRYPOINT ["java", "-jar", "/app/app.jar"]
Multi-stage build

Maven and source files stay out of the runtime image.

Non-root user

Limits the impact of container compromise.

Immutable artifact

The same image is promoted between environments.

Resource awareness

JVM heap is sized relative to the container memory limit.

Cached dependencies

BuildKit cache reduces repeated Maven downloads.

Graceful shutdown

Kubernetes can drain traffic before terminating the JVM.

Build, inspect, run, and clean up

DOCKER_BUILDKIT=1 docker build -t order-service:local .

docker image ls order-service
docker history order-service:local
docker inspect order-service:local

docker run --name order-service --rm   -p 8080:8080   --memory=512m   --cpus=1   order-service:local

docker logs -f order-service
docker exec -it order-service sh
docker stats order-service
docker stop order-service

docker image prune -f
docker builder prune -f

Tag and push with an immutable version

REGISTRY=docker.io
NAMESPACE=your-dockerhub-user
APP=order-service
TAG=$(git rev-parse --short=12 HEAD)
IMAGE=$REGISTRY/$NAMESPACE/$APP:$TAG

docker tag order-service:local "$IMAGE"
echo "$REGISTRY_PASSWORD" |
  docker login "$REGISTRY" -u "$REGISTRY_USER" --password-stdin
docker push "$IMAGE"
docker logout "$REGISTRY"
Tag strategy
Deploy the Git SHA or image digest. Avoid relying only on latest; it is mutable, difficult to audit, and unsafe for rollback.

15. Configure Jenkins Credentials Safely

Create these credentials under Manage Jenkins → Credentials:

Credential IDTypePurpose
docker-registryUsername with password/tokenPush images to the registry.
kubeconfig-devSecret fileDeploy only to the dev namespace.
kubeconfig-stagingSecret fileDeploy only to the staging namespace.
git-credentialsSSH key or tokenRead a private source repository when SCM integration needs it.

Credential rules

  • Never place passwords directly in a Jenkinsfile.
  • Use separate credentials and permissions per environment.
  • Provision application runtime secrets separately; the pipeline must not apply secret.example.yaml.
  • Mask output and disable shell tracing around secrets.
  • Rotate tokens and remove unused credentials.
  • Prefer workload identity or short-lived credentials over long-lived static keys.
  • Limit who can edit Jenkinsfiles because pipeline code can attempt to access credentials.
PIPELINE

16. Complete Jenkinsfile

The included declarative pipeline performs checkout, test, image build, registry push, Kubernetes apply, rolling update, automatic rollback on rollout failure, and smoke testing.

pipeline {
    agent { label 'docker-kubectl' }

    options {
        timestamps()
        disableConcurrentBuilds()
        buildDiscarder(logRotator(numToKeepStr: '30'))
        timeout(time: 30, unit: 'MINUTES')
    }

    parameters {
        choice(
            name: 'DEPLOY_ENV',
            choices: ['dev', 'staging'],
            description: 'Kubernetes environment to deploy'
        )
    }

    environment {
        APP_NAME = 'order-service'
        REGISTRY = 'docker.io'
        REGISTRY_NAMESPACE = 'your-dockerhub-user'
        K8S_NAMESPACE = "${params.DEPLOY_ENV}"
        IMAGE_REPOSITORY = "${REGISTRY}/${REGISTRY_NAMESPACE}/${APP_NAME}"
    }

    stages {
        stage('Checkout') {
            steps {
                checkout scm
                script {
                    env.GIT_SHA = sh(
                        script: 'git rev-parse --short=12 HEAD',
                        returnStdout: true
                    ).trim()
                    env.IMAGE = "${env.IMAGE_REPOSITORY}:${env.GIT_SHA}"
                }
            }
        }

        stage('Build and Test') {
            steps {
                sh 'chmod +x mvnw || true'
                sh '''
                    if [ -x "./mvnw" ]; then
                      ./mvnw -B clean verify
                    else
                      mvn -B clean verify
                    fi
                '''
            }
            post {
                always {
                    junit allowEmptyResults: true, testResults: '**/target/surefire-reports/*.xml'
                }
            }
        }

        stage('Build Image') {
            steps {
                sh '''
                    docker build                       --label org.opencontainers.image.revision="${GIT_SHA}"                       --label org.opencontainers.image.source="${BUILD_URL}"                       -t "${IMAGE}" .
                '''
            }
        }

        stage('Push Image') {
            steps {
                withCredentials([
                    usernamePassword(
                        credentialsId: 'docker-registry',
                        usernameVariable: 'REGISTRY_USER',
                        passwordVariable: 'REGISTRY_PASSWORD'
                    )
                ]) {
                    sh '''
                        set +x
                        echo "${REGISTRY_PASSWORD}" |
                          docker login "${REGISTRY}"                           --username "${REGISTRY_USER}"                           --password-stdin
                        set -x

                        docker push "${IMAGE}"
                        docker logout "${REGISTRY}"
                    '''
                }
            }
        }

        stage('Deploy to Kubernetes') {
            steps {
                withCredentials([
                    file(credentialsId: "kubeconfig-${DEPLOY_ENV}", variable: 'KUBECONFIG')
                ]) {
                    sh '''
                        set -euo pipefail

                        kubectl apply -f k8s/namespace.yaml
                        kubectl apply -n "${K8S_NAMESPACE}"                           -f k8s/configmap.yaml                                                   -f k8s/service.yaml                           -f k8s/deployment.yaml                           -f k8s/hpa.yaml                           -f k8s/pdb.yaml

                        kubectl -n "${K8S_NAMESPACE}" set image                           deployment/"${APP_NAME}"                           "${APP_NAME}"="${IMAGE}"

                        if ! kubectl -n "${K8S_NAMESPACE}" rollout status                           deployment/"${APP_NAME}" --timeout=5m; then
                          echo "Rollout failed. Rolling back..."
                          kubectl -n "${K8S_NAMESPACE}" rollout undo                             deployment/"${APP_NAME}"
                          kubectl -n "${K8S_NAMESPACE}" rollout status                             deployment/"${APP_NAME}" --timeout=5m
                          exit 1
                        fi
                    '''
                }
            }
        }

        stage('Smoke Test') {
            steps {
                withCredentials([
                    file(credentialsId: "kubeconfig-${DEPLOY_ENV}", variable: 'KUBECONFIG')
                ]) {
                    sh '''
                        set -euo pipefail

                        kubectl -n "${K8S_NAMESPACE}" port-forward                           service/"${APP_NAME}" 18080:80                           > port-forward.log 2>&1 &
                        PF_PID=$!
                        trap 'kill ${PF_PID} || true' EXIT

                        for i in $(seq 1 20); do
                          if curl --fail --silent                             http://127.0.0.1:18080/actuator/health/readiness; then
                            exit 0
                          fi
                          sleep 3
                        done

                        cat port-forward.log
                        exit 1
                    '''
                }
            }
        }
    }

    post {
        always {
            sh 'docker image rm "${IMAGE}" 2>/dev/null || true'
            cleanWs()
        }
        success {
            echo "Successfully deployed ${IMAGE} to ${params.DEPLOY_ENV}"
        }
        failure {
            echo 'Pipeline failed. Check the failed stage and Kubernetes events.'
        }
    }
}

Stage-by-stage reasoning

  1. Checkout: obtains source and derives an immutable Git SHA tag.
  2. Build and Test: prevents broken code from becoming a container image.
  3. Build Image: packages the tested source and records traceability labels.
  4. Push Image: publishes an artifact that Kubernetes nodes can pull.
  5. Deploy: updates only the target Deployment container image.
  6. Rollout Status: blocks until the new ReplicaSet is healthy or times out.
  7. Smoke Test: verifies behavior through the Kubernetes Service.
  8. Cleanup: reduces disk pressure on long-running agents.
Why disable concurrent builds?
Two builds deploying the same environment can race: an older build may finish after a newer build and overwrite it. A better large-scale design also adds environment-level locks or GitOps reconciliation.

Database compatibility rule

During a rolling update, version N and version N+1 can run simultaneously. Use the expand-and-contract approach: add backward-compatible schema first, deploy application changes, migrate data, then remove the old schema only after all old instances are gone.

INCIDENTS

21. Real Deployment Problems and Solutions

1. ImagePullBackOff

What: Node cannot pull the image. Impact: New Pods never start.

kubectl -n dev describe pod POD_NAME
kubectl -n dev get events --sort-by=.lastTimestamp
docker pull docker.io/your-user/order-service:TAG

Typical causes: wrong image/tag, private registry authentication, DNS/TLS problem, architecture mismatch, or registry rate limit. Verify the exact image outside Kubernetes, then configure imagePullSecrets or workload identity.

2. CrashLoopBackOff

What: Container starts and repeatedly exits. Impact: Replica never becomes available.

kubectl -n dev logs POD_NAME --previous
kubectl -n dev describe pod POD_NAME
kubectl -n dev get pod POD_NAME   -o jsonpath='{.status.containerStatuses[*].lastState.terminated.reason}'

Typical causes: missing configuration, bad JVM option, port conflict, migration failure, or OOMKilled. Read the previous container logs and termination reason before changing probes.

3. Readiness probe fails but application looks alive

Impact: Pod runs but receives no Service traffic.

kubectl -n dev exec POD_NAME --   sh -c 'wget -qO- http://127.0.0.1:8080/actuator/health/readiness'
kubectl -n dev port-forward POD_NAME 18080:8080
curl -i http://127.0.0.1:18080/actuator/health/readiness

Check the path, port name, Actuator exposure, security filter rules, startup time, and whether readiness includes an unavailable dependency.

4. Jenkins can build but cannot push

Impact: No deployable image is published.

sudo -u jenkins docker version
sudo -u jenkins bash -lc '
  echo "$REGISTRY_PASSWORD" |
  docker login docker.io -u "$REGISTRY_USER" --password-stdin
'
df -h
docker system df

Check Docker socket permission, token scope, registry hostname, disk space, and whether the secret contains an accidental newline.

5. kubectl works for an admin but Jenkins gets Forbidden

Impact: Deployment stage fails although the cluster is reachable.

KUBECONFIG=/path/to/jenkins-kubeconfig   kubectl auth can-i patch deployment -n dev

KUBECONFIG=/path/to/jenkins-kubeconfig   kubectl auth can-i --list -n dev

This is usually correct RBAC enforcement. Grant only the verbs and resource types needed by the pipeline; do not solve it by giving Jenkins cluster-admin.

6. Rolling update is stuck

kubectl -n dev rollout status deployment/order-service --timeout=2m
kubectl -n dev describe deployment order-service
kubectl -n dev get pods
kubectl -n dev get events --sort-by=.metadata.creationTimestamp
kubectl -n dev rollout undo deployment/order-service

Common causes include insufficient cluster resources, an impossible PodDisruptionBudget, failed probes, image pull errors, quota limits, and scheduling constraints.

7. Node disk is full

df -h
du -xh /var/lib/docker | sort -h | tail
docker system df
docker image prune -af
docker builder prune -af
journalctl --disk-usage

Use scheduled cleanup, ephemeral agents, build retention, registry retention, and log rotation. Avoid uncontrolled pruning on shared production hosts.

8. New release breaks database compatibility

Impact: New and old Pods fail differently during the rolling window.

Rollback may not be enough if the schema is destructive. Use backward-compatible migrations, separate migration execution, pre-deployment backups where appropriate, and an explicit restore or forward-fix plan.

22. Security and Production Hardening

Least privilege

Namespace-scoped Kubernetes RBAC and minimal registry permissions.

Immutable images

Deploy a digest or Git SHA and prevent tag overwrite.

Non-root runtime

Drop Linux capabilities and disable privilege escalation.

Secret isolation

External secret manager, rotation, audit, and no plaintext Git secrets.

Supply chain

Scan, sign, generate SBOMs, and verify provenance.

Network controls

TLS, ingress policy, NetworkPolicy, and controlled egress.

Jenkins-specific hardening

  • Use SSO, authorization matrix, CSRF protection, and audited administrative access.
  • Update Jenkins core and plugins regularly; remove unused plugins.
  • Back up JENKINS_HOME and test restore procedures.
  • Do not expose the controller directly to the internet without a hardened reverse proxy and access controls.
  • Use ephemeral build agents so workspace data and credentials do not persist.
  • Review pull-request trust boundaries before allowing untrusted Jenkinsfiles to run with secrets.

23. Rollback and Recovery Runbook

Application rollback

NAMESPACE=dev
APP=order-service

kubectl -n "$NAMESPACE" rollout history deployment/"$APP"
kubectl -n "$NAMESPACE" rollout undo deployment/"$APP"
kubectl -n "$NAMESPACE" rollout status deployment/"$APP" --timeout=5m
kubectl -n "$NAMESPACE" get pods

Rollback to a specific revision

kubectl -n dev rollout history deployment/order-service --revision=3
kubectl -n dev rollout undo deployment/order-service --to-revision=3

Recovery decision tree

  1. Stop promotion and preserve logs, events, image tag, commit, and deployment revision.
  2. Decide whether the fault is application, configuration, infrastructure, or dependency related.
  3. Rollback only when the previous version remains compatible with current data and schema.
  4. When rollback is unsafe, disable the feature, reduce traffic, or forward-fix.
  5. Verify health, business flow, metrics, and data consistency after recovery.
  6. Document root cause and add a pipeline or platform control that prevents recurrence.
Database warning
Kubernetes rollback changes the container image, not the database. Destructive schema or data changes require a separate recovery plan.

EVOLUTION

25. From Tutorial to Enterprise Platform

  1. Start: Jenkinsfile + Dockerfile + plain Kubernetes YAML.
  2. Standardize: Shared Jenkins libraries, reusable pipeline templates, base images, and policy checks.
  3. Package: Helm chart or Kustomize overlays for environment differences.
  4. Separate deployment: Jenkins builds and signs images; GitOps updates desired state; Argo CD or Flux reconciles the cluster.
  5. Progressive delivery: Canary analysis, automated metric checks, and controlled traffic shifting.
  6. Platform engineering: Self-service templates, golden paths, workload identity, centralized observability, and cost controls.

Jenkins can execute kubectl directly, but GitOps is often safer at scale because the CI system does not need broad live-cluster credentials and every desired-state change is reviewed in Git.

INTERVIEW

27. Senior-Level Interview Questions and Answers

Why should CI build an image only after tests pass?

Because an image is a release candidate. Publishing known-broken artifacts wastes registry space, risks accidental deployment, and weakens trust in the artifact repository. I still keep test evidence and may build earlier only when the image itself is required to run integration tests.

Why is latest a poor production deployment tag?

It is mutable and does not identify a specific source revision. Rollback, audit, cache behavior, and incident correlation become ambiguous. I deploy a Git SHA or immutable digest and add human-readable release metadata separately.

What is the difference between liveness and readiness?

Liveness decides whether Kubernetes should restart the container. Readiness decides whether the Pod should receive traffic. Mixing them can turn a temporary dependency outage into a restart storm.

How do you achieve zero-downtime deployment?

I use at least two replicas, readiness probes, rolling update settings such as maxUnavailable zero, graceful shutdown, compatible API and database changes, enough spare capacity, and verification after rollout. It is not guaranteed by Kubernetes alone.

How do you make rollback reliable?

I preserve immutable images, Deployment history, backward-compatible schema, externalized versioned configuration, and a tested runbook. I also recognize when rollback is unsafe and use feature disablement or forward-fix instead.

Should Jenkins have cluster-admin?

No. Jenkins should use a dedicated identity limited to the target namespace and required resources. At larger scale I prefer GitOps so CI publishes artifacts and desired-state changes, while a cluster-local reconciler performs deployment.
