Deep SQL performance guide

A composite index is useful only when its column order matches the query shape.

This document explains how composite indexes really work, why a query does not need to use every indexed column, when skipping a column reduces efficiency, how equality and range predicates affect index usage, how ORDER BY and covering indexes interact with filters, and how to optimize real SQL using actual execution plans.

Core rule: An index on (A, B, C) remains a composite index even when a query uses only A or A, B. The important question is not whether all columns are used, but whether the query can use the index's leftmost ordered prefix efficiently.

Foundation

1. How a B-tree index works

A B-tree index stores keys in sorted order and uses a balanced tree to navigate quickly from root pages to leaf pages.

Index on (customer_id, status, created_at) Root ├── customer_id 1–1000 ├── customer_id 1001–5000 └── customer_id 5001+ Leaf entries are ordered like: (customer_id=100, status=COMPLETED, created_at=2026-01-02) (customer_id=100, status=PENDING, created_at=2026-01-01) (customer_id=100, status=PENDING, created_at=2026-01-03) (customer_id=101, status=COMPLETED, created_at=2026-01-04)

The index is sorted first by customer_id. Inside the same customer, it is sorted by status. Inside the same customer and status, it is sorted by created_at.

1.1 Why lookup is fast

Instead of scanning every row, the database navigates to the relevant key range, then reads only the matching portion of the index.

1.2 An index does not guarantee usage

The optimizer estimates cost. It may choose:

  • Index seek / index range scan.
  • Index scan.
  • Full table scan.
  • Bitmap/index merge techniques, depending on the database.
Important: “An index exists” and “the optimizer uses it efficiently” are different statements.
Composite index

2. What is a composite index?

CREATE INDEX idx_orders_customer_status_created
ON orders(customer_id, status, created_at);

This is one index containing three ordered columns. It is not three independent indexes.

What it can provide

  • Filtering by the leading columns.
  • Range scanning after equality columns.
  • Potential ORDER BY support.
  • Potential covering/index-only access.

What it does not provide automatically

  • Efficient lookup by every individual column.
  • Efficient filtering when the leading column is missing.
  • Automatic speed improvement for every query.
  • Free performance without write cost.

2.1 Query does not need to use every column

QueryExpected usage
WHERE customer_id = ?Uses the leading part of the index well.
WHERE customer_id = ? AND status = ?Uses a longer prefix.
WHERE customer_id = ? AND status = ? AND created_at > ?Uses equality prefix plus range.
WHERE status = ?Usually not efficient because the leading column is missing.

Senior interview answer

A composite index remains a composite index even when a query does not use all columns. The query can still use the leftmost prefix. For an index on customer_id, status, created_at, filtering by customer_id or by customer_id plus status is normally efficient. Filtering only by status usually is not, because the index is grouped by customer_id first.

Core rule

3. Leftmost-prefix rule

For an index on:

INDEX (A, B, C)

The most natural searchable prefixes are:

(A) (A, B) (A, B, C)

3.1 Good cases

WHERE A = ?

WHERE A = ?
  AND B = ?

WHERE A = ?
  AND B = ?
  AND C >= ?

3.2 Weak cases

WHERE B = ?

WHERE C = ?

WHERE B = ?
  AND C = ?

These conditions omit the leading column A. The matching values are scattered across many A groups.

3.3 Visual intuition

Index sorted by (A, B, C): A=1 B=X C=10 C=20 B=Y C=30 A=2 B=X C=15 B=Y C=40 Searching B=X without A: must inspect B=X under A=1, A=2, A=3, ... Searching A=1 and B=X: one compact continuous range

3.4 Does column order in WHERE matter?

Usually no. These are logically equivalent to the optimizer:

WHERE customer_id = ?
  AND status = ?

WHERE status = ?
  AND customer_id = ?

What matters is index column order, not the text order of predicates in the WHERE clause.

Index ordering

4. Equality columns before range columns

Suppose the common query is:

SELECT id, status, created_at
FROM orders
WHERE customer_id = :customerId
  AND status = :status
  AND created_at >= :start
ORDER BY created_at DESC;

A strong candidate index is:

CREATE INDEX idx_orders_customer_status_created
ON orders(customer_id, status, created_at DESC);
customer_id = equality status = equality created_at = range + sort

4.1 Why range changes later-column usage

After an index range begins, later columns often cannot further narrow the searchable key range in the same way.

INDEX (customer_id, created_at, status)

WHERE customer_id = 100
  AND created_at >= '2026-01-01'
  AND status = 'PENDING'
Use customer_id = 100 Then begin range on created_at status may be checked as residual/index filter but may not narrow the initial range efficiently

4.2 Equality, range, sort, include

A useful design heuristic:

1. Equality filter columns 2. Range filter columns 3. ORDER BY columns 4. Covering/output columns But: - selectivity matters - query frequency matters - database engine matters - actual plan decides
Do not apply this mechanically. There is no universal formula that replaces execution-plan analysis.
Special case

5. What happens when a middle index column is skipped?

Index:

INDEX (customer_id, status, created_at)

Query:

WHERE customer_id = 100
  AND created_at >= '2026-01-01'

The database can normally use customer_id to find the customer range. However, because status is not constrained, the created_at values are grouped separately under each status.

customer_id=100 status=COMPLETED created_at... status=FAILED created_at... status=PENDING created_at... To find created_at >= date for all statuses: the engine may inspect multiple status groups

5.1 Practical conclusion

  • The index may still be used.
  • The leading customer condition remains useful.
  • The skipped middle column can reduce how efficiently later columns define the range.
  • The later column may become an additional filter rather than a full search key.

5.2 Better index for this query pattern

CREATE INDEX idx_orders_customer_created
ON orders(customer_id, created_at);

But do not immediately create both indexes. Check whether one index can support several important queries and whether the write cost is acceptable.

Sorting

6. Composite index and ORDER BY

6.1 Index can avoid sorting

CREATE INDEX idx_orders_customer_created
ON orders(customer_id, created_at DESC);
SELECT id, status, created_at
FROM orders
WHERE customer_id = 100
ORDER BY created_at DESC
LIMIT 20;

The database can find the customer range and read rows already ordered by created_at DESC.

6.2 Why this query is different

SELECT id, status, created_at
FROM orders
ORDER BY created_at DESC
LIMIT 20;

The index on (customer_id, created_at) is ordered by customer first, so it does not provide one global created_at order across all customers.

6.3 Equality unlocks later sort columns

INDEX (customer_id, status, created_at) WHERE customer_id = 100 AND status = 'PENDING' ORDER BY created_at Both leading columns are fixed by equality → created_at order becomes directly usable

6.4 Skipped column can prevent sort optimization

INDEX (customer_id, status, created_at)

WHERE customer_id = 100
ORDER BY created_at

Because rows are grouped by status before created_at, the database may need a separate sort.

6.5 Mixed sort directions

Some databases can scan indexes forward or backward, but mixed direction requirements can still affect usability. Always check the actual plan.

Covering index

7. Covering index and index-only scans

A covering index contains all columns needed by the query.

CREATE INDEX idx_orders_customer_status_created
ON orders(customer_id, status, created_at);
SELECT status, created_at
FROM orders
WHERE customer_id = 100;

The database may answer from the index alone without reading full table rows.

7.1 Benefits

  • Less table I/O.
  • Fewer random lookups.
  • Smaller data pages than the table in some cases.

7.2 Trade-offs

  • Larger index.
  • More write cost.
  • More memory and storage.
  • Database-specific conditions for true index-only access.

7.3 Included columns

Some databases support non-key included columns:

CREATE INDEX idx_orders_customer_created
ON orders(customer_id, created_at)
INCLUDE (status, total_amount);

Included columns can help cover the query without affecting search ordering. Syntax and support differ by database.

Optimizer

8. Selectivity and cardinality

Selectivity describes how much a predicate reduces rows.

High selectivity

Returns a small percentage of the table.

Examples: unique customer ID, order ID, email.

Low selectivity

Returns a large percentage of the table.

Examples: boolean flag, common status, gender field.

8.1 Why status-only index may not help

CREATE INDEX idx_orders_status
ON orders(status);

If 70% of rows are COMPLETED, the optimizer may prefer a table scan because reading most index entries plus table rows is more expensive.

8.2 Status combined with a selective column

CREATE INDEX idx_orders_customer_status
ON orders(customer_id, status);

Even if status has low cardinality, the combination may be highly selective within one customer.

8.3 Data distribution matters

Tenant A: 100 rows Tenant B: 100 million rows Same SQL + same index may produce different costs due to skew

Use realistic parameters when analyzing plans.

Specialized index

9. Partial or filtered indexes

If a query frequently accesses a small subset, a partial index can be smaller and more selective.

CREATE INDEX idx_pending_orders_created
ON orders(created_at)
WHERE status = 'PENDING';

9.1 Good use case

SELECT *
FROM orders
WHERE status = 'PENDING'
ORDER BY created_at
LIMIT 100;

If only 1% of orders are pending, the index is compact and efficient.

9.2 Limitations

  • Database support and syntax differ.
  • The query predicate must match the index condition.
  • Too many specialized indexes increase maintenance complexity.
Evidence

10. Read the actual execution plan

10.1 Do not decide from SQL text alone

EXPLAIN ANALYZE
SELECT id, status, created_at
FROM orders
WHERE customer_id = 100
  AND status = 'PENDING'
ORDER BY created_at DESC
LIMIT 20;

10.2 What to check

Plan detailQuestion
Access methodIndex seek/range scan, index scan, or table scan?
Index conditionWhich predicates define the searchable range?
Filter/residual conditionWhich predicates are checked after rows are found?
Estimated rowsWhat did the optimizer expect?
Actual rowsWhat really happened?
Rows removed by filterDid the index return too many candidates?
Sort operationCould the index have avoided it?

10.3 Example interpretation

Index range: customer_id = 100 Residual filter: created_at >= 2026-01-01 Meaning: Index helps find customer rows, but created_at did not fully narrow the index range, possibly because status was skipped.

10.4 Estimated vs actual row mismatch

A major mismatch can indicate:

  • Stale statistics.
  • Highly skewed data.
  • Correlated columns not understood by basic statistics.
  • Parameter-sensitive plan behavior.
Optimization cases

11. Practical query optimization cases

11.1 Function on indexed column

Less index-friendly

WHERE DATE(created_at) = :date

Range predicate

WHERE created_at >= :start
  AND created_at < :nextDay

11.2 Implicit type conversion

-- customer_id is numeric, but parameter is string
WHERE customer_id = '100'

Type mismatch may prevent efficient index usage depending on conversion direction and database.

11.3 Leading wildcard

WHERE name LIKE '%huy%'

A normal B-tree generally cannot seek efficiently from an unknown prefix. Consider full-text search, trigram indexes, or a search engine when substring search is required.

11.4 Prefix search

WHERE name LIKE 'Huy%'

A prefix search may use a suitable index because the beginning of the key is known.

11.5 OR conditions

WHERE customer_id = ?
   OR status = 'PENDING'

The optimizer may use index union/bitmap operations or may scan. Sometimes splitting with UNION ALL is better, but only if semantics and duplicate handling are correct.

11.6 SELECT *

Returning every column increases table reads, network transfer, serialization, and prevents covering access.

SELECT id, status, created_at
FROM orders
WHERE customer_id = ?;

11.7 Too many rows

An efficient index cannot make returning 10 million rows cheap. Add pagination, aggregation, export streaming, or a reporting design.

11.8 Computed expressions

If a function is required frequently, consider a function-based/expression index where supported, or store a normalized/search column.

11.9 Negative predicates

WHERE status <> 'COMPLETED'

Negative conditions often match large, scattered portions of the index. A partial index for active statuses or a more selective query can work better.

11.10 Null predicates

WHERE processed_at IS NULL

If null rows are a small active subset, a partial index can be highly effective.

Joins

12. Composite indexes for joins

12.1 Join plus filter

SELECT o.id, p.status
FROM orders o
JOIN payments p ON p.order_id = o.id
WHERE o.customer_id = ?
  AND p.status = 'COMPLETED';

Possible useful indexes:

orders(customer_id, id)
payments(order_id, status)

12.2 Which side should lead?

It depends on the optimizer's join order and cardinality. If customer filtering returns very few orders, the database may use nested-loop lookups into payments by order_id.

12.3 Foreign-key indexes

Foreign-key columns often need indexes for joins and parent-row updates/deletes, but exact requirements differ by database and workload.

12.4 Many-to-many explosion

No index can fully solve an accidental row multiplication caused by joining multiple one-to-many relationships. Fix the query shape, aggregate separately, or split the query.

Pagination

13. Offset versus keyset pagination

13.1 Offset pagination

SELECT id, created_at
FROM orders
WHERE customer_id = ?
ORDER BY created_at DESC, id DESC
OFFSET 100000 ROWS FETCH NEXT 20 ROWS ONLY;

The database must still locate and skip many rows.

13.2 Keyset pagination

SELECT id, created_at
FROM orders
WHERE customer_id = ?
  AND (created_at, id) < (:lastCreatedAt, :lastId)
ORDER BY created_at DESC, id DESC
FETCH FIRST 20 ROWS ONLY;

Supporting index:

CREATE INDEX idx_orders_customer_created_id
ON orders(customer_id, created_at DESC, id DESC);

13.3 Why include a tie-breaker

created_at may not be unique. Adding id gives deterministic ordering and prevents missing/duplicate rows between pages.

Trade-offs

14. Every index has a write cost

INSERT

Each index receives a new entry and may cause page split or maintenance.

UPDATE

Changing an indexed column updates the index entry.

DELETE

Index entries must be removed or marked for cleanup.

14.1 Costs to consider

  • Storage.
  • Memory/cache usage.
  • Write latency.
  • Vacuum/maintenance/rebuild time.
  • Backup and replication volume.

14.2 Overlapping indexes

INDEX (customer_id)
INDEX (customer_id, status)
INDEX (customer_id, status, created_at)

Some indexes may be redundant, but not always. A smaller index can still be cheaper for certain queries. Use usage statistics and plans before removing one.

Senior interview

16. Interview questions and senior answers

1. If a query does not use every column in a composite index, can the index still be used?

Yes. A query can use the leftmost prefix. For an index on A, B, C, predicates on A or A and B can normally use it efficiently. Using all columns is not required.

2. Why is an index on A, B, C usually weak for WHERE B = ?

Because entries are grouped first by A. Values of B are distributed under every A group, so the optimizer cannot usually navigate to one compact B range without scanning many index sections.

3. What happens when the query uses A and C but skips B?

The database can normally use A to locate a range. C may still be evaluated from the index, but because values are grouped by B before C, C may not fully narrow the initial range. I confirm through the execution plan.

4. Does WHERE predicate order need to match index order?

No. SQL predicate text order is not the same as index key order. The optimizer can reorder predicates. The defined index column order and query semantics are what matter.

5. Why place equality columns before range columns?

Equality predicates reduce the index to one ordered subgroup. A range can then scan a continuous section. Once a range begins, later columns often cannot narrow the searchable range as efficiently.

6. How can a composite index support ORDER BY?

If leading index columns are fixed by equality and the remaining key order matches ORDER BY, the database may return rows already sorted. If an unfixed column appears before the sort column, a separate sort may still be required.

7. What is a covering index?

It contains all columns needed by a query, allowing the database to avoid table-row lookups in suitable cases. The trade-off is a larger index and higher write cost.

8. Why may a status-only index not be used?

Status often has low cardinality. If one value matches a large percentage of the table, scanning the table can be cheaper than reading many index entries plus table rows.

9. How do you choose composite index column order?

I start from important query patterns: equality filters, range filters, join columns, ORDER BY, LIMIT, selectivity, and output columns. Then I validate with the actual execution plan and realistic data. I do not use one universal ordering rule blindly.

10. Can an index make writes slower?

Yes. Every insert, update, and delete may need index maintenance. More indexes increase storage, memory pressure, replication volume, and maintenance time.

11. Why is SELECT * bad for index-only access?

The index rarely contains every table column, so the database must fetch table rows. Selecting only required columns improves I/O, network, serialization, and the chance of covering access.

12. What is the difference between index seek and index scan?

A seek/range scan navigates directly to a narrow key range. An index scan reads a large portion or all of the index. A scan may still be better than a table scan if the index is smaller, but it is not the same as selective lookup.

13. Why can DATE(created_at) prevent index use?

The function transforms every column value before comparison, so the normal ordered key may not be directly searchable. A range predicate on the raw column is usually more index-friendly, or a function-based index may be considered.

14. When would you use a partial index?

When a frequently queried subset is small and stable, such as active or pending rows. A partial index can be much smaller and more selective than a full-table index.

15. Offset or keyset pagination?

Offset is simple but becomes expensive for deep pages. Keyset pagination uses the last ordered key and a matching composite index, giving more stable performance and consistency for large datasets.

16. What would a senior engineer check before adding an index?

I capture the exact query and parameters, inspect the actual plan, check selectivity, data distribution, rows examined, sort and join behavior, then estimate write and storage cost. I test with production-like data and monitor after release.

Final senior answer

A composite index is one ordered structure, so column order defines which query shapes are efficient. Queries do not need to use every column, but they usually need the leading prefix. Equality predicates normally come before range and sort columns, while skipped middle columns can reduce later-column usefulness. I verify all of this with actual execution plans, realistic parameter distributions, and write-cost measurement rather than relying only on theory.
