Foundation

1. ACID in practical systems

Atomicity

All operations in one transaction succeed together or fail together.

Example: debit account, credit account, and write ledger entry must not partially commit.

Consistency

A transaction moves the database from one valid state to another valid state.

Example: balance cannot become negative when the business rule forbids it.

Isolation

Concurrent transactions should not observe or create results that violate the selected isolation guarantees.

Example: two payment requests must not both spend the same available amount.

Durability

After commit succeeds, data should survive process restart or system failure according to the database durability configuration.

Example: a committed order should still exist after the application restarts.

1.1 Atomicity is not distributed rollback

Local database transaction: A, B, C database statements ↓ commit together or rollback together Distributed workflow: Order DB + Payment Provider + Inventory Service ↓ No normal local transaction can roll back all systems ↓ Use Saga, Outbox, idempotency, retries, and compensation
Important: @Transactional protects resources managed by the same transaction manager. It does not automatically roll back an HTTP call, Kafka publish, S3 upload, or another microservice.

1.2 Consistency belongs to both database and application

  • Database constraints: primary key, foreign key, unique constraint, check constraint, not-null.
  • Application invariants: order status transitions, payment amount rules, tenant ownership.
  • Transaction boundaries: related writes commit together.
  • Concurrency control: locking, optimistic versioning, atomic SQL.
ALTER TABLE payment
ADD CONSTRAINT uk_payment_order UNIQUE (order_id);

ALTER TABLE account
ADD CONSTRAINT ck_balance_non_negative CHECK (balance >= 0);

Senior interview answer

ACID describes transaction guarantees, but I do not rely only on application checks. I protect invariants at multiple layers: transaction boundaries for atomicity, database constraints for consistency, isolation and locking for concurrent correctness, and durable storage configuration for commit persistence. For distributed workflows, I explicitly switch from ACID thinking to Saga, Outbox, idempotency, and compensation.

Transactions

2. Transaction boundaries in Java and Spring

2.1 Put the boundary around a business unit

@Service
public class TransferService {

    @Transactional
    public void transfer(
            long fromAccountId,
            long toAccountId,
            BigDecimal amount
    ) {
        Account from = accountRepository.findForUpdate(fromAccountId);
        Account to = accountRepository.findForUpdate(toAccountId);

        from.debit(amount);
        to.credit(amount);

        transferRepository.save(
                new Transfer(fromAccountId, toAccountId, amount)
        );
    }
}

The transaction boundary belongs around the complete business operation, not around every repository method separately.

2.2 Common rollback mistakes

Swallowing exceptions

@Transactional
public void process() {
    try {
        repository.save(...);
        externalStep();
    } catch (Exception ex) {
        log.error("failed", ex);
        // Method returns normally, so Spring may commit.
    }
}

Self-invocation

@Transactional
public void outer() {
    innerRequiresNew(); // call does not pass through proxy
}

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void innerRequiresNew() {
}

2.3 Avoid long transactions

Do not keep a database transaction open while waiting for a slow external API unless the requirement clearly demands it. Long transactions hold locks, connections, snapshots, and memory.

Bad: Begin transaction → update DB → call payment API for 8 seconds → update DB Commit Better: Short DB transaction stores pending state + outbox → external call outside long lock window → next short transaction updates final state

2.4 Read-only transactions

@Transactional(readOnly = true)
public OrderResponse getOrder(long id) {
    return repository.findById(id)
            .map(mapper::toResponse)
            .orElseThrow(OrderNotFoundException::new);
}

readOnly = true is a hint to Spring, ORM, and sometimes the database driver. It does not guarantee that the database will reject all writes.

Spring / Spring Data

3. Spring @Transactional deep dive and special cases

Main principle: @Transactional defines the transaction boundary and transaction rules for one unit of work. It does not mean that every method must have its own transaction, and it does not make non-database side effects rollback automatically.

3.1 What Spring does when a transactional method is called

1
Call enters a Spring proxy
The proxy reads transactional metadata.
2
Choose a transaction manager
For example, JpaTransactionManager or DataSourceTransactionManager.
3
Create, join, suspend, or reject a transaction
The behavior depends on propagation.
4
Run the method
Repositories and the persistence context participate in the transaction.
5
Commit or roll back
Spring applies rollback rules when the method exits.
6
Release resources
Connections, sessions, and transaction-bound resources are cleaned up.
The annotation is metadata. Transaction behavior works only when transaction management is enabled and the invocation passes through the relevant Spring proxy or AspectJ advice.

3.4 Class-level and method-level configuration

@Service
@Transactional(readOnly = true)
public class CustomerService {

    public CustomerResponse find(long id) {
        return load(id);
    }

    @Transactional
    public void changeEmail(long id, String email) {
        Customer customer = repository.findById(id).orElseThrow(...);
        customer.changeEmail(email);
    }
}

The more specific method-level annotation overrides the class-level settings. A common style is class-level readOnly = true for a query service and method-level read-write annotations for commands.

3.5 Where should the transaction boundary be?

Recommended: application/service layer

@Transactional
public void createOrder(CreateOrderCommand command) {
    Customer customer = customerRepository.get(command.customerId());
    Order order = Order.create(customer, command.items());
    orderRepository.save(order);
    outboxRepository.save(OrderCreatedOutbox.from(order));
}

The transaction covers the complete business unit across multiple repositories.

Too narrow: every repository call separately

customerRepository.save(customer); // T1
orderRepository.save(order);       // T2
outboxRepository.save(event);      // T3

A failure after T1 can leave partial business state.

3.6 Transaction behavior in Spring Data JPA repositories

  • Inherited CRUD read methods use repository transaction configuration with readOnly = true.
  • Inherited non-read CRUD methods use a normal read-write transaction.
  • Custom declared query methods do not automatically receive transaction configuration.
  • For multi-repository business work, an outer service/facade transaction should normally define the real boundary.

Custom read query

@Transactional(readOnly = true)
public interface UserRepository extends JpaRepository<User, Long> {

    List<User> findByLastName(String lastName);
}

Modifying query

@Modifying(clearAutomatically = true, flushAutomatically = true)
@Transactional
@Query("""
    update User u
       set u.active = false
     where u.lastLoginAt < :cutoff
""")
int deactivateInactiveUsers(Instant cutoff);
A bulk JPQL update bypasses normal entity dirty checking and can leave already-managed entities stale. Consider flushing before it and clearing or refreshing the persistence context afterward.

3.7 readOnly = true is a hint, not a security rule

It can allow JDBC or ORM optimizations. With Hibernate, it can reduce dirty-checking work. However, it is not a universal guarantee that all databases will reject every write.

Do not rely on readOnly = true to enforce permissions. Authorization and database privileges are separate concerns.

3.8 Rollback rules

Runtime exception: rolls back by default

@Transactional
public void createOrder() {
    repository.save(...);
    throw new IllegalStateException("Validation failed");
}

Checked exception: does not roll back by default

@Transactional(rollbackFor = IOException.class)
public void importOrders(Path path) throws IOException {
    repository.save(...);
    readFile(path);
}

Do not roll back for a specific exception

@Transactional(noRollbackFor = NotificationFailedException.class)
public void completeRegistration() {
    userRepository.save(...);
    notificationService.send(...);
}
Use noRollbackFor carefully. Committing after an exception is correct only when the exception represents an acceptable secondary failure and the committed state remains valid.

3.9 Swallowed exception problem

@Transactional
public void process() {
    try {
        taskA();
        taskB();
    } catch (RuntimeException ex) {
        log.error("Failed", ex);
        // The proxy sees a normal return unless the transaction
        // was already marked rollback-only.
    }
}

Safer options:

  • Rethrow when the whole transaction must fail.
  • Move optional work to an independent transaction.
  • Use a result object for expected business outcomes rather than exceptions.
  • Call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly() only when explicit programmatic rollback is genuinely required.

3.10 Multi-task case 1 — A, B, and C must all roll back

executeTask() — transaction T1 ├── A joins T1 ├── B joins T1 │ ├── B1 joins T1 │ └── B2 joins T1 └── C joins T1 Any unhandled rollback exception ↓ A + B + B1 + B2 + C all roll back
@Transactional
public void executeTask() {
    taskA.execute();
    taskB.execute();
    taskC.execute();
}

This is the simplest and safest design when all steps form one local atomic business unit.

3.11 Multi-task case 2 — A and C roll back, but B remains committed

B must run in a separate physical transaction using REQUIRES_NEW. Put B in another Spring bean so the call passes through the proxy. 

@Service
public class TaskCoordinator {

    private final IndependentBService bService;

    @Transactional
    public void execute() {
        taskA();          // T1
        bService.runB();  // T2
        taskC();          // T1

        throw new RuntimeException("Outer task failed");
    }
}

@Service
public class IndependentBService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void runB() {
        taskB();
        taskB1();
        taskB2();
    }
}
T1 starts A writes T1 is suspended T2 starts B + B1 + B2 write T2 commits T1 resumes C writes outer failure T1 rolls back Result: A = rolled back C = rolled back B/B1/B2 = committed
REQUIRES_NEW needs an additional database connection while the outer transaction keeps its resources. Heavy concurrent use can exhaust the connection pool.

3.12 Multi-task case 3 — Roll back only B, continue A and C

Option A: independent B transaction

@Transactional
public void execute() {
    taskA();

    try {
        independentBService.runB(); // REQUIRES_NEW
    } catch (RuntimeException ex) {
        log.warn("B failed; continue with C", ex);
    }

    taskC();
}

If B fails, T2 rolls back. The outer T1 can continue because B's rollback-only state does not belong to T1.

Option B: nested savepoint

@Transactional
public void execute() {
    taskA();

    try {
        nestedBService.runB(); // NESTED
    } catch (RuntimeException ex) {
        log.warn("Rolled back to savepoint", ex);
    }

    taskC();
}

@Transactional(propagation = Propagation.NESTED)
public void runB() {
    taskB();
}

NESTED uses a savepoint inside one physical transaction. B can roll back to the savepoint while the outer transaction continues. If the outer transaction later rolls back, A, B, and C are all ultimately rolled back.

3.13 Why catching an exception from REQUIRED may still fail

@Transactional
public void outer() {
    try {
        requiredService.inner(); // joins same T1
    } catch (RuntimeException ex) {
        log.warn("Continue", ex);
    }

    repository.save(...);
}

If inner() marked the shared physical transaction rollback-only, catching the exception does not restore the transaction. The outer method may later receive UnexpectedRollbackException when it tries to commit.

Catching an exception is not the same as creating a partial rollback boundary. Separate the work with REQUIRES_NEW or a supported nested savepoint when partial behavior is required.

3.14 Multi-task case 4 — Each item commits independently

Useful for batch jobs where one bad item should not roll back 999 successful items.

@Service
public class BatchCoordinator {

    private final ItemWorker worker;

    public BatchResult process(List<Item> items) {
        BatchResult result = new BatchResult();

        for (Item item : items) {
            try {
                worker.processOne(item);
                result.success(item);
            } catch (RuntimeException ex) {
                result.failure(item, ex);
            }
        }

        return result;
    }
}

@Service
public class ItemWorker {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void processOne(Item item) {
        repository.save(map(item));
    }
}

Also consider Spring Batch chunk transactions, restartability, retry, and skip policies.

3.15 Multi-task case 5 — Dynamic transaction boundaries with TransactionTemplate

Annotations are best for stable method boundaries. Programmatic transactions are clearer when a loop needs one transaction per item or the boundary is dynamic. 

public class ItemProcessor {

    private final TransactionTemplate transactionTemplate;

    public ItemProcessor(PlatformTransactionManager transactionManager) {
        this.transactionTemplate = new TransactionTemplate(transactionManager);
    }

    public void process(List<Item> items) {
        for (Item item : items) {
            transactionTemplate.executeWithoutResult(status -> {
                repository.save(map(item));
            });
        }
    }
}

  • Move the transactional method to another bean.

3.18 @Async, threads, and transactions

Imperative Spring transactions are normally bound to the current thread. Starting asynchronous work does not make that work participate in the caller's transaction. 

@Transactional
public void createOrder() {
    orderRepository.save(...);
    asyncService.sendEmail(); // executes later on another thread
}

The async method should define its own transaction if it performs database work. It also needs to handle the case where the outer transaction later rolls back.

For work that must occur only after a successful commit, publish a transaction-bound event or use a transactional outbox.

3.19 Transaction-bound events

@Transactional
public OrderId createOrder(CreateOrderCommand command) {
    Order order = orderRepository.save(...);
    eventPublisher.publishEvent(new OrderCreatedEvent(order.getId()));
    return order.getId();
}

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void afterOrderCommitted(OrderCreatedEvent event) {
    notificationQueue.publish(event.orderId());
}
PhaseUse
BEFORE_COMMITRun before commit while transaction outcome is not final.
AFTER_COMMITRun only after successful commit.
AFTER_ROLLBACKReact only to rollback.
AFTER_COMPLETIONRun after commit or rollback.

If no transaction exists, a transactional event listener is not called by default unless fallbackExecution = true.

3.20 External API calls inside a transaction

Problem: DB transaction starts → row locks acquired → call provider → provider takes 10 seconds → connection and locks stay occupied Consequences: pool exhaustion lock contention deadlocks timeout ambiguity long rollback work

Better patterns:

  • Pending state + external call + final state in separate short transactions.
  • Transactional Outbox for reliable messaging.
  • Saga for multi-service workflows.
  • Provider and application idempotency keys.
  • Reconciliation when timeout does not reveal final provider outcome.

3.21 Multiple transaction managers and multiple databases

@Transactional(transactionManager = "orderTransactionManager")
public void updateOrderDatabase() {
}

@Transactional(transactionManager = "auditTransactionManager")
public void updateAuditDatabase() {
}
Two local transaction managers do not automatically create one atomic transaction across two databases. One can commit while the other fails. Use a justified distributed transaction mechanism or redesign with Outbox/Saga/eventual consistency.

3.22 Timeout

@Transactional(timeout = 5)
public void rebuildSummary() {
    // Transaction infrastructure may abort after the configured limit.
}

A transaction timeout is not a complete API timeout strategy. Also configure query, lock, HTTP-client, and request timeouts at the correct layers.

3.23 Isolation on inner methods

@Transactional(isolation = Isolation.READ_COMMITTED)
public void outer() {
    innerSerializable(); // joins existing transaction with REQUIRED
}

@Transactional(isolation = Isolation.SERIALIZABLE)
public void innerSerializable() {
}

The inner method cannot normally change the isolation of an already-running physical transaction. Use a genuinely new transaction when different isolation is required, and ensure the database and transaction manager support the configuration.

3.25 Additional transaction interview questions

Why is the service layer usually the best transaction boundary?

A business use case often calls multiple repositories and changes multiple aggregates or records. A service-level transaction can make those changes atomic. Repository-level transactions are usually too narrow and cannot express the complete business unit.

What is the difference between logical and physical transactions?

Multiple methods with REQUIRED can each have a logical transaction scope while sharing one physical database transaction. If an inner logical scope marks rollback-only, the shared physical transaction cannot later commit.

What causes UnexpectedRollbackException?

An inner participant in a shared transaction marks it rollback-only, but the outer caller catches the exception or otherwise attempts to commit. Spring throws the exception so the caller is not incorrectly told that commit succeeded.

Can Spring roll back only some statements in one transaction?

A normal transaction commits or rolls back as one physical unit. Partial rollback needs savepoints through NESTED, or separate physical transactions through REQUIRES_NEW. The two approaches have different final-rollback behavior.

Why is REQUIRES_NEW risky in high traffic?

The outer transaction retains its connection while the inner transaction obtains another connection. With many concurrent threads, the pool may be exhausted and threads can wait for connections held by each other.

Should every repository method have @Transactional?

No. Spring Data already configures inherited CRUD methods, while custom query methods may need explicit settings. More importantly, the business use-case transaction should usually be declared at the service or facade boundary.

Why can a modifying query make JPA entities stale?

Bulk JPQL or SQL operates directly in the database and bypasses normal per-entity dirty checking. Entities already loaded in the persistence context may still contain old values until they are cleared or refreshed.

Does readOnly = true guarantee no writes?

No. It is primarily a hint for drivers and ORM optimizations. Some databases may enforce it, but application authorization and database privileges must not depend on that assumption.

How do transactions behave with @Async?

The caller's thread-bound transaction does not automatically move to the async thread. The async worker should define its own transaction and should not assume the caller committed successfully unless the work is triggered after commit.

When would you use TransactionTemplate?

I use it when the transaction boundary is dynamic, such as one transaction per loop item, or when annotation-based method boundaries make control flow less clear. For stable service methods, declarative transactions remain simpler.

How do you make email or Kafka publication happen only after commit?

For local lightweight behavior, a transaction-bound event can run after commit. For reliable distributed publication, I prefer the Transactional Outbox because an in-memory event can be lost if the process stops after commit.

Senior interview answer

I define Spring transactions around business units, usually in the application service, and let repository calls participate. I understand that REQUIRED methods share one physical transaction, so catching an inner exception does not necessarily make the transaction healthy again. For independent commit I use REQUIRES_NEW; for savepoint-based partial rollback I use NESTED only when the transaction manager supports it.

I also consider proxy boundaries, checked-exception rollback rules, connection-pool impact, read-only semantics, JPA persistence-context staleness after bulk updates, async thread boundaries, and after-commit event behavior. For external systems, I do not pretend a local annotation provides distributed rollback; I use idempotency, Outbox, Saga, and reconciliation.

4. Isolation levels and anomalies

3.1 The main anomalies

AnomalyMeaningProject example
Dirty ReadTransaction B reads uncommitted data written by A.B shows a payment as completed, but A later rolls back.
Non-repeatable ReadThe same row returns different committed values inside one transaction.Order status is PENDING at first read and CANCELLED at second read.
Phantom ReadRepeating a range query returns additional or missing rows.First count finds 5 active coupons; another transaction inserts one; second count finds 6.
Lost UpdateTwo transactions read the same value and one overwrites the other's update.Two requests both read stock=10, subtract 1, and both write stock=9.
Write SkewTransactions update different rows after reading a shared condition, breaking an invariant.Two doctors independently go off-call, leaving no doctor available.

3.2 Isolation-level summary

Isolation levelDirty readNon-repeatable readPhantomTypical use
READ UNCOMMITTEDPossiblePossiblePossibleRare in business systems; weak correctness.
READ COMMITTEDPreventedPossiblePossibleCommon default; good balance for many CRUD systems.
REPEATABLE READPreventedPrevented for repeated row readsDatabase-specific behaviorLonger consistent reads and some concurrency protection.
SERIALIZABLEPreventedPreventedPrevented logicallyCritical invariants when retry cost is acceptable.
Database-specific behavior matters. The SQL isolation names are standard concepts, but real behavior differs by database engine and MVCC/locking implementation. Always validate against the actual database used in production.

3.3 READ COMMITTED

Each statement usually sees data committed before that statement begins. Two SELECT statements in one transaction may observe different committed versions.

T1: SELECT status → PENDING T2: UPDATE status = PAID; COMMIT T1: SELECT status → PAID

3.4 REPEATABLE READ

A transaction gets a more stable view. Re-reading the same row normally returns the same version. However, exact phantom and write-conflict behavior depends on the database.

3.5 SERIALIZABLE

The database attempts to provide a result equivalent to transactions running one at a time. This can reduce concurrency and may abort transactions that must be retried.

Senior approach: SERIALIZABLE is not “always safest.” It is safest only if the application correctly handles serialization failures, retries idempotently, and accepts lower concurrency.

3.6 Lost update is often solved explicitly

Option A — Atomic SQL update

UPDATE inventory
SET quantity = quantity - :requested
WHERE product_id = :productId
  AND quantity >= :requested;

If the affected-row count is 0, stock was insufficient or concurrently consumed.

Option B — Optimistic locking

@Entity
public class ProductStock {
    @Id
    private Long productId;

    private int quantity;

    @Version
    private long version;
}

Concurrent updates cause one transaction to fail with an optimistic locking exception. The application may retry or return a conflict.

Option C — Pessimistic locking

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select s from ProductStock s where s.productId = :id")
ProductStock findForUpdate(@Param("id") Long id);

The selected row is locked for update until transaction end. This is useful for short critical sections but can reduce throughput and create deadlocks.

Option D — Serializable transaction

Useful for complex invariants that cannot be protected with one row lock or one atomic SQL statement, but the code must handle retries.

Senior interview answer

I choose isolation based on the invariant, not by selecting the highest level globally. For a counter or stock value, an atomic conditional UPDATE is often better than raising isolation. For entity edits, optimistic locking works well when conflicts are rare. For short high-contention critical sections, pessimistic locking may be appropriate. For multi-row invariants, Serializable can be correct, but I must design retry and idempotency behavior.

Locks

5. Locking, blocking, and deadlocks

4.1 Optimistic versus pessimistic locking

Optimistic locking

Assumes conflicts are uncommon. Transactions proceed without blocking and detect conflicts at update time using a version.

Good for: user profile edits, administrative forms, low-contention records.

Pessimistic locking

Locks data before update because conflicts are expected or the operation must serialize.

Good for: short stock reservation or balance-critical sections.

4.2 Deadlock example

Transaction 1: lock Account A wait for Account B Transaction 2: lock Account B wait for Account A Database detects cycle ↓ one transaction is aborted

4.3 How to reduce deadlocks

  • Lock rows in a consistent order, for example smaller account ID first.
  • Keep transactions short.
  • Avoid user interaction or external API calls inside the transaction.
  • Use indexes so updates locate rows quickly and lock fewer records.
  • Reduce transaction batch size.
  • Retry deadlock victims with bounded backoff and idempotency.
long first = Math.min(fromAccountId, toAccountId);
long second = Math.max(fromAccountId, toAccountId);

Account a = repository.findForUpdate(first);
Account b = repository.findForUpdate(second);

4.4 Blocking is not always a deadlock

A query can be slow because it waits for another transaction's lock. The correct action is to identify the blocking session and the long-running transaction, not immediately add an index.

Common mistake: Looking only at query execution time without separating CPU time, I/O time, connection-pool wait, and lock wait.
Real project cases

6. Isolation problems in real projects

5.1 Two payment requests charge the provider twice

Request A: payment status is PENDING Request B: payment status is PENDING Both call payment provider Both update status to COMPLETED

Problem: isolation at the database read alone cannot undo duplicate external side effects.

Solution:

  • Use an idempotency key with a unique constraint.
  • Atomically move payment from PENDING to PROCESSING.
  • Only the request that updated one row may call the provider.
  • Use provider-side idempotency when available.
  • Persist provider request/result for recovery.
UPDATE payment
SET status = 'PROCESSING',
    processing_token = :token
WHERE payment_id = :id
  AND status = 'PENDING';

5.2 Overselling inventory

Unsafe: SELECT quantity, check in Java, then UPDATE.

Safer: one conditional atomic UPDATE and check affected rows.

5.3 Coupon claimed more times than allowed

Use a unique constraint on customer and coupon for one-time claims, plus an atomic capacity update for globally limited coupons.

CREATE UNIQUE INDEX uk_coupon_customer
ON coupon_claim(coupon_id, customer_id);

5.4 Duplicate order creation after timeout

The client times out and retries, while the first request may already have committed. Use an idempotency key persisted with a unique constraint and return the original result for duplicate requests.

5.5 Booking the same seat

Use a unique seat reservation constraint, short transaction, and either conditional insert/update or row locking. The database constraint is the final protection.

5.6 User profile lost update

Two admins edit the same customer. Optimistic locking with a version field prevents silent overwriting and returns a conflict for manual resolution.

5.7 Batch processing

Do not process 100,000 records in one transaction. Use chunks, one transaction per chunk or item, checkpoint progress, and make work idempotent.

5.8 Audit record must survive outer rollback

Use REQUIRES_NEW in another Spring bean only when the business requirement truly wants independent commit. Remember that this creates partial commit intentionally.

5.9 Saga workflow

Order creation, payment, inventory, and shipment across services require local transactions and compensating actions. There is no global rollback unless using a distributed transaction technology with significant trade-offs.

5.10 Read consistency for reports

A report that runs for several minutes may require a consistent snapshot. Depending on the database, use Repeatable Read, a replica, a reporting warehouse, or an exported snapshot rather than locking production tables.

Performance workflow

7. When an API is slow: the investigation workflow

Start with scope: Is every request slow, only one endpoint, only one tenant, only one region, only writes, only peak traffic, or only after deployment?

6.1 Step 1 — Confirm the symptom

  • Measure p50, p95, and p99 latency, not only average.
  • Check error rate, timeout rate, throughput, and saturation.
  • Compare before/after deployment or incident start time.
  • Separate client-observed latency from server processing latency.

6.2 Step 2 — Trace one slow request end to end

Client → Load Balancer → API Gateway → Application queue/thread wait → Controller → Service → Database → External API / Redis / Kafka → Serialization → Network response

Use a correlation ID or distributed trace to identify which span consumed time.

6.3 Step 3 — Break latency into categories

CategoryEvidenceTypical fix
Connection-pool waitHigh pool wait time, active connections at maxFind long queries/transactions, right-size pool, reduce connection hold time.
Database executionSlow-query log, plan, high DB CPU/I/OQuery/index/schema optimization.
Lock waitBlocked sessions, lock wait eventsShorten blockers, consistent lock order, reduce contention.
External APITrace span dominated by HTTP clientTimeout, retry policy, circuit breaker, caching, async design.
Thread-pool saturationQueue length high, active threads maxedRemove blocking, separate pools, tune after root cause.
GC / memoryLong pauses, allocation spike, heap pressureReduce allocation, fix leak, right-size heap, tune GC only with evidence.

Payload sizeLarge response/serialization timePagination, projection, compression, remove unused fields.

6.4 Step 4 — Check application resources

  • HTTP worker threads and queue.
  • Database pool active/idle/pending.
  • WebClient/HTTP client connection pool.
  • CPU, heap, GC pauses, direct memory.
  • Container throttling and memory limits.
  • File descriptors and socket counts.

6.5 Step 5 — Check downstream dependencies

  • Database latency and lock waits.
  • Redis latency and hit ratio.
  • External provider latency and error codes.
  • Kafka producer acknowledgements or consumer lag.
  • DNS, TLS handshake, proxy, and network route.

6.6 Step 6 — Reproduce safely

  • Use production-like data distribution and indexes.
  • Test one variable at a time.
  • Capture trace, plan, and resource metrics.
  • Do not run destructive load tests against production.

6.7 Step 7 — Apply the smallest targeted fix

Database bottleneck

Optimize query, add correct index, reduce selected rows/columns, fix transaction scope.

External dependency

Set timeouts, isolate pool, circuit breaker, cache stable data, redesign synchronous path.

Application CPU

Profile, reduce repeated mapping/serialization, improve algorithm, avoid unnecessary object creation.

6.8 Step 8 — Verify after the fix

  • Compare p95/p99 and throughput before/after.
  • Check errors and resource saturation.
  • Verify correctness and no new stale-data or consistency issue.
  • Add a regression test, dashboard, and alert.

Senior interview answer

When an API is slow, I first prove where time is spent. I use p95/p99 metrics and a distributed trace to split queue time, application time, database time, lock wait, and downstream HTTP time. I then correlate that with thread pools, connection pools, CPU, GC, and dependency metrics. I avoid blindly increasing pools or adding cache. After identifying the bottleneck, I make the smallest fix, load-test it with realistic data, and verify latency, throughput, error rate, and correctness.

SQL tuning

8. When SQL is slow: detailed troubleshooting steps

7.1 Step 1 — Capture the exact SQL and bind values

Performance can depend heavily on parameter values. A query that is fast for one tenant may be slow for another due to data skew.

7.2 Step 2 — Measure execution and wait type

  • Execution time.
  • Rows returned and rows examined.
  • CPU time versus I/O time.
  • Lock wait versus actual execution.
  • Temporary files, spill, sort, and hash memory usage.

SELECT o.id, o.status, o.created_at

7.4 Step 4 — Check cardinality and selectivity

An index helps most when it eliminates a large portion of rows. Indexing a column with very few distinct values may not help by itself.

7.5 Step 5 — Check predicate usability

Function on indexed column

WHERE DATE(created_at) = :date

Range predicate

WHERE created_at >= :start
  AND created_at < :nextDay

Leading wildcard

WHERE name LIKE '%huy%'

Search solution

Use a suitable full-text index or search engine when substring search is a real requirement.

7.6 Step 6 — Check joins

  • Join columns have compatible types.
  • Foreign-key or lookup columns are indexed where needed.
  • No accidental many-to-many row multiplication.
  • Filter early when semantically correct.
  • Return only required columns.

7.7 Step 7 — Check sorting and pagination

Offset pagination becomes slower for deep pages because the database must find and skip many rows.

-- Offset pagination
SELECT *
FROM orders
ORDER BY created_at DESC, id DESC
OFFSET 100000 ROWS FETCH NEXT 20 ROWS ONLY;

-- Keyset pagination
SELECT *
FROM orders
WHERE (created_at, id) < (:lastCreatedAt, :lastId)
ORDER BY created_at DESC, id DESC
FETCH FIRST 20 ROWS ONLY;

7.8 Step 8 — Check aggregation

  • Can old data be pre-aggregated?
  • Can a materialized view or reporting table help?
  • Is the query scanning operational tables for a dashboard every second?
  • Would a warehouse or replica be more appropriate?

7.9 Step 9 — Check statistics and plan stability

Stale statistics or highly skewed data can cause poor plans. Refresh statistics appropriately and validate with real parameter distributions.

7.10 Step 10 — Validate index cost

Every index increases storage and write cost. Too many indexes slow INSERT, UPDATE, DELETE, vacuum/maintenance, and backups.

Senior rule: Do not add an index only because the query has a WHERE clause. Design the index from the query shape, equality predicates, range predicates, join columns, sort order, selectivity, and write workload.

Senior interview answer

For slow SQL, I capture the exact statement and parameter values, then inspect actual execution behavior rather than guessing. I compare estimated and actual row counts, identify scans, joins, sorts, spills, lock waits, and rows examined. I then check predicate sargability, index design, join cardinality, selected columns, pagination, and statistics. I validate the new plan and measure write overhead before adding an index.

Indexes

9. Index design in real systems

8.1 B-tree intuition

A B-tree keeps sorted keys in a balanced multi-level structure. The database can navigate from root to leaf with relatively few page reads.

Root page ├── values < 1000 ├── values 1000–5000 └── values > 5000 ↓ Intermediate page ↓ Leaf page with sorted keys and row references

8.2 Composite index order

For this query:

SELECT id, created_at
FROM orders
WHERE customer_id = ?
  AND status = ?
ORDER BY created_at DESC
LIMIT 20;

A possible index:

CREATE INDEX idx_orders_customer_status_created
ON orders(customer_id, status, created_at DESC);

Equality columns commonly come before range/sort columns, but always validate with the actual query plan and data distribution.

8.3 Left-prefix principle

An index on (customer_id, status, created_at) is naturally useful for predicates beginning with customer_id. It is not equally useful for a query filtering only by status.

8.4 Covering index

If all required columns are available from the index, the database may avoid table lookups. This can improve reads but makes the index larger.

8.5 Index anti-patterns

  • Index every column independently.
  • Create many overlapping composite indexes.
  • Ignore write volume.
  • Use low-selectivity leading columns without evidence.
  • Keep unused indexes forever.
Java persistence

10. JPA and Hibernate performance problems

9.1 N+1 query problem

List<Order> orders = orderRepository.findAll();

for (Order order : orders) {
    System.out.println(order.getItems().size());
}
1 query loads orders N additional queries load items for each order Total = N + 1 queries

Possible solutions

  • Fetch join for one specific use case.
  • Entity graph.
  • Batch fetching.
  • DTO projection.
  • Dedicated query designed for the response.
@Query("select distinct o from Order o left join fetch o.items " +
       "where o.customerId = :customerId")
List<Order> findWithItems(@Param("customerId") Long customerId);
Do not fetch-join every relationship. Multiple to-many joins can multiply rows and create huge result sets.

9.2 Loading too much data

Returning entities can load unnecessary columns and relationships. Use DTO projections for read APIs.

9.3 Dirty checking and large persistence context

A long transaction managing thousands of entities increases memory and flush cost. Batch work should flush and clear periodically.

for (int i = 0; i < records.size(); i++) {
    entityManager.persist(records.get(i));

    if (i > 0 && i % 100 == 0) {
        entityManager.flush();
        entityManager.clear();
    }
}

9.4 JDBC batching

Batch INSERT/UPDATE reduces round trips, but generated IDs, ordering, and database capabilities affect the result.

9.5 LazyInitializationException

This is usually a transaction and data-shaping design problem. Avoid solving it by globally enabling eager loading or keeping sessions open across the web layer.

Resources

11. Connection-pool diagnosis

10.1 A larger pool is not always faster

If the database can efficiently process 30 concurrent queries, giving the application 200 connections may create more context switching, locks, and queueing inside the database.

10.2 What to monitor

  • Active connections.
  • Idle connections.
  • Pending threads waiting for a connection.
  • Connection acquisition time.
  • Connection usage duration.
  • Timeout count.
  • Database maximum connections and actual workload capacity.

10.3 Pool exhaustion causes

  • Slow SQL.
  • Long transactions.
  • External API call inside transaction.
  • Connection leak.
  • Traffic spike.
  • Pool too small for proven safe database capacity.
Correct order: fix long query/transaction first, then size the pool based on database capacity and workload. Do not use pool growth to hide blocked or slow connections.
Caching

12. Caching without breaking correctness

11.1 Cache-aside flow

GET key → cache hit → return → cache miss → query DB → put cache → return

11.2 Questions before adding cache

  • Is the data read frequently and changed less often?
  • How stale may it be?
  • What invalidates it?
  • What happens during cache outage?
  • Can many misses create a cache stampede?
  • Does caching personal or tenant data create leakage risk?

11.3 Common fixes

TTL

Bounds staleness and forgotten entries.

Jitter

Prevents many keys from expiring at the same moment.

Single flight / lock

Only one request rebuilds a hot missing value.

Negative caching

Temporarily caches “not found” to reduce repeated misses.

Versioned key

Changes key when source version changes.

Event invalidation

Publishes update event; accept eventual delivery trade-offs.

Cache is not the first answer to slow SQL. A cache can hide a bad query temporarily while adding consistency and operational complexity.

Senior interview

15. Interview questions and senior answers

1. Explain ACID with a payment example.

Atomicity means payment state, ledger, and order update commit together in one local transaction. Consistency means constraints and business invariants remain valid. Isolation prevents concurrent payment requests from both acting on the same pending state. Durability means committed payment data survives restart. I would also clarify that the external payment provider is outside the local ACID transaction, so I need idempotency, persistent state, retry, and reconciliation.

2. Which isolation level do you normally use?

I usually start with the database default, often Read Committed, and solve specific concurrency problems explicitly. I do not globally move everything to Serializable. I identify the invariant and choose atomic SQL, optimistic locking, pessimistic locking, unique constraints, or Serializable only where needed.

3. How do you prevent lost updates?

For counters or stock, I prefer an atomic conditional UPDATE. For entity editing where conflicts are uncommon, optimistic locking with a version is effective. For short high-contention operations, pessimistic locking may be appropriate. The final choice depends on conflict frequency, retry cost, and user experience.

4. Optimistic versus pessimistic locking?

Optimistic locking allows concurrent work and detects conflict at commit/update time, so it is good when conflicts are rare. Pessimistic locking blocks competitors early, which can be safer for short critical sections but reduces throughput and can cause deadlocks. I never hold a pessimistic lock while calling a slow external service.

5. What causes a deadlock and how do you solve it?

A deadlock is a cycle of transactions waiting on each other's locks. I inspect the database deadlock graph, identify the SQL and lock order, then make lock order consistent, shorten transactions, add missing indexes, reduce batch size, and retry the aborted transaction with bounded backoff and idempotency.

6. An API is slow. What do you check first?

I confirm the symptom using p95/p99 and trace a slow request. I separate queue time, connection-pool wait, application CPU, database execution, lock wait, external HTTP, and serialization. Then I correlate with resource metrics. I avoid guessing from one log line or increasing pools before locating the bottleneck.

7. SQL is slow. What is your exact process?

I capture the exact SQL and parameters, then inspect the actual execution plan and wait type. I compare estimated and actual rows, review scans, joins, sorts, spills, and locks, check sargability and index order, reduce selected data, review pagination and statistics, then test the change with production-like distribution and measure write overhead.

8. Why can an index make the system slower?

Indexes improve selected reads but add storage and maintenance to every insert, update, and delete. Too many overlapping indexes increase write latency, memory pressure, vacuum/maintenance work, and backup size. I add an index only after validating the workload and query plan.

9. What is the N+1 problem?

One query loads parent rows, then one additional query runs for each parent's lazy relationship. I detect it using SQL count or tracing and solve it with a use-case-specific fetch join, entity graph, batch fetching, or DTO projection. I avoid making every relationship eager.

10. How do you size a database connection pool?

I size it from database capacity and application concurrency, not from HTTP thread count alone. I monitor acquire time, pending requests, query duration, and database saturation. If connections are always busy because queries or transactions are slow, increasing the pool can make the database worse.

11. How do you handle duplicate API retries?

I use an idempotency key stored with a unique constraint. The first request owns the operation; later requests return the stored result or current status. For external providers, I also use provider idempotency when supported. Timeout does not mean failure, so reconciliation is necessary.

12. When would you use Serializable?

I use Serializable for complex cross-row invariants that are difficult to protect correctly with narrower locks or atomic statements. I expect possible serialization failures and implement bounded idempotent retries. I evaluate throughput impact before enabling it broadly.

13. Why is average latency not enough?

Average hides tail latency. A service may average 100 ms while 5% of requests take several seconds. Users and upstream timeouts are affected by p95 and p99, so I monitor percentiles together with throughput, errors, and saturation.

14. How do you distinguish slow SQL from lock wait?

I inspect database wait events and blocking sessions. A query may have an efficient plan but spend ten seconds waiting for a row lock. The fix is the blocking transaction or contention pattern, not necessarily the query plan.

15. Cache or optimize SQL first?

I first understand and usually optimize the query and data access. I add cache only when the access pattern and staleness requirement justify it. Cache introduces invalidation, stampede, outage, and consistency concerns, so it should solve a measured workload problem rather than hide unknown behavior.

16. How would you investigate a sudden latency increase after deployment?

I compare the deployment timestamp with latency and resource metrics, review changed SQL, transaction scope, serialization, dependency calls, thread pools, and configuration. I use traces to identify the new slow span, then decide whether to roll back or mitigate. After stabilization, I reproduce and add a regression test and alert.

Final senior answer

A senior database investigation is evidence-driven. I first protect correctness with constraints, explicit transaction boundaries, and concurrency control. For performance, I decompose latency instead of guessing: queue, pool, lock, SQL, CPU, network, and dependency time. I fix the narrowest root cause, validate with realistic data, and measure both performance and correctness after the change.
