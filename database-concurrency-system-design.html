Database Under Peak Traffic

A senior-level guide to database concurrency, inventory correctness, order processing, locking, transactions, idempotency, queues, sharding, and user experience during flash sales and promotion events.

Core question:

Imagine an e-commerce promotion where 100,000 users arrive within seconds, 10,000 users try to buy the same SKU, and only 100 units exist.

The real engineering problem is not simply “How can the database handle 10,000 requests?” It is:

How do we guarantee that at most 100 units are sold
while keeping latency acceptable,
preventing duplicate orders,
protecting the database,
and giving users a good experience?

Important production principle

Inventory correctness must have one authoritative source of truth. A cache can accelerate availability checks, but the final reservation/commit must be protected by an authoritative concurrency mechanism.

Recent production material from Shopify describes moving inventory reservation into MySQL so reservation and inventory ledger operations can share ACID guarantees, while using database techniques such as SKIP LOCKED and a design that avoids a single highly contended quantity row. citeturn0search7

1. What Actually Happens During a Promotion Event?

Normal traffic may look like:

200 requests/sec → DB handles comfortably

A promotion may suddenly become:

10:00:00 → 100,000 users enter
10:00:01 → 20,000 checkout attempts
10:00:02 → 10,000 attempts target the same SKU
10:00:03 → payment/order retries begin

The important observation is that average traffic is not the problem. The problem is synchronized concurrency against the same data.

Connection Pool

Too many requests can wait for DB connections.

Hot Row

Thousands of transactions may contend for one inventory row.

Lock Wait

Transactions queue behind one another.

CPU / I/O

Queries, indexes, WAL/redo, locks and fsync can increase DB pressure.

Retries

Timeouts can create even more traffic.

Read Replica Lag

Users may see stale availability if reads are routed to replicas.

2. The Classic Overselling Bug

Naive read → check → write

// Request A
SELECT quantity FROM inventory WHERE sku = 'IPHONE';

// Request B
SELECT quantity FROM inventory WHERE sku = 'IPHONE';

// Both see quantity = 1

if (quantity > 0) {
    UPDATE inventory
    SET quantity = quantity - 1
    WHERE sku = 'IPHONE';
}

Both requests can observe the same old value before either update commits. This is a classic read-modify-write race. Concurrent updates without an appropriate concurrency-control strategy can produce lost updates or overselling. AWS also explicitly notes that read-modify-write operations require concurrency control. citeturn0search9

Better: make the decision atomic

UPDATE inventory
SET available_quantity = available_quantity - 1
WHERE sku = ?
  AND available_quantity >= 1;

Then check:

rowsAffected == 1 → reservation succeeded
rowsAffected == 0 → out of stock / conflict

The database performs the condition and modification as one atomic write operation. This is often much better than reading a value into Java and then deciding what to do.

3. Atomic Conditional Update — Often the Best Starting Point

Why it works

Request A → UPDATE ... WHERE quantity >= 1 → success → quantity 0
Request B → UPDATE ... WHERE quantity >= 1 → 0 rows → sold out

The application never needs to trust a previously read quantity for the final decision.

UPDATE inventory
SET available_quantity = available_quantity - :qty,
    reserved_quantity = reserved_quantity + :qty,
    version = version + 1
WHERE sku = :sku
  AND available_quantity >= :qty;

Check the affected-row count. If zero, the reservation did not happen.

Senior point: “Check then update” should usually become “conditional update that contains the check.”

4. Pessimistic Locking — SELECT FOR UPDATE

For a transaction that needs to read inventory and then make multiple related changes, a row-level lock can serialize modifications for the same SKU.

BEGIN;

SELECT available_quantity
FROM inventory
WHERE sku = 'IPHONE'
FOR UPDATE;

-- row is locked

UPDATE inventory
SET available_quantity = available_quantity - 1
WHERE sku = 'IPHONE';

INSERT INTO reservations (...);

COMMIT;

Only one transaction can hold the lock on that row at a time.

Recent examples of inventory reservation designs use row-level locking specifically to prevent concurrent reservations from overselling. citeturn0search4turn0search6

The problem with SELECT FOR UPDATE during a flash sale

10,000 requests
↓
all want same SKU row
↓
1 transaction gets lock
↓
9,999 wait
↓
connection pool fills
↓
latency explodes
↓
timeouts / retries

So pessimistic locking guarantees correctness but can serialize a very hot SKU. It is often excellent for moderate concurrency, but you must measure lock wait and throughput under peak load.

5. Optimistic Locking

Instead of holding a DB lock while the application works, store a version number.

id | sku | available | version
1  | A   | 10        | 42

Update only if the version is still the one that was read:

UPDATE inventory
SET available_quantity = available_quantity - 1,
    version = version + 1
WHERE sku = :sku
  AND version = :version
  AND available_quantity >= 1;

If rowsAffected = 0, another transaction changed the row first.

Optimistic locking can reduce explicit lock waiting, but retries themselves can become expensive under extreme contention. It is not automatically better for a flash-sale hot row.

Important senior nuance

If 10,000 requests all optimistically update the same row and 9,999 retry repeatedly, you can simply replace lock contention with retry contention.

Therefore combine optimistic concurrency with:

  • Bounded retries.
  • Exponential backoff + jitter.
  • Early rejection.
  • Queueing for extreme hot SKUs.
  • Admission control.

6. Inventory Reservation Is Better Than Immediate Final Deduction

A strong e-commerce model separates:

  • Physical stock: units physically available.
  • Reserved stock: temporarily held by active checkouts.
  • Available-to-sell: stock that can still be promised.
  • Sold/committed stock: permanently committed after successful payment/order completion.
AVAILABLE → RESERVED → SOLD
│ │
│ └── payment timeout → RELEASED
└── direct failure → no reservation

7. The Correct Reservation Flow

1. User clicks Buy / Checkout ↓ 2. Validate request ↓ 3. Idempotency check ↓ 4. Optional cache/Redis pre-check ↓ 5. Authoritative DB reservation ↓ 6. Reservation succeeds? ├── NO → return controlled SOLD_OUT result └── YES ↓ 7. Create/advance order state ↓ 8. Payment processing ↓ 9. Payment success → COMMIT / SOLD Payment timeout/failure → RELEASE

The crucial point is that the cache or UI availability indicator is not the final authority. The DB reservation is the authoritative decision.

8. What If Inventory Is Already Sold Out?

Do not treat “out of stock” as an exceptional server error

From the user's perspective, “sold out” is often a normal business result during a promotion.

Instead of:

HTTP 500
"Database update failed"

return a controlled business response:

{
  "status": "SOLD_OUT",
  "message": "This item is no longer available.",
  "canJoinWaitlist": true
}

The frontend can then show a friendly message, suggest another seller/product, offer a waitlist, or update the cart.

9. How to Avoid a Bad User Experience When Inventory Runs Out

Separate technical failure from business failure

SituationUser experience
Inventory truly unavailable“Sold out” / suggest alternatives.
Reservation conflict“This item was just taken by another customer.” Refresh availability.
DB temporarily overloadedDo not expose DB errors. Use controlled retry/pending state.
Payment timeout after reservationKeep reservation temporarily; show payment processing state.

Client retries same requestReturn the original result using idempotency.

10. Idempotency — Essential for Order Creation

Imagine the user clicks “Pay” and the server successfully creates the order, but the network response is lost.

Client → POST /orders
↓
DB creates ORDER-123
↓
response lost
↓
client retries
↓
WITHOUT idempotency → ORDER-124
WITH idempotency → ORDER-123 result returned

Payment APIs such as Stripe explicitly use idempotency keys so retries do not accidentally create duplicate objects or repeat operations. citeturn0search2

POST /orders
Idempotency-Key: 8d7c...

Database:
idempotency_key UNIQUE

The first successful request stores the result. A retry with the same key returns the same logical result.

11. Database Constraint for Idempotency

CREATE UNIQUE INDEX ux_order_idempotency
ON orders(customer_id, idempotency_key);

Do not rely only on an application-level “check first, then insert.” Two concurrent requests can both pass that check.

Let the database unique constraint be the final authority.

12. Multi-Item Order — Deadlock Risk

Suppose an order contains SKU A and SKU B.

Transaction 1: lock A → then B
Transaction 2: lock B → then A
↓
T1 waits for B
T2 waits for A
↓
DEADLOCK

Use a deterministic lock order, for example always lock SKUs in ascending ID order.

Order items:
A, B, C

Always lock:
A → B → C

This dramatically reduces circular wait patterns.

13. SKIP LOCKED — When Queue-Like DB Processing Helps

For worker-style workloads, FOR UPDATE SKIP LOCKED can allow workers to skip rows already being processed instead of waiting.

SELECT id
FROM reservations
WHERE status = 'PENDING'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 100;

This is useful when the database is being used as a work queue and many workers process independent rows.

Shopify's 2026 inventory reservation architecture describes using MySQL SKIP LOCKED with a row-per-unit model to increase reservation throughput and avoid one highly contended quantity row. citeturn0search7

Important: SKIP LOCKED does not magically make every inventory update scalable. It is most useful when work can be divided into independently lockable rows.

14. Hot Row Problem

A classic schema is:

inventory
----------------
sku = IPHONE
available = 100

Every checkout modifies the same row.

Even if the database is otherwise capable of thousands of writes/sec, one hot row creates a serialization point.

Possible approaches

  • Atomic conditional update.
  • Optimistic concurrency.
  • Reservation queue.
  • Inventory bucket/shard design.
  • One row per inventory unit for extreme contention.
  • Separate hot-SKU processing path.

15. Inventory Bucketing

Instead of one counter:

SKU A → available = 10,000

split inventory into multiple buckets:

SKU A
bucket 1 → 1,000
bucket 2 → 1,000
bucket 3 → 1,000
...
bucket 10 → 1,000

Requests can be distributed across buckets. This can reduce contention, but it introduces allocation complexity and requires careful correctness rules.

For extremely hot SKUs, this can be more scalable than forcing every transaction to update one physical database row.

16. Queue-Based Reservation

When demand is much higher than the number of units available, processing every request synchronously against the database may be wasteful.

100,000 requests
↓
Admission control
↓
Queue
↓
Inventory workers
↓
DB reservation
↓
Winner / SOLD_OUT

The queue converts uncontrolled concurrency into controlled work.

But what does the user see?

Instead of waiting for a DB transaction to finish:

“Your request is being processed.”
Request ID / order attempt ID
↓
Poll or WebSocket/SSE
↓
RESERVED / SOLD_OUT

This can produce a much better experience than thousands of requests timing out.

18. Why Redis DECR Alone Is Dangerous for Inventory

A tempting design is:

if Redis.DECR(stockKey) >= 0:
    create order
else:
    reject

Redis can serialize the decrement, but now inventory exists in Redis and the authoritative ledger exists in the database.

Redis reservation succeeds
↓
DB transaction fails
↓
Redis says reserved
DB says not reserved
↓
inventory divergence

Shopify's engineering write-up describes this exact class of consistency problem when reservations and the inventory ledger lived in separate systems, motivating a move toward a unified database strategy. citeturn0search7

Better: Redis can be used as a fast admission/filter layer, but the authoritative reservation should have a clear consistency boundary.

19. Transaction Isolation Levels

IsolationTypical behaviorInventory consideration
READ UNCOMMITTEDCan observe uncommitted changesUsually inappropriate for inventory correctness.
READ COMMITTEDReads committed dataCommon default; still need atomic updates/locking.
REPEATABLE READStable transaction snapshot semanticsUseful, but understand DB-specific locking behavior.
SERIALIZABLEStrongest isolationCorrect but can reduce throughput and increase retries.

Senior point: Increasing isolation is not automatically the solution to high concurrency. It can increase contention and aborts. Prefer the smallest concurrency-control mechanism that guarantees the business invariant.

20. Database Connection Pool Protection

Suppose the application receives 20,000 requests/sec but the DB connection pool has 100 connections.

20,000 HTTP requests
↓
100 DB connections
↓
19,900 requests wait
↓
thread/request queues grow
↓
timeouts
↓
retries

Increasing the pool to 1,000 is not necessarily a solution. The database may become overloaded with 1,000 concurrent queries.

Use:

  • Bounded DB pool.
  • Application-level concurrency limit.
  • Short connection acquisition timeout.
  • Query timeout.
  • Bulkhead isolation for critical operations.
  • Separate pools for different workloads where appropriate.
Senior principle: The connection pool is a protective boundary, not a number you maximize.

21. Read Replicas — Why Inventory Reads Are Special

Read replicas are excellent for read-heavy catalog queries, but inventory availability is often sensitive to replication lag.

Primary DB: quantity = 0
↓ replication lag
Replica: quantity = 1
↓
User sees “In Stock”
↓
Checkout reaches primary
↓
SOLD OUT

This can be acceptable if the UI treats availability as advisory. The final reservation must be decided against the authoritative write path.

Pattern: use replicas for browsing; use primary/authoritative reservation path for commit.

22. CQRS-Style Separation for E-commerce

Read side
CDN / Cache / Read replicas / Search
↓
Product browsing

Write side
Primary DB / Inventory service
↓
Order + Reservation

Do not force the same database path to serve product browsing and inventory correctness.

During a promotion, product pages can generate millions of reads while only a smaller subset actually performs reservation. Separating read-heavy and correctness-critical workloads prevents browsing traffic from starving inventory writes.

23. Order State Machine

CREATED
↓
RESERVING_INVENTORY
├── SOLD_OUT → FAILED
└── RESERVED
↓
PAYMENT_PENDING
├── PAYMENT_FAILED → RELEASED
└── PAYMENT_SUCCESS
↓
CONFIRMED
↓
FULFILLING
↓
SHIPPED

A state machine is safer than scattered boolean flags such as paid=true, reserved=true, cancelled=false. Every transition should have clear ownership and idempotency rules.

24. Payment + Inventory: Do Not Hold DB Locks During Payment

Bad design:

BEGIN DB transaction
↓
lock inventory
↓
call payment provider
↓
wait 2 seconds
↓
commit

Holding an inventory DB lock while calling an external payment service can create massive lock contention.

Better:

DB TX → reserve inventory for short TTL → COMMIT
↓
call payment provider outside DB transaction
↓
payment success → confirm reservation
payment failure → release reservation

The DB transaction should be short and contain only the operations that must be atomic.

25. Reservation Expiration

If users abandon checkout, reserved inventory must return to available stock.

reservation:
status = ACTIVE
expires_at = now + 10 minutes

Release can be driven by:

  • Delayed message.
  • Scheduled worker.
  • Database job.
  • Event-driven timeout service.

A robust design often has both an event-driven fast path and a periodic reconciliation job as a safety net.

26. Reconciliation — The Safety Net

Even with good transactional logic, distributed systems eventually encounter partial failures. Build reconciliation jobs that compare:

Inventory ledger
vs
Reservations
vs
Orders
vs
Payment state

Examples:

  • Reservation ACTIVE but expired.
  • Payment succeeded but order is still PAYMENT_PENDING.
  • Order CONFIRMED but inventory reservation is missing.
  • Inventory count does not equal ledger-derived quantity.

Reconciliation should repair or flag inconsistencies rather than silently ignoring them.

27. Database Indexes During Peak Traffic

Concurrency is not only about locks. Bad indexes can turn a simple operation into a large scan.

UPDATE inventory
SET available_quantity = available_quantity - 1
WHERE sku = ?;

The sku lookup must be indexed appropriately.

For reservations:

CREATE INDEX idx_reservation_expiry
ON inventory_reservation(status, expires_at);

For order lookup:

CREATE UNIQUE INDEX ux_order_idempotency
ON orders(customer_id, idempotency_key);

Peak traffic is a terrible time to discover that a supposedly tiny operation is scanning millions of rows.

28. Database Capacity Planning

Do not calculate DB capacity from HTTP RPS alone.

Estimate:

HTTP requests
× DB operations/request
× retry factor
× cache-miss factor
= effective DB operation rate

Example:

50,000 checkout attempts/sec
× 4 DB statements
× 1.1 retry factor
= 220,000 DB statements/sec

Then benchmark the actual query mix, transaction duration, lock contention, CPU, I/O, WAL/redo, connection pool and storage latency.

30. What Happens When 10,000 Users Buy the Last 100 Units?

Let's walk through a concrete design using an atomic DB update.

UPDATE inventory
SET available_quantity = available_quantity - 1
WHERE sku = 'PROMO-001'
  AND available_quantity >= 1;

Exactly 100 transactions can successfully affect one row before the quantity reaches zero.

The remaining requests get zero affected rows.

10,000 attempts ↓ 100 successful reservations ↓ 9,900 business-level SOLD_OUT results ↓ No oversell

But this does not mean all 10,000 DB requests should be allowed to hammer the database. At extreme scale, add admission control, pre-checking, queueing, and/or a dedicated hot-SKU strategy.

31. The Most Important Optimization: Reject Work Before the DB

If only 100 units exist and 100,000 users want them, making all 100,000 requests execute expensive DB transactions is wasteful.

Use layers:

100,000 users ↓ rate limit / virtual queue ↓ fast availability signal ↓ admission control ↓ small number of DB reservation attempts ↓ 100 winners

The authoritative DB still decides correctness, but the system avoids creating unnecessary database contention.

32. Production Scenarios

Scenario A — 1 SKU, 100 Units, 100,000 Users

Recommendation: virtual queue/admission control + fast pre-check + authoritative DB atomic reservation + idempotency + asynchronous payment + reservation timeout.

Do not put a long DB lock around payment.

Scenario B — 10,000 Different SKUs, Normal Distribution

Contention is spread across many rows. Atomic updates or optimistic locking may be sufficient. A single global queue would unnecessarily reduce parallelism.

Scenario C — One Hot SKU With 1,000,000 Requests

Use a specialized hot-key path. Consider pre-warming, admission control, request coalescing for reads, inventory buckets or queue-based reservation, and strict DB concurrency limits.

Scenario D — Multi-SKU Cart

Reserve all required inventory in a deterministic order. If any SKU cannot be reserved, roll back the reservation transaction or use a clearly defined saga/reservation workflow. Avoid inconsistent partial reservation.

Scenario E — Payment Provider Is Slow

Never keep DB inventory locks open while waiting for the payment provider. Create a short-lived reservation, commit it, then process payment asynchronously or outside the transaction.

33. Senior Interview Questions & Answers

Q1. How do you prevent overselling during a flash sale?

Answer: I would make the inventory reservation atomic at the authoritative store. The simplest form is a conditional update such as UPDATE inventory SET available = available - ? WHERE sku = ? AND available >= ? and checking affected rows. For more complex reservation workflows, I may use row-level locking or optimistic concurrency. At extreme contention, I would add admission control or a queue so the DB does not receive unlimited concurrent attempts. I would also use idempotency to prevent duplicate reservations caused by retries.

Q2. Would you use Redis to manage inventory?

Answer: Redis can be useful as a fast admission or pre-check layer, but I would be careful about making Redis and the relational database independent sources of truth. If reservation state and the inventory ledger are split across Redis and the DB, failures between the two systems can create divergence. For strong correctness, I want a clearly defined authoritative reservation boundary. Shopify's 2026 inventory architecture is a good real-world example of moving reservation state into the database to keep ACID consistency with the inventory ledger. citeturn0search7

Q3. SELECT FOR UPDATE or optimistic locking?

Answer: It depends on contention and transaction complexity. SELECT FOR UPDATE is simple and predictable when I need to read and update several related values atomically, but a very hot row can create lock queues. Optimistic locking avoids holding a long lock but can create many retries under extreme contention. I would benchmark lock wait, conflict rate and transaction latency before choosing. For a flash-sale hot SKU, I may move toward atomic conditional updates, admission control, queueing or a more scalable inventory allocation model.

Q4. How do you prevent 10,000 requests from exhausting the DB connection pool?

Answer: I would not simply increase the pool. I would control concurrency before the DB using rate limiting, bulkheads, admission control and bounded DB concurrency. Requests that cannot be admitted should fail fast or enter a queue rather than wait indefinitely for a connection. I would also use query timeouts and monitor connection acquisition latency.

Q5. What happens if the payment succeeds but the order service crashes before confirming the inventory?

Answer: This is a distributed transaction problem. I would use an explicit order state machine and durable events/outbox. The payment result must be recoverable, and a reconciliation worker can find PAYMENT_SUCCESS + ORDER_PENDING records and complete the transition. The inventory reservation should have a durable state and a timeout so it is not silently lost.

Q6. How do you give a good UX when inventory is gone?

Answer: I would model SOLD_OUT as a business outcome, not a server exception. The API can return a stable business code such as SOLD_OUT, and the UI can show a clear message, suggest alternatives, allow a waitlist, or refresh the cart. If the request is still processing, I would expose a pending state rather than making the user wait synchronously for a heavily contended DB transaction.

Q7. How do you handle duplicate checkout requests?

Answer: Use an idempotency key generated for the logical checkout operation. Store it with a unique database constraint and return the original result when the same key is retried. This is essential because network timeouts do not tell the client whether the server committed the operation.

Q8. Why not set SERIALIZABLE isolation for everything?

Answer: SERIALIZABLE provides strong guarantees but can increase contention, blocking or serialization failures. Under a promotion event, that can reduce throughput significantly. I prefer a targeted concurrency mechanism that protects the actual business invariant, such as an atomic conditional update or row-level lock, instead of globally increasing isolation.

Q9. What metrics do you monitor during a promotion?
  • DB CPU and I/O.
  • Transaction latency p50/p95/p99.
  • Lock wait time.
  • Deadlock count.
  • Serialization/deadlock retry count.
  • Connection pool utilization and acquisition time.
  • Slow query count.
  • Rows affected by inventory reservations.
  • SOLD_OUT rate.
  • Reservation success/failure rate.
  • Payment pending duration.
  • Order state transition failures.
  • Queue depth and consumer lag.
  • Inventory reconciliation discrepancies.

34. Senior Mental Model

When designing DB behavior for a promotion event, ask:

  1. What is the source of truth?
  2. What exact business invariant must never be violated?
  3. Can two transactions read the same old state?
  4. Can I make the check + update atomic?
  5. Where is the serialization point?
  6. What happens when thousands of requests target the same row?
  7. Can I reject work before reaching the DB?
  8. Can retries multiply traffic?
  9. Can a client safely retry?
  10. Can payment or another external call hold a DB lock?
  11. What happens if the DB times out after the transaction actually committed?
  12. How are reservations released?
  13. How do I reconcile partial failures?
  14. How does the user experience the business failure?
  15. What metrics prove the design is safe under peak load?

35. Final Architecture Principle

The goal is not to make the database accept unlimited concurrency.

The goal is to control concurrency so the database only processes the work necessary to maintain correctness.

Millions of requests ↓ Cache / CDN / fast reads ↓ Rate limiting / admission control ↓ Virtual queue if necessary ↓ Idempotency ↓ Short authoritative DB transaction ↓ Atomic inventory reservation ↓ Reservation state machine ↓ Async payment / fulfillment ↓ Reconciliation + observability

That architecture gives you three properties:

  • Correctness: no overselling and no duplicate order.
  • Resilience: DB is protected from synchronized traffic and retries.
  • User experience: SOLD_OUT and PENDING are normal business states rather than mysterious 500 errors.

36. User Experience: Never Expose Concurrency Problems to the Buyer

The most important UX principle

A database conflict is a technical event. SOLD_OUT is a business outcome.

The customer should not see:

500 Internal Server Error
Deadlock found
Lock wait timeout
Connection pool exhausted
SQL timeout
UPDATE failed

Those details belong to logs, metrics and traces. The customer should see a small set of understandable states.

The key idea is that RESERVING is a valid temporary state. The user does not need to receive a failure simply because the system is processing a highly contested operation.

37. Virtual Queue — Better Than Letting 100,000 Users Hit the DB

Suppose 100 units are available and 100,000 users click at exactly 10:00:00.

A poor design lets all 100,000 requests enter checkout. A better design introduces a virtual waiting room.

100,000 users ↓ Virtual Queue ↓ Admission controller releases 500 users ↓ Reservation processing ↓ next batch of users ↓ ...

The queue protects the DB and also improves perceived reliability. Instead of thousands of users receiving errors, users receive a stable position/token and a predictable state.

AWS explicitly recommends planning for flash-sale traffic because sudden demand can create resource bottlenecks and system unavailability. citeturn0search2

Fairness vs raw throughput

A queue is not only a DB protection mechanism. It can also provide fairness.

  • One user should not create 500 concurrent checkout attempts and dominate the inventory.
  • Rate-limit purchase attempts per account/device/session.
  • Use a signed admission token so clients cannot freely bypass the queue.
  • Optionally randomize or lottery the first admission batch for extremely scarce products.

Senior interview point: “For scarce inventory, admission control is part of business correctness and fairness, not just infrastructure protection.”

38. Hide Retries From the User — But Only When Safe

Suppose the DB returns a transient deadlock. It is usually a poor UX to immediately show an error.

Request ↓ DB transaction ↓ Deadlock ↓ Rollback ↓ bounded retry #1 ↓ success ↓ user sees normal confirmation

But retrying is safe only when the operation is designed for it.

Required:

  • Idempotency key.
  • Unique business constraint where appropriate.
  • Bounded retry count.
  • Backoff + jitter.
  • Retry only transient failures.
  • Never blindly retry an unknown payment outcome.

39. “Processing” Is Better Than a Fake Failure

There is a major difference between:

POST /checkout
→ 5 second timeout
→ HTTP 500

and:

POST /checkout
→ 202 Accepted

{
  "orderAttemptId": "OA-123",
  "status": "PROCESSING"
}

The second model allows the backend to continue processing and the client to query or receive an event later.

Client ↓ POST /checkout ↓ 202 PROCESSING ↓ Queue ↓ Inventory reservation ↓ Payment ↓ CONFIRMED / SOLD_OUT ↓ WebSocket / SSE / polling ↓ UI update

This is especially useful when peak traffic is intentionally throttled.

40. Do Not Promise Inventory Too Early in the UI

“Only 1 left!” is not the same as “Your item is reserved.”

During a promotion, product pages may use cached or replicated availability. That number is an advisory signal.

The UI should make the guarantee only after the authoritative reservation succeeds.

StateMeaning
AVAILABLESystem believes stock exists.
RESERVINGCheckout is attempting an authoritative reservation.
RESERVEDStock is actually held for this user/order.
SOLD_OUTNo reservation was obtained.

This prevents a painful UX where the UI says “success” and then the backend later cancels the order.

41. Production Case Study — Shopify Inventory Reservations

Shopify published a detailed engineering post in May 2026 describing its inventory reservation system. During Black Friday 2025, Shopify reported a peak of $5.1 million in sales per minute. The engineering problem was not merely speed; it was preventing oversells while avoiding lost sales and preserving checkout latency. citeturn0search0

The important production lessons are directly relevant to system design interviews:

  • Reservation is a short hold during payment processing.
  • Successful payment permanently claims inventory.
  • A single quantity row created too much contention.
  • SKIP LOCKED enabled concurrent transactions to select different available inventory rows.
  • Reservations and inventory ledger were moved into the same MySQL consistency boundary to obtain ACID guarantees.
  • Composite primary-key design reduced lock overhead.
  • They changed selected reservation transactions to READ COMMITTED to avoid problematic gap-lock behavior.
  • They standardized lock ordering to eliminate deadlock cycles.
  • They discovered that connection usage, not only CPU/query performance, was a major throughput bottleneck.
  • They used shadow mode and gradual rollout before switching the source of truth.

Senior lesson: high concurrency is a whole-system problem. A perfectly optimized inventory query can still fail if unrelated checkout code holds DB connections too long.

42. Production Case Study — Redis vs Database: There Is No Universal Answer

There are two legitimate production strategies.

A. Database-authoritative reservation

Request ↓ DB atomic reservation ↓ ACID order/inventory state

This is attractive when correctness and a unified transactional boundary are the priority. Shopify's 2026 architecture is an example. citeturn0search0

B. Fast admission layer + durable database

Request ↓ Redis / admission gate ↓ Queue ↓ DB authoritative persistence

This can reduce the number of expensive DB attempts dramatically, especially when demand is many orders of magnitude larger than supply. The important requirement is that the architecture defines what happens if the fast layer and DB disagree.

Interview answer: “I would not choose Redis or MySQL based on fashion. I would first define the consistency boundary. Then I would decide where admission control happens and where the authoritative inventory transition is committed.”

43. Production Case Study — Flash Sales Are About Traffic Shaping

A flash sale is fundamentally a traffic-shaping problem.

Normal system: traffic ≈ processing capacity Flash sale: traffic >>> processing capacity Correct architecture: traffic ↓ shape ↓ admit ↓ process at sustainable rate

If 100 units exist, accepting 100,000 simultaneous synchronous transactions is not inherently a sign of a better system. It is often a sign that the system has failed to shape traffic.

AWS's flash-sale guidance emphasizes preparing for sudden traffic spikes, resource bottlenecks and capacity constraints before the event. citeturn0search2

44. High-Consistency Pattern: Keep the Business Invariant Small

Do not put the entire checkout workflow inside one huge ACID transaction.

Instead define the smallest invariant that absolutely requires strong consistency:

INVARIANT:
reserved_quantity + sold_quantity
    <= physical_quantity

Then protect that invariant with a short transaction.

Everything else can be state-machine/event driven:

Short ACID reservation ↓ Order state = RESERVED ↓ Payment event ↓ Claim inventory ↓ Fulfillment event ↓ Shipment

This is the key balance between strong consistency and high throughput.

45. Outbox Pattern for Reliable Order Events

If the DB commits an order and the application then publishes Kafka/RabbitMQ, there is a failure window:

DB COMMIT ✓ ↓ publish event ✗ ↓ Order exists but downstream never hears about it

Use a transactional outbox:

BEGIN

INSERT INTO orders(...);

INSERT INTO outbox(
  event_type,
  aggregate_id,
  payload,
  status
);

COMMIT

A publisher reads the outbox and publishes the event. If publishing fails, it retries later.

This does not create a distributed ACID transaction across Kafka and the DB; it creates a reliable bridge from the authoritative transaction to asynchronous processing.

46. Exactly-Once Is Usually an Application Property

Do not casually claim “Kafka gives exactly once” or “the DB guarantees exactly once.” At the business level, duplicate messages and retries can still occur around system boundaries.

Use:

  • Idempotent consumers.
  • Unique business keys.
  • Processed-event tables when appropriate.
  • State transition validation.
  • Outbox pattern.
UPDATE orders
SET status = 'CONFIRMED'
WHERE order_id = ?
  AND status = 'PAYMENT_PENDING';

If affected rows = 0, the transition may already have happened. That makes retries safe.

47. Reconciliation Is Part of High Consistency

Strong consistency does not mean “nothing can ever go wrong.”

Distributed failures can happen after a transaction commits and before another system observes it.

Build periodic reconciliation:

Orders ↕ Reservations ↕ Inventory ledger ↕ Payment records

Examples:

  • Payment SUCCESS + order still PENDING → repair transition.
  • Reservation expired but still ACTIVE → release.
  • Order CANCELLED but inventory not released → compensate.
  • Inventory ledger and reservation totals differ → alert and repair according to business rules.

Reconciliation should be designed before the incident, not after the first production mismatch.

48. Production Failure: Database Is Healthy, but Connections Are Exhausted

This is a particularly important senior-level scenario.

You observe:

DB CPU: 45%
DB latency: acceptable
Connection pool: 100%
Request latency: huge

A junior diagnosis may be: “Increase DB CPU.”

A senior diagnosis asks: Who is holding connections, and for how long?

Shopify reported exactly this class of lesson: their reservation workload hit a throughput ceiling even though query/CPU symptoms did not initially point to the real bottleneck. They instrumented connection usage by business process and found other checkout work was holding connections too long. citeturn0search0

Interview takeaway: always monitor connection acquisition time and connection hold duration, not just DB CPU.

50. Senior System Design Answer — Complete Version

“For a flash-sale e-commerce system, I would separate the problem into traffic management, inventory correctness, order processing and user experience.

First, I would not allow every incoming request to hit the primary database. I would use CDN/cache for read-heavy product data, rate limiting and admission control, and for extremely scarce inventory I would introduce a virtual queue. This protects the database and also gives users a stable waiting experience instead of thousands of timeout errors.

For inventory, I would define the primary database as the authoritative source of truth or establish another explicit consistency boundary. The critical invariant is that we must never reserve more inventory than physically available. I would protect that invariant with a short atomic database transaction, for example a conditional update, row-level locking, or a scalable row-allocation design such as SKIP LOCKED when the workload justifies it.

I would not hold database locks while calling payment services. I would create a short-lived inventory reservation, commit it, then process payment outside the transaction. On success, the reservation becomes SOLD/CONFIRMED. On failure or timeout, it is released.

Every checkout request would have an idempotency key, because network retries are unavoidable. Database unique constraints and state-transition conditions would provide the final protection against duplicate orders.

For multi-item orders, I would use deterministic lock ordering to reduce deadlocks, and I would retry only transient database conflicts with a small bounded retry budget and jitter.

For asynchronous events, I would use a transactional outbox so an order commit and the event describing that commit cannot silently diverge.

From the UX perspective, SOLD_OUT is not a server error. If another customer wins the final unit, I would return a business-level SOLD_OUT response and show a friendly message. If the system is overloaded but the request is accepted into the processing queue, I would return PROCESSING and let the user see progress rather than exposing database timeouts.

Finally, I would monitor lock wait, deadlocks, connection utilization, connection hold time, transaction latency, queue depth, reservation success rate and inventory reconciliation. The objective is not to make the database accept unlimited concurrency. The objective is to shape traffic and keep the authoritative transaction short enough that the database remains healthy while maintaining the inventory invariant.”

51. Interview Trap Questions

  • “Just use Redis for inventory.” → Ask where the authoritative consistency boundary is.
  • “Just use SELECT FOR UPDATE.” → Ask what happens when 100,000 requests target one row.
  • “Just increase DB connections.” → More connections can make overload worse.
  • “Just use SERIALIZABLE.” → Stronger isolation can reduce throughput.
  • “Just retry every failure.” → Retries can amplify an outage and duplicate business operations.
  • “Return 500 when inventory is gone.” → SOLD_OUT is a business state, not necessarily a server failure.
  • “Keep the DB transaction open until payment finishes.” → External latency can hold locks/connections and collapse throughput.
  • “Cache says one item is available, so reserve it.” → Cache availability is advisory; final reservation needs authoritative concurrency control.
  • “Exactly once means no duplicates.” → Design idempotency at business boundaries.
