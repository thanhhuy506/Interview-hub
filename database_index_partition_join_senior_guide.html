How to Use Indexes, Partitions, and Joins Effectively

A practical guide to choosing useful indexes, designing partitions that actually reduce work, writing joins that scale, and understanding when partitioning should be combined with indexing.

Indexing Selectivity, composite indexes, covering indexes, SARGability, write cost.
Partitioning Partition pruning, key selection, range/list/hash, operational trade-offs.
Joins Join keys, filter strategy, data types, execution plans, large-table joins.
Senior Reasoning How to explain trade-offs, not just repeat keywords in an interview.

1. Effective Indexing

An index is useful only when it helps the database reduce the amount of data it must scan, sort, or look up. Creating an index on every column is not a performance strategy.

Senior mindset: Ask, “Which query pattern am I optimizing?” before asking, “Which column should I index?”
1

Index columns with useful selectivity

Selectivity means how well a column can narrow down rows. A column such as user_id, email, or order_id often has high selectivity.

A column like is_active with only true/false usually has low selectivity. If 95% of rows are active, an index on is_active alone may not help because the database still needs to read most of the table.

2

Index based on real WHERE / JOIN / ORDER BY patterns

Common candidates are columns used frequently in:

  • WHERE filters
  • JOIN ... ON conditions
  • ORDER BY
  • GROUP BY
  • Foreign-key lookups

But “used in WHERE” does not automatically mean “must be indexed.” Frequency, selectivity, table size, and query shape all matter.

1.1 Low-cardinality columns: should they be indexed?

Columns such as status codes, flags, and small enums often have low cardinality: status IN ('NEW','PAID','FAILED') or enabled IN (0,1).

Usually weak as a standalone index

CREATE INDEX idx_order_status
ON orders(status);

If millions of rows share the same status, the optimizer may choose a table scan instead.

Often strong as part of a composite index

CREATE INDEX idx_orders_status_created
ON orders(status, created_at);

This can be useful for a query such as: 

SELECT id, created_at
FROM orders
WHERE status = 'PENDING'
  AND created_at >= :fromDate
ORDER BY created_at;

1.2 Composite indexes and the leftmost-prefix rule

A composite index stores multiple columns in a defined order. Column order is critical. 

CREATE INDEX idx_orders_customer_status_created
ON orders(customer_id, status, created_at);

This index is naturally suitable for query patterns starting from customer_id:

WHERE customer_id = ?
WHERE customer_id = ? AND status = ?
WHERE customer_id = ? AND status = ? AND created_at > ?
A common mistake is creating (A, B, C) and assuming it is equally useful for a query filtering only by B. Usually it is not. Index column order should match how the application searches.

1.3 Equality columns usually come before range columns

For B-tree indexes, a useful rule is: put columns used with equality predicates first, then range columns. 

WHERE tenant_id = ?
  AND status = ?
  AND created_at BETWEEN ? AND ?

A reasonable index can be:

CREATE INDEX idx_tx_tenant_status_created
ON transactions(tenant_id, status, created_at);

Once the optimizer enters a broad range on one index dimension, columns after that range may be less useful for narrowing the search.

1.4 Functions on indexed columns can make the index ineffective

This is one of the most common SQL performance mistakes. A normal B-tree index stores the original column values in sorted order. When a query wraps that indexed column inside a function, cast, calculation, or expression, the database may no longer be able to navigate the original index efficiently.

Important: If a column has an index, do not assume the index will still be useful when you write FUNCTION(indexed_column) in WHERE, JOIN, or sometimes ORDER BY. In many cases this becomes a non-SARGable condition and can lead to an index scan or full table scan.

SARGable means the search condition can use the index structure directly to locate the required range of rows.

Example 1 — DATE function on an indexed timestamp

Less efficient 
-- Assume created_at has a B-tree index

SELECT *
FROM orders
WHERE DATE(created_at) = '2026-08-29';

The database may need to calculate DATE(created_at) for many rows before comparing the result. A normal index on created_at may therefore not be searchable as a direct range.

Better 
SELECT *
FROM orders
WHERE created_at >= '2026-08-29 00:00:00'
  AND created_at <  '2026-08-30 00:00:00';

Now the optimizer can navigate directly to the required range in the created_at index.

Example 2 — LOWER / UPPER on an indexed string

Potential problem 
-- email is indexed

SELECT *
FROM users
WHERE LOWER(email) = 'user@example.com';

A normal index on the original email value may not directly match the transformed value LOWER(email).

Possible solutions 
-- Option 1: store normalized data
WHERE email_normalized = 'user@example.com';

-- Option 2: use a function/expression index
-- if the database supports it
INDEX ON LOWER(email)

The exact syntax differs between PostgreSQL, Oracle, MySQL, SQL Server, and other engines.

Example 3 — CAST on an indexed column

Less efficient 
-- user_id is BIGINT and indexed

WHERE CAST(user_id AS VARCHAR) = '10001'

The indexed numeric value is converted before comparison, so the optimizer may not be able to use the original index efficiently.

Better 
WHERE user_id = 10001

Keep the parameter and the indexed column in compatible data types.

Example 4 — Calculation on an indexed numeric column

Less efficient 
-- price is indexed

WHERE price * 1.1 > 100
Better 
WHERE price > 100 / 1.1

Keep the indexed column itself unchanged when possible.

Example 5 — String function on an indexed column

Potential problem 
WHERE SUBSTRING(code, 1, 3) = 'ABC'
Often better 
WHERE code LIKE 'ABC%'

A prefix search can often use a B-tree index, depending on the database, collation, and operator class.

Other common non-SARGable patterns

WHERE YEAR(created_at) = 2026
WHERE COALESCE(status, 'NEW') = 'NEW'
WHERE ABS(balance) > 1000
WHERE UPPER(username) = 'ADMIN'
WHERE CAST(order_id AS CHAR) = '123'
WHERE amount + tax > 1000

Functions in JOIN conditions can have the same problem

Bad pattern 
SELECT *
FROM orders o
JOIN users u
  ON CAST(u.id AS VARCHAR) = o.user_id;

Even if users.id is indexed, the cast may make the join lookup much more expensive.

Better design 
SELECT *
FROM orders o
JOIN users u
  ON u.id = o.user_id;

Keep join columns in compatible data types at schema level.

Important exception: function-based / expression indexes

Applying a function does not always mean the query must be slow. Some database engines support indexes on the expression itself. 

-- Conceptual example
CREATE INDEX idx_users_lower_email
ON users (LOWER(email));

SELECT *
FROM users
WHERE LOWER(email) = 'user@example.com';

In this case the query can use the expression index because the indexed expression matches the query expression. Generated/computed columns can provide a similar solution in some systems.

Senior rule: Try to keep the indexed column “naked” in the predicate: indexed_column operator value. If the business requirement needs a function, consider rewriting the predicate, normalizing the stored value, using a generated column, or creating an expression index. Then verify the result with EXPLAIN / the actual execution plan.

1.5 Covering indexes

A covering index contains all columns required by a query, allowing the engine in some cases to answer the query mainly from the index without reading the table row. 

SELECT order_id, created_at, amount
FROM orders
WHERE customer_id = ?
  AND status = 'PAID';

A possible index design:

-- Syntax differs by database.
CREATE INDEX idx_orders_customer_status
ON orders(customer_id, status, created_at, amount);
Do not turn every index into a wide covering index. Wider indexes consume more memory/storage and make INSERT/UPDATE/DELETE more expensive.

1.6 Every index has a write cost

When a row changes, relevant indexes also need maintenance.

INSERT rowWrite table data.
Update indexesMaintain each affected index tree.
More I/O and CPUAdditional page changes and logging.
Potential side effectsMore storage, cache pressure, and slower writes.

Therefore, a write-heavy table should not have unnecessary indexes. Indexes should exist because important queries need them.

1.7 Index design checklist

  • What are the top slow or high-frequency queries?
  • Which columns are used for equality filters?
  • Which columns are used for range filters?
  • Which columns are used in JOIN conditions?
  • Does the query need ORDER BY or GROUP BY?
  • Can one composite index replace multiple overlapping indexes?
  • Is the first index column selective enough for the real query pattern?
  • Are predicates SARGable?
  • Is the index actually used according to EXPLAIN / execution plan?

2. Effective Partitioning

Partitioning divides one logical table into smaller physical pieces. It is most effective when the database can eliminate irrelevant partitions before scanning data.

The main goal is partition pruning: reduce the number of partitions that must be touched. Partitioning is not automatically faster just because the table is split.

2.1 Common partition strategies

Strategy Good for Typical example Risk
Range Time-series, logs, transactions Partition by month/day on created_at Hot recent partitions can become much larger than old ones
List Known discrete groups Partition by country or region Operational management becomes harder when values grow
Hash Distributing rows more evenly Hash by customer_id Not ideal for time-range pruning

2.2 Choose a partition key that appears in real query filters

Suppose a table is partitioned by month:

transactions
  ├── p_2026_06
  ├── p_2026_07
  ├── p_2026_08
  └── p_2026_09

This query can benefit strongly:

SELECT *
FROM transactions
WHERE created_at >= '2026-08-01'
  AND created_at <  '2026-09-01';

The optimizer may only scan the August partition.

If most queries do not filter by the partition key, partitioning may provide little pruning benefit. The engine may still need to inspect many or all partitions.

2.3 Avoid functions on the partition key when they block pruning

Risky 
WHERE DATE(created_at) = :date

Depending on the database and partition expression, this may make pruning harder.

Preferred 
WHERE created_at >= :startTime
  AND created_at <  :endTime

The predicate aligns directly with the range partition boundary.

2.4 Do not create too many partitions

More partitions are not always better. Thousands of tiny partitions can increase planning overhead, metadata complexity, maintenance cost, and operational risk.

Partition size should match the data lifecycle and common access pattern. For a large transaction table, monthly partitions may be better than daily partitions if daily pruning does not materially improve the workload.

2.5 Partitioning is also an operational tool

Partitioning can simplify:

  • Archiving old data
  • Dropping expired data quickly
  • Bulk loading
  • Maintenance on recent vs historical data
  • Managing very large tables
-- Conceptually much cheaper than:
DELETE FROM logs WHERE created_at < '2025-01-01';

-- If old data is in its own partition:
DROP PARTITION old_partition;

2.6 Partitioning checklist

  • Is the table large enough to justify partitioning?
  • Does the partition key appear in common filters?
  • Can queries achieve partition pruning?
  • Are partitions balanced enough?
  • Is the partition granularity operationally manageable?
  • Will unique keys and indexes work correctly with this partition scheme?
  • Does the design help retention, archiving, or maintenance?

3. How to Use JOIN Efficiently

Join performance depends on the amount of data being joined, the join algorithm chosen by the optimizer, available indexes, filter selectivity, data distribution, and memory.

3.1 Index important join keys

SELECT o.id, c.name
FROM orders o
JOIN customers c
  ON c.id = o.customer_id
WHERE o.created_at >= :fromDate;

Typical useful indexes:

customers(id)              -- often the primary key
orders(customer_id)
orders(created_at)
-- or possibly a composite index based on the full query pattern

The best index depends on which table is filtered first, data volume, and how the optimizer executes the join.

3.2 Join columns should use compatible data types

Problem 
users.id          BIGINT
orders.user_id    VARCHAR

Type conversion may occur during the join and reduce index efficiency.

Better 
users.id          BIGINT
orders.user_id    BIGINT

Matching types reduce unnecessary conversion and make statistics more reliable.

3.3 Filter as early as possible — but let the optimizer do its job

Write predicates that clearly reduce data. Modern optimizers can often push predicates down, but you should still avoid writing unnecessarily broad joins. 

SELECT o.id, p.name
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p     ON p.id = oi.product_id
WHERE o.created_at >= :fromDate
  AND o.status = 'PAID';

If orders can be reduced from 100 million rows to 100 thousand rows before the large join work, the optimizer has a much smaller problem.

3.4 Avoid functions and casts on join keys

Weak pattern 
JOIN customer c
  ON CAST(c.id AS VARCHAR) = o.customer_id
Better design 
JOIN customer c
  ON c.id = o.customer_id

Keep data types aligned at schema level.

3.5 Understand the main physical join algorithms

Algorithm Works well when Typical concern
Nested Loop Outer input is small and inner side has a good index Can become very expensive if outer rows are large
Hash Join Large equi-joins, enough memory, no useful ordered lookup Large hash tables may spill to disk
Merge Join Both inputs are sorted or naturally ordered by join key Sorting cost can be high if inputs are not already ordered
A senior engineer does not force one join algorithm by habit. They inspect the execution plan, row estimates, actual row counts, and I/O behavior.

3.6 Use EXISTS when you only need to test existence

Potentially unnecessary row expansion

SELECT DISTINCT c.id
FROM customers c
JOIN orders o
  ON o.customer_id = c.id
WHERE o.status = 'FAILED';

Clear existence intent

SELECT c.id
FROM customers c
WHERE EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.id
    AND o.status = 'FAILED'
);

Many optimizers transform these patterns intelligently, but EXISTS often expresses the business intent better: “return customers for whom at least one matching row exists.”

3.7 Be careful with many-to-many joins

If table A produces 1 million rows and table B produces 1 million matching rows with poor join selectivity, the intermediate result can explode. 

A filtered rows: 1,000,000
B filtered rows: 1,000,000
Poor join relationship
        ↓
Huge intermediate result
        ↓
Sort / hash / temp disk / memory pressure

Senior debugging should inspect row multiplication, not only whether an index exists.

3.8 Avoid application-level N+1 queries

SELECT * FROM orders WHERE customer_id = ?;

-- Then 500 times:
SELECT * FROM order_items WHERE order_id = ?;

This can create hundreds of database round trips. A well-designed join, batch fetch, or ORM fetch strategy can be much faster.

4. Should Partitioning Be Used Together with Indexes?

Yes, very often. Partitioning and indexing solve different parts of the problem. They are complementary, not substitutes.

Partition pruning Decides which partitions can be skipped entirely.
Index lookup Finds matching rows efficiently inside the remaining partition(s).
Result Reduce both the number of partitions and the number of rows scanned.

4.1 Example: transaction table

Table:

transactions(
  id,
  tenant_id,
  status,
  created_at,
  amount
)

Partition by month on created_at.

Query:

SELECT id, amount
FROM transactions
WHERE created_at >= '2026-08-01'
  AND created_at <  '2026-09-01'
  AND tenant_id = 42
  AND status = 'FAILED';

A good plan can conceptually work like this:

1. Partition pruning:
   Keep only August 2026 partition.

2. Inside August partition:
   Use index on (tenant_id, status, created_at)
   or another index designed for the real query pattern.

3. Return a small result set.
Partition removes large regions of data.
Index finds specific rows inside the remaining region.

4.2 When partitioning alone may be enough

If each partition is already small and a query reads most rows in one partition, an index may provide limited value. 

SELECT SUM(amount)
FROM daily_metrics
WHERE metric_date = '2026-08-29';

If the daily partition contains only the rows needed for the aggregation, a sequential scan of that one partition can be efficient.

4.3 When an index alone may be enough

If the table is not extremely large and indexed lookups already return very few rows, partitioning may add unnecessary operational complexity. 

SELECT *
FROM users
WHERE email = ?;

A unique index on email is normally far more relevant than partitioning the users table by registration date.

4.4 Local vs global indexes

Some database engines support different index relationships with partitions:

Index type Concept Trade-off
Local / partition-aligned index Each partition has its own corresponding index Easier partition maintenance; queries may need pruning to avoid many index probes
Global index One logical index can span multiple partitions Useful for cross-partition lookup, but maintenance can be more complex
Support and behavior differ across PostgreSQL, MySQL, Oracle, SQL Server, and other databases. Treat “local/global index” rules as database-specific implementation details.

4.5 Do I need to include the partition key in every index?

Not always. The answer depends on:

  • The database engine
  • Unique constraint rules
  • Whether indexes are local or global
  • Common query patterns
  • Whether the query already prunes to one partition

Example: if the query always filters by created_at and partition pruning already selects one monthly partition, an index inside that partition might focus on (tenant_id, status). But another workload may benefit from including created_at in the index for sorting or range filtering.

Senior answer: do not add the partition key to every index by rule. Design the index from the access pattern, then validate with the execution plan.

5. Senior Interview Questions and Answers

These answers are written in the style expected from a senior backend engineer: explain the decision, trade-off, and how you would validate it in production.

Q1. Should we create an index on every column used in a WHERE clause?

Senior answer

No. I first look at query frequency, table size, selectivity, and whether an existing composite index already covers the query. An index improves reads but adds write, storage, and maintenance cost. I usually start from the top queries by latency or load, inspect their execution plans, then add the smallest useful index that solves a real bottleneck.

Q2. Is an index on a boolean or status column useful?

Senior answer

It depends on data distribution. If a boolean column is 50/50 or one value represents most rows, a standalone B-tree index may not be selective enough. But it can still be useful as part of a composite index, a partial/filtered index in supported databases, or when one value represents a very small subset. I decide based on the actual distribution and query plan, not only cardinality.

Q3. Why can a function on an indexed column make a query slow?

Senior answer

Because a normal B-tree index stores the original column values in sorted order. If I write DATE(created_at), LOWER(email), CAST(user_id ...), price * 1.1, or another expression on the indexed column, the optimizer may no longer be able to search the original index directly. It may need to evaluate the function for many rows, resulting in an index scan or full table scan instead of an efficient index seek/range scan.

My first choice is to rewrite the condition so the indexed column remains unchanged, for example replacing DATE(created_at) = :date with a start/end timestamp range. If the expression is genuinely required, I consider an expression/function-based index or a generated column, depending on the database. Finally, I confirm the behavior using the actual execution plan rather than assuming the index is used.

Q4. How do you choose the order of columns in a composite index?

Senior answer

I start from the real query patterns. Equality filters usually come first, followed by range columns. I also consider whether the index should support ordering, joining, or covering the query. I do not blindly put the “most selective” column first because a column can be selective but still not match the query’s leading predicate pattern.

Q5. If a table is partitioned, do we still need indexes?

Senior answer

Very often, yes. Partitioning and indexing operate at different levels. Partition pruning removes irrelevant partitions, while an index finds rows efficiently inside the remaining partition. For a huge time-partitioned transaction table, I may prune to one month and then use an index on tenant, status, or account inside that month. But if the query reads most rows from the selected partition, a sequential scan can still be cheaper.

Q6. Can partitioning make performance worse?

Senior answer

Yes. If the partition key does not match query filters, the database may touch many partitions. Too many small partitions can increase planning and metadata overhead. Poor partition design can also complicate unique constraints, indexes, maintenance, and data movement. I use partitioning when it provides measurable pruning or lifecycle benefits, not only because the table is large.

Q7. Is it always necessary to put the partition key in the WHERE clause?

Senior answer

It is not syntactically required, but from a performance perspective it is often important because it enables partition pruning. If a query frequently omits the partition key, I ask whether the partition strategy matches the workload. Sometimes we need a different partition key, a global index, a routing layer, or a different table design.

Q8. What should be indexed in a JOIN?

Senior answer

Primary keys are usually already indexed. On the referencing side, foreign-key or join columns often need indexes, especially when the joined table is large. But I also look at filters applied before the join. For example, an index like (status, created_at, customer_id) may be more useful than only (customer_id) if the query first narrows orders by status and time.

Q9. Why can a JOIN still be slow even when both join columns are indexed?

Senior answer

Indexes are only one factor. The query may still return too many rows, the join can multiply rows, statistics may be stale, data types may require casts, the optimizer may estimate cardinality incorrectly, a hash join may spill to disk, or an ORDER BY / GROUP BY may dominate the cost. I always inspect the full execution plan and actual row counts.

Q10. INNER JOIN vs EXISTS — which is faster?

Senior answer

There is no universal winner because optimizers can transform both forms. I use EXISTS when I only need to know whether a related row exists, and a normal join when I need columns from the related table. Then I validate the actual execution plan instead of assuming one syntax is always faster.

Q11. What is your process when a query is slow in production?

Senior answer

First I capture the SQL, bind values, latency, frequency, and rows returned. Then I inspect the actual execution plan, not only the estimated plan. I look for full scans, bad join order, row-estimation errors, large sorts, hash spills, non-SARGable predicates, missing or unused indexes, partition pruning, lock waits, and I/O. After changing an index or query, I compare before/after execution plans and production-like data volumes.

Q12. When would you prefer a full table or partition scan over an index?

Senior answer

When the query needs a large percentage of the rows, sequential I/O can be cheaper than many random index lookups. For analytics over most rows in one partition, a partition scan may be the correct plan. “Index used” is not the goal; lower total work and lower latency are the goal.

Q13. Is a subquery slower than a JOIN?

Senior answer

Not necessarily. Modern optimizers often rewrite subqueries into joins or semi-joins. I choose the form that expresses the requirement clearly, then inspect the plan. Correlated subqueries can be expensive if they effectively execute repeated work per row, but even that depends on whether the optimizer can decorrelate the query.

Q14. A query already filters by the partition key. Should I still add an index?

Senior answer

I check how much data remains after pruning. If pruning selects one partition with 50 million rows and the query needs only 100 rows, an index can still provide a major benefit. If the query needs 80% of that partition, an index may not help. Partition pruning answers “which partition?”; indexing answers “which rows inside it?”

Q15. How do you know an index is really useful?

Senior answer

I verify it with the execution plan, actual execution statistics, logical/physical reads, latency, CPU, rows scanned, and workload-level impact. I also monitor write cost and index size. A useful index should improve an important workload without creating a larger regression elsewhere.

6. Practical Senior Checklist

Index

  • Optimize real queries, not columns in isolation.
  • Check selectivity and data distribution.
  • Use composite indexes intentionally.
  • Keep predicates SARGable.
  • Avoid overlapping / unused indexes.
  • Measure read benefit vs write cost.

Partition

  • Choose key from real filter patterns.
  • Verify partition pruning.
  • Avoid excessive partition counts.
  • Use partitioning for lifecycle management too.
  • Check unique/index rules in your DB engine.

Join

  • Index important join/filter keys.
  • Keep join data types compatible.
  • Reduce rows before expensive joins.
  • Watch many-to-many row explosion.
  • Inspect join algorithm and spills.
  • Use EXPLAIN / actual plans.
Final principle: Never optimize a database only by rules of thumb. Use rules to create a hypothesis, then validate it with the execution plan, realistic data, production metrics, and the actual workload.
Note: SQL syntax and optimizer behavior differ across PostgreSQL, MySQL, Oracle, SQL Server, and other systems. The design principles in this guide are general; engine-specific implementation details should always be validated.
