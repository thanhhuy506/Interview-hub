1. Core concepts you should say correctly in an interview

Deployment means putting a new version into an environment. Release means making a capability available to users. They can happen at different times.

1. Những khái niệm nền tảng cần nói đúng khi phỏng vấn

Deployment là đưa version mới vào environment. Release là cho user thực sự sử dụng tính năng. Hai việc này có thể diễn ra ở hai thời điểm khác nhau.

Deployment

Move/build/run version v2 in production.

Đưa/build/chạy version v2 trên production.

Release

Expose the feature to users, often controlled by a feature flag.

Mở tính năng cho user, thường được điều khiển bởi feature flag.

Rollout

Gradually change the percentage of traffic or hosts using the new version.

Tăng dần phần trăm traffic hoặc số host sử dụng version mới.

Interview point
A senior answer should discuss not only “how to deploy”, but also blast radius, rollback speed, backward compatibility, observability, traffic control, infrastructure cost, and database migration.
Câu trả lời senior không chỉ nói “deploy thế nào”, mà nên nói thêm về blast radius, tốc độ rollback, backward compatibility, observability, traffic control, chi phí hạ tầng và database migration.

3. Detailed deployment strategies

3. Chi tiết từng deployment strategy

1 Recreate / Big-Bang Deployment

v1: ██████████ stop v1 deploy v2 v2: ██████████

How it works: stop all old instances, then start the new version.

  • Pros: simple, cheap, easy to understand.
  • Cons: downtime; high blast radius; rollback can be slow.

Use when: internal systems, development/test, scheduled maintenance, small non-critical applications, or versions that cannot coexist.

Avoid when: public APIs, 24/7 services, payment/order systems, strict SLA.

Cách hoạt động: dừng toàn bộ instance cũ rồi mới khởi động version mới.

  • Ưu: đơn giản, rẻ, dễ vận hành.
  • Nhược: có downtime; blast radius lớn; rollback có thể chậm.

Dùng khi: hệ thống nội bộ, dev/test, maintenance window, app nhỏ không critical, hoặc 2 version không thể chạy song song.

Không nên dùng: public API, hệ thống 24/7, payment/order, SLA cao.

2 Rolling Deployment / Rolling Update

Step 1: v1 v1 v1 v1 Step 2: v2 v1 v1 v1 Step 3: v2 v2 v1 v1 Step 4: v2 v2 v2 v2

How it works: replace instances gradually. Old and new versions run together during the rollout.

  • Pros: near-zero downtime; no duplicate full environment; native in Kubernetes.
  • Cons: mixed-version compatibility is required; rollback is not instant; bugs can affect traffic while rollout proceeds.

Use when: default choice for stateless services with backward-compatible APIs and DB changes.

Key controls: maxSurge, maxUnavailable, readiness probe, health checks.

Cách hoạt động: thay từng nhóm instance từ v1 sang v2. Trong lúc rollout, cả v1 và v2 cùng chạy.

  • Ưu: gần như zero downtime; không cần dựng full environment thứ hai; Kubernetes hỗ trợ sẵn.
  • Nhược: v1/v2 phải tương thích; rollback không tức thời; bug vẫn có thể nhận traffic trong rollout.

Dùng khi: lựa chọn mặc định cho stateless service, API và DB change backward-compatible.

Điểm cần nhớ: maxSurge, maxUnavailable, readiness probe, health checks.

3 Blue–Green / Red–Black Deployment

BLUE = v1 ← 100% traffic GREEN = v2 ← 0% validate GREEN BLUE = v1 ← 0% GREEN = v2 ← 100%

How it works: maintain two production-like environments. Deploy and test the inactive environment, then switch traffic.

  • Pros: very fast cutover and rollback; clean separation; excellent for high-risk releases.
  • Cons: roughly 2× runtime capacity during deployment; DB/stateful systems are harder.

Use when: fast rollback matters, releases are less frequent but high impact, enough infrastructure budget exists.

Important: traffic switch can be done via load balancer, ingress, service selector, DNS, or routing layer.

Cách hoạt động: duy trì hai environment production-like. Deploy/test ở environment đang inactive, sau đó switch traffic.

  • Ưu: cutover và rollback rất nhanh; tách biệt rõ; phù hợp release rủi ro cao.
  • Nhược: tốn gần gấp đôi capacity trong thời gian deploy; khó hơn với DB/stateful system.

Dùng khi: cần rollback nhanh, release ít nhưng ảnh hưởng lớn, ngân sách infrastructure đủ.

Lưu ý: switch traffic có thể bằng load balancer, ingress, service selector, DNS hoặc routing layer.

4 Canary Deployment

v1 95% ─────────────┐ ├─ users v2 5% ─────────────┘ 5% → 10% → 25% → 50% → 100%

How it works: send a small percentage of real traffic to v2, observe metrics, then progressively increase traffic.

  • Pros: small blast radius; detects production-only problems; supports automated promotion/rollback.
  • Cons: complex routing/metrics; both versions must coexist; requires strong observability.

Use when: large-scale consumer systems, risky changes, high traffic, strong SRE/observability maturity.

Typical success metrics: error rate, p95/p99 latency, CPU, memory, conversion, payment success, business KPI.

Cách hoạt động: gửi một phần nhỏ traffic thật vào v2, theo dõi metrics, sau đó tăng dần traffic.

  • Ưu: blast radius nhỏ; phát hiện lỗi chỉ xuất hiện trên production; có thể tự động promote/rollback.
  • Nhược: routing và metrics phức tạp; v1/v2 phải cùng tồn tại; cần observability tốt.

Dùng khi: hệ thống consumer lớn, thay đổi rủi ro, traffic cao, đội có SRE/observability tốt.

Metrics thường theo dõi: error rate, p95/p99 latency, CPU, memory, conversion, payment success, business KPI.

5 A/B Testing

Group A → version/experience A Group B → version/experience B Measure → conversion / behavior

Purpose: product experimentation, not primarily deployment safety.

Traffic is split by a deliberate user attribute or experiment cohort, not just random rollout percentage.

  • Pros: compare user behavior and business outcomes.
  • Cons: experiment contamination, data analysis complexity, sticky routing may be required.

Use when: deciding which UX, pricing flow, recommendation algorithm, or business behavior performs better.

Mục đích: product experimentation, không phải chủ yếu để giảm rủi ro deployment.

Traffic được chia theo nhóm user/experiment cohort, thay vì chỉ chia ngẫu nhiên theo % rollout.

  • Ưu: so sánh hành vi user và business outcome.
  • Nhược: phân tích dữ liệu phức tạp, có thể cần sticky routing, dễ bị nhiễu experiment.

Dùng khi: chọn UX, pricing flow, recommendation algorithm hoặc business behavior tốt hơn.

6 Shadow / Mirroring Deployment

User → v1 → real response │ └──── copy request ───→ v2 response ignored

How it works: mirror production traffic to v2, but users still receive the response from v1.

  • Pros: validate performance and behavior using realistic traffic with almost no user impact.
  • Cons: dangerous for side effects; doubles downstream load; data privacy must be considered.

Use when: major refactor, new search engine, new recommendation service, JVM/runtime upgrade, performance validation.

Critical: shadow requests must not create real orders, charge cards, send emails, or mutate production data unless side effects are isolated.

Cách hoạt động: copy traffic production sang v2 nhưng response trả cho user vẫn lấy từ v1.

  • Ưu: test bằng traffic thật mà gần như không ảnh hưởng user.
  • Nhược: nguy hiểm với side effect; có thể tăng gấp đôi load downstream; phải chú ý dữ liệu nhạy cảm.

Dùng khi: refactor lớn, search engine mới, recommendation service mới, nâng JVM/runtime, kiểm thử performance.

Rất quan trọng: shadow request không được tạo order thật, charge card, gửi email hoặc mutate production data nếu chưa cô lập side effect.

7 Feature Flag / Dark Launch

deploy code v2 → feature OFF ↓ enable for staff ↓ 1% users → 10% → 100%

Key idea: separate deployment from release. Code can be in production while the feature remains disabled.

  • Pros: quick enable/disable; business-controlled rollout; supports canary by user cohort.
  • Cons: stale flags create technical debt; combinatorial testing becomes difficult.

Use when: features must be released independently from deployment, coordinated launches, kill switches, beta users.

Ý chính: tách deployment khỏi release. Code đã ở production nhưng feature vẫn có thể OFF.

  • Ưu: bật/tắt nhanh; business có thể kiểm soát rollout; hỗ trợ canary theo nhóm user.
  • Nhược: flag cũ tạo technical debt; số tổ hợp cần test tăng mạnh.

Dùng khi: muốn release độc lập với deployment, coordinated launch, kill switch, beta users.

8 Immutable Deployment

old VM/image/container: do not patch build new artifact/image create new instances switch traffic destroy old instances

How it works: never mutate running infrastructure in place. Build a new image/container/VM and replace the old one.

  • Pros: reproducible, less configuration drift, easier rollback and auditing.
  • Cons: image pipeline and infrastructure automation are required.

Use when: cloud-native systems, Docker/Kubernetes, autoscaling groups, strict consistency between environments.

Cách hoạt động: không patch trực tiếp instance đang chạy. Build image/container/VM mới rồi thay thế instance cũ.

  • Ưu: reproducible, giảm configuration drift, dễ rollback/audit.
  • Nhược: cần image pipeline và infrastructure automation tốt.

Dùng khi: cloud-native, Docker/Kubernetes, autoscaling group, cần consistency cao giữa các environment.

9 In-Place Deployment

server A: v1 → patch/install → v2 server B: v1 → patch/install → v2

How it works: update software on existing servers rather than replacing them.

  • Pros: low infrastructure cost; common on legacy/on-prem systems.
  • Cons: configuration drift, harder rollback, partially updated servers, manual-state risk.

Use when: legacy applications, expensive stateful hosts, on-prem constraints.

Cách hoạt động: cập nhật phần mềm trực tiếp trên server hiện tại thay vì tạo server mới.

  • Ưu: chi phí infrastructure thấp; phổ biến ở legacy/on-prem.
  • Nhược: configuration drift, rollback khó, dễ có server cập nhật dở dang.

Dùng khi: legacy app, stateful host đắt tiền, môi trường on-prem bị giới hạn.

10 Ring / Wave Deployment

Ring 0: internal users Ring 1: 1 region / low-risk customers Ring 2: 10–25% Ring 3: global rollout

How it works: roll out by groups of machines, regions, tenants, or customer risk levels.

  • Pros: controlled blast radius; ideal for multi-region and enterprise SaaS.
  • Cons: longer deployment window; version skew across rings.

Use when: multi-region systems, desktop agents, enterprise tenants, infrastructure changes.

Cách hoạt động: rollout theo từng nhóm máy, region, tenant hoặc mức độ rủi ro của customer.

  • Ưu: kiểm soát blast radius tốt; phù hợp multi-region và enterprise SaaS.
  • Nhược: thời gian rollout dài; nhiều version cùng tồn tại giữa các ring.

Dùng khi: hệ thống multi-region, desktop agent, enterprise tenant, infrastructure change.

11 Progressive Delivery

deploy → 5% observe metrics → auto promote 20% observe → 50% → 100% or auto rollback

Definition: an operational approach that combines staged rollout, metrics, policy, feature flags, and automation. Canary is a common implementation.

  • Pros: data-driven releases; automatic risk control.
  • Cons: requires mature telemetry, SLOs, routing, and automation.

Typical tools/concepts: Argo Rollouts, Flagger, service mesh, feature-flag platforms, SLO gates.

Định nghĩa: cách vận hành kết hợp staged rollout, metrics, policy, feature flag và automation. Canary là một cách triển khai phổ biến.

  • Ưu: release dựa trên dữ liệu; tự động kiểm soát rủi ro.
  • Nhược: cần telemetry, SLO, routing và automation trưởng thành.

Công cụ/khái niệm thường gặp: Argo Rollouts, Flagger, service mesh, feature-flag platform, SLO gate.

12 Hybrid Strategy

Immutable infrastructure + Blue/Green environment + Canary traffic shift + Feature Flags

Real systems often combine strategies rather than choose only one.

Example: deploy immutable container images into a green environment, send 5% canary traffic, then switch 100%, while risky features remain behind flags.

This is often the strongest senior-level answer: strategies are composable.

Hệ thống thực tế thường kết hợp nhiều strategy thay vì chỉ chọn một.

Ví dụ: deploy immutable container image vào Green, cho 5% canary traffic, sau đó switch 100%, còn feature rủi ro vẫn nằm sau feature flag.

Đây là điểm trả lời senior rất tốt: các strategy có thể kết hợp với nhau.

Most important differences

  • Rolling vs Blue–Green: Rolling replaces instances gradually. Blue–Green prepares a full second environment then switches traffic. Blue–Green rollback is usually faster, but costs more.
  • Blue–Green vs Canary: Blue–Green changes environment/traffic mostly as a cutover. Canary intentionally exposes only a small percentage first and grows gradually.
  • Canary vs A/B: Canary optimizes deployment safety. A/B optimizes product learning.
  • Canary vs Shadow: Canary users receive responses from v2. Shadow users do not; v2 responses are ignored or compared offline.
  • Deployment strategy vs Feature Flag: deployment controls which code is running; a flag controls which behavior is enabled.
  • Immutable vs Blue–Green: immutable describes how infrastructure is replaced; Blue–Green describes how environments/traffic are switched. They can be used together.

Những khác biệt quan trọng nhất

  • Rolling vs Blue–Green: Rolling thay instance từ từ. Blue–Green dựng full environment thứ hai rồi switch traffic. Blue–Green rollback nhanh hơn nhưng tốn tài nguyên hơn.
  • Blue–Green vs Canary: Blue–Green thường cutover traffic giữa hai environment. Canary cố tình chỉ đưa một lượng traffic nhỏ vào version mới rồi tăng dần.
  • Canary vs A/B: Canary tối ưu deployment safety. A/B tối ưu product learning.
  • Canary vs Shadow: Canary user nhận response từ v2. Shadow thì không; response của v2 bị bỏ qua hoặc chỉ dùng để so sánh.
  • Deployment strategy vs Feature Flag: deployment quyết định code nào đang chạy; feature flag quyết định behavior nào được bật.
  • Immutable vs Blue–Green: immutable nói về cách thay infrastructure; Blue–Green nói về cách switch environment/traffic. Có thể dùng chung.

6. Database migration — where deployments often fail

6. Database migration — nơi deployment thường gặp lỗi

Expand → Migrate → Contract

1. EXPAND Add new schema in backward-compatible way. 2. MIGRATE Deploy code that can work with old + new schema. Backfill data. 3. SWITCH New code starts using new schema. 4. CONTRACT Remove old column/table/API only after old code is gone.

This pattern is essential for Rolling, Canary, and Blue–Green because multiple application versions may coexist.

Unsafe example: rename or drop column customer_name in the same release that deploys code expecting full_name. Old pods may still require customer_name.

Safer approach: add full_name, dual-read/write if needed, backfill, migrate traffic, verify, then remove the old column in a later release.

Pattern này cực kỳ quan trọng với Rolling, Canary và Blue–Green vì có thể tồn tại nhiều version application cùng lúc.

Ví dụ nguy hiểm: rename/drop cột customer_name ngay trong release deploy code mới dùng full_name. Pod cũ vẫn có thể cần customer_name.

Cách an toàn hơn: add full_name, dual-read/write nếu cần, backfill data, migrate traffic, verify rồi mới xóa cột cũ ở release sau.

Backward compatibility

New database/API changes should continue to support the old version during the rollout window.

DB/API mới vẫn nên support version cũ trong khoảng thời gian rollout.

Forward compatibility

Old consumers tolerate new fields or messages when possible.

Consumer cũ nên tolerate field/message mới nếu có thể.

Event schema

Kafka/event changes need versioning and tolerant consumers; do not assume every consumer upgrades together.

Kafka/event schema cần versioning và tolerant consumer; không nên giả định tất cả consumer upgrade cùng lúc.

Rollback limitation

Application rollback may be easy while database rollback is not. Prefer roll-forward-compatible migrations.

Rollback application có thể dễ nhưng rollback DB thì khó. Nên ưu tiên migration tương thích để có thể roll forward.

7. Kubernetes interview notes

7. Kiến thức Kubernetes khi phỏng vấn

RollingUpdate

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0

maxSurge: how many extra pods can be created above desired replicas.

maxUnavailable: how many desired pods may be unavailable during rollout.

maxSurge: cho phép tạo thêm bao nhiêu pod vượt replica mong muốn.

maxUnavailable: trong rollout được phép thiếu tối đa bao nhiêu pod.

Readiness vs Liveness

Readiness probe: controls whether a pod receives traffic.

Liveness probe: decides whether Kubernetes should restart the container.

Startup probe: protects slow-starting applications from premature liveness failures.

Readiness probe: quyết định pod có được nhận traffic hay không.

Liveness probe: quyết định Kubernetes có restart container hay không.

Startup probe: bảo vệ app khởi động chậm khỏi bị liveness restart quá sớm.

Graceful shutdown

On termination: stop accepting new requests, finish in-flight requests, close resources, then exit before terminationGracePeriodSeconds.

In Spring Boot, configure graceful shutdown and make readiness fail before process exit.

Khi terminate: ngừng nhận request mới, xử lý xong request đang chạy, đóng resource rồi exit trước terminationGracePeriodSeconds.

Với Spring Boot nên bật graceful shutdown và remove pod khỏi readiness trước khi process exit.

Canary in Kubernetes

Basic Kubernetes Deployment does not provide advanced weighted traffic shifting by itself. Common solutions use multiple Services/Ingress rules, service mesh, or rollout controllers such as Argo Rollouts.

Kubernetes Deployment cơ bản không tự cung cấp weighted traffic shifting nâng cao. Thường dùng nhiều Service/Ingress rule, service mesh hoặc rollout controller như Argo Rollouts.

8. A production-grade CI/CD deployment flow

8. Flow CI/CD production-grade

Commit / PR ↓ Compile + Unit Test + Static Analysis ↓ Build immutable artifact / Docker image ↓ Security / dependency scan ↓ Deploy to staging ↓ Integration / API / contract / smoke tests ↓ Approval or automated policy gate ↓ Production rollout ↓ Health checks + metrics + logs + traces ↓ Promote ──────────────┐ or rollback / disable ┘

Good production gates

  • Error rate does not exceed baseline/SLO threshold.
  • p95/p99 latency remains within limit.
  • CPU/memory/thread pool/DB pool remain healthy.
  • No abnormal increase in downstream failures.
  • Business KPI remains healthy: payment success, order completion, login success, etc.
  • Smoke test and synthetic test pass after deployment.

Những gate nên có trên production

  • Error rate không vượt baseline/SLO threshold.
  • p95/p99 latency nằm trong giới hạn.
  • CPU/memory/thread pool/DB pool ổn định.
  • Không tăng bất thường lỗi từ downstream.
  • Business KPI ổn định: payment success, order completion, login success...
  • Smoke test và synthetic test pass sau deployment.

9. Interview questions & strong answers

9. Câu hỏi phỏng vấn & cách trả lời tốt

Q1. Rolling deployment vs Blue–Green — what is the difference?

Strong answer: Rolling replaces instances incrementally, so old and new versions coexist. It uses less extra infrastructure but requires backward compatibility and rollback takes some time. Blue–Green prepares a full second environment and switches traffic after validation. It costs more, but cutover and rollback are much faster. I normally use Rolling for standard stateless services and Blue–Green when rollback speed or release isolation is more important.

Trả lời: Rolling thay instance từ từ nên version cũ và mới cùng tồn tại. Chi phí hạ tầng thấp hơn nhưng cần backward compatibility và rollback mất một khoảng thời gian. Blue–Green chuẩn bị một full environment thứ hai rồi switch traffic sau khi validate. Tốn resource hơn nhưng cutover và rollback rất nhanh. Tôi thường dùng Rolling cho stateless service bình thường và Blue–Green khi tốc độ rollback hoặc isolation quan trọng hơn.

Q2. Canary vs Blue–Green?

Blue–Green mainly isolates two environments and often switches most or all traffic in one controlled cutover. Canary focuses on risk reduction by exposing only a small portion of real traffic to the new version first. Canary needs stronger metrics and traffic routing, while Blue–Green needs more infrastructure capacity.

Blue–Green chủ yếu tách hai environment và thường switch phần lớn hoặc toàn bộ traffic trong một cutover có kiểm soát. Canary tập trung giảm rủi ro bằng cách chỉ cho một lượng traffic nhỏ vào version mới trước. Canary cần metrics và routing tốt hơn, còn Blue–Green tốn infrastructure hơn.

Q3. Canary vs A/B Testing?

Canary answers “is this new version safe enough to roll out further?” A/B testing answers “which experience performs better for a selected cohort?” Canary is operational safety; A/B is product experimentation.

Canary trả lời “version mới có đủ an toàn để tăng rollout không?”. A/B trả lời “trải nghiệm nào tốt hơn cho nhóm user nhất định?”. Canary là operational safety, A/B là product experimentation.

Q4. How do you deploy with zero downtime?

I would combine several controls: multiple healthy replicas, Rolling or Blue–Green/Canary rollout, readiness probes, graceful shutdown, load-balancer draining, backward-compatible APIs and database migrations, sufficient capacity, and post-deployment health checks. Zero downtime is not only a deployment setting; it depends on application lifecycle, networking, database compatibility, and observability.

Tôi sẽ kết hợp nhiều cơ chế: nhiều replica healthy, Rolling hoặc Blue–Green/Canary, readiness probe, graceful shutdown, load-balancer draining, API và DB migration backward-compatible, capacity đủ và health check sau deploy. Zero downtime không chỉ là một setting deployment; nó phụ thuộc cả application lifecycle, network, database compatibility và observability.

Q5. What can go wrong with Rolling Deployment?
  • Old and new instances are incompatible.
  • Database migration breaks old pods.
  • Readiness becomes green too early.
  • Insufficient capacity while pods restart.
  • Sticky sessions break user flow.
  • Long-running requests are terminated without graceful shutdown.
  • Versioned events/messages are not compatible.
  • Version cũ và mới không tương thích.
  • DB migration làm pod cũ bị lỗi.
  • Readiness báo healthy quá sớm.
  • Không đủ capacity khi pod restart.
  • Sticky session làm flow user bị lỗi.
  • Long-running request bị terminate do thiếu graceful shutdown.
  • Event/message giữa các version không tương thích.
Q6. What is your preferred production deployment strategy?

There is no single best strategy. For a normal stateless Java service on Kubernetes, Rolling Update is usually my default because it balances availability, simplicity, and cost. For high-risk changes I prefer Canary with metrics-based promotion, and for releases where rollback speed is the highest priority I consider Blue–Green. I also separate deployment from release with feature flags when business rollout needs independent control.

Không có một strategy tốt nhất cho mọi trường hợp. Với Java stateless service trên Kubernetes, Rolling Update thường là default vì cân bằng availability, độ đơn giản và chi phí. Với thay đổi rủi ro cao tôi ưu tiên Canary có metrics-based promotion, còn khi rollback speed là ưu tiên cao nhất tôi cân nhắc Blue–Green. Tôi cũng tách deployment khỏi release bằng feature flag khi business cần kiểm soát rollout độc lập.

Q7. How would you rollback a failed release?

First I stop further rollout and protect users. Depending on the mechanism, I switch traffic back to Blue, reduce canary weight to zero, roll back the Kubernetes Deployment, or disable the feature flag. Then I confirm recovery using error rate, latency, business KPIs and logs/traces. Database rollback is more dangerous, so I prefer backward-compatible schema changes that allow application rollback without reverting data.

Đầu tiên tôi dừng rollout tiếp và bảo vệ user. Tùy cơ chế, tôi switch traffic về Blue, giảm canary weight về 0, rollback Kubernetes Deployment hoặc tắt feature flag. Sau đó xác nhận hệ thống phục hồi bằng error rate, latency, business KPI, logs/traces. Rollback DB nguy hiểm hơn nên tôi ưu tiên schema change backward-compatible để application rollback mà không cần revert dữ liệu.

Q8. What metrics do you monitor during deployment?

I monitor technical and business signals together: HTTP 5xx/4xx anomalies, request rate, p95/p99 latency, CPU, memory, GC, JVM thread pools, DB connection pool, downstream errors, queue lag, and business KPIs such as login, order or payment success. The exact rollback threshold should ideally be defined against SLOs or a known baseline.

Tôi theo dõi cả technical và business signal: HTTP 5xx/4xx bất thường, request rate, p95/p99 latency, CPU, memory, GC, JVM thread pool, DB connection pool, downstream error, queue lag và business KPI như login/order/payment success. Rollback threshold nên được định nghĩa dựa trên SLO hoặc baseline đã biết.
