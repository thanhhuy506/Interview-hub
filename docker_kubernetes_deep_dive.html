Docker + Kubernetes, from process isolation to production microservices

The goal is not to memorize commands. The goal is to understand what happens inside Linux, inside Docker Engine, inside a Kubernetes cluster, and on the network when one microservice talks to another.

01 - Start here

The mental model: containers are isolated processes, not tiny virtual machines

A container normally runs as one or more ordinary Linux processes on the host kernel. Isolation is created by kernel primitives. Docker packages and manages those primitives. Kubernetes does not replace Docker's low-level container concept; Kubernetes orchestrates large numbers of containers through a container runtime.

Virtual machine

Hypervisor provides virtual hardware. Each VM usually boots a full guest OS and its own kernel.

Guest kernelVirtual hardwareStrong boundary

Container

Processes share the host kernel but receive isolated views of PID, network, filesystem, hostname and other resources.

Shared kernelNamespacescgroups
Illustration: VM vs containerWhy containers start faster
Critical relationship: you can build an OCI-compatible image with Docker, push it to a registry, and run it on Kubernetes nodes using containerd or CRI-O. Kubernetes does not require the Docker daemon to be present on worker nodes.
02 - Docker architecture

Docker components and what each one owns

Docker CLI

docker build, docker run, docker ps. The CLI is a client. It sends requests to Docker Engine's API.

dockerd

The long-running Docker daemon. It manages high-level Docker objects: images, containers, networks, volumes and API requests.

Docker API

HTTP API, commonly exposed locally through a Unix socket. Remote access is possible but must be secured.

containerd

Container lifecycle and image management layer used by Docker Engine. It manages tasks, images and low-level runtime integration.

runc

OCI runtime that creates the actual containerized process according to an OCI runtime specification.

Registry

Stores image manifests, metadata and content-addressed layers. Docker Hub and private registries are examples.

ObjectWhat it meansTypical lifetime
ImageImmutable template composed from layers plus metadata.Until removed from local cache/registry.
ContainerRuntime instance of an image with a writable layer and isolated process environment.Start, stop, restart, remove.
VolumeDocker-managed persistent data outside the container writable layer.Independent from container lifecycle.
NetworkConnectivity domain managed by a network driver.Independent object; containers attach/detach.
Security: access to the Docker daemon socket is highly privileged. Treat membership in the Docker administration path as effectively host-level control unless you deliberately use a constrained/rootless architecture.
03 - Docker internals

What really happens when you run docker run

CLI sends an API request.
The CLI resolves flags such as image name, ports, volumes, environment variables and resource limits, then talks to the daemon.
dockerd resolves the image.
If image content is not present locally, the engine pulls the manifest and required layers from a registry.
Runtime creates a container filesystem view.
Read-only image layers are combined with a writable container layer or snapshot.
Isolation and limits are prepared.
Linux namespaces, cgroups, capabilities, seccomp/AppArmor/SELinux configuration and mount points are prepared according to configuration.
Networking is attached.
A network namespace and interfaces are created. For bridge networking, a veth pair connects the container namespace to a host bridge.
containerd invokes an OCI runtime such as runc.
runc asks the kernel to create the isolated process. A shim remains involved in lifecycle and I/O management after the initial creation.
The configured process becomes PID 1 inside the container namespace.
It is still a host process with a normal host PID, but it sees a different PID namespace.
Sequence: docker run nginxControl path to the Linux kernel
04 - Images

Images, layers, copy-on-write and registries

An image is not one giant archive copied for every container. It is a set of content-addressed filesystem layers plus metadata. Multiple images and containers can share the same immutable layer content.

Layer

A filesystem delta produced by a build step. Content is addressed by digest, so identical content can be reused.

Manifest

Describes image configuration and references layers. Multi-platform indexes can point to architecture-specific manifests.

Writable layer

A running container gets a writable top layer/snapshot. Writes do not mutate the underlying image.

Overlay filesystem mental model

base image layer+runtime/JDK layer+application layer+container writable layer=>merged root filesystem
Important: on modern Docker Engine installations the exact image storage backend may be containerd's image store/snapshotters rather than the older classic graph-driver model. The conceptual rule is unchanged: immutable shared image content plus a writable container view.

Production-friendly Java Dockerfile

# syntax=docker/dockerfile:1
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY . .
RUN ./mvnw -q -DskipTests package

FROM eclipse-temurin:21-jre
WORKDIR /app
RUN useradd -r -u 10001 appuser
COPY --from=build /src/target/app.jar /app/app.jar
USER 10001
EXPOSE 8080
ENTRYPOINT ["java","-jar","/app/app.jar"]

Good build habits

  • Use a small trusted base image.
  • Pin critical dependencies or use digest policies where appropriate.
  • Use multi-stage builds.
  • Keep build context small with .dockerignore.
  • Run as non-root.
  • Do not bake secrets into layers.

Why layer order matters

Docker/BuildKit can reuse unchanged build cache. Put slowly-changing dependency steps before frequently-changing source code when your build system allows it.

05 - Linux isolation

Namespaces isolate what a process can see; cgroups control what it can consume

PrimitivePurposeContainer effect
PID namespaceProcess ID isolationContainer has its own process tree; its main process can appear as PID 1 inside.
Network namespaceInterfaces, routes, ports, firewall contextContainer can have its own eth0, IP, routes and localhost.
Mount namespaceFilesystem mount viewContainer sees its rootfs and mounted volumes.
UTS namespaceHostname/domain isolationContainer can have its own hostname.
IPC namespaceShared memory/semaphore isolationLimits IPC visibility between workloads.
User namespaceUID/GID mappingContainer root can be mapped to an unprivileged host ID when configured.
cgroupsResource accounting and limitsCPU, memory and other resources can be constrained and measured.

Resource example

docker run --memory=512m --cpus=1.5 my-api:1.0

The application may believe it runs on a normal Linux environment, but the kernel applies cgroup constraints. If memory usage exceeds the cgroup limit, the workload can be killed by the kernel's OOM behavior rather than gracefully receiving unlimited memory.

PID 1 behavior: the main process in a container should handle termination signals correctly and reap child processes. This matters for clean shutdown and rolling deployments.

07 - Docker networking

How Docker containers communicate

Case A: container to container on a user-defined bridge

Each container gets a network namespace. Docker attaches a virtual Ethernet pair: one end inside the container, the other end on the host side. Host-side interfaces attach to a software bridge. On a user-defined bridge, Docker provides embedded DNS so containers can resolve each other by name.

Packet path: api calls dbSame Docker host

Case B: container calls the internet

container eth0->veth->Docker bridge->host netfilter / masquerade->host NIC->internet

Masquerading typically rewrites the source address so external systems see the Docker host address rather than the private container address. Connection tracking lets return traffic be mapped back.

Case C: external client reaches a published port

client->HostIP:8080->DNAT / forwarding rule->containerIP:8080
docker network create app-net

docker run -d --name db  --network app-net postgres:17
docker run -d --name api --network app-net -p 8080:8080 my-api:1.0

# Inside api, connect to:
# db:5432

bridge

Most common single-host Docker network. User-defined bridge gives name-based service discovery.

host

Removes normal network namespace separation and uses the host network directly. Fewer abstractions, less isolation.

overlay

Multi-host Docker/Swarm networking. Provides a distributed virtual network across Docker daemons.

Embedded DNS: containers on a custom Docker network use Docker's embedded DNS service for container-name resolution. Do not hard-code container IPs because IPs can change after recreation.

10 - Kubernetes

Kubernetes mental model: desired state + continuous reconciliation

You do not normally tell Kubernetes, "start process X on machine Y and never move it." You declare an object such as a Deployment: "I want three healthy replicas of image X, each with these resource limits and labels." Kubernetes continuously works to make actual state match desired state.

Desired state

Stored as API objects: Deployment, Service, ConfigMap, Secret, StatefulSet, Job, and others.

Observed state

Controllers and node agents observe Pods, Nodes, endpoints, health and resource state.

Reconciliation

Control loops compare desired vs actual and take corrective actions.

The API is the center of Kubernetes. Almost every control-plane component communicates through the API server rather than directly modifying etcd or another component's memory.

13 - Pod internals

A Pod is the scheduling unit; its containers share important namespaces

A Pod can contain one or more containers that are intentionally co-located. The containers in a normal Pod share the same network namespace, so they share one Pod IP and can communicate through localhost. They can also share explicitly mounted volumes.

Illustration: one Pod with app + sidecarShared network namespace

Init container

Runs before regular app containers and must finish successfully. Useful for setup/migrations only when carefully designed.

Sidecar

Long-lived helper container, for example a proxy, log shipper or local agent. Adds operational cost and resource usage.

Pod sandbox

The runtime creates the Pod-level environment used to hold shared namespaces, typically involving an infrastructure/pause container concept.

14 - Plugin boundaries

CRI, CNI and CSI: three interfaces that explain a large part of Kubernetes internals

InterfaceWho calls itWhat it controls
CRI - Container Runtime Interfacekubelet -> runtime over gRPCPod sandboxes, containers, images, exec/log/status operations.
CNI - Container Network InterfaceRuntime / node networking integrationPod interfaces, IP assignment, routes and often NetworkPolicy implementation depending on plugin.
CSI - Container Storage InterfaceKubernetes storage controllers / node integrationProvision, attach, mount and lifecycle of persistent volumes through storage drivers.
kubelet-- CRI/gRPC -->containerd->OCI runtime->Linux kernel
Docker vs Kubernetes runtime: Kubernetes removed the old built-in Docker integration known as dockershim. Current Kubernetes nodes use a CRI-compatible runtime. Docker Engine can still be integrated through an adapter, but containerd or CRI-O are more direct choices.
15 - Kubernetes networking

Four networking problems Kubernetes must solve

  1. Container to container inside one Pod: use localhost because containers share the Pod network namespace.
  2. Pod to Pod: each Pod gets a unique cluster IP and should be reachable across nodes according to the cluster network model.
  3. Pod to Service: clients target a stable Service address/name while backing Pods can change.
  4. External to Service: LoadBalancer, Gateway or Ingress-style components bring outside traffic into the cluster.

Pod-to-Pod across two nodes

The exact packet path depends on the CNI implementation. Some route Pod CIDRs directly, some use overlays/tunnels, and some use eBPF-based data planes. The Kubernetes contract is more important than memorizing one vendor-specific path.

Conceptual packet pathPod A on Node A to Pod B on Node B

Service virtual IP path

client Pod->Service ClusterIP:port->node service data plane->EndpointSlice backend->Pod IP:targetPort

With kube-proxy, node rules are programmed from Service and EndpointSlice state. Current Kubernetes supports iptables and nftables modes on Linux; IPVS is deprecated in recent releases. Some CNI implementations replace kube-proxy functionality with their own data plane.

16 - Service discovery

How one microservice finds another without knowing Pod IPs

Suppose order-service needs to call inventory-service. The inventory Deployment may have five Pods today and twelve Pods during a sale. Those Pod IPs are ephemeral. The caller should use the stable Service identity.

Application calls http://inventory-service:8080.
Within the same namespace, the short Service name is usually enough.
DNS resolution goes to CoreDNS.
CoreDNS returns the Service ClusterIP for a normal ClusterIP Service.
The connection targets the virtual Service IP.
This IP is not usually a process listening on one physical machine.
Node data plane picks a healthy backend endpoint.
kube-proxy rules or an alternative implementation maps the Service to one Pod endpoint.
CNI networking carries the packet to the destination Pod.
The Pod may be on the same node or another node.
Sequence: order-service calls inventory-serviceDNS + Service + EndpointSlice
Best practice: application code should depend on logical service names, not Pod IPs. Add timeouts, bounded retries with backoff/jitter, connection pools and idempotency where retries can repeat an operation.

19 - Configuration and security

Separate code, configuration, identity and authorization

ConfigMap

Non-secret configuration such as feature flags, hostnames or application settings.

Secret

Sensitive values. Base64 encoding in a Kubernetes Secret is not encryption by itself. Use encryption at rest, external secret stores and access controls where appropriate.

ServiceAccount + RBAC

Workload identity and API authorization. Give a service only the permissions it needs.

NetworkPolicy

L3/L4 traffic policy, enforced only if the installed network implementation supports it.

SecurityContext example

securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  seccompProfile:
    type: RuntimeDefault
containers:
  - name: app
    image: registry.example.com/order-service:1.4.2
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
  • Use non-root images where practical.
  • Drop Linux capabilities you do not need.
  • Do not mount host paths or privileged mode casually.
  • Restrict egress as well as ingress for sensitive namespaces.
  • Scan images and sign/verify supply-chain artifacts if your platform supports it.
  • Keep Kubernetes and node OS patch levels within supported security policy.

21 - Capacity

Requests, limits and autoscaling

Request

Amount of resource the scheduler uses when deciding whether a Pod fits on a node. CPU-based HPA utilization also depends on configured CPU requests.

Limit

Upper bound enforced by runtime/kernel behavior. CPU can be throttled. Memory pressure can result in OOM termination.

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "768Mi"

Horizontal Pod Autoscaler loop

metrics source->HPA controllercompares targetdesired replicas->Deployment->more/fewer Pods
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 3
  maxReplicas: 30
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
HPA is not instant. During traffic spikes, new Pods need scheduling, image availability, startup and readiness. For flash-sale systems, combine autoscaling with headroom, fast startup, queue-based load leveling, rate limiting and capacity planning.
22 - Reliability

Health probes and self-healing are different mechanisms

ProbeQuestionIf it fails
startupProbeHas this slow application finished starting?Protects startup from premature liveness failures.
readinessProbeShould this Pod receive traffic now?Pod is removed from ready Service endpoints.
livenessProbeIs this process stuck in a way a restart can fix?Kubelet restarts the container after threshold conditions.
Common mistake: make liveness depend on every downstream dependency. If the database has a temporary issue, restarting every application Pod can turn one dependency incident into a cluster-wide restart storm.

Graceful shutdown

Pod terminating->stop sending new traffic->SIGTERM->finish in-flight requests->exit before grace period

PodDisruptionBudget

A PDB limits how many replicas can be unavailable during voluntary disruptions such as a node drain. It does not prevent every involuntary failure, and it does not replace a good replica/topology design.

23 - Placement

How Kubernetes decides where a Pod runs

The scheduler filters and scores candidate nodes based on resource requests and placement constraints. Production design should avoid concentrating all replicas in one failure domain.

nodeSelector / affinity

Place workloads on nodes matching labels or richer node/pod relationships.

anti-affinity / topology spread

Spread replicas across nodes or zones so one failure does not remove every replica.

taints / tolerations

Keep general workloads away from special nodes unless explicitly allowed.

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: order-service

25 - Example sequence

Checkout sequence: what happens from user request to events

Sequence: place orderOne possible design; adjust transaction boundaries to business rules

Why this is hard

  • Retry safety: if the client times out after the server committed, retry must not create a second order. Use an idempotency key.
  • Inventory race: stock reservation must be concurrency-safe at the inventory source of truth.
  • Payment uncertainty: a timeout does not always mean payment failed; query provider state using a stable transaction ID.
  • Event atomicity: an outbox pattern prevents "DB committed but event publishing was lost".
  • Compensation: distributed workflows commonly use Saga-like state machines rather than cross-service database transactions.
26 - Deployments

Rolling updates, canary and blue-green

Rolling update sequence

Deployment v1: 6 Pods->create v2 Pod->v2 ready->terminate v1 Pod->repeat->all v2
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
minReadySeconds: 5
StrategyHow it worksWhen useful
RollingGradually replace old replicas with new ones.Default general-purpose deployment.
CanarySend a small portion of traffic to the new version and observe metrics.High-risk releases, progressive delivery.
Blue-greenMaintain old and new environments, then switch traffic.Fast rollback, enough spare capacity available.
Readiness is central to safe rollout. A container being started is not enough. Traffic should reach a new version only after it is genuinely able to serve requests.
27 - Production failure thinking

Failure scenarios and what should happen

FailureExpected Kubernetes behaviorApplication / platform responsibility
App process crashesKubelet restarts container according to Pod restart behavior; repeated failures become backoff.Inspect logs, exit code, startup dependencies and memory.
Pod becomes unreadyService stops routing new traffic to that unready endpoint after state propagates.Readiness should reflect ability to serve, not every optional dependency.
Node diesControl plane detects node health change; controllers eventually create replacement Pods elsewhere.Have enough replicas, capacity and multi-zone placement.
Image cannot pullPod cannot start; image pull backoff/events show failure.Fix registry auth, image reference, network, rate limits or architecture mismatch.
Memory limit exceededContainer can be OOM-killed and restarted.Fix leak/heap sizing, requests/limits and load behavior.
Dependency timeoutKubernetes does not automatically make business request correct.Timeout budget, retry policy, circuit breaking, idempotency, fallback.

  name: order-ingress
  namespace: commerce
spec:
  podSelector:
    matchLabels:
      app: order-service
  policyTypes: [Ingress]
  ingress:
    - from:

            matchLabels:
              app: api-gateway

Network debugging checklist

  1. Can the process listen on the expected port inside the Pod?
  2. Is readiness passing?
  3. Does the Service selector match the Pod labels?
  4. Does the EndpointSlice contain the expected ready Pod IPs?
  5. Can DNS resolve the Service name?
  6. Does NetworkPolicy permit traffic?
  7. Is the CNI healthy on both nodes?
  8. If external traffic fails, is Gateway/Ingress/LB configuration correct?
Best debugging habit: identify the exact boundary where the request stops. DNS? Service endpoint selection? CNI routing? TCP connect? TLS? Application handler? Database? This is much faster than randomly restarting Pods.

33 - Senior engineer summary

How to explain Docker and Kubernetes in an interview

"What happens internally when a Docker container starts?"

The Docker CLI sends an API request to dockerd. Docker resolves image content and asks containerd to manage the container lifecycle. An OCI runtime such as runc creates the isolated process using kernel namespaces, cgroups, filesystem mounts and security configuration. Docker also attaches networking, typically using a network namespace and veth pair. The application is still a host process sharing the host kernel.

"How do two Kubernetes microservices communicate?"

The caller uses a stable Kubernetes Service DNS name, not Pod IPs. CoreDNS resolves that name to the Service ClusterIP. kube-proxy or an alternative data plane maps the virtual Service address to one ready backend endpoint from EndpointSlice state. CNI networking routes the packet to the destination Pod, even if it runs on another node.

"What happens after kubectl apply?"

The request reaches kube-apiserver, passes validation/authn/authz/admission, and the desired object is persisted to etcd. Controllers observe the new desired state and create subordinate objects. The scheduler assigns pending Pods to nodes. Kubelet on the chosen node calls the CRI runtime to create the Pod sandbox, attach networking, pull images and start containers. Status and readiness flow back through the API.

"Does Kubernetes use Docker?"

Kubernetes runs OCI-compatible container images, but modern nodes normally use a CRI-compatible runtime such as containerd or CRI-O. The old direct Docker integration, dockershim, was removed. Docker remains commonly used by developers and CI systems to build images.

"Why does Kubernetes need a Service if Pods already have IPs?"

Pods are ephemeral; replica count and Pod IPs change. A Service gives callers a stable logical identity and a stable virtual address while the control plane continually updates the set of healthy backend endpoints.

"What does Kubernetes not solve for microservices?"

It does not automatically solve business transaction consistency, idempotency, retry correctness, schema evolution, data ownership, distributed tracing, application-level authorization or dependency failure semantics. It provides orchestration primitives; distributed-system design is still your responsibility.

34 - Glossary

Important terms

OCI

Open standards around container image/runtime formats.

CRI

Kubernetes runtime interface between kubelet and container runtime.

CNI

Container networking integration used for Pod networking.

CSI

Container storage integration for persistent storage drivers.

Pod

Smallest schedulable Kubernetes workload unit.

Node

Worker machine that runs Pods.

ClusterIP

Virtual internal address assigned to a Service.

EndpointSlice

Scalable representation of current Service backend endpoints.

Reconciliation

Control loop moving observed state toward desired state.

Namespace

Kubernetes logical scope; unrelated to Linux namespaces even though the word is the same.

Linux namespace

Kernel isolation primitive used by containers.

cgroup

Kernel resource accounting/limit mechanism.

Service mesh

Optional traffic layer for mTLS, routing and telemetry; not required for basic Kubernetes service communication.

HPA

Controller/API that changes replica count based on metrics.

PDB

Availability budget for voluntary disruptions.
