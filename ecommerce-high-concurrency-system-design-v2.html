System Design Case Study · E-commerce at Promotion Peak

Designing an E-commerce System for Millions of Users

A practical design for Product, Shopping Cart, Order, and Inventory under normal traffic and large promotion events. The main goal is: keep inventory correct while the user experience stays fast and predictable.

1. Workload and Design Requirements

Different data has different access patterns. A good design does not use one database rule or one cache rule for every domain.

DomainTraffic patternMain riskRecommended priority
Product
Sản phẩm		 Very high read, low write. Product name, description, image change slowly. Read pressure during a hot promotion. Cache aggressively. CDN + Redis + long TTL.
Shopping Cart
Giỏ hàng		 Frequent read/write per user, but low shared contention. Session loss, stale cart, write latency. Use Redis as fast working store, with persistence or snapshot strategy.
Order
Đơn hàng		 Frequent writes and reads. Many users create orders at the same time. Duplicate order, high insert rate, inconsistent state. Partition, idempotency, async events, controlled concurrency.
Inventory
Tồn kho		 Very high contention for hot SKUs during promotion. Overselling, lock contention, hot row / hot key. Correctness first. Atomic reservation + queue/admission control.
Correct mental model: Product, Cart, Order, and Inventory should not have the same database and caching strategy. Product can accept temporary stale data. Inventory cannot.

2. Core Design Principles

Principle 1

Reduce traffic before DB

Use CDN, cache, rate limiting, waiting room, request coalescing, and queues before traffic reaches the primary database.

Principle 2

Separate read path and write path

Reads should be served by cache and replicas. Critical writes should use a controlled, authoritative path.

Principle 3

Inventory uses reservation

Do not directly “sell” stock at button click. Reserve stock first, then confirm after payment.

Principle 4

Idempotency everywhere

Idempotency (tính lặp an toàn) prevents retry, double click, or duplicate message from creating duplicate side effects.

Principle 5

Async slow work

Email, analytics, notifications, indexing, and some order workflows should be processed by queue workers, not inside the user request.

Principle 6

Degrade gracefully

Graceful degradation (giảm chức năng có kiểm soát) protects checkout even if recommendations, reviews, or analytics are slow.

3. Two Architecture Designs

Both designs can scale. The key difference is operational complexity and isolation level.

Monolith architecture

One deployable application, but internally divided into strong modules: Product, Cart, Order, Inventory, Promotion, and Checkout. The monolith can still use Redis, queues, read replicas, and partitioned tables.

When this design is strong

  • One team or several small teams.
  • Need simple deployment and easier transactions.
  • Business logic changes quickly.
  • Traffic is large but can be handled with horizontal app scaling and DB isolation.

Main risk

  • One application can become a shared bottleneck.
  • Bad inventory query may affect product/cart traffic.
  • Need module boundaries and separate resource pools even inside the same deployable unit.

Microservices architecture

Separate services and databases by business ownership. Inventory receives the strongest isolation because a hot SKU must not overload Product or Cart.

4. Database Layer Design

Database design should follow contention level. Contention (mức tranh chấp truy cập) is much more important than simple request count.

Product DB

  • Relational DB or document store both work well.
  • Primary + read replicas.
  • Product list/search can use a search index.
  • Writes are low, so strong write scaling is not the first concern.
  • Most reads should never reach DB because CDN/Redis serves them.

Shopping Cart store

  • Redis is a strong fit because access is per user/session.
  • Key example: cart:{userId}.
  • Use atomic operations for quantity changes.
  • Use persistence / periodic snapshot if cart durability matters.
  • Cart price is not final. Revalidate price/promotion during checkout.

Order DB

  • Relational DB is useful because order state needs strong constraints.
  • Partition by time, tenant, or hashed order/customer id.
  • Indexes: order_id, user_id + created_at, status when needed.
  • Use idempotency key unique constraint for order creation.
  • Use transactional outbox for reliable event publication.

Inventory DB

  • Keep authoritative stock in a primary transactional database.
  • Recommended columns: on_hand, reserved, sold, version.
  • Use atomic conditional update or serialized SKU worker.
  • Never trust a stale cache value to commit stock.
  • Reservations must have TTL and release workflow.

Atomic reservation — safest basic pattern

UPDATE inventory
SET reserved = reserved + :qty,
    version  = version + 1
WHERE sku_id = :sku
  AND (on_hand - reserved - sold) >= :qty;
If the affected row count is 1, reservation succeeded. If it is 0, stock is not enough. The stock check and stock change happen in one atomic database operation, so two buyers cannot both reserve the last item.

5. Caching Layer Design

Caching is not one pattern. Different data needs different TTL, consistency, and invalidation behavior.

DataPatternTTL strategyImportant rule
Product core CDN + Cache-Aside + Refresh-Ahead + SWR Long TTL, e.g. minutes to hours Serve stale during refresh if product text/image is still valid.
Price / Promotion Cache-Aside + event invalidation + prewarm Shorter TTL Revalidate at checkout before payment.
Cart Redis working store Session TTL Redis is not “just cache” if it is the main active cart store.
Order read Cache-Aside Short TTL Invalidate after status change.
Inventory display Very short TTL approximate cache Seconds Display only. Never use it to finalize reservation.

2 million requests hit one product exactly when TTL expires

Bad flow — Cache stampede
TTL expires
2,000,000 requests see cache miss
All requests call DB
DB connection pool is exhausted
Latency rises → clients retry → system collapses
Recommended flow
CDN still absorbs most requests
Redis value has soft TTL + hard TTL
Only one request gets refresh ownership using singleflight / lock
Other requests receive stale-but-safe product data
Refresh completes → cache becomes fresh again
2M requests→ CDN / Edge→ Redis→ Serve stale + 1 refresh owner→ DB

Anti-stampede techniques

Soft TTL + hard TTL

Soft TTL means “refresh now”. Hard TTL means “data is too old and cannot be served”.

Stale-While-Revalidate

Serve old safe data while one background worker refreshes it.

Singleflight

Many cache misses for the same key share one DB request.

TTL jitter

Add random TTL so many hot keys do not expire at the exact same second.

Refresh-ahead

Refresh popular keys before TTL expires.

Prewarm

Load promotion products into CDN/Redis before the event starts.

Negative caching

Cache “not found” for a short time to stop repeated invalid SKU queries.

Hot-key replication

Replicate extremely hot cache values or use L1 local cache in each app instance.

Circuit breaker

If DB is unhealthy, stop refresh attempts for a short period and serve degraded/stale data.

6. Microservice Boundaries

Boundaries should follow business ownership and scaling behavior, not technical layers.

Product

Product Service

Catalog, product detail, images metadata, category, search integration. Read-heavy and cache-heavy.

Cart

Cart Service

Add/remove/change quantity, save cart, merge guest cart. Optimized for fast session operations.

Order

Order Service

Order creation, order state, order history, idempotency, outbox events.

Inventory

Inventory Service

Reserve, release, commit stock. Owns authoritative inventory DB and concurrency strategy.

Promotion

Promotion Service

Campaign rules, promotion price, start/end time, coupon eligibility. Precompute hot promotion data.

Edge

API Gateway / BFF

Authentication, routing, rate limit, bot filtering, request shaping, waiting room integration.

Avoid making services too small. A “Price Service”, “Product Name Service”, and “Image Service” would create too many network calls. Service boundaries should reduce coupling, not create it.

7. Performance Optimization During Promotion Peak

The main idea is a traffic funnel: each layer should reduce, absorb, or control traffic before the next expensive layer.

Millions of requests→ CDN→ WAF / Bot filter→ Rate limit→ App→ Cache→ Queue→ Controlled DB writes

1. Pre-scale

Increase app instances, Redis capacity, queue partitions, DB connections, and workers before promotion starts.

2. Prewarm caches

Warm all hot product, promotion, price, and static content keys before users arrive.

3. Use waiting room

If demand is above safe write capacity, put users into a virtual queue instead of allowing uncontrolled retries.

4. Admission control

Only allow a controlled number of “Buy” requests into the inventory path.

5. Partition queues

Partition by SKU so each hot SKU can be processed in order and independently.

6. Async non-critical work

Move email, analytics, notifications, search indexing, and audit processing to background workers.

7. Protect DB pools

Use bounded connection pools. More application pods must not create unlimited DB connections.

8. Read replicas

Send safe read workloads to replicas, but never rely on replica stock value for critical reservation.

9. Graceful degradation

Disable reviews, recommendations, or real-time analytics if checkout is under pressure.

10. Retry with backoff

Use exponential backoff + jitter. Do not retry instantly.

11. Bulkhead isolation

Separate thread pools / connection pools for product browsing and checkout so one path cannot consume everything.

12. Load shed early

Reject or queue overload at gateway instead of timing out deep inside the database.

Why “just autoscale the API” can make things worse

50 API pods may be safe. Autoscaling to 500 pods can create 10× more DB connections and 10× more concurrent attempts to update the same inventory row. If the bottleneck is a hot SKU, scaling stateless application servers does not remove the hotspot.

8. Inventory Correctness + Good User Experience

Inventory should use a reservation lifecycle instead of a single final decrement.

User clicks Buy→ Idempotency check→ Reserve stock→ Reservation created→ Create order→ Payment→ Commit stock

Reservation states

AVAILABLE
   │ reserve
   ▼
RESERVED  --payment success-->  COMMITTED / SOLD
   │
   ├--payment failed----------> RELEASED
   │
   └--TTL expired-------------> EXPIRED -> RELEASED

Why reservation helps correctness

  • The stock is protected while the user is paying.
  • Payment provider latency does not hold a DB row lock.
  • Failed payment can release stock later.
  • Reservation TTL prevents stock being blocked forever.

Why reservation helps UX

  • User sees “Reserved for 05:00” instead of uncertain stock.
  • User can finish payment without racing every second.
  • If sold out, reject early and clearly.
  • Order can show “Processing” safely while async work completes.

9. Data Consistency Rules by Domain

A production system should define a consistency contract (quy tắc nhất quán dữ liệu) for each type of data. Not every field needs the same level of freshness. This is important for both performance and user experience.

Data Can it be temporarily stale? Where must it be authoritative? Recommended rule
Product title / description / images Yes, usually for a short time. Product service / Product DB CDN + cache is fine. Do not block checkout only because an image or description changed.
SKU status
active, disabled, recalled, unpublished		 Only for browsing. Not for checkout. Product/SKU authoritative store Revalidate before order confirmation. Disabled SKU must not be sold.
Base price Can be stale while browsing. Pricing/checkout calculation Recalculate or validate a signed/versioned quote at checkout.
Promotion / coupon Can be stale while browsing. Promotion/Pricing service Validate eligibility, start/end time, usage limit, and version at checkout.
Cart Cart display can contain old price/product text. Cart store for quantity; checkout for sellable facts Store SKU + quantity. Treat displayed price as informational until checkout.
Order No after creation. Order DB Store an immutable commercial snapshot: product name, SKU, unit price, discount, tax, currency, versions.
Inventory Display may be approximate; reservation cannot. Inventory service / primary inventory DB Always reserve with atomic authoritative logic.

The key rule: separate “display truth” from “transaction truth”

Display truth

Fast, cache-friendly

Used for product page, search result, recommendation, cart preview, and approximate stock message.

  • Can use CDN / Redis / replicas.
  • Can tolerate controlled staleness.
  • Optimized for millions of reads.
Transaction truth

Correctness-first

Used when user moves from “I am interested” to “I am committing money”.

  • Product/SKU must still be sellable.
  • Price/promotion must be validated.
  • Inventory must be atomically reserved.
  • Order must store the final agreed snapshot.

10. Critical Scenario: Admin Updates Product While User Is Ordering

This is a common real production race. The correct solution depends on what changed. A product title change is different from a price increase, SKU disable, promotion expiry, or inventory adjustment.

Example timeline

T0 User sees Product v41 · $100 → T1 Add to cart → T2 Admin updates Product/Pricing to v42 · $120 → T3 Cache invalidation event → T4 Checkout revalidates

Do not use one rule for every product update

Admin changeCan current checkout continue?Backend actionRecommended UX
Title / image / description update Usually yes. Publish ProductUpdated; invalidate cache. No need to reject if sellable facts are unchanged. Continue checkout. New content can appear on refresh.
Price decreases Usually yes. Recalculate checkout quote. Apply lower price automatically and show “Your price was updated from $100 to $90.”
Price increases Do not silently charge more. Either honor an unexpired price quote, or reject stale quote and create a new one. Show clear price change and require one-click review/acceptance.
Promotion expired Depends on quote policy. Validate quote expiry + promotion version. Never trust old cart discount. Explain that promotion ended; show new total before payment.
SKU disabled / recalled / cannot sell No. Checkout validation returns a business error such as SKU_NOT_SELLABLE. Remove/block only the affected item; keep the rest of cart.
Variant removed No for that variant. Return alternative valid variants if available. Ask user to select another size/color without losing other checkout data.
Inventory changes Only if reservation succeeds. Ignore product cache stock value. Call authoritative Inventory reservation path. Show “Reserved” only after real reservation succeeds.

Recommended checkout quote pattern

At checkout, the server creates a checkout quote (bản tính giá/xác nhận giao dịch). The quote is a server-side record or signed token describing the exact commercial facts the user is about to accept.

At “Open Checkout”

  1. Load cart by user/session.
  2. Batch validate SKU status.
  3. Batch calculate current price and promotions.
  4. Generate quote with versions and expiry.
  5. Show any differences from cart preview.

At “Place Order”

  1. Send quote_id + idempotency_key.
  2. Verify quote is active and belongs to user.
  3. Recheck critical invalidations according to business rule.
  4. Reserve inventory atomically.
  5. Create order from the quote snapshot.
  6. Mark quote USED so it cannot create a second order.

What if the product changes after quote creation?

Option A

Honor the quote

Best UX when business policy allows a short price guarantee. Product/pricing changes after quote creation do not change the user's agreed price until quote expiry.

Option B

Revalidate before commit

Use when legal/business rules require newest price or promotion. If changed, return a structured conflict and ask user to review.

Always

Inventory is separate

A valid price quote does not guarantee stock. Inventory reservation still runs against current authoritative stock.

Structured conflict response

HTTP 409 CHECKOUT_CHANGED

{
  "quoteId": "q_123",
  "changes": [
    {
      "skuId": "SKU-RED-M",
      "type": "PRICE_CHANGED",
      "oldValue": 100,
      "newValue": 120
    }
  ],
  "newQuoteId": "q_124",
  "action": "REVIEW_AND_CONFIRM"
}
UX rule: never reset the whole checkout page because one item changed. Preserve address, shipping choice, coupon input, and unaffected cart items. Highlight only the changed item and let the user confirm with minimal extra work.

How admin updates propagate safely

Admin UI→ Product/Pricing write→ DB transaction + version++→ Transactional Outbox→ ProductUpdated / PriceChanged event→ Redis invalidation→ Search/CDN refresh

Cache invalidation can be asynchronous. Correctness does not depend on every cache being refreshed immediately, because checkout uses authoritative versions/quotes for critical fields.

Admin stock adjustment while reservations exist

available_to_sell = on_hand - reserved - sold
An admin should not directly overwrite available. Use an inventory adjustment ledger (sổ điều chỉnh tồn kho). If 10 units are reserved, an admin cannot reduce physical stock below committed/reserved obligations without creating an explicit exception workflow.

11. End-to-End Workflows in Both Architectures

A. Modular Monolith: place order

Gateway→ Checkout Module→ Pricing Module→ Inventory Module→ Order Module→ DB Commit→ Outbox→ Payment / async workers

Monolith transaction boundary

If Order and Inventory tables share one transactional database, the monolith can use one short transaction for quote validation + inventory reservation + order creation + outbox write. This is a real advantage: no distributed transaction is required. 

BEGIN;

verify quote;
atomic reserve inventory;
insert order;
insert order_items snapshot;
insert outbox event;

COMMIT;

The payment provider call must happen after this DB transaction. Never keep the transaction open while waiting for an external network request.

B. Microservices: place order

API Gateway→ Checkout Orchestrator→ Pricing/Promo→ Inventory Reserve→ Order Create→ Payment→ Inventory Commit + Order Paid

Microservices use Saga, not a distributed DB transaction

Each service commits its own local transaction. The checkout workflow is a Saga (chuỗi giao dịch có bước bù trừ).

12. Real High-Concurrency and Failure Scenarios

These are common production problems. Each one needs a clear protection strategy.

1

Two users buy the last item

Risk: both read stock = 1, both write stock = 0.

Fix: atomic conditional update or serialized SKU worker. Never “read then update” without protection.

2

User double-clicks Buy

Risk: duplicate order or duplicate payment.

Fix: idempotency key + unique DB constraint + disable button after first click.

3

Client times out and retries

Risk: first request succeeded but user did not receive response.

Fix: same idempotency key returns the original result.

4

2M requests + product TTL expires

Risk: cache stampede overloads DB.

Fix: CDN + SWR + singleflight + refresh-ahead + TTL jitter + stale fallback.

5

Many cache keys expire together

Risk: cache avalanche (nhiều key hết hạn đồng loạt).

Fix: random TTL jitter, staged prewarm, different TTL classes.

6

Requests for invalid SKU

Risk: cache penetration causes repeated DB misses.

Fix: negative caching + Bloom filter + input validation.

7

One SKU becomes a hot key

Risk: one Redis shard or one DB row receives extreme load.

Fix: L1 local cache for reads; queue/serialize writes by SKU; prefilter sold-out requests.

8

Payment is slow

Risk: holding DB lock during payment blocks other buyers.

Fix: commit inventory reservation first, close transaction, call payment outside DB transaction.

9

Payment succeeds after reservation expires

Risk: money captured but stock released.

Fix: payment state machine + reconciliation + compensation/refund workflow.

10

Queue consumer crashes

Risk: message is re-delivered.

Fix: idempotent consumer + durable offset/ack + deduplication key.

11

Out-of-order events

Risk: OrderPaid arrives before OrderCreated consumer state.

Fix: partition by aggregate id, event version, ignore older version, retry missing dependency.

12

DB connection pool exhausted

Risk: every request waits, latency explodes.

Fix: bounded pool, admission control, queue writes, circuit breaker, fail fast.

13

Retry storm

Risk: timeout causes clients/services to instantly retry and multiply load.

Fix: exponential backoff + jitter + retry budget + circuit breaker.

14

Replica lag

Risk: user creates order, then reads replica and does not see it.

Fix: read-your-write from primary for a short window or route by session token.

15

Order DB write succeeds, event publish fails

Risk: downstream services never know about the order.

Fix: transactional outbox + background publisher.

16

Promotion starts but cache is cold

Risk: first traffic wave hits DB directly.

Fix: scheduled prewarm + synthetic traffic + readiness check before campaign opens.

17

Bots dominate the sale

Risk: real users cannot enter checkout.

Fix: WAF, bot score, per-account/device rate limits, waiting room, purchase quota.

18

Sold-out status spreads slowly

Risk: users keep clicking Buy after stock is gone.

Fix: publish SoldOut event, update CDN/Redis fast, reject at gateway or inventory admission layer.

14. Good User Experience Under Extreme Traffic

Before checkout

  • Serve product page fast from CDN.
  • Show approximate stock text such as “Low stock” instead of exact number when traffic is huge.
  • Use virtual waiting room when write capacity is full.
  • Disable Buy button after click and show clear progress.

During checkout

  • If price/promotion changes, never silently increase the payable amount. Show the exact changed line and require review.
  • If the new price is lower, prefer automatically giving the user the better price and explain the saving.
  • Preserve address, shipping, and unaffected cart data when one SKU changes.
  • After stock reservation, show a visible countdown.
  • Use clear states: Reserving → Reserved → Payment → Confirmed.
  • If async order creation takes longer, return 202 Accepted and let UI poll or subscribe for status.
  • Do not let the user press Pay several times.

When sold out

  • Fail early. Do not let the user fill a long form before saying sold out.
  • Update cache/edge sold-out flag quickly.
  • Offer “Notify me”, alternative product, or next promotion time.

When system is degraded

  • Keep login, cart, order, inventory, and payment healthy first.
  • Turn off recommendations, reviews, analytics widgets, and non-critical personalization.
  • Show honest status instead of infinite spinners.

15. Production Checklist

  • CDN configured for product static content.
  • Hot product keys prewarmed.
  • Soft TTL / hard TTL / SWR configured.
  • TTL jitter enabled.
  • Singleflight or request coalescing enabled.
  • Negative caching for invalid product/SKU.
  • Gateway rate limits tested.
  • Waiting room capacity defined.
  • Bot protection enabled.
  • Idempotency key on Buy / Create Order / Payment.
  • Inventory reservation is atomic.
  • Reservation expiration worker tested.
  • Queue partition key is SKU or aggregate id.
  • Queue lag dashboard and alert exist.
  • DB connection pools have hard limits.
  • Indexes verified by production-like query plans.
  • Read replica lag is monitored.
  • Transactional outbox exists for critical events.
  • Retry uses exponential backoff + jitter.
  • Circuit breakers have tested fallback behavior.
  • Load test includes hot-key / hot-SKU traffic, not only uniform traffic.
  • Load test includes client retries and failures.
  • p50 / p95 / p99 latency dashboards exist.
  • Inventory oversell invariant is monitored.
  • Promotion rollback / kill switch exists.
  • Graceful degradation switches exist.

16. Final Recommended Architecture

If the company is still small or medium: start with a modular monolith, Redis, queue, partitioned relational DB, atomic inventory reservation, CDN, and strong observability. This is simpler and can support very large traffic if designed well.
If independent scaling and team ownership become necessary: split Product, Cart, Order, Inventory, and Promotion into services. Give Inventory its own database and queue partition strategy. Move to microservices because isolation and ownership are needed — not because “microservices are more scalable by default”.

Most important rule

Millions of users ≠ millions of DB transactions.

A strong system absorbs reads at the edge and cache, controls writes with admission and queues, and protects the small critical path where inventory correctness is decided.
