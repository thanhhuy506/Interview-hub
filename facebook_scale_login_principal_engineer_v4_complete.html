Facebook-Scale Login, From the Ocean Cable to the Password Record

This page explains much more than “put an index on email”. We start from physical server placement, ISP routing, DNS, BGP, Points of Presence, load balancers, private backbone links, data-center network fabric, service placement, cache hierarchy, sharding, replication, password verification, consistency, and failure recovery.

Important: Meta does not publish the exact current private architecture of Facebook Login. This page separates public Meta infrastructure facts from reasonable design inferences that a Principal Engineer could make.

1.1 PoP is not the same as a data center

A PoP is close to the internet edge. It meets ISPs and Internet Exchanges. It can terminate network connections, run load balancers, enforce network policy, and relay traffic. A data-center region has much larger compute and storage capacity.

2. DNS and Global Traffic Steering

Before your login request reaches a service, the client needs an address. DNS is part of the performance design.

2

3

The ISP and Meta exchange routes. The actual path is selected by internet routing, not by a simple geographic map.

2.1 Cartographer vs Taiji

2.3 “Nearest” is a network decision, not only a map decision

The geographically closest PoP may have bad peering or congestion. A slightly farther PoP may give lower real latency. A global system should use measured latency, packet loss, route quality, health, and capacity.

3.1 BGP and peering

Meta can meet external networks using private peering, Internet Exchanges, and transit. BGP tells routers how to reach network prefixes. But BGP itself does not understand “this path has better Facebook p99 latency”, so Meta has published additional edge traffic control systems.

3.2 Virtual IP and L4 load balancing

3.3 L7 and TLS at the PoP

Meta has publicly described Proxygen as an HTTP/HTTPS L7 proxy at the PoP. The TLS handshake can end near the user, rather than crossing an ocean before encryption setup completes. Meta also published Fizz for TLS 1.3 and mvfst for QUIC/HTTP/3.

Security trade-off: QUIC/TLS 0-RTT can reduce setup latency, but early data can have replay concerns. A login POST is security-sensitive. Do not use 0-RTT blindly for non-idempotent authentication operations.

5.1 Why a fabric instead of one giant switch?

  • Many smaller switches reduce the single failure domain.
  • Capacity grows horizontally.
  • There are several paths between racks.
  • A new rack can join without redesigning one huge central network.

Meta's published Data Center Fabric used pods and multiple spine planes, and used BGP inside the data center. Later generations such as F16/HGRID increased bandwidth and changed the physical topology, but the scale-out principle remains important.

6A. What Really Happens After the User Clicks “Log In”?

First fix the mental model: the complete login usually cannot finish in only a few milliseconds over the public Internet. A few milliseconds is realistic for a warm cache lookup, a local RPC, or an indexed local database read. The full login also includes network RTT and password verification, and password verification is intentionally expensive.

6A.1 The login page already did work before the click

When the login form is already visible, the browser or mobile app may already have paid several costs: DNS resolution may be cached, a TCP/TLS or QUIC connection may already be open, cookies/device identifiers are loaded, and the page can already contain a CSRF token or request nonce. Therefore the click can often reuse a warm connection. This is a major reason the action feels fast. 

COLD CONNECTION
DNS -> TCP/QUIC -> TLS -> HTTP request -> backend

WARM LOGIN PAGE
click -> reuse existing HTTP/2 or HTTP/3 connection -> backend

The second path removes setup work from the click itself.

6A.2 Exact request sequence — fast normal path

Step 0
UI event

JavaScript/native code receives the click, disables duplicate submission, validates basic form shape, and creates the login request. No database call yet.

Step 1
Connection reuse

If the page is already connected, HTTP/2 or HTTP/3 reuses the existing encrypted connection. A cold connection would need DNS and a transport/TLS handshake first.

Step 2
PoP entry

The packet reaches a Meta edge PoP through ISP peering/BGP. Edge networking validates the flow and sends it to a healthy proxy/load-balancer host.

Step 3
L4 load balance

A Katran-style layer can hash the connection 5-tuple with a Maglev-style table so packets of one connection reach a stable backend with very low per-packet cost.

Step 4
L7 proxy

A Proxygen-style HTTP layer parses the request, terminates TLS when applicable, applies routing/policy, attaches request metadata, and forwards the request toward the selected regional service.

Step 5
Admission control

Before expensive crypto, perform cheap checks: request format, IP/device/account rate limits, bot/abuse signals, and whether the service is overloaded. Bad traffic should die here.

Step 6
Login service

The regional login service normalizes the identifier and creates a stable lookup key. It should not scan the user table.

Step 7
L1 identity cache

Check a tiny in-process cache first. CPU-local or process-local memory avoids a network hop. If it hits, email_key → user_id can be extremely cheap.

Step 8
L2 regional cache

If L1 misses, query a distributed regional cache through a router such as mcrouter. Consistent hashing sends the key to one cache shard or replica set.

Step 9
Directory store

If cache misses again, do one indexed/key-value lookup in the identity directory. The result is normally user_id + routing metadata, not a full profile object.

Step 10
Credential routing

Use user_id to identify a logical credential shard. Shard placement metadata maps the logical shard to healthy replicas in the current region.

Step 11
Credential read

Read password-verifier data and security metadata from a nearby replica when allowed. Security transitions may require a fresher/authoritative read.

Step 12
Password KDF

Run a deliberately expensive password verification algorithm. Exact Facebook password KDF parameters are not public; designs normally use a modern slow KDF and constant-time comparison.

Parallel
Risk checks

In parallel with password verification, fetch device/IP/location/account-risk signals. Independent reads should not be serialized.

Step 13
Decision

Combine password result, account state, abuse policy and risk score. Return success, generic invalid-credential result, or request 2FA/passkey/challenge.

Step 14
Session issue

Create or rotate an authenticated session. A browser typically receives a secure cookie; a native client may receive another session/token representation. Exact Meta token format is private.

Step 15
Response

The response travels back through the regional proxy and PoP over the already-open connection. The UI transitions to the authenticated application state.

Async
After response

Audit events, metrics, analytics, model-training events and non-critical notifications are queued asynchronously so the user does not wait for them.

The important point is not a magical algorithm that searches one billion users. The system turns the identifier into a key, then performs one direct lookup in memory or one correctly routed shard.

6A.4 If the email does not exist

A naive server returns immediately for an unknown email, but this can leak account existence through message text or timing. A safer design uses the same generic response and can perform dummy password-verification work so the two paths are harder to distinguish. This is an authentication security design choice, not a Meta-specific public claim.

6B.1 Power of Two Choices

A simple but powerful load-balancing algorithm is: choose two candidate replicas, compare their load, and send the request to the less loaded one. Meta has publicly discussed this in ServiceRouter-related production work. 

candidate A: 82 active/queued requests
candidate B: 24 active/queued requests

choose B

Why not always query every server?
Because the load-check itself becomes expensive at large scale.

  consistent-hash space

6B.3 Raft is not for every read

Raft is useful for strongly ordered replicated state, but forcing a cross-region quorum into every normal read would add WAN latency. A good auth design often separates a fast regional read path from stronger security-sensitive write/invalidation paths.

6B.4 The best optimization is often “do less work”

  • Reuse the existing connection.
  • Do not call services that are not required for the decision.
  • Read only small authentication records, not the user profile.
  • Run independent checks in parallel.
  • Keep analytics off the critical path.
  • Reject abuse before CPU-expensive crypto.
  • Keep the request in one region when possible.
Status legend for the next sections: PUBLIC META means Meta/Facebook has publicly described using the technique somewhere in production infrastructure. DESIGN OPTION means it is a strong authentication-system technique, but the exact Facebook Login implementation is private.

6B.5 Negative cache — remember that a key is absent

DESIGN OPTION for Login. Negative caching stores a short-lived answer such as email_key → NOT_FOUND. It protects the identity directory when bots repeatedly ask for random accounts.

first request:
unknown@example.com
   -> L1 miss
   -> L2 miss
   -> Identity Directory: NOT_FOUND
   -> cache NOT_FOUND for a short TTL

next requests:
unknown@example.com
   -> negative-cache HIT
   -> no storage read

The trade-off is freshness. If the user signs up immediately after a negative result, a long negative TTL could make the new account look absent. A good design uses a short TTL and/or explicit invalidation during signup. Authentication must also avoid turning this optimization into a user-enumeration oracle.

6B.6 Cache stampede and leases

PUBLIC FACEBOOK/META TECHNIQUE. Facebook's published Memcache design describes the thundering herd: a hot cache key expires and thousands of callers miss at once. If every caller queries storage, one cache expiry becomes a database DDoS.

WITHOUT COALESCING
50,000 cache misses
     | | | | | | | | |
     v v v v v v v v v
         DATABASE

WITH A LEASE
50,000 misses
     |
     +--> one lease owner --> DB --> refill cache
     |
     +--> other callers wait / retry cache

Facebook's Memcache paper describes lease tokens bound to keys. Conceptually this is the same family as single-flight / request coalescing: only one request performs the expensive refill.

6B.7 TTL + randomized jitter

DESIGN OPTION; TTL is common, exact Facebook Login jitter policy is not public. If ten million entries are inserted together with the same 300-second TTL, they can expire together five minutes later.

BAD
TTL = 300 seconds for every key
          |
          v
millions of keys expire together
          |
          v
miss spike -> storage spike

BETTER
TTL = baseTTL + random_jitter

example:
271s, 286s, 302s, 319s, 327s ...

Jitter spreads refill work over time. It reduces correlated cache expiry, but TTL is still not a replacement for correct invalidation of security-sensitive state.

6B.8 Bloom Filter — a fast “definitely absent / maybe present” test

PUBLIC META TECHNIQUE elsewhere; exact Facebook Login usage is not public. Meta has published Bloom-filter usage in storage/cache systems. For a login directory, a Bloom Filter is an optional front filter when negative lookups are very expensive.

email key
   |
   v
Bloom Filter
   |
   +-- definitely NOT present --> skip expensive storage lookup
   |
   +-- MAYBE present -----------> query authoritative directory

A standard Bloom Filter has no normal false negatives but can have false positives. A false positive only causes an unnecessary lookup. For login, the design must also consider privacy, account enumeration, signup updates, deletion semantics, and whether the saved storage QPS is worth the extra system complexity.

6B.9 Token Bucket — reject abuse before password hashing

DESIGN OPTION; Meta publicly uses throttling/rate limiting broadly, but Facebook Login's exact limiter algorithm is private.

bucket capacity = 10 tokens
refill rate     = 1 token / second
login attempt   = consume 1 token

10 -> 9 -> 8 -> ... -> 0
                       |
                       +--> throttle / challenge

normal burst: accepted
long attack: limited

A real auth system usually needs several limits at once: per IP, per account, per device, per network/ASN, per region, and possibly a global emergency limit. The important ordering is to run cheap abuse controls before the expensive password KDF.

6B.10 Constant-time comparison and timing side channels

SECURITY BEST PRACTICE; exact Facebook Login implementation is private. A naive secret comparison can return after the first different byte. In security-sensitive code, comparison should avoid making “first byte wrong” measurably faster than “last byte wrong”.

password input
    |
    v
slow password KDF
    |
    v
derived verifier
    |
    v
constant-time comparison
    |
    +--> stored verifier

There is a second timing problem: an unknown email could return immediately while a real email executes a 40 ms password KDF. A defensive design can perform dummy verification work for unknown users so response timing is less useful for account enumeration.

6B.11 Exponential backoff + jitter

PUBLIC META TECHNIQUE in retry/downstream-protection systems; exact Login policy is private. A million clients retrying exactly one second after an outage can kill the recovering service again.

retry 1: 100 ms
retry 2: 200 ms
retry 3: 400 ms
retry 4: 800 ms

then add randomness:
actual_delay = random(0, exponential_delay)

For login, retries must also be safe. A blind retry can double-create sessions or repeat side effects. A strong design uses request IDs/idempotency semantics and retries only operations that are safe to repeat.

6B.12 Hedged / backup requests

PUBLIC META TECHNIQUE in production systems; exact Facebook Login use is not public. Hedging reduces tail latency for safe reads.

t=0ms   send READ to replica A

usually:
A replies at 2ms -> done

slow case:
t=5ms   A has not replied
        send backup READ to replica B

t=7ms   B replies -> use B

t=80ms  A eventually replies -> ignore

This is good for idempotent reads such as identity metadata or replicated state. Do not naively hedge side-effecting operations such as session creation, OTP sending, account lock mutation, or password-attempt counters.

6B.13 p99 tail latency and fan-out amplification

PUBLIC META FOCUS. At hyperscale, average latency hides user pain. A service can have a good average while 1% of requests are very slow. With billions of requests, 1% is huge.

p50 = 20 ms
p95 = 70 ms
p99 = 250 ms

If one login fans out to 5 dependencies:
fast + fast + fast + SLOW + fast
                    |
                    v
               whole login is SLOW

That is why Principal-level designs reduce the number of sequential hops, run independent branches in parallel, isolate overloaded resources, use strict deadlines, and sometimes use backup reads.

6B.14 Timeout budget and deadline propagation

PUBLIC PLATFORM CONCEPT; exact Facebook Login numbers are private. A request should carry one end-to-end deadline instead of giving every downstream service a long independent timeout.

global server deadline = 150 ms

Auth sees:       140 ms remaining
Identity budget:   5 ms
Credential:       15 ms
Risk:             25 ms
Session:          10 ms

Downstream receives:
deadline_at = absolute_timestamp
remaining = deadline_at - now

If only 3 ms remain:
fail fast instead of doing 100 ms of useless work.

6C.7 Feature flags and emergency kill switches

A risky auth feature such as a new risk-model call should be behind a gate. If latency or errors rise, operations can turn the feature off without waiting for a full binary redeployment. Meta historically published Gatekeeper for this style of feature gating.

6C.9 SLOs and tail latency

Average latency hides real user pain. Production should track at least p50, p95, p99 and timeout/error rate. A single overloaded credential host can make p99 terrible even while average latency looks good. This is why load-aware routing, queue limits, deadlines and load shedding matter.

6C.10 Timeout budget, not unlimited retries

Total server budget: 100 ms example

identity        10 ms deadline
credential      15 ms deadline
risk            30 ms deadline
password KDF    controlled CPU budget
session         10 ms deadline

Never allow:
service A timeout 5s
  -> retries B 5s
     -> retries C 5s

One login can otherwise live for seconds and create retry storms.

6C.11 Capacity isolation

Password verification is CPU-heavy, while identity cache lookup is memory/network-heavy. Do not let one resource class starve another. A good design uses separate pools and queue limits: 

Pool 1: edge / HTTP
Pool 2: lightweight login orchestration
Pool 3: password KDF CPU workers
Pool 4: risk-model workers
Pool 5: cache
Pool 6: durable storage

If Pool 3 is attacked:
identity lookup and normal infrastructure should stay healthy.

META NOTE: Meta has publicly described CPU/workload isolation and latency-critical scheduling in other large production services. The exact Facebook Login worker-pool layout is not public, but this is the right principle for an auth service because KDF work is intentionally expensive.

6D. Where Do the Milliseconds Actually Go?

Key insight: The fastest login click is a warm path: DNS cached, connection open, caches warm, local replica healthy, no 2FA, no cross-region call. The slow path pays for setup, misses, failures or extra security.

6D.3 Why “email check feels instant”

  1. The login page is already loaded and connection may already be warm.
  2. The identifier lookup can be a direct cache/key lookup.
  3. The UI can show immediate local feedback while network work continues.
  4. The backend avoids loading profile/feed/messages during login.
  5. Risk checks can run in parallel.
  6. Non-critical work is asynchronous.

6D.4 Optimize p99, not only p50

If 99 users finish in 60 ms but one waits 2 seconds because a shard is overloaded, the average can still look acceptable. Principal-level design focuses on queueing, overload, per-stage deadlines, healthy-replica selection, and cold-cache recovery to control the tail.

7.2 Directory lookup

7bd18...       -> 91827364 -> shard 421

A database index or key-value store goes directly to the relevant key. The system does not scan all users. It also does not broadcast the request to every shard.

7.3 Logical shard is not a physical server

user_id -> logical shard 421

Today:
shard 421 replicas -> server A, B, C

After a machine failure:
shard 421 replicas -> server D, E, F

user_id stays the same.

Meta has publicly described Shard Manager managing very large numbers of logical shards across large fleets. This is the important abstraction: move data placement without changing user identity.

7.4 Why hash only by country can be dangerous

A country partition can create hotspots when one market grows much faster than another. A better design often combines region locality with hash-based distribution inside a region.

7.5 A hot account is a different problem

Hash sharding spreads many users. It does not solve one account receiving 100,000 attacks per second. That hot key still maps to the same logical account. Use account/device/IP rate limiting before expensive password verification.

8. Caching Strategy: Much More Than “Use Redis”

At this scale, the hard cache questions are: what to cache, where to cache, how long, who invalidates it, what happens on a miss, and what happens when the cache is wrong.

8.3 Look-aside cache

READ:
1. GET cache(key)
2. hit  -> return
3. miss -> read source of truth
4. SET cache(key, value)

WRITE:
1. update source of truth
2. invalidate/delete cache key
3. later read refills it

Facebook's published Memcache paper used this demand-filled look-aside model. Deleting on write is useful because deletion is easier to make idempotent than many distributed cache updates.

8.4 Cache stampede / thundering herd

Suppose one hot key expires while 50,000 requests arrive. If every request goes to the database, the cache can cause a database outage. Meta's Memcache paper describes leases: only a controlled client refills the key while others wait/retry.

8.5 Separate cache pools

Do not let high-churn keys evict stable identity-routing data. Separate cache pools by workload: 

Pool A: stable identity mappings
Pool B: short-lived risk/device features
Pool C: rate-limit counters
Pool D: negative lookup cache

8.6 Protect the DB when cache servers fail

The worst design is: cache dies → all traffic hits DB → DB dies → total outage. Facebook's published Memcache design used a small fallback pool called Gutter to absorb traffic from failed cache servers. Modern alternatives also include circuit breakers, stale-safe reads, request coalescing, admission control, and load shedding.

8.7 Cache correctness is different from cache availability

A cache can be healthy and still contain the wrong value. Meta has published work on Polaris and cache-consistency tracing. For authentication, this is critical: stale “account enabled” state can be worse than a cache outage.

8.12 Cache hierarchy is also a security decision

Not every auth field should be cached in every layer. Stable routing metadata is low-risk and highly cacheable. 9. Credential Storage: Stronger Rules Than Feed Data

A stale Like count is annoying. A stale password, account lock, or session-revocation state can be a security incident. Different data classes need different consistency guarantees.

DataPossible consistency policy
Like countEventual consistency is usually fine.
Feed ranking stateEventual / bounded stale is usually fine.
Email → user_idStable mapping; good candidate for replicated reads.
Password hashStronger consistency and stricter security boundary.
Account disabledFast global propagation / strong security semantics.
Session revocationFast invalidation using version/revocation state.

9.1 Public Meta storage building blocks

  • MySQL: publicly described by Meta as massively sharded and geo-replicated. MySQL Raft improved safe leader/failover behavior.
  • ZippyDB: a geographically distributed strongly consistent key-value store with tunable guarantees.
  • TAO: a read-heavy social-graph system that normally favors availability and eventual consistency.

For a new authentication system, I would choose a stronger storage class for credentials/security state than I would for normal social graph data.

9.2 Regional read, authoritative fallback

Normal login can use a nearby replica if it is fresh enough. Password reset, account lock, suspicious login, or replica uncertainty can force a stronger authoritative check. This keeps the common path fast but protects security transitions.

9.3 Security version

account.security_version = 81

old_session.security_version = 80

80 != 81
=> reject old session

This can invalidate many sessions without scanning a giant session table. But the version itself becomes security-critical and must propagate quickly.

9.4 Password hashing should not be “too fast”

Email lookup should be fast. Password verification should use an expensive password KDF because that slows brute-force attackers. Therefore, password verification needs isolated CPU capacity and strict rate limiting before the expensive operation.

11. Failure Cases a Principal Engineer Must Discuss

1. PoP failure

Move traffic to another healthy PoP using DNS/routing. Keep spare edge capacity. Lower DNS TTL can speed movement but increases DNS load.

2. Entire data-center region fails

Global traffic management moves user traffic to surviving regions. Capacity planning must keep disaster headroom; a region cannot normally run at 100% if it must absorb another region's users.

3. Cache node failure

Do not let all misses hit the database. Use fallback caches, coalescing, circuit breakers, and load shedding.

4. Cache cold start after an outage

When millions of users return, caches may be empty. Warm gradually, control refill concurrency, and prioritize critical keys. Recovery can otherwise cause a second outage.

5. Credential leader failure

A replicated/consensus storage group should elect or promote another replica safely. The important question is what happens to writes during the failover window.

6. Backbone partition

A PoP can be alive but unable to reach data-center services. Health checks must include end-to-end backend reachability, not only “the PoP server has power”.

7. DNS and backbone failure amplify each other

Meta's October 2021 outage is a real lesson: backbone loss caused DNS locations to lose data-center reachability and withdraw BGP advertisements, making authoritative DNS unreachable. Control-plane dependencies can turn one failure into a global failure.

8. One account is under attack

Sharding does not fix one hot account. Apply per-account, per-device, per-IP, ASN/network reputation, bot detection, and challenges before password KDF work.

9. Password changed in USA, immediate login in Vietnam

Security state must beat stale replicas. Use versioned invalidation, bounded staleness, or an authoritative fallback after security changes.

10. Cache is healthy but wrong

This is harder than a crash because normal health checks are green. You need cache correctness monitoring and consistency tracing, not only uptime dashboards.

15. Fast Review: 12 Principles to Remember

  1. Do not scan users. Key → directory → one shard.
  2. PoP is not a data center. Edge entry and large compute regions are different layers.
  3. Route by measured network quality, not only geography.
  4. Terminate transport near the user when safe.
  5. Use a private backbone for controlled inter-region transport.
  6. Keep normal login inside one region.
  7. Cache stable mappings aggressively; cache security state carefully.
  8. Prevent thundering herd before it reaches the DB.
  9. Logical shard placement must be independent of physical servers.
  10. Use stronger consistency only for data that needs it.
  11. Parallelize independent security work.
  12. Design failure recovery before production, not after the outage.
