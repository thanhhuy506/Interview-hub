Round 1 OOP / Design

2. Explain SOLID principles.

Weak point in original answer: The original answer mentioned the principles but sounded unclear and mixed Spring DI with dependency inversion too early.

Senior answer script

SOLID is a set of object-oriented design principles that helps us build maintainable, testable, and extensible software.

S — Single Responsibility Principle: a class should have one reason to change. For example, a UserService should handle user business logic, while UserRepository should handle database access. We should not mix validation, persistence, email sending, and logging all in one class.

O — Open/Closed Principle: code should be open for extension but closed for modification. For example, if we support multiple payment methods, we can define a PaymentProcessor interface and add CreditCardPaymentProcessor, BankTransferPaymentProcessor, or WalletPaymentProcessor without modifying the existing checkout flow.

L — Liskov Substitution Principle: subclasses or implementations should be replaceable by their parent type without breaking behavior. For example, if we have a NotificationSender interface, EmailSender and SmsSender should both follow the expected contract of send().

I — Interface Segregation Principle: clients should not be forced to depend on methods they do not use. Instead of one large UserOperation interface with createUser(), approveLoan(), generateReport(), and exportCsv(), we split it into smaller interfaces.

D — Dependency Inversion Principle: high-level modules should depend on abstractions, not concrete implementations. In Spring, we usually depend on interfaces and let the container inject the actual implementation.

Concrete example to add

Payment example:
PaymentService depends on PaymentProcessor, not directly on VisaPaymentProcessor. Tomorrow, if we add MomoPaymentProcessor or PayPalPaymentProcessor, we add a new implementation without changing the core service.

Round 1 Java Streams

3. Intermediate vs terminal operations and lazy evaluation in Stream API.

Weak point in original answer: The original answer had the right idea but wording was confusing. It should explain laziness with a small example.

Senior answer script

In Stream API, intermediate operations return another Stream and are lazy. They do not execute immediately. Examples are filter(), map(), sorted(), distinct(), and flatMap().

Terminal operations produce a final result or side effect and trigger the whole pipeline. Examples are collect(), forEach(), count(), reduce(), findFirst(), and anyMatch().

Lazy evaluation means Java does not process the stream until a terminal operation is called. This is important for performance because Java can combine operations and stop early for short-circuit operations such as findFirst(), anyMatch(), or limit().

Concrete example to add

Example:
list.stream()
.filter(x -> x > 10) // not executed yet
.map(x -> x * 2) // not executed yet
.findFirst(); // terminal operation triggers execution

If the first matching element is found, Java does not process the rest of the list.

Round 1 Java Collections

4. How does HashMap work internally?

Weak point in original answer: The original answer mentioned hash and bucket but included inaccurate details about primitive keys and hash functions.

Senior answer script

HashMap stores data as key-value pairs. Internally, it uses an array of buckets. When we put a key-value pair, HashMap calculates the key hashCode(), applies an internal hash spreading function, and maps it to a bucket index using the array capacity.

If the bucket is empty, the entry is stored there. If another key already exists in the same bucket, a collision happens. HashMap then compares keys using equals(). If the key is equal, the value is replaced. If not, the new entry is added to that bucket.

Before Java 8, collisions were handled using a linked list. From Java 8 onward, when a bucket has many entries and the capacity is large enough, the linked list can be converted to a red-black tree. This improves worst-case lookup from O(n) to O(log n) for that bucket.

Default initial capacity is 16 and default load factor is 0.75. When size exceeds capacity × load factor, HashMap resizes and redistributes entries.

Average time complexity for put/get is O(1), but it depends on good hashCode() distribution and proper equals()/hashCode() implementation.

Concrete example to add

Interview example:
If two different keys have the same hashCode or map to the same bucket, HashMap stores them in the same bucket and uses equals() to identify the exact key.

That is why if we override equals(), we must override hashCode() too.

Senior answer script

A simple and reliable approach is to store all positive numbers in a HashSet, then check from 1 upward until we find the first number that is not present.

This handles duplicates, negative numbers, zero, and unsorted input.

Time complexity is O(n), because we insert n numbers into the set and then check at most n + 1 candidates. Space complexity is O(n).

Round 2 Java 8

7. Explain CompletableFuture.

Weak point in original answer: The original answer mentioned async but did not explain Future limitation and real use cases clearly.

Senior answer script

CompletableFuture is a Java 8 API for asynchronous, non-blocking programming. It improves the older Future API because Future.get() is blocking and Future does not support easy chaining or composition.

With CompletableFuture, we can run tasks asynchronously using supplyAsync() or runAsync(), transform the result using thenApply(), consume the result using thenAccept(), compose dependent async calls using thenCompose(), combine independent async calls using thenCombine(), and handle errors using exceptionally() or handle().

It is useful when we have independent I/O operations, such as calling multiple external services in parallel. Instead of calling service A, then B, then C sequentially, we can call them concurrently and combine the results.

Round 2 JVM

8. How does garbage collection work in heap memory?

Weak point in original answer: The original answer used unclear terms. It should describe generations, minor/full GC, and object lifecycle.

Senior answer script

Java garbage collection automatically reclaims heap memory used by objects that are no longer reachable.

The heap is commonly divided into Young Generation and Old Generation. New objects are usually created in Eden space. When Eden becomes full, Minor GC runs. Live objects are copied to Survivor spaces. Objects that survive multiple GC cycles are promoted to the Old Generation.

Old Generation stores long-lived objects. When it becomes full, Major GC or Full GC may occur, depending on the collector. Full GC is usually more expensive because it may scan a larger part of the heap and can cause longer pauses.

Modern JVMs provide different collectors such as G1 GC, ZGC, and Shenandoah. In production, we monitor GC logs, pause time, heap usage, allocation rate, and memory leaks using tools such as Actuator, Prometheus, Grafana, VisualVM, JFR, or APM tools.

Concrete example to add

Production example:
If response time suddenly increases, I check GC pause time and heap usage. If Old Gen keeps growing and never drops after GC, it may indicate a memory leak or objects retained by cache/static references.

Senior answer script

Runnable and Callable both represent tasks that can run in a separate thread.

Runnable has run(), returns void, and cannot throw checked exceptions directly. It is suitable when we only need to execute a task without returning a result.

Callable has call(), returns a value, and can throw checked exceptions. It is suitable when we need the result of asynchronous computation. Callable is usually submitted to ExecutorService and returns a Future.

Round 2 Concurrency

10. synchronized vs ReentrantLock.

Weak point in original answer: The original answer admitted not remembering ReentrantLock. Better answer should compare clearly.

Senior answer script

synchronized is a built-in Java locking mechanism. It is simple and automatically releases the lock when the block or method exits, even if an exception occurs.

ReentrantLock is an explicit lock from java.util.concurrent.locks. It provides more control, such as tryLock(), lockInterruptibly(), fairness policy, and multiple Condition objects.

Use synchronized when locking is simple. Use ReentrantLock when we need advanced features like timeout-based lock acquisition, interruptible waiting, or multiple wait conditions.

Concrete example to add

Example:
tryLock() is useful when a thread should not wait forever. If it cannot acquire the lock within a timeout, it can return fallback response or retry later.

Round 2 Microservices

13. How do you handle distributed transactions?

Weak point in original answer: The original answer listed patterns but did not explain when to use each.

Senior answer script

In microservices, distributed transactions are difficult because each service owns its own database. We usually avoid global ACID transactions across services.

Common approaches:

Two-Phase Commit: a coordinator asks all services to prepare, then commit. It provides stronger consistency but is blocking, complex, and not ideal for highly scalable microservices.

Saga Pattern: split the business process into local transactions. Each step commits locally. If a later step fails, we execute compensating actions. Saga is more common in microservices.

There are two Saga styles:
- Choreography: services publish and react to events.
- Orchestration: a central orchestrator controls the workflow.

For most business workflows like order → payment → inventory → shipment, I prefer Saga with idempotent operations, retry handling, and compensation.

Concrete example to add

Example:
Order service creates order as PENDING.
Payment service charges customer.
Inventory service reserves stock.
If inventory fails, payment is refunded and order becomes CANCELLED.

Round 2 Kafka

14. How can Kafka guarantee message delivery?

Weak point in original answer: The original answer was incomplete. Need mention producer ack, idempotence, replication, offset commit.

Senior answer script

Kafka delivery guarantee depends on producer, broker, and consumer configuration.

Producer side:
- Use acks=all so the leader waits for replicas.
- Set proper replication.factor and min.insync.replicas.
- Enable retries.
- Enable idempotent producer to avoid duplicate writes during retry.

Consumer side:
- Commit offset only after processing successfully.
- Use manual acknowledgment when needed.
- Make processing idempotent because duplicates can still happen in at-least-once delivery.
- Use retry topics or dead-letter topics for failed messages.

Kafka commonly provides at-least-once delivery. Exactly-once is possible in some Kafka workflows using idempotent producer and transactions, but application-level idempotency is still very important.

Concrete example to add

Example:
When processing payment events, store eventId in the database. If the same event is consumed again, skip it. This protects the system from duplicate processing.

Round 2 Database

15. How do you optimize SQL query performance?

Weak point in original answer: The original answer listed some points but included inaccurate wording about symbols. It should be production-focused.

Senior answer script

To optimize SQL performance, I usually start by checking the execution plan instead of guessing.

Important practices:
- Select only required columns, avoid SELECT *.
- Add indexes for columns used in WHERE, JOIN, ORDER BY, and GROUP BY.
- Use composite indexes based on query patterns and column order.
- Avoid functions on indexed columns in WHERE because they can prevent index usage.
- Avoid leading wildcard LIKE '%abc' when possible because it usually cannot use a normal index efficiently.
- Use pagination for large result sets.
- Avoid N+1 queries in ORM by using fetch join, entity graph, or batch fetching.
- Keep table statistics updated.
- Avoid over-indexing because indexes slow down insert/update/delete.

Concrete example to add

Example:
Query: WHERE status = ? AND created_at BETWEEN ? AND ? ORDER BY created_at DESC
A useful composite index may be (status, created_at), depending on cardinality and database optimizer.

Round 3 REST

18. What is idempotency in REST APIs?

Weak point in original answer: The original answer mixed up POST wording. Need clarify methods and retry safety.

Senior answer script

Idempotency means executing the same request multiple times has the same final effect as executing it once.

GET is idempotent because it only reads data.
PUT is idempotent because replacing a resource with the same payload multiple times leaves the resource in the same state.
DELETE is idempotent because after the resource is deleted, repeating delete keeps it deleted.
POST is usually not idempotent because repeating it may create multiple resources.

In real systems, even POST can be made idempotent using an idempotency key. This is common in payment APIs to avoid duplicate charges during retries.

Concrete example to add

Payment example:
Client sends POST /payments with Idempotency-Key: abc-123.
If network timeout happens and client retries, server detects the same key and returns the original result instead of charging again.

Round 1 — Employee Stream Tasks

import java.util.*;
import java.util.stream.*;

public class EmployeeStreamTask {
    static class Employee {
        private final int id;
        private final String name;
        private final double salary;

        public Employee(int id, String name, double salary) {
            this.id = id;
            this.name = name;
            this.salary = salary;
        }

        public int getId() { return id; }
        public String getName() { return name; }
        public double getSalary() { return salary; }

        public Employee withSalary(double newSalary) {
            return new Employee(this.id, this.name, newSalary);
        }

        @Override
        public String toString() {
            return id + " - " + name + " - " + salary;
        }
    }

    public static void main(String[] args) {
        List<Employee> employees = List.of(
            new Employee(1, "Alice", 4500),
            new Employee(2, "Bob", 7000),
            new Employee(3, "Charlie", 9000)
        );

        double threshold = 5000;

        // 1. Print names of employees whose salary is greater than threshold
        employees.stream()
            .filter(e -> e.getSalary() > threshold)
            .map(Employee::getName)
            .forEach(System.out::println);

        // 2. Create a new list with 10% salary increase
        List<Employee> increasedSalaryEmployees = employees.stream()
            .map(e -> e.withSalary(e.getSalary() * 1.10))
            .collect(Collectors.toList());

        // 3. Find employee with highest salary
        Employee highestPaid = employees.stream()
            .max(Comparator.comparingDouble(Employee::getSalary))
            .orElseThrow(() -> new NoSuchElementException("Employee list is empty"));

        System.out.println("After increase: " + increasedSalaryEmployees);
        System.out.println("Highest paid: " + highestPaid);
    }
}

import java.util.*;

public class SmallestPositiveMissing {
    public static int findSmallestMissingPositive(int[] nums) {
        Set<Integer> positives = new HashSet<>();

        for (int num : nums) {
            if (num > 0) {
                positives.add(num);
            }
        }

        int candidate = 1;
        while (positives.contains(candidate)) {
            candidate++;
        }
        return candidate;
    }

    public static void main(String[] args) {
        System.out.println(findSmallestMissingPositive(new int[]{1, 2, 3, 4, 6})); // 5
        System.out.println(findSmallestMissingPositive(new int[]{-3, -1, 0, 2}));  // 1
        System.out.println(findSmallestMissingPositive(new int[]{1, 1, 2, 2}));   // 3
    }
}

public class CompletableFutureExample {
    public static void main(String[] args) {

    }

    private static String getOrders() { return "Orders: 5"; }

}

public class ReentrantLockExample {
    private final ReentrantLock lock = new ReentrantLock();

    }

public class PatternCounter {
    public static Map<String, Long> countPairs(String input) {
        if (input == null || input.isBlank()) {
            return Collections.emptyMap();
        }

        String[] tokens = input.trim().split("\\s+");

        return Arrays.stream(tokens)
            .collect(Collectors.groupingBy(
                Function.identity(),
                LinkedHashMap::new,
                Collectors.counting()
            ));
    }

    public static void main(String[] args) {
        String input = "xx vc ff yy vc tt xx";

        countPairs(input).forEach((pattern, count) ->
            System.out.println(pattern + " = " + count)
        );
    }
}
