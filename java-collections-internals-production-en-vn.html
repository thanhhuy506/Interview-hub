01 • Why collections matter

A collection choice is an architecture decisionChọn collection là một quyết định kiến trúc

Collections appear in almost every Java backend path: request aggregation, caching, deduplication, scheduling, batching, indexing, messaging, authorization, and persistence mapping.

A senior engineer chooses by access pattern, ordering, uniqueness, concurrency, mutation frequency, boundedness, and data size—not by habit.

Collection xuất hiện trong hầu hết Java backend code: gom request, cache, loại trùng, scheduling, batching, indexing, messaging, authorization và mapping dữ liệu.

Senior phải chọn dựa trên access pattern, ordering, uniqueness, concurrency, tần suất thay đổi, giới hạn dung lượng và data size—không chọn theo thói quen.

Access

Index lookup, key lookup, sequential scan, range query, head/tail operations.

Semantics

Duplicates, order, sort order, null policy, mutability.

Concurrency

Single-thread, externally locked, concurrent reads, atomic updates, blocking coordination.

Capacity

Expected cardinality, growth policy, node overhead, queue bounds, retention lifecycle.

Senior rule: Big-O is only the first filter. Memory locality, contention, allocation overhead, iteration cost, and business lifecycle often decide production performance.

Quy tắc senior: Big-O chỉ là bước lọc đầu tiên. Memory locality, contention, allocation overhead, iteration cost và business lifecycle mới thường quyết định hiệu năng production.

Collection

A group of individual elements. Core operations include add, remove, contains, size, iteration.

Map

Key-value associations. A map cannot contain duplicate keys; each key maps to at most one value.

Collections

A utility class containing algorithms and wrappers. It is not the Collection interface.

Why Map does not extend Collection

A map stores entries with two-part semantics: key and value. Operations such as add(E) or “one element” are ambiguous. Instead, Map exposes collection views through keySet(), values(), and entrySet().

Map lưu entry có hai phần: key và value. Các operation như add(E) hoặc khái niệm “một element” không rõ ràng. Vì vậy Map cung cấp collection view qua keySet(), values() và entrySet().

04 • Dynamic array

ArrayList internals

ArrayList<E>

size = 5
elementData (capacity = 8)
┌────┬────┬────┬────┬────┬──────┬──────┬──────┐
│ A  │ B  │ C  │ D  │ E  │ null │ null │ null │
└────┴────┴────┴────┴────┴──────┴──────┴──────┘
  0    1    2    3    4        spare capacity

size      = number of logical elements
capacity  = length of backing Object[]

How add(E) works

  1. Check whether the backing array has free capacity.
  2. If full, allocate a larger array—current OpenJDK growth is approximately 1.5× for normal growth.
  3. Copy old references to the new array.
  4. Store the new element at elementData[size].
  5. Increase size and structural modification count.
public boolean add(E element) {
    // conceptual, simplified
    if (size == elementData.length) {
        elementData = grow();
    }
    elementData[size++] = element;
    return true;
}

Why end insertion is amortized O(1)

Most additions only write one array slot. A resize is O(n), but it occurs occasionally, so the average cost over many additions is constant.

Phần lớn lần add chỉ ghi một ô array. Resize có cost O(n), nhưng chỉ thỉnh thoảng xảy ra nên cost trung bình trên nhiều lần add là O(1).

Insertion and removal in the middle

// Insert at index 2
[A][B][C][D][E][_]
       └──────────► shift C,D,E right
[A][B][X][C][D][E]

// Remove index 2
[A][B][X][C][D][E]
          ◄──────── shift C,D,E left
[A][B][C][D][E][null]

OpenJDK uses efficient array-copy operations, but shifting is still proportional to the number of moved references.

Important production details

Pre-size

Use new ArrayList<>(expectedSize) when cardinality is known to avoid repeated allocation and copying.

Remove references

Removal and clear null out unused slots so referenced objects can become collectible.

Excess capacity

A list that temporarily grew very large can retain a large backing array. trimToSize() may help only when justified.

subList() retention trap

List<LargeObject> huge = loadOneMillionObjects();
List<LargeObject> firstTen = huge.subList(0, 10);

// firstTen is a view and can retain the root list/backing array.
List<LargeObject> detached = new ArrayList<>(huge.subList(0, 10));
Default choice for most list workloads: ArrayList. Choose LinkedList only when its actual node-based access pattern is proven beneficial.
05 • Linked nodes and deque

LinkedList vs ArrayDeque

LinkedList (doubly linked)

null ← [prev|A|next] ⇄ [prev|B|next] ⇄ [prev|C|next] → null
       ↑ first                                  last ↑

Each element requires a Node object containing:
item + previous reference + next reference

How indexed access works

LinkedList.get(index) does not jump directly to the index. It traverses from the head if the index is in the first half, otherwise from the tail.

get(800) in a list of 1,000:
start from last and follow prev about 199 times → O(n)

The common interview trap

“LinkedList insertion is O(1)” is incomplete. It is O(1) only when you already have the node/iterator position. Inserting by index first requires O(n) traversal.

Câu “LinkedList insert O(1)” chưa đầy đủ. Nó chỉ O(1) khi đã có node/iterator position. Insert bằng index phải traverse O(n) trước.

06 • Most important interview topic

HashMap internals — step by step

table: Node[]power-of-two capacity default load factor 0.75list → red-black tree not thread-safe

Core structure

HashMap table (capacity = 16)

index 0   null
index 1   [hash,key,value,next] → [collision node] → null
index 2   null
...
index 9   [single node] → null
...
index 15  [tree bin when heavily collided]

Node contains:
hash | key reference | value reference | next reference

1. Hash calculation

static int spread(int h) {
    return h ^ (h >>> 16); // conceptual form used by HashMap
}

HashMap mixes high bits into low bits because the bucket index uses low bits when capacity is a power of two. This improves distribution for hash codes whose useful variation is mostly in higher bits.

HashMap trộn high bits xuống low bits vì bucket index dùng low bits khi capacity là lũy thừa của 2. Việc này cải thiện distribution khi hashCode() có độ biến thiên chủ yếu ở high bits.

2. Bucket index

index = (capacity - 1) & hash

Example:
capacity = 16       → capacity - 1 = 0000 1111
hash                →                  ... 1010
index               →                      1010 = 10

A power-of-two capacity makes bit masking fast and allows efficient splitting during resize.

3. Complete put(key, value) flow

put(key, value)
   │
   ├─ key == null ? hash = 0 : spread(key.hashCode())
   ├─ table absent/empty? → initialize table
   ├─ calculate bucket index
   │
   ├─ bucket empty?
   │      └─ create Node
   │
   └─ bucket occupied
          ├─ first node has same hash and equals key?
          │      └─ replace value
          ├─ bucket is TreeNode?
          │      └─ insert/search in red-black tree
          └─ linked-list traversal
                 ├─ equal key found → replace value
                 └─ append new node
                       └─ treeify if collision chain threshold reached
   │
   └─ new key inserted → size++
          └─ size > threshold? → resize

How key equality is checked

// Conceptually
if (storedHash == searchedHash
        && (storedKey == searchedKey || searchedKey.equals(storedKey))) {
    // same logical key
}

Hash equality narrows candidates; equals() confirms logical equality. Different hash means HashMap normally does not call equals() for that candidate.

Collision handling

Empty bucket

Insert one node directly.

Linked bin

Multiple keys sharing a bucket are connected through next.

Tree bin

Heavily collided bins can become red-black trees to improve worst-case lookup.

OpenJDK uses a treeification threshold of 8, an untreeification threshold of 6, and treeifies only when table capacity is at least 64; otherwise it prefers resizing. These are implementation details, not a general Map contract.

Why a red-black tree?

A red-black tree keeps height approximately logarithmic through coloring and rotations. This changes a severe collision chain from linear traversal toward O(log n), while regular well-distributed buckets remain cheaper linked nodes.

Resize process

threshold = capacity × loadFactor

Example:
capacity   = 16
loadFactor = 0.75
threshold  = 12

When size exceeds threshold:
capacity usually doubles → 32
threshold usually doubles → 24
During Java 8+ style resize, each old bucket is split:

(hash & oldCapacity) == 0 → stays at old index
(hash & oldCapacity) != 0 → moves to old index + oldCapacity

This avoids recomputing a completely new hash for every node.

get(key) flow

  1. Calculate spread hash.
  2. Calculate bucket index.
  3. Check first node.
  4. If necessary, traverse linked nodes or search the tree bin.
  5. Match by hash and logical equality.
  6. Return value or null.

Complexity with the correct nuance

ConditionLookup costExplanation
Good distributionExpected O(1)Small number of nodes per bucket
Collision linked binO(k)k entries in the selected bucket
Tree binApproximately O(log k)Balanced tree search within one bucket
IterationO(capacity + size)Iterator visits table slots and entries

Capacity sizing

// Rough planning before power-of-two rounding:
requiredCapacity ≈ ceil(expectedEntries / loadFactor)

expectedEntries = 100_000
loadFactor       = 0.75
raw capacity     ≈ 133_334

Pre-sizing avoids repeated resize and temporary allocation pressure.
HashMap is not thread-safe. Concurrent reads and writes without synchronization can produce lost updates, stale visibility, inconsistent iteration, and invalid compound operations. Use a proper concurrent design.
07 • Identity contract

equals(), hashCode(), and mutable keys

The required contract

Equal → same hash

If a.equals(b) is true, a.hashCode() == b.hashCode() must be true.

Same hash ≠ equal

Different objects may legally produce the same hash code; HashMap resolves collision using equals.

Stable while stored

Fields participating in equality/hash must not change while the object is used as a hash key.

What goes wrong when only equals() is overridden?

final class UserKey {
    private final String tenant;
    private final String userId;

    @Override
    public boolean equals(Object o) {
        // logical equality implemented
    }

    // hashCode() forgotten → inherits identity-based Object.hashCode()
}

Two logically equal keys can be sent to different buckets, so get(), containsKey(), and Set uniqueness fail unexpectedly.

Correct immutable key

public record UserKey(String tenant, String userId) {
    public UserKey {
        Objects.requireNonNull(tenant);
        Objects.requireNonNull(userId);
    }
}
// record provides value-based equals() and hashCode()

Mutable-key production bug

final class AccountKey {
    String accountNumber; // mutable and used by equals/hashCode
}

AccountKey key = new AccountKey();
key.accountNumber = "A-100";

Map<AccountKey, String> map = new HashMap<>();
map.put(key, "ACTIVE");

key.accountNumber = "A-200"; // hash may now point to another bucket

map.get(key);    // may return null
map.remove(key); // may fail; the old entry remains retained

Use immutable hash keys. A mutable key can become “lost” inside the map: the node remains in the old bucket but future lookup calculates a new bucket.

Hãy dùng immutable key. Mutable key có thể bị “mất” trong map: node vẫn nằm ở bucket cũ nhưng lần lookup sau tính ra bucket mới.

Good hashCode characteristics

  • Consistent with equals.
  • Stable while used as a key.
  • Uses the same significant fields as equals.
  • Distributes expected business data reasonably.
  • Cheap enough for frequent lookup.
08 • Uniqueness

How Set uniqueness works

HashSet

Backed internally by a HashMap. Elements are stored as keys with a shared dummy value.

LinkedHashSet

Hash-based uniqueness plus predictable insertion order.

TreeSet

Tree-based uniqueness and sorted order determined by natural ordering or Comparator.

// Conceptual HashSet internals
private transient HashMap<E, Object> map;
private static final Object PRESENT = new Object();

public boolean add(E e) {
    return map.put(e, PRESENT) == null;
}

HashSet duplicate decision

1. Calculate element.hashCode()
2. Select HashMap bucket
3. Compare hash and equals against candidates
4. Equal candidate exists → add returns false
5. No equal candidate → insert key, add returns true

TreeSet uniqueness trap

Comparator<Employee> bySalary =
    Comparator.comparing(Employee::salary);

TreeSet<Employee> set = new TreeSet<>(bySalary);

// Two different employees with the same salary compare as 0.
// TreeSet treats them as the same position/key.
For sorted sets/maps, compare(a,b) == 0 determines key uniqueness. A comparator inconsistent with equals may be legal but can produce surprising Set/Map behavior.

Mutable sorted elements

Changing a field used by the comparator after insertion can break tree ordering. The element remains physically at an old tree position, so lookup/removal may fail. Prefer immutable ordering fields.

Simple LRU cache

class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int maxEntries;

    LruCache(int maxEntries) {
        super(16, 0.75f, true); // access-order
        this.maxEntries = maxEntries;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxEntries;
    }
}

10 • Queue, deque, priority

Queue selection and PriorityQueue internals

PriorityQueue is a binary min-heap

Logical tree                 Backing array

        2                    [2, 5, 4, 9, 7, 8]
      /   \                   0  1  2  3  4  5
     5     4
    / \   /
   9   7 8

parent(i)     = (i - 1) / 2
leftChild(i)  = 2i + 1
rightChild(i) = 2i + 2

Add and poll

  • add/offer: append at end, then sift up until heap order is restored — O(log n).
  • peek: return root — O(1).
  • poll: move last element to root, then sift down — O(log n).
  • iteration: not globally sorted. Only the head is guaranteed to be the minimum by comparator.
PriorityQueue<Job> jobs =
    new PriorityQueue<>(Comparator.comparing(Job::priority));

while (!jobs.isEmpty()) {
    process(jobs.poll()); // priority order
}

BlockingQueue selection

ImplementationCapacityUse caseProduction warning
ArrayBlockingQueueBoundedFixed-capacity producer/consumerProvides explicit backpressure
LinkedBlockingQueueOptional boundProducer/consumer with flexible capacityDefault capacity is extremely large; specify a bound
SynchronousQueueNo storageDirect handoffProducer waits for consumer
PriorityBlockingQueueLogically unboundedConcurrent priority schedulingCan grow memory without backpressure
DelayQueueUnboundedDelayed expiration/schedulingRetention until delay and removal

Unbounded queue = hidden memory policy. When producers are faster than consumers, the queue becomes an in-memory backlog until latency or OOM exposes the problem.

Unbounded queue chính là một memory policy ẩn. Khi producer nhanh hơn consumer, queue biến thành backlog trong memory cho đến khi latency tăng hoặc OOM xảy ra.

11 • Iteration behavior

Fail-fast, snapshot, and weakly consistent iterators

Fail-fast internals

Collection:
    modCount = number of structural modifications

Iterator creation:
    expectedModCount = collection.modCount

During next/remove:
    if (modCount != expectedModCount)
        throw ConcurrentModificationException
Fail-fast is best effort, not a concurrency guarantee. Never use ConcurrentModificationException as synchronization or program correctness logic.

Structural modification

Adding/removing elements, resizing, or otherwise changing collection structure usually increments modCount. Replacing a value for an existing map key may not be considered structural because the number/topology of entries does not change.

Correct removal during iteration

Iterator<Order> it = orders.iterator();
while (it.hasNext()) {
    Order order = it.next();
    if (order.isExpired()) {
        it.remove(); // updates iterator state correctly
    }
}

// Or:
orders.removeIf(Order::isExpired);

“Fail-safe” is not an official iterator category

BehaviorExampleWhat iteration sees
Fail-fastArrayList, HashMapDetects some structural modifications and may throw CME
SnapshotCopyOnWriteArrayListImmutable snapshot from iterator creation; later writes are not visible
Weakly consistentConcurrentHashMapNo CME; may reflect some modifications during traversal, never requires a full snapshot

Synchronized wrapper iteration

List<String> list =
    Collections.synchronizedList(new ArrayList<>());

synchronized (list) {
    for (String value : list) {
        consume(value);
    }
}

The wrapper synchronizes individual methods. A multi-step iteration still requires locking on the wrapper object for the whole traversal.

12 • Concurrent map internals

ConcurrentHashMap — how it works

Modern ConcurrentHashMap does not use the old Java 7 fixed Segment architecture as its primary design. Java 8+ implementations use table bins, CAS, synchronized bin-level updates, tree bins, and cooperative resizing.

High-level structure

ConcurrentHashMap table

bucket 0   null
bucket 1   Node → Node
bucket 2   TreeBin → TreeNode tree
bucket 3   ForwardingNode → points to next table during resize
...

Reads:
mostly volatile/ordered reads without locking the whole map

Writes:
CAS into empty bin
or synchronize on selected bin head for collision updates

get(key)

  1. Calculate spread hash and bucket index.
  2. Read table/bin using memory-safe volatile semantics.
  3. Check first node, linked nodes, tree bin, or forwarding state.
  4. No global lock is required for ordinary retrieval.

put(key,value) simplified

put
 ├─ initialize table if needed
 ├─ target bin empty?
 │      └─ CAS new Node into slot
 ├─ bin is ForwardingNode?
 │      └─ help transfer during resize
 └─ occupied normal/tree bin
        └─ synchronize on bin head
             ├─ revalidate bin
             ├─ insert/update list or tree
             └─ release bin lock
 └─ update count; resize if needed

Why reads scale

Retrievals normally do not acquire a map-wide lock. Updates to unrelated bins can progress concurrently. A completed update for a key has a happens-before relationship with a subsequent non-null retrieval of that key.

Cooperative resizing

When resizing begins, bins can be marked with forwarding nodes. Multiple threads encountering the migration can help transfer bins to the new table instead of one thread performing all work.

Khi resize bắt đầu, bucket có thể được đánh dấu bằng forwarding node. Nhiều thread gặp quá trình migration có thể cùng chuyển bucket sang table mới thay vì chỉ một thread làm toàn bộ.

Why null keys and values are forbidden

null is used as an unambiguous signal that no mapping currently exists. In concurrent code, allowing null would make it impossible to distinguish “absent” from “mapped to null” without another atomic check.

Atomic methods

// Race-prone check-then-act
if (!map.containsKey(key)) {
    map.put(key, load(key));
}

// Atomic map operation
map.computeIfAbsent(key, this::load);
Keep computeIfAbsent, compute, and merge functions short and side-effect controlled. Some updates for the same bin/key may block while computation runs. Do not perform slow remote I/O under an atomic map computation without deliberate design.

Scalable frequency map

ConcurrentHashMap<String, LongAdder> frequencies =
    new ConcurrentHashMap<>();

frequencies
    .computeIfAbsent(eventType, ignored -> new LongAdder())
    .increment();

Iteration semantics

Iterators are weakly consistent: they do not throw ConcurrentModificationException, can proceed during updates, and may observe some but not necessarily all concurrent changes. Aggregate methods such as size() should not be used as exact coordination signals while updates are ongoing.

CopyOnWriteArrayList internals

read:
    read current immutable array snapshot

write:
    lock
    copy old array → new array
    apply change to new array
    publish new array
    unlock

iterator:
    traverses the captured old array snapshot

Excellent when

Reads/iterations greatly outnumber writes, list is moderate in size, and snapshot semantics are acceptable.

Bad when

Writes are frequent or list is large; every mutation allocates and copies O(n) references.

Thread-safe collection does not make a workflow atomic

// Each method is thread-safe, but this sequence is not atomic:
if (inventory.get(sku) > 0) {
    inventory.put(sku, inventory.get(sku) - 1);
}

// Use compute, merge, atomic value, or a domain lock:
inventory.computeIfPresent(sku, (k, stock) ->
    stock > 0 ? stock - 1 : stock
);

15 • Ordering algorithms

Sorting, Comparable, Comparator, and Top-K

Comparable vs Comparator

Comparable<T>

Defines the type's natural order inside the class through compareTo.

Comparator<T>

Defines an external or alternative order and supports composition.

Comparator<Employee> order =
    Comparator.comparing(Employee::department)
        .thenComparing(Employee::salary, Comparator.reverseOrder())
        .thenComparing(Employee::id);

employees.sort(order);

Comparator contract

  • Antisymmetry/sign consistency.
  • Transitivity.
  • Consistent result for equivalent comparison state.
  • Prefer consistency with equals for sorted sets/maps.

How List sorting works

List.sort guarantees a stable sort: equal elements retain their relative order. Current OpenJDK object-list sorting is based on a TimSort adaptation, which takes advantage of existing ordered runs.

// Stable multi-step sort can preserve previous order among equal values,
// but a single composed Comparator is clearer and usually preferable.
employees.sort(Comparator.comparing(Employee::department)
                         .thenComparing(Employee::name));

Do not sort everything for Top-K

Full sort

O(n log n)
sort all, take first k

Bounded heap

O(n log k)
maintain PriorityQueue of size k
PriorityQueue<Employee> top =
    new PriorityQueue<>(Comparator.comparing(Employee::salary));

for (Employee e : employees) {
    top.offer(e);
    if (top.size() > k) {
        top.poll();
    }
}

Sorted collection vs sorting on demand

  • Use ArrayList + sort when writes happen in batches and reads need occasional ordered output.
  • Use TreeMap/TreeSet when you continuously need ordered lookup and range navigation.
  • Use PriorityQueue when only the next highest/lowest element matters.
16 • Real failure modes

Common collection bugs in production

Mutable hash key

Entry becomes unreachable through normal lookup after key fields change.

Wrong equals/hashCode

Duplicate Set values or missing Map lookup despite logical equality.

Unbounded growth

Cache, queue, dedup Set, retry map, or session registry grows until OOM.

Wrong concurrent type

Lost updates, visibility bugs, CME, or race conditions from HashMap/ArrayList sharing.

Expensive atomic callback

Slow computeIfAbsent blocks competing updates and creates latency spikes.

Hidden backing view

subList, unmodifiableList, keySet, or Arrays.asList behaves differently than a copy.

Unbounded cache

private final Map<String, CustomerProfile> cache =
    new ConcurrentHashMap<>();

CustomerProfile get(String customerId) {
    return cache.computeIfAbsent(customerId, repository::load);
}
// No maximum size, TTL, invalidation, or tenant-cardinality protection.

Fix with an explicit capacity/weight, expiry, invalidation, hit-rate metrics, loading policy, and ownership lifecycle.

Parallel stream with shared mutable collection

// Wrong
List<Result> results = new ArrayList<>();
inputs.parallelStream().forEach(x -> results.add(process(x)));

// Better
List<Result> results = inputs.parallelStream()
    .map(this::process)
    .toList();

Check-then-act race

// Wrong under concurrency
if (!map.containsKey(id)) {
    map.put(id, create());
}

// Depending on semantics:
map.putIfAbsent(id, create());
map.computeIfAbsent(id, this::create);

putIfAbsent(id, create()) evaluates create() before the call, so it may perform unnecessary work. computeIfAbsent coordinates map insertion but its callback must remain suitable for an atomic map operation.

Memory investigation checklist

  1. Identify growing collection type and owning object via heap dominator tree.
  2. Inspect element count, key cardinality, retained size, and paths to GC roots.
  3. Determine whether growth is expected business state or missing eviction/removal.
  4. Check large backing arrays, HashMap table capacity, queues, and duplicate-retention structures.
  5. Add metrics: size, capacity limit, rejection count, eviction count, oldest-entry age, consumer lag.

18 • Senior interview

Interview questions and model answers

1. Explain HashMap.put() internally.

HashMap spreads the key hash, selects a bucket using (n-1)&hash, inserts directly if empty, otherwise checks hash and equals through a linked or tree bin, replaces the value for an equal key, and resizes after a new insertion exceeds the threshold. Heavily collided bins may treeify when capacity and thresholds allow.

2. Why must equals and hashCode be overridden together?

Hash-based collections choose a bucket using hashCode, then confirm equality using equals. If equal objects produce different hashes, lookup may search different buckets and fail.

3. What happens when two keys have the same hash?

They can land in the same bucket. HashMap compares equals; equal keys replace the existing value, while unequal keys coexist in a linked or tree bin.

4. Why is HashMap capacity a power of two?

It enables efficient bucket selection with a bit mask and efficient low/high bin splitting when capacity doubles.

5. What is load factor?

It controls the density threshold before resizing: roughly capacity multiplied by load factor. A lower value uses more memory for fewer collisions; a higher value saves table space but increases bucket density.

6. ArrayList vs LinkedList?

ArrayList offers O(1) indexed access, compact storage, and good locality. LinkedList has O(n) indexed access and node overhead; O(1) insertion only applies when the node position is already known. ArrayList is the general default.

7. Why is ArrayDeque often better than LinkedList for queues?

ArrayDeque uses a compact circular array, avoiding one node object and two links per element. Operations at both ends are efficient and iteration has better locality.

8. HashSet internals?

HashSet delegates storage to a HashMap, storing each set element as a map key and using one shared dummy object as the value. Uniqueness follows hashCode and equals.

9. HashMap vs TreeMap?

HashMap gives expected O(1) key operations and no order guarantee. TreeMap gives O(log n) operations, sorted order, and range/navigation methods.

10. Fail-fast vs fail-safe?

Fail-fast iterators detect some structural changes using modification counts and may throw CME on a best-effort basis. “Fail-safe” is informal; describe the actual behavior instead: CopyOnWrite uses snapshots, while ConcurrentHashMap iterators are weakly consistent.

11. How does ConcurrentHashMap differ from HashMap?

ConcurrentHashMap provides thread-safe retrieval/update semantics, mostly lock-free reads, CAS for empty bins, synchronized bin-level collision updates, cooperative resize, weakly consistent iteration, and atomic map methods. It forbids null keys/values.

12. Does ConcurrentHashMap make all business operations atomic?

No. Individual operations and specified compound methods are atomic according to their contracts, but arbitrary multi-step workflows require compute/merge, atomic values, or explicit domain locking.

13. When should CopyOnWriteArrayList be used?

When iteration/read frequency is much higher than writes, the list is not huge, and snapshot iteration is correct. It is poor for write-heavy or large lists because each mutation copies the array.

14. Why is a mutable HashMap key dangerous?

Changing a field used by hashCode/equals changes the lookup bucket or equality after insertion. The entry remains stored under its old placement and may become impossible to retrieve/remove normally.

15. What causes ConcurrentModificationException?

A fail-fast iterator detects that the collection was structurally modified outside the iterator. It can occur in one thread as well; the name does not require multi-threading.

16. Why can a collection cause OOM?

Collections strongly retain their keys/elements/values. An unbounded cache, queue, Set, map, listener registry, or large spare backing array can keep an object graph reachable indefinitely.

17. Is PriorityQueue iteration sorted?

No. The heap only guarantees that the head is the minimum/highest-priority element. Repeated poll returns priority order.

18. How do you choose initial HashMap capacity?

Estimate expected entries divided by load factor, account for power-of-two rounding, or use appropriate modern factory helpers when available. The goal is avoiding repeated resize without creating an excessively sparse table.

19. Why can TreeSet drop a seemingly different object?

If the comparator returns zero, TreeSet treats the objects as occupying the same sorted key position, even when equals returns false.

20. How do you diagnose collection memory growth?

Use heap histograms and dominator trees, inspect retained size and path to GC roots, identify the owning collection, measure its cardinality over time, and verify eviction/removal/backpressure against business lifecycle.

Hands-on exercises

Exercise 1 — Mutable key

Create a mutable key, put it into HashMap, change the hash field, then test get/remove. Explain the bucket mismatch.

Exercise 2 — Collision

Create keys with the same hash but different equals identities. Inspect map correctness and performance as the bin grows.

Exercise 3 — Queue backpressure

Compare an unbounded queue with ArrayBlockingQueue when producers run faster than consumers. Observe memory and rejection/blocking behavior.

Exercise 4 — Collection benchmark

Use JMH to compare ArrayList and LinkedList iteration, random access, end insertion, and iterator-position insertion at realistic sizes.

Code-review checklist

  • Is the collection implementation appropriate for the dominant operation?
  • Are keys/elements immutable with correct equality and comparator contracts?
  • Is concurrent access visible in the type and atomic workflow?
  • Is capacity bounded or governed by eviction/backpressure?
  • Does the API expose a mutable internal collection accidentally?
  • Can views retain a much larger source collection?
  • Are metrics available for size, growth, lag, eviction, and rejection?
