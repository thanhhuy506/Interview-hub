Complete practical guide

Design patterns are reusable decisions, not code templates.

This document covers all 23 classic Gang of Four patterns, plus the Java, Spring, DDD, architecture, data, resilience, and microservice patterns most often discussed in senior backend interviews. Every pattern explains the problem, internal idea, suitable and unsuitable cases, advantages, trade-offs, a Java 8 example, a real project scenario, and a senior-level interview answer.

Senior mindset: Do not start with “Which pattern can I use?” Start with the problem, forces, failure behavior, rate of change, and simplest design. A pattern is useful only when it makes those decisions clearer.

Foundation

1. Principles before patterns

Program to interfaces

Depend on stable behavior, not concrete classes. This makes Strategy, Factory, Adapter, and Proxy possible.

Composition over inheritance

Compose behavior when combinations and runtime replacement matter. Use inheritance for a true substitutable relationship or a stable Template Method.

Open/Closed Principle

New behavior should often be added through a new strategy, decorator, state, or handler rather than editing a large conditional.

Dependency Inversion

High-level business policy depends on ports/interfaces. Infrastructure implements those ports.

Explicit boundaries

Patterns should make network, transaction, state, and consistency boundaries clearer—not hide them.

YAGNI

Do not build variation points before there is credible variation. A simple constructor or method is often the best first design.

GoF

2. Creational patterns

Creational

Singleton

One controlled instance
Simple idea: Guarantee that a class has one logical instance and provide a controlled access point.

Why this pattern exists

Some infrastructure objects represent one shared resource or one application-wide policy, such as a configuration registry, metrics collector, or immutable lookup table. Creating many independent instances may waste resources or break consistency.

How it works

The constructor is hidden, and instance creation is controlled by the class or by a dependency-injection container. In modern Java applications, a Spring singleton-scoped bean is usually safer and easier to test than manually calling a global Singleton.

Use it when

  • The object is stateless or safely thread-safe.
  • Exactly one logical instance is required in one application context.
  • Lifecycle and creation must be centrally controlled.

Avoid it when

  • You only want convenient global access.
  • The object contains mutable request or user state.
  • Tests need isolated instances but the design hides dependencies.

Advantages

  • Controlled lifecycle and shared resource usage.
  • Can delay expensive creation.
  • Easy to integrate when a framework owns the singleton scope.

Disadvantages / trade-offs

  • Global state creates hidden coupling.
  • Thread safety is still your responsibility.
  • Manual singletons are harder to mock and reset in tests.

Java 8 example

public final class AppConfig {
    private AppConfig() {
    }

    private static class Holder {
        private static final AppConfig INSTANCE = new AppConfig();
    }

    public static AppConfig getInstance() {
        return Holder.INSTANCE;
    }
}

// Preferred in Spring:
// @Component
// public class AppConfig { ... }

Real project example

A Spring Boot application may have one immutable CurrencyRatePolicy bean used by multiple services. Spring creates and manages one singleton bean, while each service receives it through constructor injection.

Senior interview answer

Singleton controls instance count, but I do not use it simply to avoid passing dependencies. In Spring, I normally use a singleton-scoped bean and constructor injection because the container controls lifecycle and tests can replace the dependency. If the singleton has mutable state, I must make it thread-safe because many request threads may access the same instance.

Creational

Factory Method

Delegate object creation
Simple idea: Define a creation method and let subclasses or implementations decide which concrete object is created.

Why this pattern exists

Calling constructors directly couples business code to concrete classes. A factory method moves creation decisions behind a stable abstraction, so adding a new implementation does not require changing every caller.

How it works

The caller depends on an interface. A creator method selects or constructs the implementation. The classic GoF form uses inheritance, but practical Java code often uses a dedicated factory service.

Use it when

  • Creation depends on runtime input or configuration.
  • The caller should depend on an interface, not implementation classes.
  • Construction includes validation, mapping, or dependency selection.

Avoid it when

  • There is only one simple class and no expected variation.
  • The factory becomes a large switch with unrelated responsibilities.
  • A dependency-injection container already provides the required selection cleanly.

Advantages

  • Reduces direct coupling to concrete classes.
  • Centralizes creation rules.
  • Makes new implementations easier to introduce.

Disadvantages / trade-offs

  • Adds extra abstraction and classes.
  • A poorly designed factory can become a large conditional block.
  • It does not automatically remove all caller changes when behavior differs significantly.

Java 8 example

public interface NotificationSender {
    void send(String recipient, String message);
}

public final class EmailSender implements NotificationSender {
    public void send(String recipient, String message) {
        System.out.println("Email to " + recipient + ": " + message);
    }
}

public final class SmsSender implements NotificationSender {
    public void send(String recipient, String message) {
        System.out.println("SMS to " + recipient + ": " + message);
    }
}

public final class NotificationSenderFactory {
    public NotificationSender create(String channel) {
        if ("EMAIL".equalsIgnoreCase(channel)) {
            return new EmailSender();
        }
        if ("SMS".equalsIgnoreCase(channel)) {
            return new SmsSender();
        }
        throw new IllegalArgumentException("Unsupported channel: " + channel);
    }
}

Real project example

An order system chooses EmailSender, SmsSender, or PushSender based on customer preference. OrderService depends only on NotificationSender, while the factory owns the channel-to-implementation mapping.

Senior interview answer

Factory Method separates object creation from object use. I use it when runtime conditions choose an implementation or construction is non-trivial. I still watch for a factory with a very large switch; at that point I may register strategies in a Map or let Spring inject implementations by qualifier.

Creational

Abstract Factory

Create compatible object families
Simple idea: Create related objects as one compatible family without exposing their concrete classes.

Why this pattern exists

Some products must be used together. Mixing implementations from different vendors or platforms may produce invalid behavior. Abstract Factory keeps the family consistent.

How it works

The abstract factory declares multiple creation methods. Each concrete factory returns products belonging to one family. The client works only with product interfaces.

Use it when

  • You support multiple vendors, platforms, regions, or themes.
  • Products in one family must remain compatible.
  • You need to switch the whole family through configuration.

Avoid it when

  • Only one product varies.
  • The family changes frequently and adding one product forces every factory to change.
  • A simpler factory or dependency injection is enough.

Advantages

  • Ensures product-family consistency.
  • Hides vendor-specific classes.
  • Supports environment-level replacement.

Disadvantages / trade-offs

  • Adding a new product type affects all factories.
  • Creates many interfaces and classes.
  • Can be over-engineering for a small system.

Java 8 example

public interface PaymentClient {
    void charge(long amount);
}

public interface RefundClient {
    void refund(long amount);
}

public interface PaymentProviderFactory {
    PaymentClient paymentClient();
    RefundClient refundClient();
}

public final class ProviderAFactory implements PaymentProviderFactory {
    public PaymentClient paymentClient() {
        return amount -> System.out.println("Provider A charge " + amount);
    }

    public RefundClient refundClient() {
        return amount -> System.out.println("Provider A refund " + amount);
    }
}

Real project example

A payment platform supports Provider A and Provider B. Each provider has charge, refund, and status clients with different authentication and payloads. One factory produces the complete compatible adapter family.

Senior interview answer

Abstract Factory creates a family of related products. The key value is consistency: I can swap the entire provider family without letting the caller accidentally combine Provider A charge logic with Provider B refund logic. Its weakness is that adding a new product method changes every concrete factory.

Creational

Builder

Construct complex objects step by step
Simple idea: Build an object through readable steps while keeping construction separate from the final object.

Why this pattern exists

Constructors with many parameters are hard to read and easy to call incorrectly, especially when several arguments share the same type. Builder supports optional fields and centralized validation.

How it works

The builder stores temporary construction state. Fluent methods set values, and build() validates and creates the final object. The final object should preferably be immutable.

Use it when

  • The object has many optional parameters.
  • Construction must be readable and validated.
  • You want immutable domain or DTO objects.

Avoid it when

  • The object has two or three obvious required fields.
  • The builder allows invalid intermediate state without build-time validation.
  • The object is a simple mutable JPA entity managed through setters.

Advantages

  • Readable named construction.
  • Supports immutability and validation.
  • Avoids telescoping constructors.

Disadvantages / trade-offs

  • More code and another class.
  • Required fields may be forgotten unless validated.
  • A generic builder can weaken domain invariants.

Java 8 example

public final class PaymentRequest {
    private final String customerId;
    private final long amount;
    private final String currency;
    private final String description;

    private PaymentRequest(Builder builder) {
        this.customerId = builder.customerId;
        this.amount = builder.amount;
        this.currency = builder.currency;
        this.description = builder.description;
    }

    public static Builder builder(String customerId, long amount) {
        return new Builder(customerId, amount);
    }

    public static final class Builder {
        private final String customerId;
        private final long amount;
        private String currency = "USD";
        private String description;

        private Builder(String customerId, long amount) {
            this.customerId = customerId;
            this.amount = amount;
        }

        public Builder currency(String currency) {
            this.currency = currency;
            return this;
        }

        public Builder description(String description) {
            this.description = description;
            return this;
        }

        public PaymentRequest build() {
            if (amount <= 0) {
                throw new IllegalStateException("amount must be positive");
            }
            return new PaymentRequest(this);
        }
    }
}

Real project example

A PSP request may contain customer ID, amount, currency, callback URL, metadata, risk data, and optional 3DS information. A builder makes call sites readable and validates mandatory rules before sending the request.

Senior interview answer

Builder is valuable for complex immutable objects with optional fields. I make required values explicit in the builder constructor or static factory and validate invariants in build(). I avoid builders that simply mirror every setter because they add syntax without protecting the domain model.

Creational

Prototype

Create by copying
Simple idea: Create new objects by copying an existing configured object instead of constructing from the beginning.

Why this pattern exists

Some objects are expensive or complicated to initialize. A configured prototype can be copied and then adjusted for a specific request.

How it works

The prototype exposes a copy operation. The implementation must decide whether nested mutable objects require a deep copy or can be shared safely.

Use it when

  • Initial setup is expensive.
  • Many objects share a common configuration.
  • Runtime classes should be copied without knowing exact concrete types.

Avoid it when

  • The object graph has complex mutable references and copy semantics are unclear.
  • A normal constructor is cheap and clear.
  • Java clone() would expose unsafe shallow-copy behavior.

Advantages

  • Reduces repeated initialization.
  • Hides concrete creation details.
  • Can create variants quickly.

Disadvantages / trade-offs

  • Deep copying is difficult.
  • Shared mutable state can create subtle bugs.
  • Copy behavior must evolve with every new field.

Java 8 example

public final class ReportTemplate {
    private String title;
    private Map<String, String> settings;

    public ReportTemplate copy() {
        ReportTemplate copy = new ReportTemplate();
        copy.title = this.title;
        copy.settings = new HashMap<String, String>(this.settings);
        return copy;
    }
}

Real project example

A report engine loads a complex base template from storage. For each customer, it copies the template and changes title, filters, and branding instead of loading and parsing the complete template again.

Senior interview answer

Prototype is copying-based creation. The main design question is copy depth. I prefer an explicit copy method or copy constructor over Object.clone(), because explicit code makes ownership of nested mutable fields clear.

GoF

3. Structural patterns

Structural

Adapter

Convert incompatible interfaces
Simple idea: Wrap an incompatible class and expose the interface expected by the application.

Why this pattern exists

External SDKs and legacy code often use APIs that do not match the application's domain interfaces. Direct use spreads vendor types throughout the codebase.

How it works

The adapter implements the application's interface, translates the request to the external format, calls the external component, and maps the result back.

Use it when

  • Integrating a third-party SDK.
  • Migrating a legacy implementation behind a new interface.
  • Preventing vendor models from leaking into the domain.

Avoid it when

  • The interfaces already match.
  • The adapter starts containing major business rules.
  • You need to simplify a large subsystem rather than convert one interface; use Facade.

Advantages

  • Isolates vendor changes.
  • Keeps the domain model clean.
  • Improves testability.

Disadvantages / trade-offs

  • Adds mapping code.
  • Can hide important semantic differences.
  • May require many adapters for a large external API.

Java 8 example

public interface PaymentGateway {
    PaymentResult charge(PaymentRequest request);
}

public final class PspPaymentAdapter implements PaymentGateway {
    private final ExternalPspClient client;

    public PspPaymentAdapter(ExternalPspClient client) {
        this.client = client;
    }

    public PaymentResult charge(PaymentRequest request) {
        ExternalRequest external = mapRequest(request);
        ExternalResponse response = client.makePayment(external);
        return mapResponse(response);
    }

    private ExternalRequest mapRequest(PaymentRequest request) {
        return new ExternalRequest();
    }

    private PaymentResult mapResponse(ExternalResponse response) {
        return new PaymentResult();
    }
}

Real project example

Your domain uses PaymentGateway. Provider A requires XML, Provider B requires JSON, and Provider C returns HTML redirect data. Each adapter maps between the domain and provider-specific contracts.

Senior interview answer

Adapter changes the interface, not the underlying responsibility. I use it at integration boundaries so vendor DTOs and errors do not spread into business code. I keep business decisions outside the adapter; it should translate protocol and semantics, then return domain-level results.

Structural

Bridge

Separate two independent dimensions
Simple idea: Split an abstraction from its implementation so both dimensions can vary independently.

Why this pattern exists

Inheritance creates a class explosion when two dimensions vary. For example, Email/SMS/Push combined with AWS/Azure/OnPrem would produce many subclasses.

How it works

One hierarchy represents the abstraction, and it delegates to another hierarchy representing implementation. Composition connects them at runtime.

Use it when

  • Two dimensions change independently.
  • Inheritance would create many combinations.
  • Runtime switching is useful.

Avoid it when

  • Only one dimension varies.
  • The extra abstraction makes a simple design harder to understand.
  • The implementation interface is unstable and not meaningful.

Advantages

  • Avoids subclass explosion.
  • Supports independent evolution.
  • Promotes composition over inheritance.

Disadvantages / trade-offs

  • More moving parts.
  • The abstraction boundary can be difficult to discover.
  • May be confused with Adapter.

Java 8 example

public interface MessageTransport {
    void deliver(String recipient, String content);
}

public abstract class Notification {
    protected final MessageTransport transport;

    protected Notification(MessageTransport transport) {
        this.transport = transport;
    }

    public abstract void send(String recipient, String content);
}

public final class UrgentNotification extends Notification {
    public UrgentNotification(MessageTransport transport) {
        super(transport);
    }

    public void send(String recipient, String content) {
        transport.deliver(recipient, "[URGENT] " + content);
    }
}

Real project example

Notification type varies by business meaning—urgent, marketing, security—while transport varies independently—email, SMS, push. Bridge avoids one subclass for every pair.

Senior interview answer

Bridge is useful when both abstraction and implementation have independent variation. Unlike Adapter, which makes an existing interface compatible, Bridge is designed upfront to prevent combinatorial inheritance.

Structural

Composite

Treat part and whole uniformly
Simple idea: Represent tree structures so clients can work with a single object or a group through the same interface.

Why this pattern exists

Hierarchical data such as menus, organization units, file systems, or rules contains both leaves and containers. Without Composite, client code repeatedly checks types.

How it works

A common component interface defines operations. Leaves perform the operation directly; composites store children and delegate recursively.

Use it when

  • The domain is naturally hierarchical.
  • Clients should treat leaves and groups uniformly.
  • Recursive operations are common.

Avoid it when

  • The hierarchy needs very different operations for leaves and containers.
  • Uniformity would hide invalid operations.
  • The structure is not really a tree.

Advantages

  • Simple recursive client code.
  • Easy to add new component types.
  • Models hierarchies naturally.

Disadvantages / trade-offs

  • Can make the common interface too general.
  • Runtime validation may replace compile-time constraints.
  • Large trees may need performance controls.

Java 8 example

public interface PricingRule {
    BigDecimal apply(BigDecimal amount);
}

public final class DiscountRule implements PricingRule {
    private final BigDecimal rate;

    public DiscountRule(BigDecimal rate) {
        this.rate = rate;
    }

    public BigDecimal apply(BigDecimal amount) {
        return amount.subtract(amount.multiply(rate));
    }
}

public final class RuleGroup implements PricingRule {
    private final List<PricingRule> rules = new ArrayList<PricingRule>();

    public void add(PricingRule rule) {
        rules.add(rule);
    }

    public BigDecimal apply(BigDecimal amount) {
        BigDecimal result = amount;
        for (PricingRule rule : rules) {
            result = rule.apply(result);
        }
        return result;
    }
}

Real project example

A promotion may contain individual rules and nested rule groups. The pricing engine applies any PricingRule without checking whether it is a leaf or a group.

Senior interview answer

Composite models a part-whole hierarchy. The benefit is uniform client code, but I ensure the shared interface remains semantically valid. If leaf nodes expose meaningless add/remove methods, the abstraction is probably too broad.

Structural

Decorator

Add behavior dynamically
Simple idea: Wrap an object with the same interface and add behavior before or after delegation.

Why this pattern exists

Inheritance fixes behavior at compile time and creates many subclasses for combinations. Decorator composes behaviors dynamically.

How it works

Both the original component and decorator implement the same interface. The decorator stores another component and delegates while adding behavior.

Use it when

  • Cross-cutting behavior must be composed per instance.
  • Many optional behavior combinations exist.
  • The original class should remain unchanged.

Avoid it when

  • The behavior should apply globally through middleware or AOP.
  • Many decorators make the call chain difficult to understand.
  • Order-dependent decorators are not documented.

Advantages

  • Flexible composition.
  • Follows Open/Closed Principle.
  • Avoids subclass explosion.

Disadvantages / trade-offs

  • Many small wrapper objects.
  • Behavior order matters.
  • Debugging wrapper chains can be difficult.

Java 8 example

public interface DocumentStorage {
    void save(String key, byte[] content);
}

public final class S3DocumentStorage implements DocumentStorage {
    public void save(String key, byte[] content) {
        System.out.println("Saved " + key);
    }
}

public final class EncryptedStorageDecorator implements DocumentStorage {
    private final DocumentStorage delegate;

    public EncryptedStorageDecorator(DocumentStorage delegate) {
        this.delegate = delegate;
    }

    public void save(String key, byte[] content) {
        byte[] encrypted = encrypt(content);
        delegate.save(key, encrypted);
    }

    private byte[] encrypt(byte[] content) {
        return content;
    }
}

Real project example

A storage service can be decorated with encryption, compression, metrics, or checksum validation. Different deployments can compose only the required behaviors.

Senior interview answer

Decorator keeps the same interface and adds behavior dynamically. I distinguish it from Proxy by intent: Decorator adds responsibilities, while Proxy primarily controls access or location. In Spring, filters and many stream wrappers are decorator-style designs.

Structural

Facade

Provide a simple entry point
Simple idea: Expose a small, convenient interface over a complex subsystem.

Why this pattern exists

A use case may require many services in a specific sequence. If controllers or clients coordinate them directly, orchestration becomes duplicated and tightly coupled.

How it works

The facade owns the high-level workflow and delegates to subsystem components. It does not need to hide every advanced API; it offers the common path.

Use it when

  • A subsystem has many steps or interfaces.
  • Clients need a stable use-case-level API.
  • You want to reduce coupling to subsystem details.

Avoid it when

  • The facade becomes a god service containing all business logic.
  • Clients need low-level capabilities that the facade hides.
  • The subsystem is already simple.

Advantages

  • Simplifies common use cases.
  • Reduces client coupling.
  • Centralizes orchestration.

Disadvantages / trade-offs

  • Can become too large.
  • May hide important failure or transaction behavior.
  • Does not remove subsystem complexity internally.

Java 8 example

public final class OrderCheckoutFacade {
    private final InventoryService inventory;
    private final PaymentService payment;
    private final OrderService orderService;

    public OrderCheckoutFacade(
            InventoryService inventory,
            PaymentService payment,
            OrderService orderService) {
        this.inventory = inventory;
        this.payment = payment;
        this.orderService = orderService;
    }

    public OrderId checkout(CheckoutCommand command) {
        inventory.reserve(command.getItems());
        PaymentId paymentId = payment.charge(command.getPayment());
        return orderService.create(command, paymentId);
    }
}

Real project example

A checkout facade coordinates inventory, promotions, payment, order creation, and notification. The REST controller calls one use-case method instead of knowing every internal service.

Senior interview answer

Facade simplifies a subsystem; it does not convert an incompatible interface like Adapter. I keep the facade use-case focused and explicit about transaction and failure boundaries, especially when external systems are involved.

Structural

Flyweight

Share immutable intrinsic state
Simple idea: Reuse many small immutable objects by separating shared intrinsic state from per-use extrinsic state.

Why this pattern exists

Applications may create millions of logically similar objects. Sharing stable state can reduce memory usage.

How it works

A factory caches flyweight instances keyed by intrinsic state. The caller supplies changing extrinsic data when invoking behavior.

Use it when

  • Very many objects share the same immutable data.
  • Memory profiling proves object duplication is significant.
  • Extrinsic state can be passed separately.

Avoid it when

  • Object count is small.
  • State is mutable or user-specific.
  • The cache costs more complexity than the saved memory.

Advantages

  • Large memory reduction in the right problem.
  • Centralized shared state.
  • Can improve cache locality.

Disadvantages / trade-offs

  • Separating intrinsic and extrinsic state complicates APIs.
  • Requires careful immutability.
  • Caching can grow without bounds.

Java 8 example

public final class Currency {
    private final String code;

    Currency(String code) {
        this.code = code;
    }

    public String getCode() {
        return code;
    }
}

public final class CurrencyFactory {
    private final Map<String, Currency> cache =
            new ConcurrentHashMap<String, Currency>();

    public Currency get(String code) {
        return cache.computeIfAbsent(code, Currency::new);
    }
}

Real project example

A financial system reuses immutable Currency objects for USD, JPY, and EUR across millions of Money values instead of repeatedly storing equivalent metadata.

Senior interview answer

Flyweight is a memory optimization pattern, so I use it only after measurement. The shared state must be immutable, and the cache needs a bounded lifecycle if keys are not naturally limited.

Structural

Proxy

Control access to another object
Simple idea: Provide a stand-in that controls access, location, lifecycle, security, caching, or lazy creation.

Why this pattern exists

Clients may need to call an object without knowing whether it is remote, expensive, secured, transactional, or lazily loaded.

How it works

The proxy implements the same interface and delegates to the real subject after applying control logic.

Use it when

  • Remote calls, lazy loading, security, caching, transactions, or monitoring.
  • The client should see the same interface.
  • Access control belongs outside core behavior.

Avoid it when

  • The proxy hides expensive remote behavior behind a cheap-looking method.
  • Self-invocation bypasses framework proxies.
  • A wrapper is adding business responsibility rather than access control.

Advantages

  • Separates access concerns.
  • Transparent to callers.
  • Foundation of Spring AOP and Hibernate lazy proxies.

Disadvantages / trade-offs

  • Hidden network or transaction behavior.
  • Proxy limitations can surprise developers.
  • Stack traces and debugging become more complex.

Java 8 example

public interface CustomerService {
    Customer findById(long id);
}

public final class CachingCustomerServiceProxy implements CustomerService {
    private final CustomerService target;
    private final Map<Long, Customer> cache = new ConcurrentHashMap<Long, Customer>();

    public CachingCustomerServiceProxy(CustomerService target) {
        this.target = target;
    }

    public Customer findById(long id) {
        return cache.computeIfAbsent(id, target::findById);
    }
}

Real project example

Spring creates a transactional proxy around a service. Calls entering through the proxy open or join a transaction. A direct method call inside the same object bypasses the proxy, which explains the self-invocation problem.

Senior interview answer

Proxy controls access to a subject. Spring transactions, security, and caching frequently use proxies. A senior answer should mention that proxy behavior is applied only when calls pass through the proxy; self-invocation may bypass the advice.

GoF

4. Behavioral patterns

Behavioral

Chain of Responsibility

Pass a request through handlers
Simple idea: Send a request through an ordered chain until handlers process, enrich, reject, or pass it onward.

Why this pattern exists

Large conditional blocks couple every validation or processing rule. A chain makes handlers independent and reorderable.

How it works

Each handler decides whether to stop or delegate to the next handler. Some variants allow every handler to run.

Use it when

  • Validation pipelines, servlet filters, security filters, approval rules.
  • Handlers need configurable order.
  • New steps should be added independently.

Avoid it when

  • Order is unclear or unstable.
  • Every handler shares large mutable context.
  • A simple sequence of three explicit calls is clearer.

Advantages

  • Loose coupling between sender and handlers.
  • Easy extension and reordering.
  • Supports short-circuit behavior.

Disadvantages / trade-offs

  • Request may silently remain unhandled.
  • Order-related bugs.
  • Tracing a long chain is difficult.

Java 8 example

public interface RequestHandler {
    void handle(RequestContext context);
}

public abstract class BaseHandler implements RequestHandler {
    private RequestHandler next;

    public BaseHandler linkWith(RequestHandler next) {
        this.next = next;
        return this;
    }

    protected void next(RequestContext context) {
        if (next != null) {
            next.handle(context);
        }
    }
}

public final class AuthenticationHandler extends BaseHandler {
    public void handle(RequestContext context) {
        if (!context.isAuthenticated()) {
            throw new SecurityException("Unauthenticated");
        }
        next(context);
    }
}

Real project example

Spring Security uses an ordered filter chain. Authentication, CSRF, authorization, exception translation, and other filters process the request in sequence.

Senior interview answer

Chain of Responsibility is useful for ordered, independently replaceable processing steps. I make order explicit, define whether handlers short-circuit, and add observability because debugging a hidden chain can be difficult.

Behavioral

Command

Represent an action as an object
Simple idea: Encapsulate a request and its data as an object that can be queued, logged, retried, or executed later.

Why this pattern exists

A direct method call is difficult to serialize, schedule, retry, audit, or undo. A command makes the action explicit.

How it works

A command contains the data required for one action. A handler executes it. In enterprise systems, the command is often a message or application-layer DTO.

Use it when

  • Queues, job scheduling, audit, retry, undo, CQRS write models.
  • You need to decouple request creation from execution.
  • Actions need explicit names and validation.

Avoid it when

  • The command is only a meaningless wrapper around one method parameter.
  • Business behavior is scattered into an excessive number of tiny handlers.
  • A simple local call needs no decoupling.

Advantages

  • Supports asynchronous execution and retries.
  • Clear use-case boundary.
  • Easy auditing and testing.

Disadvantages / trade-offs

  • More classes.
  • Versioning serialized commands is difficult.
  • Exactly-once execution is not guaranteed by the pattern.

Java 8 example

public final class CreateOrderCommand {
    private final String customerId;
    private final List<String> productIds;

    public CreateOrderCommand(String customerId, List<String> productIds) {
        this.customerId = customerId;
        this.productIds = productIds;
    }

    public String getCustomerId() {
        return customerId;
    }
}

public final class CreateOrderHandler {
    public OrderId handle(CreateOrderCommand command) {
        // validate and create order
        return new OrderId();
    }
}

Real project example

An API accepts CreateOrderCommand, validates it, stores an outbox event, and later a worker executes downstream fulfillment. The command ID is used for idempotency.

Senior interview answer

Command makes a use case first-class. It is valuable for queues, retries, CQRS, and audit. I also design idempotency because a message broker can redeliver a command; the Command pattern alone does not guarantee exactly-once processing.

Behavioral

Interpreter

Evaluate a small language
Simple idea: Represent grammar rules as objects and evaluate expressions built from those rules.

Why this pattern exists

Some domains require a small configurable language, such as rules, search filters, or access expressions.

How it works

Each expression node implements interpret/evaluate. Composite expressions recursively evaluate child expressions.

Use it when

  • Small, stable domain-specific languages.
  • Expression trees generated from parsed input.
  • Rules need composition.

Avoid it when

  • The grammar is large or performance-critical.
  • A parser generator or existing expression engine is better.
  • Untrusted expressions are evaluated without limits.

Advantages

  • Grammar maps directly to classes.
  • Easy to compose expressions.
  • Useful for simple rules.

Disadvantages / trade-offs

  • Class explosion for large grammars.
  • Parsing and security are still separate problems.
  • Can be slow for complex expressions.

Java 8 example

public interface Expression {
    boolean evaluate(User user);
}

public final class HasRole implements Expression {
    private final String role;

    public HasRole(String role) {
        this.role = role;
    }

    public boolean evaluate(User user) {
        return user.getRoles().contains(role);
    }
}

public final class AndExpression implements Expression {
    private final Expression left;
    private final Expression right;

    public AndExpression(Expression left, Expression right) {
        this.left = left;
        this.right = right;
    }

    public boolean evaluate(User user) {
        return left.evaluate(user) && right.evaluate(user);
    }
}

Real project example

A promotion engine builds an expression tree such as customerIsPremium AND orderAmountAbove100. For more complex rules, a dedicated rules engine is often better.

Senior interview answer

Interpreter is appropriate for a small DSL. I do not build a large language manually with this pattern; once grammar, performance, diagnostics, and security become substantial, I use a parser library or rules engine.

Behavioral

Iterator

Traverse without exposing representation
Simple idea: Provide sequential access to elements without exposing the collection's internal structure.

Why this pattern exists

Clients should traverse a collection without depending on whether it is backed by an array, tree, database cursor, or paginated API.

How it works

The iterator maintains traversal state and exposes hasNext/next. Java's Iterable integrates this with the enhanced for loop.

Use it when

  • Custom collections.
  • Lazy traversal.
  • Pagination or cursor abstraction.

Avoid it when

  • A normal List iterator already solves the problem.
  • Resources remain open without lifecycle control.
  • The iterator hides expensive remote calls unexpectedly.

Advantages

  • Encapsulates traversal state.
  • Supports multiple traversal strategies.
  • Works with Java foreach.

Disadvantages / trade-offs

  • Concurrent modification behavior must be defined.
  • Lazy iterators may hold resources.
  • Remote or DB iteration can create N+1 calls.

Java 8 example

public final class NumberRange implements Iterable<Integer> {
    private final int start;
    private final int end;

    public NumberRange(int start, int end) {
        this.start = start;
        this.end = end;
    }

    public Iterator<Integer> iterator() {
        return new Iterator<Integer>() {
            private int current = start;

            public boolean hasNext() {
                return current <= end;
            }

            public Integer next() {
                if (!hasNext()) {
                    throw new NoSuchElementException();
                }
                return current++;
            }
        };
    }
}

Real project example

A paginated API iterator fetches the next page only when the current page is exhausted. The caller sees a normal traversal, while the iterator controls pagination.

Senior interview answer

Iterator separates traversal from representation. For lazy database or network iterators, I document resource ownership and performance because a harmless-looking loop may trigger many I/O calls.

Behavioral

Mediator

Centralize collaboration
Simple idea: Move complex communication between many objects into a mediator so they do not reference each other directly.

Why this pattern exists

When components call each other in many directions, dependencies form a difficult graph. Mediator centralizes coordination.

How it works

Colleagues communicate through the mediator. The mediator knows the collaboration workflow, while colleagues focus on their own responsibilities.

Use it when

  • UI components, workflow coordination, message routing.
  • Many-to-many communication is becoming complex.
  • You want to reduce direct dependencies.

Avoid it when

  • The mediator becomes a god object.
  • Simple direct collaboration is clearer.
  • Domain rules should live in domain objects rather than one coordinator.

Advantages

  • Reduces coupling among components.
  • Centralizes workflow.
  • Makes components reusable.

Disadvantages / trade-offs

  • Mediator can grow too large.
  • Business logic may become procedural.
  • A single coordination bottleneck may appear.

Java 8 example

public interface CheckoutMediator {
    void itemAdded(String productId);
}

public final class CheckoutPageMediator implements CheckoutMediator {
    private final PriceView priceView;
    private final InventoryView inventoryView;

    public CheckoutPageMediator(
            PriceView priceView,
            InventoryView inventoryView) {
        this.priceView = priceView;
        this.inventoryView = inventoryView;
    }

    public void itemAdded(String productId) {
        priceView.refresh(productId);
        inventoryView.refresh(productId);
    }
}

Real project example

In application architecture, an application service may act as a mediator among repositories, domain services, and external gateways for one use case.

Senior interview answer

Mediator centralizes interaction, while Facade simplifies access to a subsystem. I use Mediator when peer components would otherwise communicate in a complex graph, but I split it by use case to avoid a giant coordinator.

Behavioral

Memento

Capture and restore state
Simple idea: Save an object's internal state so it can be restored later without exposing implementation details.

Why this pattern exists

Undo, snapshots, and rollback-like user operations need historical state. Exposing every internal field breaks encapsulation.

How it works

The originator creates a memento. A caretaker stores it but does not interpret it. The originator restores itself from the memento.

Use it when

  • Undo/redo in editors.
  • Short-lived workflow snapshots.
  • State checkpoints.

Avoid it when

  • Snapshots contain huge object graphs.
  • Database transactions or event sourcing already provide the required history.
  • Sensitive state would be stored insecurely.

Advantages

  • Preserves encapsulation.
  • Simple undo behavior.
  • Clear snapshot ownership.

Disadvantages / trade-offs

  • Memory cost.
  • Version compatibility problems.
  • Deep-copy complexity.

Java 8 example

public final class TextEditor {
    private String content = "";

    public Memento save() {
        return new Memento(content);
    }

    public void restore(Memento memento) {
        this.content = memento.content;
    }

    public static final class Memento {
        private final String content;

        private Memento(String content) {
            this.content = content;
        }
    }
}

Real project example

An admin configuration screen stores a snapshot before editing. If the user cancels, the editor restores the previous state. Persistent audit history may require Event Sourcing instead.

Senior interview answer

Memento captures state for restoration while preserving encapsulation. I consider snapshot size, sensitive information, and versioning. It is not a substitute for database transaction rollback across external systems.

Behavioral

Observer

Publish state changes
Simple idea: Notify subscribed observers when a subject changes without tightly coupling the subject to concrete listeners.

Why this pattern exists

One event may trigger many independent reactions. Direct calls make the publisher depend on every consumer.

How it works

Observers subscribe to a subject or event bus. The subject publishes an event; observers react. Delivery may be synchronous or asynchronous.

Use it when

  • Domain events, UI listeners, cache invalidation, notifications.
  • Consumers can evolve independently.
  • One event has multiple reactions.

Avoid it when

  • Strong consistency is required across all reactions.
  • Events are used to hide a required direct workflow.
  • Failure, ordering, and retries are undefined.

Advantages

  • Loose coupling.
  • Easy addition of subscribers.
  • Natural event-driven design.

Disadvantages / trade-offs

  • Harder execution tracing.
  • Synchronous observers can fail the publisher.
  • Asynchronous delivery introduces eventual consistency and duplicates.

Java 8 example

public interface OrderCreatedListener {
    void onOrderCreated(OrderCreatedEvent event);
}

public final class OrderEventPublisher {
    private final List<OrderCreatedListener> listeners =
            new ArrayList<OrderCreatedListener>();

    public void subscribe(OrderCreatedListener listener) {
        listeners.add(listener);
    }

    public void publish(OrderCreatedEvent event) {
        for (OrderCreatedListener listener : listeners) {
            listener.onOrderCreated(event);
        }
    }
}

Real project example

After an order commits, an outbox event is published. Inventory, analytics, and email consumers react independently. Consumers are idempotent because the broker may redeliver.

Senior interview answer

Observer decouples the publisher from subscribers. In-process synchronous listeners and distributed asynchronous events have very different guarantees. For distributed systems, I discuss outbox, idempotency, ordering, retries, dead-letter handling, and eventual consistency.

Behavioral

State

Change behavior with state
Simple idea: Move state-specific behavior into state objects so an object's behavior changes when its state changes.

Why this pattern exists

Large if/switch blocks based on status become difficult to maintain and allow invalid transitions.

How it works

The context delegates operations to the current State. A state handles valid behavior and chooses the next state.

Use it when

  • Order, payment, workflow, or document lifecycle.
  • Behavior differs significantly by state.
  • Transition rules must be explicit.

Avoid it when

  • There are only two simple states.
  • State classes contain unrelated behavior.
  • A data-driven state machine library would be more appropriate.

Advantages

  • Eliminates large conditionals.
  • Makes transitions explicit.
  • Keeps state-specific rules together.

Disadvantages / trade-offs

  • More classes.
  • Cross-state transitions can become complex.
  • Persistence mapping requires care.

Java 8 example

public interface PaymentState {
    void capture(Payment payment);
    void cancel(Payment payment);
}

public final class AuthorizedState implements PaymentState {
    public void capture(Payment payment) {
        payment.changeState(new CapturedState());
    }

    public void cancel(Payment payment) {
        payment.changeState(new CancelledState());
    }
}

public final class Payment {
    private PaymentState state;

    public void capture() {
        state.capture(this);
    }

    void changeState(PaymentState state) {
        this.state = state;
    }
}

Real project example

Payment behavior differs for CREATED, AUTHORIZED, CAPTURED, FAILED, and REFUNDED. State objects prevent refund-before-capture or capture-after-cancel transitions.

Senior interview answer

State is appropriate when behavior, not only data, depends on lifecycle status. Strategy chooses an algorithm from outside; State usually changes internally as the object transitions.

Behavioral

Strategy

Swap algorithms
Simple idea: Encapsulate interchangeable algorithms behind one interface and select one at runtime.

Why this pattern exists

Conditional algorithm selection spreads across services and makes new policies difficult to add.

How it works

A context delegates to a Strategy interface. A factory, configuration, or dependency-injection container selects the strategy.

Use it when

  • Pricing, routing, validation, retry, tax, or payment algorithms.
  • Algorithms share the same purpose.
  • Runtime selection is needed.

Avoid it when

  • The algorithms do not have a meaningful common contract.
  • The strategy needs excessive context parameters.
  • There is only one stable algorithm.

Advantages

  • Open/Closed Principle.
  • Easy unit testing.
  • Removes repeated conditions.

Disadvantages / trade-offs

  • Clients or factories must select correctly.
  • Too many tiny strategies.
  • Common interface may become weak.

Java 8 example

public interface DiscountStrategy {
    BigDecimal calculate(Order order);
}

public final class VipDiscountStrategy implements DiscountStrategy {
    public BigDecimal calculate(Order order) {
        return order.getSubtotal().multiply(new BigDecimal("0.10"));
    }
}

public final class DiscountService {
    private final Map<String, DiscountStrategy> strategies;

    public DiscountService(Map<String, DiscountStrategy> strategies) {
        this.strategies = strategies;
    }

    public BigDecimal calculate(String type, Order order) {
        DiscountStrategy strategy = strategies.get(type);
        if (strategy == null) {
            throw new IllegalArgumentException("Unknown strategy");
        }
        return strategy.calculate(order);
    }
}

Real project example

A shipping service selects Standard, Express, or SameDay strategy based on region and order. Each strategy can be tested independently.

Senior interview answer

Strategy encapsulates interchangeable algorithms. In Spring, I often inject a list or map of strategy beans rather than maintain a large switch. I keep selection logic separate from algorithm logic.

Behavioral

Template Method

Fix algorithm skeleton
Simple idea: Define the stable algorithm steps in a base class while allowing subclasses to override selected steps.

Why this pattern exists

Multiple workflows share the same sequence but differ in a few operations. Copying the whole workflow creates duplication.

How it works

A final template method calls abstract or hook methods. Subclasses customize only designated steps.

Use it when

  • Framework extension points.
  • Import/export pipelines.
  • Stable sequence with small variations.

Avoid it when

  • Inheritance creates rigid coupling.
  • Subclasses need to reorder most steps.
  • Composition with Strategy would be more flexible.

Advantages

  • Reuses the algorithm skeleton.
  • Controls operation order.
  • Simple framework design.

Disadvantages / trade-offs

  • Inheritance-based coupling.
  • Fragile base class risk.
  • Subclass behavior can be hard to understand.

Java 8 example

public abstract class FileImporter {
    public final void importFile(Path path) {
        List<String> lines = read(path);
        List<Record> records = parse(lines);
        validate(records);
        save(records);
    }

    protected List<String> read(Path path) {
        return Collections.emptyList();
    }

    protected abstract List<Record> parse(List<String> lines);

    protected void validate(List<Record> records) {
        // default validation
    }

    protected abstract void save(List<Record> records);
}

Real project example

CSV, fixed-width, and JSON imports share read, validate, save, and audit steps but customize parsing and persistence details.

Senior interview answer

Template Method uses inheritance to preserve a stable process. Strategy uses composition to swap one algorithm. I prefer Template Method when the sequence must remain controlled; otherwise composition is usually more flexible.

Behavioral

Visitor

Add operations to stable object structures
Simple idea: Place operations in visitor objects so new operations can be added without changing every element class.

Why this pattern exists

A stable object hierarchy may need many unrelated operations such as validation, export, tax calculation, or reporting.

How it works

Elements implement accept(visitor), which dispatches to a type-specific visit method. This double dispatch selects behavior by both visitor and element type.

Use it when

  • Object structure is stable.
  • New operations are added frequently.
  • Operations need type-specific behavior.

Avoid it when

  • New element types are added frequently.
  • Double dispatch makes the model harder for the team.
  • Pattern matching or polymorphism is simpler.

Advantages

  • Adds operations without modifying element classes.
  • Keeps one operation together.
  • Supports type-specific behavior.

Disadvantages / trade-offs

  • Adding an element type changes all visitors.
  • Breaks encapsulation if visitors need internals.
  • Verbose.

Java 8 example

public interface OrderItem {
    void accept(OrderItemVisitor visitor);
}

public final class PhysicalItem implements OrderItem {
    public void accept(OrderItemVisitor visitor) {
        visitor.visit(this);
    }
}

public final class DigitalItem implements OrderItem {
    public void accept(OrderItemVisitor visitor) {
        visitor.visit(this);
    }
}

public interface OrderItemVisitor {
    void visit(PhysicalItem item);
    void visit(DigitalItem item);
}

Real project example

A stable product hierarchy needs tax, shipping, and export operations. Each visitor implements one operation across all product types.

Senior interview answer

Visitor is strongest when element types are stable and operations change frequently. If new element types are common, Visitor is expensive because every visitor must change.

Behavioral

Mediator vs Event Bus note

Clarify coordination
Simple idea: Use direct mediation for a known workflow; use events for decoupled reactions.

Why this pattern exists

Teams often confuse a mediator with an event bus. A mediator usually coordinates a request to one handler or a known set of collaborators, while an event bus broadcasts notifications to independent consumers.

How it works

A request mediator preserves a request/response flow. An event bus distributes events and accepts eventual processing.

Use it when

  • You need an explicit distinction in architecture reviews.
  • Commands and events are being mixed.
  • Request handling should stay traceable.

Avoid it when

  • Treating every method call as an event.
  • Using asynchronous events for logic that must succeed atomically.
  • Creating generic infrastructure without a concrete need.

Advantages

  • Clearer consistency boundaries.
  • Better message semantics.
  • Improved observability.

Disadvantages / trade-offs

  • Requires naming discipline.
  • Infrastructure does not solve domain design.
  • Developers may still misuse generic buses.

Java 8 example

// Command: one intended handler
commandBus.send(new CreateOrderCommand(...));

// Event: zero to many independent consumers
eventPublisher.publish(new OrderCreatedEvent(...));

Real project example

CreateOrderCommand has one application handler. OrderCreatedEvent may be consumed by email, analytics, and fulfillment.

Senior interview answer

I distinguish commands from events by intent. A command asks a specific capability to perform work and may be rejected. An event states that something already happened. This affects ownership, retries, idempotency, and consistency.

Behavioral

Null Object

Represent do-nothing behavior
Simple idea: Provide an object with neutral behavior instead of returning null and forcing repeated checks.

Why this pattern exists

Optional behavior can produce scattered null checks. A Null Object keeps polymorphic calls safe.

How it works

A no-op implementation follows the same interface and performs nothing or returns a neutral result.

Use it when

  • A neutral behavior is well-defined.
  • The caller should not branch for absence.
  • No-op logging, notification, or metrics is useful.

Avoid it when

  • Absence is an error that must be visible.
  • The neutral behavior could hide a configuration mistake.
  • Optional communicates absence more clearly.

Advantages

  • Removes repeated null checks.
  • Preserves polymorphism.
  • Simple defaults.

Disadvantages / trade-offs

  • Can hide missing configuration.
  • Neutral behavior may be domain-specific.
  • Another implementation to maintain.

Java 8 example

public interface AuditLogger {
    void log(String action);
}

public final class NoOpAuditLogger implements AuditLogger {
    public void log(String action) {
        // intentionally empty
    }
}

Real project example

A local development profile may inject NoOpMetricsPublisher, while production injects the real publisher.

Senior interview answer

Null Object is useful only when doing nothing is a valid behavior. If absence should fail fast, I throw a configuration error or use Optional rather than silently hiding it.

Java / Spring / DDD

5. Enterprise and application patterns

Enterprise / Java

Dependency Injection

Supply dependencies externally
Simple idea: An object receives its collaborators instead of creating them directly.

Why this pattern exists

Direct construction couples a class to implementations and lifecycle. DI makes dependencies explicit and replaceable.

How it works

Constructor injection is preferred for required dependencies. A container such as Spring creates objects, resolves collaborators, and manages scopes.

Use it when

  • Services depend on repositories, clients, clocks, or policies.
  • Implementations vary by environment.
  • Testability and lifecycle control matter.

Avoid it when

  • Service locator hides dependencies.
  • Field injection makes construction and tests unclear.
  • Every value object is created through the container.

Advantages

  • Loose coupling.
  • Easy testing.
  • Central lifecycle and configuration.

Disadvantages / trade-offs

  • Container configuration can become complex.
  • Runtime wiring errors.
  • Overuse may create anemic classes.

Java 8 example

@Service
public class OrderService {
    private final OrderRepository repository;
    private final PaymentGateway paymentGateway;

    public OrderService(
            OrderRepository repository,
            PaymentGateway paymentGateway) {
        this.repository = repository;
        this.paymentGateway = paymentGateway;
    }
}

Real project example

Spring injects a PSP adapter in production and a fake gateway in tests. OrderService never creates the vendor client.

Senior interview answer

DI implements Dependency Inversion by making collaborators explicit. I prefer constructor injection because required dependencies are visible, immutable, and easy to test. I avoid service locator and field injection because they hide dependencies.

Enterprise / DDD

Repository

Abstract aggregate persistence
Simple idea: Expose collection-like access to domain aggregates while hiding persistence details.

Why this pattern exists

Business services should not contain SQL or JPA query details. Repository creates a boundary between domain/application logic and persistence.

How it works

The repository interface speaks domain language. Infrastructure implements it with JPA, JDBC, or another store.

Use it when

  • Aggregate loading and saving.
  • Domain logic should be persistence-agnostic.
  • Tests need in-memory implementations.

Avoid it when

  • Wrapping every CRUD call without domain meaning.
  • Returning persistence entities directly to external APIs.
  • Building a generic repository that hides useful database capabilities.

Advantages

  • Domain-focused interface.
  • Testability.
  • Persistence isolation.

Disadvantages / trade-offs

  • Can become an unnecessary abstraction over Spring Data.
  • Complex queries may not fit collection semantics.
  • Leaky abstractions remain possible.

Java 8 example

public interface OrderRepository {
    Optional<Order> findById(OrderId id);
    void save(Order order);
    List<Order> findPendingForCustomer(CustomerId customerId);
}

Real project example

OrderService asks for pending orders by customer without knowing whether the implementation uses JPA, JDBC, or an external store.

Senior interview answer

Repository should model aggregate persistence, not blindly duplicate EntityManager or JpaRepository. I keep query names in domain language and avoid returning infrastructure-specific types from the domain boundary.

Enterprise / Data

DAO

Encapsulate data access
Simple idea: Encapsulate low-level persistence operations for tables, records, or data sources.

Why this pattern exists

SQL, JDBC mapping, and database errors should not spread through business code.

How it works

DAO methods perform queries and map rows. Repository is usually domain/aggregate focused; DAO is often data-source or table focused.

Use it when

  • JDBC applications.
  • Reporting queries.
  • Low-level database access.

Avoid it when

  • Confusing DAO with a domain repository.
  • Creating both DAO and repository with identical methods.
  • Hiding transaction boundaries inside every DAO.

Advantages

  • Central SQL and mapping.
  • Reusable database access.
  • Clear infrastructure boundary.

Disadvantages / trade-offs

  • Can expose table-centric design.
  • May produce anemic services.
  • Another layer when Spring Data already suffices.

Java 8 example

public final class UserDao {
    private final DataSource dataSource;

    public UserRecord find(long id) throws SQLException {
        String sql = "select id, name from users where id = ?";
        try (Connection c = dataSource.getConnection();
             PreparedStatement ps = c.prepareStatement(sql)) {
            ps.setLong(1, id);
            try (ResultSet rs = ps.executeQuery()) {
                return rs.next()
                        ? new UserRecord(rs.getLong("id"), rs.getString("name"))
                        : null;
            }
        }
    }
}

Real project example

A reporting module uses DAOs for optimized SQL and projections instead of loading full domain aggregates.

Senior interview answer

DAO abstracts low-level data access; Repository abstracts domain aggregate persistence. In simple CRUD systems the distinction may be small, so I avoid creating both layers without a clear reason.

Enterprise

Service Layer

Define application use cases
Simple idea: Expose application operations and coordinate transactions, domain objects, repositories, and external gateways.

Why this pattern exists

Controllers should not own business workflows. Domain objects alone may not coordinate repositories and external services.

How it works

Each service method represents a use case, validates application-level rules, defines a transaction boundary, and delegates domain behavior.

Use it when

  • Business workflows span multiple collaborators.
  • Transaction boundaries need a clear home.
  • Multiple delivery channels reuse the same use case.

Avoid it when

  • Putting all business logic in giant services.
  • Creating one service method per repository method.
  • Mixing HTTP details into application services.

Advantages

  • Clear use-case API.
  • Reusable across REST, batch, and messaging.
  • Natural transaction boundary.

Disadvantages / trade-offs

  • Can become anemic and procedural.
  • Large services become god objects.
  • Domain logic may be misplaced.

Java 8 example

@Service
public class TransferApplicationService {
    @Transactional
    public void transfer(TransferCommand command) {
        Account from = repository.get(command.getFrom());
        Account to = repository.get(command.getTo());

        from.transferTo(to, command.getAmount());

        repository.save(from);
        repository.save(to);
    }
}

Real project example

A transfer application service starts a transaction, loads two accounts, asks the domain model to transfer, and persists the result.

Senior interview answer

Service Layer defines use cases and transaction boundaries. I keep orchestration there but place business invariants in domain objects or domain services when appropriate, avoiding a service layer that becomes one large script.

Enterprise / Data

Unit of Work

Track changes and commit together
Simple idea: Track objects changed during a business transaction and coordinate persistence as one unit.

Why this pattern exists

Multiple changes must be committed consistently and efficiently. Saving every change immediately increases database calls and can break atomicity.

How it works

The unit of work tracks new, dirty, and removed objects and flushes them within a transaction. JPA EntityManager implements this through the persistence context and dirty checking.

Use it when

  • Multiple entity changes belong to one transaction.
  • Change tracking and batching help.
  • ORM persistence context is used.

Avoid it when

  • Long-lived persistence contexts.
  • Assuming it handles distributed systems.
  • Keeping thousands of entities managed in one huge transaction.

Advantages

  • Atomic commit.
  • Dirty checking.
  • Batching opportunities.

Disadvantages / trade-offs

  • Hidden SQL timing.
  • Memory use.
  • Unexpected flush and lazy-loading behavior.

Java 8 example

@Transactional
public void renameCustomer(long id, String newName) {
    Customer customer = entityManager.find(Customer.class, id);
    customer.rename(newName);
    // JPA dirty checking updates at flush/commit.
}

Real project example

JPA tracks a managed Order and its items. At commit, Hibernate generates SQL for changed entities in one transaction.

Senior interview answer

JPA's persistence context is a Unit of Work. I understand that SQL may execute at flush rather than at setter call, and I keep transaction scope short to control locks, memory, and stale managed state.

Enterprise / API

DTO

Transfer shaped data
Simple idea: Carry data across process or layer boundaries without exposing domain or persistence objects.

Why this pattern exists

API contracts, domain models, and database entities evolve for different reasons. Reusing one class for all three creates coupling and security problems.

How it works

DTOs contain only required fields. Mapping occurs at the boundary through explicit code or a mapper.

Use it when

  • REST requests/responses.
  • External integrations.
  • Read projections and versioned contracts.

Avoid it when

  • Creating DTOs for every internal method call.
  • Blind reflection mapping of security-sensitive fields.
  • Putting domain behavior into DTOs.

Advantages

  • Stable API contract.
  • Data minimization.
  • Prevents lazy-loading and persistence leakage.

Disadvantages / trade-offs

  • Mapping code.
  • Potential duplication.
  • Version management.

Java 8 example

public final class UserResponse {
    private final long id;
    private final String displayName;

    public UserResponse(long id, String displayName) {
        this.id = id;
        this.displayName = displayName;
    }
}

Real project example

UserEntity includes password hash, internal flags, and audit fields. UserResponse exposes only ID and display name.

Senior interview answer

DTO protects boundaries. I do not return JPA entities from controllers because it leaks schema, may trigger lazy loading, and can expose sensitive fields. Mapping cost is usually worth the contract isolation.

DDD / Behavioral

Specification

Compose business predicates
Simple idea: Represent a business rule as an object that can be evaluated and combined with other rules.

Why this pattern exists

Complex eligibility rules become duplicated if written as booleans in many services.

How it works

A specification exposes isSatisfiedBy and composition such as and/or/not. Persistence specifications may also translate to query predicates.

Use it when

  • Eligibility, validation, filtering, policy composition.
  • Rules are reused and combined.
  • Business language matters.

Avoid it when

  • A simple one-line condition is enough.
  • Database and in-memory semantics differ.
  • Specifications become generic technical predicates with no domain meaning.

Advantages

  • Reusable rules.
  • Readable composition.
  • Easy unit testing.

Disadvantages / trade-offs

  • Many small classes.
  • Persistence translation complexity.
  • May hide expensive checks.

Java 8 example

public interface Specification<T> {
    boolean isSatisfiedBy(T value);

    default Specification<T> and(Specification<T> other) {
        return value -> this.isSatisfiedBy(value)
                && other.isSatisfiedBy(value);
    }
}

Real project example

A loan applicant must be Adult AND HasVerifiedIncome AND NotBlacklisted. Each rule is independently tested and composed.

Senior interview answer

Specification models a named business predicate. I separate in-memory domain specifications from database query specifications when translation would otherwise leak persistence concerns.

Presentation

MVC

Separate input, model, and view
Simple idea: Separate request handling, application/domain state, and presentation rendering.

Why this pattern exists

User-interface code, business logic, and rendering change independently.

How it works

Controller accepts input and invokes application services; Model represents state/data; View renders the response. In REST, the view is often JSON serialization rather than a template.

Use it when

  • Web applications.
  • Multiple views over the same application capabilities.
  • Clear presentation boundary.

Avoid it when

  • Putting business logic in controllers.
  • Treating JPA entities as the model returned directly.
  • Creating controller-service-repository layers with no meaningful separation.

Advantages

  • Separation of concerns.
  • Testable controllers and services.
  • Multiple presentation formats.

Disadvantages / trade-offs

  • Misused as only folder structure.
  • Extra mapping.
  • Thin layers can become ceremony.

Java 8 example

@RestController
@RequestMapping("/orders")
public class OrderController {
    private final OrderApplicationService service;

    public OrderController(OrderApplicationService service) {
        this.service = service;
    }

    @PostMapping
    public OrderResponse create(@RequestBody CreateOrderRequest request) {
        return service.create(request);
    }
}

Real project example

Spring MVC controller validates HTTP input and calls an application service. Domain rules and transactions stay outside the controller.

Senior interview answer

MVC is a presentation pattern, not the complete backend architecture. In Spring, I keep controllers focused on HTTP concerns, then delegate use cases to application services.

Architecture

6. Architecture, data, resilience, and microservice patterns

Architecture

Layered Architecture

Simple idea: Organize code into presentation, application/service, domain, and infrastructure/data layers.

Use it when

Useful for CRUD and enterprise systems with clear responsibilities.

Main risk

Risk: business logic becomes database-centric and every request passes through unnecessary layers.

Typical flow

Controller → Application Service → Domain/Repository → Database

Senior interview answer

Layering gives dependency direction and separation, but I avoid treating it as only packages. Domain rules should not depend on controllers or database frameworks.

Architecture

Hexagonal Architecture

Simple idea: Place business logic at the center and connect external systems through ports and adapters.

Use it when

Useful when domain logic must be tested independently and integrations change.

Main risk

Risk: too many interfaces and mapping layers for simple CRUD.

Typical flow

Driving adapter (REST) → Input Port → Domain/Application → Output Port → DB/PSP adapter

Senior interview answer

Hexagonal Architecture protects the core from frameworks. I introduce ports at meaningful boundaries, not one interface for every class.

Architecture

Clean Architecture

Simple idea: Arrange concentric dependency boundaries so source-code dependencies point inward toward business policy.

Use it when

Useful for long-lived systems with important domain rules and multiple delivery/infrastructure mechanisms.

Main risk

Risk: ceremony, duplicated models, and excessive indirection.

Typical flow

Frameworks → Interface Adapters → Use Cases → Entities

Senior interview answer

The key is the dependency rule, not folder names. Inner layers must not depend on outer implementation details.

Architecture

CQRS

Simple idea: Separate write commands from read queries, potentially with different models and stores.

Use it when

Useful when read and write models have very different scaling or complexity.

Main risk

Risk: eventual consistency, duplicated models, operational complexity.

Typical flow

Command → Write Model; Event/Projection → Read Model → Query

Senior interview answer

CQRS does not require Event Sourcing or microservices. I use it only when asymmetric read/write needs justify the extra consistency and operations cost.

Architecture

Event Sourcing

Simple idea: Persist state changes as an append-only sequence of domain events and rebuild current state by replay.

Use it when

Useful for audit-heavy domains, temporal queries, and complex state evolution.

Main risk

Risk: event versioning, replay cost, privacy deletion, and operational complexity.

Typical flow

Events: OrderCreated, ItemAdded, OrderPaid → rebuild Order state

Senior interview answer

Event Sourcing is not just logging. Events become the source of truth, so schema evolution, idempotency, snapshotting, and correction strategy are core design concerns.

Distributed Pattern

Saga

Simple idea: Coordinate a distributed business transaction through local transactions and compensating actions.

Use it when

Useful when one ACID transaction cannot span microservices.

Main risk

Risk: compensation is not true rollback, intermediate states are visible, and workflows are complex.

Typical flow

Reserve inventory → Charge payment → Create shipment; compensate in reverse on failure

Senior interview answer

I explain orchestration versus choreography, idempotency, retry, timeout, compensation, and how the saga state is persisted.

Distributed Pattern

Transactional Outbox

Simple idea: Write business data and an outgoing event in the same local database transaction, then publish asynchronously.

Use it when

Useful to avoid the dual-write problem between database and message broker.

Main risk

Risk: duplicate publication, cleanup, ordering, and relay operations.

Typical flow

DB transaction: save Order + OutboxEvent; relay publishes event later

Senior interview answer

Outbox provides atomic persistence, not exactly-once delivery. Consumers remain idempotent, and the relay needs monitoring and retries.

Resilience Pattern

Circuit Breaker

Simple idea: Stop repeated calls to a failing dependency and periodically test recovery.

Use it when

Useful for remote calls with repeated failure or latency.

Main risk

Risk: wrong thresholds, stale fallback, and hiding failures.

Typical flow

Closed → Open → Half-open → Closed/Open

Senior interview answer

Circuit Breaker protects resources and reduces cascading failure. It is not a retry replacement; retries may increase load, so policies must be combined carefully.

Resilience Pattern

Retry

Simple idea: Repeat transiently failed operations with bounded attempts and backoff.

Use it when

Useful for temporary network errors, throttling, and optimistic conflicts.

Main risk

Risk: retry storms, duplicate side effects, and longer latency.

Typical flow

Retry with exponential backoff + jitter + idempotency

Senior interview answer

I retry only classified transient failures, use backoff and jitter, set a time budget, and ensure side effects are idempotent.

Resilience Pattern

Bulkhead

Simple idea: Isolate resources so one failing workload cannot consume all threads, connections, or capacity.

Use it when

Useful for shared services calling dependencies with different risk profiles.

Main risk

Risk: underutilized pools and configuration complexity.

Typical flow

Separate thread/connection pools for Payment, Email, Reporting

Senior interview answer

Bulkhead limits blast radius. I size pools from traffic and latency, monitor queue saturation, and combine with timeouts and circuit breakers.

Microservice Pattern

API Gateway

Simple idea: Provide one external entry point for routing, authentication, rate limits, and protocol adaptation.

Use it when

Useful for many backend services and multiple clients.

Main risk

Risk: gateway becomes a bottleneck or contains business logic.

Typical flow

Client → Gateway → Order/Payment/User services

Senior interview answer

Gateway centralizes edge concerns, but services still enforce authorization and domain rules. I avoid trusting unsigned user headers blindly.

Migration Pattern

Strangler Fig

Simple idea: Replace a legacy system incrementally by routing selected capabilities to new components.

Use it when

Useful for gradual monolith migration with lower risk.

Main risk

Risk: long-lived hybrid complexity and duplicated data/workflows.

Typical flow

Router sends migrated endpoints to new service; remaining endpoints stay legacy

Senior interview answer

Strangler is a migration strategy, not a goal. I define capability boundaries, observability, data ownership, rollback, and a plan to remove the old path.

Architecture

Backend for Frontend

Simple idea: Create a backend tailored to one frontend's needs and security model.

Use it when

Useful when web, mobile, and partner clients need different aggregation or token handling.

Main risk

Risk: duplicated logic and too many backend variants.

Typical flow

Browser → Web BFF → APIs; Mobile → Mobile BFF → APIs

Senior interview answer

BFF is valuable for browser OAuth because tokens can remain server-side. Shared business logic stays in domain services, not duplicated in each BFF.

DDD Integration

Anti-Corruption Layer

Simple idea: Protect the domain model from an external or legacy model through translation.

Use it when

Useful when integrating a system with different terminology or semantics.

Main risk

Risk: mapping cost and duplicated models.

Typical flow

Legacy CustomerCode/Status → ACL → Domain CustomerId/State

Senior interview answer

An ACL is more than DTO mapping; it translates meaning and prevents an external model from corrupting domain language.

Data Pattern

Cache-Aside

Simple idea: Application reads cache first, loads from source on miss, and updates/invalidates cache explicitly.

Use it when

Useful for read-heavy data with acceptable staleness.

Main risk

Risk: stale data, stampede, invalidation complexity.

Typical flow

Get key → cache miss → DB → put cache → return

Senior interview answer

I discuss TTL, invalidation, cache stampede, negative caching, consistency requirements, and why cache is not the source of truth.

Interview

7. Frequently confused patterns

ComparisonHow to distinguish them
Factory Method vs Abstract FactoryFactory Method creates one product and often delegates creation through a method. Abstract Factory creates a compatible family of related products.
Adapter vs FacadeAdapter changes an incompatible interface into the application's interface. Facade provides a simpler high-level interface to a complex subsystem.
Adapter vs Decorator vs ProxyAdapter changes interface. Decorator keeps interface and adds behavior. Proxy keeps interface and controls access, location, or lifecycle.
Strategy vs StateStrategy is usually selected externally to choose an algorithm. State changes behavior based on internal lifecycle and often transitions itself.
Strategy vs Template MethodStrategy uses composition and can change at runtime. Template Method uses inheritance and fixes the algorithm skeleton.
Observer vs MediatorObserver broadcasts changes to subscribers. Mediator centralizes known collaboration among components.
Repository vs DAORepository is domain/aggregate focused. DAO is data-source or table/query focused.
CQRS vs Event SourcingCQRS separates reads and writes. Event Sourcing stores events as source of truth. They can be used independently.
Saga vs TransactionA local transaction provides atomic rollback in one resource. Saga coordinates local transactions and compensation across services; compensation is not true rollback.
Decorator vs AOPDecorator is explicit object composition. AOP applies cross-cutting behavior through proxies/weaving and is useful for broad concerns such as transactions or security.
Senior interview

8. Interview questions and senior answers

1. How do you choose a design pattern?

I start from the recurring problem, forces, and trade-offs. I do not choose from a pattern list first. I prefer the simplest design and introduce a pattern only when it reduces coupling, clarifies variation, or manages a known failure mode.

2. What is the most common pattern misuse?

Over-engineering: creating interfaces, factories, and layers without real variation. Another misuse is hiding important network or transaction behavior behind transparent abstractions.

3. Why prefer composition over inheritance?

Composition allows behavior to be assembled and replaced without creating rigid class hierarchies. Inheritance is still useful for true substitutable relationships and stable template algorithms.

4. How are SOLID and patterns related?

Patterns are common structures that often apply SOLID principles. Strategy supports Open/Closed and Dependency Inversion; Decorator supports Open/Closed; Adapter protects boundaries. Patterns do not guarantee SOLID automatically.

5. Which patterns does Spring use?

Dependency Injection, Singleton bean scope, Proxy for transactions/security/AOP, Factory patterns in bean creation, Template Method in helper templates, Observer through application events, Front Controller in DispatcherServlet, and Adapter in handler adapters.

6. Which patterns does Hibernate use?

Proxy for lazy loading, Unit of Work through the persistence context, Identity Map within a session, Repository through application abstractions, and Data Mapper internally.

7. How do you prevent a Strategy factory from becoming a large switch?

Register strategies by key through dependency injection, annotations, configuration, or a Map. Keep selection policy separate from strategy implementation.

8. Why can Observer be dangerous in distributed systems?

Delivery can be duplicated, delayed, reordered, or lost without durable messaging. Consumers need idempotency, retry strategy, dead-letter handling, schema compatibility, and observability.

9. When is Singleton not thread-safe?

One instance does not mean safe concurrency. Mutable fields, non-thread-safe collections, and compound read-modify-write operations still need synchronization, immutability, or concurrent structures.

10. How do patterns affect performance?

Most patterns add indirection, allocations, calls, or network boundaries. I optimize based on measurement. Clarity and correct boundaries usually matter more until profiling proves otherwise.

11. How would you explain Proxy self-invocation in Spring?

Transactional or cached behavior is attached to a proxy. A method calling another method on this bypasses the proxy, so advice such as REQUIRES_NEW may not run. Move the method to another bean or use an appropriate alternative.

12. What makes a senior answer different?

A senior answer explains intent, real constraints, trade-offs, failure behavior, operational impact, testing, and when not to use the pattern—not only the textbook definition.

Decision guide

9. Pattern selection checklist

Before introducing a pattern

  • What concrete problem is repeated?
  • Which dimension is expected to change?
  • Can a simple method or class solve it?
  • What coupling does the pattern remove?
  • What new complexity does it add?
  • How will failure, concurrency, and transactions behave?

Code-review questions

  • Is the intent visible from names?
  • Does the abstraction have more than one meaningful implementation?
  • Are dependencies explicit?
  • Are network calls and side effects obvious?
  • Can each component be tested independently?
  • Is the pattern solving today's problem rather than an imagined future?
Final interview statement: I know the textbook patterns, but I use them as vocabulary for design trade-offs. A strong design is not the one with the most patterns. It is the one whose responsibilities, variation points, consistency boundaries, and failure behavior are easiest to understand and change safely.
