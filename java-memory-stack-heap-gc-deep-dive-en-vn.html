01 • Mental model

Start with the correct memory modelBắt đầu bằng mental model chính xác

A Java process consumes much more memory than -Xmx. The operating-system view is approximately:

Process RSS
≈ Java heap
+ Metaspace / compressed class space
+ Code cache
+ Thread stacks
+ Direct / mapped buffers
+ GC native structures
+ JNI and native libraries
+ JVM internal memory

Garbage Collection mainly manages the Java heap. It does not automatically solve native-memory leaks, unlimited thread creation, direct-buffer pressure, or class-loader retention.

Java process sử dụng nhiều memory hơn rất nhiều so với -Xmx. Nhìn từ hệ điều hành, có thể ước lượng:

Process RSS
≈ Java heap
+ Metaspace / compressed class space
+ Code cache
+ Thread stack
+ Direct / mapped buffer
+ Native structure của GC
+ JNI và native library
+ Memory nội bộ của JVM

Garbage Collection chủ yếu quản lý Java heap. GC không tự xử lý native-memory leak, tạo thread không giới hạn, direct-buffer pressure hay class-loader retention.

Senior rule: First identify which memory pool is growing. Do not call every memory problem a “heap leak.”

Quy tắc senior: Trước tiên phải xác định memory pool nào đang tăng. Không được gọi mọi vấn đề memory là “heap leak”.

02 • Java Stack Deep Dive

Java Stack: per-thread execution memoryJava Stack: vùng nhớ thực thi riêng của từng thread

Every platform thread owns a private JVM stack. A new stack frame is created for each method invocation and removed when that method returns or throws an exception. Other threads cannot directly access a thread's stack frames.

The stack is mainly used for execution state, not long-lived object storage.

Mỗi platform thread sở hữu một JVM stack riêng. Mỗi lần gọi method, JVM tạo một stack frame mới; frame bị loại bỏ khi method return hoặc throw exception. Thread khác không thể trực tiếp truy cập stack frame của thread này.

Stack chủ yếu lưu trạng thái thực thi, không phải nơi lưu object lâu dài.

Thread JVM Stack

┌─────────────────────────────────────┐
│ Frame: controller()                 │ ← current frame
│ ├─ Local Variable Table             │
│ ├─ Operand Stack                    │
│ ├─ Constant Pool Reference          │
│ └─ Return / exception information   │
├─────────────────────────────────────┤
│ Frame: service()                    │
├─────────────────────────────────────┤
│ Frame: repository()                 │
├─────────────────────────────────────┤
│ Frame: Thread.run()                 │
└─────────────────────────────────────┘

What exactly exists inside a stack frame?

Local Variable Table

Stores method parameters, local primitives, and local object references.

Nó lưu reference, không lưu toàn bộ object graph.

Operand Stack

Temporary workspace used by JVM bytecode instructions for arithmetic, method calls, field access, and return values.

Dynamic Linking

Connects symbolic references in the class constant pool to runtime methods and fields.

Return State

Contains information needed to return to the caller or propagate an exception.

Bytecode example: local variables and operand stack

int calculate(int a, int b) {
    int sum = a + b;
    return sum * 2;
}
// Simplified bytecode idea
iload_1        // push a onto operand stack
iload_2        // push b
iadd           // pop a and b, push result
istore_3       // store result in local slot 3
iload_3        // push sum
iconst_2       // push 2
imul           // multiply
ireturn        // return integer

References on stack, objects on heap

void createOrder() {
    Order order = new Order();
}
Thread Stack                         Java Heap

Local slot "order" ────────────────► Order object
(reference value)                    header + fields + referenced objects

This is the logical model. HotSpot JIT may eliminate the allocation through escape analysis and scalar replacement, so a physical heap allocation is not guaranteed for every new.

Đây là logical model. HotSpot JIT có thể loại bỏ allocation bằng escape analysis và scalar replacement, nên không phải mọi lệnh new đều chắc chắn tạo object vật lý trên heap.

Stack lifecycle

  1. A thread is created.
  2. The JVM reserves or commits stack memory according to platform/JVM behavior and -Xss.
  3. Each method call pushes a new frame.
  4. Normal return pops the frame.
  5. An exception unwinds frames until a matching handler is found.
  6. When the thread terminates, its stack memory is released.

StackOverflowError

Common causes

  • Infinite recursion.
  • Very deep recursive traversal.
  • Cyclic object graph traversal without visited-state tracking.
  • Large generated call chains.

Correct fixes

  • Fix recursion termination.
  • Convert recursion to an iterative algorithm.
  • Use an explicit queue/stack data structure.
  • Increase -Xss only after understanding the algorithm.
static void recurse() {
    recurse(); // eventually throws StackOverflowError
}

Why too many threads cause native-memory pressure

Thread stacks are outside the Java heap. Creating thousands of platform threads can exhaust native memory or OS thread limits even when heap usage is low.

Thread stack nằm ngoài Java heap. Tạo hàng nghìn platform thread có thể làm cạn native memory hoặc chạm giới hạn thread của OS dù heap vẫn còn nhiều memory.

Approximate stack reservation:
10,000 threads × 1 MiB Xss ≈ 10 GiB address-space reservation

Actual committed memory depends on OS/JVM behavior,
but the capacity risk is still significant.

Stack tuning with -Xss

Smaller -XssLarger -Xss
Supports more threads within the same memory budget. Supports deeper call stacks and recursion.
Higher risk of StackOverflowError. Higher native-memory usage per thread.
Useful after measuring actual call depth. Can reduce maximum thread capacity.

Platform threads vs virtual threads

Platform thread

Maps closely to an OS thread and has a native stack. Large thread counts are expensive.

Virtual thread

Managed by the JVM and can unmount from carrier threads. Its execution stack is represented differently and can be stored in heap-managed stack chunks.

Virtual threads reduce thread-per-request cost, but they do not remove heap pressure, pinning, blocking-library, or resource-limit concerns.

Senior interview questions about Stack

Why are local variables considered thread-safe?

Each thread has its own stack and stack frames, so normal local variables are not shared. However, a local reference may point to a shared heap object, and that object can still require synchronization.

Can an object live on the stack?

At the Java language level, object storage location is not guaranteed. HotSpot normally allocates objects on heap, but the JIT may remove allocations or scalar-replace object fields when the object does not escape.

Why is StackOverflowError not an OutOfMemoryError?

It indicates that a thread exceeded its stack capacity, usually due to excessive call depth. It is a different failure category from exhausting Java heap or another memory pool.

03 • Java Heap Deep Dive

Java Heap: shared object memory managed by GCJava Heap: vùng nhớ object dùng chung và được GC quản lý

The Java heap is the shared runtime area where object and array instances are normally allocated. Garbage collectors trace object reachability, reclaim dead objects, and may relocate live objects.

Heap performance is driven by four numbers: maximum capacity, allocation rate, live-set size, and object lifetime distribution.

Java heap là vùng runtime dùng chung, nơi object và array thường được allocate. Garbage collector trace reachability, reclaim object chết và có thể relocate object còn sống.

Hiệu năng heap phụ thuộc bốn yếu tố chính: maximum capacity, allocation rate, live-set size và phân bố vòng đời object.

Logical generational view

┌──────────────────────── Young Generation ────────────────────────┐
│ Eden / young regions │ Survivor / aging objects                 │
└──────────────────────────────────────────────────────────────────┘
                              │ survive collections
                              ▼
┌───────────────────────── Old Generation ─────────────────────────┐
│ Long-lived objects, caches, sessions, large retained graphs      │
└──────────────────────────────────────────────────────────────────┘

Note: G1 and ZGC use collector-specific region layouts,
not one universal physical Eden/Survivor/Old arrangement.

Why TLAB makes allocation fast

Each thread usually allocates from its own Thread-Local Allocation Buffer. A small object allocation can be only a pointer increment plus object initialization, avoiding a global lock for most allocations.

Mỗi thread thường allocate từ Thread-Local Allocation Buffer riêng. Việc allocate object nhỏ có thể chỉ là tăng con trỏ và initialize object, tránh global lock trong phần lớn trường hợp.

CharacteristicYoungOld

Promotion and object aging

Objects surviving young collections may be copied to survivor space or treated as older. The collector decides when to promote them based on age, survivor capacity, region policy, and current heap conditions.

Do not assume a fixed “15 GCs then promotion” rule for every collector and workload. Tenuring behavior is collector- and policy-dependent.

Không nên mặc định mọi collector đều theo luật “sống qua 15 lần GC thì promote”. Tenuring phụ thuộc collector và policy runtime.

Live set vs allocation rate

High allocation rate, stable live set

Frequent young GC, CPU overhead, latency spikes, but not necessarily a leak.

Growing live set

Post-GC occupancy trends upward. This often indicates retention, cache growth, workload-state growth, or insufficient capacity.

Heap fragmentation

Fragmentation means free memory exists but not in a shape suitable for allocation or evacuation. Compacting/copying collectors reduce fragmentation by moving live objects. Large objects and insufficient free regions can still create allocation pressure.

Fragmentation nghĩa là vẫn còn free memory nhưng không có layout phù hợp để allocate hoặc evacuate. Collector có compaction/copy sẽ giảm fragmentation bằng cách di chuyển object sống. Tuy nhiên large object và thiếu free region vẫn có thể gây allocation pressure.

Large and humongous objects

  • Large arrays, JSON payloads, byte buffers, images, files loaded fully into memory.
  • Can bypass normal small-object allocation paths.
  • In G1, humongous objects occupy one or more contiguous regions.
  • They can increase region pressure and make reclamation less flexible.
// Risk: one large heap allocation
byte[] file = Files.readAllBytes(path);

// Better: bounded streaming
try (InputStream in = Files.newInputStream(path)) {
    in.transferTo(outputStream);
}

Heap leak example: static retention

class SessionRegistry {
    private static final Map<String, Session> SESSIONS =
        new ConcurrentHashMap<>();

    static void register(Session session) {
        SESSIONS.put(session.id(), session);
    }

    // If removal never occurs, every Session remains reachable
    // from a static GC root through the map.
}

Heap dump analysis workflow

  1. Open the dump in Eclipse MAT, JMC, VisualVM, or another trusted analyzer.
  2. Check the class histogram for dominant types.
  3. Inspect dominator tree by retained size.
  4. Choose suspicious instances.
  5. Follow “Path to GC Roots”.
  6. Identify the owner: static field, cache, ThreadLocal, listener, class loader, queue, or framework container.
  7. Confirm business lifecycle and expected cardinality before calling it a leak.

Frequent GC, allocation stalls, promotion pressure, possible OOM. Larger memory footprint, potentially more marking work, bigger dumps, slower leak detection.
Application may spend excessive CPU reclaiming small amounts. May leave insufficient native memory inside the container.
Traffic bursts fail quickly. Can hide an unbounded retention issue for longer.

Senior interview questions about Heap

Is every object created in Eden?

No. Allocation can be optimized away, happen in a TLAB that belongs to a young region, use a shared allocation path, or use collector-specific handling for large objects.

Why is heap usage alone insufficient for diagnosing leaks?

Temporary allocation can drive heap usage high before each GC. The important signal is whether post-GC occupancy and retained object counts grow over time.

What is the difference between shallow size and retained size?

Shallow size is the memory of the object itself. Retained size includes the object graph that would become unreachable if that object were removed.

Can increasing Xmx fix an OOM?

It may solve legitimate capacity shortage, but it does not fix unbounded retention. It can also reduce native headroom inside a container. The root cause must be proven first.

Why can a stable heap still produce bad latency?

High allocation rate, expensive young collections, safepoint delays, CPU throttling, remembered-set scanning, or large-object allocation can affect latency even when post-GC occupancy is stable.

Stack vs Heap: the precise answer

A local variable of reference type normally lives in a stack frame, while the referenced object usually lives in the heap. However, the JIT may optimize allocation through escape analysis and scalar replacement. Therefore “all objects are always physically stored in the heap” is an oversimplification of HotSpot execution.

Biến local kiểu reference thường nằm trong stack frame, còn object được tham chiếu thường nằm ở heap. Tuy nhiên JIT có thể tối ưu bằng escape analysis và scalar replacement. Vì vậy câu “mọi object luôn luôn được lưu vật lý trên heap” là cách giải thích đơn giản hóa.

05 • Object representation

Object memory layoutCấu trúc object trong memory

Mark word

Identity hash, locking state, age bits, collector-specific state.

Class pointer

Connects the object to class metadata. Often compressed.

Fields

Primitive values and object references, possibly reordered for alignment.

Padding

Alignment bytes so object size meets JVM alignment constraints.

Exact object size is JVM-, architecture-, flag-, and field-layout-dependent. Use JOL (Java Object Layout) or a profiler instead of memorizing a universal byte count.

Kích thước object phụ thuộc JVM, kiến trúc CPU, JVM flags và field layout. Hãy dùng JOL hoặc profiler thay vì học thuộc một con số byte áp dụng cho mọi trường hợp.

Shallow size vs retained size

Shallow size

Memory occupied by the object itself, excluding referenced objects.

Ví dụ: bản thân một ArrayList, chưa tính toàn bộ phần tử mà nó giữ.

Retained size

Memory that becomes collectible when this object is no longer reachable.

Đây là metric quan trọng khi tìm object đang “giữ” một object graph lớn.

Common sizing traps

  • ArrayList holds a backing array; capacity can be larger than size.
  • HashMap has a table, node objects, references, and load-factor headroom.
  • String stores content separately from the String object; representation varies by JDK implementation.
  • Boxed numbers create objects and references; primitive arrays are often far more compact.
  • A “small” cache entry can retain a large graph through keys, values, listeners, or class loaders.
06 • Allocation

How object allocation actually happensObject được cấp phát như thế nào

new Order()
   │
   ├─ Fast path: current thread's TLAB
   │      └─ bump pointer → initialize header/fields → return reference
   │
   ├─ TLAB exhausted → request/refill TLAB
   │
   ├─ Large/special object → shared region or collector-specific path
   │
   └─ Insufficient space → GC / allocation stall / OOM

TLAB

Thread-Local Allocation Buffer lets most allocations avoid global contention. Allocation is commonly a pointer bump.

Escape analysis

The JIT checks whether an object escapes a method or thread, enabling optimizations.

Scalar replacement

The JIT may eliminate an allocation and treat object fields as independent values.

Generational hypothesis

Most objects die young. Collectors exploit this by collecting young objects frequently and scanning old objects less often. The exact layout differs: G1 uses regions, while generational ZGC has logical young and old generations.

Phần lớn object “chết sớm”. Collector tận dụng đặc điểm này bằng cách thu gom young object thường xuyên và quét old object ít hơn. Cách tổ chức cụ thể khác nhau: G1 dùng region, còn Generational ZGC chia logical young/old generation.

Object lifecycle

  1. Allocate in TLAB/Eden/young region or a collector-specific area.
  2. Use while reachable through roots or other live objects.
  3. Survive collections and accumulate age / remain in live regions.
  4. Promote or be treated as old when collector policy decides.
  5. Become unreachable after all root paths disappear.
  6. Reclaim or relocate during a later GC cycle.

Why reference counting is insufficient

Two unreachable objects can reference each other and keep non-zero reference counts. Tracing collectors start from roots, so unreachable cycles are collectible.

Hai object không còn được ứng dụng sử dụng vẫn có thể tham chiếu lẫn nhau, làm reference count khác 0. Tracing GC bắt đầu từ root nên vẫn thu gom được cycle không reachable.

11 • G1 internals

Garbage-First (G1) deep dive

Heap divided into equal-sized regions

[Eden][Eden][Free][Old][Survivor][Old][Humongous][Humongous][Free]
   └──── Young collection set ────┘       └─ contiguous regions ─┘

G1 chooses regions with high reclaimable garbage first,
while attempting to meet a pause-time target.

Young GC

Evacuates live objects from Eden and Survivor regions. Application threads pause.

Concurrent marking

Identifies old-region liveness mostly concurrently with the application.

Mixed GC

Collects young regions plus selected old regions with high reclaimable garbage.

Important G1 structures and phases

  • Regions: G1 avoids a single fixed contiguous young/old layout.
  • Collection set (CSet): Regions selected for an evacuation pause.
  • Remembered sets / card table: Track cross-region references so G1 avoids scanning the whole heap.
  • SATB marking: Snapshot-at-the-beginning maintains a logical marking snapshot while the app mutates references.
  • IHOP: Initiating Heap Occupancy Percent influences when concurrent marking starts; HotSpot can adapt it.
  • Humongous objects: Large objects occupy one or more contiguous regions and can increase fragmentation pressure.

12 • Concurrent compacting collectors

ZGC and Shenandoah

Generational ZGC

Designed for very low pause times by performing most marking, relocation, and reference processing concurrently. Generational mode divides objects into young and old generations so profitable young objects can be collected more frequently.

  • Low pause design independent of scanning the whole heap during pauses.
  • Uses barriers and metadata to handle concurrent relocation.
  • Needs heap headroom because allocation continues during concurrent GC.
  • On JDK 21, enable generational mode explicitly.

Shenandoah

A low-pause collector that performs most work concurrently, including compaction/evacuation. It trades CPU cycles and memory overhead for shorter pauses.

  • Good candidate for latency-sensitive services.
  • Check whether your JDK distribution includes and supports it.
  • Benchmark with the exact JDK build and workload.
  • Newer JDK work includes generational Shenandoah evolution.

Low-pause does not mean “free.” Concurrent collectors consume CPU and require allocation headroom. Under CPU throttling or an undersized heap, they can still experience allocation stalls.

Low-pause không có nghĩa là “không tốn chi phí”. Concurrent collector dùng CPU và cần allocation headroom. Khi container bị CPU throttle hoặc heap quá nhỏ, application vẫn có thể gặp allocation stall.

13 • Concurrency semantics

Java Memory Model is not the JVM memory layoutJava Memory Model không phải JVM memory layout

JVM memory areas

Where runtime data is stored: heap, stacks, method area/metaspace implementation, native stacks, code cache, and off-heap memory.

Java Memory Model (JMM)

Rules for visibility, ordering, synchronization, data races, and legal observations between threads.

Three concurrency properties

Atomicity

Whether an operation is observed as indivisible.

Visibility

Whether one thread sees another thread's writes.

Ordering

Which reordering is legal and what execution order is guaranteed.

Happens-before essentials

  • Program order within one thread.
  • Unlock on a monitor happens-before a later lock on the same monitor.
  • A write to a volatile field happens-before a later read of that field.
  • Thread.start() happens-before actions in the started thread.
  • Actions in a thread happen-before another thread successfully returns from join().
  • Safe publication of correctly constructed objects can rely on final-field semantics and synchronization mechanisms.
class ConfigHolder {
    private volatile Config config;

    void reload() {
        config = loadConfig(); // volatile write publishes the new reference
    }

    Config current() {
        return config;         // volatile read sees the published reference
    }
}

volatile provides visibility and ordering for the variable, but does not make compound operations such as count++ atomic.

volatile đảm bảo visibility và ordering cho biến, nhưng không làm cho compound operation như count++ trở thành atomic.

15 • Retention

Common Java memory leaksCác memory leak phổ biến trong Java

Static collections

Global maps/lists retain objects for the lifetime of the class loader.

Unbounded cache

No maximum size, TTL, weight, or eviction under unusual key cardinality.

ThreadLocal

Values remain attached to long-lived pooled threads when not removed.

Listeners

Publisher holds subscriber references after business lifecycle ends.

ClassLoader leak

Old deployment class loaders retained by static fields, threads, drivers, caches.

Off-heap leak

Direct buffers, JNI, Netty, native allocators grow outside Java heap.

ThreadLocal leak pattern

private static final ThreadLocal<RequestContext> CTX = new ThreadLocal<>();

void handle(Request request) {
    try {
        CTX.set(buildContext(request));
        process(request);
    } finally {
        CTX.remove(); // mandatory for pooled threads
    }
}

Leak diagnosis logic

  1. Confirm memory grows across multiple GC cycles.
  2. Check post-GC occupancy, not only temporary peaks.
  3. Take comparable dumps at different times under the same workload.
  4. Compare class counts, shallow sizes, retained sizes, and dominators.
  5. Use “Path to GC Roots” to identify the exact retaining reference.
  6. Fix ownership/lifecycle; do not merely increase -Xmx.

17 • Performance engineering

A disciplined GC tuning methodologyPhương pháp GC tuning có hệ thống

  1. Define SLOs: throughput, p99 latency, max pause, memory limit, startup time.
  2. Capture a baseline: same traffic, data volume, CPU/memory limits, and JDK build.
  3. Identify the bottleneck: capacity, allocation rate, live set, CPU, native memory, or safepoints.
  4. Change one major variable: collector, heap, or one relevant tuning family.
  5. Run long enough: include warmup, traffic bursts, cache growth, and scheduled jobs.
  6. Compare tail distributions: averages hide pauses and rare allocation stalls.

Container memory budgeting

Container limit = 2 GiB

Possible initial budget (workload-dependent):
  Java heap                 1.1–1.3 GiB
  Metaspace + code cache    150–250 MiB
  Direct/native buffers     150–300 MiB
  Thread stacks             threads × Xss
  GC/JVM/native headroom    remaining safety margin

Do not blindly set -Xmx equal to the container limit.

Code examples and anti-patternsVí dụ code và anti-pattern

Unbounded cache leak

class PriceService {
    // BAD: unique product/customer keys can grow forever
    private final Map<String, Price> cache = new ConcurrentHashMap<>();

    Price get(String key) {
        return cache.computeIfAbsent(key, this::load);
    }
}
// Better: use a cache with explicit maximum size, expiration,
// metrics, and a business-appropriate eviction policy.
Cache<String, Price> cache = Caffeine.newBuilder()
    .maximumSize(50_000)
    .expireAfterAccess(Duration.ofMinutes(15))
    .recordStats()
    .build();

Allocation-heavy stream pipeline

// Potentially creates multiple intermediate objects/collections.
List<String> result = orders.stream()
    .map(Order::getItems)
    .flatMap(Collection::stream)
    .filter(Item::isActive)
    .map(Item::getSku)
    .distinct()
    .sorted()
    .toList();

This is not automatically wrong. Profile before rewriting. For very large datasets, consider database-side filtering, streaming/pagination, bounded aggregation, or specialized data structures.

19 • Interview

Senior Java interview questions and answersCâu hỏi phỏng vấn Senior Java và trả lời

1. What is the difference between heap, stack, and metaspace?

Heap is shared and primarily stores objects/arrays. Each thread has its own stack containing frames, local values/references, and operand stacks. Metaspace is native memory used by HotSpot for class metadata. GC primarily reclaims heap objects and can unload class metadata when the corresponding class loader becomes unreachable and class unloading occurs.

Heap được share và chủ yếu chứa object/array. Mỗi thread có stack riêng chứa frame, local value/reference và operand stack. Metaspace là native memory HotSpot dùng cho class metadata. GC chủ yếu reclaim object trên heap và có thể unload class metadata khi class loader tương ứng không còn reachable.

2. Why can a Java process exceed -Xmx?

Because -Xmx limits Java heap, not total process RSS. Metaspace, code cache, thread stacks, direct buffers, GC structures, JNI, and native libraries consume additional memory.

3. What makes an object eligible for GC?

No live path exists from any GC root to the object. A null assignment can remove one path but does not guarantee unreachability or immediate collection.

4. Minor, major, mixed, and full GC?

Terminology is collector-specific. In generational explanations, a young/minor collection targets young objects. G1 mixed collections include young regions and selected old regions. “Full GC” generally means a broad, expensive collection of most/all heap, usually STW, but always interpret the exact collector log.

5. Why does G1 use regions?

Regions let G1 construct collection sets dynamically, prioritize regions with more reclaimable garbage, avoid a fixed contiguous old/young boundary, and incrementally compact by evacuation.

6. What is a remembered set?

Metadata recording references from outside a region/generation into it. It reduces the need to scan the entire heap during a partial collection. Write barriers maintain this information.

7. What is an allocation rate and why does it matter?

Bytes allocated per unit time. A high allocation rate fills young space quickly, increases GC frequency, consumes copying/marking CPU, and may create allocation stalls even when there is no leak.

8. How do you distinguish a leak from high temporary allocation?

A leak normally causes post-GC occupancy/live set to rise over time. Temporary allocation may create high peaks and frequent young GC, but post-GC occupancy returns to a stable baseline.

9. G1 vs ZGC?

G1 is a balanced general-purpose regional collector with STW evacuation pauses and concurrent marking. ZGC performs much more work concurrently and targets very low pauses, especially for large heaps, at the cost of concurrent CPU/memory overhead. Benchmark against SLOs.

10. Why can ZGC still stall?

If allocation outpaces concurrent reclamation, heap headroom is insufficient, or CPU is throttled, application threads can wait for memory. Low-pause does not remove capacity constraints.

11. What is the Java Memory Model?

It defines inter-thread visibility, ordering, synchronization, data-race behavior, and happens-before guarantees. It is not the physical JVM heap/stack layout.

12. Does volatile make count++ thread-safe?

No. count++ is read-modify-write and is not atomic. Use AtomicInteger, LongAdder for suitable counters, or locking.

13. Why is System.gc() discouraged?

It is only a request and can trigger expensive collection behavior depending on flags/collector. Application code should fix lifecycle and sizing rather than using explicit GC as control flow.

14. What causes Metaspace OOM?

Too many loaded/generated classes, class-loader leaks, repeated redeployments, dynamic proxies/bytecode generation, or an intentionally small cap. Inspect class-loader statistics and loaded-class growth.

15. How would you investigate an OOM in Kubernetes?

First determine Java OOME vs cgroup OOMKill/exit 137. Check pod events and memory limit, compare RSS with heap, inspect GC metrics/logs, thread count, direct buffers, NMT, and take JFR/heap dump when operationally safe.

16. Why can too many threads cause OOM with free heap remaining?

Each platform thread reserves/commits native stack memory and consumes OS resources. The process can exhaust native memory or PID/thread limits while Java heap still has free capacity.

17. What is a humongous object in G1?

A collector-defined large object, typically large enough to occupy one or more contiguous regions. Frequent large arrays can create region pressure and fragmentation-like issues. Confirm via G1 heap logs rather than guessing.

18. Why does increasing Xmx sometimes make latency worse?

A larger heap can reduce GC frequency but may increase live-set scan/evacuation work, delay leak detection, enlarge dumps, and exceed container/native budgets. Collector and workload determine the result.

19. Is Xms = Xmx always recommended?

It improves capacity predictability and avoids heap resizing, common for stable server deployments. It is not universally correct for density-sensitive environments; total container memory and startup footprint still matter.

20. What are shallow and retained heap sizes?

Shallow size is the object itself. Retained size is the memory that becomes unreachable if the object is removed. Large retained size often identifies a meaningful dominator/leak owner.

Quick checkpoint

Question: Heap usage repeatedly reaches 90%, drops to 35% after GC, and remains near 35% for weeks. Is this automatically a memory leak?

No. A stable post-GC baseline suggests temporary allocation pressure rather than retained growth. Investigate allocation rate and GC cost, but do not label it a leak without evidence.

Production checklistChecklist production

Before release

  • Set container memory and CPU requests/limits intentionally.
  • Reserve non-heap/native headroom; do not equate limit with Xmx.
  • Enable rotating GC logs.
  • Configure OOM dump path and disk capacity.
