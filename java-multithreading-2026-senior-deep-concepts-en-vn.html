01 • Big picture

Multithreading: the main idea

Multithreading means one process has multiple threads of execution. Threads share the same heap and application resources, but each thread owns its own stack and execution state.

Multithreading nghĩa là một process có nhiều luồng thực thi. Các thread dùng chung heap và resource của application, nhưng mỗi thread có stack và execution state riêng.

Java Process
┌────────────────────────────────────────────┐
│ Shared Heap: objects, services, caches     │
│                                            │
│ Thread A Stack  Thread B Stack  Thread C   │
│ request #1     request #2       scheduler  │
└────────────────────────────────────────────┘

Multithreading

Multiple threads inside one process.

Concurrency

Tasks make progress during overlapping time.

Parallelism

Tasks execute at the same time on different cores.

Asynchrony

Caller does not wait in the same call path.

Concurrency is working together; parallelism is running at the same time; asynchrony is a completion/control-flow model.

Thread

A thread is one path of work inside a Java process.

Một thread là một luồng công việc bên trong Java process.

Use it when / Dùng khi

Use it when one task needs its own flow of execution.

Dùng khi một task cần luồng thực thi riêng.

Be careful / Cẩn thận

Do not create many platform threads by hand for every small request.

Không tự tạo quá nhiều platform thread cho từng request nhỏ.

Concrete example / Ví dụ cụ thể

An HTTP server uses worker threads to handle requests.

HTTP server dùng worker thread để xử lý request.

Runnable

Runnable describes a task that does not return a value.

Runnable mô tả task không trả về giá trị.

Use it when / Dùng khi

Use it for a command or side effect, such as sending a log or clearing a cache.

Dùng cho command hoặc side effect như ghi log hoặc xóa cache.

Be careful / Cẩn thận

Do not use it when the caller needs a result or checked exception.

Không dùng khi caller cần result hoặc checked exception.

Concrete example / Ví dụ cụ thể

executor.execute(() -> cache.clear());

executor.execute(() -> cache.clear());

Callable

Callable describes a task that returns a value and may throw an exception.

Callable mô tả task trả về giá trị và có thể throw exception.

Use it when / Dùng khi

Use it when background work must return data.

Dùng khi background work phải trả dữ liệu.

Be careful / Cẩn thận

Do not call Future.get immediately if you want real async flow.

Không gọi Future.get ngay nếu muốn async thật sự.

Concrete example / Ví dụ cụ thể

Callable task = () -> createInvoice(id);

Callable task = () -> createInvoice(id);

Future

Future is a handle for a task result that may come later.

Future là handle cho result có thể có sau.

Use it when / Dùng khi

Use it to check, wait for, or cancel one task.

Dùng để kiểm tra, chờ hoặc cancel một task.

Be careful / Cẩn thận

It is not good for long chains of dependent tasks.

Không phù hợp cho chuỗi task phụ thuộc dài.

Concrete example / Ví dụ cụ thể

Invoice invoice = future.get(2, SECONDS);

Invoice invoice = future.get(2, SECONDS);

FutureTask

FutureTask is both a Runnable task and a Future result holder.

FutureTask vừa là Runnable task vừa là nơi giữ Future result.

Use it when / Dùng khi

Use it when a Callable must run inside a raw Thread or custom executor.

Dùng khi Callable cần chạy trong raw Thread hoặc custom executor.

Be careful / Cẩn thận

Most business code can use ExecutorService instead.

Phần lớn business code nên dùng ExecutorService.

Concrete example / Ví dụ cụ thể

new Thread(new FutureTask<>(callable)).start();

new Thread(new FutureTask<>(callable)).start();

Concurrency

Concurrency means many tasks make progress in the same time period.

Concurrency nghĩa là nhiều task cùng tiến triển trong một khoảng thời gian.

Use it when / Dùng khi

Use it to serve many users or overlap I/O waiting.

Dùng để phục vụ nhiều user hoặc tận dụng thời gian chờ I/O.

Be careful / Cẩn thận

More concurrency is not always more speed.

Nhiều concurrency hơn không phải lúc nào cũng nhanh hơn.

Concrete example / Ví dụ cụ thể

Many requests wait for DB while other requests run.

Nhiều request chờ DB trong lúc request khác chạy.

Parallelism

Parallelism means tasks really run at the same time on different CPU cores.

Parallelism nghĩa là các task thực sự chạy cùng lúc trên các CPU core khác nhau.

Use it when / Dùng khi

Use it for work that can be safely split into independent CPU parts.

Dùng cho work CPU có thể chia thành các phần độc lập an toàn.

Be careful / Cẩn thận

Do not use it for tiny tasks or highly shared state.

Không dùng cho task quá nhỏ hoặc state chia sẻ quá nhiều.

Concrete example / Ví dụ cụ thể

Split a large image or array calculation across cores.

Chia xử lý image hoặc array lớn trên nhiều core.

Race condition

A race condition happens when the result depends on thread timing.

Race condition xảy ra khi kết quả phụ thuộc vào timing của thread.

Use it when / Dùng khi

Look for it when many threads read and write the same state.

Kiểm tra khi nhiều thread đọc và ghi cùng state.

Be careful / Cẩn thận

Do not try to fix it with sleep.

Không sửa bằng sleep.

Concrete example / Ví dụ cụ thể

Two payment requests both see status=PENDING and both charge.

Hai payment request cùng thấy PENDING và cùng charge.

Thread-safe

Thread-safe code stays correct when many threads use it at the same time.

Code thread-safe vẫn đúng khi nhiều thread dùng cùng lúc.

Use it when / Dùng khi

Use immutability, locks, atomics, confinement, or safe concurrent tools.

Dùng immutability, lock, atomic, confinement hoặc concurrent tool an toàn.

Be careful / Cẩn thận

A thread-safe collection does not make a whole business flow atomic.

Collection thread-safe không làm toàn business flow atomic.

Concrete example / Ví dụ cụ thể

ConcurrentHashMap.compute protects one key update.

ConcurrentHashMap.compute bảo vệ update trên một key.

synchronized

synchronized lets only one thread enter a protected block for the same monitor.

synchronized chỉ cho một thread vào protected block trên cùng monitor.

Use it when / Dùng khi

Use it for a small critical section with shared state.

Dùng cho critical section nhỏ có shared state.

Be careful / Cẩn thận

Do not keep a lock during slow HTTP or database calls.

Không giữ lock trong lúc gọi HTTP hoặc DB chậm.

Concrete example / Ví dụ cụ thể

synchronized(lock) { balance += amount; }

synchronized(lock) { balance += amount; }

volatile

volatile makes writes to one variable visible to other threads.

volatile làm write trên một biến visible cho thread khác.

Use it when / Dùng khi

Use it for a stop flag or an immutable config reference.

Dùng cho stop flag hoặc immutable config reference.

Be careful / Cẩn thận

Do not use it for count++ or multi-field rules.

Không dùng cho count++ hoặc rule gồm nhiều field.

Concrete example / Ví dụ cụ thể

private volatile boolean running = true;

private volatile boolean running = true;

ReentrantLock

Reentrant (the same thread can lock again)Lock is an explicit lock with more control than synchronized.

ReentrantLock là explicit lock có nhiều quyền điều khiển hơn synchronized.

Use it when / Dùng khi

Use it for tryLock, timeout, interruption, fairness, or many Conditions.

Dùng khi cần tryLock, timeout, interrupt, fairness hoặc nhiều Condition.

Be careful / Cẩn thận

Always unlock inside finally.

Luôn unlock trong finally.

Concrete example / Ví dụ cụ thể

if (lock.tryLock(100, MILLISECONDS)) { ... }

if (lock.tryLock(100, MILLISECONDS)) { ... }

ReadWriteLock

ReadWriteLock allows many readers or one writer.

ReadWriteLock cho nhiều reader hoặc một writer.

Use it when / Dùng khi

Use it when reads are long, frequent, and writes are rare.

Dùng khi read dài, nhiều và write hiếm.

Be careful / Cẩn thận

Do not use it for very small getters without measurement.

Không dùng cho getter rất nhỏ nếu chưa đo.

Concrete example / Ví dụ cụ thể

Many threads read a large routing table while one thread updates it.

Nhiều thread đọc routing table lớn trong khi một thread update.

StampedLock

StampedLock supports read, write, and optimistic read modes.

StampedLock hỗ trợ read, write và optimistic read.

Use it when / Dùng khi

Use optimistic read only for short reads that can be checked again.

Chỉ dùng optimistic read cho read ngắn và có thể validate.

Be careful / Cẩn thận

It is not reentrant (the same thread can lock again) and is easier to use incorrectly.

Nó không reentrant và dễ dùng sai hơn.

Concrete example / Ví dụ cụ thể

Read x/y, validate the stamp, then retry with read lock if needed.

Đọc x/y, validate stamp rồi retry bằng read lock nếu cần.

AtomicInteger

AtomicInteger updates one integer safely without a normal lock.

AtomicInteger update một integer an toàn không cần normal lock.

Use it when / Dùng khi

Use it for one exact counter or state change inside one JVM.

Dùng cho một counter hoặc state change chính xác trong một JVM.

Be careful / Cẩn thận

Do not use many atomic values for one rule that must change together.

Không dùng nhiều atomic value cho một rule phải đổi cùng nhau.

Concrete example / Ví dụ cụ thể

counter.incrementAndGet();

counter.incrementAndGet();

CAS

CAS means: change the value only if it is still the expected old value.

CAS nghĩa là chỉ đổi value nếu nó vẫn bằng expected old value.

Use it when / Dùng khi

Used inside atomic classes and many lock-free algorithms.

Được dùng trong atomic class và nhiều lock-free algorithm.

Be careful / Cẩn thận

High many threads fighting for the same resource can cause many retries.

Contention cao có thể gây nhiều retry.

Concrete example / Ví dụ cụ thể

compareAndSet(5, 6)

compareAndSet(5, 6)

LongAdder

LongAdder spreads counter updates across small internal cells.

LongAdder phân tán counter update qua các internal cell.

Use it when / Dùng khi

Use it for high-traffic metrics.

Dùng cho metric có traffic cao.

Be careful / Cẩn thận

Do not use sum() as an exact business value during active updates.

Không dùng sum() như business value chính xác khi đang update.

Concrete example / Ví dụ cụ thể

requestCount.increment();

requestCount.increment();

wait / notify

wait and notify are low-level monitor tools for thread conditions.

wait và notify là low-level monitor tool cho condition giữa thread.

Use it when / Dùng khi

Learn them for Java basics and old code.

Học để hiểu Java core và legacy code.

Be careful / Cẩn thận

For normal backend work, prefer BlockingQueue or other higher-level tools.

Với backend thông thường, ưu tiên BlockingQueue hoặc tool cấp cao.

Concrete example / Ví dụ cụ thể

A consumer waits while a custom queue is empty.

Consumer chờ khi custom queue rỗng.

BlockingQueue

BlockingQueue safely passes work from producers to consumers.

BlockingQueue truyền work an toàn từ producer sang consumer.

Use it when / Dùng khi

Use it for worker queues and backpressure.

Dùng cho worker queue và backpressure.

Be careful / Cẩn thận

Prefer a bounded queue so memory cannot grow forever.

Ưu tiên bounded queue để memory không tăng vô hạn.

Concrete example / Ví dụ cụ thể

new ArrayBlockingQueue<>(500)

new ArrayBlockingQueue<>(500)

ExecutorService

ExecutorService manages task submission, worker threads, and shutdown.

ExecutorService quản lý submit task, worker thread và shutdown.

Use it when / Dùng khi

Use it instead of creating raw platform threads for many tasks.

Dùng thay vì tạo raw platform thread cho nhiều task.

Be careful / Cẩn thận

Do not forget shutdown and monitoring.

Không quên shutdown và monitoring.

Concrete example / Ví dụ cụ thể

executor.submit(callable);

executor.submit(callable);

ThreadPoolExecutor

ThreadPoolExecutor is a configurable worker pool with a queue.

ThreadPoolExecutor là worker pool có thể cấu hình cùng queue.

Use it when / Dùng khi

Use it when pool size, queue limit, and rejection policy must be clear.

Dùng khi cần rõ pool size, queue limit và rejection policy.

Be careful / Cẩn thận

Do not use an unbounded queue without understanding the memory risk.

Không dùng unbounded queue nếu chưa hiểu memory risk.

Concrete example / Ví dụ cụ thể

8 core threads, queue 500, CallerRunsPolicy.

8 core thread, queue 500, CallerRunsPolicy.

CompletableFuture

CompletableFuture connects async steps and handles their results.

CompletableFuture kết nối các async step và xử lý result.

Use it when / Dùng khi

Use it for a limited number of parallel calls, combining results, and async pipelines.

Dùng cho bounded fan-out, combine result và async pipeline.

Be careful / Cẩn thận

Do not block the common pool with slow I/O.

Không block common pool bằng I/O chậm.

Concrete example / Ví dụ cụ thể

loadUser.thenCompose(this::loadOrders)

loadUser.thenCompose(this::loadOrders)

Synchronous

Synchronous means the caller gets the final result in the same call flow.

Synchronous nghĩa là caller nhận final result trong cùng call flow.

Use it when / Dùng khi

Use it when the next step needs the result and simple code is more important.

Dùng khi step sau cần result và code đơn giản quan trọng hơn.

Be careful / Cẩn thận

It may block the caller if the operation is slow.

Nó có thể block caller nếu operation chậm.

Concrete example / Ví dụ cụ thể

PaymentResult result = pay(request);

PaymentResult result = pay(request);

Asynchronous

Asynchronous means the result comes later through a future, callback, or event.

Asynchronous nghĩa là result đến sau qua future, callback hoặc event.

Use it when / Dùng khi

Use it for independent slow work or when services should be separated.

Dùng cho work chậm độc lập hoặc khi service cần tách rời.

Be careful / Cẩn thận

Async does not mean faster and still needs limits.

Async không có nghĩa nhanh hơn và vẫn cần limit.

Concrete example / Ví dụ cụ thể

Return 202 Accepted, then process an export job.

Trả 202 Accepted rồi xử lý export job.

Blocking

Blocking means a thread waits and cannot do other application work.

Blocking nghĩa là thread chờ và không làm application work khác.

Use it when / Dùng khi

Blocking code is simple and works well with a controlled pool or virtual threads.

Blocking code đơn giản và phù hợp với pool có kiểm soát hoặc virtual thread.

Be careful / Cẩn thận

Do not block event-loop threads.

Không block event-loop thread.

Concrete example / Ví dụ cụ thể

JDBC waits for the database response.

JDBC chờ database response.

Non-blocking

Non-blocking means the thread does not wait for unfinished I/O.

Non-blocking nghĩa là thread không chờ I/O chưa hoàn thành.

Use it when / Dùng khi

Use it when the full stack supports non-blocking I/O and very high concurrency is needed.

Dùng khi toàn bộ stack hỗ trợ non-blocking I/O và cần concurrency rất cao.

Be careful / Cẩn thận

One blocking call can hurt a small event-loop.

Một blocking call có thể làm hại event-loop nhỏ.

Concrete example / Ví dụ cụ thể

WebClient with a non-blocking driver.

WebClient cùng non-blocking driver.

Semaphore

Semaphore limits how many tasks may use a resource at the same time.

Semaphore giới hạn bao nhiêu task dùng resource cùng lúc.

Use it when / Dùng khi

Use it for a downstream service, file process, or special resource limit.

Dùng cho downstream service, file process hoặc resource limit.

Be careful / Cẩn thận

A semaphore does not execute tasks like a thread pool.

Semaphore không execute task như thread pool.

Concrete example / Ví dụ cụ thể

Only 20 calls may reach a partner API at once.

Chỉ 20 call được tới partner API cùng lúc.

CountDownLatch

CountDownLatch lets a thread wait until N events finish.

CountDownLatch cho thread chờ đến khi N event hoàn tất.

Use it when / Dùng khi

Use it for one-time startup or completion waiting.

Dùng cho startup một lần hoặc chờ completion.

Be careful / Cẩn thận

It cannot be reset and reused.

Nó không reset để tái sử dụng.

Concrete example / Ví dụ cụ thể

Wait until three services finish loading.

Chờ ba service load xong.

CyclicBarrier

CyclicBarrier makes a fixed group of threads wait for each other.

CyclicBarrier làm một nhóm thread cố định chờ nhau.

Use it when / Dùng khi

Use it for repeated parallel phases.

Dùng cho các parallel phase lặp lại.

Be careful / Cẩn thận

Do not use it when the number of workers changes often.

Không dùng khi số worker thay đổi thường xuyên.

Concrete example / Ví dụ cụ thể

Three calculation workers meet after each round.

Ba calculation worker gặp nhau sau mỗi vòng.

Phaser

Phaser coordinates many phases and allows tasks to join or leave.

Phaser phối hợp nhiều phase và cho task tham gia hoặc rời.

Use it when / Dùng khi

Use it for a dynamic multi-step workflow.

Dùng cho workflow nhiều bước có số task thay đổi.

Be careful / Cẩn thận

It is more complex than CountDownLatch or CyclicBarrier.

Nó phức tạp hơn CountDownLatch hoặc CyclicBarrier.

Concrete example / Ví dụ cụ thể

Import partitions register for validate, transform, and save phases.

Import partition register cho phase validate, transform và save.

ForkJoinPool

ForkJoinPool splits a large CPU task into smaller tasks.

ForkJoinPool chia CPU task lớn thành task nhỏ.

Use it when / Dùng khi

Use it for divide-and-conquer CPU work.

Dùng cho divide-and-conquer CPU work.

Be careful / Cẩn thận

Do not put slow blocking I/O in the common pool.

Không đưa blocking I/O chậm vào common pool.

Concrete example / Ví dụ cụ thể

Parallel sum of a very large array.

Tính tổng parallel cho array rất lớn.

Virtual thread

A virtual thread is a light Java thread made for many blocking I/O tasks.

Virtual thread là Java thread nhẹ cho nhiều blocking I/O task.

Use it when / Dùng khi

Use it when simple blocking code must handle high concurrency.

Dùng khi code blocking đơn giản phải xử lý concurrency cao.

Be careful / Cẩn thận

It does not increase DB connections or make CPU work faster.

Nó không tăng DB connection hoặc làm CPU work nhanh hơn.

Concrete example / Ví dụ cụ thể

One virtual thread handles one request.

Một virtual thread xử lý một request.

Interrupt

Interrupt is a polite request for a thread to stop or change its work.

Interrupt là yêu cầu lịch sự để thread dừng hoặc đổi công việc.

Use it when / Dùng khi

Use it for cancellation and graceful shutdown.

Dùng cho cancellation và graceful shutdown.

Be careful / Cẩn thận

Do not catch InterruptedException and ignore it.

Không catch InterruptedException rồi bỏ qua.

Concrete example / Ví dụ cụ thể

Restore the flag and leave the task.

Restore flag rồi thoát task.

What volatile really guarantees

The problem

One thread may update a variable, but another thread may keep reading an old value because there is no visibility rule between them.

Thread A                         Thread B
--------                         --------
running = false                 while (running) {
                                   doWork();
                                }

Without a visibility rule,
Thread B may keep seeing running = true.
What volatile gives
  • A write to a volatile variable becomes visible to a later read of that same variable.
  • It also creates ordering rules around that access.
  • It does not lock the code.
  • It does not make many-step operations atomic.
Why volatile does not make count++ safe

count++;

count++ is:
1. read count
2. add 1
3. write count

Two threads can read the same old value.
One update is lost.
Use volatile when

The variable is independent, one write does not depend on the old value, and no larger business rule must be protected.

Good examples: stop flag, feature switch, reference to a new immutable configuration.

Senior answer

“volatile gives visibility and ordering for one variable. It does not give mutual exclusion. I use it for flags or immutable snapshots, but not for count++, check-then-act logic, or rules that use many fields.”

Why JMM exists

When fairness matters

What fairness means

A fair ReentrantLock tries to give the lock to the thread that waited longest. A non-fair lock allows a new thread to get the lock first.

Waiting queue:
Thread A → Thread B → Thread C

Fair lock:
A normally gets the lock first.

Non-fair lock:
A new Thread D may get the lock
before A if timing is favorable.
Trade-off

Fair mode can reduce starvation and long wait differences, but it usually lowers throughput. Use it only when wait order is an important requirement.

How ReadWriteLock can improve throughput

Main idea

Many readers may hold the read lock together. A writer needs exclusive access.

Reader A ─┐
Reader B ─┼─ can read together
Reader C ─┘

Writer D ─ waits until all readers leave
and blocks new readers while writing.
Good use case

A large in-memory routing table is read many times and updated rarely. Reads take enough time that parallel readers give a real benefit.

When it can backfire
  • Reads are very short, so lock overhead is bigger than the benefit.
  • Writes are frequent, so readers and writers keep blocking each other.
  • Lock upgrade from read to write is used incorrectly.
  • A simple volatile immutable snapshot would be easier.

How deadlocks happen in production

Thread A:
lock(account1)
call method that needs account2

Thread B:
lock(account2)
call method that needs account1

A waits for B.
B waits for A.
Neither can continue.
Real causes
  • Different lock order in different service methods.
  • Calling external or callback code while holding a lock.
  • Nested locks across cache, account, session, or connection objects.
  • One task waits for another task in the same small thread pool.
How to reduce the risk
  • Use one fixed lock order.
  • Keep lock scope small.
  • Do not call HTTP, DB, or unknown callbacks while holding a lock.
  • Use tryLock with timeout when recovery is possible.
  • Use thread dumps and JFR to find blocked lock chains.

Reentrant (the same thread can lock again)Lock, AQS, fairness, and Conditions

Reentrant (the same thread can lock again)Lock provides monitor-like exclusive locking through an explicit API. It is built on AbstractQueuedSynchronizer (AQS), which manages state and a queue of waiting threads.

ReentrantLock cung cấp exclusive lock tương tự monitor qua explicit API. Nó được xây trên AbstractQueuedSynchronizer (AQS), quản lý state và hàng đợi thread chờ.

Basic usage

private final ReentrantLock lock = new ReentrantLock();

void update() {
    lock.lock();
    try {
        updateSharedState();
    } finally {
        lock.unlock();
    }
}

Conceptual internal model

AQS state = 0 → lock is free
AQS state = 1 → owned once
AQS state = 2 → same owner re-entered twice

Owner: Thread A

Waiting queue:
HEAD ← Thread B ← Thread C ← Thread D

lock() flow

lock()
  ├─ CAS state 0 → 1 succeeds
  │    └─ current thread becomes owner
  ├─ current thread is already owner
  │    └─ increment reentrancy count
  └─ otherwise
       ├─ enqueue in AQS wait queue
       ├─ park thread
       └─ retry when predecessor releases/signals

unlock() flow

unlock()
  ├─ verify current thread owns lock
  ├─ decrement reentrancy count
  ├─ count still > 0 → lock remains owned
  └─ count becomes 0
       ├─ clear owner

Real failure scenarios

Two requests process the same payment

Both read “not completed”, call provider, then update. A Java lock protects only one JVM. Use durable idempotency keys, database transactions, optimistic/pessimistic locking, unique constraints, and provider-side idempotency.

Unbounded executor queue

Tasks arrive faster than workers. Queue wait and memory grow until timeout/OOM. Use bounded queues, rejection, backpressure, and metrics.

Pool larger than DB connection pool

Many workers wait for a few DB connections. Throughput does not rise; latency and memory do.

Blocking common ForkJoinPool

Slow I/O starves unrelated CompletableFuture operations. Use a dedicated executor or virtual threads.

Deadlock through inconsistent lock order

One path locks A then B; another locks B then A. Establish global order or use tryLock/transactional design.

How a senior engineer reasons about concurrency

1. Make a service thread-safe without destroying throughput

Step 1: Find the shared mutable state. Do not lock code that does not share state.

Step 2: Define the exact business rule that must stay true.

Step 3: Reduce shared state with immutable objects or thread-local data.

Step 4: Use a small lock, atomic update, single-writer model, or database transaction for the remaining rule.

Step 5: Measure lock wait, throughput, and tail latency.

Senior candidates do not say “make the method synchronized”. They protect only the state that needs protection.

2. Handle shared mutable state in a high-traffic microservice

First ask whether the state should live inside one JVM at all. With many service instances, local locks do not protect other instances.

  • Use immutable request objects.
  • Use local concurrent structures only for local cache or metrics.
  • Use database constraints and transactions for durable business state.
  • Use Redis, Kafka, or another coordinator only when the design needs distributed state.
  • Add idempotency for retries and duplicate messages.
3. Debug a race condition that only appears in production

Do not add sleep and hope. Collect evidence.

  1. Find the wrong business result and its timeline.
  2. Use request IDs, thread names, state versions, and timestamps.
  3. Check whether two requests read the same old state.
  4. Look for check-then-act code and non-atomic multi-step updates.
  5. Use stress tests, repeated tests, JFR, and multiple thread dumps.
  6. Add database version columns, unique constraints, or idempotency keys where needed.
4. Two requests charge the same payment

A Java synchronized block works only inside one JVM. It does not protect another service instance or a retry after restart.

A strong solution usually includes:

  • Unique idempotency key.
  • Database unique constraint.
  • Atomic state change such as PENDING → PROCESSING.
  • Provider-side idempotency.
  • Retry and reconciliation process.

1. Concurrency vs parallelism?
Easy answer first / Trả lời dễ trước

Direct answer / Trả lời trực tiếp

Concurrency means multiple tasks can make progress during the same time period and therefore need working together. Parallelism means two or more tasks are really running at the same instant, usually on different CPU cores. Concurrency is a software-structure concept; parallelism is an execution-resource concept.

Concurrency nghĩa là nhiều task cùng tiến triển trong các khoảng thời gian chồng lấn và vì vậy cần được phối hợp. Parallelism nghĩa là từ hai task trở lên thực sự chạy cùng một thời điểm, thường trên các CPU core khác nhau. Concurrency là khái niệm về cấu trúc phần mềm; parallelism là khái niệm về tài nguyên thực thi.

How it works inside / Cơ chế bên trong

On a single core, the scheduler can switch between runnable threads, creating concurrency without running at the same time. On multiple cores, runnable threads may truly execute in parallel. The Java Memory Model, locks, atomics, and thread-safe collections are required because concurrent tasks may access shared state regardless of whether the machine happens to run them in parallel.

Trên máy một core, scheduler chuyển qua lại giữa các runnable thread nên vẫn có concurrency nhưng không có thực thi đồng thời thật sự. Trên nhiều core, các runnable thread có thể chạy parallel. Java Memory Model, lock, atomic và concurrent collection vẫn cần thiết vì task concurrent có thể truy cập shared state dù tại một thời điểm chúng có chạy parallel hay không.

Good and bad points / Điểm tốt và hạn chế

Adding threads does not automatically improve throughput. CPU-bound work can slow down through context switching, cache invalidation, lock many threads fighting for the same resource, and too many runnable threads. I/O-bound work can benefit from concurrency because another task can run while one task waits.

Tăng số thread không tự động tăng throughput. Với CPU-bound task, context switching, cache invalidation, lock contention và oversubscription có thể làm chậm hơn. Với I/O-bound task, concurrency hữu ích vì task khác có thể chạy trong lúc một task đang chờ.

Real backend example / Ví dụ backend thực tế

For example, handling 1,000 HTTP requests concurrently does not mean 1,000 requests execute CPU instructions simultaneously. A limited number run on available cores; many others wait for database, network, locks, or scheduling.

Ví dụ service xử lý 1.000 HTTP request cùng lúc không có nghĩa 1.000 request đang chạy CPU instruction đồng thời. Chỉ một số chạy trên các core hiện có; số còn lại chờ database, network, lock hoặc scheduler.

I use concurrency to structure independent work and hide waiting. I use parallelism only when the workload can be split safely and the CPU, memory bandwidth, and downstream systems can support running at the same time.

Tôi dùng concurrency để tổ chức các công việc độc lập và che thời gian chờ. Tôi chỉ dùng parallelism khi workload có thể chia an toàn và CPU, memory bandwidth cùng downstream đủ khả năng xử lý đồng thời.

2. What makes code thread-safe?
Easy answer first / Trả lời dễ trước

Code is thread-safe when concurrent calls preserve its rules that must stay true and visible result without requiring callers to add hidden synchronization. It is not enough that the code does not throw an exception; results must remain correct under every possible thread order.

Code thread-safe khi nhiều lời gọi concurrent vẫn giữ đúng invariant và observable behavior đã cam kết mà caller không phải tự thêm synchronization ẩn. Không phải cứ không ném exception là thread-safe; kết quả phải đúng với mọi interleaving hợp lệ.

Direct answer / Trả lời trực tiếp

Code is thread-safe when concurrent calls preserve its rules that must stay true and visible result without requiring callers to add hidden synchronization. It is not enough that the code does not throw an exception; results must remain correct under every possible thread order.

Code thread-safe khi nhiều lời gọi concurrent vẫn giữ đúng invariant và observable behavior đã cam kết mà caller không phải tự thêm synchronization ẩn. Không phải cứ không ném exception là thread-safe; kết quả phải đúng với mọi interleaving hợp lệ.

How it works inside / Cơ chế bên trong

Thread safety requires controlling shared mutable state. The main strategies are immutability, thread confinement, sharing a ready object safely, one-thread-at-a-time access, atomic state transitions, concurrent data structures, and message passing. The selected strategy must provide the required atomicity, visibility, and ordering guarantees.

Muốn thread-safe phải kiểm soát shared mutable state. Các chiến lược chính gồm immutability, thread confinement, safe publication, mutual exclusion, atomic state transition, concurrent data structure và message passing. Cơ chế được chọn phải cung cấp đủ atomicity, visibility và ordering.

Good and bad points / Điểm tốt và hạn chế

A coarse lock is simple but can reduce throughput. Fine-grained locks improve concurrency but increase complexity and deadlock risk. Lock-free algorithms reduce blocking but are harder to reason about and may retry heavily under many threads fighting for the same resource. Immutability is often simplest but can increase allocation.

Coarse lock đơn giản nhưng có thể giảm throughput. Fine-grained lock tăng concurrency nhưng phức tạp và dễ deadlock hơn. Lock-free tránh blocking nhưng khó chứng minh và có thể retry nhiều khi contention cao. Immutability thường dễ nhất nhưng có thể tăng allocation.

Real backend example / Ví dụ backend thực tế

A ConcurrentHashMap alone does not make a workflow thread-safe if the invariant spans multiple map operations, multiple keys, or a database call. For example, containsKey followed by put is still a race unless replaced by an atomic operation or a larger transaction.

ConcurrentHashMap không làm cả workflow thread-safe nếu invariant trải qua nhiều map operation, nhiều key hoặc có database call. Ví dụ containsKey rồi put vẫn là race trừ khi dùng atomic operation hoặc transaction lớn hơn.

My review question is: what is the invariant, which state participates, who mutates it, and what creates the happens-before relation? I choose the simplest mechanism that protects the complete invariant.

Khi review tôi hỏi: invariant là gì, state nào tham gia, ai được mutate, và cơ chế nào tạo happens-before? Tôi chọn cơ chế đơn giản nhất bảo vệ trọn vẹn invariant.

Easy answer first / Trả lời dễ trước

synchronized provides two guarantees: one-thread-at-a-time access for a monitor and memory visibility across monitor release and subsequent getting the lock. Only one thread can execute a critical section protected by the same monitor at a time.

synchronized cung cấp hai bảo đảm: mutual exclusion trên một monitor và memory visibility giữa lần release monitor với lần acquire sau đó. Chỉ một thread được chạy critical section dùng cùng monitor tại một thời điểm.

Direct answer / Trả lời trực tiếp

synchronized provides two guarantees: one-thread-at-a-time access for a monitor and memory visibility across monitor release and subsequent getting the lock. Only one thread can execute a critical section protected by the same monitor at a time.

synchronized cung cấp hai bảo đảm: mutual exclusion trên một monitor và memory visibility giữa lần release monitor với lần acquire sau đó. Chỉ một thread được chạy critical section dùng cùng monitor tại một thời điểm.

How it works inside / Cơ chế bên trong

An instance synchronized method locks the current object; a static synchronized method locks the Class object; a synchronized block locks the specified reference. The JVM uses monitor-enter/monitor-exit semantics. A thread that cannot acquire the monitor enters BLOCKED state. The monitor is reentrant (the same thread can lock again), so the owner can acquire it again and an internal hold count is increased.

Instance synchronized method lock object hiện tại; static synchronized method lock Class object; synchronized block lock reference được chỉ định. JVM áp dụng monitor-enter/monitor-exit semantics. Thread không acquire được monitor chuyển sang BLOCKED. Monitor là reentrant nên owner có thể acquire lại và hold count được tăng.

Good and bad points / Điểm tốt và hạn chế

It is limited to the code block and automatically released, which makes it safer than manual locking. However, it does not offer timed getting the lock, tryLock, multiple condition queues, or interruptible monitor getting the lock. Many threads fighting for the same resource can create queueing and latency even if average throughput looks acceptable.

Nó có lexical scope và tự release nên an toàn hơn manual lock. Tuy nhiên không có timed acquisition, tryLock, nhiều condition queue hoặc interruptible monitor acquisition. Contention có thể tạo queueing và latency dù throughput trung bình vẫn có vẻ tốt.

Real backend example / Ví dụ backend thực tế

The critical section should contain only state that must be atomic. Remote calls, database queries, callbacks, logging with slow appenders, or waiting on another future should normally not occur while holding the monitor.

Critical section chỉ nên chứa state thực sự cần atomic. Remote call, database query, callback, logging chậm hoặc chờ future khác thường không nên thực hiện trong lúc giữ monitor.

Senior decision / Quyết định senior

Tôi dùng synchronized làm lựa chọn mặc định cho critical section nhỏ và rõ ràng. Tôi kiểm tra mọi read/write thuộc cùng invariant đều dùng đúng một monitor.

4. synchronized vs Lock?
Easy answer first / Trả lời dễ trước

Both can provide one-thread-at-a-time access and happens-before guarantees. synchronized is language-level, automatically released, and usually easier to audit.

Cả hai đều có thể cung cấp mutual exclusion và happens-before. synchronized là language-level, tự release và thường dễ audit hơn.

Direct answer / Trả lời trực tiếp

Both can provide one-thread-at-a-time access and happens-before guarantees. synchronized is language-level, automatically released, and usually easier to audit. Lock is an explicit API that provides advanced getting the lock and working together features.

Cả hai đều có thể cung cấp mutual exclusion và happens-before. synchronized là language-level, tự release và thường dễ audit hơn. Lock là explicit API cung cấp các khả năng acquire và coordination nâng cao.

How it works inside / Cơ chế bên trong

Reentrant (the same thread can lock again)Lock is commonly implemented on AbstractQueuedSynchronizer. It tracks ownership and state, queues threads waiting for the same lock, parks them, and unparks successors. Lock supports tryLock, timed lock, lockInterruptibly, fairness, and multiple Condition objects. synchronized uses the JVM monitor associated with an object.

ReentrantLock thường được xây trên AbstractQueuedSynchronizer. Nó theo dõi owner và state, xếp hàng thread contention, park và unpark successor. Lock hỗ trợ tryLock, timed lock, lockInterruptibly, fairness và nhiều Condition. synchronized dùng JVM monitor gắn với object.

Good and bad points / Điểm tốt và hạn chế

The explicit API is more flexible but introduces a correctness obligation: unlock must be called in finally. Fair locks can reduce starvation but normally reduce throughput. In modern JVMs, synchronized is highly optimized, so Reentrant (the same thread can lock again)Lock should not be selected merely because of an assumption that it is always faster.

Explicit API linh hoạt hơn nhưng tạo thêm nghĩa vụ correctness: luôn unlock trong finally. Fair lock giảm nguy cơ starvation nhưng thường giảm throughput. JVM hiện đại tối ưu synchronized rất tốt nên không chọn ReentrantLock chỉ vì nghĩ nó luôn nhanh hơn.

I choose Lock when a request must fail fast if a lock cannot be obtained, when cancellation must interrupt lock waiting, or when separate notEmpty and notFull condition queues are useful. Otherwise synchronized usually produces clearer code.

The decision is feature-driven, not performance folklore: synchronized for simple structured locking; Lock for advanced getting the lock or condition management.

5. volatile vs synchronized?
Easy answer first / Trả lời dễ trước

volatile guarantees visibility and execution order for accesses to one variable, but it does not provide one-thread-at-a-time access. synchronized provides visibility, ordering, and exclusive execution of a critical section.

volatile bảo đảm visibility và ordering cho việc truy cập một biến nhưng không có mutual exclusion. synchronized cung cấp visibility, ordering và exclusive execution cho critical section.

Direct answer / Trả lời trực tiếp

volatile guarantees visibility and execution order for accesses to one variable, but it does not provide one-thread-at-a-time access. synchronized provides visibility, ordering, and exclusive execution of a critical section.

volatile bảo đảm visibility và ordering cho việc truy cập một biến nhưng không có mutual exclusion. synchronized cung cấp visibility, ordering và exclusive execution cho critical section.

How it works inside / Cơ chế bên trong

A volatile write happens-before a later volatile read of the same variable. The JVM and CPU must respect the required memory visibility rules around that access. But an expression such as count++ still consists of read, compute, and write, so multiple threads can lose updates. synchronized groups multiple actions into one protected critical section.

Một volatile write happens-before volatile read sau đó trên cùng biến. JVM và CPU phải tuân theo memory-ordering effect cần thiết. Nhưng count++ vẫn gồm read, compute và write nên nhiều thread có thể lost update. synchronized nhóm nhiều action thành một protected critical section.

Good and bad points / Điểm tốt và hạn chế

volatile is lightweight and excellent for independent state such as a shutdown flag or immutable configuration reference. It is insufficient for invariants involving multiple variables, check-then-act logic, or updates based on the old value. synchronized may block, but it makes compound state transitions easier to reason about.

volatile nhẹ và phù hợp cho independent state như shutdown flag hoặc immutable configuration reference. Nó không đủ cho invariant gồm nhiều biến, check-then-act hoặc update phụ thuộc old value. synchronized có thể block nhưng giúp reasoning compound state transition dễ hơn.

Real backend example / Ví dụ backend thực tế

Publishing a fully built immutable configuration through a volatile reference is appropriate. Updating account balance and transaction count together requires a lock or another atomic domain design.

Publish immutable configuration đã build hoàn chỉnh qua volatile reference là phù hợp. Update account balance và transaction count cùng nhau cần lock hoặc domain design atomic khác.

Senior decision / Quyết định senior

I use volatile for visibility of independent state; I use locking or atomics when the operation itself must be atomic.

Tôi dùng volatile cho visibility của independent state; dùng lock hoặc atomic khi chính operation phải atomic.

Easy answer first / Trả lời dễ trước

count++ không phải một atomic operation. Nó là chuỗi read-modify-write nên hai thread có thể đọc cùng giá trị và một update ghi đè update còn lại.

Direct answer / Trả lời trực tiếp

count++ is not one atomic operation. It is a read-modify-write sequence, so two threads can read the same value and one update can overwrite the other.

count++ không phải một atomic operation. Nó là chuỗi read-modify-write nên hai thread có thể đọc cùng giá trị và một update ghi đè update còn lại.

How it works inside / Cơ chế bên trong

Conceptually the execution is load count, add one, store count. The scheduler may interleave threads between any of these actions. volatile would make reads and writes visible but would not combine the three actions atomically.

Với request metric, LongAdder có thể rất phù hợp. Với invoice number tuần tự tuyệt đối, local atomic counter vẫn chưa đủ vì restart và nhiều service instance đòi hỏi database sequence hoặc distributed allocation.

The correct fix depends on the business scope, not only the Java statement: atomic for one-process one-value updates, lock for compound state, durable coordinator for distributed identity.

Cách sửa phụ thuộc phạm vi business chứ không chỉ câu lệnh Java: atomic cho update một giá trị trong một process, lock cho compound state, durable coordinator cho distributed identity.

7. What is happens-before?
Easy answer first / Trả lời dễ trước

Happens-before is a Java Memory Model ordering relation. If action A happens-before action B, B is guaranteed to observe the effects of A that are relevant through that synchronization relation.

Happens-before là quan hệ ordering trong Java Memory Model. Nếu action A happens-before action B, B được bảo đảm nhìn thấy effect của A liên quan qua synchronization relation đó.

Direct answer / Trả lời trực tiếp

Happens-before is a Java Memory Model ordering relation. If action A happens-before action B, B is guaranteed to observe the effects of A that are relevant through that synchronization relation.

Happens-before là quan hệ ordering trong Java Memory Model. Nếu action A happens-before action B, B được bảo đảm nhìn thấy effect của A liên quan qua synchronization relation đó.

How it works inside / Cơ chế bên trong

Important rules include monitor unlock before a later lock on the same monitor, volatile write before a later read of the same variable, actions before Thread.start before actions in the new thread, and all actions in a thread before another thread successfully returns from join. Happens-before is works through a chain.

Các rule quan trọng gồm monitor unlock trước lần lock sau trên cùng monitor, volatile write trước volatile read sau trên cùng biến, action trước Thread.start trước action trong thread mới, và mọi action trong thread trước khi thread khác join thành công. Happens-before có tính bắc cầu.

Good and bad points / Điểm tốt và hạn chế

It does not mean wall-clock time alone is enough. Thread A may execute a write before Thread B physically performs a read, yet without synchronization B is not guaranteed to observe it. Conversely, adding the correct synchronization provides visibility without needing unknown or uncontrolled sleep calls.

Nó không có nghĩa chỉ cần thứ tự thời gian thực là đủ. Thread A có thể write trước khi Thread B read về mặt thời gian, nhưng không có synchronization thì B không được bảo đảm nhìn thấy. Ngược lại, synchronization đúng cung cấp visibility mà không cần sleep tùy ý.

Real backend example / Ví dụ backend thực tế

Sharing a ready object safely depends on happens-before. For example, construct an immutable object completely, then publish its reference through a volatile field, synchronized block, concurrent collection, static initialization, or another defined safe-publication mechanism.

Safe publication dựa trên happens-before. Ví dụ build immutable object hoàn chỉnh rồi publish reference qua volatile field, synchronized block, concurrent collection, static initialization hoặc cơ chế safe publication được định nghĩa.

Senior decision / Quyết định senior

When reviewing concurrency code, I do not ask only whether an assignment occurs first. I ask what clear synchronization rule makes its effects visible to the reader.

Khi review concurrent code, tôi không chỉ hỏi assignment nào xảy ra trước. Tôi hỏi synchronization edge chính thức nào làm effect visible cho reader.

8. wait vs sleep?
Easy answer first / Trả lời dễ trước

sleep pauses the current thread for a duration and does not release monitors it owns. wait is a condition-working together method on an object monitor; it must be called while owning that monitor and releases the monitor while waiting.

sleep tạm dừng current thread trong một khoảng thời gian và không release monitor đang giữ. wait là method phối hợp condition trên object monitor; phải gọi khi đang sở hữu monitor và sẽ release monitor trong lúc chờ.

Direct answer / Trả lời trực tiếp

sleep pauses the current thread for a duration and does not release monitors it owns. wait is a condition-working together method on an object monitor; it must be called while owning that monitor and releases the monitor while waiting.

sleep tạm dừng current thread trong một khoảng thời gian và không release monitor đang giữ. wait là method phối hợp condition trên object monitor; phải gọi khi đang sở hữu monitor và sẽ release monitor trong lúc chờ.

How it works inside / Cơ chế bên trong

A waiting thread enters WAITING or TIMED_WAITING and joins the monitor's wait set. After notification, timeout, or interruption, it must compete to reacquire the monitor before wait returns. sleep simply makes the thread temporarily non-runnable; after the timeout it becomes eligible to run again.

Waiting thread vào WAITING hoặc TIMED_WAITING và tham gia wait set của monitor. Sau notify, timeout hoặc interrupt, nó phải cạnh tranh acquire lại monitor trước khi wait trả về. sleep chỉ làm thread tạm thời không runnable; hết thời gian thì có thể được schedule lại.

Good and bad points / Điểm tốt và hạn chế

sleep is appropriate for delay or backoff, although scheduled executors are often better. wait is low-level condition working together and is easy to misuse. The condition must always be checked in a while loop because of a thread may wake without the expected signal and competition from other threads.

sleep phù hợp cho delay hoặc backoff, dù scheduled executor thường tốt hơn. wait là low-level coordination và dễ dùng sai. Condition luôn phải kiểm tra trong while vì spurious wakeup và vì thread khác có thể lấy resource trước.

Real backend example / Ví dụ backend thực tế

Do not use sleep to 'wait until another thread finishes' or to fix a race. Use join, Future, CountDownLatch, BlockingQueue, or another tool with explicit semantics.

Không dùng sleep để 'chờ thread khác hoàn thành' hoặc sửa race condition. Hãy dùng join, Future, CountDownLatch, BlockingQueue hoặc tool có semantics rõ ràng.

Senior decision / Quyết định senior

sleep is time-based pausing; wait is monitor-based condition waiting that releases the lock.

sleep là pause theo thời gian; wait là chờ condition theo monitor và release lock.

9. notify vs notifyAll?
Easy answer first / Trả lời dễ trước

notify wakes one unknown or uncontrolled thread from the monitor's wait set. notifyAll wakes all waiting threads; each awakened thread must later reacquire the monitor and recheck its condition.

notify đánh thức một thread bất kỳ trong wait set của monitor. notifyAll đánh thức toàn bộ thread đang chờ; mỗi thread sau đó phải acquire lại monitor và kiểm tra lại condition.

Direct answer / Trả lời trực tiếp

notify wakes one unknown or uncontrolled thread from the monitor's wait set. notifyAll wakes all waiting threads; each awakened thread must later reacquire the monitor and recheck its condition.

notify đánh thức một thread bất kỳ trong wait set của monitor. notifyAll đánh thức toàn bộ thread đang chờ; mỗi thread sau đó phải acquire lại monitor và kiểm tra lại condition.

How it works inside / Cơ chế bên trong

Notification does not transfer the lock immediately. The notifying thread continues until it exits the synchronized section. A notified waiter only becomes eligible to compete for the monitor. With multiple logical predicates sharing one wait set, notify may wake a thread whose condition is still false.

Notification không chuyển lock ngay. Thread gọi notify tiếp tục cho đến khi rời synchronized section. Waiter được notify chỉ trở thành eligible để cạnh tranh monitor. Nếu nhiều predicate logic dùng chung wait set, notify có thể đánh thức thread mà condition vẫn false.

Good and bad points / Điểm tốt và hạn chế

notify may reduce unnecessary wakeups but is difficult to prove correct. notifyAll can cause a many threads waking at once, yet it is normally safer in general-purpose monitor code because all waiters re-evaluate their predicates.

notify có thể giảm wakeup thừa nhưng khó chứng minh correctness. notifyAll có thể gây thundering herd nhưng thường an toàn hơn trong monitor code tổng quát vì mọi waiter tự kiểm tra lại predicate.

For a hand-written bounded queue with producer and consumer conditions, a single wait set is awkward. Reentrant (the same thread can lock again)Lock with separate notEmpty and notFull Conditions, or a standard BlockingQueue, is clearer and safer.

Với bounded queue tự viết có condition producer và consumer, một wait set duy nhất rất khó quản lý. ReentrantLock với Condition notEmpty/notFull riêng hoặc BlockingQueue chuẩn sẽ rõ và an toàn hơn.

Senior decision / Quyết định senior

I default to notifyAll unless I can formally prove that exactly one same type waiter is sufficient. In application code I prefer higher-level synchronizers.

Tôi mặc định dùng notifyAll trừ khi chứng minh được chỉ một nhóm waiter đồng nhất cần thức dậy. Trong application code tôi ưu tiên synchronizer cấp cao.

10. How do you prevent deadlock?
Easy answer first / Trả lời dễ trước

Deadlock occurs when threads form a cycle of waiting for resources that will never be released. Prevention starts by removing circular wait or making lock getting the lock bounded and recoverable.

Deadlock xảy ra khi các thread tạo thành vòng chờ resource không bao giờ được release. Phòng tránh bắt đầu bằng loại bỏ circular wait hoặc làm lock acquisition có giới hạn và có khả năng recovery.

Direct answer / Trả lời trực tiếp

Deadlock xảy ra khi các thread tạo thành vòng chờ resource không bao giờ được release. Phòng tránh bắt đầu bằng loại bỏ circular wait hoặc làm lock acquisition có giới hạn và có khả năng recovery.

How it works inside / Cơ chế bên trong

The classic conditions are one-thread-at-a-time access, hold-and-wait, no preemption, and circular wait. In Java, the most practical prevention technique is a globally consistent lock order. Other options include tryLock with timeout, reducing nested locks, copying state before callbacks, and designing single-writer or message-passing flows.

Bốn điều kiện kinh điển là mutual exclusion, hold-and-wait, no preemption và circular wait. Trong Java, cách thực tế nhất là global lock ordering nhất quán. Các lựa chọn khác gồm tryLock có timeout, giảm nested lock, copy state trước callback và thiết kế single-writer/message-passing.

Good and bad points / Điểm tốt và hạn chế

tryLock avoids permanent waiting but introduces retry, rollback, and fairness decisions. One global lock removes deadlock risk but reduces concurrency. Fine-grained locks improve parallelism but multiply ordering complexity.

tryLock tránh chờ vô hạn nhưng tạo quyết định retry, rollback và fairness. Một global lock loại bỏ nhiều nguy cơ deadlock nhưng giảm concurrency. Fine-grained lock tăng parallelism nhưng làm ordering phức tạp hơn.

Với account transfer, luôn lock account theo thứ tự xác định như account ID tăng dần. Không gọi plugin, HTTP service hoặc callback người dùng trong lúc giữ internal lock vì code bên ngoài có thể acquire lock theo thứ tự không biết trước.

Senior decision / Quyết định senior

I prevent deadlocks by design rather than detecting them after deployment: documented lock hierarchy, minimal lock scope, no external calls under lock, and timeout where recovery is possible.

Tôi phòng deadlock bằng design thay vì chờ production phát hiện: lock hierarchy được document, lock scope nhỏ, không external call dưới lock và timeout khi có thể recovery.

Queue lớn giảm rejection nhưng che overload thành latency và memory retention. Maximum pool lớn có thể làm quá tải database hoặc downstream. CallerRunsPolicy tạo backpressure cho submitter nhưng có thể bất ngờ chạy task trên request thread hoặc event-loop.

I configure pool size, bounded queue, task timeout, rejection policy, thread names, metrics, and graceful shutdown together. I also align the pool with database connections and downstream concurrency limits.

Tôi cấu hình pool size, bounded queue, task timeout, rejection policy, thread name, metrics và graceful shutdown cùng nhau. Tôi cũng căn pool theo DB connection và downstream concurrency limit.

A thread pool is an overload-control system, not only a thread-reuse optimization.

14. thenApply vs thenCompose?

A fair Reentrant (the same thread can lock again)Lock generally grants access to the longest-waiting queued thread. A non-fair lock allows barging, where a newly arriving thread may acquire the free lock before queued waiters.

Fair ReentrantLock thường cấp lock cho thread đã chờ lâu nhất trong queue. Non-fair lock cho barging, tức thread mới đến có thể lấy free lock trước waiter đã queue.

Direct answer / Trả lời trực tiếp

A fair Reentrant (the same thread can lock again)Lock generally grants access to the longest-waiting queued thread. A non-fair lock allows barging, where a newly arriving thread may acquire the free lock before queued waiters.

Fair ReentrantLock thường cấp lock cho thread đã chờ lâu nhất trong queue. Non-fair lock cho barging, tức thread mới đến có thể lấy free lock trước waiter đã queue.

How it works inside / Cơ chế bên trong

In non-fair mode, a thread first attempts an immediate CAS getting the lock. In fair mode, getting the lock considers whether queued predecessors exist. Fairness applies to the queued getting the lock policy, not to operating-system scheduling or untimed tryLock behavior in every case.

Ở non-fair mode, thread thử immediate CAS trước. Fair mode xem có queued predecessor hay không. Fairness áp dụng cho queued acquisition policy, không kiểm soát toàn bộ OS scheduling hoặc mọi hành vi untimed tryLock.

Good and bad points / Điểm tốt và hạn chế

Fairness reduces difference between fast and slow waits and starvation risk but increases working together overhead and lowers throughput because the lock cannot exploit a running thread that is already on CPU as aggressively. Non-fair mode is normally preferred.

Fairness giảm variance và starvation risk nhưng tăng coordination overhead và giảm throughput vì lock khó tận dụng thread đang chạy trên CPU. Non-fair thường được ưu tiên.

Real backend example / Ví dụ backend thực tế

Use fairness only when long wait difference between fast and slow waits is a correctness or important SLO requirement, such as a controlled resource allocator. Do not enable it merely because it sounds more equitable.

Chỉ dùng fairness khi long wait variance là correctness/SLO concern, ví dụ resource allocator có kiểm soát. Không bật chỉ vì nghe có vẻ công bằng hơn.

Senior decision / Quyết định senior

Fair is a latency-distribution policy with a throughput cost; non-fair is the default performance policy.

Fair là latency-distribution policy có throughput cost; non-fair là performance policy mặc định.

26. When is ReadWriteLock useful?
Easy answer first / Trả lời dễ trước

ReadWriteLock is useful when many threads read the same state, writes are relatively infrequent, reads are long enough to benefit from concurrency, and a consistent snapshot can be protected by a shared read lock.

ReadWriteLock is useful when many threads read the same state, writes are relatively infrequent, reads are long enough to benefit from concurrency, and a consistent snapshot can be protected by a shared read lock.

ReadWriteLock hữu ích khi nhiều thread đọc cùng state, write tương đối hiếm, read đủ dài để hưởng lợi từ concurrency và consistent snapshot cần được bảo vệ bằng shared read lock.

Multiple readers may hold the read lock simultaneously. The write lock is exclusive against readers and writers. Reentrant (the same thread can lock again)ReadWriteLock maintains counts for read and write ownership and can use fair or non-fair policy.

In-memory routing table lớn với read consistent đắt và update hiếm có thể phù hợp. Getter đọc một immutable snapshot qua volatile thường tốt hơn bằng atomic reference replacement.

I benchmark against synchronized and immutable-snapshot publication; read/write locking is not automatically faster for read-heavy code.

An optimistic read obtains a stamp without blocking writers, reads the fields, and then validates that no conflicting write occurred. If validation fails, the code retries under a real read lock.

Optimistic stamp đại diện version của lock state. Nó không ngăn mutation nên field có thể được đọc trong lúc writer đang thay đổi. Phải copy value vào local rồi validate trước khi dùng combined result. StampedLock không reentrant.

Nó có thể nhanh cho read rất ngắn và write hiếm nhưng correctness tinh tế. Đọc reference tới mutable object, computation dài trước validation hoặc quên validation có thể thấy inconsistent state. Nó không hỗ trợ Condition.

Có thể dùng cho coordinate hoặc numeric state nơi copy vài primitive rẻ. Thường không phù hợp traverse mutable object graph lớn.

Optimistic read là measured optimization nâng cao, không phải default replacement cho ReadWriteLock.

28. Semaphore vs thread pool?
Easy answer first / Trả lời dễ trước

A thread pool owns workers and schedules tasks. A Semaphore owns permits and limits how many callers may enter a protected operation.

Thread pool sở hữu worker và schedule task. Semaphore sở hữu permit và giới hạn bao nhiêu caller được vào protected operation.

Direct answer / Trả lời trực tiếp

A thread pool owns workers and schedules tasks. A Semaphore owns permits and limits how many callers may enter a protected operation. It does not create threads or queue executable work by itself.

Thread pool sở hữu worker và schedule task. Semaphore sở hữu permit và giới hạn bao nhiêu caller được vào protected operation. Nó không tự tạo thread hay queue executable work.

How it works inside / Cơ chế bên trong

Semaphore acquire decrements available permits or waits; release increments permits and wakes eligible waiters. A pool uses workers plus a work queue and rejection policy. The two can be combined: many virtual threads may run, while a Semaphore limits concurrent calls to a scarce dependency.

Semaphore acquire giảm permit hoặc chờ; release tăng permit và đánh thức waiter phù hợp. Pool dùng worker cùng work queue và rejection policy. Có thể kết hợp: nhiều virtual thread chạy nhưng Semaphore giới hạn call concurrent tới scarce dependency.

Good and bad points / Điểm tốt và hạn chế

Using a small pool as a concurrency limit also constrains where tasks execute and can cause starvation if tasks block each other. Semaphore expresses resource capacity more directly, but callers still consume their own thread or virtual thread while waiting unless using tryAcquire/timeouts.

Dùng pool nhỏ làm concurrency limit cũng ràng buộc nơi task chạy và có thể starvation nếu task block lẫn nhau. Semaphore biểu diễn resource capacity trực tiếp hơn, nhưng caller vẫn giữ thread/virtual thread trong lúc chờ trừ khi tryAcquire/timeout.

Real backend example / Ví dụ backend thực tế

With virtual threads, use a semaphore of 20 around a downstream service that allows 20 concurrent requests, while still permitting many unrelated tasks to run.

Với virtual thread, dùng semaphore 20 quanh downstream chỉ cho 20 concurrent request, trong khi task không liên quan vẫn chạy.

Senior decision / Quyết định senior

Pool controls execution resources; Semaphore controls admission to a limited resource.

Pool kiểm soát execution resource; Semaphore kiểm soát admission tới limited resource.

29. CountDownLatch vs CyclicBarrier?
Easy answer first / Trả lời dễ trước

CountDownLatch is a used one time gate that opens after a count of events reaches zero. CyclicBarrier is a reusable meeting point where a fixed number of participating threads wait for one another.

CountDownLatch là one-shot gate mở khi count event về 0. CyclicBarrier là reusable meeting point nơi số lượng thread cố định chờ nhau.

Direct answer / Trả lời trực tiếp

CountDownLatch is a used one time gate that opens after a count of events reaches zero. CyclicBarrier is a reusable meeting point where a fixed number of participating threads wait for one another.

CountDownLatch là one-shot gate mở khi count event về 0. CyclicBarrier là reusable meeting point nơi số lượng thread cố định chờ nhau.

How it works inside / Cơ chế bên trong

Latch awaiters do not have to be the threads that decrement the count; countDown does not block. A barrier counts arriving parties, optionally runs a barrier action when the last party arrives, then releases the group and can be used again.

Thread await latch không cần là thread countDown; countDown không block. Barrier đếm party đến, có thể chạy barrier action khi party cuối đến, rồi release nhóm và tái sử dụng.

Latch đơn giản cho startup hoặc chờ N completion độc lập. Barrier tốt cho parallel algorithm lặp, nơi mọi worker phải xong phase một trước khi ai bắt đầu phase hai. Barrier timeout/failure có thể broken và mọi party phải xử lý.

Real backend example / Ví dụ backend thực tế

Use CountDownLatch to wait for three caches to warm before accepting traffic. Use CyclicBarrier for a fixed simulation in which all workers exchange phase results repeatedly.

Dùng CountDownLatch chờ ba cache warm trước nhận traffic. Dùng CyclicBarrier cho simulation cố định nơi worker trao đổi result qua nhiều phase.

Senior decision / Quyết định senior

Latch coordinates events; barrier coordinates participating threads at a phase boundary.

Latch phối hợp event; barrier phối hợp participating thread tại phase boundary.

31. How does ForkJoinPool work?
Easy answer first / Trả lời dễ trước

ForkJoinPool is a work-stealing executor optimized for many small divide-and-conquer tasks, especially CPU-bound computations. Each worker has a deque; idle workers steal tasks from other workers.

ForkJoinPool là work-stealing executor tối ưu cho nhiều divide-and-conquer task nhỏ, đặc biệt CPU-bound computation. Mỗi worker có deque; worker rảnh steal task từ worker khác.

Direct answer / Trả lời trực tiếp

ForkJoinPool is a work-stealing executor optimized for many small divide-and-conquer tasks, especially CPU-bound computations. Each worker has a deque; idle workers steal tasks from other workers.

ForkJoinPool là work-stealing executor tối ưu cho nhiều divide-and-conquer task nhỏ, đặc biệt CPU-bound computation. Mỗi worker có deque; worker rảnh steal task từ worker khác.

How it works inside / Cơ chế bên trong

A task recursively splits until it reaches a threshold. fork pushes a subtask for asynchronous execution, compute may process another branch directly, and join waits for the result while the worker can assist the pool. Local LIFO processing improves locality; stealing from the opposite end reduces many threads fighting for the same resource.

Task recursively split đến threshold. fork push subtask để chạy async, compute có thể xử lý branch khác trực tiếp và join chờ result trong khi worker có thể hỗ trợ pool. Local LIFO tăng locality; steal từ đầu đối diện giảm contention.

Good and bad points / Điểm tốt và hạn chế

The threshold is critical: tasks that are too small create overhead, while tasks that are too large not fully use cores. Blocking I/O can starve workers unless managed blocking or another executor is used. Parallel streams normally use the common pool, which is shared process-wide.

Threshold rất quan trọng: task quá nhỏ tạo overhead, task quá lớn không dùng hết core. Blocking I/O có thể starvation worker nếu không dùng managed blocking hoặc executor khác. Parallel stream thường dùng common pool chia sẻ toàn process.

Real backend example / Ví dụ backend thực tế

I avoid placing unpredictable blocking calls in the common ForkJoinPool. For controlled CPU transformations, I benchmark task task size and consider whether a simple parallel loop or vectorized algorithm is better.

Tôi tránh đưa blocking call khó đoán vào common ForkJoinPool. Với CPU transformation có kiểm soát, tôi benchmark task granularity và cân nhắc simple parallel loop hoặc vectorized algorithm.

Senior decision / Quyết định senior

ForkJoinPool is a CPU work-decomposition engine, not a generic default executor for all asynchronous work.

ForkJoinPool là CPU work-decomposition engine, không phải generic default executor cho mọi async work.

33. What is interruption?
Easy answer first / Trả lời dễ trước

Interruption is Java's cooperative cancellation and attention mechanism. It sets an interrupt status on a thread; the thread or blocking operation must observe and respond to it.

Interruption là cơ chế cooperative cancellation/attention của Java. Nó set interrupt status trên thread; thread hoặc blocking operation phải observe và phản ứng.

Direct answer / Trả lời trực tiếp

Interruption is Java's cooperative cancellation and attention mechanism. It sets an interrupt status on a thread; the thread or blocking operation must observe and respond to it.

Interruption là cơ chế cooperative cancellation/attention của Java. Nó set interrupt status trên thread; thread hoặc blocking operation phải observe và phản ứng.

How it works inside / Cơ chế bên trong

interrupt sets the status. Methods such as sleep, wait, join, BlockingQueue.take, and lockInterruptibly may detect it, clear the status, and throw InterruptedException. isInterrupted reads status without clearing; Thread.interrupted reads and clears the current thread's status.

interrupt set status. sleep, wait, join, BlockingQueue.take và lockInterruptibly có thể detect, clear status rồi throw InterruptedException. isInterrupted đọc không clear; Thread.interrupted đọc và clear status của current thread.

Ở task boundary, chỉ catch InterruptedException để cleanup, restore flag nếu không propagate và kết thúc sớm. Library không nên tự quyết cancellation không quan trọng với caller.

Senior decision / Quyết định senior

Interrupt is a request, not Thread.stop. Correct code preserves the signal.

Interrupt là request, không phải Thread.stop. Code đúng phải bảo toàn signal.

Real backend example / Ví dụ backend thực tế

A cancellable loop should periodically test Thread.currentThread().isInterrupted and exit after cleanup. For external calls, configure their own timeout/cancellation API rather than assuming thread interruption is sufficient.

Loop có thể cancel nên định kỳ check isInterrupted và exit sau cleanup. Với external call, cấu hình timeout/cancellation API riêng thay vì nghĩ thread interrupt là đủ.

Senior decision / Quyết định senior

Future cancellation changes the result contract and sends a signal; task code must implement safe cancellation.

Future cancellation thay đổi result contract và gửi signal; task code phải implement safe cancellation.

35. BlockingQueue vs wait/notify?
Easy answer first / Trả lời dễ trước

BlockingQueue is a high-level producer-consumer abstraction that already implements thread safety, waiting, visibility, and optional capacity. wait/notify are low-level monitor primitives used to build such abstractions.

BlockingQueue là high-level producer-consumer abstraction đã implement thread safety, waiting, visibility và optional capacity. wait/notify là low-level monitor primitive dùng để xây abstraction như vậy.

Direct answer / Trả lời trực tiếp

BlockingQueue is a high-level producer-consumer abstraction that already implements thread safety, waiting, visibility, and optional capacity. wait/notify are low-level monitor primitives used to build such abstractions.

BlockingQueue là high-level producer-consumer abstraction đã implement thread safety, waiting, visibility và optional capacity. wait/notify là low-level monitor primitive dùng để xây abstraction như vậy.

How it works inside / Cơ chế bên trong

A queue implementation manages internal locks or lock-free algorithms and separate conditions for not-empty and sometimes not-full states. put can wait for capacity; take waits for an element. With manual wait/notify, the developer must protect every state access, loop on predicates, handle interruption, select notifications, and avoid missed signals.

Queue implementation quản lý internal lock hoặc lock-free algorithm và condition riêng cho not-empty, đôi khi not-full. put có thể chờ capacity; take chờ element. Với manual wait/notify, developer phải bảo vệ mọi state access, loop predicate, handle interrupt, chọn notification và tránh missed signal.

Good and bad points / Điểm tốt và hạn chế

BlockingQueue is less flexible than a custom protocol but dramatically safer. Queue choice matters: ArrayBlockingQueue is bounded and array-based, LinkedBlockingQueue can be optionally bounded, SynchronousQueue performs direct handoff, and PriorityBlockingQueue is unbounded and ordered.

BlockingQueue ít linh hoạt hơn custom protocol nhưng an toàn hơn nhiều. Loại queue quan trọng: ArrayBlockingQueue bounded array-based, LinkedBlockingQueue có thể bounded, SynchronousQueue direct handoff, PriorityBlockingQueue unbounded và ordered.

Real backend example / Ví dụ backend thực tế

For background workers, a bounded BlockingQueue makes overload visible through blocking, timeout, or rejection. A custom List plus wait/notify often accidentally becomes an unbounded memory buffer.

Với background worker, bounded BlockingQueue làm overload visible qua blocking, timeout hoặc rejection. Custom List cộng wait/notify thường vô tình thành unbounded memory buffer.

Senior decision / Quyết định senior

Use BlockingQueue for producer-consumer unless implementing a concurrency library or a genuinely specialized protocol.

Dùng BlockingQueue cho producer-consumer trừ khi đang implement concurrency library hoặc protocol thực sự đặc biệt.

36. AtomicLong vs LongAdder?
Easy answer first / Trả lời dễ trước

AtomicLong stores one atomic long value and updates it with CAS. LongAdder spreads high-many threads fighting for the same resource updates across multiple cells and sums them when requested.

AtomicLong lưu một atomic long value và update bằng CAS. LongAdder phân tán update contention cao qua nhiều cell rồi sum khi được yêu cầu.

Direct answer / Trả lời trực tiếp

AtomicLong stores one atomic long value and updates it with CAS. LongAdder spreads high-many threads fighting for the same resource updates across multiple cells and sums them when requested.

AtomicLong lưu một atomic long value và update bằng CAS. LongAdder phân tán update contention cao qua nhiều cell rồi sum khi được yêu cầu.

How it works inside / Cơ chế bên trong

AtomicLong many threads fighting for the same resource concentrates on one memory location, causing repeated CAS failures and cache-line movement. LongAdder starts with a base value and creates striped cells under many threads fighting for the same resource, so different threads update different cells. sum aggregates base and cells.

AtomicLong tập trung contention trên một memory location, gây CAS fail và cache-line movement. LongAdder bắt đầu bằng base value rồi tạo striped cell khi contention để thread khác nhau update cell khác nhau. sum aggregate base và cell.

Good and bad points / Điểm tốt và hạn chế

AtomicLong supports exact operations such as compareAndSet, getAndSet, and a current value with one clear exact order. LongAdder provides higher update throughput but sum is not an atomic snapshot while updates are in progress, and it uses more memory.

AtomicLong hỗ trợ operation chính xác như compareAndSet, getAndSet và current value có linearizable semantics. LongAdder có update throughput cao hơn nhưng sum không phải atomic snapshot khi update đang diễn ra và dùng nhiều memory hơn.

Real backend example / Ví dụ backend thực tế

Use LongAdder for request, error, or hit counters exposed as metrics. Use AtomicLong for sequence-like state or when the read-modify-write transition itself must be exact within one process.

Dùng LongAdder cho request/error/hit counter làm metric. Dùng AtomicLong cho sequence-like state hoặc khi read-modify-write transition phải chính xác trong một process.

Senior decision / Quyết định senior

LongAdder optimizes metric counting; AtomicLong models one exact atomic state.

LongAdder tối ưu statistical aggregation; AtomicLong mô hình hóa một exact atomic state.

37. When is CompletableFuture not appropriate?
Easy answer first / Trả lời dễ trước

It is not appropriate when it makes a simple workflow harder to reason about, when work is mostly sequential blocking I/O that virtual threads can express more clearly, or when the system lacks executor, timeout, cancellation, and context-propagation discipline.

Nó không phù hợp khi làm workflow đơn giản khó reasoning hơn, khi work chủ yếu sequential blocking I/O mà virtual thread diễn đạt rõ hơn, hoặc khi hệ thống thiếu discipline về executor, timeout, cancellation và context propagation.

Direct answer / Trả lời trực tiếp

It is not appropriate when it makes a simple workflow harder to reason about, when work is mostly sequential blocking I/O that virtual threads can express more clearly, or when the system lacks executor, timeout, cancellation, and context-propagation discipline.

Nó không phù hợp khi làm workflow đơn giản khó reasoning hơn, khi work chủ yếu sequential blocking I/O mà virtual thread diễn đạt rõ hơn, hoặc khi hệ thống thiếu discipline về executor, timeout, cancellation và context propagation.

How it works inside / Cơ chế bên trong

A CompletionStage graph distributes execution across completion threads and executors. Non-Async continuations may run on whichever thread completes the previous stage. Async variants use the common pool unless an executor is supplied. Exception handling and cancellation do not automatically propagate in every direction.

CompletionStage graph phân tán execution qua completion thread và executor. Non-Async continuation có thể chạy trên thread complete stage trước. Async variant dùng common pool nếu không truyền executor. Exception handling và cancellation không tự động propagate mọi hướng.

Good and bad points / Điểm tốt và hạn chế

It is excellent for a limited number of parallel calls/fan-in and independent asynchronous composition. It is poor when developers immediately call join/get after every stage, use it as a decorative wrapper around blocking work, or create thousands of unbounded dependent calls.

Nó rất tốt cho bounded fan-out/fan-in và composition async độc lập. Nó tệ khi developer gọi join/get ngay sau mỗi stage, dùng như wrapper trang trí quanh blocking work hoặc tạo hàng nghìn call phụ thuộc không giới hạn.

Real backend example / Ví dụ backend thực tế

For three independent HTTP calls with clear timeouts and a custom executor, CompletableFuture can reduce latency through parallel fan-out. For one JDBC call followed by one transformation, a virtual thread and normal code may be simpler.

Ba HTTP call độc lập có timeout rõ và custom executor thì CompletableFuture có thể giảm latency nhờ fan-out parallel. Một JDBC call rồi một transformation thì virtual thread và code thường có thể đơn giản hơn.

Senior decision / Quyết định senior

Use CompletableFuture when composition is the requirement, not merely because the method name should end with Async.

Dùng CompletableFuture khi composition là requirement, không chỉ vì muốn method có chữ Async.

38. How should InterruptedException be handled?
Easy answer first / Trả lời dễ trước

The preferred choices are to propagate it, or if the method cannot declare it, restore the interrupt status and terminate or translate the operation into cancellation. Silently swallowing it is almost always wrong.

Lựa chọn ưu tiên là propagate; nếu method không khai báo được thì restore interrupt status rồi terminate hoặc translate operation thành cancellation. Nuốt im lặng gần như luôn sai.

Direct answer / Trả lời trực tiếp

The preferred choices are to propagate it, or if the method cannot declare it, restore the interrupt status and terminate or translate the operation into cancellation. Silently swallowing it is almost always wrong.

Lựa chọn ưu tiên là propagate; nếu method không khai báo được thì restore interrupt status rồi terminate hoặc translate operation thành cancellation. Nuốt im lặng gần như luôn sai.

How it works inside / Cơ chế bên trong

Many blocking methods clear interrupt status before throwing InterruptedException. Therefore, if code catches the exception and does not rethrow it, calling Thread.currentThread().interrupt restores the signal for higher layers. Cleanup should occur before returning.

Nhiều blocking method clear interrupt status trước khi throw InterruptedException. Vì vậy nếu catch mà không rethrow, Thread.currentThread().interrupt() khôi phục signal cho layer trên. Cleanup cần thực hiện trước khi return.

Good and bad points / Điểm tốt và hạn chế

Some top-level task boundaries may deliberately consume interruption after completing shutdown logic because no caller remains. Lower-level library methods should normally preserve it. Wrapping it in a generic RuntimeException without restoring status can also lose cancellation semantics.

Một số top-level task boundary có thể chủ động consume interrupt sau shutdown logic vì không còn caller. Lower-level library method thường phải preserve. Wrap thành RuntimeException chung mà không restore status cũng có thể làm mất cancellation semantics.

Real backend example / Ví dụ backend thực tế

A worker taking from BlockingQueue should catch interruption, restore status if needed, exit the loop, release resources, and let executor shutdown complete. Logging and continuing can make an application impossible to stop gracefully.

Worker take từ BlockingQueue nên catch interrupt, restore nếu cần, exit loop, release resource và cho executor shutdown. Log rồi continue có thể khiến app không thể graceful stop.

Senior decision / Quyết định senior

Treat InterruptedException as a control-flow signal, not merely an error to log.

Xem InterruptedException là control-flow signal, không chỉ là error để log.

39. Why is bounded concurrency important?
Easy answer first / Trả lời dễ trước

Every concurrent task consumes a limited resource: CPU time, memory, queue slots, threads, virtual-thread objects, database connections, sockets, or downstream quota. Bounds prevent overload from becoming unbounded latency and memory growth.

Mỗi concurrent task dùng resource hữu hạn: CPU, memory, queue slot, thread, virtual-thread object, DB connection, socket hoặc downstream quota. Bound ngăn overload biến thành latency và memory growth không giới hạn.

Direct answer / Trả lời trực tiếp

Every concurrent task consumes a limited resource: CPU time, memory, queue slots, threads, virtual-thread objects, database connections, sockets, or downstream quota. Bounds prevent overload from becoming unbounded latency and memory growth.

Mỗi concurrent task dùng resource hữu hạn: CPU, memory, queue slot, thread, virtual-thread object, DB connection, socket hoặc downstream quota. Bound ngăn overload biến thành latency và memory growth không giới hạn.

How it works inside / Cơ chế bên trong

When arrival rate exceeds service rate, work accumulates according to queueing theory. An unbounded queue can keep accepting tasks while wait time grows far beyond request timeouts. A bound forces a visible policy: block, timeout, reject, shed load, or persist elsewhere.

Khi arrival rate vượt service rate, work tích lũy theo queueing theory. Unbounded queue tiếp tục nhận task trong khi wait time vượt xa request timeout. Bound buộc policy rõ ràng: block, timeout, reject, shed load hoặc persist nơi khác.

Good and bad points / Điểm tốt và hạn chế

A bound that is too low wastes capacity and rejects healthy bursts. A bound that is too high hides overload and worsens tail latency. Limits should be based on service time, allowed waiting time, burst size, and downstream capacity.

Bound quá thấp lãng phí capacity và reject burst lành mạnh. Bound quá cao che overload và làm tail latency tệ. Limit phải dựa trên service time, allowed wait, burst size và downstream capacity.

Real backend example / Ví dụ backend thực tế

For an HTTP dependency that safely handles 50 concurrent calls, use a bulkhead/semaphore near 50, a finite waiting queue or timeout, and metrics for saturation and rejection. Do not allow 10,000 futures to accumulate.

Downstream HTTP chịu an toàn 50 concurrent call thì dùng bulkhead/semaphore gần 50, waiting queue hữu hạn hoặc timeout và metric saturation/rejection. Không cho 10.000 future tích lũy.

Senior decision / Quyết định senior

Bounded concurrency is stability engineering: fail predictably before the whole process fails unpredictably.

Bounded concurrency là stability engineering: fail có kiểm soát trước khi cả process fail không kiểm soát.

40. How do you choose between Lock, Atomic, and message passing?
Easy answer first / Trả lời dễ trước

I choose based on the invariant and ownership model. Atomics are best for independent single-value state transitions.

Tôi chọn theo invariant và ownership model. Atomic phù hợp cho independent single-value transition.

Direct answer / Trả lời trực tiếp

I choose based on the invariant and ownership model. Atomics are best for independent single-value state transitions. Locks are best when multiple fields or operations must change together. Message passing is best when mutable state can have a single owner and other threads can send commands.

Tôi chọn theo invariant và ownership model. Atomic phù hợp cho independent single-value transition. Lock phù hợp khi nhiều field/operation phải thay đổi cùng nhau. Message passing phù hợp khi mutable state có một owner và thread khác gửi command.

How it works inside / Cơ chế bên trong

Atomic CAS loops retry when state changes and become complex for multi-variable invariants. Locks serialize a critical section and establish visibility. Message passing moves working together into a queue and single-threaded state machine, avoiding direct shared mutation but introducing ordering, queueing, and rules for failures.

Atomic CAS loop retry khi state thay đổi và trở nên phức tạp với multi-variable invariant. Lock serialize critical section và tạo visibility. Message passing chuyển coordination vào queue và single-thread state machine, tránh direct shared mutation nhưng thêm ordering, queueing và failure semantics.

Good and bad points / Điểm tốt và hạn chế

Atomics can suffer many threads fighting for the same resource and ABA-style design issues. Locks can block and deadlock. Message passing adds latency, memory, backpressure, and possibly data may become correct a little later. Immutability and snapshot replacement should also be considered before all three.

Atomic có thể contention và gặp vấn đề design kiểu ABA. Lock có thể block/deadlock. Message passing thêm latency, memory, backpressure và có thể eventual consistency. Immutability/snapshot replacement cũng cần xét trước cả ba.

Real backend example / Ví dụ backend thực tế

For a request metric use LongAdder. For an in-process account object updating balance plus status use a lock. For an order aggregate processed through commands and events, a single-writer/message-driven model may remove most shared-state locking.

Request metric dùng LongAdder. In-process Account object update balance cùng status dùng lock. Order aggregate xử lý qua command/event có thể dùng single-writer/message-driven để loại phần lớn shared-state locking.

Senior decision / Quyết định senior

I do not select a primitive first. I define ownership and invariant first, then select the mechanism that makes correctness easiest to prove.

Tôi không chọn primitive trước. Tôi định nghĩa ownership và invariant trước, rồi chọn cơ chế giúp correctness dễ chứng minh nhất.

Ten things to remember

  1. Threads share heap but own stacks.
  2. Concurrency is not automatically parallelism.
  3. Shared mutable state creates race, visibility, and ordering risks.
  4. synchronized gives locking and visibility.
  5. volatile gives visibility, not compound atomicity.
  6. Atomics use CAS.
  7. Prefer high-level working together tools.
  8. Thread pools need bounds and rejection policy.
  9. Async changes control flow, not total work.
  10. Virtual threads reduce waiting cost, not downstream limits.

Study order: thread model → race → JMM → synchronized → volatile → Lock/atomic → pools → CompletableFuture → async/non-blocking → production.

Thứ tự học: thread model → race → JMM → synchronized → volatile → Lock/atomic → pool → CompletableFuture → async/non-blocking → production.
