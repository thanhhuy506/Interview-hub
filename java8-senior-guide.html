Java 8 Functional style

1. Stream API

A Stream is a pipeline for processing data from a source such as a collection, array, or generated sequence. A stream does not normally store data. It describes operations that will be performed on the data.

Important idea: A collection stores values. A stream describes how values should be processed.

1.1 Stream pipeline

1
Source
List, Set, array, file lines, generated values.
2
Intermediate operations
filter, map, sorted, distinct, limit. These are lazy.
3
Terminal operation
collect, count, reduce, max, forEach. This starts processing.
List<String> names = employees.stream()
        .filter(employee -> employee.getSalary() > 5_000)
        .map(Employee::getName)
        .sorted()
        .collect(Collectors.toList());

1.2 Stream versus normal loops

Traditional loop

List<String> names = new ArrayList<>();

for (Employee employee : employees) {
    if (employee.getSalary() > 5_000) {
        names.add(employee.getName());
    }
}

Collections.sort(names);

Stream

List<String> names = employees.stream()
        .filter(e -> e.getSalary() > 5_000)
        .map(Employee::getName)
        .sorted()
        .collect(Collectors.toList());

The loop explains how to iterate, check, add, and sort. The stream explains what result is required: filter employees, extract names, sort, and collect.

1.3 Advantages of Stream API

1. More declarative code

The business transformation is visible in one pipeline. There is less temporary state and less manual control flow.

2. Composable operations

Operations such as filter, map, groupingBy, and reduce can be combined without deeply nested loops.

3. Lazy execution

Intermediate operations do not run until a terminal operation is called. Short-circuit operations such as findFirst may stop early.

4. Easier parallel processing

A suitable CPU-bound pipeline can sometimes use parallelStream(). However, this is not automatically faster and requires careful measurement.

5. Fewer mutable variables

Streams encourage immutable transformations. This reduces bugs caused by counters, shared lists, or variables changed in many places.

6. Powerful collectors

Grouping, partitioning, counting, joining, and aggregation are available through standard collectors.

1.4 Disadvantages and trade-offs

Disadvantage Why it matters Better choice
Harder debugging A long pipeline can be harder to step through than a loop. Split complex pipelines into named methods.
Can reduce readability Nested lambdas and complicated collectors may hide business rules. Use a loop when control flow is clearer.
Object and lambda overhead Boxing and intermediate objects may matter in hot code. Measure with a profiler or JMH before optimizing.
One-time use A stream cannot be reused after a terminal operation. Create a new stream from the original source.
Side effects are dangerous Changing external state can create ordering and concurrency bugs. Prefer collect/reduce over mutating shared variables.
Parallel stream risk It uses the common ForkJoinPool and may affect unrelated work. Use explicit executors for controlled concurrency.

1.5 When a normal loop is better

  • The algorithm has many break, continue, or complex branches.
  • You need to update several variables during one traversal.
  • You need indexed access or modification of the original list.
  • The code is performance-critical and profiling shows stream overhead.
  • The stream version is shorter but less understandable.

1.6 Important Stream operations

filter

Keeps elements matching a condition.

map

Transforms one element into another value.

flatMap

Flattens nested streams into one stream.

sorted

Sorts elements using natural order or a comparator.

reduce

Combines many values into one result.

collect

Builds a list, map, group, or other final container.

Find employee with highest salary

Optional<Employee> highestPaid = employees.stream()
        .max(Comparator.comparingDouble(Employee::getSalary));

Increase salary by 10% without modifying original objects

List<Employee> updatedEmployees = employees.stream()
        .map(employee -> new Employee(
                employee.getId(),
                employee.getName(),
                employee.getSalary() * 1.10
        ))
        .collect(Collectors.toList());

Group employees by department

Map<String, List<Employee>> byDepartment = employees.stream()
        .collect(Collectors.groupingBy(Employee::getDepartment));

Count employees by department

Map<String, Long> employeeCount = employees.stream()
        .collect(Collectors.groupingBy(
                Employee::getDepartment,
                Collectors.counting()
        ));

1.7 Lazy execution and short-circuiting

Optional<Employee> result = employees.stream()
        .filter(employee -> {
            System.out.println("Checking " + employee.getName());
            return employee.getSalary() > 10_000;
        })
        .findFirst();

findFirst() can stop as soon as it finds one matching employee. The stream may not process every element.

1.8 Parallel stream: use carefully

Do not say: “Parallel stream is always faster.” Splitting work, scheduling tasks, merging results, synchronization, and cache behavior all add cost.

A parallel stream is more suitable when:

  • The data set is large.
  • Each element requires significant CPU work.
  • Operations are stateless and independent.
  • The source splits efficiently, such as an array or ArrayList.
  • Performance has been measured in the real environment.

Avoid it when:

  • The operation is mainly database, network, or file I/O.
  • The data set is small.
  • Order and side effects are important.
  • The application server already manages many threads.

Senior interview answer

Stream API provides a declarative pipeline for data processing. It improves readability for filtering, transformation, grouping, and aggregation, and it reduces mutable state. However, I do not use streams automatically. A normal loop can be clearer for complex control flow, indexed updates, or performance-sensitive code. Parallel streams also require measurement because they use shared thread-pool resources and are not always faster.

Java 8 Null safety

2. Optional

Optional<T> is a container that either contains a non-null value or is empty. Its main purpose is to make the possibility of “no result” explicit in an API.

Optional does not magically prevent every NullPointerException. It gives you a clearer contract and operations for handling an absent value.

2.1 Why not just check null?

Traditional null return

User user = userRepository.findById(id);

if (user != null) {
    return user.getEmail();
}

return "unknown@example.com";

Optional return

return userRepository.findById(id)
        .map(User::getEmail)
        .orElse("unknown@example.com");

A null check is valid Java. The problem is that a method returning User does not clearly tell the caller whether null is possible. A return type of Optional<User> communicates that “no user” is an expected outcome.

2.2 What Optional improves

  • API clarity: absence is part of the method contract.
  • Fluent transformations: use map, filter, flatMap, and orElse.
  • Fewer scattered checks: handle absence near the decision point.
  • Safer nested access: avoid many chained null checks.

2.3 Creating Optional values

Optional<String> empty = Optional.empty();

Optional<String> name = Optional.of("Huy");

// Accepts a nullable value:
Optional<String> possibleName = Optional.ofNullable(databaseValue);
Optional.of(null) throws NullPointerException. Use Optional.ofNullable(value) when the value may be null.

2.4 Important Optional methods

Method Purpose Example use
map Transform a present value. Convert User to email.
flatMap Transform when the mapping already returns Optional. User → Optional<Address>.
filter Keep the value only when it matches a condition. Keep only active users.
orElse Return a default value. Use a fallback name.
orElseGet Create a fallback lazily. Call another service only if empty.
orElseThrow Throw a business exception if empty. User not found.
ifPresent Run an action when a value exists. Send a notification.

2.5 orElse versus orElseGet

User user = optionalUser.orElse(loadDefaultUser());

loadDefaultUser() is executed even when the Optional already contains a user. 

User user = optionalUser.orElseGet(this::loadDefaultUser);

With orElseGet, the fallback method runs only when the Optional is empty.

2.6 Avoid nested null checks

Many null checks

String city = null;

if (user != null
        && user.getAddress() != null
        && user.getAddress().getCity() != null) {
    city = user.getAddress().getCity();
}

Optional mapping

String city = Optional.ofNullable(user)
        .map(User::getAddress)
        .map(Address::getCity)
        .orElse("Unknown");

2.7 Real-world use cases

Repository lookup

Optional<User> findById(Long id);

A record may not exist. Empty is a normal result.

Optional configuration

Optional<String> findHeader(
        HttpServletRequest request,
        String headerName
);

A request header may be absent.

Business lookup

Payment payment = paymentRepository.findById(id)
        .orElseThrow(() ->
                new PaymentNotFoundException(id));

Convert technical absence into a business exception.

Conditional transformation

Optional<Coupon> validCoupon =
        couponRepository.findByCode(code)
                .filter(Coupon::isActive)
                .filter(c -> !c.isExpired());

2.8 When not to use Optional

  • Do not normally use Optional for every method parameter. Method overloads or nullable annotations may be clearer.
  • Do not normally store Optional as a JPA entity field. It can create persistence and serialization problems.
  • Do not return Optional collections. Return an empty list instead of Optional<List<T>>.
  • Avoid calling get() without checking. Prefer orElseThrow, map, or ifPresent.
  • Do not wrap a value in Optional only to immediately call isPresent() and get() everywhere.

Weak style

Optional<User> user = repository.findById(id);

if (user.isPresent()) {
    return user.get().getName();
}

return "Unknown";

Better style

return repository.findById(id)
        .map(User::getName)
        .orElse("Unknown");

Senior interview answer

Optional is mainly an API design tool. It represents that a return value may be absent. We can still write correct code with null checks, but Optional makes the contract clearer and provides operations such as map, filter, orElseGet, and orElseThrow. I mainly use it for return values such as repository lookups. I avoid using it for entity fields, every method parameter, or collection results.

Spring Database consistency

3. @Transactional

A database transaction groups operations into one logical unit. Either all important changes succeed, or the transaction rolls them back.

Main goal: protect a business invariant, not simply “put an annotation on every service method.”

3.1 Basic transaction example

@Service
public class TransferService {

    @Transactional
    public void transfer(
            Long fromAccountId,
            Long toAccountId,
            BigDecimal amount
    ) {
        accountRepository.decreaseBalance(fromAccountId, amount);
        accountRepository.increaseBalance(toAccountId, amount);
        transferRepository.save(
                new Transfer(fromAccountId, toAccountId, amount)
        );
    }
}

If the second or third operation fails, the debit should not remain alone. The full transaction rolls back.

3.2 Default rollback behavior

  • Spring normally rolls back for RuntimeException and Error.
  • Spring does not roll back checked exceptions by default.
  • Use rollbackFor when a checked exception must trigger rollback.
@Transactional(rollbackFor = IOException.class)
public void importFile(Path path) throws IOException {
    // database changes
    // file processing
}
Catching an exception and not rethrowing it may cause Spring to commit, because the transactional proxy sees a successful method return.

3.3 Important transaction cases in real systems

Case Recommended boundary Important note
Create order Order, order items, payment record in one transaction. External payment call should not be treated like a normal DB statement.
Money transfer Debit, credit, and ledger entry together. Use locking or optimistic versioning to avoid race conditions.
Inventory reservation Check available stock and reserve atomically. A plain read followed by update may have a race condition.
User registration User, role, profile, and verification record together. Email sending should usually happen after commit or through an outbox.
Batch processing One transaction per item or chunk. A single huge transaction creates long locks and large rollback cost.
Audit log Sometimes use an independent transaction. Decide whether audit must survive the business rollback.
Read-only query @Transactional(readOnly = true). It is a hint and can reduce unnecessary dirty checking in some cases.
Cross-service workflow Saga, outbox, idempotency, compensation. A local Spring transaction cannot roll back another microservice.

3.4 A, B, C: rollback only A and C, not B

Required behavior:

Task
 ├── A   → outer transaction T1
 ├── B   → independent transaction T2
 │    ├── B1
 │    └── B2
 └── C   → outer transaction T1

If a later error occurs:
A and C rollback
B, B1, and B2 remain committed

Outer service

@Service
@RequiredArgsConstructor
public class TaskService {

    private final AService aService;
    private final BService bService;
    private final CService cService;

    @Transactional
    public void executeTask() {
        aService.execute(); // joins T1

        bService.execute(); // starts T2

        cService.execute(); // joins T1

        // If a RuntimeException occurs here:
        // T1 rolls back: A and C
        // T2 is already committed: B, B1, B2 remain
    }
}

Independent B transaction

@Service
@RequiredArgsConstructor
public class BService {

    private final B1Service b1Service;
    private final B2Service b2Service;

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void execute() {
        // B logic
        b1Service.execute(); // joins T2
        b2Service.execute(); // joins T2
    }
}
How it works: Spring suspends T1, starts T2 for B, commits T2, and then resumes T1.

Important consequence

This creates intentional partial commit. If C fails, B remains in the database. That is correct only when the business requirement really wants B to survive.

Typical examples:

  • An audit record must remain even when the main operation fails.
  • A retry record must be committed before the outer process fails.
  • Each batch item should commit independently.
  • An operational log must survive a business rollback.

3.5 Important propagation types

Propagation Behavior Typical use
REQUIRED Join the current transaction, or create one if none exists. Default business service behavior.
REQUIRES_NEW Suspend the current transaction and create a new one. Independent audit, retry, or item commit.
NESTED Create a savepoint inside the existing transaction. Partial rollback with JDBC savepoint support.
SUPPORTS Join if a transaction exists; otherwise run without one. Read helper methods.
NOT_SUPPORTED Suspend an existing transaction and run without one. Long non-transactional work.
MANDATORY Fail if no transaction exists. Internal methods that must be called inside a business transaction.
NEVER Fail if a transaction exists. Operations that must not run transactionally.

3.6 REQUIRES_NEW versus NESTED

REQUIRES_NEW

Uses a separate physical transaction.

It may commit even if the outer transaction later rolls back.

NESTED

Usually uses a savepoint inside the same physical transaction.

The outer rollback still rolls back everything.

3.7 Proxy and self-invocation problem

Spring transaction behavior is usually applied by a proxy. A method call inside the same object does not pass through that proxy.

May not work as expected

@Service
public class TaskService {

    @Transactional
    public void executeTask() {
        executeB(); // self-invocation
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void executeB() {
        // REQUIRES_NEW may not be applied
    }
}

Better design

TaskService  →  BService.execute()

Place the independent transactional method in another Spring bean so the call goes through the transactional proxy.

3.8 Other important transaction pitfalls

Calling external APIs inside a long transaction

Database locks remain open while the network call waits. This increases lock time, timeout risk, and connection usage. Prefer a shorter DB transaction plus an outbox, state machine, or saga.

@Async and transactions

Transaction context is normally bound to the current thread. An asynchronous method runs in another thread and does not automatically continue the caller's transaction.

Private or non-proxied methods

Proxy-based transaction management is most reliable on public methods called from another Spring bean.

Swallowed exceptions

If you catch an exception and return normally, the transaction may commit. Rethrow the exception or mark the transaction rollback-only when rollback is required.

Very large transactions

They hold locks, use memory, keep connections busy, and make failure expensive. Use chunk-based processing when appropriate.

Multiple databases or services

One local transaction manager normally cannot provide atomic rollback across independent databases and microservices. Consider XA only when justified; often saga and outbox patterns are simpler.

3.9 Isolation and concurrency

A transaction does not automatically prevent every concurrency bug. You may also need:

  • Optimistic locking with a @Version field.
  • Pessimistic locking such as SELECT ... FOR UPDATE.
  • Unique constraints.
  • Idempotency keys.
  • An appropriate database isolation level.

Senior interview answer

I place a transaction around a complete database business unit, not around every repository call. By default, Spring uses REQUIRED and rolls back unchecked exceptions. For an operation that must commit independently, such as an audit or retry record, I use REQUIRES_NEW in another Spring bean. I also consider proxy limitations, self-invocation, lock duration, external API calls, idempotency, and whether a distributed workflow needs saga or outbox instead of one local transaction.

Java 7+ Safe cleanup

4. Try-with-resources

Try-with-resources automatically closes resources that implement AutoCloseable. It is commonly used with files, streams, readers, writers, JDBC objects, sockets, and other closeable resources.

4.1 The problem it solves

A resource may remain open when an exception happens. This can cause:

  • File descriptor leaks.
  • Database connection leaks.
  • Locked files.
  • Memory or operating-system resource pressure.

Old manual style

BufferedReader reader = null;

try {
    reader = new BufferedReader(new FileReader(path));
    return reader.readLine();
} finally {
    if (reader != null) {
        try {
            reader.close();
        } catch (IOException ignored) {
            // cleanup error may be lost
        }
    }
}

Try-with-resources

try (BufferedReader reader =
             new BufferedReader(new FileReader(path))) {
    return reader.readLine();
}

Java calls close() automatically, even when the body throws an exception.

4.2 Multiple resources

try (
    BufferedReader reader =
            new BufferedReader(new FileReader(source));
    BufferedWriter writer =
            new BufferedWriter(new FileWriter(target))
) {
    String line;

    while ((line = reader.readLine()) != null) {
        writer.write(line);
        writer.newLine();
    }
}

Resources are closed in reverse order: writer first, then reader.

4.3 JDBC example

String sql = "SELECT id, name FROM users WHERE status = ?";

try (
    Connection connection = dataSource.getConnection();
    PreparedStatement statement =
            connection.prepareStatement(sql)
) {
    statement.setString(1, "ACTIVE");

    try (ResultSet resultSet = statement.executeQuery()) {
        while (resultSet.next()) {
            System.out.println(resultSet.getLong("id"));
            System.out.println(resultSet.getString("name"));
        }
    }
}

4.4 Suppressed exceptions

If the main block throws an exception and close() also throws, Java keeps the main exception and attaches the close exception as a suppressed exception. 

catch (Exception ex) {
    for (Throwable suppressed : ex.getSuppressed()) {
        log.error("Cleanup also failed", suppressed);
    }
}

4.5 Custom AutoCloseable resource

public class ReportSession implements AutoCloseable {

    public ReportSession() {
        System.out.println("Open report session");
    }

    public void generate() {
        System.out.println("Generate report");
    }

    @Override
    public void close() {
        System.out.println("Close report session");
    }
}
try (ReportSession session = new ReportSession()) {
    session.generate();
}

4.6 When to use it

  • File input/output.
  • Raw JDBC connections, statements, and result sets.
  • Network sockets.
  • Zip files and archive streams.
  • Custom sessions or handles that require deterministic cleanup.
Do not manually close a Spring-managed JPA EntityManager or Spring-managed database connection unless you explicitly created it. The framework manages its lifecycle.

Senior interview answer

Try-with-resources guarantees deterministic cleanup for AutoCloseable resources. It is safer than a manual finally block, especially when both the business operation and close operation throw exceptions. I use it for file streams, JDBC objects, sockets, and custom resources, but not for framework-managed resources whose lifecycle is controlled by Spring.

Collections Internals

5. HashMap internals and complexity

Yes, HashMap.get() is normally O(1) average time. It is not guaranteed O(1) in every situation because multiple keys can map to the same bucket.

Best interview wording: HashMap get and put are average O(1). With collisions, lookup depends on the bucket structure. In Java 8, a heavily-collided bucket can become a red-black tree, giving approximately O(log n) lookup inside that bucket.

5.1 High-level structure

HashMap
  └── table: Node<K,V>[]
        ├── bucket 0
        ├── bucket 1 → Node → Node
        ├── bucket 2
        └── bucket 3 → TreeNode (red-black tree)

5.2 How get(key) works

1
Calculate hash
Use key.hashCode() and spread high bits.
2
Find bucket index
Use the table length and hash value.
3
Check first node
Compare hash, then compare keys with equals().
4
Search collision structure
Linked list or red-black tree.
int hash = hash(key);
int index = (table.length - 1) & hash;

The table length is normally a power of two. Bitwise AND is efficient and distributes entries using the prepared hash value.

5.3 Complexity

Operation Average Collision case
get O(1) O(n) in a linked list, approximately O(log n) after treeification.
put O(1) Can include bucket traversal and occasional resize.
remove O(1) Depends on bucket search.
containsValue O(n) Must scan entries.

5.4 Collision and Java 8 treeification

A collision occurs when different keys map to the same bucket. Java 8 can convert a long linked list into a red-black tree when the bucket becomes large enough and the table is already sufficiently large.

  • Treeification threshold is normally 8 nodes.
  • The table normally needs capacity of at least 64 before treeification.
  • When the bucket becomes small again, it may convert back to a linked structure.

The capacity requirement avoids creating tree structures too early. When the table is small, resizing may distribute the keys into different buckets more effectively.

5.5 Why equals and hashCode are critical

public class UserKey {

    private final Long tenantId;
    private final Long userId;

    @Override
    public boolean equals(Object other) {
        if (this == other) {
            return true;
        }

        if (!(other instanceof UserKey)) {
            return false;
        }

        UserKey that = (UserKey) other;

        return Objects.equals(tenantId, that.tenantId)
                && Objects.equals(userId, that.userId);
    }

    @Override
    public int hashCode() {
        return Objects.hash(tenantId, userId);
    }
}
If two objects are equal according to equals(), they must return the same hashCode().

5.6 Mutable keys are dangerous

Map<UserKey, String> map = new HashMap<>();

UserKey key = new UserKey(1L, 100L);
map.put(key, "Huy");

// If fields used by hashCode are changed here,
// map.get(key) may fail to find the entry.

The key may now calculate a different bucket index from the one used during insertion. Prefer immutable key objects.

5.7 Capacity, load factor, and resizing

The default load factor is normally 0.75. When the number of entries passes the threshold: 

threshold = capacity × loadFactor

HashMap creates a larger table, normally doubles the capacity, and redistributes entries. Resizing is relatively expensive, so choosing an appropriate initial capacity can help when the expected size is known. 

Map<Long, User> users = new HashMap<>(1_024);

5.8 Other important HashMap facts

  • HashMap is not thread-safe.
  • It permits one null key and multiple null values.
  • Iteration order is not guaranteed.
  • Use ConcurrentHashMap for common concurrent access patterns.
  • Use LinkedHashMap when stable insertion or access order is required.
  • Use TreeMap when sorted key order is required.

Senior interview answer

HashMap uses an array of buckets. It calculates a spread hash, derives the bucket index, and compares both hash and equals to find the key. Get and put are average O(1). Collisions place multiple entries in one bucket. In Java 8, a heavily-collided bucket may be converted from a linked list into a red-black tree, improving lookup in that bucket from O(n) to approximately O(log n). Correct equals/hashCode implementation and immutable keys are essential.

Review

6. Senior engineer checklist

Stream API

  • Explain source, intermediate, and terminal operations.
  • Know lazy evaluation and short-circuiting.
  • Compare stream readability with normal loops.
  • Do not claim parallel stream is always faster.
  • Avoid shared mutable state.

Optional

  • Use mainly as a return type.
  • Know orElse versus orElseGet.
  • Avoid get() without a clear guarantee.
  • Return empty collections instead of Optional collections.
  • Do not treat Optional as a replacement for every null.

Transactions

  • Choose a business transaction boundary.
  • Know default rollback rules.
  • Understand REQUIRED and REQUIRES_NEW.
  • Remember self-invocation and proxy behavior.
  • Do not keep DB transactions open during long API calls.

Resources

  • Use try-with-resources for AutoCloseable objects.
  • Know reverse close order.
  • Understand suppressed exceptions.
  • Do not manually close framework-managed resources.

HashMap

  • Average get/put is O(1).
  • Know collision behavior and treeification.
  • Explain equals/hashCode contract.
  • Avoid mutable keys.
  • Know it is not thread-safe.

Practical mindset

  • Prefer clarity over showing advanced syntax.
  • Measure performance instead of guessing.
  • Protect business invariants with DB constraints too.
  • Choose patterns based on failure behavior.
  • Explain trade-offs, not only definitions.
