3. Optional Deep Dive

Optional<T> represents a result that may intentionally contain no value. It does not make all code null-safe, and it is not a universal replacement for null.

3.1 What problem does Optional solve?

A method returning User does not tell the caller whether absence is expected. It may return a user, return null, or throw an exception. Returning Optional<User> makes expected absence part of the method contract. 

public Optional<User> findByEmail(String email) {
    return userRepository.findByEmail(email);
}

User user = userService.findByEmail(email)
    .orElseThrow(() -> new UserNotFoundException(email));

Good use

A lookup may validly produce no result and the caller should choose the next action: use a default, return 404, create a new resource, skip processing, or throw a domain exception.

Poor use

The value is mandatory and absence is a programming/data-integrity error. In that case, validate early and return the actual type or throw a meaningful exception.

3.2 Common operations

Optional<User> optional = userRepository.findById(id);

// Transform only when present
Optional<String> email =
    optional.map(User::getEmail);

// Continue with another Optional-returning operation
Optional<Address> address =
    optional.flatMap(user -> addressRepository.findPrimaryByUserId(user.getId()));

// Keep the value only when it matches
Optional<User> active =
    optional.filter(User::isActive);

// Lazy fallback
User result =
    optional.orElseGet(() -> createGuestUser(id));

// Explicit failure
User required =
    optional.orElseThrow(() -> new UserNotFoundException(id));

3.3 map versus flatMap

// map would create Optional<Optional<Address>>
Optional<Optional<Address>> nested =
    userOptional.map(user -> addressRepository.findByUserId(user.getId()));

// flatMap keeps one Optional layer
Optional<Address> flattened =
    userOptional.flatMap(user -> addressRepository.findByUserId(user.getId()));

3.4 orElse versus orElseGet

// loadFallback() executes even when optional contains a value
User a = optional.orElse(loadFallback());

// loadFallback() executes only when optional is empty
User b = optional.orElseGet(this::loadFallback);
Use orElseGet when the fallback performs I/O, object construction, logging, metrics, database work, or any non-trivial computation.

3.5 When should Optional be used in a real project?

Repository lookup

findById, findByEmail, or configuration lookup where no row is a normal result.

Parsing

A non-critical conversion can fail without throwing, such as parsing an optional header or query value.

Cache lookup

Useful at the API boundary, but avoid caching an Optional blindly unless negative caching is intentional.

Composable navigation

Navigate nullable nested objects without repeated temporary variables, provided the chain remains readable.

3.6 When should Optional usually not be used?

  • Entity fields: ORM mapping and proxy behavior become awkward; use nullable fields plus domain validation.
  • DTO fields: JSON serialization contracts become less clear; model required/nullable fields explicitly.
  • Method parameters: it forces callers to wrap values. Use overloads, a parameter object, or nullable annotation when justified.
  • Collections: return an empty collection instead of Optional<List<T>> in most cases.
  • Primitive values: prefer OptionalInt, OptionalLong, or OptionalDouble when boxing matters.
  • Internal fields for every nullable value: this adds allocations and complexity without improving the API contract.

3.7 Does Optional prevent NullPointerException?

It can reduce accidental null handling at a method boundary, but it does not guarantee NPE-free code. These examples can still fail: 

// Never return null instead of Optional.empty()
public Optional<User> findUser() {
    return null;
}

// of() rejects null
Optional<String> value = Optional.of(possiblyNull);

// map function itself may dereference null state inside the object
String city = userOptional
    .map(User::getAddress)
    .map(Address::getCity)
    .orElse("UNKNOWN");

Yes. Optional is one tool. Other approaches are often better depending on the domain.

3.9 Optional in Spring applications

@GetMapping("/users/{id}")
public ResponseEntity<UserResponse> getUser(@PathVariable long id) {
    return userService.findById(id)
        .map(userMapper::toResponse)
        .map(ResponseEntity::ok)
        .orElseGet(() -> ResponseEntity.notFound().build());
}

A service may convert the Optional into a domain exception instead, allowing a global exception handler to produce a consistent error response. 

@Transactional(readOnly = true)
public User getRequiredUser(long id) {
    return userRepository.findById(id)
        .orElseThrow(() -> new UserNotFoundException(id));
}

3.10 Optional performance and design concerns

Advantages

  • Absence becomes visible in the return type.
  • Encourages explicit fallback or failure handling.
  • Supports map/filter/flatMap composition.
  • Reduces repeated null-check boilerplate at boundaries.

Disadvantages

  • Can create unreadable chains.
  • Object Optional adds wrapper allocation conceptually, though JIT may optimize some cases.
  • Poor fit for JPA fields and many serialization contracts.
  • Misuse can hide bugs or replace a simple conditional with ceremony.

3.11 Deep Optional interview questions

DeepWhy is Optional mainly recommended as a return type?

A return type communicates that absence is an expected outcome controlled by the callee. As a parameter, Optional makes callers manufacture a wrapper and usually indicates that the method has two modes. Overloads or a request object are often clearer. As a field, Optional complicates persistence, serialization, frameworks, and object invariants.

DeepOptional or exception: how do you choose?

Use Optional when absence is a normal domain outcome and the caller owns the decision. Throw an exception when an invariant is violated or the operation cannot continue. For example, searchCustomer may return Optional, while loadCustomerForPayment should normally fail with a domain exception.

DeepWhy is Optional<List<T>> often a smell?

It introduces two empty states: Optional.empty and an empty List. Unless those states have different domain meanings, return an empty immutable collection. If they do have different meanings, model the states explicitly with a domain result type.

AdvancedCan Optional itself be null?

Technically a reference of type Optional can be null, but returning null violates the API convention and defeats the purpose. A method declaring Optional must return either Optional.of(value) or Optional.empty().

AdvancedWhy should Optional.get() usually be avoided?

It moves the failure to a generic NoSuchElementException and does not express the intended behavior. Prefer orElseThrow with a meaningful exception, or use map, flatMap, and fallback methods.

HTTP/3 uses QUIC over UDP and can reduce some transport-level head-of-line blocking and improve connection behavior on changing networks. Adoption still depends on server, proxy, firewall, observability, and infrastructure support.

A Senior engineer should not assume that changing the protocol version automatically improves application latency. Measure DNS, TLS/QUIC handshake behavior, payload size, server processing, packet loss, and fallback behavior.

Ahead-of-Time object caching

AOT object caching extends startup and warm-up optimization by allowing suitable object graphs to be restored rather than recreated during every startup. This is relevant to command-line tools, serverless workloads, short-lived containers, and large frameworks.

Applet API removed

This completes removal of a legacy browser deployment model. Migration means replacing applets with modern web applications, desktop packaging, or service-based architectures.

Preview features remain preview

Lazy constants and structured concurrency are preview features in Java 26. They require preview flags and may change in later releases.

Ask deeper: Why can HTTP/3 be blocked by enterprise infrastructure? What is the difference between AOT class loading, method profiling, and object caching? Why should a team avoid exposing preview APIs in a public library?

6. Deep Feature Interview Questions

These questions are designed to distinguish syntax knowledge from production experience.

Java 8Why must a reduction function be associative for parallel streams?

A parallel stream partitions data and combines partial results in an order that may differ from sequential encounter order. If the operation is not associative, regrouping changes the result. Subtraction and floating-point accumulation are common examples where order matters.

Java 8How can CompletableFuture cause thread starvation?

Async methods without an explicit executor commonly use the common ForkJoinPool. Blocking database or network calls occupy workers intended for fork/join computation. In a server, use an appropriately sized executor or a non-blocking client, and define timeout, cancellation, rejection, metrics, and context propagation.

Java 9Classpath versus module path: what changes?

The classpath places code largely in an unnamed module with traditional package visibility. The module path resolves named modules with explicit readability and exports. Reflection into non-open packages can fail even when classes are public.

Java 10Can var change overload resolution or runtime behavior?

var is compile-time syntax. However, the inferred static type can affect which methods are accessible and later overload resolution. It can also infer a concrete implementation or intersection type that is not obvious to readers.

Java 11When would you not use the standard HttpClient?

A framework client may provide stronger integration for connection pooling, service discovery, observability, declarative APIs, resilience, codecs, or reactive backpressure. The choice depends on platform standards and operational requirements, not only API simplicity.

RecordsAre records immutable?

Record component fields are final and component references cannot be reassigned, but referenced objects can still be mutable. A record containing a mutable List is only shallowly immutable unless it creates a defensive copy. 

public record Team(List<String> members) {
    public Team {
        members = List.copyOf(members);
    }
}
RecordsShould records be used as JPA entities?

Usually not as normal mutable entities. JPA traditionally expects entity identity, lifecycle mutation, a no-argument constructor, and sometimes proxies. Records work better as DTOs, projections, events, keys, and immutable domain values. Framework/version support must be verified.

SealedSealed hierarchy versus enum: how do you choose?

An enum has a fixed set of instances of one type and is ideal for simple named constants. A sealed hierarchy has a fixed set of subtypes, each with different state and behavior. Use sealed types for richer variant-specific data.

Pattern matchingCan pattern switch replace polymorphism?

Sometimes. Pattern switch is excellent for external operations over a closed hierarchy. Polymorphism is often better when behavior belongs naturally inside each subtype. Excessive switching across many services may indicate an anemic model.

Virtual threadsDo virtual threads remove the need for reactive programming?

No. Virtual threads make imperative blocking code scale much better for many I/O workloads. Reactive systems still provide explicit backpressure, streaming composition, event-loop integration, and mature reactive libraries. The best model depends on workload, team skill, latency, and ecosystem.

Virtual threadsWhy can the database still become the bottleneck?

Virtual threads increase the number of waiting tasks but do not increase database connections, transaction throughput, locks, CPU, IOPS, or downstream quotas. A bounded connection pool and explicit admission control are still necessary.

Virtual threadsWhat is pinning?

A virtual thread is normally unmounted from its carrier when blocking. In some operations, especially blocking while holding certain monitor/native states, it can remain attached to the carrier. Excessive pinning reduces scalability. Use JFR and diagnostics instead of guessing.

Scoped valuesWhy not keep using ThreadLocal?

ThreadLocal is mutable, can leak across pooled threads if cleanup is missed, and makes lifetime difficult to reason about. Scoped values are immutable bindings limited to a lexical/dynamic scope, which better matches structured concurrency and virtual-thread task lifetimes.

FFMDoes FFM make native calls safe?

It improves Java-side safety with typed layouts, bounds checks, and controlled lifetimes. Native functions can still corrupt memory, violate ABI expectations, block indefinitely, or expose security vulnerabilities. Native integration still needs isolation and testing.

GatherersWhen is a loop better than a Gatherer?

A one-off stateful algorithm is often clearer as a loop. A Gatherer is justified when the operation is reusable, composes naturally with Streams, and its sequential/parallel behavior is well tested.

MigrationHow do you upgrade Java 8 to 17 or 21 safely?

Inventory runtime and dependencies, update build tools, run tests on the target JDK, replace removed modules, inspect illegal reflective access, update containers and observability agents, benchmark GC/startup/latency, canary deploy, and retain rollback. Compile target and runtime target should be controlled independently when gradual rollout is needed.

PreviewWould you use a preview feature in production?

Usually avoid it for core production or public libraries because source and binary behavior may change, preview flags are required at compile and runtime, and ecosystem tooling may lag. It can be reasonable for controlled experiments with explicit risk acceptance and no public compatibility commitment.

JVMWhy can a newer JDK improve performance without code changes?

Newer JDKs include JIT, GC, class-data sharing, allocation, startup, intrinsic, and platform improvements. Results are workload-specific. A Senior validates throughput, p95/p99 latency, memory, startup, CPU, GC pauses, and container behavior before claiming improvement.

  1. Inventory: JDK vendor, runtime flags, frameworks, agents, native libraries, build plugins, reflection, removed Java EE APIs.
  2. Upgrade build chain: Maven/Gradle, compiler, test plugins, coverage, static analysis, annotation processors.
  3. Upgrade dependencies: especially Spring, Hibernate, bytecode libraries, logging, mocking, application servers, JDBC drivers.
  4. Run on the target JDK before using new syntax: separate runtime migration from language-feature adoption when possible.
  5. Test behavior: unit, integration, contract, security, serialization, timezone, charset, reflection, TLS, and native integration.
  6. Benchmark: throughput, p95/p99 latency, startup, RSS/heap, allocation, GC, CPU, thread counts, and connection pools.
  7. Canary and rollback: deploy a small percentage, compare telemetry, retain the previous image and database compatibility.

Senior answer: “I first make the application run unchanged on the target JDK, then adopt features. That separates compatibility risk from refactoring risk. 8. What Is the Stream API?

A Stream is a one-use pipeline for processing a sequence of elements. It does not store data. Its source is usually a Collection, array, generator, or I/O source.

7.1 Pipeline structure

Source → Intermediate Operations → Terminal Operation

List<String> emails = employees.stream()
    .filter(Employee::isActive)
    .map(Employee::getEmail)
    .filter(Objects::nonNull)
    .map(email -> email.toLowerCase(Locale.ROOT))
    .distinct()
    .sorted()
    .collect(Collectors.toList()); // Java 8
  • Source: supplies elements.
  • Intermediate operation: returns another Stream and is normally lazy.
  • Terminal operation: triggers execution and produces a result or side effect.

7.2 Why Streams are useful

Declarative processing

Express the transformation rather than manually managing indexes, temporary variables, and loop state.

Composition

Reusable predicates, functions, comparators, and collectors can be combined into readable business pipelines.

Lazy execution

Work is performed only when a terminal operation needs it, enabling fusion and short-circuiting.

Parallel capability

The API can partition work, but safe and useful parallelism requires the correct workload and stateless operations.

7.3 Lazy evaluation

Optional<String> first = names.stream()
    .filter(name -> {
        System.out.println("filter " + name);
        return name.length() > 3;
    })
    .map(name -> {
        System.out.println("map " + name);
        return name.toUpperCase(Locale.ROOT);
    })
    .findFirst();

The pipeline processes only enough elements to satisfy findFirst. It does not necessarily filter the entire input and then map a second complete list.

7.4 Streams are one-use

Stream<String> stream = names.stream();
long count = stream.count();

// IllegalStateException: the stream has already been consumed
List<String> values = stream.collect(Collectors.toList());

7.5 Stateless and stateful operations

TypeExamplesImplication
Statelessmap, filter, peekEach element can normally be processed independently.
Statefulsorted, distinct, limit in ordered parallel processingMay buffer data or coordinate across elements.
Short-circuitingfindFirst, anyMatch, limitMay stop without consuming the full source.

7.6 Side effects

// Unsafe with a parallel stream
List<String> result = new ArrayList<>();
names.parallelStream().forEach(result::add);

// Correct reduction
List<String> result = names.parallelStream()
    .collect(Collectors.toList());

Side effects make the pipeline harder to reason about, test, retry, and parallelize. Prefer returning values and using collectors.

Senior answer: “Streams are most valuable when the problem is a data-transformation pipeline. They reduce mutable state and support lazy composition. I avoid them when the algorithm needs complex state transitions, indexes, early control flow, checked-exception-heavy logic, or business side effects.”

8.2 Prefer a Stream when

  • The operation is naturally filter → transform → group/reduce.
  • Each stage is mostly stateless and side-effect free.
  • The pipeline communicates the business rule more clearly than loop mechanics.
  • You need collectors such as grouping, partitioning, joining, or summarizing.

8.3 Prefer a loop when

  • You need break, continue, mutation, retry, or index manipulation.
  • The logic has several state transitions or dependent branches.
  • You must perform ordered side effects with explicit error handling.
  • The code is a measured hot path and allocation/boxing overhead matters.
Senior answer: “I choose based on clarity and behavior, not fashion. A Stream is not automatically more efficient, and a loop is not automatically less maintainable. The better choice is the one that exposes the algorithm and failure handling most clearly.”

10. Is a Stream Always O(n)?

No. Complexity is determined by the operations and how much of the source must be consumed.

OperationTypical complexityNotes
filter / mapO(n)One pass through consumed elements.
findFirst / anyMatchBest O(1), worst O(n)Short-circuits when possible.
limit(k)Approximately O(k)Unless an earlier stateful operation requires more work.
distinctAverage O(n)Normally uses hash-based state and O(n) additional memory.
sortedO(n log n)Usually needs all elements before emitting sorted output.
groupingByAverage O(n)Depends on map operations and downstream collectors.
nested searchOften O(n × m)A Stream does not remove nested-algorithm complexity.

9.1 Big-O is not the full performance story

Two O(n) implementations can have very different throughput because of allocation, boxing, branch prediction, cache locality, JIT optimization, GC pressure, and data shape. 

// Boxing occurs
int sum = numbers.stream()
    .map(number -> number * 2)
    .reduce(0, Integer::sum);

// Primitive specialization avoids Integer boxing
int sum = numbers.stream()
    .mapToInt(Integer::intValue)
    .map(number -> number * 2)
    .sum();

9.2 Do not guess—benchmark correctly

Use JMH for microbenchmarks. Include warm-up, multiple forks, realistic data, dead-code prevention, and avoid treating a microbenchmark as a production load test.

11. How HashMap Works Internally

HashMap uses an array of buckets. A bucket can be empty, a linked list of nodes, or a red-black tree when collisions become heavy and the table is large enough. 

transient Node<K,V>[] table;

static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;
    final K key;
    V value;
    Node<K,V> next;
}

10.1 put(key, value)

  1. Obtain the key's hash code; null uses hash zero.
  2. Spread higher bits into lower bits.
  3. Calculate the bucket index using (capacity - 1) & hash.
  4. If the bucket is empty, insert a new node.
  5. Otherwise compare hash and then equals.
  6. Update an existing key or append/insert a collision node.
  7. Treeify a heavily collided bucket when thresholds permit.
  8. Resize when size exceeds the threshold.
int spread = hashCode ^ (hashCode >>> 16);
int index = (capacity - 1) & spread;

10.2 Why power-of-two capacity?

It allows a fast bit mask instead of modulo and supports an efficient resize: an entry often stays at its old index or moves to oldIndex + oldCapacity.

10.3 Load factor and resize

threshold = capacity * loadFactor

The common load factor is 0.75, balancing memory and collision probability. A resize is O(n), but insertion is O(1) amortized because resize does not occur for every put.

10.4 Treeification thresholds in Java 8

  • TREEIFY_THRESHOLD = 8
  • UNTREEIFY_THRESHOLD = 6
  • MIN_TREEIFY_CAPACITY = 64

When the table is still small, resizing is preferred over treeification because a larger table may distribute the colliding entries into separate buckets.

10.5 Complexity

OperationAverageImportant qualification

removeO(1) averageCollision structure affects bucket work.

10.6 equals and hashCode contract

  • If two objects are equal, they must have the same hash code.
  • The same hash code does not imply equality.
  • Fields used by equals/hashCode should not change while the object is a map key.
EmployeeKey key = new EmployeeKey(1001, "VN");
map.put(key, employee);

// Dangerous when country participates in equals/hashCode
key.setCountry("JP");

// Lookup can now fail because the node remains in the old bucket
Employee value = map.get(key);

10.7 Nulls and thread safety

HashMap permits one null key and multiple null values. It is not thread-safe. For shared concurrent mutation, use a concurrent design such as ConcurrentHashMap, immutability, confinement, or explicit locking.

Senior answer: “HashMap is O(1) on average, not guaranteed. Its behavior depends on hash quality, capacity, load factor, resize, collisions, and key immutability. In Java 8, heavily collided buckets can become red-black trees to improve lookup behavior.”

13. How to Use Try-with-resources

Try-with-resources deterministically closes objects implementing AutoCloseable or Closeable.

12.1 File example

try (BufferedReader reader =
         Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
    return reader.readLine();
}

12.2 JDBC example

try (
    Connection connection = dataSource.getConnection();
    PreparedStatement statement =
        connection.prepareStatement(
            "SELECT id, email FROM users WHERE status = ?"
        )
) {
    statement.setString(1, "ACTIVE");

    try (ResultSet resultSet = statement.executeQuery()) {
        while (resultSet.next()) {
            process(resultSet);
        }
    }
}

Resources close in reverse declaration order.

12.3 Suppressed exceptions

If the business body throws and close() also throws, the body exception remains primary and close failures are available through getSuppressed(). 

catch (Exception exception) {
    log.error("Primary failure", exception);
    for (Throwable suppressed : exception.getSuppressed()) {
        log.error("Resource close failure", suppressed);
    }
}

12.4 Custom resource

public final class AuditSession implements AutoCloseable {
    private boolean closed;

    public void write(String event) {
        if (closed) {
            throw new IllegalStateException("Session is closed");
        }
        // write event
    }

    @Override
    public void close() {
        closed = true;
    }
}

try (AuditSession session = new AuditSession()) {
    session.write("USER_LOGIN");
}
Senior answer: “The benefit is not only shorter code. It gives deterministic lifecycle management, reverse-order closing, and correct preservation of close failures as suppressed exceptions.”

16. Concurrent Collections

15.1 ConcurrentHashMap

ConcurrentMap<String, Session> sessions =
    new ConcurrentHashMap<>();

Session session = sessions.computeIfAbsent(
    token,
    this::loadSession
);

Java 8 ConcurrentHashMap combines lock-free/CAS techniques with synchronization at a finer granularity when needed. Reads are designed for high concurrency.

A computeIfAbsent mapping function should be short and should avoid slow blocking work or recursive updates to the same map.

15.2 CopyOnWriteArrayList

Excellent for small lists with many reads, very few writes, and snapshot iteration. Every write copies the backing array, making write cost O(n).

15.3 BlockingQueue

BlockingQueue<Task> queue =
    new ArrayBlockingQueue<>(1_000);

queue.put(task);      // producer
Task next = queue.take(); // consumer

A bounded queue provides basic backpressure. Capacity, producer behavior, consumer count, shutdown, poison messages, and retry policy still need design.

15.4 Synchronized wrappers

List<String> values =
    Collections.synchronizedList(new ArrayList<>());

synchronized (values) {
    for (String value : values) {
        process(value);
    }
}

Iteration requires external synchronization on the wrapper.

15.5 Concurrent collection does not make the workflow atomic

// Check-then-act race, even if the map methods are thread-safe
if (!sessions.containsKey(token)) {
    sessions.put(token, loadSession(token));
}

// Atomic map operation
sessions.computeIfAbsent(token, this::loadSession);

17. Real Project Cases

16.1 Replace O(n × m) lookup with O(n + m)

// Expensive nested search
for (Order order : orders) {
    Customer customer = customers.stream()
        .filter(c -> c.getId().equals(order.getCustomerId()))
        .findFirst()
        .orElse(null);
}

// Build an index once
Map<Long, Customer> customerById = customers.stream()
    .collect(Collectors.toMap(
        Customer::getId,
        Function.identity()
    ));

for (Order order : orders) {
    Customer customer = customerById.get(order.getCustomerId());
}

16.2 Batch deduplication

Set<String> seen = new HashSet<>();
List<ValidationError> errors = new ArrayList<>();

for (ImportRow row : rows) {
    String email = normalize(row.getEmail());
    if (!seen.add(email)) {
        errors.add(new ValidationError(
            row.getLineNumber(),
            "DUPLICATE_EMAIL"
        ));
    }
}

16.3 Grouping and aggregation

Map<String, BigDecimal> amountByMerchant =
    transactions.stream()
        .filter(Transaction::isSuccessful)
        .collect(Collectors.groupingBy(
            Transaction::getMerchantId,
            Collectors.reducing(
                BigDecimal.ZERO,
                Transaction::getAmount,
                BigDecimal::add
            )
        ));

16.4 Do not use parallelStream as an API-call concurrency policy

// Risky server code
List<Profile> profiles = users.parallelStream()
    .map(user -> remoteClient.loadProfile(user.getId()))
    .collect(Collectors.toList());
  • Uses the common ForkJoinPool by default.
  • Blocking I/O consumes workers.
  • Concurrency is not aligned with rate limits or connection pools.
  • Timeout, tracing, cancellation, and partial failure are harder to control.

16.5 Avoid persistence side effects hidden in Stream stages

// Misleading and difficult to recover
orders.stream()
    .peek(orderRepository::save)
    .forEach(notificationService::send);

// More explicit
for (Order order : orders) {
    orderRepository.save(order);
    notificationService.send(order);
}

For database plus messaging, also consider transaction boundaries, idempotency, retry, and an outbox pattern.

18. Java 8 & Collections Interview Q&A

1. Stream versus Collection?

A Collection stores reusable data. A Stream is a one-use, usually lazy processing pipeline over a source.

2. map versus flatMap?

map transforms one element into one result. flatMap transforms an element into a Stream-like container and flattens nested results.

Stream<String> tags =
    posts.stream()
        .flatMap(post -> post.getTags().stream());
3. reduce versus collect?

reduce is suitable for immutable combination into a value; collect is designed for mutable reduction into containers such as List, Map, or StringBuilder.

4. Why should parallel reduction be associative?

Parallel partitions may be combined in different groupings. Non-associative operations can produce different results depending on partitioning and order.

5. When is parallelStream useful?

For sufficiently large, CPU-bound, splittable, stateless work with associative reductions. It is usually a poor default for blocking I/O or request-sized data.

6. Why is peek not a business side-effect API?

It is mainly for observation/debugging. Lazy execution and short-circuiting mean it may not run for every source element.

7. How does HashSet work internally?

It is backed by a HashMap: the set element is stored as the key and a shared dummy object is stored as the value.

8. Why is a mutable HashMap key dangerous?

Changing fields used by equals/hashCode changes the logical bucket while the node remains in the original bucket, so lookup and removal can fail.

9. ArrayList versus LinkedList?

ArrayList is normally the default because of O(1) random access, low per-element overhead, and good locality. LinkedList's O(1) insertion applies only when the node position is already known.

10. Why can LinkedList be slow despite O(1) insertion?

Finding the position is usually O(n), and each node adds allocation, pointers, and poor CPU cache locality.

11. TreeMap versus HashMap?

TreeMap maintains sorted keys with O(log n) operations and range/navigation APIs. HashMap provides average O(1) key access without sorted order.

12. Comparable versus Comparator?

Comparable defines one natural ordering in the type. Comparator defines external, reusable orderings and supports multiple sort strategies.

13. What is a fail-fast iterator?

It detects certain structural modifications and may throw ConcurrentModificationException. It is best-effort bug detection, not a thread-safety guarantee.

14. How do you remove during iteration? 
Iterator<Order> iterator = orders.iterator();
while (iterator.hasNext()) {
    if (iterator.next().isExpired()) {
        iterator.remove();
    }
}

For simple predicates, orders.removeIf(Order::isExpired) is clearer.

15. Unmodifiable view versus immutable copy?

An unmodifiable view may reflect changes to its mutable backing collection. A defensive immutable copy is independent of later source mutation.

16. Why does ConcurrentHashMap reject null?

In concurrent lookup, null would be ambiguous between “no mapping” and “a mapping whose value is null,” making atomic APIs harder to define safely.

17. How do you pre-size a HashMap? 
int expectedSize = 1_000;
Map<String, User> map =
    new HashMap<>((int) (expectedSize / 0.75f) + 1);

Pre-sizing can reduce resize work, but excessive capacity increases memory use and iteration cost.

18. What collection should implement top K?

Use a PriorityQueue of size K. Processing n items costs O(n log K), which is better than sorting all n values when K is small.

19. Why return an empty collection instead of null?

It provides one consistent zero-result state and allows callers to iterate without null checks. Distinguish “not loaded” separately if the domain requires it.

20. Which collections do you use most in projects?
Sample answer: “ArrayList is my default List. I use HashMap for lookup and in-memory joins, HashSet for deduplication, LinkedHashMap when encounter order matters, ArrayDeque for queues, PriorityQueue for scheduling/top K, and concurrent collections only when ownership cannot be confined. I choose based on access pattern, ordering, uniqueness, concurrency, memory, and failure behavior.”

19. Common Mistakes

Using Streams everywhere

Long nested pipelines with state and side effects are harder to maintain than a clear loop.

Nested Stream lookup

Searching a second list for every element creates O(n × m) behavior; build an index Map.

parallelStream for remote I/O

The common pool is not a rate limiter, connection pool, timeout policy, or bulkhead.

Ignoring duplicate toMap keys

A duplicate key throws unless a merge function defines the domain rule.

Mutable map keys

Changing equality fields after insertion can make entries unreachable.

Choosing LinkedList from Big-O alone

Traversal, allocation, and cache locality usually dominate.

Returning null Optional

An Optional-returning method must return Optional.empty, never null.

Using Optional.get

It hides the intended failure or fallback behavior behind a generic exception.

Not closing resources

Connection and file leaks cause pool exhaustion and production instability.

Using preview features as stable APIs

Preview source and bytecode require flags and may change in later releases.
