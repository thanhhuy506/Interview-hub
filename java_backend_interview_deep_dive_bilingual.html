Q1Payment & Traffic Protection

How does adding a credit card work, and how do you secure card information?Luồng add credit card hoạt động thế nào và bảo vệ thông tin thẻ ra sao?

Interview answer
Câu trả lời phỏng vấn
A strong design avoids letting the backend store raw card data. The frontend sends card details directly to a PCI-compliant PSP/tokenization endpoint over TLS. The PSP returns a token/payment-method ID; our backend stores only that token plus non-sensitive metadata such as brand and last4. For higher-risk payments, 3-D Secure can add cardholder authentication.
Thiết kế tốt nhất là backend không lưu dữ liệu thẻ thô. Frontend gửi card number/CVV trực tiếp tới PSP hoặc tokenization endpoint đạt PCI qua TLS. PSP trả về token/payment-method ID; backend chỉ lưu token cùng metadata không nhạy cảm như brand và last4. Với giao dịch cần xác thực mạnh, có thể dùng 3-D Secure.
Deep dive / internal workGiải thích sâu / internal work
Typical flow
  1. User enters PAN/expiry/CVV into PSP-hosted fields or a PSP SDK.
  2. Browser/app → PSP through TLS. Raw card data should not pass through ordinary application logs or databases.
  3. PSP validates/tokenizes the card and returns a reusable token or payment-method ID.
  4. Application backend associates that token with the authenticated customer.
  5. On payment, backend sends token + amount + merchant order/payment ID to PSP.
  6. PSP talks to acquiring bank → card network → issuing bank.
  7. If required, 3DS challenge/authentication happens before authorization/capture.
Security controls: TLS, tokenization, strict secrets management, log masking, least privilege, network segmentation, CSP/secure frontend integration, idempotency, audit logs, webhook signature validation, PCI-DSS scope minimization. Never store CVV. If storing PAN is unavoidable, use a dedicated PCI vault/HSM-backed encryption model rather than normal application tables.
Luồng điển hình
  1. User nhập PAN/expiry/CVV qua hosted field hoặc SDK của PSP.
  2. Browser/app → PSP qua TLS. Dữ liệu thẻ thô không nên đi qua log/database thông thường của hệ thống.
  3. PSP validate và tokenize, trả reusable token/payment-method ID.
  4. Backend map token đó với customer đang đăng nhập.
  5. Khi charge, backend gửi token + amount + merchant order/payment ID tới PSP.
  6. PSP giao tiếp acquiring bank → card network → issuing bank.
  7. Nếu cần, 3DS thực hiện authentication trước authorization/capture.
Control quan trọng: TLS, tokenization, secret management, mask log, least privilege, network segmentation, idempotency, audit log, verify webhook signature, giảm PCI scope. Tuyệt đối không lưu CVV. Nếu bắt buộc lưu PAN thì cần card vault chuyên dụng và encryption/HSM thay vì table application thông thường.

Q2Payment & Traffic Protection

What do you do when a payment transaction fails?Payment transaction fail thì xử lý như thế nào?

Interview answer
Câu trả lời phỏng vấn
Model payment as a state machine, persist every attempt, use idempotency, and distinguish a definite failure from an unknown result. A timeout is not necessarily a failure: query the PSP by merchant payment ID or reconcile through webhook before retrying.
Nên model payment bằng state machine, lưu từng attempt, dùng idempotency và phân biệt “fail chắc chắn” với “chưa biết kết quả”. Timeout không đồng nghĩa fail: cần query PSP bằng merchant payment ID hoặc reconcile qua webhook trước khi retry.
Deep dive / internal workGiải thích sâu / internal work
Useful states: CREATED → PENDING → AUTHORIZED → CAPTURED; or FAILED / CANCELED / REFUNDED. Add UNKNOWN or PROCESSING for ambiguous network outcomes.

Classification:
  • Hard decline (invalid card, stolen card, do-not-honor): normally do not blindly retry; ask user for another method.
  • Soft/transient failure (timeout, 502, temporary issuer unavailable): safe retry only with the same idempotency key and bounded backoff.
  • Ambiguous timeout: first query PSP/status endpoint or wait for signed webhook. Never create a new independent charge immediately.
Reconciliation: scheduled job compares local payment records with PSP settlement/status data; fixes missing webhooks and raises alerts for mismatches. Business order state changes only after a confirmed payment state.
State nên có: CREATED → PENDING → AUTHORIZED → CAPTURED; hoặc FAILED / CANCELED / REFUNDED. Có thể thêm UNKNOWN/PROCESSING cho case network không rõ kết quả.

Phân loại lỗi:
  • Hard decline: thường không retry mù, yêu cầu user đổi payment method.
  • Lỗi tạm thời: timeout/502/issuer unavailable có thể retry có giới hạn, backoff và giữ nguyên idempotency key.
  • Timeout không rõ kết quả: query PSP/status hoặc chờ signed webhook. Không tạo charge mới ngay.
Reconciliation: batch/job định kỳ so local payment với PSP để bù webhook bị mất và cảnh báo mismatch. Chỉ chuyển business order sang paid khi payment đã confirm.
Code / Example
enum PaymentStatus {
    CREATED, PENDING, AUTHORIZED, CAPTURED,
    FAILED, CANCELED, REFUNDED, UNKNOWN
}

@Transactional
public PaymentResult pay(PayCommand cmd) {
    Payment p = repo.findByOrderId(cmd.orderId())
        .orElseGet(() -> repo.save(Payment.create(cmd.orderId())));

    // idempotent business check
    if (p.getStatus() == PaymentStatus.CAPTURED) {
        return PaymentResult.alreadyPaid(p.getPspId());
    }

    try {
        PspResponse r = psp.charge(cmd, p.getIdempotencyKey());
        p.apply(r); // map PSP status to local state
    } catch (SocketTimeoutException ex) {
        p.markUnknown(); // NOT failed
        reconciliationQueue.enqueue(p.getId());
    }
    return PaymentResult.from(p);
}
Interview pitfall: The dangerous answer is “if payment fails, retry 3 times.” Retrying without knowing whether the first request reached the PSP can double-charge the customer.
Lưu ý phỏng vấn: Câu trả lời nguy hiểm là “fail thì retry 3 lần”. Nếu request đầu đã tới PSP nhưng response bị mất, retry bằng transaction mới có thể double charge.
Likely follow-up: How would you design idempotency for payment APIs?
Câu hỏi đào sâu có thể gặp: Bạn thiết kế idempotency cho payment API như thế nào?
Q3Payment & Traffic Protection

If a user sends 10,000 attach-billing requests, how do you protect the system?Nếu user gửi 10,000 request attach billing thì bảo vệ hệ thống thế nào?

Interview answer
Câu trả lời phỏng vấn
Protect at multiple layers: authenticate, rate-limit per identity/tenant/IP, validate request size, use idempotency, bound concurrency, apply backpressure, isolate downstream resources, and reject excess traffic early. Do not let 10,000 HTTP requests become 10,000 concurrent DB/PSP calls.
Bảo vệ nhiều lớp: authentication, rate limit theo user/tenant/IP, validate request, idempotency, giới hạn concurrency, backpressure, bulkhead cho downstream và reject traffic dư càng sớm càng tốt. Không để 10,000 HTTP request biến thành 10,000 DB/PSP call đồng thời.
Deep dive / internal workGiải thích sâu / internal work
Layered protection:
  1. CDN/WAF/API Gateway: bot protection, IP/user quota, payload limits.
  2. Service: authorization + per-customer idempotency key + concurrency semaphore/bulkhead.
  3. Queue (when asynchronous business flow is acceptable): accept a bounded amount, return 202, process at controlled rate.
  4. DB: unique constraint for duplicate billing attachment, proper pool size, short transactions.
  5. Downstream PSP: separate rate limiter/circuit breaker so your service does not overload the provider.
Important: rate limit should be based on business identity, not only IP. One corporate NAT can represent many real users, while one attacker can rotate IPs.
Bảo vệ theo layer:
  1. CDN/WAF/API Gateway: chống bot, quota theo IP/user, giới hạn payload.
  2. Service: authorization + idempotency key theo customer + semaphore/bulkhead giới hạn concurrency.
  3. Queue nếu business cho phép async: chỉ accept bounded amount, trả 202, worker xử lý theo tốc độ kiểm soát.
  4. DB: unique constraint để chống duplicate attach billing, pool hợp lý, transaction ngắn.
  5. PSP/downstream: rate limiter/circuit breaker riêng để không overload provider.
Lưu ý: chỉ limit theo IP là chưa đủ; nên ưu tiên principal/customer/tenant/API key.

Q4Payment & Traffic Protection

How do you calculate and configure a rate limit such as 10,000 requests/minute?Tính và cấu hình rate limit 10,000 request/phút như thế nào?

Interview answer
Câu trả lời phỏng vấn
10,000 requests/minute is about 166.7 requests/second on average. But the correct limit comes from measured system capacity and business policy, not an arbitrary number. Decide steady rate, burst capacity, scope, and rejection behavior.
10,000 request/phút tương đương khoảng 166.7 request/giây trung bình. Nhưng limit đúng phải dựa trên capacity đo được và business policy, không chọn số tùy ý. Cần quyết định steady rate, burst capacity, scope và cách reject.
Deep dive / internal workGiải thích sâu / internal work
Capacity approach:
  1. Load-test one instance and find a safe sustainable throughput at target latency/error rate.
  2. Multiply by healthy instance count, then reserve headroom (for GC, DB spikes, instance loss, deployments).
  3. Check the narrowest downstream capacity: DB pool, PSP quota, CPU, queue consumers.
  4. Split the global budget into tenant/user/API-key budgets and burst allowance.
Example: 4 instances × safe 60 RPS = 240 RPS. Reserve ~30% headroom ⇒ ~168 RPS ≈ 10,080/min. A 10,000/min cap is therefore reasonable only if DB and downstream services also sustain it.

Algorithms: fixed window (simple but boundary burst), sliding window (more accurate), token bucket (best common choice for steady rate + burst), leaky bucket (smooth output).
Cách tính theo capacity:
  1. Load test 1 instance, tìm throughput an toàn tại latency/error rate mục tiêu.
  2. Nhân số instance healthy rồi chừa headroom cho GC, spike DB, mất instance, deployment.
  3. Kiểm tra bottleneck nhỏ nhất: DB pool, PSP quota, CPU, queue consumer.
  4. Chia global budget thành tenant/user/API-key budget và burst allowance.
Ví dụ: 4 instance × 60 RPS an toàn = 240 RPS. Chừa khoảng 30% headroom ⇒ ~168 RPS ≈ 10,080/min. Do đó 10,000/min chỉ hợp lý nếu DB/downstream cũng chịu được.

Algorithm: fixed window, sliding window, token bucket, leaky bucket. Token bucket thường dễ dùng vì vừa giới hạn tốc độ trung bình vừa cho phép burst.

Q5Payment & Traffic Protection

What happens if the limit is 10,000/min but traffic reaches 20,000/min?Limit 10,000/phút nhưng traffic lên 20,000/phút thì xử lý sao?

Interview answer
Câu trả lời phỏng vấn
The limiter admits traffic according to its algorithm and rejects or delays the excess. For a strict 10,000/minute quota, roughly half of a sustained 20,000/minute stream will be rejected with HTTP 429. With token-bucket burst capacity, a short spike may be temporarily absorbed, but sustained overload is still rejected.
Rate limiter chỉ cho qua lượng traffic theo rule và reject hoặc delay phần dư. Với quota strict 10,000/phút, traffic duy trì 20,000/phút thì xấp xỉ một nửa sẽ bị 429. Token bucket có burst capacity có thể hấp thụ spike ngắn, nhưng overload kéo dài vẫn phải reject.
Deep dive / internal workGiải thích sâu / internal work
Recommended behavior:
  • Return 429 Too Many Requests with Retry-After when the caller may safely retry.
  • Protect expensive dependencies before they are called.
  • For asynchronous non-interactive workloads, optionally enqueue within a strict bounded queue and return 202.
  • Use priority: critical payment/status callbacks should not share the exact same quota as low-priority reporting APIs.
  • Autoscaling helps only if downstream dependencies also scale; otherwise it can make DB/PSP overload worse.
Client: exponential backoff + jitter; honor Retry-After; keep idempotency key when retrying write/payment operations.
Cách xử lý nên có:
  • Trả 429 Too Many Requests + Retry-After nếu client có thể retry an toàn.
  • Chặn trước khi gọi DB/PSP đắt tiền.
  • Workload async có thể enqueue vào bounded queue và trả 202.
  • Tách quota theo priority; callback payment quan trọng không nên dùng chung quota với API report.
  • Autoscaling chỉ hữu ích nếu downstream cũng scale; nếu không có thể làm DB/PSP chết nhanh hơn.
Client: exponential backoff + jitter, honor Retry-After, giữ idempotency key khi retry write/payment.

Q6Java Core & JVM

Explain Java Core, JVM, stack, heap and GC.Giải thích Java Core, JVM, stack, heap và GC.

Interview answer
Câu trả lời phỏng vấn
Each Java process runs on a JVM. Every thread has its own stack; objects normally live on the shared heap. GC automatically finds heap objects that are no longer reachable and reclaims their memory. The JVM also has non-heap areas such as Metaspace and native memory.
Mỗi Java process chạy trên JVM. Mỗi thread có stack riêng; object thường nằm trên heap dùng chung. GC tìm các object trên heap không còn reachable để thu hồi memory. JVM còn có vùng non-heap như Metaspace và native memory.
Deep dive / internal workGiải thích sâu / internal work
Stack: per-thread frames: local primitives, references, operand stack, return information. Fast allocation/deallocation as methods enter/return. Deep recursion can cause StackOverflowError.

Heap: shared object graph, arrays, many runtime structures. If live objects cannot fit in configured heap, you can get OutOfMemoryError: Java heap space.

Metaspace: class metadata in native memory. Classloader leaks can cause OutOfMemoryError: Metaspace.

GC: starts from GC roots (thread stacks, static references, JNI roots, etc.), traces reachable objects, reclaims unreachable ones. Modern collectors try to balance throughput and pause time. Allocation itself is often very cheap; the expensive part is retaining too much live data and forcing frequent/large collections.
Stack: mỗi thread có các frame chứa local primitive, reference, operand stack, return info. Method return thì frame pop rất nhanh. Recursion sâu có thể StackOverflowError.

Heap: dùng chung, chứa object/array. Nếu live object không fit heap cấu hình thì có OutOfMemoryError: Java heap space.

Metaspace: class metadata nằm native memory. Classloader leak có thể gây OOM Metaspace.

GC: bắt đầu từ GC roots, trace object còn reachable và reclaim object không reachable. Collector hiện đại cân bằng throughput và pause. Tạo object thường khá rẻ; vấn đề lớn là giữ quá nhiều live object làm GC thường xuyên/nặng.
Code / Example
public void example() {

4. Production design: do not let every pod preload Redis blindly
In a multi-instance deployment, every pod executes its own startup hooks. If 20 pods start together and all read millions of DB rows and write the same Redis keys, the warm-up itself can create a DB/cache thundering herd. Common options are: make writes idempotent, preload in pages/batches, use a distributed lock/leader election when only one instance should warm the shared cache, or use cache-aside/lazy loading if an eager warm-up is not required.

Also define the failure policy. If this cache is mandatory for correctness, fail startup or keep readiness=false. If the cache is only an optimization, log/metric the failure and let the application start with a DB fallback.
Khi deploy nhiều instance/pod, mỗi pod đều chạy startup hook của riêng nó. Nếu 20 pod start cùng lúc và tất cả cùng đọc hàng triệu row từ DB rồi ghi cùng key vào Redis, chính cache warm-up sẽ tạo thundering herd lên DB/cache. Cách xử lý thường là: write idempotent, load theo page/batch, dùng distributed lock/leader election nếu chỉ một instance được phép warm shared cache, hoặc dùng cache-aside/lazy load nếu không bắt buộc eager preload.

Cũng phải xác định failure policy. Nếu cache bắt buộc cho correctness thì có thể fail startup hoặc giữ readiness=false. Nếu cache chỉ để tăng performance thì nên log/metric lỗi và cho app chạy với DB fallback.

Resilience: retry vs threshold/circuit breaker. What does retry=5 vs threshold=5 mean?Resilience: retry và threshold/circuit breaker khác nhau thế nào? Retry=5 vs threshold=5?

Interview answer
Câu trả lời phỏng vấn
Retry is per-call re-attempt behavior. A circuit-breaker threshold is an aggregate health rule across multiple calls that decides when to stop calling a failing dependency. They solve different problems and are often combined carefully.
Retry là hành vi thử lại trong một call. Circuit-breaker threshold là rule đánh giá sức khỏe tổng hợp qua nhiều call để quyết định khi nào ngừng gọi downstream đang lỗi. Hai cái giải quyết bài toán khác nhau.
Deep dive / internal workGiải thích sâu / internal work
Retry maxAttempts=5: one logical request may call downstream up to 5 times (depending on library semantics, often total attempts includes the first). This can recover transient errors but multiplies load.

Circuit breaker threshold: in libraries like Resilience4j, commonly a failure-rate threshold (e.g. 50%) over a sliding window and a minimum number of calls. A custom “5 consecutive failures” breaker would open after 5 failures across requests; that is still different from retrying one request 5 times.

Danger: 1,000 incoming requests × 5 attempts can produce up to 5,000 downstream attempts during an outage. Use timeouts, exponential backoff+jitter, retry only idempotent/transient errors, and put circuit breaker outside/around the retry chain according to desired metrics.
Retry maxAttempts=5: một logical request có thể gọi downstream tối đa 5 lần tùy semantics library. Hữu ích cho lỗi tạm thời nhưng nhân tải lên.

Circuit breaker threshold: Resilience4j thường dùng failure-rate threshold (ví dụ 50%) trên sliding window + minimumNumberOfCalls. Nếu hệ thống custom “5 consecutive failures” thì breaker open sau 5 failure qua nhiều request; vẫn khác retry 5 lần cho một request.

Nguy hiểm: 1,000 request × 5 attempt có thể thành 5,000 downstream call lúc outage. Cần timeout, exponential backoff+jitter, chỉ retry lỗi transient/idempotent và đặt circuit breaker/retry theo semantics mong muốn.

        slidingWindowSize: 20

        failureRateThreshold: 50
        waitDurationInOpenState: 10s
