1. Overview: What is Multithreading?

Multithreading means running multiple threads inside the same process. Each thread has its own execution stack, but threads in the same process share heap memory.

Key idea: Multithreading is easy when tasks are independent. It becomes difficult when multiple threads share and modify the same data.
Java Application Process ├── main thread ├── request worker thread 1 ├── request worker thread 2 ├── background job thread ├── scheduler thread └── GC threads

Why do we use multiple threads?

  • Handle many HTTP requests at the same time.
  • Run background jobs without blocking the main flow.
  • Call external APIs asynchronously.
  • Process files, messages, or events in parallel.
  • Improve resource utilization, especially for I/O-bound tasks.

Concurrency vs Parallelism

Concept Meaning Example
Concurrency Multiple tasks make progress in the same time period, not necessarily at the exact same instant. One CPU switches between Thread A, B, and C very quickly.
Parallelism Multiple tasks run at the exact same time on multiple CPU cores. Core 1 runs Thread A, Core 2 runs Thread B.

2. Thread Basics in Java

2.1. Create thread by extending Thread

class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println("Running in: " + Thread.currentThread().getName());
    }
}

public class Main {
    public static void main(String[] args) {
        MyThread thread = new MyThread();
        thread.start(); // creates a new thread
    }
}
Important: call start(), not run(). Calling run() directly executes the method in the current thread and does not create a new thread.

2.2. Create thread by implementing Runnable

class MyTask implements Runnable {
    @Override
    public void run() {
        System.out.println("Task running in: " + Thread.currentThread().getName());
    }
}

public class Main {
    public static void main(String[] args) {
        Thread thread = new Thread(new MyTask());
        thread.start();
    }
}

2.3. Create thread using lambda

public class Main {
    public static void main(String[] args) {
        Thread thread = new Thread(() -> {
            System.out.println("Running in: " + Thread.currentThread().getName());
        });

        thread.start();
    }
}

2.4. In production, prefer ExecutorService

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class Main {
    public static void main(String[] args) {
        ExecutorService executor = Executors.newFixedThreadPool(3);

        executor.submit(() -> System.out.println("Task 1"));
        executor.submit(() -> System.out.println("Task 2"));

        executor.shutdown();
    }
}
Production note: Avoid creating many raw threads manually. Use a thread pool to reuse threads and control resource usage.

3. Race Condition and Shared Mutable State

The most difficult part of multithreading is not creating threads. The difficult part is handling shared mutable state.

Shared mutable state means many threads access the same data, and at least one thread modifies it.

Example: non-thread-safe counter

class Counter {
    private int count = 0;

    public void increment() {
        count++; // not atomic
    }

    public int getCount() {
        return count;
    }
}
public class Main {
    public static void main(String[] args) throws InterruptedException {
        Counter counter = new Counter();

        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 1000; i++) {
                counter.increment();
            }
        });

        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 1000; i++) {
                counter.increment();
            }
        });

        t1.start();
        t2.start();

        t1.join();
        t2.join();

        System.out.println(counter.getCount());
    }
}

Expected result is 2000, but the actual result may be smaller.

Why?

count++ is not one atomic operation. It has multiple steps:

  1. Read current value.
  2. Increase value.
  3. Write value back.
count = 10 Thread A reads count = 10 Thread B reads count = 10 Thread A writes 11 Thread B writes 11 Expected: 12 Actual: 11
Race condition: The result depends on unpredictable thread scheduling. Different runs may produce different results.

4. What is Thread-Safe?

A piece of code is thread-safe if it works correctly when accessed by multiple threads at the same time.

Problem Meaning Common Fix
Race condition Multiple threads update shared data incorrectly. synchronized, locks, atomic classes, concurrent collections.
Visibility issue One thread changes data, but another thread does not see the latest value. volatile, synchronized, locks, atomic classes.
Deadlock Threads wait for each other forever. Consistent lock ordering, timeout, smaller lock scope.

Ways to make code thread-safe

Immutable objects Local variables synchronized ReentrantLock AtomicInteger ConcurrentHashMap BlockingQueue

5. synchronized

synchronized ensures that only one thread can enter a critical section at a time for the same lock.

5.1. synchronized method

class Counter {
    private int count = 0;

    public synchronized void increment() {
        count++;
    }

    public synchronized int getCount() {
        return count;
    }
}

5.2. synchronized block

class Counter {
    private int count = 0;

    public void increment() {
        synchronized (this) {
            count++;
        }
    }
}

A synchronized method:

public synchronized void increment() {
    count++;
}

is similar to:

public void increment() {
    synchronized (this) {
        count++;
    }
}
Best practice: Lock only the smallest necessary code block. Do not put slow operations such as external API calls inside synchronized blocks.

What lock does synchronized use?

Every Java object has an intrinsic lock, also called a monitor lock. When a thread enters a synchronized block, it acquires that lock. Other threads must wait until the lock is released.

6. volatile

volatile solves visibility, not atomicity.

Good use case: stop flag

class Worker {
    private volatile boolean running = true;

    public void run() {
        while (running) {
            // do work
        }
    }

    public void stop() {
        running = false;
    }
}

When one thread calls stop(), another thread running the loop can see the updated value.

Bad use case: counter

class Counter {
    private volatile int count = 0;

    public void increment() {
        count++; // still not atomic
    }
}
Important: volatile does not make count++ atomic. It only guarantees that threads see the latest value.
Feature volatile synchronized
Visibility Yes Yes
Atomicity for compound actions No Yes
Mutual exclusion No Yes
Use case Flags, state visibility Critical sections, shared data updates

7. Atomic Classes

Atomic classes provide thread-safe operations without using explicit synchronized blocks.

AtomicInteger example

import java.util.concurrent.atomic.AtomicInteger;

class Counter {
    private final AtomicInteger count = new AtomicInteger(0);

    public void increment() {
        count.incrementAndGet();
    }

    public int getCount() {
        return count.get();
    }
}

When to use AtomicInteger?

  • Simple counters.
  • Retry count.
  • Metrics.
  • Sequence-like values.
Senior note: Atomic classes often use CAS, meaning Compare-And-Swap. CAS tries to update a value only if the current value is still the expected value.

AtomicInteger vs LongAdder

Class Best For Note
AtomicInteger Simple atomic integer updates. Good for moderate contention.
LongAdder High-concurrency counters. Often better when many threads update the counter frequently.

8. ReentrantLock

ReentrantLock is a more flexible locking mechanism than synchronized.

import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

class Counter {
    private int count = 0;
    private final Lock lock = new ReentrantLock();

    public void increment() {
        lock.lock();
        try {
            count++;
        } finally {
            lock.unlock();
        }
    }

    public int getCount() {
        return count;
    }
}
Always release the lock in finally. Otherwise, an exception may prevent the lock from being released.

Why use ReentrantLock?

  • tryLock(): attempt to get lock without waiting forever.
  • lockInterruptibly(): allow interruption while waiting.
  • Fair lock option.
  • Multiple Condition objects.

tryLock example

if (lock.tryLock()) {
    try {
        // critical section
    } finally {
        lock.unlock();
    }
} else {
    // cannot acquire lock
}

9. Deadlock

Deadlock happens when threads wait for each other forever.

Thread A holds Lock 1 and waits for Lock 2 Thread B holds Lock 2 and waits for Lock 1 Result: both threads wait forever

Deadlock example

public class DeadlockExample {
    private static final Object LOCK_1 = new Object();
    private static final Object LOCK_2 = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (LOCK_1) {
                System.out.println("Thread 1 acquired LOCK_1");

                synchronized (LOCK_2) {
                    System.out.println("Thread 1 acquired LOCK_2");
                }
            }
        });

        Thread t2 = new Thread(() -> {
            synchronized (LOCK_2) {
                System.out.println("Thread 2 acquired LOCK_2");

                synchronized (LOCK_1) {
                    System.out.println("Thread 2 acquired LOCK_1");
                }
            }
        });

        t1.start();
        t2.start();
    }
}

How to avoid deadlock

  • Always acquire locks in the same order.
  • Keep lock scope small.
  • Avoid nested locks when possible.
  • Do not call external systems inside locks.
  • Use tryLock() with timeout if appropriate.

10. wait(), notify(), notifyAll()

wait(), notify(), and notifyAll() are used for thread communication.

They must be called inside a synchronized block or synchronized method.

Producer-consumer example

class SharedData {
    private String data;
    private boolean hasData = false;

    public synchronized void produce(String value) throws InterruptedException {
        while (hasData) {
            wait();
        }

        data = value;
        hasData = true;

        notifyAll();
    }

    public synchronized String consume() throws InterruptedException {
        while (!hasData) {
            wait();
        }

        String value = data;
        data = null;
        hasData = false;

        notifyAll();

        return value;
    }
}

Why use while, not if?

Because of spurious wakeup and multiple waiting threads. After waking up, the thread must re-check the condition.

// Correct
while (!condition) {
    wait();
}

// Risky
if (!condition) {
    wait();
}

11. BlockingQueue

In production, prefer BlockingQueue instead of manually writing low-level wait()/notify() code.

import java.util.concurrent.BlockingQueue;
import java.util.concurrent.LinkedBlockingQueue;

public class ProducerConsumerExample {
    public static void main(String[] args) {
        BlockingQueue<String> queue = new LinkedBlockingQueue<>();

        Thread producer = new Thread(() -> {
            try {
                queue.put("Message 1");
                queue.put("Message 2");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        Thread consumer = new Thread(() -> {
            try {
                System.out.println(queue.take());
                System.out.println(queue.take());
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        producer.start();
        consumer.start();
    }
}
Method Behavior
put() Blocks if the queue is full.
take() Blocks if the queue is empty.
offer() Attempts to add without waiting forever.
poll() Attempts to retrieve without waiting forever.

12. ExecutorService and Thread Pool

A thread pool manages a group of reusable worker threads.

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ExecutorExample {
    public static void main(String[] args) {
        ExecutorService executor = Executors.newFixedThreadPool(5);

        for (int i = 0; i < 10; i++) {
            int taskId = i;
            executor.submit(() -> {
                System.out.println("Task " + taskId + " running by "
                        + Thread.currentThread().getName());
            });
        }

        executor.shutdown();
    }
}

Common executor types

Executor Meaning Production Note
newFixedThreadPool Fixed number of threads. Good when you want to control concurrency.
newCachedThreadPool Creates threads as needed and reuses idle threads. Be careful. It may create too many threads under heavy load.
newSingleThreadExecutor Only one worker thread. Good for sequential background processing.
ScheduledExecutorService Runs tasks later or periodically. Useful for scheduled jobs.
Senior note: In real production systems, prefer creating ThreadPoolExecutor explicitly so you can control core size, max size, queue size, rejection policy, and thread naming.

13. Future and CompletableFuture

13.1. Future

Future represents a result that will be available later.

import java.util.concurrent.*;

public class FutureExample {
    public static void main(String[] args) throws Exception {
        ExecutorService executor = Executors.newFixedThreadPool(2);

        Future<Integer> future = executor.submit(() -> {
            Thread.sleep(1000);
            return 100;
        });

        Integer result = future.get(); // blocking

        System.out.println(result);
        executor.shutdown();
    }
}
future.get() blocks the current thread until the result is ready.

13.2. CompletableFuture

import java.util.concurrent.CompletableFuture;

public class CompletableFutureExample {
    public static void main(String[] args) {
        CompletableFuture<String> future = CompletableFuture
                .supplyAsync(() -> "Hello")
                .thenApply(result -> result + " Java")
                .thenApply(String::toUpperCase);

        System.out.println(future.join());
    }
}

Call two independent APIs in parallel

CompletableFuture<String> userFuture =
        CompletableFuture.supplyAsync(() -> getUser());

CompletableFuture<String> orderFuture =
        CompletableFuture.supplyAsync(() -> getOrders());

CompletableFuture<Void> combined =
        CompletableFuture.allOf(userFuture, orderFuture);

combined.join();

String user = userFuture.join();
String orders = orderFuture.join();
Use case: CompletableFuture is useful when multiple independent tasks can run in parallel and then be combined.

14. Thread-Safe Collections

Normal collections like ArrayList, HashMap, and HashSet are not thread-safe for concurrent modification.

Use Case Recommended Collection
Concurrent map access ConcurrentHashMap
Read-heavy list, rare writes CopyOnWriteArrayList
Producer-consumer queue BlockingQueue
Non-blocking queue ConcurrentLinkedQueue
Legacy synchronized wrapper Collections.synchronizedList()

ConcurrentHashMap example

import java.util.concurrent.ConcurrentHashMap;

ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

map.put("A", 1);
map.compute("A", (key, oldValue) -> oldValue == null ? 1 : oldValue + 1);

CopyOnWriteArrayList

import java.util.concurrent.CopyOnWriteArrayList;

CopyOnWriteArrayList<String> listeners = new CopyOnWriteArrayList<>();

listeners.add("listener-1");
listeners.add("listener-2");
CopyOnWriteArrayList is good for many reads and few writes. It is bad for write-heavy workloads because each write copies the underlying array.

15. ThreadLocal

ThreadLocal stores data separately for each thread.

public class UserContext {
    private static final ThreadLocal<String> currentUser = new ThreadLocal<>();

    public static void set(String userId) {
        currentUser.set(userId);
    }

    public static String get() {
        return currentUser.get();
    }

    public static void clear() {
        currentUser.remove();
    }
}

Common use cases

  • Current user ID.
  • Tenant ID.
  • Correlation ID.
  • Trace ID.
  • Request context.
Important: Always call remove() after using ThreadLocal in thread pools. Otherwise, reused threads may keep old data and cause memory leaks or incorrect request context.

16. Spring Boot Multithreading Best Practices

16.1. Spring beans are singleton by default

Most Spring services are singleton beans. Many request threads may use the same service object at the same time.

Bad example: shared request state in singleton bean

@Service
public class PaymentService {

    private String currentUserId; // dangerous shared mutable state

    public void pay(String userId) {
        this.currentUserId = userId;
        // process payment
    }
}
If two requests call pay() at the same time, one thread may overwrite currentUserId used by another thread.

Good example: use local variables

@Service
public class PaymentService {

    public void pay(String userId) {
        String currentUserId = userId;
        // process payment using local variable
    }
}

16.2. Prefer stateless services

@Service
public class OrderService {

    public OrderResponse createOrder(OrderRequest request) {
        // Use method parameters and local variables
        // Avoid storing request-specific data in fields
        return new OrderResponse();
    }
}

16.3. Use @Async carefully

@Service
public class EmailService {

    @Async
    public CompletableFuture<Void> sendEmail(String email) {
        // send email asynchronously
        return CompletableFuture.completedFuture(null);
    }
}
For @Async, configure your own executor. Do not blindly rely on defaults in production.

17. Interview Summary

Short answer: What is multithreading?

Multiple threads allow a program to execute multiple tasks concurrently within the same process. In Java, each thread has its own stack but shares heap memory with other threads in the same process.

Senior answer

The main benefit of multithreading is better resource utilization, especially for I/O-bound workloads such as handling HTTP requests, calling external APIs, processing messages, and running background jobs. However, when multiple threads access shared mutable state, we must handle thread-safety issues such as race condition, visibility problems, and deadlocks. In Java, we can manage concurrency using synchronized, volatile, locks, atomic classes, concurrent collections, ExecutorService, CompletableFuture, and BlockingQueue.

1. Tổng quan: Multithreading là gì?

Multithreading nghĩa là chạy nhiều thread bên trong cùng một process. Mỗi thread có stack riêng, nhưng các thread trong cùng process sẽ chia sẻ heap memory.

Ý quan trọng: Multithreading dễ khi các task độc lập. Nó trở nên khó khi nhiều thread cùng chia sẻ và thay đổi chung một dữ liệu.
Java Application Process ├── main thread ├── request worker thread 1 ├── request worker thread 2 ├── background job thread ├── scheduler thread └── GC threads

Vì sao cần multiple threads?

  • Xử lý nhiều HTTP request cùng lúc.
  • Chạy background job mà không block main flow.
  • Gọi external API bất đồng bộ.
  • Xử lý file, message, event song song.
  • Tận dụng tài nguyên tốt hơn, đặc biệt với I/O-bound tasks.

Concurrency vs Parallelism

Khái niệm Ý nghĩa Ví dụ
Concurrency Nhiều task cùng tiến triển trong cùng một khoảng thời gian, nhưng không nhất thiết chạy đúng cùng một thời điểm. Một CPU chuyển qua lại giữa Thread A, B, C rất nhanh.
Parallelism Nhiều task chạy thật sự cùng lúc trên nhiều CPU core. Core 1 chạy Thread A, Core 2 chạy Thread B.

2. Thread cơ bản trong Java

2.1. Tạo thread bằng cách extends Thread

class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println("Running in: " + Thread.currentThread().getName());
    }
}

public class Main {
    public static void main(String[] args) {
        MyThread thread = new MyThread();
        thread.start(); // tạo thread mới
    }
}
Quan trọng: gọi start(), không gọi trực tiếp run(). Nếu gọi run(), nó chỉ chạy như method bình thường trong thread hiện tại, không tạo thread mới.

2.2. Tạo thread bằng Runnable

class MyTask implements Runnable {
    @Override
    public void run() {
        System.out.println("Task running in: " + Thread.currentThread().getName());
    }
}

public class Main {
    public static void main(String[] args) {
        Thread thread = new Thread(new MyTask());
        thread.start();
    }
}

2.3. Tạo thread bằng lambda

public class Main {
    public static void main(String[] args) {
        Thread thread = new Thread(() -> {
            System.out.println("Running in: " + Thread.currentThread().getName());
        });

        thread.start();
    }
}

2.4. Production nên dùng ExecutorService

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class Main {
    public static void main(String[] args) {
        ExecutorService executor = Executors.newFixedThreadPool(3);

        executor.submit(() -> System.out.println("Task 1"));
        executor.submit(() -> System.out.println("Task 2"));

        executor.shutdown();
    }
}
Production note: Không nên tự tạo quá nhiều raw threads. Nên dùng thread pool để tái sử dụng thread và kiểm soát tài nguyên tốt hơn.

3. Race Condition và Shared Mutable State

Phần khó nhất của multithreading không phải là tạo thread. Phần khó nhất là xử lý shared mutable state.

Shared mutable state nghĩa là nhiều thread cùng truy cập một dữ liệu, và ít nhất một thread có thay đổi dữ liệu đó.

Ví dụ: counter không thread-safe

class Counter {
    private int count = 0;

    public void increment() {
        count++; // không atomic
    }

    public int getCount() {
        return count;
    }
}
public class Main {
    public static void main(String[] args) throws InterruptedException {
        Counter counter = new Counter();

        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 1000; i++) {
                counter.increment();
            }
        });

        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 1000; i++) {
                counter.increment();
            }
        });

        t1.start();
        t2.start();

        t1.join();
        t2.join();

        System.out.println(counter.getCount());
    }
}

Kỳ vọng kết quả là 2000, nhưng thực tế có thể nhỏ hơn.

Vì sao?

count++ không phải một operation atomic. Nó gồm nhiều bước:

  1. Đọc giá trị hiện tại.
  2. Tăng giá trị.
  3. Ghi giá trị mới trở lại.
count = 10 Thread A đọc count = 10 Thread B đọc count = 10 Thread A ghi 11 Thread B ghi 11 Kỳ vọng: 12 Thực tế: 11
Race condition: Kết quả phụ thuộc vào thứ tự chạy không thể đoán trước của các thread. Mỗi lần chạy có thể ra kết quả khác nhau.

4. Thread-safe là gì?

Một đoạn code được gọi là thread-safe nếu nhiều thread truy cập cùng lúc mà kết quả vẫn đúng, không bị corrupt data, không race condition.

Vấn đề Ý nghĩa Cách xử lý phổ biến
Race condition Nhiều thread update shared data làm kết quả sai. synchronized, locks, atomic classes, concurrent collections.
Visibility issue Một thread thay đổi data nhưng thread khác không thấy giá trị mới. volatile, synchronized, locks, atomic classes.
Deadlock Các thread chờ nhau mãi mãi. Lock ordering, timeout, giới hạn phạm vi lock.

Các cách làm code thread-safe

Immutable objects Local variables synchronized ReentrantLock AtomicInteger ConcurrentHashMap BlockingQueue

5. synchronized

synchronized đảm bảo tại một thời điểm chỉ có một thread được đi vào critical section với cùng một lock.

5.1. synchronized method

class Counter {
    private int count = 0;

    public synchronized void increment() {
        count++;
    }

    public synchronized int getCount() {
        return count;
    }
}

5.2. synchronized block

class Counter {
    private int count = 0;

    public void increment() {
        synchronized (this) {
            count++;
        }
    }
}

Synchronized method:

public synchronized void increment() {
    count++;
}

tương đương gần giống với:

public void increment() {
    synchronized (this) {
        count++;
    }
}
Best practice: Chỉ lock phần code nhỏ nhất cần thiết. Không nên gọi external API hoặc xử lý logic chậm bên trong synchronized block.

synchronized dùng lock nào?

Mỗi Java object có một intrinsic lock, còn gọi là monitor lock. Khi một thread vào synchronized block, nó lấy lock đó. Các thread khác phải chờ cho tới khi lock được release.

6. volatile

volatile xử lý vấn đề visibility, không xử lý atomicity.

Use case tốt: stop flag

class Worker {
    private volatile boolean running = true;

    public void run() {
        while (running) {
            // do work
        }
    }

    public void stop() {
        running = false;
    }
}

Khi một thread gọi stop(), thread đang chạy loop có thể thấy giá trị mới của running.

Use case sai: counter

class Counter {
    private volatile int count = 0;

    public void increment() {
        count++; // vẫn không atomic
    }
}
Quan trọng: volatile không làm count++ trở thành atomic. Nó chỉ đảm bảo các thread thấy giá trị mới nhất.
Feature volatile synchronized
Visibility Có Có
Atomicity cho compound actions Không Có
Mutual exclusion Không Có
Use case Flag, state visibility Critical section, update shared data

7. Atomic Classes

Atomic classes cung cấp các operation thread-safe mà không cần tự viết synchronized block.

Ví dụ AtomicInteger

import java.util.concurrent.atomic.AtomicInteger;

class Counter {
    private final AtomicInteger count = new AtomicInteger(0);

    public void increment() {
        count.incrementAndGet();
    }

    public int getCount() {
        return count.get();
    }
}

Khi nào dùng AtomicInteger?

  • Counter đơn giản.
  • Retry count.
  • Metrics.
  • Sequence-like values.
Senior note: Atomic classes thường dùng CAS, tức Compare-And-Swap. CAS chỉ update value nếu current value vẫn đúng như expected value.

AtomicInteger vs LongAdder

Class Phù hợp cho Ghi chú
AtomicInteger Atomic integer update đơn giản. Tốt khi contention vừa phải.
LongAdder Counter có concurrency cao. Thường tốt hơn khi nhiều thread update counter liên tục.

8. ReentrantLock

ReentrantLock là cơ chế lock linh hoạt hơn synchronized.

import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

class Counter {
    private int count = 0;
    private final Lock lock = new ReentrantLock();

    public void increment() {
        lock.lock();
        try {
            count++;
        } finally {
            lock.unlock();
        }
    }

    public int getCount() {
        return count;
    }
}
Luôn release lock trong finally. Nếu không, exception có thể làm lock không được release.

Vì sao dùng ReentrantLock?

  • tryLock(): thử lấy lock mà không chờ mãi mãi.
  • lockInterruptibly(): cho phép interrupt khi đang chờ lock.
  • Có fair lock option.
  • Hỗ trợ nhiều Condition.

Ví dụ tryLock

if (lock.tryLock()) {
    try {
        // critical section
    } finally {
        lock.unlock();
    }
} else {
    // không lấy được lock
}

9. Deadlock

Deadlock xảy ra khi các thread chờ nhau mãi mãi.

Thread A giữ Lock 1 và chờ Lock 2 Thread B giữ Lock 2 và chờ Lock 1 Kết quả: cả hai thread chờ mãi mãi

Ví dụ deadlock

public class DeadlockExample {
    private static final Object LOCK_1 = new Object();
    private static final Object LOCK_2 = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (LOCK_1) {
                System.out.println("Thread 1 acquired LOCK_1");

                synchronized (LOCK_2) {
                    System.out.println("Thread 1 acquired LOCK_2");
                }
            }
        });

        Thread t2 = new Thread(() -> {
            synchronized (LOCK_2) {
                System.out.println("Thread 2 acquired LOCK_2");

                synchronized (LOCK_1) {
                    System.out.println("Thread 2 acquired LOCK_1");
                }
            }
        });

        t1.start();
        t2.start();
    }
}

Cách tránh deadlock

  • Luôn lấy lock theo cùng một thứ tự.
  • Giữ phạm vi lock càng nhỏ càng tốt.
  • Tránh nested locks nếu có thể.
  • Không gọi external system bên trong lock.
  • Dùng tryLock() với timeout nếu phù hợp.

10. wait(), notify(), notifyAll()

wait(), notify(), notifyAll() dùng để các thread giao tiếp với nhau.

Các method này phải được gọi bên trong synchronized block hoặc synchronized method.

Ví dụ producer-consumer

class SharedData {
    private String data;
    private boolean hasData = false;

    public synchronized void produce(String value) throws InterruptedException {
        while (hasData) {
            wait();
        }

        data = value;
        hasData = true;

        notifyAll();
    }

    public synchronized String consume() throws InterruptedException {
        while (!hasData) {
            wait();
        }

        String value = data;
        data = null;
        hasData = false;

        notifyAll();

        return value;
    }
}

Vì sao dùng while, không dùng if?

Vì có thể có spurious wakeup hoặc nhiều thread cùng được đánh thức. Sau khi wake up, thread phải check lại condition.

// Đúng
while (!condition) {
    wait();
}

// Rủi ro
if (!condition) {
    wait();
}

11. BlockingQueue

Trong production, nên ưu tiên BlockingQueue thay vì tự viết code cấp thấp với wait()/notify().

import java.util.concurrent.BlockingQueue;
import java.util.concurrent.LinkedBlockingQueue;

public class ProducerConsumerExample {
    public static void main(String[] args) {
        BlockingQueue<String> queue = new LinkedBlockingQueue<>();

        Thread producer = new Thread(() -> {
            try {
                queue.put("Message 1");
                queue.put("Message 2");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        Thread consumer = new Thread(() -> {
            try {
                System.out.println(queue.take());
                System.out.println(queue.take());
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        producer.start();
        consumer.start();
    }
}
Method Hành vi
put() Block nếu queue đầy.
take() Block nếu queue rỗng.
offer() Thử add mà không chờ mãi mãi.
poll() Thử lấy data mà không chờ mãi mãi.

12. ExecutorService và Thread Pool

Thread pool quản lý một nhóm worker threads có thể tái sử dụng.

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ExecutorExample {
    public static void main(String[] args) {
        ExecutorService executor = Executors.newFixedThreadPool(5);

        for (int i = 0; i < 10; i++) {
            int taskId = i;
            executor.submit(() -> {
                System.out.println("Task " + taskId + " running by "
                        + Thread.currentThread().getName());
            });
        }

        executor.shutdown();
    }
}

Các loại executor phổ biến

Executor Ý nghĩa Production note
newFixedThreadPool Số lượng thread cố định. Tốt khi muốn kiểm soát concurrency.
newCachedThreadPool Tạo thread khi cần và reuse idle threads. Cẩn thận vì workload lớn có thể tạo quá nhiều thread.
newSingleThreadExecutor Chỉ có một worker thread. Tốt cho xử lý tuần tự.
ScheduledExecutorService Chạy task sau một khoảng delay hoặc định kỳ. Hữu ích cho scheduled jobs.
Senior note: Trong production, nên tạo ThreadPoolExecutor rõ ràng để control core size, max size, queue size, rejection policy và thread name.

13. Future và CompletableFuture

13.1. Future

Future đại diện cho kết quả sẽ có trong tương lai.

import java.util.concurrent.*;

public class FutureExample {
    public static void main(String[] args) throws Exception {
        ExecutorService executor = Executors.newFixedThreadPool(2);

        Future<Integer> future = executor.submit(() -> {
            Thread.sleep(1000);
            return 100;
        });

        Integer result = future.get(); // blocking

        System.out.println(result);
        executor.shutdown();
    }
}
future.get() sẽ block thread hiện tại cho tới khi có kết quả.

13.2. CompletableFuture

import java.util.concurrent.CompletableFuture;

public class CompletableFutureExample {
    public static void main(String[] args) {
        CompletableFuture<String> future = CompletableFuture
                .supplyAsync(() -> "Hello")
                .thenApply(result -> result + " Java")
                .thenApply(String::toUpperCase);

        System.out.println(future.join());
    }
}

Gọi 2 API độc lập song song

CompletableFuture<String> userFuture =
        CompletableFuture.supplyAsync(() -> getUser());

CompletableFuture<String> orderFuture =
        CompletableFuture.supplyAsync(() -> getOrders());

CompletableFuture<Void> combined =
        CompletableFuture.allOf(userFuture, orderFuture);

combined.join();

String user = userFuture.join();
String orders = orderFuture.join();
Use case: CompletableFuture hữu ích khi nhiều task độc lập có thể chạy song song rồi combine kết quả.

14. Thread-Safe Collections

Các collection thường như ArrayList, HashMap, HashSet không thread-safe khi nhiều thread cùng modify.

Use case Collection nên dùng
Concurrent map access ConcurrentHashMap
List đọc nhiều, ghi ít CopyOnWriteArrayList
Producer-consumer queue BlockingQueue
Non-blocking queue ConcurrentLinkedQueue
Legacy synchronized wrapper Collections.synchronizedList()

Ví dụ ConcurrentHashMap

import java.util.concurrent.ConcurrentHashMap;

ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

map.put("A", 1);
map.compute("A", (key, oldValue) -> oldValue == null ? 1 : oldValue + 1);

CopyOnWriteArrayList

import java.util.concurrent.CopyOnWriteArrayList;

CopyOnWriteArrayList<String> listeners = new CopyOnWriteArrayList<>();

listeners.add("listener-1");
listeners.add("listener-2");
CopyOnWriteArrayList phù hợp khi đọc rất nhiều và ghi rất ít. Không phù hợp nếu write-heavy, vì mỗi lần write nó copy underlying array.

15. ThreadLocal

ThreadLocal lưu data riêng cho từng thread.

public class UserContext {
    private static final ThreadLocal<String> currentUser = new ThreadLocal<>();

    public static void set(String userId) {
        currentUser.set(userId);
    }

    public static String get() {
        return currentUser.get();
    }

    public static void clear() {
        currentUser.remove();
    }
}

Use cases phổ biến

  • Current user ID.
  • Tenant ID.
  • Correlation ID.
  • Trace ID.
  • Request context.
Quan trọng: Luôn gọi remove() sau khi dùng ThreadLocal trong thread pool. Nếu không, thread được reuse có thể giữ data cũ, gây memory leak hoặc sai request context.

16. Best Practices trong Spring Boot

16.1. Spring beans mặc định là singleton

Hầu hết Spring services là singleton beans. Nhiều request threads có thể dùng chung một service object cùng lúc.

Ví dụ sai: lưu request state trong singleton bean

@Service
public class PaymentService {

    private String currentUserId; // shared mutable state nguy hiểm

    public void pay(String userId) {
        this.currentUserId = userId;
        // process payment
    }
}
Nếu hai request gọi pay() cùng lúc, thread này có thể overwrite currentUserId của thread khác.

Ví dụ đúng: dùng local variables

@Service
public class PaymentService {

    public void pay(String userId) {
        String currentUserId = userId;
        // process payment using local variable
    }
}

16.2. Ưu tiên stateless services

@Service
public class OrderService {

    public OrderResponse createOrder(OrderRequest request) {
        // Dùng method parameters và local variables
        // Không lưu request-specific data vào field
        return new OrderResponse();
    }
}

16.3. Dùng @Async cẩn thận

@Service
public class EmailService {

    @Async
    public CompletableFuture<Void> sendEmail(String email) {
        // send email asynchronously
        return CompletableFuture.completedFuture(null);
    }
}
Với @Async, nên configure executor riêng. Không nên phụ thuộc mù quáng vào default trong production.

17. Tóm tắt phỏng vấn

Câu trả lời ngắn: Multithreading là gì?

Multiple threads cho phép chương trình xử lý nhiều task đồng thời trong cùng một process. Trong Java, mỗi thread có stack riêng nhưng chia sẻ heap memory với các thread khác trong cùng process.

Câu trả lời senior hơn

Lợi ích chính của multithreading là tận dụng tài nguyên tốt hơn, đặc biệt với I/O-bound workloads như xử lý HTTP request, gọi external API, process messages và chạy background jobs. Tuy nhiên, khi nhiều thread truy cập shared mutable state, mình phải xử lý các vấn đề thread-safety như race condition, visibility problem và deadlock. Trong Java, mình có thể quản lý concurrency bằng synchronized, volatile, locks, atomic classes, concurrent collections, ExecutorService, CompletableFuture và BlockingQueue.
