1. Senior Mental Model

1. Tư duy nền tảng ở cấp Senior

Multithreading is not simply “running several methods at the same time.” It is the controlled coordination of multiple execution flows that share memory, CPU time, I/O resources, locks, queues, and failure states.

Correctness

Does the program preserve invariants under every legal thread interleaving?

Liveness

Can work always make progress, or can threads deadlock, livelock, or starve?

Performance

Does concurrency increase throughput without creating excessive contention, context switching, or memory pressure?

Operability

Can the system be observed and diagnosed through metrics, thread dumps, tracing, and timeouts?

Senior perspective: Prefer minimizing shared mutable state. Good concurrency design is usually more about ownership, isolation, queues, immutability, and bounded resources than adding more locks.

Multithreading không chỉ là “chạy nhiều method cùng lúc”. Đây là việc điều phối nhiều luồng thực thi cùng chia sẻ bộ nhớ, CPU, I/O, lock, queue và trạng thái lỗi.

Tính đúng đắn

Chương trình có giữ đúng invariant với mọi thứ tự xen kẽ hợp lệ giữa các thread không?

Khả năng tiến triển

Hệ thống có tiếp tục xử lý được hay bị deadlock, livelock hoặc starvation?

Hiệu năng

Concurrency có tăng throughput mà không gây contention, context switching và memory pressure quá mức không?

Khả năng vận hành

Có thể quan sát và chẩn đoán bằng metric, thread dump, tracing và timeout không?

Góc nhìn Senior: Hãy giảm shared mutable state. Thiết kế concurrency tốt thường dựa vào ownership, isolation, queue, immutability và giới hạn tài nguyên hơn là thêm nhiều lock.

4. Java Memory Model and Happens-Before

4. Java Memory Model và Happens-Before

The Java Memory Model defines when writes performed by one thread are guaranteed to become visible to another thread and which reorderings are legal.

The three core concurrency problems

Atomicity

An operation happens completely or not at all. count++ is not atomic.

Visibility

One thread may not immediately observe another thread’s write without synchronization.

Ordering

The compiler, CPU, and runtime may reorder instructions when single-thread semantics are preserved.

Important happens-before relationships

  • Unlocking a monitor happens-before a later lock of the same monitor.
  • A volatile write happens-before a later volatile read of the same variable.
  • Actions before Thread.start() happen-before actions in the started thread.
  • All actions in a thread happen-before another thread successfully returns from join().
  • Actions before submitting a task to an Executor happen-before task execution.
  • Transitivity applies: if A happens-before B and B happens-before C, then A happens-before C.
Interview phrase: “Thread safety is not only about mutual exclusion. It also requires safe publication, visibility, and ordering guarantees under the Java Memory Model.”

Java Memory Model định nghĩa khi nào dữ liệu được một thread ghi sẽ chắc chắn visible với thread khác và những reorder nào được phép.

Ba vấn đề cốt lõi

Atomicity

Một thao tác xảy ra trọn vẹn hoặc không xảy ra. count++ không atomic.

Visibility

Một thread có thể không thấy ngay giá trị thread khác vừa ghi nếu không có cơ chế đồng bộ.

Ordering

Compiler, CPU và runtime có thể reorder lệnh miễn vẫn giữ đúng semantics của single thread.

Các quan hệ happens-before quan trọng

  • Unlock monitor xảy ra trước lần lock tiếp theo trên cùng monitor.
  • Ghi volatile xảy ra trước lần đọc volatile tiếp theo trên cùng biến.
  • Thao tác trước Thread.start() xảy ra trước thao tác trong thread được start.
  • Mọi thao tác trong thread xảy ra trước khi thread khác join() thành công.
  • Thao tác trước khi submit task vào Executor xảy ra trước khi task chạy.
  • Có tính bắc cầu: A happens-before B, B happens-before C thì A happens-before C.
Câu trả lời phỏng vấn: “Thread safety không chỉ là mutual exclusion. Nó còn cần safe publication, visibility và ordering theo Java Memory Model.”

5. Race Condition and Lost Update

5. Race Condition và Lost Update

A race condition occurs when correctness depends on timing or interleaving between threads.

class UnsafeCounter {
    private int count;

    void increment() {
        count++; // read → add → write, not atomic
    }

    int get() {
        return count;
    }
}

Two threads may both read 10, both compute 11, and both write 11. One increment is lost.

Correct alternatives

class SynchronizedCounter {
    private int count;

    synchronized void increment() {
        count++;
    }

    synchronized int get() {
        return count;
    }
}

class AtomicCounter {
    private final AtomicInteger count = new AtomicInteger();

    void increment() {
        count.incrementAndGet();
    }

    int get() {
        return count.get();
    }
}

Race condition xảy ra khi tính đúng đắn phụ thuộc vào timing hoặc thứ tự xen kẽ giữa các thread.

class UnsafeCounter {
    private int count;

    void increment() {
        count++; // đọc → cộng → ghi, không atomic
    }

    int get() {
        return count;
    }
}

Hai thread có thể cùng đọc 10, cùng tính 11 và cùng ghi 11. Một lần tăng bị mất.

Cách sửa

6. synchronized and Intrinsic Locks

6. synchronized và Intrinsic Lock

Every Java object can act as a monitor. Entering a synchronized block acquires the monitor; exiting releases it, including when an exception is thrown.

class InventoryService {
    private final Object lock = new Object();
    private int stock = 100;

    public boolean reserve(int quantity) {
        synchronized (lock) {
            if (stock < quantity) {
                return false;
            }
            stock -= quantity;
            return true;
        }
    }
}

Method vs block

  • synchronized instanceMethod() locks this.
  • static synchronized method() locks the Class object.
  • A synchronized block can use a private dedicated lock and minimize critical-section size.
Do not lock on: public objects, string literals, boxed primitives, request objects, or mutable references that may be replaced.
Design rule: Protect an invariant, not just a field. All fields participating in the invariant must be read and modified under the same synchronization policy.

Mỗi object Java có thể hoạt động như một monitor. Vào synchronized block sẽ acquire monitor; thoát block sẽ release, kể cả khi có exception.

class InventoryService {
    private final Object lock = new Object();
    private int stock = 100;

    public boolean reserve(int quantity) {
        synchronized (lock) {
            if (stock < quantity) {
                return false;
            }
            stock -= quantity;
            return true;
        }
    }
}

Method và block

  • synchronized instanceMethod() lock trên this.
  • static synchronized method() lock trên Class object.
  • Synchronized block có thể dùng private lock riêng và thu nhỏ critical section.
Không nên lock trên: public object, string literal, boxed primitive, request object hoặc reference có thể bị thay thế.
Quy tắc thiết kế: Bảo vệ invariant, không chỉ bảo vệ một field. Mọi field thuộc invariant phải được đọc và cập nhật theo cùng synchronization policy.

7. volatile: Visibility Without Mutual Exclusion

7. volatile: Visibility nhưng không Mutual Exclusion

volatile guarantees visibility and ordering around the variable, but it does not make compound operations atomic.

class GracefulWorker implements Runnable {
    private volatile boolean running = true;

    public void shutdown() {
        running = false;
    }

    @Override
    public void run() {
        while (running) {
            doOneUnitOfWork();
        }
    }
}

Good use cases

  • Stop flags and simple state publication.
  • Immutable configuration snapshots replaced atomically.
  • Double-checked locking when the instance field is volatile.
private static volatile Client instance;

public static Client getInstance() {
    Client local = instance;
    if (local == null) {
        synchronized (Client.class) {
            local = instance;
            if (local == null) {
                local = instance = new Client();
            }
        }
    }
    return local;
}
volatile int count; count++; is still unsafe because increment is a read-modify-write sequence.

volatile đảm bảo visibility và ordering xung quanh biến đó, nhưng không làm compound operation trở thành atomic.

8. Lock, ReentrantLock and ReadWriteLock

8. Lock, ReentrantLock và ReadWriteLock

ReentrantLock provides explicit lock control, interruptible acquisition, timed acquisition, optional fairness, and multiple Condition queues.

private final ReentrantLock lock = new ReentrantLock();

public void transfer(Account from, Account to, BigDecimal amount)
        throws InterruptedException {

    if (lock.tryLock(200, TimeUnit.MILLISECONDS)) {
        try {
            // validate and update shared state
        } finally {
            lock.unlock();
        }
    } else {
        throw new TimeoutException("Could not acquire transfer lock");
    }
}
Always unlock in finally. Explicit locks are powerful but easier to misuse than synchronized.

ReadWriteLock

Useful when reads are frequent, writes are rare, and the protected operation is large enough to justify the lock overhead. It may perform worse for small critical sections or write-heavy workloads.

StampedLock

Supports optimistic reads, but it is not reentrant and is more error-prone. Use only after measurement proves value.

ReentrantLock cho phép điều khiển lock tường minh, acquire có thể interrupt, timeout, fairness và nhiều Condition queue.

private final ReentrantLock lock = new ReentrantLock();

public void transfer(Account from, Account to, BigDecimal amount)
        throws InterruptedException {

    if (lock.tryLock(200, TimeUnit.MILLISECONDS)) {
        try {
            // validate và cập nhật shared state
        } finally {
            lock.unlock();
        }
    } else {
        throw new TimeoutException("Could not acquire transfer lock");
    }
}
Luôn unlock trong finally. Explicit lock mạnh nhưng dễ dùng sai hơn synchronized.

ReadWriteLock

Phù hợp khi read nhiều, write ít và phần logic bảo vệ đủ lớn để bù chi phí lock. Có thể chậm hơn nếu critical section nhỏ hoặc write nhiều.

StampedLock

Hỗ trợ optimistic read nhưng không reentrant và dễ lỗi hơn. Chỉ dùng khi benchmark chứng minh có lợi.

9. Atomics, CAS and LongAdder

9. Atomic, CAS và LongAdder

Atomic classes use compare-and-set style operations to update a value without a traditional blocking lock.

AtomicInteger retries = new AtomicInteger();

int current = retries.incrementAndGet();

boolean updated = retries.compareAndSet(current, 0);

CAS concept

“Update the value to N only if it still equals the expected old value.” If another thread changed it, retry.

Trade-offs

  • Excellent under low-to-moderate contention.
  • Under heavy contention, retries can waste CPU.
  • Single-variable atomicity does not automatically protect multi-field invariants.
  • ABA can matter in lock-free algorithms; stamped references can help.

AtomicLong vs LongAdder

AtomicLong provides a precise atomic value. LongAdder spreads updates across cells, improving throughput for hot counters, but sum() is not a transactional snapshot.

Các lớp Atomic dùng compare-and-set để cập nhật giá trị mà không cần blocking lock truyền thống.

AtomicInteger retries = new AtomicInteger();

int current = retries.incrementAndGet();

boolean updated = retries.compareAndSet(current, 0);

Khái niệm CAS

“Chỉ cập nhật thành N nếu giá trị hiện tại vẫn bằng expected value.” Nếu thread khác đã thay đổi thì retry.

Trade-off

  • Rất hiệu quả khi contention thấp hoặc trung bình.
  • Khi contention cao, retry có thể tốn CPU.
  • Atomic cho một biến không tự động bảo vệ invariant gồm nhiều field.
  • ABA có thể ảnh hưởng lock-free algorithm; stamped reference có thể hỗ trợ.

AtomicLong và LongAdder

AtomicLong cung cấp giá trị atomic chính xác. LongAdder phân tán update ra nhiều cell để tăng throughput cho counter nóng, nhưng sum() không phải transactional snapshot.

10. wait, notify, notifyAll and Condition

10. wait, notify, notifyAll và Condition

wait() releases the current monitor and suspends the thread. sleep() does not release any lock.

class BoundedBuffer<T> {
    private final Queue<T> queue = new ArrayDeque<>();
    private final int capacity;

    BoundedBuffer(int capacity) {
        this.capacity = capacity;
    }

    public synchronized void put(T item) throws InterruptedException {
        while (queue.size() == capacity) {
            wait();
        }
        queue.add(item);
        notifyAll();
    }

    public synchronized T take() throws InterruptedException {
        while (queue.isEmpty()) {
            wait();
        }
        T item = queue.remove();
        notifyAll();
        return item;
    }
}
Always wait in a while loop. The condition may no longer be true after wake-up, and spurious wake-ups are allowed.

In production, prefer higher-level utilities such as BlockingQueue, Semaphore, CountDownLatch, or Condition.

wait() release monitor hiện tại rồi tạm dừng thread. sleep() không release lock.

Trong production nên ưu tiên utility cấp cao như BlockingQueue, Semaphore, CountDownLatch hoặc Condition.

11. ExecutorService and ThreadPoolExecutor

11. ExecutorService và ThreadPoolExecutor

Executor separates what to execute from how and where it executes.

ThreadPoolExecutor executor = new ThreadPoolExecutor(
    8,                              // corePoolSize
    16,                             // maximumPoolSize
    60, TimeUnit.SECONDS,           // keepAliveTime
    new ArrayBlockingQueue<>(500),  // bounded queue
    new NamedThreadFactory("order-worker"),
    new ThreadPoolExecutor.CallerRunsPolicy()
);

Execution decision

  1. If workers < corePoolSize, create a worker.
  2. Otherwise, enqueue the task if the queue accepts it.
  3. If the queue is full and workers < maximumPoolSize, create another worker.
  4. Otherwise, apply the rejection policy.
Unbounded queue warning: With an unbounded queue, maximumPoolSize is usually ineffective because tasks continue to queue instead of creating extra workers. This can lead to high latency or OutOfMemoryError.

Rejection policies

PolicyBehaviorUse
AbortPolicyThrows RejectedExecutionException.Fail fast and surface overload.
CallerRunsPolicyCaller executes the task.Provides natural backpressure, but can slow request threads.
DiscardPolicySilently drops the task.Only when dropping is explicitly acceptable and measured.
DiscardOldestPolicyDrops the oldest queued task.Rarely safe for business operations.

Executor tách công việc cần chạy khỏi chính sách chạy ở đâu và như thế nào.

ThreadPoolExecutor executor = new ThreadPoolExecutor(
    8,                              // corePoolSize
    16,                             // maximumPoolSize
    60, TimeUnit.SECONDS,           // keepAliveTime
    new ArrayBlockingQueue<>(500),  // bounded queue
    new NamedThreadFactory("order-worker"),
    new ThreadPoolExecutor.CallerRunsPolicy()
);

Quyết định thực thi

  1. Nếu số worker < corePoolSize, tạo worker mới.
  2. Nếu không, đưa task vào queue nếu queue còn chỗ.
  3. Nếu queue đầy và worker < maximumPoolSize, tạo worker mới.
  4. Nếu vẫn không xử lý được, áp dụng rejection policy.
Cảnh báo unbounded queue: Với queue không giới hạn, maximumPoolSize thường không có tác dụng vì task tiếp tục xếp hàng thay vì tạo worker mới. Hậu quả có thể là latency cao hoặc OutOfMemoryError.

12. Thread Pool Sizing

12. Cách tính kích thước Thread Pool

CPU-bound

threads ≈ number of CPU cores or cores + 1

Examples: compression, encryption, image processing, complex calculations. More threads than cores usually increase context switching rather than throughput.

I/O-bound

threads ≈ cores × (1 + wait time / compute time)

Example: 8 cores, average 90 ms waiting and 10 ms computing:

8 × (1 + 90/10) = 80 threads
This is a starting estimate, not a final answer. Validate with latency targets, queue time, downstream limits, connection pools, heap usage, CPU saturation, and load tests.

Little’s Law for capacity thinking

concurrency = throughput × average response time

If a service must process 1,000 requests/s and each request occupies a worker for 200 ms, expected in-flight concurrency is roughly 200.

Critical relationship: A 100-thread application pool cannot efficiently call a database through a 10-connection pool if every task needs a connection. The smallest constrained downstream resource becomes the bottleneck.

CPU-bound

số thread ≈ số CPU core hoặc core + 1

Ví dụ: nén, mã hóa, xử lý ảnh, tính toán phức tạp. Tạo nhiều thread hơn core thường chỉ làm tăng context switching.

I/O-bound

số thread ≈ core × (1 + thời gian chờ / thời gian tính toán)

Ví dụ: 8 core, trung bình chờ 90 ms và tính toán 10 ms:

8 × (1 + 90/10) = 80 thread
Đây chỉ là giá trị khởi đầu. Cần kiểm chứng bằng latency target, queue time, giới hạn downstream, connection pool, heap, CPU và load test.

Little’s Law để suy nghĩ về capacity

concurrency = throughput × response time trung bình

Nếu service phải xử lý 1.000 request/s và mỗi request giữ worker trong 200 ms, concurrency đang in-flight xấp xỉ 200.

Future represents a pending result but is difficult to compose. CompletableFuture supports pipelines, combination, recovery, and asynchronous stages.

16. Deadlock, Livelock and Starvation

16. Deadlock, Livelock và Starvation

Deadlock

Two or more threads wait forever for resources held by each other.

// Thread 1
synchronized (accountA) {
    synchronized (accountB) { transfer(); }
}

// Thread 2
synchronized (accountB) {
    synchronized (accountA) { transfer(); }
}

Four Coffman conditions

  1. Mutual exclusion
  2. Hold and wait
  3. No preemption
  4. Circular wait

Prevention

  • Use a global lock ordering.
  • Avoid nested locks.
  • Use timed tryLock and rollback.
  • Reduce lock scope and shared state.
  • Use immutable data, queues, or actors when possible.

Livelock

Threads are active and repeatedly react to each other, but no useful work completes.

Starvation

A thread is continually denied CPU or lock access because other threads dominate the resource.

Deadlock

Hai hoặc nhiều thread chờ vĩnh viễn resource đang bị thread khác giữ.

// Thread 1
synchronized (accountA) {
    synchronized (accountB) { transfer(); }
}

// Thread 2
synchronized (accountB) {
    synchronized (accountA) { transfer(); }
}

Bốn điều kiện Coffman

  1. Mutual exclusion
  2. Hold and wait
  3. No preemption
  4. Circular wait

Cách phòng tránh

  • Dùng thứ tự lock toàn cục.
  • Tránh nested lock.
  • Dùng timed tryLock và rollback.
  • Giảm phạm vi lock và shared state.
  • Ưu tiên immutable data, queue hoặc actor.

Livelock

Thread vẫn hoạt động và liên tục phản ứng với nhau nhưng không hoàn thành công việc hữu ích.

Starvation

Một thread liên tục không giành được CPU hoặc lock vì thread khác chiếm ưu thế.

17. Interruption and Cancellation

17. Interruption và Cancellation

Interruption is cooperative cancellation. It is a request, not a forced kill.

public void process() {
    try {
        while (!Thread.currentThread().isInterrupted()) {
            Task task = queue.take();
            handle(task);
        }
    } catch (InterruptedException ex) {
        Thread.currentThread().interrupt(); // restore status
        log.info("Worker interrupted, stopping");
    } finally {
        cleanup();
    }
}

Rules

  • Propagate InterruptedException when the API allows it.
  • If you catch it and cannot rethrow, restore the interrupt flag.
  • Do not swallow interruption and continue as if nothing happened.
  • Blocking operations should have timeouts where indefinite waiting is unacceptable.
Never use Thread.stop(). It can terminate a thread while shared state is inconsistent and locks are being manipulated.

Interruption là cơ chế cooperative cancellation. Đây là yêu cầu dừng, không phải cưỡng chế kill thread.

Quy tắc

  • Propagate InterruptedException nếu API cho phép.
  • Nếu catch nhưng không thể throw tiếp, phải restore interrupt flag.
  • Không swallow interruption rồi tiếp tục như không có gì xảy ra.
  • Blocking operation nên có timeout nếu không chấp nhận chờ vô hạn.
Không dùng Thread.stop(). Nó có thể dừng thread khi shared state đang không nhất quán.

18. Virtual Threads

18. Virtual Threads

Virtual threads make the thread-per-task model practical for large numbers of mostly-blocking tasks.

try (ExecutorService executor =
         Executors.newVirtualThreadPerTaskExecutor()) {

    List<Future<Response>> futures = requests.stream()
        .map(request -> executor.submit(() -> blockingCall(request)))
        .toList();

    for (Future<Response> future : futures) {
        handle(future.get());
    }
}

Good fit

  • Blocking HTTP calls, JDBC, file operations, and thread-per-request services.
  • Large numbers of independent tasks with simple imperative code.

Not a magic solution

  • CPU-bound work is still limited by CPU cores.
  • Database connections, sockets, rate limits, and memory remain finite.
  • ThreadLocal usage may become expensive when millions of virtual threads are created.
  • Long blocking while holding a monitor or native call can reduce scalability.
Design rule: With virtual threads, do not pool threads to limit concurrency. Use Semaphore, connection pools, rate limiters, or bounded queues to limit scarce resources.

Virtual thread giúp mô hình thread-per-task khả thi với số lượng lớn task chủ yếu bị blocking.

try (ExecutorService executor =
         Executors.newVirtualThreadPerTaskExecutor()) {

Phù hợp

  • Blocking HTTP, JDBC, file operation và service thread-per-request.
  • Số lượng lớn task độc lập với code imperative đơn giản.

Không phải giải pháp thần kỳ

  • CPU-bound vẫn bị giới hạn bởi số CPU core.
  • DB connection, socket, rate limit và memory vẫn hữu hạn.
  • ThreadLocal có thể tốn kém nếu tạo hàng triệu virtual thread.
  • Blocking lâu khi đang giữ monitor hoặc native call có thể giảm scalability.
Quy tắc thiết kế: Với virtual thread, không pool thread để giới hạn concurrency. Hãy dùng Semaphore, connection pool, rate limiter hoặc bounded queue để giới hạn resource khan hiếm.

25. Synchronous vs Asynchronous Programming

25. Lập trình Synchronous và Asynchronous

Synchronous and asynchronous describe how a caller coordinates with an operation and receives its result. They are different from the Java keyword synchronized, which protects shared mutable state.

Senior mental model: Ask three separate questions:
  1. Does the caller wait for the result?
  2. Is an operating-system or Java thread blocked while waiting?
  3. Can multiple operations actually execute in parallel?
These questions describe different dimensions and must not be treated as synonyms.

25.1 Synchronous execution

In synchronous execution, the caller invokes an operation and does not proceed to the next dependent step until the operation returns or fails.

public Order processOrder(String orderId) {
    Customer customer = customerClient.getCustomer(orderId);
    Payment payment = paymentClient.charge(orderId);

    return createOrder(customer, payment);
}
getCustomer()→ wait charge()→ wait createOrder()

If customer loading takes 500 ms, payment takes 700 ms, and local processing takes 100 ms, total response time is approximately:

500 ms + 700 ms + 100 ms = 1,300 ms

Advantages

  • Simple control flow.
  • Easy exception handling with try/catch.
  • Easier debugging and tracing.
  • Transaction and thread-local context normally remain on the same thread.

Disadvantages

  • The caller cannot continue while waiting.
  • Blocking I/O can occupy a thread for a long time.
  • Independent remote calls execute sequentially unless explicitly parallelized.
  • High blocking concurrency may require many platform threads.

25.2 Asynchronous execution

In asynchronous execution, the caller starts an operation and receives a handle, callback, event, stream, or acknowledgement instead of waiting in the traditional sequential manner.

CompletableFuture<Customer> customerFuture =
    CompletableFuture.supplyAsync(
        () -> customerClient.getCustomer(orderId),
        ioExecutor
    );

CompletableFuture<Payment> paymentFuture =
    CompletableFuture.supplyAsync(
        () -> paymentClient.charge(orderId),
        ioExecutor
    );

Order order = customerFuture
    .thenCombine(paymentFuture, this::createOrder)
    .orTimeout(2, TimeUnit.SECONDS)
    .join();
Customer API: 500 ms parallel with Payment API: 700 ms → combine Create order

When the two remote operations are independent, response time may be close to:

max(500 ms, 700 ms) + 100 ms ≈ 800 ms
Important: Asynchronous execution may reduce caller waiting or improve concurrency, but it does not automatically reduce the actual work, increase downstream capacity, or guarantee lower latency.

25.3 Synchronous does not mean single-threaded

A traditional servlet application can process many requests concurrently using many threads even though each individual request executes synchronously.

Request 1 → Thread 1 → blocking database/API call
Request 2 → Thread 2 → blocking database/API call
Request 3 → Thread 3 → blocking database/API call

Each request waits synchronously, while the application as a whole is concurrent.

25.4 Asynchronous does not automatically mean parallel

CompletableFuture<String> pipeline =
    CompletableFuture.completedFuture("order")
        .thenApply(this::validate)
        .thenApply(this::enrich)
        .thenApply(this::format);

The stages above are composable through an asynchronous API, but they are still dependent and normally run sequentially. Parallel execution requires independent tasks that can overlap.

25.5 Four important combinations

Combination Meaning Java example
Synchronous + blocking The caller waits and the current thread is parked or blocked. JDBC, RestTemplate, Future.get()
Asynchronous + blocking The caller delegates work, but a worker thread still blocks on I/O. CompletableFuture running JDBC on an executor
Asynchronous + non-blocking The operation returns immediately and waiting is managed through callbacks or an event loop without dedicating a thread. WebClient, Reactor Netty, NIO completion APIs
Synchronous + non-blocking The caller repeatedly checks or drives progress without parking a thread. This model is less common in business code. Polling a non-blocking state machine

25.6 Blocking asynchronous example

CompletableFuture<List<Customer>> future =
    CompletableFuture.supplyAsync(
        () -> jdbcTemplate.query(
            "select * from customer",
            customerMapper
        ),
        databaseExecutor
    );

The request thread may be free, but a worker thread still waits for JDBC. This is asynchronous from the caller’s perspective, but not non-blocking end to end.

25.7 Non-blocking asynchronous example with WebFlux

public Mono<Customer> getCustomer(String customerId) {
    return webClient.get()
        .uri("/customers/{id}", customerId)
        .retrieve()
        .bodyToMono(Customer.class)
        .timeout(Duration.ofSeconds(2));
}

While waiting for the network response, an event-loop thread can process other connections. When data becomes available, the pipeline is resumed.

Do not block an event-loop thread: Calling JDBC, Thread.sleep(), Future.get(), join(), or slow file I/O on a WebFlux event-loop thread can severely reduce throughput.

25.8 synchronized is a different concept

public synchronized void increment() {
    count++;
}

synchronized provides mutual exclusion and Java Memory Model visibility around a critical section. It does not describe whether an API call is synchronous or asynchronous.

@Async("workerExecutor")
public void updateInBackground() {
    synchronized (lock) {
        sharedState++;
    }
}

The method is asynchronous relative to its caller, while the critical section uses synchronized to protect shared state.

25.9 Ways to perform asynchronous work in Java

Creating a raw Thread

new Thread(this::sendEmail).start();

Suitable for demonstrations, but usually inappropriate in server applications because lifecycle, naming, capacity, cancellation, and monitoring are uncontrolled.

ExecutorService

ExecutorService executor = Executors.newFixedThreadPool(10);
executor.submit(this::sendEmail);

An executor separates the task from its execution policy. For production systems, explicitly configure queue capacity and rejection behavior.

ThreadPoolExecutor executor = new ThreadPoolExecutor(
    5,
    10,
    60,
    TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100),
    new NamedThreadFactory("email-worker"),
    new ThreadPoolExecutor.CallerRunsPolicy()
);

Future

Future<String> result = executor.submit(this::loadData);

String value = result.get(); // blocks the caller

The task runs on another thread, but calling get() turns result retrieval into a blocking operation.

CompletableFuture

CompletableFuture<Summary> summaryFuture =
    CompletableFuture
        .supplyAsync(this::loadCustomer, customerExecutor)
        .thenCombine(
            CompletableFuture.supplyAsync(this::loadOrders, orderExecutor),
            Summary::new
        )
        .orTimeout(2, TimeUnit.SECONDS)
        .exceptionally(this::fallback);
Method Purpose
thenApplyTransforms T into U.
thenComposeChains T into CompletableFuture<U> and flattens the nested future.
thenCombineCombines two independent results.
allOfWaits for multiple futures to finish.
anyOfCompletes when the first future completes.
exceptionallyRecovers from failure.
handleProcesses either a result or an exception.

thenApply vs thenCompose

// T → U
CompletableFuture<UserDto> dto =
    userFuture.thenApply(this::toDto);

// T → CompletableFuture<U>
CompletableFuture<Order> order =
    userFuture.thenCompose(
        user -> loadLatestOrder(user.id())
    );

Async suffix and executor selection

Methods such as thenApply() may run on the thread that completes the previous stage. Methods such as thenApplyAsync() schedule execution through an executor. Without an explicit executor, the common ForkJoinPool is frequently used.

Production rule: Do not accidentally run blocking HTTP, JDBC, or file I/O on the common ForkJoinPool. Use a named, bounded executor dedicated to that dependency or workload.

Self-invocation pitfall

@Service
public class OrderService {

    public void createOrder() {
        sendEmailAsync(); // does not pass through Spring proxy
    }

    @Async
    public void sendEmailAsync() {
        // may execute on the caller thread
    }
}

Spring commonly implements @Async through a proxy. A call from one method to another method on the same object bypasses that proxy. Move the asynchronous method to another Spring bean or redesign the boundary.

Context propagation

When execution moves to another thread, the following context may not move automatically:

  • Transaction and persistence context.
  • SecurityContext.
  • Logging MDC and trace identifiers.
  • Request-scoped state.
  • Custom ThreadLocal values.

Use explicit context propagation, task decorators, framework-supported propagation, or pass required values as method arguments.

25.11 Asynchronous execution and transactions

@Transactional
public void createOrder(Order order) {
    orderRepository.save(order);
    emailService.sendEmailAsync(order.id());

    throw new RuntimeException("Rollback order");
}

The asynchronous task may already have been submitted even though the transaction later rolls back. The email can therefore be sent for an order that was never committed.

@Async together with @Transactional

@Async("workerExecutor")
@Transactional
public void processAsync(String orderId) {
    // starts or joins a transaction on the worker thread,
    // not the caller's original transaction
}

The caller’s transaction normally does not continue on the worker thread. The asynchronous method creates its own transaction boundary when Spring applies @Transactional there.

After-commit event

@TransactionalEventListener(
    phase = TransactionPhase.AFTER_COMMIT
)
public void handle(OrderCreatedEvent event) {
    emailService.sendEmailAsync(event.orderId());
}

This prevents the listener from running before the transaction commits, but it still does not guarantee durable delivery if the process crashes after commit.

Transactional Outbox

  1. Write the business record and an outbox event in the same database transaction.
  2. A separate publisher reads committed outbox events.
  3. The publisher sends them to a broker.
  4. The consumer processes events idempotently.
Production guidance: For important side effects such as payment, email, inventory, or integration events, prefer durable messaging and idempotency over fire-and-forget in-memory asynchronous execution.

25.12 Error handling

Executor execute() vs submit()

execute(Runnable) An uncaught exception reaches the worker thread’s uncaught-exception handling.
submit(Runnable/Callable) The exception is captured inside Future and appears through get() as ExecutionException.

CompletableFuture exception operators

future
    .orTimeout(2, TimeUnit.SECONDS)

            log.error("Async operation failed", error);
            return fallbackResult();

        return result;

Fire-and-forget risk

If no one observes the returned Future, failures may be lost or appear only in logs. Important asynchronous tasks need ownership, retry policy, dead-letter handling, metrics, and correlation IDs.

25.13 Cancellation and interruption

Calling Future.cancel(true) requests interruption. It cannot safely force a task to stop.

public void runTask() {
    try {
        while (!Thread.currentThread().isInterrupted()) {
            Job job = queue.take();
            process(job);
        }
    } catch (InterruptedException ex) {
        Thread.currentThread().interrupt();
    } finally {
        cleanup();
    }
}

Cancellation should be propagated through the complete asynchronous chain where practical. Blocking calls need explicit timeouts because interruption support varies by API and driver.

25.14 Backpressure and overload

Asynchronous APIs make it easy to submit work faster than it can be completed. Without bounds, the queue becomes hidden memory consumption and hidden latency.

Incoming rate: 2,000 tasks/second
Processing rate: 1,200 tasks/second
Queue growth: 800 tasks/second

Even if the application appears healthy initially, backlog grows continuously.

Backpressure techniques

  • Bounded executor queue.
  • CallerRunsPolicy.
  • Semaphore around downstream calls.
  • Rate limiter.
  • Reactive demand control.
  • Reject with 429 or 503.

Metrics

  • Active workers.
  • Queue depth and remaining capacity.
  • Queue wait time.
  • Task duration.
  • Rejected task count.
  • Downstream timeout and connection-pool usage.

25.15 When asynchronous programming helps

  • Independent I/O calls can run concurrently.
  • A long operation should not hold an HTTP request open.
  • Background email, report generation, audit, or integration work is acceptable.
  • A producer and consumer need to be decoupled through a queue or broker.
  • End-to-end non-blocking infrastructure is available and high concurrency is required.

25.16 When synchronous programming is better

  • The caller immediately needs the result.
  • The operation is short and simple.
  • Steps are strongly dependent and cannot overlap.
  • A single transaction must cover the complete operation.
  • Async complexity would not provide meaningful capacity or latency benefits.
Senior decision: Choose the simplest model that satisfies throughput, latency, reliability, and resource constraints. Asynchronous code is not automatically more scalable, and synchronous code is not automatically slow.

25.18 Interview questions and strong answers

01What is the difference between synchronous and asynchronous execution?
Strong answer: Synchronous execution makes the caller wait for an operation before continuing. Asynchronous execution decouples initiation from completion using a Future, callback, event, or stream. I would additionally distinguish blocking from non-blocking and concurrency from parallelism because they are independent dimensions.
02Does asynchronous always mean non-blocking?
Strong answer: No. CompletableFuture can run blocking JDBC on a worker thread. The caller is asynchronous, but the worker remains blocked. End-to-end non-blocking requires non-blocking drivers and event-driven APIs throughout the call chain.
03Does synchronous mean single-threaded?
Strong answer: No. A servlet server can process thousands of synchronous requests concurrently using a thread pool. Synchronous describes each call’s waiting behavior, not the total number of application threads.
04What is the difference between asynchronous and parallel execution?
Strong answer: Asynchronous describes how completion is communicated and whether the caller must wait. Parallel execution means work actually runs at the same instant on multiple execution units. An asynchronous pipeline can still be sequential, and parallel work can still be synchronously joined.
05Why can @Async and @Transactional be dangerous together?
Strong answer: Spring transactions are thread-bound. An @Async method runs on another thread, so it does not continue the caller’s transaction. The caller can also roll back after submitting async work. For important events I use after-commit handling or a transactional outbox with idempotent consumers.
06Why might @Async not work during self-invocation?
Strong answer: @Async is commonly applied through a Spring proxy. Calling another method on the same object does not pass through that proxy, so the interceptor does not submit the work to the executor.
07What is wrong with using CompletableFuture without a custom executor?
Strong answer: Async stages may use the common ForkJoinPool, which is shared with unrelated work and optimized mainly for compute tasks. Blocking I/O can starve the pool and create cross-feature interference. I use named, bounded executors with metrics and rejection policies.
08How do you handle overload in an asynchronous service?
Strong answer: I bound queues and downstream concurrency, define rejection or degradation behavior, enforce timeouts, and monitor queue wait and rejection. For durable work I use a broker rather than accumulating tasks in process memory.
09When would you choose WebFlux over CompletableFuture?
Strong answer: WebFlux is attractive when the pipeline is non-blocking end to end, concurrency is high, backpressure matters, and the team can operate the reactive model. CompletableFuture is often simpler for combining a limited number of asynchronous operations in an otherwise imperative application.
10When would you deliberately keep processing synchronous?
Strong answer: When the caller needs the result, the operation is short, transaction boundaries must remain simple, tasks cannot meaningfully overlap, or asynchronous complexity would not improve capacity or latency.

25.1 Synchronous execution

Trong synchronous execution, caller gọi operation và không tiếp tục bước phụ thuộc tiếp theo cho tới khi operation trả kết quả hoặc thất bại.

public Order processOrder(String orderId) {
    Customer customer = customerClient.getCustomer(orderId);
    Payment payment = paymentClient.charge(orderId);

    return createOrder(customer, payment);
}
getCustomer()→ chờ charge()→ chờ createOrder()

Nếu tải customer mất 500 ms, payment mất 700 ms và xử lý local mất 100 ms thì tổng thời gian gần đúng là:

500 ms + 700 ms + 100 ms = 1.300 ms

Ưu điểm

  • Control flow đơn giản.
  • Dễ xử lý exception bằng try/catch.
  • Dễ debug và trace.
  • Transaction và thread-local context thường vẫn ở cùng thread.

Nhược điểm

  • Caller không thể tiếp tục khi đang chờ.
  • Blocking I/O có thể chiếm thread trong thời gian dài.
  • Các remote call độc lập vẫn chạy tuần tự nếu không chủ động parallelize.
  • Blocking concurrency cao có thể cần nhiều platform thread.

25.2 Asynchronous execution

Trong asynchronous execution, caller khởi động operation và nhận về handle, callback, event, stream hoặc acknowledgement thay vì phải chờ theo flow tuần tự truyền thống.

CompletableFuture<Customer> customerFuture =
    CompletableFuture.supplyAsync(
        () -> customerClient.getCustomer(orderId),
        ioExecutor
    );

CompletableFuture<Payment> paymentFuture =
    CompletableFuture.supplyAsync(
        () -> paymentClient.charge(orderId),
        ioExecutor
    );

Order order = customerFuture
    .thenCombine(paymentFuture, this::createOrder)
    .orTimeout(2, TimeUnit.SECONDS)
    .join();
Customer API: 500 ms chạy song song với Payment API: 700 ms → combine Create order

Khi hai remote operation độc lập, response time có thể gần:

max(500 ms, 700 ms) + 100 ms ≈ 800 ms
Quan trọng: Asynchronous có thể giảm thời gian caller phải chờ hoặc tăng concurrency, nhưng không tự động giảm lượng công việc, tăng capacity của downstream hay đảm bảo latency thấp hơn.

25.3 Synchronous không có nghĩa là single-thread

Một ứng dụng servlet truyền thống có thể xử lý nhiều request đồng thời bằng nhiều thread, dù từng request riêng lẻ chạy synchronous.

Request 1 → Thread 1 → blocking database/API call
Request 2 → Thread 2 → blocking database/API call
Request 3 → Thread 3 → blocking database/API call

Mỗi request phải chờ synchronously, nhưng toàn ứng dụng vẫn concurrent.

25.4 Asynchronous không tự động có nghĩa là parallel

CompletableFuture<String> pipeline =
    CompletableFuture.completedFuture("order")
        .thenApply(this::validate)
        .thenApply(this::enrich)
        .thenApply(this::format);

Các stage dùng API có khả năng asynchronous nhưng vẫn phụ thuộc nhau và thường chạy tuần tự. Muốn parallel cần các task độc lập có thể overlap.

25.5 Bốn tổ hợp quan trọng

Tổ hợp Ý nghĩa Ví dụ Java

25.6 Ví dụ asynchronous nhưng vẫn blocking

CompletableFuture<List<Customer>> future =
    CompletableFuture.supplyAsync(
        () -> jdbcTemplate.query(
            "select * from customer",
            customerMapper
        ),
        databaseExecutor
    );

Request thread có thể được giải phóng, nhưng worker thread vẫn chờ JDBC. Đây là asynchronous từ góc nhìn caller nhưng không phải non-blocking end to end.

25.7 Ví dụ asynchronous non-blocking với WebFlux

public Mono<Customer> getCustomer(String customerId) {
    return webClient.get()
        .uri("/customers/{id}", customerId)
        .retrieve()
        .bodyToMono(Customer.class)
        .timeout(Duration.ofSeconds(2));
}

Trong thời gian chờ network response, event-loop thread có thể xử lý connection khác. Khi dữ liệu về, pipeline được resume.

Không block event-loop thread: Gọi JDBC, Thread.sleep(), Future.get(), join() hoặc file I/O chậm trên WebFlux event-loop thread có thể làm throughput giảm nghiêm trọng.

25.8 synchronized là khái niệm khác

public synchronized void increment() {
    count++;
}

synchronized cung cấp mutual exclusion và visibility theo Java Memory Model quanh critical section. Nó không mô tả API call là synchronous hay asynchronous.

@Async("workerExecutor")
public void updateInBackground() {
    synchronized (lock) {
        sharedState++;
    }
}

Method chạy asynchronous so với caller, trong khi critical section dùng synchronized để bảo vệ shared state.

25.13 Cancellation và interruption

Gọi Future.cancel(true) chỉ gửi yêu cầu interruption. Nó không thể cưỡng chế dừng task một cách an toàn.

Dù ứng dụng ban đầu trông vẫn ổn, backlog sẽ tăng liên tục.

  • CallerRunsPolicy.
  • Semaphore quanh downstream call.
  • Rate limiter.
  • Reactive demand control.
  • Reject bằng 429 hoặc 503.

  • Các I/O call độc lập có thể chạy đồng thời.
  • Một operation dài không nên giữ HTTP request mở.
  • Background email, report generation, audit hoặc integration work được phép xử lý sau.
  • Producer và consumer cần decouple qua queue hoặc broker.
  • Có hạ tầng non-blocking end to end và yêu cầu concurrency cao.

25.16 Khi synchronous tốt hơn

  • Caller cần ngay kết quả.
  • Operation ngắn và đơn giản.
  • Các bước phụ thuộc chặt và không thể overlap.
  • Một transaction cần bao phủ toàn bộ operation.
  • Async complexity không mang lại lợi ích capacity hoặc latency rõ ràng.
Quyết định ở cấp Senior: Chọn mô hình đơn giản nhất đáp ứng throughput, latency, reliability và giới hạn resource. Async không tự động scalable hơn và synchronous không tự động chậm.

25.17 Production checklist

25.18 Câu hỏi phỏng vấn và câu trả lời tốt

01Synchronous và asynchronous khác nhau như thế nào?
Câu trả lời tốt: Synchronous khiến caller phải chờ operation trước khi tiếp tục. Asynchronous tách thời điểm khởi tạo khỏi thời điểm hoàn tất thông qua Future, callback, event hoặc stream. Em cũng sẽ phân biệt thêm blocking với non-blocking và concurrency với parallelism vì đây là các chiều độc lập.
02Asynchronous có luôn đồng nghĩa với non-blocking không?
Câu trả lời tốt: Không. CompletableFuture có thể chạy JDBC blocking trên worker thread. Caller thấy asynchronous nhưng worker vẫn bị block. Muốn non-blocking end to end cần non-blocking driver và event-driven API trong toàn bộ call chain.
03Synchronous có nghĩa là single-thread không?
Câu trả lời tốt: Không. Servlet server có thể xử lý hàng nghìn synchronous request concurrent bằng thread pool. Synchronous mô tả hành vi chờ của từng call, không mô tả tổng số thread của application.
04Asynchronous và parallel khác nhau thế nào?
Câu trả lời tốt: Asynchronous mô tả cách completion được thông báo và caller có phải chờ không. Parallel nghĩa là công việc thực sự chạy cùng thời điểm trên nhiều execution unit. Async pipeline vẫn có thể sequential và parallel work vẫn có thể được caller join synchronously.
05Tại sao @Async và @Transactional kết hợp có thể nguy hiểm?
Câu trả lời tốt: Spring transaction gắn với thread. @Async chạy trên thread khác nên không tiếp tục transaction của caller. Caller cũng có thể rollback sau khi đã submit async task. Với event quan trọng nên dùng after-commit hoặc transactional outbox kết hợp idempotent consumer.
06Tại sao @Async có thể không hoạt động khi self-invocation?
Câu trả lời tốt: @Async thường được áp dụng qua Spring proxy. Gọi method khác trên cùng object không đi qua proxy nên interceptor không submit công việc vào executor.
07Vấn đề khi dùng CompletableFuture mà không truyền custom executor?
Câu trả lời tốt: Async stage có thể dùng common ForkJoinPool, vốn được chia sẻ với chức năng khác và chủ yếu tối ưu cho compute task. Blocking I/O có thể làm pool thiếu worker và gây ảnh hưởng chéo. Nên dùng named bounded executor có metric và rejection policy.
08Xử lý overload trong asynchronous service như thế nào?
Câu trả lời tốt: Em giới hạn queue và downstream concurrency, định nghĩa rejection hoặc degradation, bắt buộc timeout và theo dõi queue wait/rejection. Với công việc cần durability, em dùng broker thay vì tích lũy task trong process memory.
09Khi nào chọn WebFlux thay vì CompletableFuture?
Câu trả lời tốt: WebFlux phù hợp khi pipeline non-blocking end to end, concurrency cao, backpressure quan trọng và team có khả năng vận hành reactive model. CompletableFuture thường đơn giản hơn khi chỉ combine một số lượng giới hạn async operation trong ứng dụng imperative.
10Khi nào chủ động giữ flow synchronous?
Câu trả lời tốt: Khi caller cần result ngay, operation ngắn, transaction boundary cần đơn giản, task không thể overlap có ý nghĩa hoặc async complexity không cải thiện capacity hay latency.

26. Senior Java Multithreading Interview Questions

26. Câu hỏi phỏng vấn Java Multithreading cấp Senior

Open each question and practice answering in 60–120 seconds. Start with the definition, explain the internal mechanism, discuss trade-offs, and finish with a production example.

Mở từng câu và luyện trả lời trong 60–120 giây. Bắt đầu bằng khái niệm, giải thích cơ chế, trade-off và kết thúc bằng ví dụ production.

01 What is thread safety?
Strong answer: Thread safety means code preserves its correctness guarantees when accessed concurrently, without callers needing extra synchronization. A strong answer should mention atomicity, visibility, ordering, safe publication, and protection of invariants.
Câu trả lời tốt: Thread safety nghĩa là code vẫn giữ đúng tính đúng đắn khi được nhiều thread truy cập đồng thời mà caller không cần tự đồng bộ thêm. Câu trả lời tốt cần nhắc atomicity, visibility, ordering, safe publication và bảo vệ invariant.
02 What is the difference between synchronized and volatile?
Strong answer: synchronized provides mutual exclusion and visibility for a critical section. volatile provides visibility and ordering for one variable but does not protect compound operations or multi-field invariants.
Câu trả lời tốt: synchronized cung cấp mutual exclusion và visibility cho critical section. volatile cung cấp visibility và ordering cho một biến nhưng không bảo vệ compound operation hoặc invariant gồm nhiều field.
03 Why is count++ not thread-safe?
Strong answer: It consists of read, increment, and write. Threads can interleave these steps and overwrite each other, producing a lost update.
Câu trả lời tốt: Vì nó gồm đọc, cộng và ghi. Nhiều thread có thể xen kẽ các bước này và ghi đè kết quả của nhau.
04 What is happens-before?
Strong answer: It is a Java Memory Model ordering relation. If action A happens-before action B, B is guaranteed to observe A’s effects, subject to the semantics of the actions involved.
Câu trả lời tốt: Đây là quan hệ ordering của Java Memory Model. Nếu A happens-before B thì B được đảm bảo thấy effect của A.
05 Can synchronized methods on two different objects block each other?
Strong answer: Not normally. Instance synchronized methods lock each object’s monitor. They block each other only when they synchronize on the same monitor or shared lock object.
Câu trả lời tốt: Thông thường không. Instance synchronized method lock monitor của từng object. Chúng chỉ block nhau nếu dùng cùng monitor hoặc cùng shared lock.
06 What is reentrancy?
Strong answer: A reentrant lock allows a thread that already owns the lock to acquire it again. Both synchronized and ReentrantLock are reentrant.
Câu trả lời tốt: Reentrant lock cho phép thread đang giữ lock acquire lại lock đó. synchronized và ReentrantLock đều reentrant.
07 When would you use ReentrantLock instead of synchronized?
Strong answer: When timed acquisition, interruptible acquisition, fairness, multiple Condition queues, or explicit lock management is required. Otherwise synchronized is often simpler and safer.
Câu trả lời tốt: Dùng khi cần timed acquisition, interruptible acquisition, fairness, nhiều Condition queue hoặc quản lý lock tường minh. Nếu không, synchronized thường đơn giản hơn.
08 What is the difference between wait() and sleep()?
Strong answer: wait releases the current object monitor and must be called while holding it. sleep pauses the thread for a duration and does not release locks.
Câu trả lời tốt: wait release monitor của object hiện tại và phải gọi khi đang giữ monitor. sleep tạm dừng thread nhưng không release lock.
09 Why should wait() be called in a loop?
Strong answer: Because of spurious wake-ups and because another thread may consume or change the condition before the awakened thread reacquires the monitor.
Câu trả lời tốt: Vì có spurious wake-up và vì thread khác có thể thay đổi condition trước khi thread vừa thức giành lại monitor.
10 notify() or notifyAll()?
Strong answer: notify wakes one arbitrary waiter. notifyAll wakes all waiters, which re-check their conditions. notifyAll is safer when multiple logical conditions share a monitor, though it can cause more contention.
Câu trả lời tốt: notify đánh thức một waiter bất kỳ. notifyAll đánh thức tất cả để tự kiểm tra lại condition. notifyAll an toàn hơn khi nhiều condition logic dùng chung monitor nhưng gây contention lớn hơn.
11 How does ThreadPoolExecutor decide to create threads?
Strong answer: It first grows to corePoolSize, then queues tasks, then grows toward maximumPoolSize only when the queue is full, and finally rejects.
Câu trả lời tốt: Nó tăng tới corePoolSize, sau đó queue task, chỉ tăng tới maximumPoolSize khi queue đầy, rồi mới reject.
12 Why is an unbounded executor queue dangerous?
Strong answer: It can hide overload by accumulating tasks indefinitely, increasing latency and memory use until the process becomes unstable or runs out of memory.
Câu trả lời tốt: Nó che giấu overload bằng cách tích lũy task vô hạn, làm tăng latency và memory cho tới khi process bất ổn hoặc OOM.
13 How do you size a thread pool?
Strong answer: Classify the workload as CPU-bound or blocking, estimate wait-to-compute ratio, respect downstream capacity, then validate with load tests and production metrics. There is no universal fixed number.
Câu trả lời tốt: Phân loại CPU-bound hay blocking, ước lượng tỷ lệ wait/compute, tôn trọng capacity downstream rồi kiểm chứng bằng load test và metric. Không có một con số cố định cho mọi hệ thống.
14 What is backpressure?
Strong answer: It is a mechanism that prevents producers from overwhelming consumers, for example by using bounded queues, blocking submission, caller-runs, rate limiting, or rejection.
Câu trả lời tốt: Đây là cơ chế ngăn producer làm quá tải consumer, ví dụ bounded queue, block khi submit, caller-runs, rate limiting hoặc rejection.
15 What happens when a task submitted to ExecutorService throws an exception?
Strong answer: With execute(), an uncaught exception reaches the worker thread’s uncaught-exception handling. With submit(), it is captured by Future and rethrown from get() as ExecutionException.
Câu trả lời tốt: Với execute(), exception chưa xử lý đi tới uncaught-exception handler của worker. Với submit(), exception được giữ trong Future và get() ném ExecutionException.
16 execute() vs submit()?
Strong answer: execute accepts Runnable and returns nothing. submit accepts Runnable or Callable and returns a Future, capturing exceptions in that Future.
Câu trả lời tốt: execute nhận Runnable và không trả kết quả. submit nhận Runnable hoặc Callable và trả Future, đồng thời giữ exception trong Future.
17 shutdown() vs shutdownNow()?
Strong answer: shutdown stops accepting new tasks and lets submitted tasks finish. shutdownNow attempts to interrupt running tasks and returns tasks that never started; cancellation is still cooperative.
Câu trả lời tốt: shutdown ngừng nhận task mới và cho task đã submit chạy xong. shutdownNow cố interrupt task đang chạy và trả về task chưa chạy; cancellation vẫn mang tính cooperative.
18 What is a deadlock and how do you diagnose it?
Strong answer: A deadlock is a circular wait among threads holding resources. Diagnose using repeated thread dumps or JFR; look for Java-level deadlock reports and threads mutually waiting on monitors.
Câu trả lời tốt: Deadlock là circular wait giữa các thread đang giữ resource. Chẩn đoán bằng nhiều thread dump hoặc JFR; tìm báo cáo deadlock và các thread chờ monitor của nhau.
19 How do you prevent deadlock in fund transfer?
Strong answer: Use deterministic lock ordering, such as locking accounts by stable ID order, or use tryLock with timeout and retry. Keep lock scope small.
Câu trả lời tốt: Dùng thứ tự lock cố định, ví dụ lock account theo ID, hoặc tryLock với timeout và retry. Giữ phạm vi lock nhỏ.
20 What is starvation?
Strong answer: A thread is ready but repeatedly denied access to CPU, a lock, or another resource. Causes include unfair locking, priority misuse, and long critical sections.
Câu trả lời tốt: Một thread sẵn sàng nhưng liên tục không được cấp CPU, lock hoặc resource. Nguyên nhân gồm unfair lock, lạm dụng priority và critical section quá dài.
21 What is livelock?
Strong answer: Threads are not blocked but repeatedly react to one another in a way that prevents progress, such as both backing off and retrying in sync.
Câu trả lời tốt: Thread không bị block nhưng liên tục phản ứng với nhau khiến không tiến triển, ví dụ cùng backoff và retry đồng bộ.
22 AtomicInteger vs LongAdder?
Strong answer: AtomicInteger gives an exact atomic value and CAS-based updates. LongAdder improves update throughput under heavy contention by spreading writes, but sum() is not an atomic snapshot.
Câu trả lời tốt: AtomicInteger cho giá trị atomic chính xác bằng CAS. LongAdder tăng throughput khi contention cao bằng cách phân tán write, nhưng sum() không phải atomic snapshot.
23 Is ConcurrentHashMap enough for compound operations?
Strong answer: Not automatically. Use atomic map methods such as compute, merge, replace, and putIfAbsent, or coordinate externally when multiple keys or structures form one invariant.
Câu trả lời tốt: Không tự động. Dùng compute, merge, replace, putIfAbsent hoặc cơ chế bên ngoài khi invariant liên quan nhiều key hay nhiều structure.
24 What is safe publication?
Strong answer: Making an object visible to other threads in a way that guarantees they see a fully constructed state. Examples include static initialization, volatile references, final-field guarantees, locks, and concurrent collections.
Câu trả lời tốt: Làm object visible cho thread khác sao cho chúng thấy trạng thái đã khởi tạo đầy đủ. Ví dụ static initialization, volatile reference, final-field guarantee, lock và concurrent collection.
25 Why should fields often be final in concurrent code?
Strong answer: Final fields support immutability and have special initialization safety guarantees, reducing the number of states and synchronization requirements.
Câu trả lời tốt: Final field hỗ trợ immutability và có guarantee đặc biệt khi khởi tạo, giúp giảm số trạng thái và nhu cầu đồng bộ.
26 What is false sharing?
Strong answer: Independent hot variables located on the same cache line cause cores to invalidate each other’s cache, reducing performance even though the variables are logically unrelated.
Câu trả lời tốt: Các biến nóng độc lập nằm cùng cache line khiến các core liên tục invalidate cache của nhau, làm giảm hiệu năng dù logic không liên quan.
27 What is context switching overhead?
Strong answer: The CPU and OS save and restore execution state when switching threads. Excessive runnable threads can increase scheduler overhead, cache misses, and latency.
Câu trả lời tốt: CPU và OS phải lưu/khôi phục trạng thái khi chuyển thread. Quá nhiều runnable thread làm tăng scheduler overhead, cache miss và latency.
28 Why is blocking in ForkJoinPool risky?
Strong answer: ForkJoinPool is optimized for short compute tasks and work stealing. Blocking can reduce available workers and stall unrelated tasks unless compensation or managed blocking occurs.
Câu trả lời tốt: ForkJoinPool tối ưu cho task tính toán ngắn và work stealing. Blocking có thể làm thiếu worker và kẹt task khác.
29 parallelStream: when should you avoid it?
Strong answer: Avoid it for blocking I/O, small data sets, order-sensitive side effects, shared mutable state, request-serving code that needs isolation, or when common-pool interference matters.
Câu trả lời tốt: Tránh dùng cho blocking I/O, dữ liệu nhỏ, side effect phụ thuộc thứ tự, shared mutable state, request cần isolation hoặc khi common pool gây ảnh hưởng lẫn nhau.
30 How do CompletableFuture exceptions work?
Strong answer: Exceptions propagate through dependent stages. handle observes success or failure; exceptionally recovers from failure; whenComplete observes without changing the result unless it throws.
Câu trả lời tốt: Exception propagate qua các stage phụ thuộc. handle xử lý cả success/failure; exceptionally recover failure; whenComplete quan sát kết quả và thường không đổi result.
31 thenApply vs thenCompose?
Strong answer: thenApply maps a value to another value. thenCompose chains an asynchronous operation and flattens nested CompletableFuture results.
Câu trả lời tốt: thenApply map value sang value khác. thenCompose chain async operation và flatten CompletableFuture lồng nhau.
32 What is the risk of ThreadLocal in a thread pool?
Strong answer: Pool threads are reused. If values are not removed, data may leak between tasks and retain objects in memory. Always clean up in finally or use controlled context propagation.
Câu trả lời tốt: Thread trong pool được tái sử dụng. Nếu không remove, dữ liệu có thể rò giữa các task và giữ object trong memory. Luôn cleanup trong finally hoặc propagate có kiểm soát.
33 How does @Async work in Spring?
Strong answer: Typically through a proxy that submits the method invocation to an Executor. Self-invocation bypasses the proxy, and caller transaction/request context does not automatically move to the worker thread.
Câu trả lời tốt: Thường qua proxy submit method invocation vào Executor. Self-invocation bỏ qua proxy và transaction/request context của caller không tự động chuyển sang worker.
34 Can @Transactional and @Async be used together?
Strong answer: Yes, but transaction boundaries must be understood. The async method runs in another thread, so it normally starts its own transaction if annotated; it does not continue the caller’s transaction.
Câu trả lời tốt: Có, nhưng phải hiểu transaction boundary. Async method chạy thread khác nên thường tạo transaction riêng nếu được annotate; nó không tiếp tục transaction của caller.
35 What are virtual threads best for?
Strong answer: High-concurrency workloads that spend much of their time blocking on I/O while benefiting from simple thread-per-task code.
Câu trả lời tốt: Workload concurrency cao dành nhiều thời gian blocking I/O và muốn giữ code thread-per-task đơn giản.
36 Do virtual threads remove the need for connection pools?
Strong answer: No. Connections are scarce external resources. Virtual threads reduce thread cost, not database or socket limits.
Câu trả lời tốt: Không. Connection vẫn là external resource hữu hạn. Virtual thread giảm chi phí thread chứ không tăng giới hạn database hay socket.
37 How do you limit concurrency with virtual threads?
Strong answer: Use semaphores, rate limiters, bounded queues, and resource pools around scarce dependencies, rather than pooling virtual threads simply to limit count.
Câu trả lời tốt: Dùng semaphore, rate limiter, bounded queue và resource pool quanh dependency hữu hạn, thay vì pool virtual thread chỉ để giới hạn số lượng.
38 How do you troubleshoot a saturated executor?
Strong answer: Check active threads, pool size, queue depth, queue wait, task duration, rejection count, downstream latency, connection-pool usage, CPU, and repeated thread dumps.
Câu trả lời tốt: Kiểm tra active thread, pool size, queue depth, queue wait, task duration, rejection, downstream latency, connection pool, CPU và nhiều thread dump.
39 What does a senior engineer consider before adding concurrency?
Strong answer: Correctness model, ownership of mutable state, expected throughput, latency target, downstream capacity, overload policy, failure propagation, cancellation, observability, and operational simplicity.
Câu trả lời tốt: Senior cần xem correctness model, ownership của mutable state, throughput, latency target, capacity downstream, overload policy, failure propagation, cancellation, observability và độ đơn giản vận hành.

27. Senior System Scenarios

27. Tình huống hệ thống cấp Senior

Scenario 1: Order processing overload

Tình huống 1: Order processing bị overload

Problem: A service receives 2,000 orders/s. It uses a fixed pool of 200 threads and an unbounded queue. Database connections are limited to 30. Latency climbs for 20 minutes before the JVM runs out of memory. What is wrong?

Vấn đề: Service nhận 2.000 order/s, dùng fixed pool 200 thread và unbounded queue. DB pool chỉ có 30 connection. Latency tăng trong 20 phút rồi JVM OOM. Vấn đề là gì?

Senior answer: The executor accepts work faster than the database can process it. The unbounded queue hides overload, retains task payloads, and increases queueing latency. The real concurrency limit is near the database pool capacity. Use a bounded queue, explicit rejection/backpressure, right-size workers to downstream capacity, add timeouts, measure queue wait, and scale or optimize the database path.
Câu trả lời Senior: Executor nhận việc nhanh hơn database xử lý. Unbounded queue che giấu overload, giữ payload trong memory và tăng queue latency. Giới hạn thực tế gần với DB pool. Cần bounded queue, rejection/backpressure rõ ràng, chỉnh worker theo downstream, thêm timeout, đo queue wait và scale/optimize DB.

Scenario 2: Duplicate payment

Tình huống 2: Thanh toán bị trùng

Problem: Two request threads check that a payment is not completed, then both call the provider and mark it completed. How would you fix it?

Vấn đề: Hai request thread cùng kiểm tra payment chưa hoàn tất, cùng gọi provider rồi cùng mark completed. Sửa thế nào?

Senior answer: A local synchronized block is insufficient in a multi-instance service. Use a database uniqueness constraint or atomic state transition, idempotency key, compare-and-set update such as UPDATE ... WHERE status='PENDING', and provider-side idempotency. Design the operation to be idempotent across retries and instances.
Câu trả lời Senior: Synchronized local không đủ trong service nhiều instance. Cần unique constraint hoặc atomic state transition ở DB, idempotency key, CAS update kiểu UPDATE ... WHERE status='PENDING' và idempotency phía provider. Thiết kế operation idempotent qua retry và nhiều instance.

Scenario 3: Slow external partner

Tình huống 3: External partner chậm

Problem: One partner API becomes slow and consumes all request threads, causing unrelated endpoints to time out. What design changes would you make?

Vấn đề: Một partner API chậm chiếm hết request thread làm endpoint khác timeout. Anh sẽ thay đổi thiết kế gì?

Senior answer: Use dependency-specific bulkheads: a dedicated executor or semaphore, strict connect/read/overall timeouts, circuit breaker, bounded queue, rejection or fallback, and metrics. Do not let one dependency consume the global worker pool.
Câu trả lời Senior: Dùng bulkhead riêng cho dependency: executor hoặc semaphore riêng, timeout connect/read/overall, circuit breaker, bounded queue, rejection/fallback và metric. Không để một dependency chiếm global worker pool.

Scenario 4: @Async did not run asynchronously

Tình huống 4: @Async không chạy bất đồng bộ

Problem: A method inside a Spring service calls another @Async method in the same class, but logs show the same thread. Why?

Vấn đề: Một method trong Spring service gọi method @Async khác trong cùng class nhưng log vẫn cùng thread. Tại sao?

Senior answer: Self-invocation does not pass through the Spring proxy, so the interceptor is not applied. Move the async method to another bean, inject the proxied bean, or redesign the boundary.
Câu trả lời Senior: Self-invocation không đi qua Spring proxy nên interceptor không được áp dụng. Chuyển async method sang bean khác, gọi qua proxy bean hoặc thiết kế lại boundary.

Scenario 5: Deadlock in account transfer

Tình huống 5: Deadlock khi chuyển tiền

Problem: Transfers lock the source account and then destination account. Production occasionally freezes. What is your fix and verification plan?

Vấn đề: Transfer lock source account rồi destination account. Production thỉnh thoảng bị freeze. Cách sửa và xác minh?

Senior answer: Acquire locks in deterministic order using account IDs, or use timed tryLock with rollback. Reduce lock scope. Capture repeated thread dumps to confirm circular wait, add contention metrics, and run a stress test with opposing transfers.
Câu trả lời Senior: Acquire lock theo thứ tự cố định dựa trên account ID hoặc timed tryLock kèm rollback. Giảm phạm vi lock. Chụp nhiều thread dump xác nhận circular wait, thêm contention metric và stress test transfer ngược chiều.

Scenario 6: Moving to virtual threads

Tình huống 6: Chuyển sang virtual thread

Problem: A team replaces a 100-thread pool with virtual threads and suddenly opens thousands of concurrent database requests. What was missed?

Vấn đề: Team thay pool 100 thread bằng virtual thread và đột nhiên mở hàng nghìn DB request đồng thời. Đã bỏ sót điều gì?

Senior answer: The old thread pool accidentally acted as a concurrency limiter. Virtual threads removed that limit, but database capacity remained finite. Add explicit permits or rely on a correctly sized connection pool, plus timeouts and overload handling.
Câu trả lời Senior: Thread pool cũ vô tình đóng vai trò concurrency limiter. Virtual thread bỏ giới hạn đó nhưng DB capacity vẫn hữu hạn. Cần permit rõ ràng hoặc DB pool đúng kích thước, thêm timeout và overload handling.

28. Final Cheat Sheet

28. Cheat Sheet tổng kết

Use synchronized when

Dùng synchronized khi

You need simple mutual exclusion and visibility around a small critical section.

Cần mutual exclusion và visibility đơn giản quanh critical section nhỏ.

Use volatile when

Dùng volatile khi

One variable represents independent state and operations are simple reads/writes.

Một biến biểu diễn trạng thái độc lập và operation chỉ là read/write đơn giản.

Use Atomic classes when

Dùng Atomic khi

A single value needs atomic read-modify-write operations without a larger invariant.

Một giá trị cần atomic read-modify-write và không thuộc invariant lớn hơn.

Use ReentrantLock when

Dùng ReentrantLock khi

You need timeout, interruption, fairness, or multiple conditions.

Cần timeout, interruption, fairness hoặc nhiều condition.

Use BlockingQueue when

Dùng BlockingQueue khi

You need producer-consumer coordination and bounded buffering.

Cần phối hợp producer-consumer và buffer có giới hạn.

Use CompletableFuture when

Dùng CompletableFuture khi

You need to compose several independent asynchronous operations.

Cần compose nhiều async operation độc lập.

Use virtual threads when

Dùng virtual thread khi

You have high concurrency with mostly blocking I/O and want imperative code.

Concurrency cao, chủ yếu blocking I/O và muốn giữ code imperative.

Bound resources, define overload behavior, propagate cancellation, and monitor queues.

Giới hạn resource, thiết kế overload, propagate cancellation và monitor queue.
