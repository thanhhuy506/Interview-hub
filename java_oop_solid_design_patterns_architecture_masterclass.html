1. Object-Oriented Programming — OOP (lập trình hướng đối tượng)

OOP is a way to design software around objects. An object has state (trạng thái) and behavior (hành vi). The real purpose of OOP is not only to put code inside classes. Its main purpose is to protect business rules, reduce coupling (mức độ phụ thuộc), and make change safer.

Business problem ↓ Create domain objects ↓ Put data + behavior together ↓ Protect rules inside the object ↓ Reduce incorrect usage from outside
Senior view: Good OOP is about protecting invariants (quy tắc luôn phải đúng), not about creating many classes.

1.1 Encapsulation (đóng gói)

Meaning: Hide internal data and allow access only through safe methods.

Why it exists: Without encapsulation, any code can change object state and break business rules.

Bad example

public class BankAccount {
    public BigDecimal balance;
}

// Anywhere in the system:
account.balance = new BigDecimal("-1000000");

The object can enter an invalid state.

Good example

public class BankAccount {
    private BigDecimal balance;

    public BankAccount(BigDecimal openingBalance) {
        if (openingBalance.signum() < 0) {
            throw new IllegalArgumentException("Opening balance cannot be negative");
        }
        this.balance = openingBalance;
    }

    public void withdraw(BigDecimal amount) {
        if (amount == null || amount.signum() <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }

        if (balance.compareTo(amount) < 0) {
            throw new IllegalStateException("Insufficient balance");
        }

        balance = balance.subtract(amount);
    }

    public BigDecimal getBalance() {
        return balance;
    }
}

How it works

  1. The field is private.
  2. Outside code cannot change it directly.
  3. All changes must go through methods.
  4. The method checks business rules.
  5. The object always stays valid.

Use when

  • Object has business rules.
  • State must be protected.
  • You want easier testing.

Do not misunderstand

  • Encapsulation is not only getters and setters.
  • A setter for every field may still expose too much.
  • Prefer business methods such as activate(), cancel(), withdraw().
Common mistake: Using Lombok @Data on domain entities may generate setters for all fields and break encapsulation.
Interview question: What is encapsulation?

Senior answer:

“Encapsulation means an object protects its own state and exposes only safe operations. In real projects, I do not create setters for every field. I prefer business methods such as cancelOrder or approvePayment, because these methods can enforce rules. This reduces invalid state and makes the domain model easier to maintain.”

1.2 Abstraction (trừu tượng)

Meaning: Show what a component can do, but hide how it does it.

public interface PaymentGateway {
    PaymentResult charge(PaymentRequest request);
}

The service only knows it can charge a payment. It does not need to know the vendor API details.

Real project example

CheckoutService ↓ PaymentGateway interface ↓ StripeGateway / PaypalGateway / BankGateway
@Service
public class CheckoutService {
    private final PaymentGateway paymentGateway;

    public CheckoutService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }

    public PaymentResult checkout(PaymentRequest request) {
        return paymentGateway.charge(request);
    }
}
Why useful: You can replace the payment provider without changing the core checkout flow.
AbstractionEncapsulation
Hides implementation detail.Protects internal state.
Focuses on “what”.Focuses on “safe access”.
Often uses interfaces or abstract classes.Often uses private fields and controlled methods.
Interview question: Abstraction vs Encapsulation?

Senior answer:

“Abstraction hides complexity and exposes a stable contract. Encapsulation protects object state. For example, PaymentGateway is abstraction because callers do not know the provider details. BankAccount is encapsulation because its balance can only change through valid business methods.”

1.3 Inheritance (kế thừa)

Inheritance means one class extends another class and receives its behavior.

class Employee {
    void work() {}
}

class Developer extends Employee {
    void writeCode() {}
}

Main risk

Inheritance creates strong coupling. The child depends on the parent design.

Bad inheritance: If the child cannot fully follow the parent contract, the design may break Liskov Substitution Principle. 
class Bird {
    void fly() {}
}

class Penguin extends Bird {
    @Override
    void fly() {
        throw new UnsupportedOperationException();
    }
}

Penguin is a bird in real life, but not every real-world relationship should become inheritance in code.

When to use

  • There is a real and stable “is-a” relationship.
  • The child can follow all parent behavior.
  • The base behavior is truly shared.

When not to use

  • You only want code reuse.
  • The hierarchy changes often.
  • The child needs to disable parent methods.
Interview question: Why prefer composition over inheritance?

Senior answer:

“Inheritance creates tight coupling and a fixed hierarchy. Composition is more flexible because I can replace or combine behaviors. I use inheritance only when there is a stable is-a relationship and the subtype can fully follow the parent contract.”

1.4 Polymorphism (đa hình)

Polymorphism allows different implementations to be used through the same type.

public interface NotificationSender {
    void send(String message);
}

public class EmailSender implements NotificationSender {
    public void send(String message) {
        System.out.println("Send email: " + message);
    }
}

public class SmsSender implements NotificationSender {
    public void send(String message) {
        System.out.println("Send SMS: " + message);
    }
}
List<NotificationSender> senders =
        List.of(new EmailSender(), new SmsSender());

for (NotificationSender sender : senders) {
    sender.send("Order completed");
}

The same method call produces different behavior based on the real object.

Production value: Polymorphism removes large if-else chains and makes extension easier.

1.5 Composition (kết hợp đối tượng)

Composition means a class uses other objects to build behavior.

class OrderService {
    private final PaymentGateway paymentGateway;
    private final OrderRepository orderRepository;
    private final NotificationSender notificationSender;
}

This is more flexible than extending one large base class.

InheritanceComposition
Strong relationship.Flexible relationship.
Compile-time hierarchy.Can replace behavior.
Harder to test.Easier to mock and test.
Risk of fragile base class.Better separation of responsibility.

2. SOLID Principles

SOLID is a group of design guidelines that help code become easier to change, test, and maintain.

S — Single Responsibility Principle

A class should have one main reason to change.

// Bad
class OrderService {
    void validate() {}
    void saveToDatabase() {}
    void sendEmail() {}
    void createPdf() {}
}
// Better
class OrderValidator {}
class OrderRepository {}
class OrderNotifier {}
class InvoiceGenerator {}
class OrderApplicationService {}

Do not overdo it: One method per class is not always good design.

Senior answer: “I use SRP based on business responsibility, not method count. If validation, persistence, and notification change for different reasons, I separate them.”

O — Open/Closed Principle

Open for extension, closed for modification.

interface DiscountPolicy {
    BigDecimal apply(Order order);
}

class VipDiscount implements DiscountPolicy {}
class SeasonalDiscount implements DiscountPolicy {}

New discount rules can be added without changing old rules.

Pitfall: Do not create abstractions before variation exists.

Senior answer: “I apply OCP around real change points, such as payment providers or pricing rules. I avoid adding interfaces for stable code because that creates unnecessary complexity.”

L — Liskov Substitution Principle

A child type must safely replace its parent type.

interface WritableFile {
    void write(String data);
}

interface ReadableFile {
    String read();
}

Split contracts when not every subtype supports all behavior.

Senior answer: “A subtype should not surprise the caller. If it throws unsupported exceptions for normal parent behavior, the abstraction is probably wrong.”

I — Interface Segregation Principle

Clients should not depend on methods they do not use.

interface Printer { void print(); }
interface Scanner { void scan(); }
interface Fax { void fax(); }

Senior answer: “I prefer small role-based interfaces. This reduces fake methods and makes implementations and tests clearer.”

D — Dependency Inversion Principle

High-level business logic should depend on abstractions, not vendor or infrastructure details.

class PaymentService {
    private final PaymentGateway gateway;

    PaymentService(PaymentGateway gateway) {
        this.gateway = gateway;
    }
}

Spring DI helps inject dependencies, but DI is not automatically good architecture.

Senior answer: “I put interfaces around unstable infrastructure or business variation. The application service depends on a contract, and adapters implement that contract.”

3. Design Patterns

A design pattern is a reusable design idea. It is not a fixed code template. Use a pattern only when it solves a real problem.

GroupGoalExamples
CreationalControl object creation.Factory, Builder, Singleton, Prototype
StructuralCombine classes and objects.Adapter, Decorator, Facade, Proxy

3.1 Creational Patterns

Factory Pattern

Problem: Client code knows too much about object creation.

public class PaymentProcessorFactory {
    public static PaymentProcessor create(PaymentType type) {
        return switch (type) {
            case CARD -> new CardProcessor();
            case BANK_TRANSFER -> new BankTransferProcessor();
            case WALLET -> new WalletProcessor();
        };
    }
}
Client ↓ asks for type Factory ↓ creates correct object Concrete implementation

Use when: Object creation depends on runtime input.

Avoid when: Constructor injection is already simple enough.

Builder Pattern

Builder helps create complex or immutable objects.

Customer customer = Customer.builder()
    .name("Huy")
    .email("huy@example.com")
    .active(true)
    .build();

Benefit: Clearer than a constructor with many parameters.

Pitfall: Do not use Builder for simple objects with two fields.

Singleton Pattern

Singleton gives one shared instance.

Spring beans are singleton-scoped by default.

Important: Singleton does not mean thread-safe. Mutable fields inside a singleton bean may cause race conditions.
Interview: Factory vs Builder?

Answer: Factory chooses which object to create. Builder controls how a complex object is built step by step.

3.2 Structural Patterns

Adapter

Converts one interface into another expected interface.

class StripeAdapter implements PaymentGateway {
    private final StripeClient client;

    public PaymentResult charge(PaymentRequest request) {
        StripeResponse response = client.pay(...);
        return map(response);
    }
}

Real use: Wrap third-party SDKs.

Facade

Provides one simple entry point over many services.

class CheckoutFacade {
    void checkout() {
        inventory.reserve();
        payment.charge();
        order.create();
        notification.send();
    }
}

Use: Simplify complex workflows.

Decorator

Adds behavior without changing the original class.

Examples: logging, metrics, retry, caching.

Proxy

Controls access to another object.

Spring examples: @Transactional, @Cacheable, Spring AOP.

Interview: Adapter vs Facade?

Adapter changes an interface so two incompatible parts can work together. Facade gives a simpler interface over a complex subsystem.

3.3 Behavioral Patterns

Strategy Pattern

Problem: Large if-else logic for different algorithms.

interface ShippingStrategy {
    BigDecimal calculate(Order order);
}

class StandardShipping implements ShippingStrategy {}
class ExpressShipping implements ShippingStrategy {}

Spring Strategy Example

@Component("STANDARD")
class StandardShipping implements ShippingStrategy {}

@Component("EXPRESS")
class ExpressShipping implements ShippingStrategy {}

@Service
class ShippingService {
    private final Map<String, ShippingStrategy> strategies;

    ShippingService(Map<String, ShippingStrategy> strategies) {
        this.strategies = strategies;
    }

    BigDecimal calculate(String type, Order order) {
        ShippingStrategy strategy = strategies.get(type);
        if (strategy == null) {
            throw new IllegalArgumentException("Unsupported shipping type");
        }
        return strategy.calculate(order);
    }
}

Spring injects all implementations into the map.

Observer Pattern

One component publishes an event. Other components react.

applicationEventPublisher.publishEvent(
    new OrderCompletedEvent(orderId)
);

Real use: Email, audit log, analytics, Kafka event.

Risks: Hidden flow, duplicate events, ordering, retry, eventual consistency (nhất quán cuối cùng).

Chain of Responsibility

A request goes through many handlers.

Request ↓ Authentication Filter ↓ Authorization Filter ↓ Validation Filter ↓ Controller

Real examples: Servlet Filter, Spring Security filter chain.

Interview: Strategy vs State?

Strategy selects an algorithm from outside. State changes object behavior based on its current internal state. They can look similar in code, but the purpose is different.

4. Java Architecture Styles

Architecture defines boundaries, dependency direction, deployment style, and where business rules live.

4.1 Layered Architecture

Controller ↓ Service ↓ Repository ↓ Database

Good for: CRUD systems, small to medium projects, simple business logic.

Weakness: Service classes may become very large and domain logic may become weak.

@RestController
class OrderController {
    private final OrderService orderService;
}

@Service
class OrderService {
    private final OrderRepository orderRepository;
}

@Repository
interface OrderRepository extends JpaRepository<OrderEntity, Long> {}
Interview: When is Layered Architecture enough?

“It is enough when the system is mainly CRUD, the domain is simple, and the team benefits more from simplicity than from extra abstraction.”

4.2 Hexagonal Architecture — Ports and Adapters

REST Adapter ↓ Input Port ↓ Application Core ↓ Output Port ↙ ↘ DB Adapter Kafka Adapter

Port: Interface defined by the core.

Adapter: Infrastructure implementation of that interface.

// Core
public interface OrderRepositoryPort {
    Order save(Order order);
}

// Infrastructure
@Repository
class JpaOrderRepositoryAdapter implements OrderRepositoryPort {
    private final SpringDataOrderRepository repository;
}

Use when: Many integrations, strong testing need, long-term domain complexity.

Cost: More interfaces, mapping, packages, and learning effort.

4.3 Clean Architecture

LayerRole
EntitiesCore business rules
Use CasesApplication workflows
Interface AdaptersControllers, presenters, gateways
FrameworksSpring, database, messaging

Dependencies point inward.

The business core should not depend directly on Spring annotations, JPA entities, or Kafka classes.

4.4 Domain-Driven Design — DDD (thiết kế hướng miền nghiệp vụ)

Entity

Has identity and lifecycle.

Value Object

Immutable, compared by value.

Aggregate

Consistency boundary.

Aggregate Root

Main entry point of aggregate.

Domain Service

Business logic not owned by one entity.

Bounded Context

Boundary where one model and language are valid.

Example: Order Aggregate

public class Order {
    private final OrderId id;
    private final List<OrderItem> items;
    private OrderStatus status;

    public void cancel() {
        if (status == OrderStatus.SHIPPED) {
            throw new IllegalStateException("Shipped order cannot be cancelled");
        }
        status = OrderStatus.CANCELLED;
    }
}
DDD is not only creating a “domain” folder. It requires business language, clear rules, and clear boundaries.

4.5 Modular Monolith

A modular monolith is one deployable application with strong internal module boundaries.

Single Application ├── Order Module ├── Payment Module ├── Customer Module └── Notification Module

Advantages: Simple deployment, easy local development, no network calls between modules.

Use when: Small to medium team, domain still changing, microservices are not required yet.

Risk: If boundaries are weak, it becomes a large monolith.

4.6 Microservices Architecture

Microservices split the system into independently deployable services.

BenefitCost
Independent deploymentDistributed transactions
Independent scalingNetwork failure
Team ownershipObservability complexity
Fault isolationRetry and duplicate processing
Senior rule: Start with modular monolith unless independent deployment, scaling, ownership, or compliance clearly needs microservices.
Interview: Why not always use microservices?

“Microservices solve organizational and scaling problems, but they create distributed system problems. For a small team or simple domain, a modular monolith is usually easier, cheaper, and safer.”

5. How a Senior Chooses the Design

SituationGood Choice
Simple CRUDLayered Architecture
Many external systemsHexagonal Architecture
Complex domain rulesDDD + Clean/Hexagonal
Small team, changing domainModular Monolith
Many teams, independent deploymentMicroservices

Senior decision checklist

  • What changes most often?
  • Where are the business rules?
  • Which parts need independent deployment?
  • What consistency level is required?
  • Can the team operate distributed systems?
  • Does abstraction reduce complexity or only move it?

6. Common Senior Interview Questions and Strong Answers

1. What is OOP?

“OOP organizes software around objects that own state and behavior. In real systems, I use OOP mainly to protect business rules, reduce coupling, and make change safer. I prefer composition, clear interfaces, and domain methods over deep inheritance.”

2. What are the four pillars of OOP?

“They are encapsulation, abstraction, inheritance, and polymorphism. Encapsulation protects state. Abstraction hides complexity. Inheritance reuses behavior through an is-a relationship. Polymorphism allows different implementations through the same contract.”

3. Can we achieve encapsulation without abstraction?

“Yes. A class can keep fields private and expose safe methods without using an interface. Encapsulation protects state, while abstraction hides implementation detail. They often work together, but they are different ideas.”

4. Why is composition better than inheritance?

“Composition is more flexible and creates lower coupling. I can replace dependencies, test them independently, and combine behaviors. Inheritance is useful only when the subtype fully follows the parent contract.”

5. Explain SOLID with a real example.

“In a payment system, SRP separates payment logic, persistence, and notification. OCP allows adding a new provider without changing the main payment flow. LSP ensures each provider follows the same contract. ISP keeps interfaces small. DIP makes the service depend on PaymentGateway instead of a vendor SDK.”

6. Can violating OCP ever be acceptable?

“Yes. For simple, stable, or temporary code, direct modification may be cheaper than adding abstraction. I apply OCP when I see real variation or repeated change, not before.”

7. Which design patterns do you use most in Spring?

“I often use Strategy for business rules, Adapter for external systems, Facade for workflows, Builder for immutable objects, Proxy through Spring AOP, and Chain of Responsibility for filters.”

8. Strategy vs Factory?

“Factory decides which object to create. Strategy decides which behavior or algorithm to execute. They are often used together.”

9. Adapter vs Facade?

“Adapter makes incompatible interfaces work together. Facade gives a simpler interface over a complex subsystem.”

10. Layered vs Hexagonal Architecture?

“Layered architecture is simple and suitable for CRUD systems. Hexagonal architecture protects the core behind ports and adapters, which is useful when integration and testing are important.”

11. Clean Architecture vs Hexagonal Architecture?

“They share the same main idea: business logic should not depend on infrastructure. Hexagonal uses ports and adapters. Clean Architecture gives more explicit inner layers such as entities and use cases.”

12. DDD vs Clean Architecture?

“DDD focuses on modeling the business domain and language. Clean Architecture focuses on dependency direction and separation. They can be used together.”

13. Monolith vs Modular Monolith vs Microservices?

“A basic monolith may have weak boundaries. A modular monolith keeps one deployment but strong modules. Microservices split modules into separate deployable services. I prefer modular monolith first unless there is a clear need for independent deployment.”

14. What is an anemic domain model?

“It is a domain model with only fields and getters/setters, while all business logic stays in services. It may be acceptable for simple CRUD, but for complex domains it often weakens encapsulation.”

15. What is overengineering?

“Overengineering means adding more patterns, interfaces, or layers than the problem needs. A good senior design balances flexibility and simplicity.”

Interview structure: Definition → problem solved → how it works → project example → trade-off → when not to use.
