Duplicate Payment

Thanh toán bị gửi trùng

Two identical payment requests arrive at the same time.

Hai request thanh toán giống nhau đến cùng lúc.

Main risk:Rủi ro chính: the customer is charged twice because both requests pass validation before either transaction is committed. khách hàng bị trừ tiền hai lần vì cả hai request đều qua validation trước khi transaction còn lại commit.

Recommended design

Thiết kế khuyến nghị

  1. Require an idempotency key from the client for every payment command.
  2. Store that key in the database with a unique constraint.
  3. Process the payment and store the result in the same logical transaction where possible.
  4. If the same key arrives again, return the original result instead of charging again.
  5. For external payment gateways, also send a stable request reference to the provider.
  1. Client gửi idempotency key cho mỗi lệnh payment.
  2. Lưu key vào DB và tạo unique constraint.
  3. Xử lý payment và lưu kết quả trong cùng transaction logic nếu có thể.
  4. Nếu key đã tồn tại, trả lại kết quả cũ thay vì charge lại.
  5. Nếu gọi payment gateway bên ngoài, gửi thêm request reference ổn định cho provider.

Database

CREATE TABLE payment (
    id BIGSERIAL PRIMARY KEY,
    idempotency_key VARCHAR(100) NOT NULL UNIQUE,
    customer_id BIGINT NOT NULL,
    amount NUMERIC(19,2) NOT NULL,
    status VARCHAR(30) NOT NULL,
    provider_reference VARCHAR(100),
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

Spring Boot Example

@Service
@RequiredArgsConstructor
public class PaymentService {

    private final PaymentRepository paymentRepository;
    private final PaymentGateway paymentGateway;

    @Transactional
    public PaymentResponse pay(PaymentCommand command) {
        return paymentRepository.findByIdempotencyKey(command.idempotencyKey())
            .map(PaymentResponse::from)
            .orElseGet(() -> createPayment(command));
    }

    private PaymentResponse createPayment(PaymentCommand command) {
        try {
            Payment payment = Payment.pending(
                command.idempotencyKey(),
                command.customerId(),
                command.amount()
            );

            paymentRepository.saveAndFlush(payment);

            GatewayResult result = paymentGateway.charge(
                command.customerId(),
                command.amount(),
                command.idempotencyKey()
            );

            payment.markSuccess(result.reference());
            return PaymentResponse.from(payment);

        } catch (DataIntegrityViolationException ex) {
            // Another request inserted the same key at the same time.
            Payment existing = paymentRepository
                .findByIdempotencyKey(command.idempotencyKey())
                .orElseThrow();

            return PaymentResponse.from(existing);
        }
    }
}
Important: application-level checks alone are not enough. The database unique constraint is the final protection against a race condition. Quan trọng: chỉ check ở application là chưa đủ. Unique constraint ở DB mới là lớp bảo vệ cuối cùng chống race condition.

Interview answer

Câu trả lời interview

I would make the payment API idempotent. Each request has an idempotency key, and I store it with a unique database constraint. If two requests arrive at the same time, only one can create the payment record. The second request gets the existing result. For an external payment provider, I also send the same stable reference so retrying does not create another charge.

Tôi sẽ làm payment API theo cơ chế idempotent. Mỗi request có idempotency key và key này được lưu với unique constraint trong database. Nếu hai request đến cùng lúc, chỉ một request có thể tạo payment record. Request còn lại sẽ lấy kết quả đã có. Nếu gọi payment provider bên ngoài, tôi cũng gửi cùng một reference để retry không tạo thêm charge.

Double Booking

Đặt phòng trùng

Two users try to reserve the same room at the same time.

Hai user cùng đặt một phòng tại cùng thời điểm.

Correctness options

Các cách đảm bảo tính đúng

TechniqueUse whenTrade-off
Pessimistic LockHigh contention, short transactionCan reduce throughput / cause lock waits
Optimistic LockConflict is uncommonNeed retry when version changes
Unique ConstraintBest final safety netNeed handle constraint exception
@Entity
public class RoomInventory {
    @Id
    private Long id;

    private Long roomId;
    private LocalDate bookingDate;

    @Version
    private Long version;

    private boolean booked;
}
@Repository
public interface RoomInventoryRepository
        extends JpaRepository<RoomInventory, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("""
        select r from RoomInventory r
        where r.roomId = :roomId
          and r.bookingDate = :date
    """)
    Optional<RoomInventory> findForUpdate(Long roomId, LocalDate date);
}
@Transactional
public Booking book(Long roomId, LocalDate date, Long userId) {
    RoomInventory inventory = repository.findForUpdate(roomId, date)
        .orElseThrow(() -> new NotFoundException("Room not found"));

    if (inventory.isBooked()) {
        throw new ConflictException("Room already booked");
    }

    inventory.setBooked(true);
    return bookingRepository.save(
        new Booking(roomId, date, userId)
    );
}
Best practice: combine transaction locking with a database unique rule such as UNIQUE(room_id, booking_date). Best practice: kết hợp transaction locking với unique rule ở DB, ví dụ UNIQUE(room_id, booking_date).

Interview: I would not trust the “available” state shown on the UI. Availability must be rechecked inside a database transaction. I can use pessimistic locking for high contention or optimistic locking when conflicts are rare. I also add a unique database constraint as the final protection so two bookings for the same room and date cannot be committed.

Interview: Tôi không tin trạng thái “available” trên UI vì nó có thể đã cũ. Availability phải được check lại trong database transaction. Tôi có thể dùng pessimistic locking khi conflict cao, hoặc optimistic locking nếu conflict hiếm. Ngoài ra tôi thêm unique constraint ở DB để đảm bảo hai booking cho cùng phòng và ngày không thể cùng commit.

Slow REST API

REST API bị chậm

API = 30 seconds because it calls 3 downstream services.

Step-by-step approach

Cách xử lý từng bước

  1. Measure latency of each downstream call using tracing and metrics.
  2. If calls are independent, execute them in parallel.
  3. Set connect timeout and read timeout.
  4. Add circuit breaker for unstable services.
  5. Cache stable data.
  6. Return partial/default data if business rules allow it.
  7. Move non-critical work to async messaging.
  1. Đo latency từng downstream bằng tracing và metrics.
  2. Nếu các call độc lập, chạy song song.
  3. Đặt connect timeout và read timeout.
  4. Dùng circuit breaker với service không ổn định.
  5. Cache dữ liệu ít thay đổi.
  6. Trả partial/default data nếu business cho phép.
  7. Đưa phần không critical sang async message.
@Service
@RequiredArgsConstructor
public class DashboardService {

    private final UserClient userClient;
    private final OrderClient orderClient;
    private final RewardClient rewardClient;

    public Mono<DashboardResponse> load(Long userId) {
        Mono<User> user = userClient.getUser(userId);
        Mono<List<Order>> orders = orderClient.getOrders(userId);
        Mono<Reward> reward = rewardClient.getReward(userId);

        return Mono.zip(user, orders, reward)
            .map(tuple -> new DashboardResponse(
                tuple.getT1(),
                tuple.getT2(),
                tuple.getT3()
            ))
            .timeout(Duration.ofSeconds(3));
    }
}
Do not blindly use more threads. If downstream is slow, creating more threads can make the system worse by exhausting thread pools and connections. Không nên tăng thread một cách mù quáng. Nếu downstream đang chậm, tạo thêm thread có thể làm hệ thống tệ hơn do cạn thread pool và connection.

First I would use tracing to find which downstream is slow. If the three calls are independent, I would call them in parallel instead of sequentially. I would configure strict timeouts, use circuit breakers, cache stable responses, and move non-critical work to asynchronous processing. The goal is not only lower average latency but also controlled p95/p99 latency and graceful failure.

Đầu tiên tôi dùng tracing để xác định downstream nào chậm. Nếu ba call độc lập, tôi gọi song song thay vì tuần tự. Tôi cấu hình timeout rõ ràng, circuit breaker, cache dữ liệu ổn định và chuyển phần không critical sang async. Mục tiêu không chỉ giảm latency trung bình mà còn kiểm soát p95/p99 và degrade gracefully khi service lỗi.

Kafka Consumer Down

Kafka messages remain in the topic based on retention policy. The consumer group stores committed offsets. When the consumer returns, it continues from the last committed offset.

Message Kafka vẫn nằm trong topic theo retention policy. Consumer group lưu committed offset. Khi consumer chạy lại, nó tiếp tục đọc từ offset đã commit gần nhất.

What to check

Cần kiểm tra gì

  • Consumer lag increased during downtime.
  • Retention is long enough so messages are not deleted before recovery.
  • Offset commit mode is correct.
  • Processing is idempotent because retries can happen.
  • Poison messages go to a retry topic or dead-letter topic.
  • Consumer lag tăng trong thời gian downtime.
  • Retention đủ dài để message chưa bị xóa trước khi consumer quay lại.
  • Offset commit mode đúng.
  • Business xử lý idempotent vì retry có thể xảy ra.
  • Poison message nên đưa vào retry topic hoặc dead-letter topic.
@KafkaListener(topics = "payment-events", groupId = "ledger-service")
public void consume(PaymentEvent event) {
    // Idempotency check before applying business logic
    if (processedEventRepository.existsByEventId(event.eventId())) {
        return;
    }

    transactionTemplate.executeWithoutResult(status -> {
        ledgerService.apply(event);
        processedEventRepository.save(
            new ProcessedEvent(event.eventId())
        );
    });
}

Kafka does not normally lose the messages just because the consumer is down. The messages stay in the topic until retention removes them. When the consumer restarts, it resumes from its last committed offset. I would monitor consumer lag, verify retention, use idempotent processing, and configure retry/DLT handling for messages that repeatedly fail.

Kafka bình thường sẽ không mất message chỉ vì consumer bị down. Message vẫn nằm trong topic cho tới khi retention xóa. Khi consumer chạy lại, nó tiếp tục từ committed offset gần nhất. Tôi sẽ monitor consumer lag, kiểm tra retention, đảm bảo xử lý idempotent và cấu hình retry/DLT cho message lỗi nhiều lần.

HashMap Concurrency

HashMap is not thread-safe. Concurrent writes can cause lost updates, stale reads, inconsistent state, and iteration exceptions.

HashMap không thread-safe. Concurrent write có thể gây lost update, stale read, trạng thái không nhất quán và exception khi iterate.

Fix options

Các cách xử lý

  • ConcurrentHashMap — common choice for high-concurrency access.
  • Collections.synchronizedMap — simpler, but more global locking.
  • Immutable map — best if data does not change.
  • Atomic methods — compute(), merge(), putIfAbsent().
private final ConcurrentHashMap<String, Long> counters =
        new ConcurrentHashMap<>();

public void increase(String key) {
    counters.merge(key, 1L, Long::sum);
}
Wrong pattern:Pattern sai: 
if (!map.containsKey(key)) {
    map.put(key, value); // race condition
}
map.putIfAbsent(key, value);

I would not use a normal HashMap for shared mutable state. I would usually use ConcurrentHashMap and atomic methods such as compute, merge, or putIfAbsent. I also check whether the shared state should exist in memory at all, because in a multi-instance microservice local memory is not shared across pods.

Tôi không dùng HashMap thường cho shared mutable state. Tôi thường dùng ConcurrentHashMap và các atomic method như compute, merge hoặc putIfAbsent. Tôi cũng xem lại dữ liệu đó có nên lưu local memory không, vì trong microservice nhiều instance thì memory không được share giữa các pod.

High CPU Usage

CPU tăng 95%

Troubleshooting flow

Quy trình troubleshoot

  1. Check metrics: CPU, load average, request rate, latency, error rate, GC, thread count.
  2. Take thread dump: identify RUNNABLE threads and repeated stack traces.
  3. Profile CPU: JFR, async-profiler, Java Mission Control.
  4. Check thread creation: unbounded executor, blocking I/O, retry storm.
  5. Check GC: high GC CPU can look like application CPU.
  6. Compare deployment change: new release, configuration, traffic spike.
// Bad: unbounded thread creation
ExecutorService executor = Executors.newCachedThreadPool();

// Better: bounded pool
ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
executor.setCorePoolSize(20);
executor.setMaxPoolSize(50);
executor.setQueueCapacity(500);
executor.setThreadNamePrefix("payment-");
executor.initialize();
Thousands of threads can increase context switching, memory usage, and CPU even if actual business work is small. Hàng nghìn thread có thể làm tăng context switching, memory và CPU dù business workload thật sự không lớn.

I start with metrics to confirm whether CPU correlates with traffic, GC, or thread growth. Then I take thread dumps and a CPU profile. If thousands of threads appeared, I check for unbounded thread pools, blocking calls, retry loops, or thread leaks. I also compare the issue with recent deployments and use JFR or async-profiler to identify the hottest stack.

Tôi bắt đầu từ metrics để xem CPU có liên quan đến traffic, GC hay thread count tăng không. Sau đó tôi lấy thread dump và CPU profile. Nếu có hàng nghìn thread, tôi kiểm tra unbounded thread pool, blocking call, retry loop hoặc thread leak. Tôi cũng so với release gần nhất và dùng JFR hoặc async-profiler để tìm hot stack.

Memory Issue / OutOfMemoryError

Memory tăng liên tục / OutOfMemoryError

Possible causes

Nguyên nhân thường gặp

  • Unbounded cache
  • Static collections
  • Large object retention
  • ThreadLocal leak
  • Too many threads
  • Large HTTP payloads
  • File/stream resources not closed
  • Queue backlog in memory
  • Hibernate persistence context too large
  • ClassLoader leak

Investigation

Cách điều tra

  1. Check heap usage before and after Full GC.
  2. Enable heap dump on OOM.
  3. Analyze dominator tree and retained size.
  4. Find objects that keep growing.
  5. Check GC logs and allocation rate.
JAVA_TOOL_OPTIONS="
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/dumps
-Xlog:gc*:file=/logs/gc.log
"
// Bad: unbounded cache
private static final Map<String, Object> CACHE = new HashMap<>();

// Better: bounded cache policy
Caffeine.newBuilder()
    .maximumSize(100_000)
    .expireAfterWrite(Duration.ofMinutes(10))
    .build();

I first determine whether it is a real memory leak or simply not enough heap. I check whether memory returns after Full GC. Then I capture a heap dump and analyze retained objects using tools such as Eclipse MAT or JDK tools. Typical causes are unbounded caches, static collections, ThreadLocal leaks, very large persistence contexts, or queues that grow faster than they are consumed.

Đầu tiên tôi xác định đây là memory leak thật hay chỉ thiếu heap. Tôi kiểm tra memory có giảm sau Full GC hay không. Sau đó tôi lấy heap dump và phân tích retained object bằng Eclipse MAT hoặc JDK tools. Nguyên nhân thường gặp là cache không giới hạn, static collection, ThreadLocal leak, persistence context quá lớn hoặc queue tăng nhanh hơn tốc độ xử lý.

Kubernetes Issue: One Pod at 95% CPU

Check first

Kiểm tra trước tiên

  1. Is traffic distributed evenly across pods?
  2. Is one pod processing a special partition, job, or Kafka partition?
  3. Does the pod have different config, JVM args, or node placement?
  4. Is it stuck in a loop or retry storm?
  5. Are CPU requests/limits different?
  6. Is the node itself under resource pressure?
kubectl top pod
kubectl describe pod <pod-name>
kubectl logs <pod-name> --previous
kubectl get pod -o wide
kubectl top node
If only one pod is abnormal while others are healthy, first compare what is different about that pod before scaling the whole deployment. Nếu chỉ một pod bất thường còn các pod khác bình thường, hãy tìm điểm khác biệt của pod đó trước khi scale toàn bộ deployment.

I would first compare the hot pod with healthy pods: traffic, logs, thread dump, config, node, CPU limits, and assigned workload. One pod may own a hot Kafka partition, run a scheduled job, receive uneven traffic, or be stuck in a retry loop. I would not immediately scale the service before understanding why only one pod is affected.

Tôi sẽ so sánh pod nóng với pod bình thường: traffic, logs, thread dump, config, node, CPU limit và workload được assign. Một pod có thể đang giữ Kafka partition nóng, chạy scheduled job, nhận traffic không đều hoặc bị retry loop. Tôi không scale ngay trước khi hiểu vì sao chỉ một pod bị ảnh hưởng.

JWT / 401 Unauthorized

Checklist

Checklist kiểm tra

  • Authorization header format: Bearer <token>
  • Token expired?
  • Signature valid?
  • Correct issuer (iss)?
  • Correct audience (aud)?
  • Clock skew between systems?
  • Correct public key / JWKS endpoint?
  • Spring Security filter chain configuration?
  • 401 vs 403: authentication failure vs permission failure.
@Bean

    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/actuator/health").permitAll()

        .oauth2ResourceServer(oauth2 -> oauth2.jwt());

}
spring:
  security:
    oauth2:
      resourceserver:

401 usually means authentication failed. 403 usually means the user is authenticated but does not have enough permission. 401 thường là authentication thất bại. 403 thường là đã authenticate nhưng không đủ permission.

I would verify the Authorization header first, then decode the token and check expiry, issuer, audience, and signature. After that I check whether the resource server uses the correct JWKS or issuer configuration. I also verify system clock skew and Spring Security filter rules. If authentication succeeds but access is denied, I would expect 403 rather than 401.

Tôi kiểm tra Authorization header trước, sau đó decode token để xem expiry, issuer, audience và signature. Tiếp theo tôi kiểm tra resource server có dùng đúng JWKS hoặc issuer configuration không. Tôi cũng kiểm tra clock skew và Spring Security filter rule. Nếu authentication thành công nhưng thiếu quyền thì thường phải là 403 chứ không phải 401.

Database Performance After Data Growth

Database chậm khi dữ liệu lên hàng triệu record

What to inspect

Cần kiểm tra gì

  1. Execution plan: sequential scan, nested loop, sort, bad estimates.
  2. Indexes: missing index, wrong composite order, low selectivity.
  3. Query design: SELECT *, unnecessary joins, N+1 queries.
  4. Functions on indexed columns: may block index usage.
  5. Pagination: large OFFSET becomes slow.
  6. Statistics: stale statistics can produce a bad plan.
  7. Table growth: partitioning can help very large time/range data.
  8. Connection pool: slow DB can cause pool exhaustion.
-- Less index-friendly
SELECT *
FROM orders
WHERE DATE(created_at) = '2026-09-16';

-- Better
SELECT id, customer_id, status, total_amount
FROM orders
WHERE created_at >= '2026-09-16 00:00:00'
  AND created_at <  '2026-09-17 00:00:00';
CREATE INDEX idx_orders_customer_created
ON orders(customer_id, created_at DESC);
// Keyset pagination instead of very large OFFSET
@Query("""
    select o from Order o
    where o.customerId = :customerId
      and o.id < :lastId
    order by o.id desc
""")
List<Order> nextPage(
    Long customerId,
    Long lastId,
    Pageable pageable
);
Do not add indexes everywhere. Every index improves some reads but adds storage and write cost. Không nên thêm index khắp nơi. Mỗi index có thể tăng tốc read nhưng làm tăng storage và chi phí write.

I would start with the slow query and inspect EXPLAIN ANALYZE. I check for full table scans, missing or ineffective indexes, bad joins, N+1 queries, large sorts, and high OFFSET pagination. I also verify statistics and connection pool saturation. If the table is very large and queries naturally filter by time or another range key, I would consider partitioning, but only after fixing query and index design first.

Tôi bắt đầu từ slow query và xem EXPLAIN ANALYZE. Tôi kiểm tra full table scan, index thiếu hoặc không hiệu quả, join xấu, N+1 query, sort lớn và pagination OFFSET quá sâu. Tôi cũng kiểm tra statistics và connection pool. Nếu table rất lớn và query thường filter theo time/range key, tôi cân nhắc partitioning, nhưng chỉ sau khi tối ưu query và index trước.

Circuit Breaker & Resilience4j

Circuit Breaker & Resilience4j

How to stop repeated calls to an unhealthy downstream service, recover automatically, and decide when fallback is safe.

Cách ngăn việc gọi liên tục tới downstream đang lỗi, tự động thử lại khi service phục hồi, và quyết định khi nào fallback là an toàn.

Main idea: Circuit Breaker does not retry the same request many times. It watches recent calls. If too many calls fail or become too slow, it temporarily blocks new calls and returns a fallback immediately.

Ý tưởng chính: Circuit Breaker không phải là retry cùng request nhiều lần. Nó quan sát các request gần đây. Nếu quá nhiều request fail hoặc quá chậm, nó tạm thời chặn các call mới và trả fallback ngay.

Why we need it

Tại sao cần Circuit Breaker

Without Circuit Breaker

Không có Circuit Breaker

  • Service A keeps calling Service B even when B is down.
  • Threads wait until timeout.
  • Connection pools become exhausted.
  • Latency increases across the whole system.
  • Retry storms can make the outage worse.
  • Service A vẫn gọi Service B dù B đang down.
  • Thread phải chờ đến timeout.
  • Connection pool có thể bị cạn.
  • Latency tăng trên toàn hệ thống.
  • Retry storm có thể làm outage nặng hơn.

With Circuit Breaker

Có Circuit Breaker

  • Failures are measured in a rolling window.
  • When the threshold is exceeded, the circuit opens.
  • Calls fail fast instead of waiting for timeout.
  • Fallback can return cached/default/empty data.
  • After a wait period, a few probe calls are allowed.
  • Failure được đo trong một sliding window.
  • Khi vượt threshold, circuit chuyển sang OPEN.
  • Request fail fast thay vì chờ timeout.
  • Fallback có thể trả cache/default/empty data.
  • Sau thời gian chờ, cho phép một vài probe call để test recovery.

Circuit Breaker states

Các trạng thái của Circuit Breaker

State Meaning Ý nghĩa What happens Điều gì xảy ra
CLOSED Normal state Trạng thái bình thường Calls go to downstream and are measured. Request vẫn gọi downstream và được tính vào metrics.
OPEN Downstream considered unhealthy Downstream đang được xem là không ổn định Calls are blocked immediately. Fallback runs. Call mới bị chặn ngay. Fallback chạy.
HALF_OPEN Recovery testing Kiểm tra service đã phục hồi chưa Only a limited number of probe calls are allowed. Chỉ cho một số lượng nhỏ probe call đi qua.

Normal recovery: CLOSED → too many failures → OPEN → wait → HALF_OPEN → probe calls succeed → CLOSED again.

Luồng recovery bình thường: CLOSED → quá nhiều failure → OPEN → chờ → HALF_OPEN → probe call thành công → quay lại CLOSED.

How is the failure threshold calculated?

Failure threshold được tính như thế nào?

Resilience4j calculates the failure rate from calls inside the current sliding window:

Resilience4j tính failure rate dựa trên các call nằm trong sliding window hiện tại: 

failureRate = failedCalls / totalMeasuredCalls * 100

Example A

slidingWindowSize = 10

minimumNumberOfCalls = 10

failureRateThreshold = 50%

If 5 out of the latest 10 calls fail → failure rate = 50% → circuit can OPEN.

Nếu 5/10 call gần nhất fail → failure rate = 50% → circuit có thể OPEN.

Example B

minimumNumberOfCalls = 10

Only 4 calls happened and all 4 failed.

Mới có 4 call và cả 4 đều fail.

The circuit does not open yet because the minimum number of calls has not been reached.

Circuit chưa OPEN vì chưa đủ minimumNumberOfCalls.

Important threshold settings

Các threshold quan trọng

SettingPurposeÝ nghĩa
failureRateThreshold Percentage of failed calls that causes OPEN. Tỷ lệ call fail để chuyển sang OPEN.
slidingWindowSize How many recent calls, or how many seconds, are measured. Số call gần nhất hoặc số giây được dùng để tính.
minimumNumberOfCalls Do not calculate/open too early with too little data. Tránh OPEN quá sớm khi chưa đủ dữ liệu.
slowCallRateThreshold Opens the circuit when too many calls are slow, even if they still return 200. Có thể OPEN khi quá nhiều call chậm, dù response vẫn là 200.
slowCallDurationThreshold Defines what “slow” means, for example more than 2 seconds. Định nghĩa một call bao lâu thì được tính là “slow”, ví dụ > 2 giây.

After the server recovers, when will calls go through again?

Server đã work lại thì bao lâu mới gọi thật trở lại?

This is controlled mainly by waitDurationInOpenState. While the circuit is OPEN, requests do not reach the downstream. After the wait duration, the circuit moves to HALF_OPEN and allows a small number of test calls.

Việc này chủ yếu được điều khiển bởi waitDurationInOpenState. Khi circuit đang OPEN, request không đi đến downstream. Sau thời gian chờ này, circuit chuyển sang HALF_OPEN và cho một số call test đi qua. 

waitDurationInOpenState = 10s
permittedNumberOfCallsInHalfOpenState = 3
  1. Downstream fails repeatedly.
  2. Circuit becomes OPEN.
  3. For 10 seconds, calls immediately use fallback.
  4. After 10 seconds, circuit becomes HALF_OPEN.
  5. Three real calls are allowed as health probes.
  6. If they are healthy enough, circuit returns to CLOSED.
  7. Normal requests call downstream again.
  1. Downstream fail nhiều lần.
  2. Circuit chuyển sang OPEN.
  3. Trong 10 giây, request mới đi thẳng vào fallback.
  4. Sau 10 giây, circuit chuyển sang HALF_OPEN.
  5. Cho phép 3 call thật đi qua để kiểm tra.
  6. Nếu các call test đủ tốt, circuit quay về CLOSED.
  7. Request sau đó gọi downstream bình thường trở lại.

Do not set the wait time too short. If a service needs 30 seconds to recover but the circuit retries every 1 second, you can create a new load spike during the outage.

Không set wait quá ngắn. Nếu service cần 30 giây để recover nhưng circuit cứ thử lại mỗi 1 giây, chính các probe đó có thể tạo thêm load trong lúc outage.

Với cấu hình này, sau khi đã có ít nhất 10 call được đo, nếu 50% trở lên fail hoặc 50% trở lên mất hơn 2 giây, circuit có thể chuyển sang OPEN.

Fallback to empty so the next steps can continue

Fallback về empty để flow vẫn chạy tiếp

Returning empty data is useful when the downstream data is optional. Example: a dashboard can still show user and order information even if the reward service is temporarily unavailable.

Trả empty rất hữu ích khi dữ liệu downstream chỉ là optional. Ví dụ dashboard vẫn có thể hiển thị user và order dù reward service tạm thời lỗi. 

@Service
@RequiredArgsConstructor
public class RewardClient {

    private final WebClient webClient;

    @CircuitBreaker(name = "rewardService", fallbackMethod = "rewardFallback")
    public List<Reward> getRewards(Long userId) {
        return webClient.get()
            .uri("/users/{id}/rewards", userId)
            .retrieve()
            .bodyToFlux(Reward.class)
            .collectList()
            .block();
    }

    private List<Reward> rewardFallback(Long userId, Throwable ex) {
        // Optional data -> continue next step safely
        return Collections.emptyList();
    }
}

Then the business flow can continue

Sau đó flow business vẫn tiếp tục

public DashboardResponse getDashboard(Long userId) {
    User user = userClient.getUser(userId);
    List<Order> orders = orderClient.getOrders(userId);

    // May return empty list when reward service is unavailable
    List<Reward> rewards = rewardClient.getRewards(userId);

    return new DashboardResponse(user, orders, rewards);
}

Reactive fallback example

Ví dụ fallback với WebFlux

@CircuitBreaker(name = "rewardService", fallbackMethod = "rewardFallback")
public Mono<Reward> getReward(Long userId) {

Do not blindly return empty. Fallback is only safe when the missing data is optional and the caller can clearly understand that it is degraded data.

Không được fallback empty một cách mù quáng. Chỉ nên làm vậy khi dữ liệu bị thiếu là optional và caller hiểu rõ response đang ở trạng thái degraded.

How to choose threshold values

Cách chọn threshold hợp lý

There is no universal “correct” value. Use production latency, failure rate, traffic volume, and business tolerance.

Không có một con số đúng cho mọi hệ thống. Phải dựa trên latency thực tế, error rate, traffic và mức độ business chấp nhận được.

Traffic pattern Loại traffic Typical consideration Điểm cần cân nhắc
High traffic High traffic Larger sliding window gives more stable statistics. Sliding window lớn hơn giúp số liệu ổn định hơn.
Low traffic Low traffic Do not set minimum calls too high or breaker may never react. Không set minimum calls quá cao vì breaker có thể không bao giờ phản ứng.
Very sensitive downstream Downstream yếu / dễ overload Lower threshold and longer open wait can protect it better. Threshold thấp hơn và thời gian OPEN dài hơn có thể bảo vệ downstream tốt hơn.
Temporary network errors Lỗi network ngắn hạn A small retry may help before the breaker records final failure. Có thể dùng retry nhỏ trước khi breaker tính request là fail cuối cùng.

Reasonable starting point for many internal services: window 20-50 calls, minimum 10-20 calls, failure threshold around 50%, open wait 10-30 seconds, and 3-10 half-open probe calls. Then tune using real metrics.

Một điểm bắt đầu hợp lý cho nhiều internal service: window 20-50 call, minimum 10-20 call, failure threshold khoảng 50%, OPEN 10-30 giây, HALF_OPEN cho 3-10 probe call. Sau đó tune theo metrics thật.

Circuit Breaker vs Retry

Circuit Breaker khác Retry như thế nào?

Retry Circuit Breaker
Main goal Recover from temporary/transient failure. Protect the system from a persistently unhealthy dependency.
Mục tiêu Xử lý lỗi tạm thời/transient. Bảo vệ hệ thống khi dependency lỗi liên tục.
Behavior Calls the downstream again for the same operation. Stops calling downstream for a period.
Hành vi Gọi lại downstream cho cùng operation. Ngừng gọi downstream trong một khoảng thời gian.
Best for Temporary timeout, short network glitch, transient 5xx. Service down, overload, repeated timeout, repeated 5xx.
Phù hợp Timeout ngắn, network glitch, transient 5xx. Service down, overload, timeout/5xx liên tục.
Risk Too many retries can create a retry storm. Wrong fallback can hide real business failures.
Rủi ro Retry quá nhiều có thể tạo retry storm. Fallback sai có thể che giấu business failure thật.

Using Retry and Circuit Breaker together

Kết hợp Retry và Circuit Breaker

A common design is: timeout first, retry only a small number of times for transient failures, and use the circuit breaker to stop repeated pressure when the dependency remains unhealthy.

Một thiết kế phổ biến là: timeout rõ ràng, retry rất ít lần cho transient failure, và Circuit Breaker dùng để ngăn tiếp tục gây áp lực nếu downstream vẫn lỗi. 

resilience4j:
  retry:
    instances:
      rewardService:
        maxAttempts: 2
        waitDuration: 200ms

  circuitbreaker:
    instances:
      rewardService:
        slidingWindowSize: 20
        minimumNumberOfCalls: 10
        failureRateThreshold: 50
        waitDurationInOpenState: 15s

Example: If 1 request is retried 5 times and 100 clients do it at once, the unhealthy downstream may receive 500 calls instead of 100. This is why retry must be bounded and usually combined with backoff/jitter.

Ví dụ: Nếu 1 request retry 5 lần và 100 client cùng làm vậy, downstream đang lỗi có thể nhận 500 call thay vì 100. Vì vậy retry phải giới hạn và thường nên kết hợp backoff/jitter.

Interview answer — concise but senior

Câu trả lời interview — ngắn nhưng thể hiện senior

I use Circuit Breaker when a downstream service is repeatedly failing or becoming too slow. In Resilience4j, I configure a sliding window, minimum number of calls, failure-rate threshold, slow-call threshold, and the wait time in the OPEN state. For example, after at least 10 calls, if 50% of the latest calls fail, the circuit opens. During OPEN state, calls fail fast and go to fallback. After the configured wait time, it moves to HALF_OPEN and allows a few probe calls. If those calls succeed, it closes and normal traffic resumes. For optional data I can fallback to an empty list or cached response so the remaining flow can continue, but I would not do that for critical operations like payment or balance checks. Retry is different: retry repeats a failed request for transient errors, while Circuit Breaker stops calling an unhealthy dependency. I usually keep retry small and bounded, then let the Circuit Breaker protect the system if the dependency remains unhealthy.

Tôi dùng Circuit Breaker khi downstream service fail liên tục hoặc trở nên quá chậm. Trong Resilience4j, tôi cấu hình sliding window, minimum number of calls, failure-rate threshold, slow-call threshold và thời gian chờ ở trạng thái OPEN. Ví dụ sau khi có ít nhất 10 call, nếu 50% số call gần nhất fail thì circuit OPEN. Khi OPEN, request fail fast và đi vào fallback. Sau thời gian chờ, circuit chuyển sang HALF_OPEN và cho một vài probe call đi qua. Nếu các call đó thành công, circuit quay lại CLOSED và traffic hoạt động bình thường. Với dữ liệu optional, tôi có thể fallback về empty list hoặc cache để các step sau tiếp tục chạy, nhưng tôi không làm vậy cho nghiệp vụ critical như payment hoặc balance. Retry khác ở chỗ retry gọi lại request lỗi khi lỗi có tính transient, còn Circuit Breaker ngừng gọi dependency đang lỗi. Tôi thường để retry ít và có giới hạn, sau đó để Circuit Breaker bảo vệ hệ thống nếu downstream vẫn không khỏe.
