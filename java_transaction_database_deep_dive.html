1. Transaction Basics

A transaction is a group of database operations treated as one business unit.

BEGIN
 ↓
SELECT payment
 ↓
UPDATE payment
 ↓
INSERT transaction
 ↓
COMMIT

If an important operation fails, the database changes can be rolled back.

Important: A DB transaction protects database changes. It cannot automatically roll back an external bank or PSP API.

2. @Transactional Configuration

OptionExampleWhen to use
readOnly@Transactional(readOnly=true)Only reads data: search, detail, reports.
timeout@Transactional(timeout=5)Limit how long the transaction may run.
rollbackFor@Transactional(rollbackFor=Exception.class)Make selected checked exceptions trigger rollback.
noRollbackFor@Transactional(noRollbackFor=BusinessWarning.class)Rare case where a selected exception should not trigger rollback.

isolation@Transactional(isolation=Isolation.READ_COMMITTED)Control concurrent read/write visibility.

3. READ_ONLY

@Transactional(readOnly = true)
public Payment getPayment(Long id) {
    return paymentRepository.findById(id).orElseThrow();
}

Use it for get/search/report/dashboard operations.

Important: readOnly=true is not a universal guarantee that the database will reject every write. It can be a hint/optimization depending on DB, JDBC driver, transaction manager and ORM.

It also does not automatically route traffic to a read replica. That requires explicit datasource/routing configuration.

4. Normal Read-Write Transaction

@Transactional
public void processPayment(Long paymentId) {
    Payment payment = paymentRepository.findById(paymentId).orElseThrow();
    payment.setStatus("SUCCESS");
    transactionRepository.save(new PaymentTransaction(paymentId));
}
BEGIN → SELECT → UPDATE → INSERT → COMMIT

Use this when the business operation creates or changes database state.

5. Timeout

@Transactional(timeout = 5)
public void updatePayment(Long id) {
    // DB work
}

Useful to avoid very long transactions, long-held locks and connection-pool pressure.

Bad: BEGIN DB transaction → call bank API → wait 20 seconds → update DB → COMMIT.
Better: keep the DB transaction short. Call the external service outside the DB transaction when possible, then start a short transaction to save the result.

6. COMMIT

Commit confirms the database changes.

@Transactional
public void createOrder() {
    orderRepository.save(order);
    paymentRepository.save(payment);
}
// successful method completion → commit

7. ROLLBACK

@Transactional
public void createOrder() {
    orderRepository.save(order);
    paymentRepository.save(payment);
    throw new RuntimeException("Payment failed");
}
INSERT order ✓
INSERT payment ✓
Exception ✗
   ↓
ROLLBACK
   ↓
Both DB changes are undone

This supports Atomicity: the DB changes succeed together or are rolled back.

8. rollbackFor

Spring normally rolls back for unchecked exceptions such as RuntimeException and Error, but checked exceptions need explicit rules when rollback is required.

@Transactional(rollbackFor = Exception.class)
public void processPayment() throws Exception {
    updatePayment();
    createTransaction();
    throw new Exception("Checked exception");
}

Use it when a checked exception represents a failure that must undo the transaction.

9. noRollbackFor

@Transactional(noRollbackFor = BusinessWarningException.class)
public void process() {
    saveSomething();
    throw new BusinessWarningException();
}

The selected exception should not trigger rollback.

Use carefully. For payment failures, it is usually better to model the business state explicitly than to simply prevent rollback.

10. Rollback-Only

A transaction can be marked rollback-only. It may continue running, but it cannot finally commit.

Outer transaction
 ↓
Inner service
 ↓
failure
 ↓
transaction marked rollback-only
 ↓
outer method continues
 ↓
commit requested
 ↓
ROLLBACK

In Spring this can result in UnexpectedRollbackException when an outer method tries to commit a transaction already marked rollback-only.

11. Isolation Level

@Transactional(isolation = Isolation.READ_COMMITTED)
public Payment getPayment(Long id) { ... }
LevelMain ideaTypical use
READ_UNCOMMITTEDMay see uncommitted changes.Rare; normally unsuitable for financial data.
READ_COMMITTEDReads committed data.Common choice.
REPEATABLE_READRepeated reads are more stable.When repeatable reads matter.
SERIALIZABLEStrongest isolation; lower concurrency.Special correctness-critical cases.

Know these problems: dirty read, non-repeatable read, phantom read, lost update, write skew.

12. Optimistic Locking

@Version
private Long version;
UPDATE account
SET balance = 80, version = 6
WHERE id = 1 AND version = 5;

If another transaction already changed version 5, the update affects zero rows and the application detects a concurrent update.

Use when: conflicts are not frequent and you do not want to hold database locks for a long time.

13. Pessimistic Locking

SELECT *
FROM account
WHERE id = 1
FOR UPDATE;

JPA example:

@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Account> findByIdForUpdate(Long id);

Use when: concurrent changes to the same critical row are likely and the operation must serialize access.

Locks should be short. Inconsistent lock order can cause deadlocks.

14. Transaction Propagation

PropagationMeaningWhen
REQUIREDJoin current transaction or create one.Default service behavior.
REQUIRES_NEWSuspend current transaction and create a new one.Independent audit/log record.
SUPPORTSJoin if one exists; otherwise run without one.Some read operations.
NOT_SUPPORTEDSuspend current transaction.Special non-transactional work.
MANDATORYMust already have a transaction.Internal method requiring a transaction.
NEVERMust not run inside a transaction.Rare.
NESTEDUses nested transaction/savepoint when supported.Partial rollback cases.

REQUIRED

@Transactional
public void processPayment() {
    updatePayment();
    createTransaction();
}

@Transactional(propagation = Propagation.REQUIRED)
public void updatePayment() { ... }

The inner method joins the outer transaction.

REQUIRES_NEW

@Transactional
public void processPayment() {
    updatePayment();
    auditService.saveAudit();
}

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void saveAudit() {
    auditRepository.save(...);
}
Transaction A → suspend → Transaction B → commit → A resumes

Useful when the audit record must be independent from the main transaction.

15. Read Replica + Master/Replica Switching

Application
 ├── WRITE → Master / Primary DB
 └── READ  → Replica DB

15.1 Why use Read Replicas?

When the system has many more reads than writes, read traffic can be distributed to replicas while writes stay on the master.

100,000 requests
      ↓
Application
 ├── 90,000 READ  ──→ Replica
 └── 10,000 WRITE ──→ Master

15.2 Configure two DataSources

spring:
  datasource:
    master:
      jdbc-url: jdbc:postgresql://db-master:5432/payment
      username: app
      password: ${DB_PASSWORD}

    replica:
      jdbc-url: jdbc:postgresql://db-replica:5432/payment
      username: app
      password: ${DB_PASSWORD}

15.3 Routing DataSource

public enum DbType {
    MASTER, REPLICA
}

public class RoutingDataSource
        extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        return DbContext.get();
    }
}

The application can route a request to Master or Replica. A common design is to use the transaction's read-only state as the routing signal.

@Transactional(readOnly = true)
public Payment getPayment(Long id) {
    return paymentRepository.findById(id).orElseThrow();
}

@Transactional
public void updatePayment(Long id) {
    // write → Master
}
readOnly = true
      ↓
Replica

readOnly = false
      ↓
Master
Important: @Transactional(readOnly=true) does NOT automatically switch to a Replica. You need a routing DataSource / transaction-aware routing mechanism.

15.4 Replication Lag

1. UPDATE payment on Master
        ↓
2. COMMIT
        ↓
3. SELECT payment from Replica
        ↓
4. Replica has not caught up
        ↓
5. Old data returned

This is replication lag. It creates an important consistency problem called read-after-write inconsistency.

15.5 How to handle read-after-write?

  • Read from Master immediately after a critical write.
  • Use consistency-aware routing for the affected user/request.
  • Use Replica only when slightly stale data is acceptable.
  • For payment status, prefer Master when the user must immediately see the latest result.
Production example: User pays successfully → update payment on Master → immediately show SUCCESS from Master. Do not depend on a lagging Replica for that immediate response.

15.6 Important architecture point

Read replicas improve read scalability, but they do not remove the need for a strong primary database. Writes, locks and consistency-critical reads still depend on the primary.

17. Deadlock

Transaction A: lock User 1 → wait User 2
Transaction B: lock User 2 → wait User 1
                         ↓
                      DEADLOCK

Reduce risk with short transactions, consistent lock ordering, good indexes, fewer unnecessary locks, timeout and safe retry.

18.1 Why use a Connection Pool?

Opening a new DB connection for every request is expensive. A pool keeps reusable connections ready.

18.2 Important HikariCP settings

SettingMeaning
maximumPoolSizeMaximum DB connections for one application instance.
minimumIdleIdle connections the pool tries to keep available.
connectionTimeoutMaximum time a request waits for a connection.
idleTimeoutHow long an idle connection can remain.
maxLifetimeMaximum lifetime of a pooled connection.

18.3 Practical sizing formula — Little's Law

DB connection concurrency ≈ Throughput × Average DB time
Example:
500 requests/sec
Average DB time = 20 ms = 0.020 sec

DB concurrency
= 500 × 0.020
= 10 connections

Add headroom for bursts and variation:

10 × 1.5 = 15

Starting point:
maximumPoolSize ≈ 15

18.4 Production example

1,000 requests/sec
Average DB time = 30 ms

Concurrency
= 1,000 × 0.030
= 30 connections

30% headroom
= 30 × 1.3
≈ 39

Starting point
≈ 40 connections
Do not blindly use: CPU cores × 2. Pool size depends on DB latency, query behavior, workload, DB capacity and number of application instances.

18.5 Total connection calculation

10 application instances
× 40 connections per instance
= 400 possible DB connections

The database must support the total, not just the pool size of one instance. Leave capacity for other services, jobs, migrations and administration.

18.7 Pool exhaustion

Request 1..40 → connections occupied

Request 41
    ↓
No connection available
    ↓
wait up to connectionTimeout
    ↓
timeout
    ↓
request fails

Increasing the pool is not always the solution. Too many connections can overload the database, increase CPU usage, lock contention and query latency.

18.8 What should you monitor?

  • Active connections
  • Idle connections
  • Pending/waiting requests
  • Connection acquisition time
  • DB CPU and memory
  • Query latency
  • Slow queries
  • Lock waits

18.9 Senior tuning process

  1. Measure request throughput.
  2. Measure actual DB time.
  3. Calculate approximate DB concurrency.
  4. Add reasonable headroom.
  5. Check database maximum connections.
  6. Multiply by application instance count.
  7. Load test.
  8. Monitor pool and DB metrics.
  9. Tune from real measurements.
Senior point: The goal is not to maximize connections. The goal is to have enough connections to meet the target throughput without overwhelming the database.

20. Dirty Checking

@Transactional
public void updatePayment(Long id) {
    Payment payment = paymentRepository.findById(id).orElseThrow();
    payment.setStatus("SUCCESS");
}
SELECT → managed entity → change field → dirty checking → UPDATE → COMMIT

Hibernate can detect changes to managed entities and flush them at the right time.

21. N+1 Query

List<Order> orders = orderRepository.findAll();

for (Order order : orders) {
    order.getItems();
}

Depending on mappings, this can cause 1 query for orders plus N queries for items. Use appropriate joins, projections or batch fetching.

24. Complete @Transactional Example

@Transactional(
    propagation = Propagation.REQUIRED,
    isolation = Isolation.READ_COMMITTED,
    timeout = 5,
    rollbackFor = PaymentException.class
)
public void updatePayment(Long paymentId, PaymentStatus status) {

    Payment payment =
        paymentRepository.findById(paymentId)
            .orElseThrow();

    payment.setStatus(status);

    transactionRepository.save(
        new PaymentTransaction(paymentId, status)
    );
}
  • REQUIRED: join an existing transaction or create one.
  • READ_COMMITTED: do not read uncommitted changes.
  • timeout=5: limit transaction execution time.
  • rollbackFor: PaymentException should roll back the DB work.
  • Payment update and transaction record should commit together.

26. Database Fundamentals You Should Know as a Senior Backend Engineer

26.1 Index

An index is an extra data structure that helps the database find rows faster.

SELECT *
FROM payment
WHERE user_id = 1001;

If user_id is frequently searched, an index can avoid scanning the entire table.

Without index:
10 million rows
 ↓
scan many/all rows

With index:
user_id = 1001
 ↓
index lookup
 ↓
small set of rows
Indexes speed up reads but cost storage and make INSERT/UPDATE/DELETE more expensive because indexes also need maintenance.

26.2 Composite Index

CREATE INDEX idx_payment_user_status
ON payment(user_id, status);

Column order matters. The database can use the leftmost part efficiently.

WHERE user_id = ?
WHERE user_id = ? AND status = ?

These are usually good matches for this index. A query filtering only by status may not get the same benefit.

26.3 EXPLAIN / Query Plan

EXPLAIN
SELECT *
FROM payment
WHERE user_id = 1001;

Use the execution plan to understand whether the DB uses an index, scans a table, estimates many rows, or performs expensive joins/sorts.

26.4 Full Table Scan

A full table scan reads many or all rows. It is not always bad: for a small table, scanning may be cheaper than using an index. The important point is to understand why the database selected that plan.

26.5 Pagination

For large datasets, avoid returning millions of rows.

SELECT *
FROM payment
ORDER BY id
LIMIT 50;

For very large tables, keyset pagination is often better than a huge OFFSET.

SELECT *
FROM payment
WHERE id > :lastId
ORDER BY id
LIMIT 50;

This avoids walking through many skipped rows.

26.6 Constraints

ConstraintPurpose
PRIMARY KEYUniquely identifies a row.
FOREIGN KEYProtects relationships between tables.
UNIQUEPrevents duplicate business values.
NOT NULLRequires a value.
CHECKProtects simple data rules when supported.

Use the database to protect important invariants. Application validation alone can fail under concurrent requests.

26.7 Unique Constraint + Idempotency

For payment APIs, an idempotency key can be protected by a unique constraint.

CREATE UNIQUE INDEX uk_payment_idempotency
ON payment(idempotency_key);

Two identical requests cannot create two payment records if the database constraint is correctly designed.

26.8 Locking and Row Scope

A good index can reduce the number of rows the database needs to inspect and lock. Poor queries can increase lock scope and contention.

26.9 Long Transaction

 ↓

 ↓
wait 10 seconds
 ↓

This can hold resources for too long. Keep transaction boundaries close to the database work that must be atomic.

26.11 Database Normalization vs Denormalization

Normalization reduces duplicate data and update anomalies. Denormalization intentionally duplicates some data to improve read performance.

Normalized:
Order → Customer
Order → OrderItem → Product

Denormalized:
Order also stores customer_name
for fast reporting/read

Denormalization increases write complexity and consistency responsibility.

26.12 Cache vs Database

Request
 ↓
Redis cache
 ├── HIT  → return quickly
 └── MISS → DB → cache → return

Cache reduces DB load, but creates cache invalidation and consistency problems.

26.13 Cache Stampede

1 million requests
      ↓
same Redis key expires
      ↓
1 million requests hit DB
      ↓
DB overload

Common solutions include locking/single-flight, jittered TTL, background refresh and careful cache-aside design.

26.14 Write-Through / Write-Behind

PatternIdea
Cache-asideApplication reads cache; on miss reads DB and fills cache.
Write-throughWrite goes through cache and DB according to the cache design.
Write-behindCache accepts the write and DB update happens later; higher consistency risk.

26.15 Outbox Pattern

When DB state and an event must be consistent, store the event in the same DB transaction.

BEGIN
 ↓
UPDATE payment = SUCCESS
 ↓
INSERT outbox_event
 ↓
COMMIT
 ↓
Outbox worker publishes event to Kafka
 ↓
mark event as published

This avoids the dangerous situation where the DB commits but the application crashes before publishing the event.

26.16 Backup, Recovery and Replication

  • Backup: recover data after corruption or disaster.
  • Replication: maintain another database copy, often for availability/read scaling.
  • Failover: move traffic to another database when the primary fails.
  • RPO: how much data loss is acceptable.
  • RTO: how quickly the system must recover.

26.17 CAP and Database Trade-offs

In distributed systems, network partitions force trade-offs between consistency and availability. Do not treat distributed database design as simply “make everything strongly consistent”; choose consistency based on the business requirement.

26.18 Production DB Checklist

  • Correct transaction boundary
  • Correct isolation level
  • Indexes based on real query patterns
  • EXPLAIN slow queries
  • Connection pool sized from measurements
  • Read replicas with a clear consistency strategy
  • Locking strategy
  • Deadlock detection/retry
  • Timeouts
  • Slow-query monitoring
  • Backup and recovery plan
  • Idempotency for retryable APIs
  • Outbox for reliable event publishing
  • Capacity/load testing
