JPA, Hibernate, Transaction, ACID, Isolation Level, N+1 Query

A practical senior-level study note explaining how ORM, persistence context, transaction management, isolation, and query performance work in real Spring Boot applications.

JPAHibernate@TransactionalACIDIsolation LevelN+1 QuerySpring Data JPA FetchType Hibernate Cache Database Cache

1. Big Picture

In a typical Spring Boot backend application, these concepts work together.

JPA

A Java specification for ORM. It defines annotations and APIs such as @Entity, EntityManager, and JPQL.

Hibernate

The most common JPA implementation. It provides SQL generation, dirty checking, lazy loading, flushing, and caching.

Spring Data JPA

A Spring abstraction that reduces repository boilerplate by generating repository implementations at runtime.

Transaction

A unit of work that should be committed or rolled back as a whole.

Simple relationship: JPA is the standard, Hibernate is the implementation, Spring Data JPA is the repository abstraction, and Spring Transaction manages commit/rollback boundaries.

2. JPA

Concept Overview

JPA — Java Persistence API is a Java specification for ORM, which means Object Relational Mapping. It defines how Java objects are mapped to relational database tables.

@Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private BigDecimal amount;

    @Column(name = "customer_name")
    private String customerName;
}

This entity maps to a database table like this:

orders
------
id
amount
customer_name
Important: JPA is only a specification. It does not execute SQL by itself. It needs a provider such as Hibernate, EclipseLink, or OpenJPA.

Common JPA APIs and Annotations

ItemPurpose
@EntityMarks a class as a persistent entity.
@IdDefines the primary key.
@OneToMany, @ManyToOneDefines relationships between entities.
EntityManagerMain JPA API for persist, find, merge, remove, and query operations.
JPQLObject-oriented query language based on entities, not database tables directly.

Spring Data JPA

Spring Data JPA is not JPA itself. It is a Spring abstraction that helps us write less repository code.

@Repository
public interface OrderRepository extends JpaRepository<Order, Long> {

    List<Order> findByCustomerName(String customerName);

    @Query("select o from Order o where o.amount > :amount")
    List<Order> findLargeOrders(BigDecimal amount);
}

3. Hibernate

Concept Overview

Hibernate is the most popular implementation of JPA. JPA defines the contract. Hibernate provides the real ORM behavior.

When we call:

entityManager.persist(order);

Hibernate handles:

  • SQL generation
  • Entity state management
  • Persistence Context / first-level cache
  • Dirty checking
  • Lazy loading
  • Flush
  • Mapping Java types to SQL types
  • Optional second-level cache

JPA vs Hibernate

JPAHibernate
SpecificationImplementation
Defines standard APIProvides real ORM behavior
Uses EntityManagerUses Session internally
Portable across providersHas provider-specific features
Defines annotations like @EntityGenerates SQL, tracks changes, manages proxies

Persistence Context

The Persistence Context is a memory area where Hibernate manages entities during a transaction. It is also known as the first-level cache.

@Transactional
public Order getOrder(Long id) {
    Order order1 = entityManager.find(Order.class, id);
    Order order2 = entityManager.find(Order.class, id);

    System.out.println(order1 == order2); // true
    return order1;
}

Hibernate executes SQL only once. The second call returns the same object from the Persistence Context.

Entity States

StateMeaningExample
TransientObject is created but not managed by Hibernate.new Order()
ManagedObject is inside Persistence Context and Hibernate tracks changes.entityManager.persist(order)
DetachedObject was managed before but is no longer attached to current Persistence Context.Entity after transaction/context is closed.
RemovedObject is marked for deletion.entityManager.remove(order)

Dirty Checking

Dirty checking means Hibernate automatically detects changes in managed entities and generates SQL update during flush or commit.

@Transactional
public void updateOrder(Long id) {
    Order order = orderRepository.findById(id)
            .orElseThrow();

    order.setAmount(BigDecimal.valueOf(500));

    // No explicit save is required if the entity is managed.
}

At commit time, Hibernate may execute:

update orders
set amount = ?
where id = ?
Senior note: If the entity is managed inside a transaction, Hibernate can update it automatically through dirty checking. Calling save() is not always required for managed entities.

Flush

Flush means synchronizing changes from the Persistence Context to the database. Flush sends SQL to the database, but it does not necessarily commit the transaction.

@Transactional
public void createOrder() {
    Order order = new Order();
    orderRepository.save(order);

    entityManager.flush(); // Force SQL execution now

    // Transaction is still not committed until the method finishes.
}

Lazy Loading and Eager Loading

@Entity
public class Order {

    @ManyToOne(fetch = FetchType.LAZY)
    private Customer customer;
}

With lazy loading, Hibernate loads related data only when we access it. Lazy loading usually uses proxy objects internally.

Order order = orderRepository.findById(1L).orElseThrow();

// This line can trigger another SQL query
String customerName = order.getCustomer().getName();
Production recommendation: Prefer LAZY by default. Fetch required data explicitly using JOIN FETCH, EntityGraph, or DTO projection.

4. Hibernate Fetching: FetchType, FetchMode, Fetch Strategy

Fetching is one of the most important Hibernate topics for performance. It answers two different questions: when related data is loaded and how related data is loaded.

FetchType

Defines when the association is loaded: immediately with the owner or later when accessed.

FetchMode / Fetch Strategy

Defines how Hibernate loads the association: SELECT, JOIN, BATCH, SUBSELECT, query fetch join, or EntityGraph.

FetchType.LAZY vs FetchType.EAGER

Fetch Type Meaning Pros Risks
FetchType.LAZY Load related data only when it is accessed. Better for performance when relationship data is not always needed. Can cause N+1 queries or LazyInitializationException if accessed outside transaction/session.
FetchType.EAGER Load related data immediately with the owner entity. Convenient when the relationship is always required. Can load too much data, create heavy joins, and make query behavior hard to control.

Default FetchType in JPA

Relationship Default FetchType Senior Recommendation
@ManyToOne EAGER Usually override to LAZY.
@OneToOne EAGER Usually override to LAZY, but be aware of proxy/bytecode enhancement details.
@OneToMany LAZY Keep LAZY.
@ManyToMany LAZY Keep LAZY; avoid direct many-to-many for complex domains.
Senior rule: Prefer marking associations as LAZY by default. Then fetch exactly what each use case needs by using JOIN FETCH, EntityGraph, DTO projection, batch fetching, or subselect fetching.

Example: Prefer LAZY for ManyToOne

@Entity
public class Order {

    @Id
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id")
    private Customer customer;
}

Even though @ManyToOne is EAGER by default in JPA, in real backend systems it is often better to set it to LAZY explicitly. Otherwise, loading an order may unexpectedly load customer data even when the API does not need it.

FetchType vs JOIN FETCH

FetchType.LAZY on the mapping does not mean you can never fetch the relationship together. It only means the default behavior is lazy. For a specific query, you can fetch the relationship explicitly. 

@Query("""
    select o
    from Order o
    join fetch o.customer
    where o.id = :id
""")
Optional<Order> findByIdWithCustomer(Long id);

This keeps the mapping flexible and lets the query decide what data is needed for each use case.

Hibernate Fetch Strategies

Strategy How it works Typical Usage Risk
SELECT Load association using separate select statements. Default lazy behavior. Can cause N+1 queries.
JOIN Load association using SQL join. Fetch required ManyToOne or small relationship data in one query. Can duplicate parent rows and become heavy for large collections.
BATCH Load multiple lazy associations using IN (?, ?, ?). Reduce N+1 when multiple proxies/collections are initialized. Still uses extra queries, but fewer than N+1.
SUBSELECT Load collections using a subselect based on the original parent query. Useful when loading collections for many parent rows. Can be expensive if the parent query is large.
DTO Projection Select only required columns into DTO. Best for read-heavy REST APIs. Not suitable when you need managed entities for updates.

Batch Fetching

Batch fetching reduces N+1 by grouping multiple lazy loads into fewer SQL queries using an IN clause. 

@Entity
public class Customer {

    @OneToMany(mappedBy = "customer")
    @BatchSize(size = 50)
    private List<Order> orders = new ArrayList<>();
}

Or configure globally:

spring.jpa.properties.hibernate.default_batch_fetch_size=50

Instead of:

select * from orders where customer_id = 1;
select * from orders where customer_id = 2;
select * from orders where customer_id = 3;

Hibernate can optimize to:

select * from orders where customer_id in (?, ?, ?);

Subselect Fetching

Subselect fetching loads all collections for the parent entities returned by the original query. 

@Entity
public class Customer {

    @OneToMany(mappedBy = "customer")
    @Fetch(FetchMode.SUBSELECT)
    private List<Order> orders = new ArrayList<>();
}

Example behavior:

select * from customers where status = 'ACTIVE';

select * from orders
where customer_id in (
    select id from customers where status = 'ACTIVE'
);
When to use: Batch fetching is usually safer as a general default. Subselect fetching can be useful when you know the parent query is controlled and not too large.

EntityGraph

EntityGraph lets you keep entity mappings lazy but define a fetch plan for a specific repository method. 

@EntityGraph(attributePaths = {"customer", "items"})
@Query("select o from Order o where o.id = :id")
Optional<Order> findDetailById(Long id);

LazyInitializationException

LazyInitializationException happens when lazy data is accessed after the Hibernate Session / Persistence Context is already closed. 

@Service
public class OrderService {

    public Order getOrder(Long id) {
        return orderRepository.findById(id).orElseThrow();
    }
}

// Later, outside transaction/session:
order.getCustomer().getName(); // LazyInitializationException

Good solutions

  • Use @Transactional(readOnly = true) around read logic and map to DTO inside the transaction.
  • Use JOIN FETCH or EntityGraph for required associations.
  • Use DTO projection for read APIs.

Bad solutions

  • Changing everything to EAGER.
  • Relying on Open Session In View to hide poor fetch planning.
  • Returning JPA entities directly from REST controllers.
Interview warning: EAGER is not a real solution for N+1 or lazy loading issues. It often moves the problem to another place and makes performance less predictable.

5. Hibernate Cache Levels

Hibernate caching is another very important performance topic. There are multiple cache layers, and each one has a different lifecycle and purpose.

Cache Level Overview

Cache Scope Enabled by default? Purpose
First-Level Cache One Hibernate Session / JPA EntityManager Yes Avoid repeated DB access for the same entity inside the same Persistence Context.
Second-Level Cache SessionFactory / EntityManagerFactory No, must be configured Share cached entity data across sessions.
Query Cache Second-level cache region No, must be enabled and query must be marked cacheable Cache query result identifiers, not full entity objects.
Collection Cache Second-level cache region No, explicit mapping required Cache collection relationship data such as a list of child IDs.
Natural ID Cache Second-level cache region No, explicit mapping required Cache lookup by business key such as email, username, or code.

First-Level Cache

First-level cache is the Persistence Context. It exists inside one Hibernate Session / JPA EntityManager. 

@Transactional(readOnly = true)
public void demo(Long id) {
    Product p1 = entityManager.find(Product.class, id);
    Product p2 = entityManager.find(Product.class, id);

    System.out.println(p1 == p2); // true
}

The first query loads the entity from the database. The second call returns the same managed object from the Persistence Context.

Important: First-level cache is not a distributed cache and not an application-wide cache. It only lives within the current Persistence Context.

Second-Level Cache

Second-level cache is shared across sessions under the same SessionFactory. It can reduce database access for reference data or data that changes infrequently. 

@Entity
@Cacheable
@org.hibernate.annotations.Cache(
    usage = CacheConcurrencyStrategy.READ_WRITE,
    region = "product"
)
public class Product {

    @Id
    private Long id;

    private String name;
}

Typical Spring Boot configuration example:

spring.jpa.properties.hibernate.cache.use_second_level_cache=true
spring.jpa.properties.hibernate.cache.region.factory_class=org.hibernate.cache.jcache.JCacheRegionFactory
spring.jpa.properties.hibernate.javax.cache.provider=org.ehcache.jsr107.EhcacheCachingProvider

Cache Concurrency Strategies

Strategy Use Case Risk / Note
READ_ONLY Immutable reference data, countries, currencies, static config. Fastest, but data must not be updated.
NONSTRICT_READ_WRITE Data rarely updated and small stale window is acceptable. Possible stale reads.
READ_WRITE Data can be updated and stronger consistency is needed. More overhead due to consistency handling.
TRANSACTIONAL Requires transactional cache provider support. More complex, provider-dependent.

Query Cache

Query cache does not simply cache full entity objects. It usually caches query result identifiers and works together with the second-level cache. 

@QueryHints({
    @QueryHint(name = "org.hibernate.cacheable", value = "true"),
    @QueryHint(name = "org.hibernate.cacheRegion", value = "productQueries")
})
@Query("select p from Product p where p.status = :status")
List<Product> findByStatusCached(ProductStatus status);
Important: Query cache is useful mostly for stable query results. For frequently changing tables, it can add invalidation overhead and may not improve performance.

What Should Be Cached?

Good Candidate Bad Candidate
Reference data: country, currency, role, permission, product category. Highly transactional data: order, payment, stock movement, account balance.
Data read frequently but updated rarely. Data updated frequently by many users or services.
Small or medium-size entities. Large entity graphs with many collections.

Cache Eviction

Sometimes cached data must be removed manually, especially after external updates or admin operations. 

SessionFactory sessionFactory = entityManagerFactory.unwrap(SessionFactory.class);

sessionFactory.getCache().evictEntityData(Product.class, productId);
sessionFactory.getCache().evictEntityData(Product.class);
sessionFactory.getCache().evictAllRegions();

Senior Cache Advice

  • Do not enable second-level cache for everything.
  • Start with reference/read-mostly data.
  • Measure cache hit ratio, query count, memory usage, and stale data risk.
  • Be careful with multi-node deployments because cache invalidation/replication matters.
  • DTO projection may be better than Hibernate cache for many API read cases.

6. Database, Application, and Cache Layers

In production, performance is not only Hibernate cache. Data may be cached at several layers.

Common Cache Layers in Backend Systems

Layer Example Purpose Risk
Hibernate L1 Cache Persistence Context Avoid duplicate entity loads within one transaction/session. Memory grows if processing many entities without clearing.
Hibernate L2 Cache Ehcache, Infinispan, Hazelcast via provider Reuse entity state across sessions. Stale data, invalidation complexity.
Application Cache Spring Cache, Caffeine, Redis Cache DTOs, API responses, computed results, external API responses. Cache invalidation, TTL strategy, consistency.
Database Buffer Cache PostgreSQL shared buffers, Oracle buffer cache, MySQL buffer pool Cache frequently accessed data pages/index pages in DB memory. Not controlled directly from application code.
Database Plan Cache Prepared statement / execution plan cache Reuse parsed SQL/execution plans. Bad plans can hurt performance depending on parameters/statistics.
Result / Materialized Cache Materialized view, DB result cache depending on DB Precompute expensive query results. Refresh strategy and stale data.

Hibernate Cache vs Redis/Application Cache

Hibernate L2 Cache Redis / Application Cache
Works at ORM entity level. Works at application-defined data level: DTO, response, token, session, external API result.
Tightly integrated with Hibernate entity lifecycle. More flexible and can cache non-DB data.
Best for reference/read-mostly entities. Best for expensive computed result, API response, distributed cache, rate limit, session, temporary data.
Can be risky for transactional entities. Requires explicit TTL/invalidation design.

Example: Spring Cache with Redis/Caffeine

@Service
public class ProductQueryService {

    @Cacheable(value = "productDetail", key = "#id")
    public ProductDetailDto getProductDetail(Long id) {
        return productRepository.findProductDetail(id)
                .orElseThrow();
    }

    @CacheEvict(value = "productDetail", key = "#id")
    public void evictProductDetail(Long id) {
        // Evict cache after update
    }
}

Cache Decision Guide

Situation Recommended Approach
Need to update entity inside transaction. Use JPA/Hibernate normally. Avoid DTO cache for write path.
Read API needs only a few columns. Use DTO projection first.
Reference data changes rarely. Consider Hibernate L2 cache or application cache.
External API result is slow and can be reused. Use Redis/Caffeine with TTL.
Database query is slow due to missing index. Fix query/index/execution plan before adding cache.
Senior mindset: Cache is not a replacement for a bad query, missing index, wrong fetch plan, or incorrect transaction design. First optimize data access, then add cache when the data access pattern is stable and measurable.

7. Transaction

Concept Overview

A transaction is a unit of work that should be completed fully or rolled back fully.

@Transactional
public void placeOrder(OrderRequest request) {
    orderRepository.save(order);
    paymentRepository.save(payment);
    stockRepository.reduceStock(productId, quantity);
}

If payment fails, the order and stock update should be rolled back.

How @Transactional Works

In Spring, @Transactional is implemented using AOP proxy.

Client calls proxy
↓
Proxy opens transaction
↓
Business method executes
↓
If success: commit
If exception: rollback
↓
Release connection

Simplified internal flow:

@Transactional method called
↓
TransactionInterceptor
↓
PlatformTransactionManager
↓
Open database connection
↓
Set autoCommit = false
↓
Execute business method
↓
Commit or rollback
↓
Close/release connection

Rollback Rules

By default, Spring rolls back for RuntimeException and Error, but not checked exceptions.

@Transactional(rollbackFor = IOException.class)
public void process() throws IOException {
    throw new IOException();
}

Transaction Propagation

PropagationMeaningCommon Usage
REQUIREDUse existing transaction, or create a new one if none exists.Default for service methods.
REQUIRES_NEWSuspend current transaction and create a new one.Audit log, independent event logging.
MANDATORYMust run inside an existing transaction.Low-level method that must be called from transactional service.
SUPPORTSUse transaction if available, otherwise run without transaction.Read-only helper logic.
NOT_SUPPORTEDAlways run without transaction.Non-transactional long-running work.
NEVERThrow exception if transaction exists.Rarely used.
NESTEDRuns inside nested transaction using savepoint if supported.Partial rollback with savepoint.

Common @Transactional Pitfalls

1. Self-invocation problem

@Service
public class OrderService {

    public void methodA() {
        methodB(); // Bypasses proxy
    }

    @Transactional
    public void methodB() {
        // Transaction may not work here
    }
}

2. Private method does not work

@Transactional
private void saveOrder() {
}

3. Exception swallowed

@Transactional
public void createOrder() {
    try {
        paymentService.pay();
    } catch (Exception e) {
        log.error("Payment failed", e);
        // If not rethrown, Spring may commit the transaction
    }
}
Important: If exception is caught and not rethrown, Spring thinks the method succeeded and may commit the transaction.

8. ACID

ACID is a set of properties that guarantee reliable transaction processing.

PropertyMeaningExample
A — AtomicityAll operations succeed together or fail together.Debit account A and credit account B must happen together.
C — ConsistencyDatabase moves from one valid state to another valid state.Unique email, valid foreign key, non-negative balance.
I — IsolationConcurrent transactions should not affect each other incorrectly.Two users reducing stock at the same time.
D — DurabilityAfter commit, data should survive system crash.Database transaction log / redo log / write-ahead log.

Atomicity Example

@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    accountRepository.debit(fromId, amount);
    accountRepository.credit(toId, amount);
}

Isolation Example

Stock = 10

Transaction A reads 10
Transaction B reads 10

A subtracts 1 → 9
B subtracts 1 → 9

Expected stock = 8
Actual stock = 9

This is a lost update problem.

9. Isolation Level

Isolation level controls how concurrent transactions see each other's changes. Higher isolation gives stronger consistency but lower concurrency.

Common Concurrency Problems

ProblemDescription
Dirty ReadA transaction reads uncommitted data from another transaction.
Non-repeatable ReadA transaction reads the same row twice and gets different values because another transaction committed an update.
Phantom ReadA transaction runs the same query twice and gets different rows because another transaction inserted or deleted rows.
Lost UpdateTwo transactions read the same value and update based on the old value, causing one update to be lost.

Isolation Level Comparison

Isolation LevelDirty ReadNon-repeatable ReadPhantom ReadPerformance
READ_UNCOMMITTEDPossiblePossiblePossibleHighest
READ_COMMITTEDPreventedPossiblePossibleHigh
REPEATABLE_READPreventedPreventedPossible depending on DBMedium
SERIALIZABLEPreventedPreventedPreventedLowest

Spring Example

@Transactional(isolation = Isolation.READ_COMMITTED)
public void createOrder() {
    // business logic
}
Senior note: Spring only passes the isolation level to the database. The actual behavior depends on the database engine.

Database Defaults

DatabaseCommon Default Isolation
PostgreSQLREAD COMMITTED
OracleREAD COMMITTED
MySQL InnoDBREPEATABLE READ

10. N+1 Query

Concept Overview

N+1 query is a common ORM performance problem. It happens when the application executes one query to load parent records, then N additional queries to load related records.

1 query to load 100 orders
100 additional queries to load customer for each order

Total = 101 queries

N+1 with ManyToOne

@Entity
public class Order {

    @Id
    private Long id;

    private BigDecimal amount;

    @ManyToOne(fetch = FetchType.LAZY)
    private Customer customer;
}
@Transactional(readOnly = true)
public List<OrderDto> getOrders() {
    List<Order> orders = orderRepository.findAll();

    return orders.stream()
            .map(order -> new OrderDto(
                    order.getId(),
                    order.getCustomer().getName()
            ))
            .toList();
}

SQL may look like this:

select * from orders;

select * from customers where id = ?;
select * from customers where id = ?;
select * from customers where id = ?;
...

N+1 with OneToMany

@Entity
public class Customer {

    @Id
    private Long id;

    @OneToMany(mappedBy = "customer", fetch = FetchType.LAZY)
    private List<Order> orders;
}
@Transactional(readOnly = true)
public List<CustomerDto> getCustomers() {
    List<Customer> customers = customerRepository.findAll();

    return customers.stream()
            .map(customer -> new CustomerDto(
                    customer.getName(),
                    customer.getOrders().size()
            ))
            .toList();
}

Why N+1 Happens

  • Lazy loading inside a loop.
  • Accessing relationships after loading parent records.
  • Poor fetch planning.
  • Returning JPA entities directly from REST APIs.
  • JSON serialization triggers lazy loading.
  • Using EAGER mapping without understanding the query plan.
Production warning: Do not expose JPA entities directly from REST APIs. Use DTOs and control fetching explicitly.

How to Fix N+1

Solution 1: JOIN FETCH

@Query("""
    select o
    from Order o
    join fetch o.customer
""")
List<Order> findAllWithCustomer();

Solution 2: EntityGraph

@EntityGraph(attributePaths = {"customer"})
@Query("select o from Order o")
List<Order> findAllWithCustomer();

Solution 3: DTO Projection

@Query("""
    select new com.example.OrderDto(
        o.id,
        c.name,
        o.amount
    )
    from Order o
    join o.customer c
""")
List<OrderDto> findOrderDtos();

Solution 4: Batch Fetching

spring.jpa.properties.hibernate.default_batch_fetch_size=50
@BatchSize(size = 50)
@OneToMany(mappedBy = "customer")
private List<Order> orders;

Solution 5: Do not use EAGER everywhere

Do not fix N+1 by changing every relationship to FetchType.EAGER. It can load unnecessary data, create huge joins, and make performance unpredictable.

11. Senior-Level Interview Answer — English

JPA is a Java specification for ORM. It defines how Java objects are mapped to relational database tables using annotations such as @Entity, @Id, @OneToMany, and APIs like EntityManager and JPQL. Hibernate is one of the most popular JPA implementations. It provides the actual ORM behavior such as SQL generation, persistence context, dirty checking, lazy loading, flushing, and caching.

In Hibernate, the Persistence Context works as a first-level cache and manages entity states such as transient, managed, detached, and removed. When an entity is managed, Hibernate automatically tracks changes through dirty checking and synchronizes them to the database during flush or transaction commit.

A transaction is a unit of work that should be committed or rolled back as a whole. In Spring, @Transactional is implemented using AOP proxy. The proxy opens a transaction before method execution and commits or rolls back after execution. By default, Spring rolls back on runtime exceptions, but checked exceptions require rollbackFor.

ACID means Atomicity, Consistency, Isolation, and Durability. Isolation levels control how concurrent transactions interact. READ COMMITTED prevents dirty reads, REPEATABLE READ prevents non-repeatable reads, and SERIALIZABLE provides the strongest isolation but with lower performance.

N+1 query is a common ORM performance issue where one query loads parent entities and then N additional queries load related entities. It usually happens because of lazy loading inside loops or poor fetch planning. We can solve it using JOIN FETCH, EntityGraph, DTO projection, or Hibernate batch fetching. In production, I usually prefer DTO projection for read APIs and explicit fetch planning instead of relying on default lazy or eager behavior.

For Hibernate fetching, I normally keep associations LAZY by default and choose the fetch plan per use case. For caching, I treat first-level cache as transaction/session-level cache, and I only enable second-level or query cache for read-mostly data after measuring query count, cache hit ratio, and stale data risk.

9. JPA là gì?

JPA — Java Persistence API là một specification của Java dùng cho ORM. ORM nghĩa là mapping giữa object trong Java và table trong database.

@Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private BigDecimal amount;

    @Column(name = "customer_name")
    private String customerName;
}
Điểm quan trọng: JPA không phải implementation. JPA chỉ là specification. Nó cần implementation như Hibernate, EclipseLink hoặc OpenJPA.

JPA cung cấp gì?

  • Annotation để mapping entity: @Entity, @Id, @Table, @Column.
  • Annotation để mapping relationship: @OneToMany, @ManyToOne, @OneToOne, @ManyToMany.
  • API thao tác persistence: EntityManager.
  • Ngôn ngữ query theo object: JPQL.
  • Criteria API cho dynamic query.

Spring Data JPA

Spring Data JPA là abstraction của Spring giúp giảm boilerplate khi viết repository.

@Repository
public interface OrderRepository extends JpaRepository<Order, Long> {

    List<Order> findByCustomerName(String customerName);

    @Query("select o from Order o where o.amount > :amount")
    List<Order> findLargeOrders(BigDecimal amount);
}

10. Hibernate

Hibernate là implementation phổ biến nhất của JPA. JPA định nghĩa chuẩn, còn Hibernate thực thi chuẩn đó.

Khi gọi:

entityManager.persist(order);

Hibernate xử lý bên trong:

  • Generate SQL.
  • Quản lý Persistence Context.
  • Dirty checking.
  • Lazy loading.
  • Flush.
  • Cache.
  • Mapping Java type sang SQL type.

JPA vs Hibernate

JPAHibernate
SpecificationImplementation
Định nghĩa chuẩn APICung cấp ORM thật sự
Có EntityManager, @Entity, @IdGenerate SQL, dirty checking, lazy loading
Có thể đổi providerCó feature riêng của Hibernate
Nói dễ hiểu: JPA giống như interface, Hibernate giống như class implement interface đó.

Persistence Context

Persistence Context là vùng nhớ nơi Hibernate quản lý entity trong một transaction. Nó cũng chính là first-level cache.

@Transactional
public Order getOrder(Long id) {
    Order order1 = entityManager.find(Order.class, id);
    Order order2 = entityManager.find(Order.class, id);

    System.out.println(order1 == order2); // true
    return order1;
}

Entity States

StateÝ nghĩa
TransientObject mới tạo bằng new, chưa được Hibernate quản lý.
ManagedEntity đang nằm trong Persistence Context, Hibernate đang track thay đổi.
DetachedEntity từng được quản lý, nhưng hiện tại không còn thuộc Persistence Context.
RemovedEntity được đánh dấu để delete.

Dirty Checking

Dirty checking là cơ chế Hibernate tự phát hiện thay đổi của managed entity và generate SQL update.

@Transactional
public void updateOrder(Long id) {
    Order order = orderRepository.findById(id)
            .orElseThrow();

    order.setAmount(BigDecimal.valueOf(500));

    // Không cần gọi save nếu entity đang managed
}
Nếu entity đang ở managed state trong transaction, Hibernate có thể tự update DB thông qua dirty checking.

Flush

Flush là quá trình Hibernate đồng bộ thay đổi trong Persistence Context xuống database. Flush gửi SQL xuống DB, nhưng chưa chắc đã commit transaction.

@Transactional
public void createOrder() {
    Order order = new Order();
    orderRepository.save(order);

    entityManager.flush(); // ép Hibernate gửi SQL xuống DB
}

Lazy Loading và Eager Loading

Lazy loading nghĩa là data liên quan chỉ được load khi thật sự access. Eager loading nghĩa là load relationship ngay lập tức.

Trong production, không nên lạm dụng EAGER. Nên dùng LAZY mặc định và fetch rõ ràng theo từng use case bằng JOIN FETCH, EntityGraph hoặc DTO projection.

11. Hibernate Fetching: FetchType, FetchMode, Fetch Strategy

Fetching là chủ đề rất hay bị hỏi khi phỏng vấn Senior vì nó ảnh hưởng trực tiếp tới performance. Cần phân biệt rõ khi nào load data và load data bằng cách nào.

FetchType

Quyết định khi nào association được load: load ngay hay load khi access.

FetchMode / Fetch Strategy

Quyết định Hibernate load association bằng cách nào: SELECT, JOIN, BATCH, SUBSELECT, JOIN FETCH hoặc EntityGraph.

FetchType.LAZY vs FetchType.EAGER

Fetch Type Ý nghĩa Ưu điểm Rủi ro
FetchType.LAZY Chỉ load data liên quan khi thật sự access. Tốt hơn cho performance nếu không phải lúc nào cũng cần relationship data. Có thể gây N+1 query hoặc LazyInitializationException.
FetchType.EAGER Load data liên quan ngay khi load owner entity. Tiện nếu relationship luôn cần. Dễ load dư data, query nặng, khó kiểm soát performance.

Default FetchType trong JPA

Relationship Default FetchType Khuyến nghị Senior
@ManyToOne EAGER Thường nên override sang LAZY.
@OneToOne EAGER Thường nên override sang LAZY, nhưng cần hiểu proxy/bytecode enhancement.
@OneToMany LAZY Giữ LAZY.
@ManyToMany LAZY Giữ LAZY, tránh many-to-many trực tiếp nếu domain phức tạp.
Rule khi đi phỏng vấn: Mapping nên để LAZY mặc định. API nào cần data gì thì fetch rõ ràng bằng JOIN FETCH, EntityGraph, DTO projection, batch fetching hoặc subselect fetching.

Ví dụ: override ManyToOne sang LAZY

@Entity
public class Order {

    @Id
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id")
    private Customer customer;
}

Dù @ManyToOne default là EAGER trong JPA, ở project thực tế thường nên set rõ là LAZY. Nếu không, khi load Order có thể load luôn Customer dù API không cần.

FetchType khác JOIN FETCH thế nào?

FetchType.LAZY trong mapping chỉ là behavior mặc định. Với từng query cụ thể, mình vẫn có thể fetch association ngay bằng JOIN FETCH. 

@Query("""
    select o
    from Order o
    join fetch o.customer
    where o.id = :id
""")
Optional<Order> findByIdWithCustomer(Long id);

Cách này giúp entity mapping linh hoạt, còn query quyết định data nào cần load cho từng use case.

Các Fetch Strategy của Hibernate

Strategy Cách hoạt động Khi nào dùng Rủi ro
SELECT Load association bằng câu select riêng. Default lazy behavior. Có thể gây N+1 query.
JOIN Load association bằng SQL join. Khi cần fetch ManyToOne hoặc relationship nhỏ trong một query. Có thể duplicate parent row và query nặng nếu join collection lớn.
BATCH Load nhiều lazy association bằng IN (?, ?, ?). Giảm N+1 khi nhiều proxy/collection được initialize. Vẫn có query phụ, nhưng ít hơn N+1.
SUBSELECT Load collection bằng subselect dựa trên parent query ban đầu. Khi load collection cho nhiều parent rows. Có thể nặng nếu parent query quá lớn.
DTO Projection Select column cần thiết vào DTO. Rất tốt cho read API. Không phù hợp nếu cần managed entity để update.

Batch Fetching

Batch fetching giúp giảm N+1 bằng cách gom nhiều lazy load thành ít query hơn bằng mệnh đề IN. 

@Entity
public class Customer {

    @OneToMany(mappedBy = "customer")
    @BatchSize(size = 50)
    private List<Order> orders = new ArrayList<>();
}

Hoặc config global:

spring.jpa.properties.hibernate.default_batch_fetch_size=50

Thay vì:

select * from orders where customer_id = 1;
select * from orders where customer_id = 2;
select * from orders where customer_id = 3;

Hibernate có thể tối ưu thành:

select * from orders where customer_id in (?, ?, ?);

Subselect Fetching

@Entity
public class Customer {

    @OneToMany(mappedBy = "customer")
    @Fetch(FetchMode.SUBSELECT)
    private List<Order> orders = new ArrayList<>();
}

Ví dụ behavior:

select * from customers where status = 'ACTIVE';

select * from orders
where customer_id in (
    select id from customers where status = 'ACTIVE'
);
Khi nào dùng: Batch fetching thường an toàn hơn để config chung. Subselect fetching phù hợp khi parent query được kiểm soát và không quá lớn.

EntityGraph

EntityGraph giúp giữ mapping là LAZY nhưng định nghĩa fetch plan riêng cho từng repository method. 

@EntityGraph(attributePaths = {"customer", "items"})
@Query("select o from Order o where o.id = :id")
Optional<Order> findDetailById(Long id);

LazyInitializationException

LazyInitializationException xảy ra khi lazy data được access sau khi Hibernate Session / Persistence Context đã đóng. 

@Service
public class OrderService {

    public Order getOrder(Long id) {
        return orderRepository.findById(id).orElseThrow();
    }
}

// Bên ngoài transaction/session:
order.getCustomer().getName(); // LazyInitializationException

Cách xử lý tốt

  • Dùng @Transactional(readOnly = true) và map sang DTO bên trong transaction.
  • Dùng JOIN FETCH hoặc EntityGraph cho association cần thiết.
  • Dùng DTO projection cho read API.

Cách xử lý không tốt

  • Đổi hết relationship sang EAGER.
  • Phụ thuộc vào Open Session In View để che lỗi fetch plan.
  • Return JPA entity trực tiếp từ REST controller.
Điểm phỏng vấn: EAGER không phải giải pháp thật sự cho N+1 hoặc lazy loading issue. Nó thường chỉ chuyển vấn đề performance sang chỗ khác.

12. Hibernate Cache Levels

Hibernate cache có nhiều level khác nhau. Mỗi level có scope, lifecycle và mục đích riêng.

Tổng quan cache level

Cache Scope Mặc định bật? Mục đích
First-Level Cache Một Hibernate Session / JPA EntityManager Có Tránh query DB lặp lại cho cùng entity trong cùng Persistence Context.
Second-Level Cache SessionFactory / EntityManagerFactory Không, cần config Share cached entity data giữa nhiều session.
Query Cache Second-level cache region Không, cần enable và mark query cacheable Cache danh sách ID kết quả query, không đơn giản là cache full object.
Collection Cache Second-level cache region Không, cần mapping rõ Cache relationship/collection data, ví dụ list child IDs.
Natural ID Cache Second-level cache region Không, cần mapping rõ Cache lookup theo business key như email, username, code.

First-Level Cache

First-level cache chính là Persistence Context. Nó tồn tại trong một Hibernate Session / JPA EntityManager. 

@Transactional(readOnly = true)
public void demo(Long id) {
    Product p1 = entityManager.find(Product.class, id);
    Product p2 = entityManager.find(Product.class, id);

    System.out.println(p1 == p2); // true
}
First-level cache không phải distributed cache và không phải application-wide cache. Nó chỉ sống trong current Persistence Context.

Second-Level Cache

Second-level cache được share giữa nhiều session trong cùng SessionFactory. Nó phù hợp với reference data hoặc data ít thay đổi. 

@Entity
@Cacheable
@org.hibernate.annotations.Cache(
    usage = CacheConcurrencyStrategy.READ_WRITE,
    region = "product"
)
public class Product {

    @Id
    private Long id;

    private String name;
}

Ví dụ config Spring Boot:

spring.jpa.properties.hibernate.cache.use_second_level_cache=true
spring.jpa.properties.hibernate.cache.region.factory_class=org.hibernate.cache.jcache.JCacheRegionFactory
spring.jpa.properties.hibernate.javax.cache.provider=org.ehcache.jsr107.EhcacheCachingProvider

Cache Concurrency Strategy

Strategy Khi nào dùng Lưu ý
READ_ONLY Data immutable/reference data: country, currency, static config. Nhanh nhất, nhưng data không được update.
NONSTRICT_READ_WRITE Data ít update và chấp nhận stale data trong thời gian ngắn. Có thể đọc data cũ.
READ_WRITE Data có update và cần consistency tốt hơn. Overhead cao hơn.
TRANSACTIONAL Cần cache provider hỗ trợ transactional. Phức tạp và phụ thuộc provider.

Query Cache

Query cache thường cache result identifiers và phối hợp với second-level cache. Nó không đơn giản là cache full entity object. 

@QueryHints({
    @QueryHint(name = "org.hibernate.cacheable", value = "true"),
    @QueryHint(name = "org.hibernate.cacheRegion", value = "productQueries")
})
@Query("select p from Product p where p.status = :status")
List<Product> findByStatusCached(ProductStatus status);
Query cache chỉ nên dùng cho query result ổn định. Nếu table thay đổi liên tục, invalidation overhead có thể làm chậm hơn.

Nên cache gì?

Nên cache Không nên cache
Reference data: country, currency, role, permission, product category. Transactional data: order, payment, stock movement, account balance.
Data đọc nhiều, update ít. Data update liên tục bởi nhiều user/service.
Entity nhỏ hoặc vừa. Entity graph lớn, nhiều collection.

Cache Eviction

SessionFactory sessionFactory = entityManagerFactory.unwrap(SessionFactory.class);

sessionFactory.getCache().evictEntityData(Product.class, productId);
sessionFactory.getCache().evictEntityData(Product.class);
sessionFactory.getCache().evictAllRegions();

Senior Cache Advice

  • Không bật second-level cache cho tất cả entity.
  • Bắt đầu với reference/read-mostly data.
  • Đo cache hit ratio, số lượng query, memory usage và stale data risk.
  • Cẩn thận với multi-node deployment vì cache invalidation/replication rất quan trọng.
  • Với nhiều read API, DTO projection có thể tốt hơn Hibernate cache.

13. Database, Application, and Cache Layers

Trong production, performance không chỉ nằm ở Hibernate cache. Data có thể được cache ở nhiều layer khác nhau.

Các cache layer phổ biến

Layer Ví dụ Mục đích Rủi ro
Hibernate L1 Cache Persistence Context Tránh load duplicate entity trong một transaction/session. Memory tăng nếu xử lý quá nhiều entity mà không clear.
Hibernate L2 Cache Ehcache, Infinispan, Hazelcast qua provider Reuse entity state giữa nhiều session. Stale data, invalidation phức tạp.
Application Cache Spring Cache, Caffeine, Redis Cache DTO, API response, computed result, external API response. TTL, invalidation, consistency.
Database Buffer Cache PostgreSQL shared buffers, Oracle buffer cache, MySQL buffer pool Cache data page/index page trong memory của database. Application không điều khiển trực tiếp.
Database Plan Cache Prepared statement / execution plan cache Reuse parsed SQL/execution plan. Bad plan có thể làm performance tệ tùy parameter/statistics.
Result / Materialized Cache Materialized view, DB result cache tùy DB Precompute expensive query result. Cần refresh strategy, có thể stale data.

Hibernate Cache vs Redis/Application Cache

Hibernate L2 Cache Redis / Application Cache
Cache ở ORM entity level. Cache ở application-defined level: DTO, response, token, session, external API result.
Gắn chặt với Hibernate entity lifecycle. Linh hoạt hơn và cache được cả non-DB data.
Tốt cho reference/read-mostly entity. Tốt cho computed result, API response, distributed cache, rate limit, session, temporary data.
Rủi ro với transactional entity. Cần thiết kế TTL/invalidation rõ ràng.

Ví dụ Spring Cache

@Service
public class ProductQueryService {

    @Cacheable(value = "productDetail", key = "#id")
    public ProductDetailDto getProductDetail(Long id) {
        return productRepository.findProductDetail(id)
                .orElseThrow();
    }

    @CacheEvict(value = "productDetail", key = "#id")
    public void evictProductDetail(Long id) {
        // Evict cache after update
    }
}

Cache Decision Guide

Tình huống Cách nên dùng
Cần update entity trong transaction. Dùng JPA/Hibernate bình thường. Tránh DTO cache cho write path.
Read API chỉ cần vài column. Ưu tiên DTO projection.
Reference data ít thay đổi. Cân nhắc Hibernate L2 cache hoặc application cache.
External API chậm và có thể reuse. Dùng Redis/Caffeine với TTL.
Query chậm do thiếu index. Sửa query/index/execution plan trước khi thêm cache.
Senior mindset: Cache không thay thế cho bad query, missing index, wrong fetch plan hoặc transaction design sai. Trước tiên phải tối ưu data access, sau đó mới thêm cache khi access pattern rõ ràng và đo lường được.

14. Transaction

Transaction là một unit of work. Các thao tác bên trong transaction phải thành công hết hoặc rollback hết.

@Transactional
public void placeOrder(OrderRequest request) {
    orderRepository.save(order);
    paymentRepository.save(payment);
    stockRepository.reduceStock(productId, quantity);
}

@Transactional hoạt động thế nào?

Trong Spring, @Transactional được implement bằng AOP proxy.

Client gọi proxy
↓
Proxy mở transaction
↓
Business method chạy
↓
Nếu success → commit
Nếu exception → rollback
↓
Release connection

Rollback Rule

Mặc định Spring rollback với RuntimeException và Error, nhưng không rollback với checked exception theo mặc định.

@Transactional(rollbackFor = IOException.class)
public void process() throws IOException {
    throw new IOException();
}

Propagation

PropagationÝ nghĩa
REQUIREDDefault. Có transaction thì dùng transaction hiện tại, chưa có thì tạo mới.
REQUIRES_NEWLuôn tạo transaction mới, transaction hiện tại bị suspend.
MANDATORYBắt buộc phải có transaction trước đó.
SUPPORTSCó transaction thì tham gia, không có thì chạy không transaction.
NOT_SUPPORTEDLuôn chạy ngoài transaction.
NEVERKhông được chạy trong transaction.
NESTEDTạo nested transaction dùng savepoint nếu DB hỗ trợ.

Pitfalls thường gặp

  • Self-invocation: method trong cùng class gọi nhau làm bypass proxy.
  • @Transactional trên private method không hoạt động.
  • Final method/class có thể làm proxy không hoạt động đúng.
  • Catch exception nhưng không throw lại làm transaction commit ngoài ý muốn.

16. Isolation Level

Isolation level quyết định transaction này nhìn thấy dữ liệu của transaction khác như thế nào.

Các vấn đề concurrency phổ biến

17. N+1 Query

N+1 query là vấn đề performance phổ biến khi dùng ORM. Nó xảy ra khi một query load danh sách parent, sau đó phát sinh thêm N query để load related entity.

1 query load 100 orders
100 query load customer cho từng order

Total = 101 queries

Ví dụ với ManyToOne

@Entity
public class Order {

    @Id
    private Long id;

    private BigDecimal amount;

    @ManyToOne(fetch = FetchType.LAZY)
    private Customer customer;
}
@Transactional(readOnly = true)
public List<OrderDto> getOrders() {
    List<Order> orders = orderRepository.findAll();

    return orders.stream()
            .map(order -> new OrderDto(
                    order.getId(),
                    order.getCustomer().getName()
            ))
            .toList();
}

SQL có thể thành:

select * from orders;

select * from customers where id = ?;
select * from customers where id = ?;
select * from customers where id = ?;
...

Vì sao N+1 xảy ra?

  • Lazy loading trong vòng lặp.
  • Access relationship sau khi load parent.
  • Không có fetch plan rõ ràng.
  • Trả entity trực tiếp ra REST API.
  • JSON serialization trigger lazy loading.
  • Dùng EAGER không kiểm soát.

Cách fix N+1

Cách 1: JOIN FETCH

@Query("""
    select o
    from Order o
    join fetch o.customer
""")
List<Order> findAllWithCustomer();

Cách 2: EntityGraph

@EntityGraph(attributePaths = {"customer"})
@Query("select o from Order o")
List<Order> findAllWithCustomer();

Cách 3: DTO Projection

@Query("""
    select new com.example.OrderDto(
        o.id,
        c.name,
        o.amount
    )
    from Order o
    join o.customer c
""")
List<OrderDto> findOrderDtos();

Cách 4: Batch Fetching

spring.jpa.properties.hibernate.default_batch_fetch_size=50

Cách 5: Không dùng EAGER bừa bãi

Không nên fix N+1 bằng cách đổi hết sang FetchType.EAGER. Nên dùng LAZY mặc định, API nào cần data gì thì fetch rõ ràng ở query đó.

18. Câu trả lời phỏng vấn — Vietnamese

JPA là một specification của Java dùng cho ORM, định nghĩa cách map Java object với relational database thông qua các annotation như @Entity, @Id, @OneToMany, @ManyToOne và API như EntityManager, JPQL. Hibernate là implementation phổ biến nhất của JPA, chịu trách nhiệm generate SQL, quản lý Persistence Context, dirty checking, lazy loading, flush và caching.

Trong Hibernate, Persistence Context đóng vai trò như first-level cache và quản lý các trạng thái của entity như transient, managed, detached và removed. Khi entity đang ở managed state, Hibernate tự động track sự thay đổi thông qua dirty checking và đồng bộ xuống database khi flush hoặc transaction commit.

Transaction là một unit of work, các thao tác bên trong phải commit cùng nhau hoặc rollback cùng nhau. Trong Spring, @Transactional được implement bằng AOP proxy. Proxy sẽ mở transaction trước khi method chạy, sau đó commit nếu thành công hoặc rollback nếu có exception. Mặc định Spring rollback với runtime exception, còn checked exception thì cần cấu hình rollbackFor.

ACID gồm Atomicity, Consistency, Isolation và Durability. Isolation level kiểm soát mức độ các transaction song song nhìn thấy dữ liệu của nhau. READ COMMITTED ngăn dirty read, REPEATABLE READ ngăn non-repeatable read, còn SERIALIZABLE là mức cao nhất nhưng performance thấp hơn.

N+1 query là vấn đề performance phổ biến trong ORM, khi một query load danh sách parent, sau đó phát sinh thêm N query để load related entity. Nó thường xảy ra do lazy loading trong vòng lặp hoặc fetch plan không rõ ràng. Có thể xử lý bằng JOIN FETCH, EntityGraph, DTO projection hoặc Hibernate batch fetching. Trong production, với read API, em thường ưu tiên DTO projection và fetch rõ ràng theo từng use case thay vì phụ thuộc vào lazy/eager mặc định.

Về Hibernate fetching, em thường để association là LAZY mặc định và chọn fetch plan theo từng use case. Về cache, em hiểu first-level cache là cache theo transaction/session, còn second-level cache hoặc query cache chỉ nên bật cho read-mostly data sau khi đo query count, cache hit ratio và stale data risk.
