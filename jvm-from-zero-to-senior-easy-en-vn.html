01 • Start here

JVM in one picture

The JVM is a virtual computer inside your real computer. It reads Java bytecode, creates memory for the program, runs instructions, optimizes hot code, manages threads, and cleans unused objects.

JVM là một máy tính ảo nằm trong máy tính thật. Nó đọc Java bytecode, tạo memory cho chương trình, chạy instruction, tối ưu code chạy nhiều, quản lý thread và dọn object không còn dùng.

Java source (.java)
       │ javac
       ▼
Bytecode (.class)
       │
       ▼
┌──────────────────── JVM ────────────────────┐
│ ClassLoader       → loads classes           │
│ Stack / Heap      → stores runtime data     │
│ Interpreter / JIT → executes code           │
│ Garbage Collector → cleans unused objects   │
│ Thread runtime    → manages Java threads    │
└─────────────────────────────────────────────┘
       │
       ▼
Operating System + CPU

First remember only five verbs: load, store, execute, optimize, clean.

Đầu tiên chỉ cần nhớ 5 việc: load, lưu, chạy, tối ưu, dọn.

02 • Basic terms

JDK vs JRE vs JVM

JDK

Tools for creating Java programs.

javac + debugger + tools + runtime

JRE

Conceptual runtime needed to run Java.

runtime libraries + JVM

JVM

The engine that executes bytecode.

load + memory + execute + GC
Easy memory: JDK is for development, JRE is for running, JVM is the execution engine.
03 • Program lifecycle

How Java code becomes a running program

1

Write source code

public class Main {
    public static void main(String[] args) {
        User user = new User("Huy");
    }
}
2

Compile with javac

javac Main.java
→ Main.class

The result is bytecode, not normal CPU machine code.

3

ClassLoader loads the class

The JVM locates Main.class and User.class, verifies them, and creates runtime metadata.

4

Main thread and memory are prepared

The main thread gets a Stack. New objects normally use Heap memory.

5

Interpreter starts executing

It executes bytecode instruction by instruction, allowing fast startup.

6

JIT optimizes hot code

Methods executed many times are compiled into native machine code.

7

GC reclaims unreachable objects

Unused heap objects can be removed automatically.

04 • Loading classes

ClassLoader in simple language

ClassLoader is the JVM's librarian. It finds class bytecode when the program needs it.

ClassLoader là thủ thư của JVM. Khi chương trình cần class nào, nó tìm bytecode của class đó.

Need com.shop.User
       │
Bootstrap ClassLoader → core Java classes
       │ not found
Platform ClassLoader  → platform modules
       │ not found
Application ClassLoader → application classes

Four important phases

Loading

Read class bytes.

Verification

Check bytecode validity.

Preparation

Create static storage with default values.

Initialization

Run static assignments and blocks.

Runtime class identity is class name + defining ClassLoader. The same class loaded by two loaders becomes two different runtime types.

Runtime identity của class là class name + ClassLoader define nó. Cùng bytecode nhưng hai loader khác nhau tạo hai runtime type khác nhau.

06 • Stack

Stack stores the current work of one thread

void methodA() {
    int number = 10;
    methodB(number);
}

void methodB(int input) {
    String text = "Hello";
}
Main Thread Stack

┌─────────────────────────────┐
│ Frame: methodB              │ ← running now
│ input = 10                  │
│ text reference ─────────────┼──► String object in Heap
├─────────────────────────────┤
│ Frame: methodA              │
│ number = 10                 │
├─────────────────────────────┤
│ Frame: main                 │
└─────────────────────────────┘

Local variables

Arguments, primitives, object references.

Operand stack

Temporary values used by bytecode.

Return state

Where execution continues afterward.

Frame lifecycle

call method → push frame
method runs
return/throw → pop frame

Why StackOverflowError happens

void recurse() {
    recurse();
}

Every call adds another frame until the stack has no capacity left.

-Xss controls platform-thread stack size. Increasing it does not fix infinite recursion and reduces how many threads fit in native memory.

-Xss điều khiển stack size của platform thread. Tăng nó không sửa infinite recursion và làm giảm số thread có thể tạo.

07 • Heap

Heap stores objects shared by the application

User user = new User("Huy");
Stack                         Heap
user reference ─────────────► User object
                               │
                               └─ name ─────► String "Huy"

Young and Old

Young generation

New objects. Most die quickly. Collected frequently.

Old generation

Long-lived objects such as caches, sessions, and application state.

Four numbers to understand

Used

Current occupied heap.

Max

Maximum heap, often -Xmx.

Allocation rate

How fast new objects are created.

Live set

Objects still alive after GC.

Leak or temporary allocation?

90% before GC → 35% after GC → stays near 35%
Likely temporary allocations, not automatically a leak.

90% before GC → 35%, later 45%, later 60%, later 75%
Post-GC live set is growing → investigate retention.
08 • One object journey

What happens to new User("Huy")?

1

A stack frame already exists

The method frame has a local slot for the variable user.

2

The JVM requests object memory

Small objects are normally allocated quickly from the thread's TLAB inside a young heap region.

3

The object is initialized

JVM initializes object header and fields, then the constructor assigns the name.

4

A reference is returned

The local variable on Stack stores a reference pointing to the object on Heap.

5

The object may escape

If returned or stored in a field, other code can keep it alive.

6

Eventually it may become unreachable

When no GC Root can reach it, GC may reclaim its memory.

Beginner model: reference on Stack, object on Heap. Advanced model: JIT may remove some allocations through escape analysis and scalar replacement.

Mô hình dễ hiểu: reference trên Stack, object trên Heap. Mô hình nâng cao: JIT có thể loại bỏ allocation bằng escape analysis và scalar replacement.

09 • Garbage Collection

GC removes unreachable objects

An object is not collected because it is old. It is collectible when no path from a GC Root reaches it.

Object không bị collect vì nó cũ. Nó có thể được collect khi không còn đường đi từ GC Root tới nó.

GC Roots

  • References from live thread stacks.
  • Static fields of loaded classes.
  • JNI references.
  • JVM internal references.
GC Root ─► A ─► B ─► C     → alive

D ─► E                    → no root path
                            → eligible for GC

Mark

Find reachable objects.

Sweep

Reclaim dead memory.

Copy

Move live objects.

Compact

Reduce fragmentation.

Stop-the-world

Some GC phases pause application threads. Modern collectors try to do more work concurrently so pauses are shorter.

12 • Threads

Java Memory Model is not Heap/Stack

Heap and Stack describe where data is stored. The Java Memory Model describes what one thread can see from another thread.

Heap và Stack nói dữ liệu nằm ở đâu. Java Memory Model nói thread này nhìn thấy thay đổi của thread khác như thế nào.

Atomicity

Operation is indivisible.

Visibility

One thread sees another's write.

Ordering

Operations follow guaranteed observation rules.

volatile boolean running = true;

A volatile write is visible to a later volatile read. However, count++ is not atomic because it is read + add + write.

AtomicInteger count = new AtomicInteger();
count.incrementAndGet();

14 • Production

How to investigate memory problems

Ask one question first

Post-GC Heap grows?
→ heap retention / leak

RSS grows but Heap is stable?
→ native memory, direct buffers, threads, JNI

GC frequent but post-GC Heap stable?
→ allocation churn or undersized Heap

Pauses are long?
→ live set, collector phases, CPU throttling, safepoints

Useful commands

jcmd -l
jcmd <pid> VM.flags
jcmd <pid> GC.heap_info
jcmd <pid> GC.class_histogram
jcmd <pid> Thread.print -l
jcmd <pid> GC.heap_dump /tmp/app.hprof

GC log

-Xlog:gc*,safepoint:file=gc.log:time,uptime,level,tags:filecount=10,filesize=20M

Heap dump flow

  1. Open heap dump.
  2. Check class histogram.
  3. Check dominator tree and retained size.
  4. Follow Path to GC Roots.
  5. Find the owner: cache, queue, static map, ThreadLocal, listener, or ClassLoader.
15 • Interview

Senior JVM questions with clear answers

1. What is JVM?

JVM is the execution environment that loads bytecode, manages runtime memory, executes code through Interpreter/JIT, manages threads, and performs Garbage Collection.

2. Stack vs Heap?

Each thread owns a private Stack containing frames and local values/references. Heap is shared and normally stores objects and arrays. Frames disappear when methods return; Heap objects remain until unreachable and reclaimed.

3. What makes an object eligible for GC?

No live path exists from a GC Root to the object. Setting one reference to null does not guarantee that all other references are gone.

4. Why can process memory exceed Xmx?

Xmx limits only Java Heap. Metaspace, code cache, direct buffers, thread stacks, GC structures, JNI, and native libraries use additional memory.

5. What is JIT?

JIT compiles frequently executed bytecode into optimized native machine code using runtime profiling information.

6. What is a Java memory leak?

An object is no longer useful but remains reachable, often through static collections, unbounded caches, queues, ThreadLocals, listeners, or ClassLoaders.

7. Leak vs high allocation?

A leak causes post-GC occupancy to rise over time. High temporary allocation causes peaks and frequent GC but returns to a stable post-GC baseline.

8. G1 vs ZGC?

G1 is a balanced regional collector for general services. ZGC performs most work concurrently for very low pauses, with CPU and memory-headroom trade-offs.

9. What is parent delegation?

A ClassLoader asks its parent to load a class first. This protects core classes and reduces duplicate normal definitions.

10. What is Java Memory Model?

It defines cross-thread visibility, ordering, atomicity, synchronization, and happens-before rules. It is different from physical Stack/Heap areas.

11. How do you investigate Kubernetes OOM?

First distinguish Java OOME from OOMKilled/exit 137. Check pod events, cgroup limit, RSS vs Heap, GC logs, direct memory, thread count, NMT, JFR, and heap dump when safe.

12. Does every object physically live on Heap?

That is the useful logical model, but JIT escape analysis may eliminate an allocation or scalar-replace object fields.

16 • Remember this

JVM in 10 sentences

  1. Java source becomes bytecode.
  2. ClassLoader loads classes.
  3. Each thread has a Stack.
  4. Each method call creates a frame.
  5. Objects normally live in Heap.
  6. GC reclaims unreachable objects.
  7. Interpreter starts execution quickly.
  8. JIT optimizes hot code.
  9. Process memory is larger than Heap alone.
