Java Stack, Heap, Static, String Pool & Garbage Collection

Focus: what the Stack stores, exactly what lives in the Heap, how static fields keep heap objects alive, how the String Pool works, and the original interview scenarios about StackOverflow, Heap OOM and GC.

Core rule: Java objects and arrays are heap objects. A primitive can also be physically inside the Heap when it is an object field or an array element.

1. What exactly does the Stack store?

Each Java thread has its own Stack (vùng nhớ Stack riêng của từng thread). Every method call creates a stack frame (khung ngăn xếp).

DataWhere?Explanation
Local primitive: int x = 10, boolean ok = trueStack frameThe local primitive value belongs to the current method frame.
Local object reference: User uStack frameThe reference is local to the method. The User object it points to is on Heap.
Method argumentsStack frameArguments are part of the called method's frame.
Operand stack / call bookkeepingStack frameUsed by JVM execution for intermediate values and method calls.
 
void process() {
    int count = 10;
    User user = new User();
}

Thread Stack                         Heap
------------                         -------------------
process() frame
|- count = 10
`- user ---------------------------> User object
Key distinction: the local reference user is in the Stack frame, but new User() creates the object on Heap. When the method returns, its frame is removed; the heap object is collected only if it is no longer reachable.

StackOverflowError: happens when a thread keeps creating stack frames until its stack has no room left, commonly because of infinite or very deep recursion. Stack size is typically controlled with -Xss.

2. What exactly does the Heap store?

The Heap (vùng nhớ Heap) is the shared JVM memory area used mainly for Java objects and arrays. GC manages the lifetime of those heap objects.

DataIs it on Heap?Explanation
new User()YesThe whole User object is a heap object.
Primitive instance field: user.age, user.activeYesThe primitive value is stored inside the User object's memory.
Reference field: user.addressYesThe reference is part of the User object; the Address object it points to is also on Heap.
String objectYesString is an object. Its backing byte[] on modern JDKs is also a heap object.
Boolean, Integer, LongYesWrapper types are objects.
int[], boolean[], User[]YesEvery Java array is an object, including primitive arrays.
ArrayList, HashMapYesThe collection object and its backing arrays/nodes/entries are heap objects.
Class<?> mirror objectYesLoaded classes have Java Class mirror objects on Heap. Class metadata itself is mainly in Metaspace.
 
class User {
    int age;
    boolean active;
    String name;
    Address address;
}

User u = new User();
Stack                               Heap
-----                               ---------------------------------
u --------------------------------> User object
                                    |- age = 30          (primitive)
                                    |- active = true     (primitive)
                                    |- name ------------> String "Huy"
                                    `- address ---------> Address object
Important: Do not memorize primitive = Stack. A local primitive belongs to a method frame, but a primitive field or primitive array element is part of a heap object.

3. String and the String Pool

A String is always an object. The actual String object is therefore on the Heap.

String a = "hello";
String b = "hello";
String c = new String("hello");
Stack                                  Heap
-----                                  --------------------------------
a ----\
       +-----------------------------> pooled String "hello"
b ----/

c -----------------------------------> separate String object "hello"
                                       created by new String(...)

What is the String Pool?

The String Pool (bộ nhớ dùng chung cho chuỗi intern) keeps a canonical reference for interned strings so equal literals can reuse the same String object instead of creating a new object for every literal occurrence.

CodeWhat happens?
String a = "abc";Uses the interned "abc" String object.
String b = "abc";Normally points to the same pooled String as a.
new String("abc")Creates a separate String object on Heap, in addition to the pooled literal that may already exist.
s.intern()Returns the canonical pooled String reference for that content.
 
String a = "abc";
String b = "abc";
String c = new String("abc");

System.out.println(a == b); // true
System.out.println(a == c); // false
System.out.println(a == c.intern()); // true
Modern HotSpot: interned String objects live on the Java Heap. Do not use the old statement “String Pool is in PermGen” for modern Java. The JVM's internal StringTable implementation is a JVM detail, but the String objects themselves are heap objects.

4. boolean vs Boolean — where are they stored?

void test() {
    boolean active = true;
    Boolean enabled = Boolean.TRUE;
}
Stack                               Heap
-----                               -------------------------
active = true
enabled --------------------------> Boolean.TRUE object

boolean is a primitive. A local primitive conceptually belongs to the method's stack frame. Boolean is a Java object type, so the Boolean object is on Heap.

class User {
    boolean active;
}

new User()  --->  Heap object
                  |- active = true

Here active is also physically part of the Heap because it is an instance field inside the heap object.

5. Static and the Heap

class Cache {
    static int count = 10;
    static String VERSION = "1.0";
    static User admin = new User();
    static Map<String, User> users = new HashMap<>();
}

The JVM specification does not require one exact physical memory layout for static fields. For modern HotSpot, a useful implementation-level model is:

Metaspace                         Heap
---------                         ----------------------------------
Cache class metadata              Class<Cache> mirror
                                  |- static count = 10
                                  |- VERSION ----------------------> String "1.0"
                                  |- admin ------------------------> User object
                                  `- users ------------------------> HashMap
                                                                       |
                                                                       +--> User
                                                                       +--> User
Correct interview wording: Do not simply say “static variables are stored in Metaspace.” Class metadata is mainly in Metaspace. Objects referenced by static fields are heap objects, and in HotSpot the static field storage is associated with the class's java.lang.Class mirror on Heap.

Does creating many static variables increase Heap usage?

Yes, but the impact depends on what the static fields hold.

  • static int, static boolean, static long: usually a very small amount of memory.
  • static String, static User, static List, static Map: the referenced objects live on Heap and can consume a lot of memory.
  • The dangerous case is an unbounded static collection/cache that keeps adding objects and never removes them.
static int count = 10;                 // tiny
static boolean enabled = true;         // tiny
static User admin = new User();        // User object on Heap
static List<User> users = new ArrayList<>();
// ArrayList + its backing array + referenced User objects are on Heap

Key idea: many static primitives usually do not cause a serious Heap problem. Static references to large or growing object graphs can.

6. Can GC remove a static variable or object?

This question must distinguish the static field from the object referenced by that field.

static User admin = new User();
GC Root
   |
   v
loaded Class / class state
   |
   v
static admin
   |
   v
User object

As long as the static reference still points to the User object and the class remains reachable/loaded, GC normally cannot collect that User object because it is still reachable (còn đường tham chiếu tới).

admin = null;

If no other strong reference points to that User object, it becomes eligible for GC. GC does not necessarily remove it immediately; it can reclaim it on a later collection.

Static primitive: static int count is not a separate Java object for GC to collect. It remains part of the class state while the class is loaded.

8. Keep these interview scenarios

Q1. When does StackOverflowError happen?

It happens when one thread needs another stack frame but its thread stack has no room left. The most common cause is infinite recursion or very deep recursion.

void call() {
    call();
}
Thread Stack
call()
call()
call()
call()
...
No room for the next frame
-> StackOverflowError

Interview answer: “StackOverflowError is mainly a per-thread stack problem, not a heap problem. I would first inspect recursion depth, recursive cycles and unusually large call chains.”

Q2. When does OutOfMemoryError: Java heap space happen?

The JVM needs to allocate another heap object, there is not enough free Heap, GC cannot reclaim enough unreachable objects, and the Heap cannot grow further within its configured maximum such as -Xmx.

Need new object
     |
     v
Not enough Heap
     |
     v
GC tries to reclaim objects
     |
     v
Still not enough free memory
     |
     v
Heap cannot grow beyond -Xmx
     |
     v
OutOfMemoryError: Java heap space
Q3. Does Heap OOM always mean there is a memory leak?

No. A memory leak is only one cause. Heap OOM can also occur because the configured Heap is too small, the application processes a very large payload, too many requests are alive at the same time, a queue grows during a slow downstream call, or a large cache legitimately holds more data than the Heap can fit.

Useful signal: inspect memory after GC. If post-GC usage keeps increasing over time, object retention is suspicious. If memory drops after traffic decreases, it may be temporary load pressure rather than a permanent leak.

Q4. What are common real-world causes of Java heap space?

Typical scenarios include:

  • Unbounded static cache or collection.
  • Unbounded message/task queue.
  • Reading a huge file or response fully into memory.
  • Very large byte[], String, JSON object graph or collection.
  • High concurrency: many requests keep objects alive at the same time.
  • A downstream service becomes slow, so in-flight request objects accumulate.
  • Object retention bug: listeners, maps, sessions or references are never cleared.
  • -Xmx is smaller than the application's legitimate live set.
Q5. Does creating many static variables make the Heap grow?

It can, but not all static fields have the same impact. Many static primitives such as int or boolean usually use little memory. The real Heap growth comes from static references that keep large objects, collections, caches, arrays, or object graphs alive.

static int count = 10;                  // small
static User user = new User();          // User object on Heap
static List<User> users = new ArrayList<>();
// users may retain thousands or millions of User objects

Interview answer: “Static itself is not automatically a memory problem. The risk is that a long-lived static reference can retain a large heap object graph for the lifetime of the loaded class.”

Q6. Can a static variable be deleted by GC?

Do not describe it as “GC deletes the static variable.” A static field is part of class state. If it holds a reference to a heap object, that object normally stays alive while the static reference keeps it reachable.

static User user = new User();

class -> static user -> User object   // reachable, not collectible

user = null;

User object                           // collectible if no other reference exists

Class unloading is a separate case: if a class loader and its classes become unreachable and the JVM unloads them, objects that were reachable only through that class state can also become eligible for GC.

Q7. If a method returns, are the objects created inside it immediately removed?

No. The method's stack frame disappears, but heap objects survive if another reachable object still references them.

User create() {
    User u = new User();
    return u;
}

The local reference u disappears when the method returns, but the caller now holds the returned reference, so the User object remains alive.

Q8. Can a circular reference cause a Java Heap memory leak?

Not by itself. Java GC uses reachability, not simple reference counting.

A -> B
^    |
|____|

No GC Root can reach A or B
-> both can still be collected.

A cycle becomes a problem only when something reachable, such as a static cache, still points into that cycle.

Q9. Can the String Pool contribute to Heap pressure?

Yes, especially if an application calls intern() on a very large number of distinct dynamic strings or otherwise retains many unique strings. The String objects live on Heap, so a large live set of strings consumes Heap like other objects.

Modern HotSpot can clean up unreachable interned strings; they are not automatically immortal forever. The real danger is keeping large numbers of unique strings strongly reachable.

9. Common StackOverflowError & OutOfMemoryError scenarios

This section focuses on the failure patterns that are most useful in production debugging and interviews.

StackOverflowError scenarios

ScenarioWhy it happensTypical fix
Infinite recursion
method() -> method()		Every call creates another stack frame until the thread stack is full.Fix the termination condition or remove the recursion.
Valid but very deep recursionThe algorithm has a base case, but the input depth is larger than the available stack can support.Use iteration, an explicit heap-based stack/queue, or reduce recursion depth.
Mutual recursion
a() -> b() -> a()		The recursive cycle is indirect, so it is harder to notice in code review.Break the cycle and define a clear termination path.
Recursive toString(), equals() or hashCode()Bidirectional object relationships can call each other forever, common with JPA entities or Lombok-generated methods.Exclude back-references or implement these methods using stable identifiers instead of the full object graph.
Circular JSON serializationParent -> Child -> Parent can be serialized recursively when cycle handling is missing.Break the serialized cycle with DTOs or serializer cycle-handling annotations/configuration.
Thread stack configured too smallA very small -Xss allows fewer stack frames before overflow.First fix excessive recursion/call depth. Increase -Xss only when the deeper stack is legitimate.

Important: forgetting to close a file is usually not Java heap space

for (...) {
    FileInputStream in = new FileInputStream(file);
    // forgot to close in
}

This usually causes a resource leak (rò rỉ tài nguyên), especially a file-descriptor leak. The operating system may eventually reject new files with an error such as Too many open files. It is not normally the direct cause of OutOfMemoryError: Java heap space.

try (FileInputStream in = new FileInputStream(file)) {
    // read safely
} // automatically closed
Interview distinction: Not closing a file usually leaks an OS/native resource. Reading a huge file completely into a byte[] or String can cause Heap OOM. These are two different problems.

Other important OutOfMemoryError types

ErrorTypical cause
OutOfMemoryError: MetaspaceToo many loaded/generated classes or a ClassLoader leak. This is not Java Heap exhaustion.
OutOfMemoryError: Direct buffer memoryToo much off-heap/direct memory, commonly from ByteBuffer.allocateDirect(), networking or native buffers.
OutOfMemoryError: unable to create native threadToo many threads or insufficient native memory / OS thread resources.
GC overhead limit exceededThe JVM spends most of its time collecting but recovers very little Heap, often because the Heap is almost completely occupied by live objects.
Interview scenario: “The service runs normally for hours, then Heap keeps growing until OOM. What do you check?”

First determine whether this is retention or just a temporary load spike. Check post-GC Heap usage over time. If the baseline after GC keeps rising, capture a heap dump and inspect the largest retained objects and their path to GC roots. Common suspects are static caches, unbounded queues, sessions, listeners and ThreadLocals.

Interview scenario: “Traffic spikes and the service OOMs, but memory goes back to normal when traffic drops. Is that a leak?”

Not necessarily. It may be a high live set: too many legitimate request objects are alive at the same time. I would check concurrency, request size, in-flight request count, downstream latency, queue depth and whether the configured -Xmx is appropriate.

GC follows reachability from GC Roots and reclaims unreachable heap objects.
Remember these four lines:
1. Objects and arrays live on Heap.
2. String Pool contains/reuses String objects that live on Heap in modern HotSpot.
3. Static references can keep heap objects reachable for a very long time.
4. GC removes unreachable heap objects; it does not remove an object just because it is old or created inside a finished method.
