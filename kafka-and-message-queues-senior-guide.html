Apache Kafka and Message Queues

A detailed guide for Java and Spring Boot engineers. It explains what Kafka and queues are, how messages move through the system, which settings matter in production, how failures are handled, and how a senior engineer should answer interview questions.

1. Start with the Correct Mental Model

The most important difference is not API syntax. It is the way the system stores, distributes, and owns messages.

Traditional Message Queue

A queue is mainly a work distribution system. A message is sent to a queue, one worker processes it, and the message is normally removed after successful acknowledgement.

Producer → Queue → One Consumer └→ ACK → Message removed

Main question: “Which worker should execute this job?”

Kafka

Kafka is mainly a distributed, retained, append-only log. Records stay for a configured retention period. Consumers track their own positions and can replay old records.

Producer → Topic Partition Log ├→ Group A reads offsets ├→ Group B reads offsets └→ Replay later

Main question: “Which applications need to observe this stream of facts?”

Simple rule: A queue distributes tasks. Kafka distributes a history of events. Kafka can be used for work distribution through consumer groups, but its storage and replay model remain different.

Command, event, and job are not the same

TypeMeaningExampleCommon transport
CommandA request for one receiver to perform an action.ChargePaymentQueue, Kafka command topic, HTTP
EventA fact that already happened. Multiple systems may react.PaymentCompletedKafka topic, exchange with fan-out
JobA unit of background work that should normally be processed once by one worker.GenerateMonthlyInvoiceRabbitMQ, SQS, task queue

2. Core Terms You Must Understand

Broker

A server that accepts, stores, and serves messages. A Kafka cluster normally has several brokers.

Topic

A named stream of records, such as order-events. A Kafka topic is divided into partitions.

Partition

An ordered append-only log. It is Kafka’s unit of parallelism, storage, and replication.

Offset

A record’s position inside one partition. Offset 150 in partition 0 is unrelated to offset 150 in partition 1.

Producer

An application that writes records to Kafka or sends messages to a queue.

Consumer

An application that reads records and performs business processing.

Consumer Group

A logical application instance group. Within one Kafka group, each partition is assigned to at most one active consumer.

Leader Replica

The replica that handles reads and writes for a partition.

Follower Replica

A copy that fetches records from the partition leader and can become leader after failure.

ISR

In-Sync Replicas: replicas sufficiently caught up with the leader.

Acknowledgement

A signal that data was received or processed. Producer acknowledgements and consumer acknowledgements solve different problems.

Backpressure

A mechanism that prevents fast producers from overwhelming slower consumers or downstream systems.

4. How a Kafka Producer Writes a Record

A successful send() is not a single network call. Several steps happen inside the client and cluster.

1
Serialize. The producer converts the key and value into bytes. Serialization format is a long-term contract, not a small implementation detail.
2
Select a partition. An explicit partition wins. Otherwise the producer normally hashes the key, or uses a keyless partitioning strategy.
3
Append to a client-side batch. Records for the same partition are grouped. batch.size and linger.ms influence batch efficiency.
4
Compress. Compression is most effective on batches. Common choices include gzip, snappy, lz4, and zstd.
5
Send to the partition leader. The client obtains cluster metadata and contacts the broker leading that partition.
6
Leader appends the record. The record is written to the leader log. Followers fetch and replicate it.
7
Wait according to acks. With acks=all, the leader waits for required in-sync replicas.
8
Complete or retry. Retriable failures may be sent again. Idempotent producing prevents retry-created duplicates within its supported scope.

Why keys matter

ProducerRecord<String, OrderEvent> record =
    new ProducerRecord<>("order-events", orderId, event);

kafkaTemplate.send(record);

Using orderId as the key normally keeps all events for one order in the same partition, which preserves order for that order.

Kafka does not provide one global order across all partitions. Ordering exists inside a single partition only.

5. How a Kafka Consumer Reads and Processes Records

1
The consumer joins a group and receives partition assignments.
2
It polls brokers for records beginning from its current position.
3
It deserializes records and calls application logic.
4
The application updates a database, calls another service, or produces new records.
5
The consumer commits offsets, indicating the next position it should resume from.

Position versus committed offset

  • Current position: where the active consumer is reading now.
  • Committed offset: the restart checkpoint stored for the consumer group.

The critical ordering decision

Commit before processing

If the process crashes after committing but before completing business logic, the record may be lost from the application’s perspective.

Result: closer to at-most-once.

Process before committing

If processing succeeds but the process crashes before committing, Kafka delivers the record again.

Result: at-least-once, requiring idempotency.

In most business systems, prefer process first, commit later, and make processing idempotent. Duplicates are usually safer than silent data loss.

6. Partitioning, Keys, Ordering, and Hot Partitions

What a partition controls

  • Maximum useful consumer parallelism for one consumer group.
  • Ordering boundary.
  • Replication and leader election unit.
  • Storage files, segment management, and recovery work.

Key selection examples

Use caseGood keyReason
Order lifecycleorderIdAll status changes for one order remain ordered.
Bank account ledgeraccountIdTransactions for one account are processed sequentially.
User profile updatesuserIdProfile versions stay ordered per user.
TelemetrydeviceIdMeasurements remain ordered per device.

Hot partition problem

A hot key sends disproportionate traffic to one partition. For example, using countryCode as the key may put most traffic into the partition for a large country.

Possible responses:

  • Choose a higher-cardinality key.
  • Add a controlled shard suffix such as merchantId + bucket, but accept weaker ordering.
  • Separate extreme tenants into dedicated topics.
  • Apply quotas or upstream rate limits.
  • Measure per-partition throughput instead of only topic totals.

How many partitions?

Do not choose a magic number. Benchmark with your payload, compression, acknowledgement level, hardware, and processing logic.

required partitions ≈ max(
    target produce throughput / tested produce throughput per partition,
    target consume throughput / tested consume throughput per consumer-partition
)
Increasing partitions later can change key-to-partition mapping. That may break ordering expectations for existing keys. Plan growth and key behavior before production.

7. Consumer Groups and Rebalancing

Topic: order-events (4 partitions) Consumer Group: payment-service Consumer A → P0, P1 Consumer B → P2, P3 Consumer Group: analytics-service Consumer X → P0, P1, P2, P3 Each group receives the full topic independently. Inside one group, partitions are divided among consumers.

Rules you must remember

  • If a group has 4 partitions and 2 consumers, each consumer usually receives 2 partitions.
  • If a group has 4 partitions and 6 consumers, at least 2 consumers are idle.
  • Adding consumers beyond partition count does not increase record-processing parallelism.
  • Different consumer groups independently read the same records.

What triggers a rebalance?

  • A consumer joins or leaves.
  • A consumer is considered dead because heartbeats stop.
  • A consumer takes too long between polls and exceeds max.poll.interval.ms.
  • Subscribed topic partitions change.
  • Group metadata or assignment protocol changes.

Why rebalances hurt

Partitions may temporarily stop processing. In-flight records can be repeated. Caches and local state may need to move. Frequent rebalances create latency spikes and reduce throughput.

Ways to reduce disruption

  • Keep processing time below max.poll.interval.ms.
  • Reduce max.poll.records when each record is expensive.
  • Move long processing to a controlled executor only when offset and ordering behavior are carefully designed.
  • Use cooperative assignment where appropriate to reduce full stop-the-world movement.
  • Use static membership for stable instances, while still handling actual failures.
  • Avoid unstable deployments that repeatedly start and stop pods.

8. Replication, ISR, Acknowledgements, and Durability

Partition 0 Broker 1: Leader [0 ... 105] Broker 2: Follower [0 ... 105] ← ISR Broker 3: Follower [0 ... 104] ← ISR Producer with acks=all waits for the in-sync replica requirements.

Three settings must be understood together

SettingMeaningTrade-off
replication.factorNumber of copies of each partition.More durability and availability, but more disk and replication traffic.
acksHow many acknowledgements the producer waits for.Lower values reduce latency but increase loss risk.
min.insync.replicasMinimum ISR requirement for successful acks=all writes.Higher durability may reject writes during replica failures.

Common production durability combination

replication.factor = 3
min.insync.replicas = 2
producer acks = all
enable.idempotence = true

With three replicas, the system can normally lose one replica and still accept writes. If too few in-sync replicas remain, writes fail rather than accepting data with a weak durability level.

Availability versus durability

A senior engineer does not say “replication factor 3 means no data loss.” Durability also depends on:

  • Which acknowledgements the producer waits for.
  • Whether replicas are in sync.
  • Whether unclean leader election is allowed.
  • Disk and filesystem behavior.
  • Client retry and timeout configuration.
  • Whether the application correctly handles send failures.
  • Rack and availability-zone placement.

9. At-Most-Once, At-Least-Once, and Exactly-Once

SemanticPossible resultTypical methodSuitable for
At-most-onceNo duplicate, but data may be lost.Commit before processing.Low-value telemetry where loss is acceptable.
At-least-onceNo silent loss under expected failures, but duplicates may occur.Process, then commit; retry failures.Most business systems with idempotent processing.
Exactly-onceOne visible result inside a defined boundary.Kafka idempotent producer and transactions for Kafka read-process-write.Kafka-to-Kafka pipelines and carefully designed stateful processing.

Exactly-once is always scoped

Kafka transactions do not automatically make a PostgreSQL update and a Kafka publish one atomic transaction. If your consumer updates an external database, you still need database idempotency, an inbox table, an outbox pattern, or another explicit consistency design.

Producer idempotence

The producer uses a producer ID and sequence numbers so broker-side retries do not create duplicate log entries in the supported producer session and partition scope.

Kafka transaction example

Consume input record ↓ Transform ↓ Produce output records + commit consumed offsets ↓ All committed or all aborted as one Kafka transaction

Consumers that use isolation.level=read_committed do not expose aborted transactional records.

10. Retention, Segments, and Log Compaction

Kafka does not normally delete a record just because a consumer read it. Deletion is controlled by topic retention policy.

Delete retention

With cleanup.policy=delete, old log segments are removed according to time or size limits.

cleanup.policy=delete
retention.ms=604800000     # 7 days
retention.bytes=-1         # no size limit

Log compaction

With cleanup.policy=compact, Kafka eventually keeps the latest value for each key, plus records needed while compaction is in progress.

Key A → v1 Key B → v1 Key A → v2 Key A → v3 After compaction, the latest state is approximately: Key B → v1 Key A → v3

Tombstone

A record with a key and a null value is a tombstone. It represents deletion of that key in a compacted topic after the configured delete retention period.

Use cases

  • Delete policy: event history, audit stream, telemetry, activity logs.
  • Compact policy: latest customer state, configuration state, changelog, cache rebuild source.
  • Delete + compact: retain latest key state while also limiting old data.
Compaction is asynchronous. Do not assume old versions disappear immediately, and do not use it as a privacy erasure mechanism without a wider data-governance design.

11. Traditional Queue Model: RabbitMQ and Amazon SQS

RabbitMQ routing model

Producer ↓ publish with routing key Exchange ├─ binding → Queue A → Consumers ├─ binding → Queue B → Consumers └─ binding → Queue C → Consumers
RabbitMQ componentPurpose
ExchangeReceives published messages and routes them using bindings.
Direct exchangeRoutes by exact routing-key match.
Topic exchangeRoutes by wildcard patterns such as order.*.
Fanout exchangeCopies a message to all bound queues.
Headers exchangeRoutes by message headers.
QueueStores messages until consumers receive and acknowledge them.
Consumer acknowledgementConfirms successful processing so RabbitMQ can remove the delivery.
Publisher confirmConfirms broker acceptance of a published message. It is different from consumer acknowledgement.
PrefetchLimits unacknowledged deliveries per consumer to protect workers and improve fairness.
Dead-letter exchangeReceives messages rejected, expired, or otherwise dead-lettered according to policy.

Amazon SQS model

Producer → SQS Queue → Consumer polls ↓ message becomes invisible process successfully? ├─ yes → DeleteMessage └─ no → visibility timeout expires → redelivery

Visibility timeout

After a consumer receives a message, SQS temporarily hides it. The consumer must delete it after successful processing. If it does not delete it before the visibility timeout expires, the message becomes visible again.

Standard versus FIFO

FeatureSQS StandardSQS FIFO
DeliveryAt least once; duplicates are possible.Deduplication support with FIFO processing within a message group.
OrderingBest effort.Strict ordering within a message group.
ParallelismVery high.Parallel across message groups; sequential inside one group.

12. Kafka versus Traditional Message Queue

DimensionKafkaRabbitMQ / SQS-style queue
Primary modelRetained distributed log / event stream.Work queue and message routing.
After consumptionRecord remains until retention removes it.Message is normally removed after acknowledgement or deletion.
ReplayNative: reset or seek offsets.Not the main model; usually requires republishing or a separate archive.
Multiple applicationsEach consumer group reads the full stream independently.Use separate queues or subscriptions for fan-out.
OrderingPer partition.Queue-dependent; FIFO may be affected by concurrency, redelivery, and priorities.
RoutingTopic and partition model; less flexible broker-side routing.Rich exchange, binding, filter, and queue routing options.
Delayed messageUsually implemented with retry topics, scheduling systems, or application logic.Often easier through TTL, delay queues, visibility settings, or broker features.
Consumer speedHigh-throughput sequential fetch and batching.Excellent for task dispatch; throughput varies by product and durability mode.
BacklogDesigned for large retained backlogs and replay.Large backlog may be supported, but queue health and latency must be considered carefully.
Typical useEvent-driven architecture, CDC, data pipelines, analytics, integration, event sourcing support.Background jobs, commands, request buffering, email sending, workflow tasks.
Operational complexityPartition planning, brokers, replication, storage, schemas, offsets, rebalances.Queue topology, acknowledgements, prefetch, DLQ, visibility timeout, routing, worker concurrency.

A common interview trap

“Kafka is faster than RabbitMQ.” This is an incomplete answer. Performance depends on durability, payload, batching, routing, storage, consumer behavior, and workload. The better answer is that Kafka’s append-only partitioned storage and batching are optimized for high-throughput streaming, while queue systems often optimize flexible routing and task dispatch.

13. How to Choose

Choose Kafka when...

  • Many applications need the same event history.
  • Replay is a business or operational requirement.
  • You need high-throughput pipelines and retained backlogs.
  • You need CDC, stream processing, analytics, or event-driven integration.
  • Per-key ordering is enough.
  • You can operate topics, partitions, schemas, and consumer lag.

Choose a queue when...

  • One job should be executed by one available worker.
  • You need rich routing, per-message TTL, priority, or delay behavior.
  • Messages are commands rather than a reusable event history.
  • Workers have varying speed and require explicit prefetch or visibility control.
  • You do not need replay by many independent consumer applications.

Use both when each solves a different problem

Business events → Kafka OrderCreated, PaymentCompleted, CustomerUpdated Task execution → Queue GeneratePDF, SendEmail, ResizeImage, CallSlowPartnerAPI

A mature architecture does not force every asynchronous use case into one product.

14. Production Setup: What Must Be Decided

Running Kafka is not only starting three containers. Production setup starts with workload and failure requirements.

14.1 Workload questions

  • Peak records per second and peak MB per second?
  • Average and maximum message size?
  • How bursty is traffic?
  • How long must records be retained?
  • How many consumer groups read each topic?
  • What is the acceptable end-to-end latency?
  • What data loss is acceptable?
  • How fast must recovery occur after a broker or zone failure?
  • Are events regulated, confidential, or personally identifiable?

14.2 Cluster topology

  • Use multiple brokers across failure domains.
  • Use an odd KRaft controller quorum, commonly three controllers.
  • For larger clusters, consider dedicated controller nodes rather than combined broker-controller roles.
  • Configure rack awareness so replicas do not all live in one availability zone.
  • Separate production from development and test traffic.

14.3 Storage and operating system

  • Kafka relies heavily on sequential disk I/O and the operating-system page cache.
  • Use reliable disks with enough sustained throughput, not only enough capacity.
  • Leave memory for page cache; do not assign all RAM to the JVM heap.
  • Monitor disk utilization, disk latency, inode/file descriptor usage, and log-directory failures.
  • Keep network capacity for both client traffic and replica traffic.

14.4 Topic governance

DecisionQuestions
OwnershipWhich team owns schema, retention, access, incidents, and deprecation?
NamingUse a stable convention such as domain.entity.event.v1 or organization standards.
Partition countWhat throughput and consumer parallelism are required now and later?
ReplicationWhat broker or zone failures must the topic survive?
RetentionHow far back must consumers replay? What is the storage cost?
KeyWhich entity needs ordering? Is the key distribution balanced?
SchemaWhat compatibility rules and registry are used?
SecurityWhich producers and groups may read or write?
DLT/retryWho handles failures, and how are messages replayed safely?

14.5 Capacity model

daily raw bytes =
  records_per_second × average_record_bytes × 86,400

retained bytes ≈
  daily raw bytes × retention_days × replication_factor × compression_ratio
  + index/segment overhead
  + safety margin

Compression ratio should be measured. Replication multiplies cluster storage. Reprocessing, maintenance, and uneven partition distribution require spare capacity.

14.6 Security baseline

  • TLS for client-broker and inter-broker traffic.
  • SASL or mutual TLS authentication.
  • Least-privilege ACLs for topics, groups, transactional IDs, and cluster operations.
  • Secrets stored outside source code.
  • Audit and access review.
  • Private networking and controlled advertised listeners.

14.7 Upgrade and disaster recovery

  • Document compatible broker and client versions.
  • Use rolling upgrades and verify health after each stage.
  • Test restore and regional failover; do not assume replication inside one cluster is a backup.
  • Keep infrastructure configuration in version control.
  • Practice broker loss, disk loss, controller loss, and consumer replay.

16.2 Publish with a stable key

public record OrderCreatedEvent(
        UUID eventId,
        UUID orderId,
        BigDecimal amount,
        Instant occurredAt,
        int schemaVersion) {
}

@Service
public class OrderEventPublisher {

    private final KafkaTemplate<String, OrderCreatedEvent> kafkaTemplate;

    public OrderEventPublisher(
            KafkaTemplate<String, OrderCreatedEvent> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    public CompletableFuture<SendResult<String, OrderCreatedEvent>> publish(
            OrderCreatedEvent event) {

        ProducerRecord<String, OrderCreatedEvent> record =
                new ProducerRecord<>(
                        "commerce.order.created.v1",
                        event.orderId().toString(),
                        event);

        record.headers().add(
                "event-id",
                event.eventId().toString().getBytes(StandardCharsets.UTF_8));

        return kafkaTemplate.send(record);
    }
}

16.3 Consumer with controlled acknowledgement

spring:
  kafka:
    consumer:
      group-id: payment-service-v1
      enable-auto-commit: false
      auto-offset-reset: earliest
      properties:
        max.poll.interval.ms: 300000
      max-poll-records: 100
    listener:
      ack-mode: record
@Component
public class OrderCreatedListener {

    private final PaymentApplicationService paymentService;

    public OrderCreatedListener(PaymentApplicationService paymentService) {
        this.paymentService = paymentService;
    }

    @KafkaListener(
            topics = "commerce.order.created.v1",
            groupId = "payment-service-v1")
    public void onOrderCreated(OrderCreatedEvent event) {
        // Throwing an exception prevents successful acknowledgement
        // under the configured container error-handling strategy.
        paymentService.createPayment(event);
    }
}

16.4 Do not block the consumer indefinitely

A slow partner API can make the listener exceed max.poll.interval.ms. Better choices include:

  • Use short client timeouts and controlled retries.
  • Move slow work to a dedicated queue designed for worker jobs.
  • Pause consumption under downstream overload.
  • Use bounded concurrency with clear ordering and offset rules.
  • Use retry topics rather than sleeping inside the listener thread.

17. Retry, Dead-Letter Topic, and Idempotent Consumer

Classify failures first

FailureExampleResponse
TransientDatabase connection timeout, HTTP 503.Retry with backoff and limits.
Permanent business failureAccount is closed, order already cancelled.Record business outcome; do not retry forever.
Poison messageInvalid schema, impossible field value.Send to DLT/quarantine with diagnostic metadata.
Code defectNull pointer for a valid event.Alert, stop or quarantine, fix code, then replay safely.

Retry topic flow

main topic ↓ failure retry-1 (30 seconds) ↓ failure retry-2 (5 minutes) ↓ failure dead-letter topic ↓ operator investigation / repair / controlled replay

Why immediate retries are dangerous

If a database is down, retrying the same record immediately in a tight loop increases load, blocks a partition, and creates an incident storm. Use exponential backoff, jitter, maximum attempts, and circuit breaking where appropriate.

Idempotency with a database uniqueness constraint

CREATE TABLE processed_event (
    consumer_name VARCHAR(100) NOT NULL,
    event_id UUID NOT NULL,
    processed_at TIMESTAMP NOT NULL,
    PRIMARY KEY (consumer_name, event_id)
);
@Transactional
public void createPayment(OrderCreatedEvent event) {
    try {
        processedEventRepository.saveAndFlush(
            new ProcessedEvent("payment-service", event.eventId(), Instant.now())
        );
    } catch (DataIntegrityViolationException duplicate) {
        // This event has already changed the database.
        return;
    }

    Payment payment = Payment.pending(
        event.orderId(),
        event.amount()
    );
    paymentRepository.save(payment);
}
The processed-event insert and business update must be in the same local database transaction. A “check then insert” without a unique constraint is race-prone.

DLT is not a trash bin

  • Include original topic, partition, offset, timestamp, exception type, and correlation ID.
  • Restrict access because payloads may contain sensitive data.
  • Alert on arrival rate and age.
  • Define ownership and service-level objectives.
  • Provide a tested replay tool that preserves or deliberately changes keys.
  • Do not replay until the cause is fixed, or you create an endless loop.

Outbox integration

Application DB transaction: INSERT order INSERT outbox_event ↓ CDC / outbox publisher ↓ Kafka topic

Outbox solves the database-plus-Kafka dual-write problem. Kafka producer idempotence alone does not make an external database transaction atomic with Kafka.

18. Event Schema Design and Evolution

Recommended event envelope

{
  "eventId": "d84bb586-8cdd-4e27-8a18-6dfe87ef34a2",
  "eventType": "OrderCreated",
  "schemaVersion": 2,
  "aggregateId": "5dbbeef3-50bd-495d-a805-38d897f0d60e",
  "occurredAt": "2026-07-17T02:20:00Z",
  "producer": "order-service",
  "correlationId": "req-9f61...",
  "data": {
    "orderId": "5dbbeef3-50bd-495d-a805-38d897f0d60e",
    "customerId": "c-1007",
    "totalAmount": 499000,
    "currency": "VND"
  }
}

Evolution rules

  • Prefer adding optional fields with meaningful defaults.
  • Do not silently change a field’s meaning.
  • Do not reuse removed field identifiers in formats that track field numbers.
  • Keep producer and consumer deployments compatible during rolling releases.
  • Use schema compatibility checks in CI/CD.
  • Version the event contract when a breaking semantic change is unavoidable.

Event notification versus event-carried state transfer

Notification

{ "orderId": "O-100", "type": "OrderCreated" }

Small and stable, but consumers may need synchronous callbacks to fetch details.

Carried state

{ "orderId": "O-100", "customerId": "C-9",
  "amount": 100, "currency": "USD" }

Reduces runtime coupling, but creates larger contracts and duplication.

19. Security

Threat model

  • Unauthorized producer writes fake business events.
  • Unauthorized consumer reads personal or financial data.
  • A compromised service reads unrelated topics.
  • Credentials leak through source code or logs.
  • Unencrypted traffic is inspected or modified.
  • A tenant produces excessive traffic and harms other workloads.

Controls

ControlPurpose
TLSEncrypt traffic and authenticate endpoints where configured.
SASLAuthenticate clients using supported mechanisms.

QuotasLimit producer, consumer, request, or tenant resource use.

20. Monitoring and Observability

Cluster and broker signals

  • Offline partitions.
  • Under-replicated partitions and ISR shrink/expand rate.
  • Active controller count and KRaft quorum health.
  • Request latency, request queue time, and network handler utilization.
  • Disk usage, disk latency, failed log directories, and filesystem errors.
  • Bytes in/out and replication traffic.
  • Produce and fetch error rates.

Producer signals

  • Record error and retry rate.
  • Request latency.
  • Batch size and compression ratio.
  • Buffer available, waiting threads, and send timeouts.

Consumer signals

  • Lag per group, topic, and partition.
  • Lag growth rate, not only absolute lag.
  • Time lag when event timestamps are trustworthy.
  • Records consumed and processing latency.
  • Rebalance count and duration.
  • Commit failures.
  • Retry and DLT rate.

Lag is not enough

Zero lag can still hide a broken consumer that commits offsets before completing business work. High lag can be acceptable for a batch consumer with a relaxed SLA. Monitor business outcomes such as payments created, emails sent, and order states advanced.

Traceability fields

  • eventId
  • correlationId
  • causationId
  • topic, partition, offset
  • producer service and schema version
  • business aggregate ID

21. Performance Tuning

Producer

  • Increase batching with linger.ms and appropriate batch.size.
  • Use compression after measuring CPU and latency.
  • Send asynchronously, but always observe completion failures.
  • Avoid excessively large records. Store large files in object storage and publish references.
  • Use stable, well-distributed keys.

Consumer

  • Batch database writes where business semantics allow it.
  • Increase partitions only after proving consumer or partition throughput is the bottleneck.
  • Tune poll size and fetch size with memory and processing time.
  • Avoid one remote API call per event when batching is possible.
  • Protect downstream databases using bounded concurrency and rate limits.

Broker

  • Balance leaders and partitions across brokers.
  • Maintain disk and network headroom for recovery traffic.
  • Avoid putting all partitions with high traffic on one broker.
  • Keep JVM pauses controlled, but remember that page cache is central to Kafka performance.
  • Use realistic load tests with replication, TLS, compression, and real payload sizes.
Do not optimize only records per second. Measure end-to-end latency, durability, CPU, network, disk, retry rate, consumer lag, downstream impact, and recovery behavior.

22. Failure Scenarios and Correct Responses

Scenario 1: Producer times out, but broker stored the record

The client cannot know whether the write succeeded. It retries. Without idempotence, a duplicate may be appended. With idempotence, Kafka can deduplicate supported retries.

Scenario 2: Consumer updates DB, then crashes before offset commit

The record is delivered again. The database update must be idempotent, normally using a unique event ID or a business uniqueness constraint.

Scenario 3: Consumer commits offset, then DB transaction fails

The business update is lost while Kafka moves forward. This is why offset acknowledgement must follow successful processing.

Scenario 4: A broker leader fails

An eligible replica is elected leader. Clients refresh metadata and retry. Availability and data safety depend on ISR state and election policy.

Scenario 5: One consumer is slow

Its assigned partitions build lag. Adding consumers helps only if enough partitions exist and downstream dependencies can handle the added load.

Scenario 6: A poison message blocks a partition

Bound retries, classify the failure, route the record to a DLT, alert, and continue only if business ordering permits. For strict sequences, later events may depend on the failed event and cannot safely pass it.

Scenario 7: Database is down for 30 minutes

Pause or back off consumption, avoid hot retry loops, preserve offsets, monitor retention risk, and ensure the backlog can be drained without overloading the database after recovery.

Scenario 8: Consumer lag is larger than topic retention

Old records are deleted before the consumer reads them. Recovery may require another source, database snapshot, compacted state topic, or replay from an archive.

Client ↓ POST /orders Order Service + PostgreSQL ├─ orders row └─ outbox OrderCreated ↓ CDC Kafka: commerce.order.created.v1 ├─ Payment Service group ├─ Inventory Service group └─ Analytics group

Step 1: Order service local transaction

VALUES (:orderId, :customerId, 'PENDING', :amount);

INSERT INTO outbox_event(
    event_id, aggregate_id, event_type, payload, created_at
) VALUES (
    :eventId, :orderId, 'OrderCreated', :payload, CURRENT_TIMESTAMP
);

Step 2: Payment consumer

  • Consumes with group payment-service-v1.
  • Uses eventId uniqueness to avoid duplicate charges.
  • Creates a payment intent or calls a payment provider using an idempotency key.
  • Stores payment state and a new outbox event in one database transaction.

Step 3: Inventory consumer

  • Uses orderId for business ordering.
  • Reserves stock using an atomic conditional update.
  • Publishes InventoryReserved or InventoryRejected.

Step 4: Saga decision

PaymentCompleted + InventoryReserved → Confirm order PaymentCompleted + InventoryRejected → Refund payment → Cancel order

Where Kafka helps

  • Durable event transport.
  • Independent consumer groups.
  • Replay and auditing.
  • Per-order ordering with orderId key.

What Kafka does not solve by itself

  • Database-Kafka atomicity: use outbox.
  • Duplicate business effects: use idempotency.
  • Saga compensation logic.
  • External payment-provider exactly-once behavior.
  • Correct event schema and business ownership.

24. Common Anti-patterns

One topic for everything

Creates unclear ownership, incompatible retention needs, weak ACLs, and difficult schemas.

Random key for ordered entities

Events for one order move across partitions and can be processed out of order.

No key for business events

Distribution may be balanced, but per-entity ordering is lost.

Auto-commit without understanding

Offsets may advance independently of successful business processing.

Infinite retry

One poison record blocks progress and overloads dependencies.

DLT without ownership

Failures accumulate silently and are never repaired.

Kafka as a database replacement

Kafka is powerful storage, but query patterns, constraints, mutations, and transactional needs may still require databases.

More partitions fixes everything

It may increase parallelism, but also metadata, file handles, rebalances, and operational cost.

Large binary payloads

Large messages hurt batching, memory, replication, retries, and recovery. Store the blob elsewhere.

Assuming exactly-once globally

Kafka EOS has boundaries. External databases and APIs require their own consistency design.

25. Senior Interview Questions and Answers

Open each question. The answers focus on trade-offs and production reasoning rather than definitions only.

1. What is the main difference between Kafka and a message queue?

Senior answer:

Kafka is a retained, partitioned log. Consumers keep their own offsets and can replay records. A traditional queue is mainly a work-distribution mechanism where a message is normally removed after successful acknowledgement. Kafka is stronger for event history, multiple independent consumer groups, CDC, and streaming. A queue is often simpler for one-worker-per-job execution, flexible routing, delay, TTL, and priority. I choose based on delivery model, replay, ordering, routing, and operational needs rather than popularity.

2. Is Kafka a queue?

Kafka can distribute work among consumers in one group, so it can behave like a queue for some workloads. However, its core model is different: records are retained independently of consumption, offsets belong to consumer groups, and multiple groups can replay the same partition history. Calling it only a queue hides the features and responsibilities that matter most.

3. What is a Kafka partition?

A partition is an ordered append-only log and the unit of storage, replication, and consumer parallelism. Ordering is guaranteed only within one partition. A consumer group can process a partition with only one active consumer at a time. Therefore partition count limits useful consumer concurrency, while key design decides which records share an ordering boundary.

4. Why does Kafka need a message key?

The key normally controls partition selection. Records with the same key are sent to the same partition while the partition count and partitioning logic remain compatible. I use a key such as order ID when per-order ordering is needed. I also review key cardinality to prevent hot partitions. A key is a business and scalability decision, not only a producer parameter.

5. Can Kafka guarantee global ordering?

Only if the topic uses one partition, which limits parallelism and availability flexibility. Normally Kafka guarantees ordering per partition. In real systems, we choose a business entity key and require ordering per entity, not globally. If an interviewer asks for both unlimited parallelism and total global order, I would explain that these requirements conflict.

6. Explain consumer groups.

A consumer group represents one logical subscriber application. Kafka assigns each partition to at most one active consumer within that group. Different groups independently consume the full topic. If consumers exceed partitions, extra consumers are idle. If partitions exceed consumers, one consumer processes multiple partitions.

7. What is a rebalance and why is it expensive?

A rebalance changes partition ownership when group membership or topic metadata changes. Processing can pause, local state may move, and records in progress may be repeated. I reduce unnecessary rebalances by keeping poll timing healthy, sizing poll batches correctly, using stable deployments, and choosing cooperative or static membership features where appropriate.

8. What happens if processing takes longer than max.poll.interval.ms?

The group may treat the consumer as unable to make progress and reassign its partitions. The original consumer may then finish work after ownership changed, creating duplicates or commit failures. I reduce the poll batch, increase the interval based on measured worst-case processing, avoid blocking calls, or redesign the slow task.

9. Explain acks=0, 1, and all.

acks=0 does not wait for broker acknowledgement and has the highest loss risk. acks=1 waits for the leader, but the leader can fail before followers replicate. acks=all waits for the in-sync replica requirement and is normally used for important business events. It should be combined with a suitable replication factor and min.insync.replicas.

10. What is min.insync.replicas?

It is the minimum number of in-sync replicas required for a successful write when the producer uses acks=all. With replication factor three and minimum ISR two, the topic can normally tolerate one unavailable replica and still accept writes. If fewer than two are in sync, Kafka rejects writes to protect durability.

11. Does replication factor 3 guarantee no data loss?

No. The producer may use weak acknowledgements, ISR can shrink, unclean leader election can allow stale replicas, the application may ignore send errors, or all replicas may share one failure domain. Replication factor is only one part of a durability design.

12. Explain at-least-once delivery.

The system avoids silently skipping a record under expected failures, but it may deliver a record more than once. A common case is: business processing commits, then the consumer crashes before the Kafka offset commits. The record is delivered again. Therefore business operations need idempotency.

13. How do you implement an idempotent consumer?

I put a unique event ID in each event. In the consumer database, I insert that ID into a processed-event or inbox table with a unique constraint in the same transaction as the business update. A duplicate insert means the event was already applied. For external providers, I also pass an idempotency key when supported.

14. What does Kafka exactly-once semantics really mean?

Kafka EOS gives exactly-once visibility for a defined Kafka read-process-write transaction: consumed offsets and produced Kafka records commit or abort together. It does not automatically include PostgreSQL, REST APIs, email, or payment providers. I always state the transaction boundary rather than saying “the whole system is exactly once.”

15. What is the dual-write problem?

A service updates its database and publishes a Kafka event as two separate operations. If the database commits but publish fails, downstream systems miss the event. If publish succeeds but the database rolls back, consumers see an event for nonexistent state. I normally solve this with a transactional outbox and CDC or a reliable publisher.

16. What is the difference between producer idempotence and consumer idempotency?

Producer idempotence prevents duplicate log entries caused by supported producer retries. Consumer idempotency prevents duplicate business effects when the same record is processed again. They solve different failure points and are often both required.

17. What is consumer lag?

Lag is the difference between the latest available offset and the consumer group’s processed or committed position. It indicates backlog, but it is not enough alone. I also monitor lag growth rate, event age, processing latency, rebalances, errors, and business completion metrics.

18. How do you handle a poison message?

I classify whether it is schema corruption, permanent business invalidity, or a software defect. I use bounded retry with backoff, then route it to a DLT or quarantine with diagnostic metadata and alerting. I define how to repair and replay it. For strict per-key workflows, I consider whether later events are allowed to pass the failed event.

19. Why should you not sleep inside a Kafka listener for retry?

Sleeping blocks the consumer thread, delays all records on its assigned partitions, can exceed poll intervals, and wastes resources. Retry topics, scheduled queues, or framework-supported backoff provide better control and observability.

20. How do you choose the number of partitions?

I start from target producer and consumer throughput, benchmark throughput per partition with real payload and durability settings, and consider the maximum consumer parallelism. I include growth and recovery needs, but avoid excessive partitions because they increase metadata, files, rebalances, and replication work. I also remember that increasing partitions can change key mapping.

21. What happens when you add more consumers than partitions?

Extra consumers in the same group stay idle because one partition cannot be actively owned by two consumers in the classic consumer group model. To increase useful parallelism, the topic needs enough partitions, but the downstream system must also support the additional load.

22. What is log compaction?

Log compaction eventually retains the latest record for each key, allowing a consumer to rebuild current state. It does not immediately remove all old records, and it is not the same as time retention. A null-valued record acts as a tombstone for deletion.

23. When would you use RabbitMQ instead of Kafka?

I would consider RabbitMQ when the main requirement is task dispatch, rich exchange routing, per-message TTL, priorities, short-lived queues, or fine-grained worker acknowledgements and prefetch. Kafka is usually stronger when replay, multiple independent subscribers, retained event history, and streaming throughput are central.

24. What is prefetch in RabbitMQ?

Prefetch limits how many unacknowledged messages a consumer can hold. A large value increases throughput but can overload a slow consumer and reduce fair distribution. A small value improves fairness and memory safety but may reduce throughput. I tune it using actual processing time and concurrency.

25. What is SQS visibility timeout?

After a message is received, it is hidden from other consumers for the visibility period. The consumer must delete it after successful processing. If processing is not complete before timeout, the message becomes visible and can be delivered again. I set it above normal processing time and extend it for genuinely long tasks, while keeping idempotency.

26. How do you guarantee ordering in SQS FIFO?

Ordering is within a message group ID. Messages in one group are processed sequentially, while different groups can run in parallel. Therefore the group ID acts like an ordering and concurrency key. A poor choice such as one global group removes parallelism.

27. How would you monitor Kafka in production?

I monitor offline and under-replicated partitions, ISR changes, KRaft quorum health, broker request and disk latency, network throughput, producer errors and retries, consumer lag and lag age, rebalance rate, commit failures, DLT traffic, and business KPIs. Alerts must be connected to runbooks and ownership.

28. Why are large Kafka messages a problem?

They increase producer and consumer memory, network transfer, replication time, retries, broker request handling, and recovery cost. Several size settings must also align. I normally put files in object storage and send metadata plus a secure reference.

29. How would you migrate from a synchronous design to Kafka?

I first identify which calls are true commands, which are facts, and which responses are required immediately. I define event contracts, ownership, idempotency, outbox publication, retries, DLT, observability, and consistency expectations. I avoid replacing every HTTP call with an event because asynchronous systems introduce eventual consistency and operational complexity.

30. Design a reliable payment event flow.

I store payment state and a payment outbox event in one database transaction. CDC publishes it to Kafka using payment or order ID as the key. Consumers use unique event IDs and local transactions. Producer uses strong acknowledgements and idempotence. Retries are bounded, permanent failures go to a controlled DLT, and provider calls use provider idempotency keys. I monitor event age, consumer lag, duplicate detection, provider outcomes, and reconciliation differences.

31. How do you deal with events arriving out of order?

First, I preserve per-entity order using the correct key. Because retries, multiple topics, external systems, or repartitioning can still cause stale updates, events carry an aggregate version or event time. Consumers use conditional updates such as “apply only if version is newer.” For workflows where every transition matters, I quarantine gaps rather than blindly skipping them.

32. What would you review in a Kafka production readiness checklist?

I review workload sizing, partitions, key distribution, replication, minimum ISR, acknowledgements, retention, schemas, security, quotas, producer failure handling, consumer commit behavior, idempotency, retry and DLT ownership, monitoring, capacity headroom, upgrade compatibility, backup or cross-region strategy, and tested failure runbooks.

26. Quick Revision Cheat Sheet

Kafka essentials

  • Topic = named stream.
  • Partition = ordered shard.
  • Offset = position inside one partition.
  • Key = partition and ordering decision.
  • Consumer group = one logical subscriber.
  • Replay = reset/seek offsets within retention.
  • Replication + acks + ISR = durability design.

Queue essentials

  • Queue = pending work.
  • ACK/Delete = successful completion.
  • Prefetch/visibility = in-flight control.
  • DLQ = failed-message isolation.
  • Routing = exchange/binding or subscription rules.
  • FIFO often has a grouping key.

Reliability essentials

  • At-least-once means duplicates are expected.
  • Idempotent producer ≠ idempotent consumer.
  • Kafka transaction ≠ DB transaction.
  • Use Outbox for DB + event publication.
  • Use Inbox/unique ID for duplicate business effects.
  • Bound retries; own the DLT.

Setup essentials

  • Benchmark before choosing partitions.
  • Use KRaft for modern Kafka.
  • Spread replicas across failure domains.
  • Leave disk/network/recovery headroom.
  • Define schema compatibility and ownership.
  • Monitor lag plus business outcomes.
Senior summary: Kafka is not only a transport. It is a distributed storage and coordination system. Correct design requires understanding partitioning, ordering, offset ownership, durability, duplicates, schemas, failure recovery, and downstream capacity.
