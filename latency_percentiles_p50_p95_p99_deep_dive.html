Understanding p50, p95, p99 Latency

A practical, senior-level guide to latency percentiles, tail latency, SLOs, microservices, monitoring, debugging, and production performance — written in clear English with Vietnamese translations for important technical vocabulary.

1. The big picture

When we measure the performance of an API, database, service, or distributed system, one number such as average latency (độ trễ trung bình) is usually not enough. We need to understand the full latency distribution (phân bố độ trễ).

p50Typical user experience
Trải nghiệm phổ biến
p95Almost all requests
Gần như toàn bộ request
p99Tail performance at scale
Hiệu năng phần đuôi ở quy mô lớn
Simple interpretation
If p99 = 800 ms, it means 99% of requests completed in 800 ms or less. The slowest 1% took longer than 800 ms.

3. What is a percentile?

A percentile (phân vị) tells us the value below which a given percentage of observations fall.

Example: 100 requests sorted from fastest to slowest

p50: 50% of requests are at or below this latency.

p95: 95% of requests are at or below this latency.

p99: 99% of requests are at or below this latency.

Important
p99 does not mean “request number 99 always takes this long.” It is a statistical position in the latency distribution.

4. p50, p95, and p99 explained

p50 — Median

Median (trung vị) represents the middle request.

If p50 = 80 ms, half the requests finished in 80 ms or less, and half took 80 ms or more.

Use: understand the typical experience.

p95 — High percentile

p95 captures almost all common requests while excluding the slowest 5%.

If p95 = 350 ms, 95% of requests finished in 350 ms or less.

Use: production health, customer experience, capacity review.

p99 — Tail percentile

p99 exposes the slowest meaningful portion of traffic.

If p99 = 1.8 s, 1% of requests are slower than 1.8 seconds.

Use: distributed systems, large scale, SLOs, tail-latency investigation.

A realistic API example

POST /orders

p50   = 120 ms
p95   = 350 ms
p99   = 1.8 s
p99.9 = 7.2 s

A senior engineer should not say only “the API is fast because p50 is 120 ms.” The correct observation is: typical performance is good, but the tail is unhealthy.

5. How percentiles are calculated

For learning purposes, imagine these 10 latency samples:

20, 25, 30, 35, 40, 50, 80, 100, 200, 900 ms

They are already sorted from smallest to largest.

Approximate percentile rank = percentile × number of observations

With a small data set, percentile libraries may use different interpolation algorithms, so exact values can vary slightly. In production, monitoring systems normally calculate percentiles from histograms, sketches, or time-series aggregations.

For operational monitoring, understanding the meaning is more important than manually calculating the exact interpolation formula.

6. Why average latency is not enough

Consider 100 requests:

99 requests = 100 ms
 1 request  = 10,000 ms

Average = (99 × 100 + 10,000) / 100 = 199 ms

An average of 199 ms looks acceptable. However, one user waited 10 seconds. The average (trung bình) hides the outlier.

Average answers

“How much latency did all requests contribute in total?”

Percentile answers

“How slow are requests for a particular percentage of users?”

In user-facing systems, percentiles usually describe experience better than a single average.

7. Tail latency

Tail latency (độ trễ phần đuôi) describes the slow requests at the far end of the distribution, commonly p95, p99, or p99.9. 

Most requests
fast  ───────────────────────────────► slow

p50           p95       p99        p99.9
 |             |         |            |
 80ms         250ms     1.2s         8s

A system can have an excellent p50 but a terrible p99. This often happens when only a subset of requests encounters locks, cache misses, retries, slow downstream services, GC pauses, or resource contention.

8. Why 1% matters at scale

If a service handles 10,000 requests per second and 1% are slow:

10,000 requests/s × 1% = 100 slow requests/s

100 × 60 × 60 × 24
= 8,640,000 slow requests/day

This is why p99 becomes more important as traffic grows. At large scale, a “small percentage” can still represent millions of bad user experiences.

9. Why microservices amplify tail latency

In a distributed system (hệ thống phân tán), one user request may call many internal services.

If the Order Service must wait for all required dependencies, the end-to-end latency is strongly influenced by the slowest critical dependency.

Dependencyp50p99

Even when most services are fast, Payment Service can dominate the Order API p99. This is called latency propagation (lan truyền độ trễ).

More synchronous dependencies usually mean more opportunities for one slow dependency to increase tail latency.

10. Why p99 becomes high

Database problems

  • Slow query (truy vấn chậm)
  • Missing index
  • Row/table lock contention
  • Connection pool exhaustion
  • Disk I/O spikes
  • Replica lag

Application problems

  • Thread pool exhaustion
  • CPU saturation
  • Memory pressure
  • Long GC pause
  • Blocking operation
  • Large payload serialization

Cache problems

  • Cache miss
  • Cold cache
  • Cache stampede
  • Hot key overload
  • Expired entries at the same time

Network / downstream problems

  • Packet loss
  • Network congestion
  • DNS delay
  • Slow downstream API
  • Timeout + retry chains
  • Cross-region calls

Classic p99 pattern

Normal request:
API -> Cache HIT -> return
80 ms

Slow request:
API -> Cache MISS
    -> DB connection wait
    -> slow query
    -> retry downstream
    -> return
2.3 s

11. SLI, SLO, and SLA

TermMeaningVietnameseExample
SLI Service Level Indicator: the measured metric. Chỉ số mức dịch vụ p99 latency = 420 ms
SLO Service Level Objective: internal reliability target. Mục tiêu mức dịch vụ 99% of requests under 500 ms
SLA Service Level Agreement: formal agreement, often with business consequences. Cam kết mức dịch vụ Monthly availability ≥ 99.9%
If the SLO says “99% of requests must complete within 500 ms”, then one useful way to express it is: p99 latency ≤ 500 ms.

Do not confuse latency SLO with availability SLO

“99.9% availability” and “p99 under 500 ms” measure different things. A request may succeed but still be too slow.

13. Histograms and percentile estimation

Monitoring systems often store latency in a histogram (biểu đồ phân bố / histogram). A histogram counts how many observations fall within configured buckets. 

Latency bucket       Request count
<= 100 ms            6,000
<= 250 ms            8,500
<= 500 ms            9,600
<= 1,000 ms          9,900
<= 2,000 ms          10,000

From these cumulative counts, the monitoring system can estimate percentiles such as p95 or p99.

Bucket design matters. If buckets are too broad, percentile estimation can be imprecise.

14. Prometheus example

With a Prometheus histogram, a common p99 query looks like:

histogram_quantile(
  0.99,
  sum by (le) (
    rate(http_request_duration_seconds_bucket[5m])
  )
)

What this means

  1. rate(...[5m]) calculates the recent rate of observations in each bucket.
  2. sum by (le) aggregates histogram buckets.
  3. histogram_quantile(0.99, ...) estimates the 99th percentile.
In real systems, preserve labels such as service, route, method, or status_code only when they are useful and do not create excessive metric cardinality.

15. A senior debugging workflow for high p99

1Confirm the scope

Is p99 high for all endpoints, one route, one region, one instance, one customer segment, or only one downstream dependency?

2Check traffic and errors

Determine whether the problem starts with a traffic spike, timeout spike, deployment, or infrastructure change.

3Check saturation

CPU, memory, GC, thread pools, connection pools, queue length, file descriptors, disk I/O.

4Use distributed tracing

Find slow traces and identify the longest span. A trace can show whether 1.5 seconds was spent in the DB, payment service, external API, or queue.

5Compare fast and slow requests

Compare a p50 trace with a p99 trace. The difference is often more useful than looking at one slow trace alone.

6Check recent changes

Deployments, feature flags, query changes, traffic routing, index changes, autoscaling changes, dependency versions.

7Fix the root cause and verify percentiles

After the change, verify p50, p95, p99, errors, and resource saturation—not only average latency.

17. Common mistakes

1. Looking only at average latency

It hides the slow tail and can make an unhealthy service look healthy.

2. Looking at p99 without traffic volume

A percentile from only a few requests may be statistically noisy. Always consider sample size.

3. Aggregating percentiles incorrectly

You generally cannot calculate a correct global p99 by averaging the p99 values of individual servers. Percentiles are not directly additive.

4. Mixing unrelated endpoints

A fast health endpoint and a slow report endpoint should not necessarily share one latency SLO. Measure latency by meaningful route/workload.

5. Ignoring coordinated omission

Some benchmark tools stop sending work while waiting for a slow response. This can under-report latency under overload. Good load testing should model the intended arrival rate carefully.

6. Optimizing p50 while p99 remains bad

Faster happy-path caching may improve p50 while rare DB-lock or retry scenarios remain unchanged. Production optimization must consider the full distribution.

18. Senior-level interview answer

Example answer:

“p50, p95, and p99 are latency percentiles. If p99 is 500 milliseconds, it means 99% of requests complete within 500 milliseconds and the slowest 1% take longer. I do not rely only on average latency because an average can hide slow outliers. In production, I usually monitor p50 for the normal user experience, p95 for broad service quality, and p99 for tail latency. p99 becomes especially important at scale because even 1% can represent millions of requests. If p99 increases, I correlate it with traffic, error rate, CPU, thread pools, DB connection pools, cache misses, and distributed traces to identify which dependency or resource is causing the long tail.”

Stronger follow-up

If the interviewer asks “Why can p99 be high while p50 is normal?”, explain that only a subset of requests may hit a slow path: cache miss, cold data, database lock, slow downstream service, retry, GC pause, or resource queue.

21. Knowledge check

1. If p95 = 300 ms, what does it mean?

95% of requests complete in 300 ms or less. The slowest 5% take longer than 300 ms.

2. Why can average latency be misleading?

Because a small number of very slow requests can be hidden inside a reasonable average.

3. Why is p99 important in a system with millions of requests?

Because 1% still represents a large number of real requests and real users.

4. Why may p99 increase while p50 stays stable?

Only a subset of requests may hit slow paths such as cache misses, DB locks, retries, or slow downstream dependencies.

5. Can we average the p99 from ten servers to get the global p99?

No. Percentiles are not directly additive. Use the underlying histogram/distribution to compute an aggregated percentile.

23. 15 Senior Production Troubleshooting Questions

These questions are common in senior backend, Java, Spring Boot, Microservices, and system-design interviews. A strong answer should not jump directly to one solution. It should show a structured troubleshooting process: measure → narrow the scope → find the bottleneck → protect the system → fix the root cause → verify with metrics.

A useful senior mindset
In production, avoid guessing. Start with evidence from metrics (số liệu giám sát), logs (nhật ký hệ thống), and distributed traces (truy vết phân tán). Then correlate the symptom with traffic, errors, latency, and resource saturation.

1. Your Spring Boot API suddenly becomes slow. How would you find the bottleneck?

I would first determine whether the problem is global or limited to one endpoint, one instance, one region, or one dependency. Then I would follow the request path and inspect each layer rather than immediately changing code.

Step 1 — Confirm the symptom

  • Compare p50, p95, and p99 latency.
  • Check whether only tail latency is bad or all requests are slower.
  • Check request rate, error rate, and timeout rate.
  • Compare the current values with the normal baseline.

Step 2 — Check application resources

  • CPU saturation (CPU bị bão hòa).
  • Heap usage and GC pause time.
  • Tomcat/Jetty/Netty worker threads.
  • Blocked or waiting threads.
  • DB connection pool active, idle, and waiting connections.
  • Queue depth if asynchronous work is used.

Step 3 — Use distributed tracing

HTTP request = 2.4 seconds

Controller       5 ms
Service         10 ms
Redis           15 ms
Database      2100 ms  <-- bottleneck
Serialization   20 ms
Network        250 ms

A trace allows me to identify which span (đoạn xử lý trong trace) dominates total latency.

Step 4 — Inspect the slow dependency

If the database is slow, I check slow-query logs, execution plans, locks, missing indexes, connection wait time, and I/O. If a downstream service is slow, I check its p95/p99, timeout rate, thread pool, and network path.

Senior interview answer: “I would not guess from the code first. I would start with p50/p95/p99, throughput, error rate, and saturation. Then I would use distributed tracing to identify where the request spends its time. If the slow span is the DB, I inspect query latency, locks, indexes, and connection pool. If it is another service, I inspect that dependency. After fixing the root cause, I verify the same percentiles again.”

2. 5,000 requests hit your API simultaneously. What could become the bottleneck?

Almost any shared or bounded resource can become the bottleneck. The important point is that 5,000 incoming requests do not mean the application can process 5,000 requests at exactly the same time.

LayerPossible bottleneckWhat happens
Load balancerConnection or throughput limitRequests queue or get rejected.
Application serverWorker-thread poolRequests wait for a free thread.
CPUCPU saturationContext switching and processing latency increase.
MemoryAllocation pressure / GCLong GC pauses and higher p99.
DatabaseConnection pool / locks / IOPSThreads wait for connections or queries.
CacheHot key / network / cache missCache becomes overloaded or DB receives a spike.
Downstream serviceCapacity limitTimeouts and retries amplify load.

Example

Incoming requests:       5,000
Tomcat max threads:        200
DB pool size:               50

At most:
~200 requests execute application code concurrently.
Only ~50 DB-heavy requests can use DB connections concurrently.

The rest wait in queues.

If each DB operation takes too long, the DB pool becomes a bottleneck first. Increasing the thread pool without increasing downstream capacity can actually make the system worse.

Senior answer: “I would check bounded resources: application threads, CPU, memory, DB pool, DB locks, Redis connections, downstream capacity, queues, and network limits. I would also check whether the system has backpressure or load shedding, because accepting unlimited concurrent work can create queue growth and p99 collapse.”

3. Your database connection pool is exhausted. What would you check first?

Connection-pool exhaustion means all available DB connections are busy and new requests must wait. The first question is not “Should I increase the pool?” but “Why are connections being held for so long?”

Check in this order

  1. Active connections versus maximum pool size.
  2. Connection acquisition wait time.
  3. Slow queries.
  4. Long-running transactions.
  5. Database locks or blocked sessions.
  6. Connection leaks.
  7. Traffic increase.
  8. Database CPU, I/O, memory, and max connection limits.
Request A opens transaction
    |
    +-- Query 1
    +-- HTTP call to another service: 5 seconds
    +-- Query 2
    |
commit

DB connection may be held for the whole 5+ seconds.

Calling slow external services inside a transaction is a common cause of unnecessarily long connection holding.

Blindly increasing HikariCP maximumPoolSize can shift the bottleneck to the database. More connections can mean more DB concurrency, more lock contention, and higher CPU.

4. A downstream service takes 10 seconds to respond. How would you protect your API?

Never allow one unhealthy dependency to consume the entire request budget. I would use several resilience patterns together.

5. The same request reaches your API twice. How would you make it idempotent?

Idempotency (tính bất biến khi gọi lặp lại) means processing the same logical request multiple times has the same effect as processing it once.

Example: payment API

POST /payments
Idempotency-Key: pay-20260826-abc123

First request:
key not found
-> create payment
-> save result with key
-> return 201

Second request:
same key found
-> do NOT create another payment
-> return stored result

Possible implementation

  • Client sends a unique idempotency key.
  • Server stores the key with request hash, status, and result.
  • Use a unique DB constraint on the key.
  • Process key creation and business operation atomically if possible.
  • If the same key is reused with a different payload, reject it.
CREATE UNIQUE INDEX uq_payment_idempotency_key
ON payment_request(idempotency_key);
Idempotency is especially important for payment, order creation, booking, and event consumers because clients may retry after a timeout without knowing whether the first request succeeded.

6. Two users update the same record simultaneously. How would you handle it?

This is a concurrency-control problem. The correct strategy depends on the business rule.

Option A — Optimistic locking

Use when conflicts are possible but not extremely frequent. 

@Entity
class Product {
    @Id
    private Long id;

    @Version
    private Long version;

    private BigDecimal price;
}
User A reads version 10
User B reads version 10

A updates:
WHERE id = 1 AND version = 10
-> success, version becomes 11

B updates:
WHERE id = 1 AND version = 10
-> 0 rows updated
-> OptimisticLockException

Then return a conflict such as HTTP 409 or reload/retry depending on the business requirement.

Option B — Pessimistic locking

Use a DB lock such as SELECT ... FOR UPDATE when the critical section must be serialized. This provides stronger protection but reduces concurrency.

Option C — Atomic update

UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = ?
  AND quantity > 0;

For inventory, an atomic conditional update can be more efficient than reading and then writing separately.

8. A @Transactional operation partially fails. Why might rollback not happen as expected?

There are several common Spring transaction pitfalls.

Reason 1 — Exception is caught and swallowed

@Transactional
public void createOrder() {
    orderRepository.save(order);

    try {
        paymentService.pay();
    } catch (Exception e) {
        log.error("payment failed", e);
    }

    auditRepository.save(audit);
}

If the exception never escapes the transactional boundary and nothing marks the transaction rollback-only, Spring may commit.

Reason 2 — Checked exception

By default, Spring commonly rolls back for unchecked exceptions (RuntimeException and Error), not every checked exception. 

@Transactional(rollbackFor = Exception.class)

Reason 3 — Self-invocation

public void outer() {
    this.inner(); // proxy may be bypassed
}

@Transactional
public void inner() { ... }

Spring's proxy-based transaction interceptor may not run when a method in the same bean calls another transactional method directly.

Reason 4 — Propagation behavior

REQUIRES_NEW creates an independent transaction. The inner transaction can commit even if the outer one later rolls back.

Reason 5 — Database operation has already committed elsewhere

A remote API call, Kafka publish, file write, or external system is not automatically rolled back with the database transaction.

@Transactional is not a distributed transaction across every side effect. For cross-service consistency, patterns such as Outbox, Saga, or compensating actions may be required.

9. Your Java application suddenly consumes too much memory. How would you debug it?

First determine whether this is a true memory leak (rò rỉ bộ nhớ), temporary traffic-related memory pressure, or simply a larger healthy working set.

Metrics to inspect

  • Heap used / committed / max.
  • Old-generation usage after full GC.
  • GC frequency and pause duration.
  • Allocation rate.
  • Off-heap / direct-buffer usage.
  • Thread count and stack memory.
  • Container RSS versus JVM heap.

Leak pattern

Heap after GC:

10:00  1.2 GB
11:00  1.7 GB
12:00  2.3 GB
13:00  3.0 GB
14:00  3.8 GB

Memory does not return after GC
-> possible leak / retained objects

Tools

  • Heap dump.
  • JDK Flight Recorder (JFR).
  • Java Mission Control.
  • jcmd / jmap / jstack where appropriate.
  • Eclipse MAT for retained-object analysis.

Common causes

  • Unbounded cache.
  • Static collection retaining objects.
  • Large session objects.
  • Listener not removed.
  • ThreadLocal leak.
  • Large byte arrays / payload buffering.
  • Too many threads.
  • Direct ByteBuffer / native memory leak.

10. A Microservice goes down while other services are healthy. How should your system handle it?

The failure should be isolated rather than propagated through the entire system. This is the purpose of fault isolation (cô lập lỗi).

Protection strategy

  1. Remove unhealthy instances from service discovery/load balancing.
  2. Use health/readiness checks.
  3. Apply short timeouts.
  4. Open a circuit breaker after repeated failures.
  5. Use bulkhead isolation so blocked calls do not consume all threads.
  6. Use fallback or cached data where business rules allow it.
  7. Queue asynchronous work if immediate completion is not required.
Order Service
    |
    +-- Product Service        healthy
    +-- Inventory Service      healthy
    +-- Recommendation Service DOWN

If recommendation is optional:
return order result without recommendations

Do not fail the entire purchase flow.

This is called graceful degradation (giảm cấp dịch vụ có kiểm soát).

11. Kafka consumer lag keeps increasing. What would you investigate?

Consumer lag (độ trễ consumer) grows when producers create messages faster than consumers can process them.

First check the equation

Producer rate = 20,000 msg/s
Consumer processing capacity = 15,000 msg/s

Lag growth = 5,000 msg/s

Investigate

  • Producer throughput.
  • Consumer processing time per message.
  • Number of partitions.
  • Number of active consumers in the consumer group.
  • Slow DB or downstream calls inside message processing.
  • Frequent consumer rebalances.
  • GC pauses and CPU saturation.
  • Large messages or slow deserialization.
  • Broker health and disk/network I/O.
  • Error retries causing repeated processing.
Adding more consumers only improves parallelism up to the number of partitions. With 6 partitions, 20 consumers in the same consumer group do not give 20-way parallel processing.

Peak-only slowness usually points to resource saturation, queueing, lock contention, or a downstream capacity limit.

One important concept is queueing delay. A server may execute each request quickly after it gets a worker, but users still experience high latency because requests wait in a queue.

13. A retry mechanism is making a downstream outage worse. Why?

This is a retry storm (bão retry). When a dependency becomes slow, callers retry failed requests, increasing load exactly when the dependency has the least capacity. 

Normal:
1,000 original requests/s

Dependency starts failing.
Each request retries 3 times.

Potential downstream load:
1,000 original
+ 3,000 retries
= 4,000 attempts/s

If multiple service layers retry independently, the amplification can be even worse.

Safer retry policy

  • Retry only transient errors.
  • Retry only safe/idempotent operations.
  • Set a small maximum number of attempts.
  • Use exponential backoff.
  • Add jitter.
  • Use a circuit breaker.
  • Respect an end-to-end timeout budget.
  • Consider retry budgets to limit total retry traffic.

14. A scheduled job runs twice after scaling your application. How would you prevent it?

A normal Spring @Scheduled task runs independently in every application instance. Therefore, scaling from one pod to three pods can make the job run three times. 

Before scaling:
Pod A -> @Scheduled job

After scaling:
Pod A -> job
Pod B -> job
Pod C -> job

Solutions

ApproachWhen to use
Distributed lockSimple jobs where only one instance should execute.
ShedLockCommon Spring solution using DB/Redis/etc. as lock storage.
Kubernetes CronJobRun the scheduled task outside the application instances.
Quartz clustered modeAdvanced distributed scheduling requirements.
Leader electionOnly the leader instance executes scheduled work.

Also make the job idempotent

Even with a distributed lock, design the job to tolerate duplicate execution because network failures and lock edge cases can happen.
