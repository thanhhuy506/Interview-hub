How Can 2 Million Live Viewers Click the Same Product Without Killing the Database?

This page explains caching for a TikTok-like live commerce event. We study three hard problems: millions of users watching one stream, a huge click burst on one product when its cache expires, and an admin updating the product while users are reading it. English is kept around IELTS 5.5–6.5, and technical terms are translated into Vietnamese.

Main rule: 2 million viewers must never mean 2 million database reads. Large systems collapse repeated work through CDN, multi-level caches, request coalescing, prewarming, version-aware invalidation, and protected origin/database paths.

0. Public Facts vs Design Inference

BYTEPLUS / BYTEDANCE PUBLIC

Multilevel CDN

BytePlus, which says it is born from ByteDance technology, publicly documents edge cache nodes and regional cache nodes. This reduces origin load and serves content near users.

BYTEPLUS / BYTEDANCE PUBLIC

Live GOP cache

BytePlus MediaLive documents a short GOP cache on edge servers for live pull streams. The cache uses FIFO and trades latency against resilience.

BYTEPLUS / BYTEDANCE PUBLIC

Purge + prefetch

BytePlus publicly documents cache purge/refresh and content prefetch/warm-up for updated content and high-traffic events.

AMAZON PUBLIC

Request coalescing

Amazon Builders' Library explicitly recommends request coalescing so a thundering herd does not create many downstream requests for one uncached item.

AMAZON PUBLIC

Soft + hard TTL

Amazon describes refreshing after a soft TTL while keeping the last good value usable until a hard TTL when dependencies are impaired.

DESIGN PATTERN

TikTok product metadata

The exact TikTok Live product-cache architecture is private. The product design below is a strong architecture built from public ByteDance/BytePlus and Amazon caching lessons.

Careful: BytePlus exposes technology born from ByteDance engineering, but a public BytePlus feature is not proof that TikTok internally uses the exact same component or configuration.

1. Separate the System Into Three Planes

Media Plane

Video/audio. Host → ingest → transcode → CDN → viewers. It should not touch a relational database for every frame or viewer.

Product/Data Plane

Product title, image, display price, seller, promotion, product status. This is a read-heavy metadata workload.

Realtime Interaction Plane

Chat, likes, gifts, reactions, viewer count. These fit stream/pub-sub and sharded counters better than one hot database row.

MEDIA

Host → Ingest → Transcode → Regional CDN → Edge → Player

PRODUCT

Product API → L1 → Regional L2 → Read Model → DB

INTERACTION

WebSocket/RTC → Stream Bus → Sharded Counters → Aggregation

Principal-level insight: these traffic classes need separate capacity, caches, failure domains, and backpressure rules.

The video stream is distributed by CDN. Edge nodes keep recent chunks/GOPs (GOP — Group of Pictures / nhóm khung hình) and serve many nearby viewers from one local stream copy.

2.3 BytePlus public live behavior

BytePlus MediaLive documents a server-side GOP cache at the edge for FLV/RTMP pull streaming. The cache is measured in seconds and uses FIFO — First-In, First-Out / vào trước ra trước. A larger cache improves protection against network fluctuation but adds more playback latency.

2.4 Origin pull

Origin pull — kéo dữ liệu từ máy chủ gốc means the CDN obtains the stream from the source and fans it out. BytePlus documents both viewer-triggered on-demand pull and scheduled pull. Scheduled pull can keep the path already warm before a big event.

4. The Dangerous Moment — Product TTL Expires During the Live

Cache stampede / thundering herd — hiệu ứng bầy đàn dồn xuống DB.

4.1 Broken expiration

product:889 expires at 20:00:00

20:00:00.001
100,000 requests arrive

every request:
  cache MISS
      |
      v
      DB

100,000 DB queries
for one product.
Never design TTL as: “delete the only usable value and let everyone rebuild it.” Under viral traffic, expiration must be controlled.

4.2 Soft TTL + hard TTL

Amazon publicly describes this technique.

product v42

soft_expire = 20:00:00
hard_expire = 20:05:00

At 20:00:01:

one caller:
  refreshes

all other callers:
  still get stale-but-safe v42

when refresh completes:
  cache becomes v43

Soft TTL — hết hạn mềm: the value should be refreshed. Hard TTL — hết hạn cứng: after this point the value should not be served.

4.3 Why stale can be better than error

For title, description, seller name, or a non-critical badge, a value that is a few seconds old is often better than a 500 error. Final price, product status, and inventory are revalidated at checkout.

5. Anti-Stampede Techniques — Make 100,000 Misses Become ~1 Refresh

5.1 Request coalescing

Request coalescing — gộp các request trùng nhau. Amazon explicitly recommends it.

100,000 requests for product:889
          |
          v
refresh already in progress?
      /            \
    yes             no
     |               |
serve stale/wait   one caller
                    |
                    v
                 downstream

5.2 Singleflight inside one app process

Singleflight — một request đại diện làm công việc dùng chung.

refresh_in_flight["product:889"] = Future

first caller:
  creates Future
  calls L2/read model

later callers:
  share the Future
  or receive stale value

5.3 Distributed refresh lease

Local singleflight is not enough when thousands of application servers exist.

SET refresh:product:889 owner-id
NX
PX 3000

winner:
  refresh

losers:
  serve stale
  or wait with a small deadline

Lease — quyền làm mới tạm thời. The lease needs an expiry. Version/fencing logic should prevent a very slow old refresher from overwriting newer data.

5.4 TTL jitter

Jitter — độ lệch ngẫu nhiên.

Instead of:
TTL = 300 for everything

Use:
TTL = 300 + random(-30,+30)

Examples:
273, 286, 302, 319, 329...

AWS documentation provides examples of adding jitter so expiration is spread instead of synchronized.

5.5 Refresh-ahead

Refresh-ahead — làm mới trước khi hết hạn.

if product.qps > HOT_THRESHOLD
and ttl_remaining < REFRESH_WINDOW:
    refresh asynchronously

5.6 Probabilistic early refresh

Probabilistic early refresh — làm mới sớm theo xác suất. The closer the key gets to expiry, the more likely one request refreshes it early. This is a strong industry pattern; exact TikTok use is not public.

5.7 Event prewarming

Prewarm / warm-up — làm nóng cache trước sự kiện.

T - 10 minutes:
KOL campaign says product 889 will be pinned

control plane:
  load product v42
  warm APAC L2
  warm US L2
  warm EU L2
  prefetch images to CDN

T = product pin:
first viewers already HIT cache

BytePlus publicly documents CDN/VOD prefetch and warm-up for large events and releases to reduce origin load and improve first access.

5.8 Negative cache

Negative cache — cache kết quả không tồn tại/lỗi.

product:BAD -> NOT_FOUND
TTL = short

Repeated invalid requests
do not keep hitting the DB.

Amazon's Builders' Library explicitly discusses negative caching using a different TTL from positive values.

7. Hidden Race — “Update DB Then Delete Cache” Is Not Enough

7.1 Stale resurrection

Initial:
DB = v42
Cache = v42

Request A:
  misses cache
  reads DB v42
  pauses before SET

Admin:
  DB -> v43
  DELETE cache

Request A resumes:
  SET cache = v42

Final:
DB = v43
Cache = v42

Old data is alive again.
This race is why simple cache deletion is not a full consistency strategy.

7.2 Versioned cache keys

product:889:v42
product:889:v43

latest_version:889 = 43

A delayed request can still write v42, but new readers ask for v43.

7.3 Version-aware CAS

CAS — Compare-And-Set / so sánh rồi cập nhật nguyên tử.

if incoming.version >= cached.version:
    SET incoming
else:
    IGNORE

7.4 CDC + version protects event ordering

event v43 -> apply
late event v41 -> ignore
late stale fill v42 -> CAS reject

7.5 Hard TTL is a safety net

Even with events, keep a bounded hard TTL so one lost invalidation message cannot leave data stale forever.

7.6 Checkout revalidation is the final correctness wall

Browse cache is never the final authority for final price, inventory, product blocked status, or promotion eligibility.

9. Amazon Public Caching Lessons

9.1 Request coalescing

Amazon says thundering-herd miss traffic should be coalesced so only one downstream request is pending for the uncached resource.

9.2 Soft/hard TTL with backpressure

Backpressure — tín hiệu giảm tải ngược. Amazon describes keeping last-good cached data usable until hard TTL when the dependency is under pressure.

9.3 Brownout

Brownout — hệ thống còn sống nhưng suy giảm. During brownout, upstream may stop refreshing non-critical keys and serve safe stale values to let the dependency recover.

9.4 DynamoDB cache bimodality lesson

Amazon Science described a historical DynamoDB design where a very effective cache meant a metadata table saw only a tiny share of normal traffic. If cache behavior changed, the table could suddenly face nearly all traffic. Amazon redesigned the metadata serving layer so the fallback path was continuously exercised and horizontally scalable.

Lesson: never size the product DB for “Redis will always work.” Load-test cache-off and cold-cache paths, cap downstream QPS, and avoid a system where cache-hit mode is safe but cache-miss mode is catastrophic.

9.5 Bimodal behavior

15. Deep Senior Interview Walkthrough — How to Answer Convincingly

A strong Senior or Principal Engineer should not start with “I will use Redis”. Start with the workload, business requirement, failure model, and consistency requirement. Then explain why each cache layer exists.

Strong opening sentence:
“I would first separate media delivery, product metadata, and realtime interactions because they have very different traffic patterns. Two million viewers should not create two million database reads. The main design goal is to reduce repeated work at every layer and keep the database outside the normal hot read path.”

15.1 Interviewer: “Two million users are watching one live. What happens behind the scenes?”

I would answer:

“The video path should not be a database problem. I would ingest one stream from the creator, transcode it into several qualities, then distribute it through regional CDN and edge nodes. The edge keeps recent video chunks or GOPs and fans one upstream stream out to many viewers. Therefore two million viewers mostly create edge bandwidth, not two million origin or database reads.”

Fan-out — phân phối một nguồn thành nhiều nhánh is the key idea. One edge may pull one recent stream path and serve thousands of viewers. BytePlus publicly documents edge/regional CDN concepts and short GOP caching for live media; exact TikTok internal topology is private.

15.4 Why L1 cache matters even when L2 Redis exists

Suppose Product Service has 2,000 instances and everybody asks for the same product. If every request calls Redis, the database is safe but Redis can become the new bottleneck.

L1 cache — cache trong bộ nhớ của process removes network calls. For a viral hot key, this is important because one L2 shard can otherwise receive an extreme read rate.

15.5 Interviewer: “What happens exactly when TTL expires?”

This is where a weak answer often fails. A naive cache-aside implementation can create a database stampede: 

20:00:00
product:P123 expires

20:00:00.001
100,000 requests arrive

All see MISS
All call source

I would explicitly say:

“A cache miss is normal. A hundred thousand identical misses reaching the origin is an architecture bug.”

15.6 Layer 1 protection: local singleflight

Singleflight — một request đại diện làm công việc dùng chung means one application process keeps one in-flight refresh per key. 

Process A receives 1,000 requests for P123

refresh_in_flight[P123] exists?

No:
  request #1 starts refresh
  store Future

Yes:
  request #2..#1000
  reuse same Future
  or receive stale value

This can convert 1,000 local misses into one L2/source request. But it does not solve fleet-wide coordination.

15.7 Layer 2 protection: distributed refresh lease

If 2,000 Product Service instances all miss together, each process can still become its own local winner. Therefore a hot key may need a short distributed refresh lease: 

SET refresh:P123 owner-991 NX PX 3000

Winner:
  refreshes from source

Losers:
  serve stale
  or wait a small bounded time
  then retry cache

Lease — quyền sở hữu tạm thời is better than an unlimited lock because it expires automatically if the owner crashes. But a lease creates another subtle race.

15.8 The slow-owner problem and fencing token

A gets lease token 100
A starts reading old data
A pauses for 5 seconds

lease expires

B gets token 101
B reads product v44
B writes cache v44

A wakes up
A tries to write old v43

Without protection, A can overwrite v44 with v43. Use a version or fencing token — mã thứ tự để chặn owner cũ: 

cache currently accepts token 101

A writes token 100
100 < 101
=> reject

B writes token 101
=> valid

This is why “just use a distributed lock” is not a complete Senior-level answer.

15.9 Soft TTL + hard TTL instead of destructive expiry

product P123 = v43

soft_expiry = 20:00:00
hard_expiry = 20:05:00

At 20:00:01:

Request A:
  sees soft-expired
  wins refresh ownership
  refreshes in background

Requests B..100,000:
  keep receiving v43
  instead of waiting or hitting DB

Refresh returns v44
Cache becomes v44

Stale-while-revalidate — phục vụ dữ liệu cũ trong lúc làm mới keeps latency stable during refresh. Amazon Builders' Library publicly discusses a soft/hard TTL model for similar resilience goals.

15.10 Why hard TTL is still necessary

If the dependency stays unhealthy forever, stale data cannot be served forever. The hard TTL defines the final safety boundary. 

0 - 30 sec:
normal fresh value

30 sec - 5 min:
soft expired
serve stale if safe + attempt refresh

> 5 min:
hard expired
must fail, use stronger source,
or apply a business-specific fallback

  reads DB v42
  pauses before cache SET

Admin:
  updates DB -> v43
  deletes cache

Request A resumes:
  SET cache = v42

Final:
DB = v43
Cache = v42

This is stale resurrection — dữ liệu cũ sống lại sau invalidation. It is a very good Senior interview edge case.

15.16 Solution: version-aware CAS

incoming.version = 42
cached/latest.version = 43

if incoming.version >= current.version:
    write
else:
    reject

CAS — Compare-And-Set / so sánh rồi cập nhật nguyên tử stops a slow old fill from replacing newer data.

15.17 Alternative: immutable versioned cache keys

product:P123:v42
product:P123:v43

latest:P123 = 43

A delayed request may still fill product:P123:v42, but readers that need the latest object follow version 43. Old and new values do not overwrite each other.

15.18 Product images should be immutable assets

Immutable asset — tài nguyên bất biến means the content behind a URL never changes. 

BAD:
/product/P123/main.jpg

GOOD:
/product/P123/main-v43.jpg
or
/product/P123/hash-a81f2.jpg

Admin publishes a new URL for a new image. Old CDN copies can live until natural expiry without creating freshness bugs.

15.19 Checkout is the final correctness wall

The browse cache may be slightly stale. The checkout path must revalidate critical fields. 

User saw:
price = $10
product_version = 42

Admin changed:
price = $12
version = 43

Checkout request:
product_id = P123
expected_version = 42
shown_price = $10

Pricing authority:
current_version = 43
current_price = $12

Business decision:
A) PRICE_CHANGED -> ask user to confirm
or
B) honor a still-valid server-issued price quote

The important principle is that cache freshness should not accidentally decide how much money the customer pays.

15.20 Inventory cache is never the final authority

Browse cache:
"In stock"

Checkout:
atomic inventory reservation

UPDATE inventory
SET available = available - 1
WHERE sku_id = :sku
  AND available >= 1;

The product page can be temporarily stale. The authoritative reservation decides the real winner.

15.21 Hot-key problem: Redis can become the new database bottleneck

Suppose product P123 receives 70% of all reads. Consistent hashing sends one key to one shard, so normal sharding alone does not spread that hot key. 

product:P123
    |
    v
cache shard 19
    |
1,000,000 GET/sec

Other shards:
mostly idle

Protect the hot key with:

  • L1 near-cache on Product API servers.
  • Read replicas or replicated hot-value copies inside the region.
  • A compact precomputed product document.
  • Separate hot-key capacity or cache pool.
  • Refresh coalescing so hot reads do not become hot refreshes.

15.22 Interviewer: “What if Redis fails during the live?”

A weak design:

Redis DOWN
    |
500k req/sec
    |
    v
Database
    |
Database DOWN

A stronger degradation path:

    |
    +--> use L1 last-good values
    +--> stale-if-error for safe fields
    +--> request coalescing
    +--> bounded origin concurrency
    +--> circuit breaker
    +--> load shedding
    +--> protected read model
    +--> progressive cache recovery

Bounded concurrency — giới hạn số request chạy đồng thời is important. If the database can safely handle 5,000 concurrent product reads, do not allow 500,000 callers to queue against it.

15.23 Semaphore-style database protection

DB read permits = 5,000

Request wants DB read:
  acquire permit?

Yes:
  call DB

No:
  serve safe stale value
  or shed low-priority request
  or return bounded retry response

Semaphore — cơ chế giới hạn số tác vụ đồng thời protects the dependency from an uncontrolled fallback wave.

15.24 Circuit breaker means users do not “test the DB” 500,000 times

cooldown
   |
   v
HALF-OPEN

healthy -> CLOSED

Circuit breaker — cầu dao ngắt mạch stops every user request from becoming a health probe for a broken dependency.

15.25 Backpressure and load shedding

If Product Read Model or DB is overloaded, upstream should reduce work instead of retrying harder. 

Dependency says OVERLOADED
        |
        v
Upstream actions:
  stop refreshing cold keys
  serve safe stale hot keys
  reduce concurrency
  reject low-priority requests
  protect checkout/critical flows

Backpressure — giảm tải ngược communicates pressure upstream. Load shedding — chủ động bỏ bớt tải keeps the whole system alive by sacrificing lower-priority work.

15.26 Amazon's bimodal-cache lesson

A dangerous system has two completely different modes: 

Normal:
1,000,000 requests/sec
99.9% cache hit
DB sees only 1,000 req/sec

Cache failure:
DB suddenly sees close to 1,000,000 req/sec

The DB collapses.

Bimodal behavior — hành vi hai chế độ means the system is healthy in cache-hit mode but catastrophic in cache-miss mode. Amazon Science has publicly described a related DynamoDB metadata-cache lesson.

“I would explicitly load-test the cache-off and cold-cache path. I do not size the database only from normal cache-miss traffic. The fallback path must have admission control, stale serving, coalescing, and bounded downstream concurrency.”

15.28 A polished two-minute interview answer

“I would first separate the media plane from the product-data plane. Two million viewers are served through hierarchical CDN fan-out, so the video origin is not contacted once per viewer. For the pinned product, I use an L1 in-process cache plus regional distributed L2 cache, and I prewarm products that are scheduled for the live event.

The dangerous case is cache expiration. I would not hard-delete a hot key and allow every caller to rebuild it. I use a soft TTL and hard TTL. After soft expiry, one caller gets refresh ownership while other callers receive the last safe value. Within a process I use singleflight; across the fleet I can use request coalescing or a short refresh lease. Version or fencing-token checks stop a slow old refresher from overwriting newer cache data. TTL jitter and refresh-ahead reduce synchronized expiration further.

For admin changes, the source database commits first. Then an outbox or CDC pipeline publishes a versioned ProductUpdated event. Regional caches apply only newer versions, so delayed events and old in-flight reads cannot resurrect stale values. Product images use immutable versioned URLs. I define a bounded freshness SLO for browsing instead of pretending every cache updates in the same microsecond.

Finally, the browse cache is never the authority for money or inventory. Checkout revalidates current price, sellability, and inventory using stronger services. I also design the cache-loss path explicitly: stale-if-error, request coalescing, bounded DB concurrency, circuit breakers, backpressure, load shedding, and progressive cache warm-up. This prevents a Redis failure from becoming a database failure.”
