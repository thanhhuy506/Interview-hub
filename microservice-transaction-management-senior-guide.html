Transaction Management in Microservices

A practical, senior-level guide to local transactions, Outbox, Inbox, idempotency, Saga, compensation, TCC, 2PC, Kafka transactions, locking, testing, and production failure recovery. The examples use clear English and Java/Spring-style implementation ideas.

Core problemOne business action, many independent services
Main patternsOutbox, Saga, Inbox, TCC, 2PC
Real examplesOrder, payment, inventory, shipping
Interview prepSenior questions with strong answers

1. The Correct Mental Model

In a monolith, one database transaction can protect many tables. In microservices, each service normally owns its own database. Therefore, one business operation becomes a sequence of independent local transactions.

Monolith

Order table
+
Payment table
+
Inventory table

One database can commit or rollback all changes together.

@Transactional
public void placeOrder() {
    orderRepository.save(order);
    paymentRepository.save(payment);
    inventoryRepository.reserve(items);
}

Microservices

Order DB
→
Payment DB
→
Inventory DB

Each service commits independently. A later failure cannot automatically rollback an earlier remote commit.

Important Spring @Transactional protects only resources participating in the same local transaction manager. It does not magically rollback another service through REST or Kafka.

What “transaction management” means in microservices

It is not only about rollback. A production design must answer all of these questions:

  • How do we avoid losing an event after committing the database?
  • How do we handle partial success across services?
  • How do we retry without creating duplicate payments or orders?
  • How do we compensate a completed business step?
  • How do we detect timeout, stuck workflows, and poison messages?
  • How do we preserve ordering when it matters?
  • How do we trace one transaction across many services?
  • How do we reconcile data after an unexpected production failure?

2. Local Transactions Still Matter

Distributed patterns do not replace normal database transactions. Every service should first make its own local state change correctly.

ACID in one service

Atomicity

All local database statements succeed or all rollback.

Consistency

Constraints and business invariants remain valid.

Isolation

Concurrent transactions do not corrupt each other.

Durability

Committed data survives restart or crash.

Example: local payment state transition

@Transactional
public void markPaymentCompleted(String paymentId, String providerReference) {
    Payment payment = paymentRepository.findByIdForUpdate(paymentId)
        .orElseThrow(() -> new PaymentNotFoundException(paymentId));

    if (payment.isCompleted()) {
        return; // idempotent behavior
    }

    payment.complete(providerReference);
    paymentRepository.save(payment);
}
Senior design rule Keep a local transaction short. Do not hold a database lock while calling a slow external API. Remote calls can timeout and keep locks open, causing contention and deadlocks.

Common Spring transaction pitfalls

PitfallWhy it happensBetter design
Self-invocationA method in the same class calls another @Transactional method, bypassing the Spring proxy.Move the transactional method to another bean, or call through a proxy only when truly needed.
Checked exception does not rollbackDefault rollback is usually for unchecked exceptions.Use rollbackFor intentionally, or convert to a domain runtime exception.
Remote call inside DB transactionThe database transaction remains open while waiting for the network.Persist intent first, commit, then call asynchronously or through a workflow.
Wrong isolation assumptionTwo requests read the same old state and both update it.Use optimistic locking, pessimistic locking, unique constraints, or atomic SQL.

3. The Distributed Transaction Problem

Problem A: Database + message broker dual write

@Transactional
public void createOrder(CreateOrderCommand command) {
    Order order = orderRepository.save(Order.create(command));
    kafkaTemplate.send("order-created", new OrderCreated(order.getId()));
}

This code looks simple, but the database and Kafka are separate systems.

Database resultKafka resultBusiness consequence
CommitPublish failsOrder exists, but downstream services never receive the event.
RollbackPublish succeedsConsumers process an event for an order that does not exist.
CommitPublish succeeds, acknowledgement lostProducer may retry and publish a duplicate.

Problem B: Partial success across services

Order created
→
Payment charged
→
Inventory failed
→
What now?

The payment is already committed in the Payment Service. A database rollback in Order Service cannot refund it. The system needs an explicit business recovery action such as Refund Payment.

Problem C: At-least-once delivery

Most reliable messaging designs prefer retry over message loss. This means the same event may be delivered more than once. Every consumer must be safe when processing duplicates.

Exactly-once is often misunderstood A broker may provide exactly-once behavior inside a limited boundary, but your complete business operation also touches databases, HTTP services, email providers, payment gateways, and side effects. End-to-end duplicate protection is still your responsibility.

4. Transactional Outbox Pattern

Outbox solves the dual-write problem between a service database and a message broker. The business change and the outgoing message are stored in the same local database transaction.

Business request
→
Local DB transaction
Business row + Outbox row
→
Outbox publisher / CDC
→
Kafka / RabbitMQ

Database structure

CREATE TABLE outbox_event (
    id              VARCHAR(64) PRIMARY KEY,
    aggregate_type  VARCHAR(100) NOT NULL,
    aggregate_id    VARCHAR(100) NOT NULL,
    event_type      VARCHAR(150) NOT NULL,
    payload         TEXT NOT NULL,
    status          VARCHAR(30) NOT NULL,
    created_at      TIMESTAMP NOT NULL,
    published_at    TIMESTAMP NULL,
    retry_count     INTEGER NOT NULL DEFAULT 0,
    next_retry_at   TIMESTAMP NULL
);

CREATE INDEX idx_outbox_pending
    ON outbox_event(status, next_retry_at, created_at);

Write business data and event together

@Transactional
public OrderResult createOrder(CreateOrderCommand command) {
    Order order = Order.create(command);
    orderRepository.save(order);

    OutboxEvent event = OutboxEvent.newEvent(
        UUID.randomUUID().toString(),
        "ORDER",
        order.getId(),
        "OrderCreated",
        jsonSerializer.serialize(new OrderCreated(order))
    );
    outboxRepository.save(event);

    return OrderResult.from(order);
}

If the transaction commits, both the order and event exist. If it rolls back, neither exists.

Publishing strategies

StrategyHow it worksAdvantagesTrade-offs
Polling publisher A scheduled worker reads pending rows and publishes them. Simple to understand and implement. Polling delay, DB load, row locking, duplicate publication after crash.
CDC Change Data Capture reads the database log and sends changes to the broker. Low latency and lower query overhead. More infrastructure and operational complexity.
Database notification The DB notifies a worker that a row was inserted. Fast signal. Still needs durable recovery when notifications are missed.

Safe polling publisher

@Scheduled(fixedDelayString = "${outbox.publisher.delay-ms:1000}")
public void publishBatch() {
    List<OutboxEvent> events = outboxRepository.lockNextBatch(100);

    for (OutboxEvent event : events) {
        try {
            broker.publish(event.getEventType(), event.getPayload(), event.getId());
            outboxService.markPublished(event.getId());
        } catch (Exception ex) {
            outboxService.scheduleRetry(event.getId(), ex.getMessage());
        }
    }
}

Crash scenario you must understand

  1. Publisher sends the event successfully.
  2. Process crashes before marking the outbox row as published.
  3. After restart, the event is published again.

Therefore, Outbox normally provides at-least-once publication, not automatic exactly-once business processing.

Outbox solves Reliable creation of an outgoing message after a local database commit.
Outbox does not solve Business compensation, consumer duplicates, long-running workflow state, or external side-effect rollback.

5. Inbox Pattern and Idempotent Consumers

Outbox protects the producer side. Inbox and idempotency protect the consumer side.

Inbox table

CREATE TABLE processed_message (
    consumer_name VARCHAR(100) NOT NULL,
    message_id    VARCHAR(100) NOT NULL,
    processed_at  TIMESTAMP NOT NULL,
    PRIMARY KEY (consumer_name, message_id)
);

Consumer transaction

@Transactional
public void handle(OrderCreated event, String messageId) {
    boolean firstTime = processedMessageRepository.tryInsert(
        "inventory-order-created-consumer",
        messageId
    );

    if (!firstTime) {
        return; // duplicate message
    }

    inventoryRepository.createReservation(
        event.getOrderId(),
        event.getItems()
    );
}

The unique key makes duplicate detection atomic. Do not rely only on “check then insert” without a constraint, because two threads may pass the check at the same time.

Business-key idempotency

Sometimes the message ID is not enough. Use a business constraint too.

ALTER TABLE payment
ADD CONSTRAINT uq_payment_order_operation
UNIQUE(order_id, operation_type);

HTTP idempotency key

For client retries, accept a stable idempotency key:

POST /payments
Idempotency-Key: 2f2a1c5c-7e90-4a8d-94bd-4e1a0d0d77a1

{
  "orderId": "ORD-1001",
  "amount": 125.50,
  "currency": "USD"
}

The service stores the key with the result. A retry returns the same result instead of charging again.

TechniqueBest useTypical key
Inbox tableBroker message deduplicationConsumer name + message ID
Unique business constraintPrevent duplicate domain operationsOrder ID + operation type
HTTP idempotency keyClient/API retriesClient-generated request key
State transition validationRepeated commandsCurrent status + allowed transition

6. Saga Pattern

Saga manages a business transaction across multiple services. It divides the flow into local transactions and runs compensating transactions when a later step fails.

Example business flow

Create Order
→
Authorize Payment
→
Reserve Inventory
→
Create Shipment

Compensation flow

Shipment failed
→
Release Inventory
→
Void / Refund Payment
→
Cancel Order

Choreography Saga

Services react to events. There is no central coordinator.

Order Service      publishes OrderCreated
Payment Service    consumes OrderCreated, publishes PaymentAuthorized
Inventory Service  consumes PaymentAuthorized, publishes InventoryReserved
Shipping Service   consumes InventoryReserved, publishes ShipmentCreated

Advantages

  • Loose coupling between participants.
  • No central orchestrator service.
  • Good for short and naturally event-driven flows.

Risks

  • The full business flow becomes difficult to understand.
  • Event chains create hidden dependencies.
  • Compensation and timeout logic become scattered.
  • Debugging requires strong tracing and event visibility.

Orchestration Saga

A coordinator sends commands, receives results, stores workflow state, and decides the next action.

OrderSaga Orchestrator
  1. Send AuthorizePayment command
  2. Wait for PaymentAuthorized or PaymentRejected
  3. Send ReserveInventory command
  4. Wait for InventoryReserved or InventoryRejected
  5. Send CreateShipment command
  6. Complete order or execute compensation

Advantages

  • Business flow is visible in one place.
  • Timeout, retry, and compensation are easier to control.
  • Useful for long-running and complex workflows.

Risks

  • The orchestrator can become a large “god service.”
  • It must be durable and highly available.
  • Poor design can tightly couple all participant details.

Choreography vs orchestration

QuestionChoreographyOrchestration
Who controls the flow?Events and participant reactionsCentral saga coordinator
Best forSmall, simple event chainsComplex, long-running business processes
VisibilityDistributedCentralized workflow state
Change impactCan be hidden across event consumersUsually easier to reason about centrally
Main dangerEvent spaghettiGod orchestrator
Senior recommendation Use choreography for a few stable steps. Use orchestration when the process has branching, timeout, manual review, multiple compensation paths, or must remain visible for hours or days.

7. Designing Compensating Transactions

Compensation is not a technical rollback. It is a new business operation that attempts to reverse or neutralize an earlier effect.

Forward actionPossible compensationImportant limitation
Authorize card paymentVoid authorizationVoid may be unavailable after capture.
Capture paymentRefundRefund can fail or take days.
Reserve inventoryRelease reservationItem may already be packed or shipped.
Create shipmentCancel shipmentCarrier may reject cancellation after pickup.
Send emailSend correction emailThe original email cannot be unsent.
Create external accountDeactivate accountExternal provider may have different lifecycle rules.

Compensation design rules

  1. Make compensation idempotent. It may be retried.
  2. Record why it is running. Operations teams need audit information.
  3. Allow compensation to fail. A failed refund needs its own retry and alerting workflow.
  4. Use business states. For example, REFUND_PENDING, REFUNDED, REFUND_FAILED.
  5. Do not delete history. Keep the original action and the compensating action for audit.
  6. Define irreversible steps. Run them late when possible.

Pivot transaction concept

In many sagas, early steps are compensatable, one step is the point of no return, and later steps must be retryable rather than compensated.

Compensatable
Reserve stock
→
Pivot
Capture payment
→
Retryable
Issue receipt
Practical example After a parcel has physically left the warehouse, “cancel shipment” may no longer be possible. The recovery action may become “create return request” instead. Compensation must follow real business rules, not database imagination.

8. Try–Confirm–Cancel (TCC)

TCC reserves resources before final confirmation. Each participant exposes three semantic operations: Try, Confirm, and Cancel.

TRY
Reserve resources
→
CONFIRM
Finalize all
or
CANCEL
Release all

Example: travel booking

  • Try: hold a seat, hold a hotel room, authorize payment.
  • Confirm: issue ticket, confirm hotel, capture payment.
  • Cancel: release seat, release hotel hold, void payment authorization.

API example

POST /inventory/reservations/try
POST /inventory/reservations/{reservationId}/confirm
POST /inventory/reservations/{reservationId}/cancel

Advantages and trade-offs

AdvantagesTrade-offs
Reduces risk of committing one participant while another cannot proceed.Every service must implement reservation semantics.
Clear resource lifecycle.Resources stay locked or reserved during the transaction window.
Good for scarce resources such as seats or inventory.Expired reservations and cleanup jobs are required.
Confirm and cancel can be retried.More APIs, states, storage, and operational complexity.
When to prefer TCC Use it when participants can naturally reserve resources and the business wants a clear prepare/commit model without database-level 2PC.

9. Two-Phase Commit (2PC / XA)

2PC coordinates multiple transactional resources so they commit or rollback together.

Protocol

Phase 1: Prepare
→
All participants vote
→
Phase 2: Commit or rollback

Why it is uncommon in independent microservices

  • Participants hold locks while waiting for the coordinator.
  • Coordinator or network failure can block progress.
  • All resources must support the transaction protocol.
  • It reduces service autonomy and increases infrastructure coupling.
  • Latency and availability are worse than local transactions.

When it may still be reasonable

  • A controlled enterprise environment with a small number of compatible resources.
  • Strong consistency is required and latency is acceptable.
  • The services are not truly independent and share an operational boundary.
  • A legacy integration already uses XA reliably.
Area2PCSaga
ConsistencyAtomic commit across participantsEventual consistency
LocksCan hold locks across resourcesLocal short transactions
AvailabilityLower during coordinator/network failureHigher, but business state may be temporarily inconsistent
RecoveryProtocol-level rollback/commitBusiness compensation and retry
Microservice autonomyLowHigher

10. Kafka Transactions and Exactly-Once Boundaries

Kafka transactions can atomically write records to multiple Kafka partitions and can combine consumed offsets with produced records. This is useful for consume → process → produce pipelines that remain inside Kafka.

Strong use case

Consume OrderCreated
  → transform data
  → produce OrderValidated
  → commit consumed offset and produced record atomically

Boundary limitation

Once processing also updates PostgreSQL, calls a payment gateway, sends email, or invokes another HTTP API, Kafka cannot make those external side effects part of the same atomic transaction.

Interview trap Do not say “Kafka exactly-once means the payment can never be charged twice.” Kafka cannot control the payment provider. You still need an idempotency key, unique business constraints, and safe recovery.

Practical combinations

FlowRecommended protection
Kafka → KafkaKafka transactions may provide a strong processing boundary.
Database → KafkaTransactional Outbox or CDC.
Kafka → DatabaseInbox/idempotent consumer + local transaction.
Kafka → payment providerInbox + provider idempotency key + persisted operation state.

11. Event Sourcing and CQRS

Event Sourcing

Event Sourcing stores domain events as the source of truth. Current state is rebuilt by replaying events. 

OrderCreated
ItemAdded
PaymentAuthorized
InventoryReserved
OrderConfirmed

Advantages

  • Complete audit history.
  • Can rebuild projections and investigate how state changed.
  • Events naturally support integration and temporal analysis.

Trade-offs

  • Event versioning and schema evolution are difficult.
  • Debugging requires event-stream thinking.
  • Replaying side effects must be carefully separated from rebuilding state.
  • It is much more complex than adding an Outbox table.

CQRS

Command Query Responsibility Segregation separates write models from read models. It is often used with event-driven architecture, but it is not itself a transaction pattern.

Relationship Outbox reliably publishes events. Saga coordinates a distributed process. Event Sourcing stores domain history. CQRS separates write and read concerns. These patterns can be combined, but they solve different problems.

12. Locking, Concurrency, and Atomic State Changes

Distributed patterns are useless if one service cannot safely handle two concurrent requests.

Scenario: two requests charge the same payment

Thread A: read payment status = PENDING
Thread B: read payment status = PENDING
Thread A: call provider
Thread B: call provider
Result: customer may be charged twice

Defense layers

  1. Database state transition: atomically change PENDING → PROCESSING.
  2. Unique operation key: one charge operation per order.
  3. Provider idempotency key: repeated calls return the same provider result.
  4. Persist provider request state: recover after timeout.
  5. Reconciliation: compare local state with provider records.

Atomic SQL approach

UPDATE payment
SET status = 'PROCESSING', version = version + 1
WHERE payment_id = :paymentId
  AND status = 'PENDING';

If the affected row count is zero, another request already claimed the work.

Optimistic locking

@Entity
public class Payment {
    @Id
    private String id;

    @Version
    private long version;

    private String status;
}

Pessimistic locking

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p from Payment p where p.id = :id")
Optional<Payment> findByIdForUpdate(@Param("id") String id);
ApproachGood whenRisk
Atomic conditional updateSimple state claim or transitionBusiness logic may need extra reads
Optimistic lockingConflicts are rareRequires retry strategy
Pessimistic lockingConflicts are frequent and transaction is shortLock wait, deadlock, reduced throughput
Distributed lockCross-node coordination without a better data constraintLease expiry and split-brain complexity

13. End-to-End Example: Order, Payment, Inventory, Shipping

Business requirements

  • Create an order.
  • Authorize payment.
  • Reserve inventory.
  • Create shipment.
  • If any later step fails, recover safely.
  • No duplicate payment during retries.

Recommended architecture

Order API
→
Order DB + Outbox
→
Message Broker
→
Saga Orchestrator
Payment Service
Inbox + DB + Outbox
Inventory Service
Inbox + DB + Outbox
Shipping Service
Inbox + DB + Outbox

Happy path

  1. Order Service creates PENDING order and an Outbox event in one transaction.
  2. Outbox publisher sends OrderCreated.
  3. Orchestrator sends AuthorizePayment.
  4. Payment Service deduplicates the command, uses a provider idempotency key, and stores AUTHORIZED.
  5. Payment Service publishes PaymentAuthorized through its Outbox.
  6. Orchestrator sends ReserveInventory.
  7. Inventory Service reserves items and publishes InventoryReserved.
  8. Orchestrator sends CreateShipment.
  9. Shipping Service creates the shipment.
  10. Orchestrator marks the saga completed and Order Service marks the order CONFIRMED.

Failure path: inventory unavailable

  1. Inventory Service publishes InventoryRejected.
  2. Orchestrator sends VoidPaymentAuthorization.
  3. Payment Service safely voids the authorization using an idempotent operation.
  4. Orchestrator sends CancelOrder.
  5. Order Service changes status to CANCELLED.

Timeout path: provider response unknown

This is one of the hardest real production cases.

  1. Payment Service sends an authorization request.
  2. The provider processes it, but the network times out before the response reaches the service.
  3. The service must not assume failure and send a new charge with a different key.
  4. It stores AUTHORIZATION_UNKNOWN and queries the provider using the original idempotency/reference key.
  5. A reconciliation job resolves the final state.
Pattern combination Saga manages the business flow. Outbox protects outgoing messages. Inbox protects consumers. Idempotency protects retries. Local transactions and locking protect each service’s state.

Transactional event creation

@Service
public class OrderApplicationService {
    private final OrderRepository orderRepository;
    private final OutboxRepository outboxRepository;
    private final JsonSerializer jsonSerializer;

    @Transactional
    public String createOrder(CreateOrderCommand command) {
        Order order = Order.create(command);
        orderRepository.save(order);

        EventEnvelope<OrderCreated> event = EventFactory.orderCreated(order);
        outboxRepository.save(OutboxEvent.from(event, jsonSerializer));

        return order.getId();
    }
}

Idempotent command handler

@Service
public class AuthorizePaymentHandler {
    private final ProcessedMessageRepository processedMessageRepository;
    private final PaymentRepository paymentRepository;
    private final OutboxRepository outboxRepository;

    @Transactional
    public void handle(AuthorizePayment command, MessageMetadata metadata) {
        if (!processedMessageRepository.insertIfAbsent(
                "authorize-payment",
                metadata.getMessageId())) {
            return;
        }

        Payment payment = paymentRepository.findOrCreate(command.getOrderId());
        payment.requestAuthorization(command.getAmount());

        outboxRepository.save(
            OutboxEvent.paymentAuthorizationRequested(payment, metadata)
        );
    }
}

Orchestrator state machine idea

public void onPaymentAuthorized(PaymentAuthorized event) {
    OrderSaga saga = sagaRepository.findByOrderId(event.getOrderId());

    if (!saga.canAcceptPaymentAuthorized()) {
        return;
    }

    saga.markPaymentAuthorized();
    commandOutbox.save(new ReserveInventoryCommand(
        saga.getOrderId(),
        saga.getItems(),
        saga.getCorrelationId()
    ));
}

public void onInventoryRejected(InventoryRejected event) {
    OrderSaga saga = sagaRepository.findByOrderId(event.getOrderId());

    saga.markInventoryRejected(event.getReason());
    commandOutbox.save(new VoidPaymentCommand(
        saga.getOrderId(),
        saga.getPaymentReference(),
        saga.getCorrelationId()
    ));
}

Retry with backoff

nextDelay = min(maxDelay, baseDelay * 2^retryCount) + randomJitter;

Jitter prevents many failed messages from retrying at exactly the same time.

Dead-letter handling

A Dead Letter Queue is not the end of the design. Store enough metadata to replay safely: message ID, original topic, partition, offset, exception, stack trace, retry count, correlation ID, and payload version.

15. Pattern Decision Guide

ProblemPrimary patternUsually combined with
DB commit and event publish must not divergeTransactional OutboxInbox and idempotent consumers
Multi-service business flow with compensationSagaOutbox, Inbox, state machine
Reserve scarce resources before final commitTCCTimeout cleanup and idempotency
Atomic commit across compatible controlled resources2PC/XACoordinator monitoring
Complete domain history is the source of truthEvent SourcingCQRS and projections
Duplicate broker messagesInbox/idempotent consumerUnique business constraints
Duplicate HTTP requestsIdempotency keyStored response and unique constraint
Concurrent state updateAtomic SQL / optimistic lockRetry and conflict handling

Simple decision questions

  1. Does one service update its DB and publish a message? Use Outbox.
  2. Can the same command or event arrive twice? Design idempotency and Inbox.
  3. Does the operation cross service boundaries? Consider Saga or TCC.
  4. Can previous steps be semantically reversed? Saga is possible.
  5. Can resources be reserved before final confirmation? TCC may fit.
  6. Do all participants support XA and share one operational boundary? 2PC may be considered.
  7. Is a complete immutable history a core requirement? Consider Event Sourcing carefully.

16. Failure Handling in Production

Classify failures

Failure typeExampleResponse
TransientBroker unavailable, temporary network issueRetry with exponential backoff and jitter
Business rejectionInsufficient stock, card declinedDo not blindly retry; follow compensation/business path
Unknown outcomePayment timeout after provider may have processed requestQuery status using same reference; reconcile
Permanent technicalInvalid schema, unsupported event versionDLQ, alert, fix, replay
Poison messageAlways crashes the consumerStop infinite retry; isolate and inspect

Timeout management

Every saga waiting state should have a deadline.

PAYMENT_PENDING until 2026-07-17T10:00:00Z
INVENTORY_PENDING until 2026-07-17T10:02:00Z
SHIPMENT_PENDING until 2026-07-17T10:05:00Z

A scheduler scans expired states and starts a defined recovery action.

Ordering

Global ordering is expensive and usually unnecessary. Preserve ordering per aggregate, such as one order ID, by using the aggregate ID as the message partition key.

Reconciliation

Reconciliation compares systems and repairs mismatches. It is essential for payments and other external providers.

  • Compare local payment status with provider settlement records.
  • Find orders stuck in pending states.
  • Find published events without expected downstream results.
  • Generate repair commands or manual operation tasks.
Senior mindset Do not design only the happy path. Design the restart path, duplicate path, timeout path, compensation-failure path, and manual-repair path.

17. Observability and Testing

Important identifiers

  • Correlation ID: one business transaction across services.
  • Message ID: one event or command.
  • Causation ID: which message caused the current message.
  • Saga ID: one workflow instance.
  • Aggregate ID: domain entity such as Order ID.

Useful metrics

Outbox

Pending count, oldest pending age, publish latency, retry count.

Saga

Active count, duration, timeout count, compensation count, stuck state count.

Consumer

Lag, duplicate count, processing latency, DLQ rate, failure rate.

Testing pyramid

  1. Unit tests: state transitions, compensation decisions, idempotent behavior.
  2. Repository tests: unique constraints, locking, transaction rollback.
  3. Contract tests: event schemas and API behavior.
  4. Integration tests: database + broker + consumer.
  5. Failure injection: crash after publish, timeout before acknowledgement, duplicate delivery.
  6. End-to-end tests: happy path and compensation path.

Critical failure test cases

  • Crash after DB commit but before event publication.
  • Crash after broker publish but before outbox status update.
  • Duplicate event arrives while first processing is still running.
  • Compensation command is delivered twice.
  • Provider times out after processing the request.
  • Saga orchestrator restarts in the middle of the workflow.
  • Out-of-order events arrive for the same aggregate.
  • DLQ message is replayed after the code is fixed.

18. Common Anti-Patterns

1. Calling Kafka directly after a database save

This creates the dual-write problem. Use Outbox or another atomic integration strategy.

2. Assuming retry is always safe

Retrying a charge, shipment creation, or email can duplicate a side effect. Add idempotency before retry.

3. Treating compensation as delete

A real business action may already be visible externally. Record a new compensating operation and keep audit history.

4. Keeping a DB transaction open during an external API call

This increases lock time and failure coupling. Persist intent, commit, then execute the remote operation through a durable workflow when possible.

5. Building a Saga without persisted state

In-memory workflow state is lost on restart. Store saga state durably and make transitions idempotent.

6. Using distributed locks as the first solution

Prefer database constraints, atomic state transitions, partitioning, or idempotency. Distributed locks add lease and failure complexity.

7. Sending sensitive private data in events

Events are copied into brokers, logs, retries, and archives. Publish only needed data, encrypt where required, and apply retention controls.

8. No reconciliation process

External systems can always create unknown outcomes. Payment systems especially require periodic reconciliation and manual repair support.

1. Why does @Transactional not solve a transaction across microservices?

Senior answer: @Transactional normally controls one local transaction manager, such as one relational database connection. A REST call, Kafka publish, payment provider, or another service database is outside that boundary. Once another service commits, the caller cannot rollback it with a local exception. For cross-service consistency, I use local transactions combined with patterns such as Outbox, Saga, TCC, and idempotent consumers.

2. What problem does the Outbox Pattern solve?

Senior answer: Outbox solves the dual-write problem between a service database and a message broker. I save the business change and an outgoing event in the same local database transaction. A separate publisher or CDC process sends the event later. If the business transaction commits, the event is durable. However, publication is normally at least once, so consumers must still be idempotent.

3. Can Outbox guarantee exactly-once processing?

Senior answer: Not by itself. The publisher can crash after sending the message but before marking the row as published, so the message can be sent again. Outbox gives reliable publication, usually at least once. Exactly-once business behavior requires idempotent consumers, unique constraints, stable business keys, and safe external API handling.

4. What is the difference between Outbox and Saga?

Senior answer: Outbox handles reliable message publication from one service. Saga manages a multi-service business transaction and decides the next step or compensation. They are commonly used together: Saga controls the workflow, while Outbox ensures saga commands and events are not lost.

5. Choreography or orchestration: which would you choose?

Senior answer: I choose based on flow complexity. Choreography is good for a small number of stable event reactions. For branching, timeout, manual review, long-running steps, or complex compensation, I prefer orchestration because the workflow state and decision logic are visible. I also avoid putting all domain logic into the orchestrator; participants still own their domain rules.

6. What makes a good compensating transaction?

Senior answer: It must be a valid business operation, idempotent, auditable, and retryable. It should represent the real reverse action, such as refund instead of deleting a payment row. I also design states for compensation progress and failure because compensation itself may fail.

7. How would you prevent duplicate payment when messages are retried?

Senior answer: I use multiple layers: an Inbox table for message deduplication, a unique database constraint for one payment operation per order, an atomic state transition from PENDING to PROCESSING, and the payment provider’s idempotency key. I also persist the provider request reference so a timeout can be reconciled instead of creating a new charge.

8. What is the Inbox Pattern?

Senior answer: Inbox stores the processed message ID in the same local transaction as the consumer’s business update. A unique key prevents processing the same message twice. It is the consumer-side partner of Outbox.

9. When would you use TCC instead of Saga?

Senior answer: I use TCC when participants can naturally reserve resources before final confirmation, such as seats, rooms, or inventory. Try reserves, Confirm finalizes, and Cancel releases. It gives a clearer reservation model than a normal Saga, but each participant must support extra lifecycle states and timeout cleanup.

10. Why is 2PC often avoided in microservices?

Senior answer: 2PC increases coupling, requires compatible transactional resources, may hold locks while waiting for the coordinator, and can reduce availability during failures. It can be valid in controlled enterprise systems, but for independent services I usually prefer local transactions and eventual consistency.

11. How do Kafka transactions help, and where do they stop helping?

Senior answer: Kafka transactions are strong for consume-process-produce flows inside Kafka because produced records and consumed offsets can commit together. They do not make PostgreSQL updates, REST calls, payment operations, or emails atomic with Kafka. For those boundaries, I still use Outbox, Inbox, and idempotency.

12. How do you handle an unknown payment outcome after timeout?

Senior answer: I do not immediately retry with a new request ID because the provider may already have charged the customer. I store an UNKNOWN or PENDING_CONFIRMATION state, keep the original idempotency/reference key, query the provider, and run reconciliation. The system should only retry the same logical operation with the same idempotency identity.

13. How would you design retry?

Senior answer: First I classify the failure. Transient technical failures can use exponential backoff and jitter. Business rejections should not be retried blindly. Unknown outcomes need status inquiry. Permanent schema or validation errors go to a DLQ. Every retried operation must be idempotent, and retries need maximum attempts, observability, and a manual recovery path.

14. What data should a saga orchestrator persist?

Senior answer: Saga ID, business aggregate ID, current state, participant results, correlation ID, retry counters, deadlines, last error, compensation progress, and version for concurrency control. This state must be durable so the orchestrator can restart safely.

15. How do you preserve event ordering?

Senior answer: I avoid requiring global ordering. I partition by aggregate ID to preserve order for one entity, include aggregate version numbers, reject or delay stale events, and make handlers idempotent. If strict ordering is a hard business requirement, I document its throughput and availability cost.

16. How do you prevent two requests from executing the same operation?

Senior answer: I prefer data-level guarantees: unique constraints, atomic conditional updates, optimistic locking, or short pessimistic locks. For external APIs I add a stable idempotency key. A distributed lock is not my first choice because it adds lease and failure complexity and still does not replace database constraints.

17. What is eventual consistency, and how do you explain it to business users?

Senior answer: It means different services may temporarily show different states while the workflow is still running, but the system has a defined path to converge. I expose clear statuses such as PAYMENT_PENDING or CANCELLATION_IN_PROGRESS instead of pretending the operation finished immediately. I also define expected completion time and recovery behavior.

18. How do you test an Outbox implementation?

Senior answer: I test transaction atomicity, publisher retry, duplicate publication, crash after send but before status update, concurrent publishers, stale lock recovery, payload versioning, and consumer idempotency. I also monitor oldest pending row age because a growing age is a production failure signal.

19. What is the biggest mistake when implementing Saga?

Senior answer: Designing only the successful sequence. A correct Saga must define compensation, compensation failure, timeout, duplicate message, out-of-order message, orchestrator restart, and manual repair. Without these paths, it is only a distributed happy-path script.

20. Describe a production-ready transaction strategy for an order system.

Senior answer: I would use local ACID transactions in each service, Outbox for reliable event publication, Inbox and unique business keys for duplicate protection, an orchestrated Saga for payment-inventory-shipping flow, idempotency keys for payment and carrier APIs, optimistic or atomic state transitions for concurrency, deadlines and retries for transient failures, DLQ for poison messages, and reconciliation for unknown external outcomes. I would also add correlation IDs, saga metrics, pending-age alerts, and replay tooling.

Best senior summary

Use the right pattern for the right boundary Local transaction protects one database. Outbox protects outgoing messages. Inbox and idempotency protect retries. Saga or TCC manages the multi-service business flow. Reconciliation repairs unknown external outcomes. Observability makes the entire process operable.

Production checklist

  • Every external side effect has an idempotency strategy.
  • Every waiting state has a timeout.
  • Every compensation can be retried safely.
  • Every message has a stable ID and correlation ID.
  • Every consumer has duplicate protection.
  • Every Outbox has pending-age monitoring.
  • Every DLQ has a review and replay procedure.
  • Every external provider has reconciliation.
  • Every state transition is concurrency-safe.
  • Every workflow can recover after restart.
