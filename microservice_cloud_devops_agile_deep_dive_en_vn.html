1. Big Picture

These topics are connected. Microservices define how we split systems. Cloud provides scalable infrastructure. DevOps and CI/CD define how we build, test, deploy, monitor, and operate software. Agile/Scrum defines how teams deliver value iteratively.

Business Requirement ↓ Agile/Scrum planning, refinement, estimation ↓ Microservice design: service boundary, API, data ownership ↓ Implementation: Java / Spring Boot / SQL / Messaging ↓ CI: build, unit test, integration test, code quality, security scan ↓ CD: Docker image, registry, Kubernetes deployment, DB migration ↓ Cloud runtime: load balancer, autoscaling, observability, reliability ↓ Feedback: monitoring, incidents, retrospectives, continuous improvement

Microservice

Architecture style that structures a system as independently deployable services built around business capabilities.

Cloud / DevOps

Infrastructure and culture to deliver reliable software frequently through automation, monitoring, and shared ownership.

Agile / Scrum

Ways of working that help teams inspect, adapt, and deliver valuable increments continuously.

Senior mindset: Do not explain these topics separately only by definition. Connect them to real delivery: requirements, architecture, code, testing, deployment, monitoring, incidents, and continuous improvement.

2. Microservice Basics

What is Microservice?

Microservice is an architectural style where a large application is built as a set of small services. Each service usually owns a specific business capability, runs in its own process, communicates through lightweight protocols, and can be deployed independently.

CharacteristicMeaningExample
Business capabilityService is aligned with a business area.Order Service, Payment Service, Inventory Service.
Independent deploymentService can be built and released without deploying the whole system.Deploy Payment Service without redeploying Catalog Service.
Decentralized dataEach service owns its data and schema.Order DB is not directly updated by Payment Service.
Lightweight communicationServices communicate through REST, gRPC, messaging, events.Order calls Payment API or publishes OrderCreated event.
Fault isolationFailure in one service should not bring down the whole system.Payment timeout should not crash Order Service.

Monolith vs Microservice

MonolithMicroservice
One deployable application.Many independently deployable services.
Simple to start, test, and deploy at small scale.More operational complexity.
Shared database is common.Database per service is preferred.
Strong local transactions are easier.Distributed consistency is harder.
Scaling is usually all-or-nothing.Each service can scale independently.
Important: Microservice is not always better. If the team is small, domain is unclear, or operational maturity is low, a modular monolith may be better than distributed complexity.

Typical Microservice Components

Client / Frontend ↓ API Gateway ↓ Service A ── Database A Service B ── Database B Service C ── Database C ↓ Message Broker / Event Bus ↓ Observability: Logs, Metrics, Traces ↓ CI/CD + Container Platform

Common Communication Styles

StyleWhen to UseRisk
RESTSimple synchronous request/response, public APIs.Timeouts, tight runtime dependency, versioning issues.
gRPCLow-latency internal communication, strongly typed contracts.Less human-readable, gateway/browser support needs planning.
MessagingAsynchronous workflows, event-driven integration.Eventual consistency, duplicate messages, ordering issues.
Event streamingHigh-throughput event pipelines, audit/event history.Schema evolution and consumer compatibility.

3. Microservice Advanced Topics

Service Boundary and Bounded Context

The hardest part of microservices is not creating many Spring Boot apps. The hardest part is choosing the right boundaries. A good service boundary usually follows a business capability and owns its data.

Good Boundary

High cohesion inside service, low coupling with other services, owns business rules and data.

Bad Boundary

Split by technical layer such as User Controller Service, User Repository Service, or Shared Database Service.

Database per Service

Each service should own its database schema. Other services should not directly read/write its tables.

Order Service ── owns ── order_db Payment Service ── owns ── payment_db Inventory Service ── owns ── inventory_db Order Service should not directly update payment_db. Payment Service should not directly update order_db.

Distributed Transaction Problem

In a monolith, a single database transaction can update many tables. In microservices, data is distributed, so one local transaction cannot safely update multiple services.

Saga Pattern

Create Order ↓ Reserve Stock ↓ Charge Payment ↓ Confirm Order If payment fails: ↓ Cancel Stock Reservation ↓ Cancel Order
Saga TypeHow it worksPros / Cons
ChoreographyServices publish/consume events without a central coordinator.Loose coupling, but flow can become hard to understand.
OrchestrationA central orchestrator commands each step.Clear process visibility, but orchestrator can become complex.

Transactional Outbox Pattern

The transactional outbox pattern solves the problem of updating database and publishing event atomically. Instead of publishing directly to broker inside business logic, service writes an outbox record in the same local DB transaction. A background publisher later sends it to message broker.

Business Transaction: 1. Insert order 2. Insert outbox_event(OrderCreated) 3. Commit DB transaction Background Publisher: 4. Read unprocessed outbox_event 5. Publish to Kafka/RabbitMQ 6. Mark event as published
CREATE TABLE outbox_event (
    id UUID PRIMARY KEY,
    aggregate_type VARCHAR(100) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,
    event_type VARCHAR(100) NOT NULL,
    payload JSONB NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL,
    published_at TIMESTAMP NULL
);

Idempotency

In distributed systems, clients may retry and messages may be delivered more than once. Idempotency means repeating the same operation produces the same final result. 

POST /api/payments
Idempotency-Key: 0cfa0e5a-4e7d-43ab-b7b4-2e77c9e9f123

{
  "orderId": "ORD-1001",
  "amount": 100.00
}

Resilience Patterns

PatternPurposeExample
TimeoutAvoid waiting forever.Payment API timeout after 2 seconds.
RetryRecover from temporary failures.Retry 3 times for network error, not for validation error.
Circuit BreakerStop calling unhealthy dependency temporarily.Open circuit when Payment Service failure rate is high.
BulkheadIsolate resources to prevent cascading failures.Separate thread pool for payment and inventory calls.
Rate LimitingProtect service from overload.Limit login API or public search API.

Observability

In microservices, debugging is difficult without observability. Senior engineers should understand logs, metrics, and traces.

PillarWhat it answersExample
LogsWhat happened?Structured JSON logs with requestId/correlationId.
MetricsHow often and how much?Request latency, error rate, CPU, memory, queue lag.
TracesWhere did time go across services?Distributed tracing with traceId/spanId.

Microservice Anti-Patterns

  • Distributed monolith: many services but tightly coupled deployment and shared data.
  • Shared database between services.
  • Too many synchronous calls in a single user request.
  • No service ownership.
  • No observability.
  • No automated deployment.
  • Splitting services before understanding domain boundaries.

Docker Basics

Docker packages an application and its runtime dependencies into an image. A container is a running instance of an image.

# Build image
docker build -t order-service:1.0.0 .

# Run container
docker run -p 8080:8080 order-service:1.0.0

# Push image
docker tag order-service:1.0.0 registry.example.com/order-service:1.0.0
docker push registry.example.com/order-service:1.0.0

5. DevOps Fundamentals

What is DevOps?

DevOps is a culture and set of practices that brings development and operations together to deliver software faster, safer, and more reliably through automation, feedback, and shared ownership.

DevOps Core Ideas

IdeaMeaningExample
AutomationAutomate repeatable tasks.Build, test, scan, package, deploy automatically.
CI/CDContinuously integrate and deliver changes.Every PR runs tests; merge to main deploys to staging.
Infrastructure as CodeManage infrastructure by versioned code.Terraform, CloudFormation, Kubernetes YAML, Helm.
ObservabilityMeasure system health and behavior.Logs, metrics, traces, dashboards, alerts.
Shift LeftFind issues earlier in development.Unit tests, static analysis, dependency scanning in CI.
Shared ResponsibilityDev team also cares about running software.You build it, you run it.

DevOps for Java Backend

Developer pushes code ↓ CI: - Compile Java - Unit tests - Integration tests - Static analysis - Security/dependency scan - Build Docker image ↓ CD: - Push image to registry - Run DB migration - Deploy to Kubernetes - Smoke test - Monitor logs/metrics ↓ Operate: - Alerts - Incident response - Rollback / roll forward - Postmortem

6. CI/CD Pipeline

CI vs CD

TermMeaningExample
Continuous IntegrationFrequently merge code and automatically verify it.Every PR runs build, tests, lint, Sonar, security scan.
Continuous DeliveryApplication is always ready to deploy, but production release may need approval.Main branch deploys to staging automatically; production needs manual approval.
Continuous DeploymentEvery verified change is automatically deployed to production.Merge to main automatically deploys to production.

Typical Pipeline Stages

1. Checkout code 2. Setup JDK / Node / build tools 3. Restore dependency cache 4. Compile 5. Unit tests 6. Integration tests 7. Static analysis / SonarQube 8. Dependency vulnerability scan 9. Build artifact / jar 10. Build Docker image 11. Push image to registry 12. Run DB migration 13. Deploy to environment 14. Smoke test 15. Notify team 16. Monitor release

Quality Gates

  • Build must pass.
  • Unit tests and integration tests must pass.
  • Code coverage should be meaningful, not blindly 100%.
  • No critical/high vulnerabilities.
  • Sonar quality gate passed.
  • Docker image scan passed.
  • Database migration tested.
  • Smoke test passed after deployment.

Deployment Strategies

StrategyHow it worksProsRisk
Rolling UpdateGradually replace old pods with new pods.Simple and common in Kubernetes.Old and new versions run together; compatibility matters.
Blue/GreenRun blue and green environments; switch traffic.Fast rollback by switching back.Higher infrastructure cost.
CanaryRelease to small percentage first, then increase traffic.Lower risk for production releases.Needs advanced routing and monitoring.
Feature FlagDeploy code but control feature visibility by config.Separate deploy from release.Flag cleanup and complexity.

7. Concrete CI/CD Examples

Example 1: GitHub Actions for Spring Boot + Docker + Kubernetes

name: order-service-ci-cd

on:
  pull_request:
    branches: [ "main" ]
  push:
    branches: [ "main" ]

env:
  IMAGE_NAME: ghcr.io/my-org/order-service
  JAVA_VERSION: "21"

jobs:
  build-test-scan:
    runs-on: ubuntu-latest

    permissions:
      contents: read
      packages: write
      security-events: write

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Java
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: ${{ env.JAVA_VERSION }}
          cache: gradle

      - name: Build and test
        run: ./gradlew clean test

      - name: Run integration tests
        run: ./gradlew integrationTest

      - name: Build jar
        run: ./gradlew bootJar

      - name: Login to container registry
        if: github.event_name == 'push'
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build Docker image
        run: |
          docker build \
            -t $IMAGE_NAME:${{ github.sha }} \
            -t $IMAGE_NAME:latest .

      - name: Push Docker image
        if: github.event_name == 'push'
        run: |
          docker push $IMAGE_NAME:${{ github.sha }}
          docker push $IMAGE_NAME:latest

  deploy-staging:
    needs: build-test-scan
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    environment: staging

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Configure kubeconfig
        run: |
          mkdir -p ~/.kube
          echo "${{ secrets.KUBE_CONFIG_STAGING }}" > ~/.kube/config

      - name: Deploy to Kubernetes
        run: |
          kubectl set image deployment/order-service \
            order-service=$IMAGE_NAME:${{ github.sha }} \
            -n staging

          kubectl rollout status deployment/order-service -n staging

      - name: Smoke test
        run: |
          curl -f https://staging-api.example.com/order-service/actuator/health

Example 2: Jenkins Declarative Pipeline

pipeline {
    agent any

    environment {
        IMAGE_NAME = 'registry.example.com/order-service'
        IMAGE_TAG = "${env.GIT_COMMIT}"
        JAVA_HOME = tool 'jdk-21'
    }

    stages {
        stage('Checkout') {
            steps {
                checkout scm
            }
        }

        stage('Build & Unit Test') {
            steps {
                sh './gradlew clean test'
            }
            post {
                always {
                    junit 'build/test-results/test/*.xml'
                }
            }
        }

        stage('Integration Test') {
            steps {
                sh './gradlew integrationTest'
            }
        }

        stage('SonarQube Analysis') {
            steps {
                withSonarQubeEnv('sonarqube') {
                    sh './gradlew sonar'
                }
            }
        }

        stage('Quality Gate') {
            steps {
                timeout(time: 5, unit: 'MINUTES') {
                    waitForQualityGate abortPipeline: true
                }
            }
        }

        stage('Build Docker Image') {
            steps {
                sh "docker build -t ${IMAGE_NAME}:${IMAGE_TAG} ."
            }
        }

        stage('Deploy Staging') {
            when {
                branch 'main'
            }
            steps {
                sh "kubectl set image deployment/order-service order-service=${IMAGE_NAME}:${IMAGE_TAG} -n staging"
                sh "kubectl rollout status deployment/order-service -n staging"
            }
        }
    }

    post {
        success { echo 'Pipeline succeeded' }
        failure { echo 'Pipeline failed' }
    }
}

8. CI/CD for SQL and Database Migration

Why SQL Migration Matters in CI/CD

Application deployment and database schema changes must be coordinated. A bad SQL migration can break production even if Java code is correct.

Database Migration Tools

ToolHow it worksCommon File Style
FlywayVersioned SQL migrations. Tracks executed scripts in schema history table.V1__create_table.sql, V2__add_column.sql
LiquibaseChangelog-based migrations in XML/YAML/JSON/SQL.db.changelog-master.yaml

Flyway Migration Example

V1__create_order_table.sql

CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    order_no VARCHAR(50) NOT NULL UNIQUE,
    customer_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    total_amount NUMERIC(18, 2) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_orders_customer_id ON orders(customer_id);
CREATE INDEX idx_orders_status ON orders(status);

V2__add_payment_status.sql

ALTER TABLE orders
ADD COLUMN payment_status VARCHAR(30);

UPDATE orders
SET payment_status = 'PENDING'
WHERE payment_status IS NULL;

ALTER TABLE orders
ALTER COLUMN payment_status SET NOT NULL;
Production warning: Adding a NOT NULL column with default to a huge table can lock or rewrite data depending on DB. For large tables, use expand-contract migration with multiple releases.

Expand-Contract Pattern

Release 1 - Expand: Add nullable column / new table / new index Application writes both old and new fields if needed Release 2 - Migrate: Backfill data safely in batches Application reads from new field Release 3 - Contract: Remove old column / old table only after no code uses it

Example: Safe Column Rename

ReleaseDB ChangeApplication Change
R1 ExpandAdd new column customer_full_name nullable.Write both customer_name and customer_full_name.
R2 BackfillBackfill old data in batches.Read from new column, fallback to old column.
R3 ContractDrop old column customer_name.Remove fallback code.

SQL Migration in GitHub Actions

jobs:
  migrate-staging-db:
    runs-on: ubuntu-latest
    environment: staging

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Java
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"

      - name: Run Flyway migration
        env:
          FLYWAY_URL: jdbc:postgresql://${{ secrets.DB_HOST }}:5432/orderdb
          FLYWAY_USER: ${{ secrets.DB_USER }}
          FLYWAY_PASSWORD: ${{ secrets.DB_PASSWORD }}
        run: |
          ./gradlew flywayInfo
          ./gradlew flywayMigrate

SQL Review Checklist

  • Is migration backward compatible with old application version?
  • Can it run safely on production data volume?
  • Does it create locks for too long?
  • Are indexes created for new query patterns?
  • Is backfill done in batches if table is large?
  • Is rollback or roll-forward strategy defined?
  • Was migration tested on staging with production-like data?
  • Are destructive changes separated into later release?
  • Is migration idempotent where needed?
  • Are DB credentials stored in CI secrets, not in repository?

Rollback Strategy for DB

Change TypeRollback Approach
Add table/column/indexUsually safe to leave. Roll back application only.
Drop column/tableDangerous. Avoid in same release. Use contract phase later.
Data transformationNeed backup or reverse script, but roll-forward is often safer.
Constraint addedValidate data first, add constraint after data is clean.

10. Soft Skills for Senior Backend Engineers

Communication

Senior engineers must explain complex technical issues clearly to developers, QA, PM, clients, and non-technical stakeholders.

Good communication pattern

Context:
Payment API is failing intermittently in staging.

Impact:
Order creation sometimes remains in PENDING status.

Root Cause:
The external PSP timeout is lower than our retry window.

Solution:
Adjust timeout/retry policy, add idempotency key, and improve error mapping.

Next Action:
I will prepare a fix and add integration test for timeout scenario.

Code Review

  • Check correctness and edge cases.
  • Check readability and maintainability.
  • Check transaction boundaries and error handling.
  • Check performance and database query impact.
  • Check security: validation, authorization, sensitive data.
  • Check tests: meaningful unit/integration cases.
  • Give comments respectfully and explain why.

Mentoring

Mentoring is not only giving answers. It means helping others build reasoning ability.

SituationSenior Response
Junior asks how to fix a bug.Ask what they observed, guide them to logs, reproduce together, then explain root cause.
PR has poor design.Explain trade-off and propose a simpler design instead of only saying “wrong”.
Team repeats same mistake.Create guideline, checklist, or small knowledge sharing session.

Handling Conflict

Good response:
"I understand why you prefer option A because it is faster to implement.
My concern is that it creates coupling between Order and Payment database.
Can we compare both options against delivery time, maintainability, and failure handling?"

Production Incident Communication

1. Acknowledge issue.
2. State impact.
3. Share current hypothesis.
4. Assign owner.
5. Give next update time.
6. After fix, write postmortem:
   - Timeline
   - Root cause
   - What worked
   - What failed
   - Prevention actions

11. Senior Interview Answers — English

Microservice Answer

Microservice is an architectural style where a system is split into small, independently deployable services aligned with business capabilities. Each service should own its data and expose behavior through APIs or events. The benefit is independent deployment, scalability, and team autonomy, but the trade-off is higher operational complexity, distributed transactions, network failures, data consistency, and observability requirements. In production, I pay special attention to service boundaries, database ownership, API versioning, resilience patterns like timeout/retry/circuit breaker, idempotency, saga, transactional outbox, and monitoring with logs, metrics, and traces.

DevOps / CI/CD Answer

CI/CD is the automation pipeline that verifies and delivers software safely. In CI, every change should be built, tested, scanned, and validated through quality gates. In CD, the artifact should be packaged as a Docker image, pushed to a registry, deployed to an environment such as Kubernetes, smoke-tested, and monitored. For database changes, I prefer versioned migrations with Flyway or Liquibase and backward-compatible expand-contract migration. A senior engineer should not only know how to deploy, but also understand rollback, health checks, secrets management, deployment strategies like rolling/blue-green/canary, and observability after release.

Agile / Scrum / Soft Skills Answer

Agile is about delivering value iteratively and adapting based on feedback. Scrum provides roles, events, and artifacts to support that. As a senior engineer, I contribute not only by coding but also by clarifying requirements, identifying technical risks, breaking down stories, improving estimates, mentoring teammates, reviewing code, communicating blockers early, and helping the team improve through retrospectives. I try to explain technical trade-offs clearly to both technical and non-technical stakeholders and take ownership from design to production support.

13. Microservice cơ bản

Microservice là gì?

Microservice là architectural style trong đó một hệ thống lớn được xây thành nhiều service nhỏ. Mỗi service thường phụ trách một business capability, chạy trong process riêng, giao tiếp qua REST/gRPC/message, và có thể deploy độc lập.

Đặc điểmÝ nghĩaVí dụ
Business capabilityService align với một business area.Order Service, Payment Service, Inventory Service.
Independent deploymentService có thể build/release độc lập.Deploy Payment Service mà không cần redeploy Catalog Service.
Decentralized dataMỗi service sở hữu data/schema riêng.Payment Service không update trực tiếp DB của Order Service.
Lightweight communicationService giao tiếp qua REST, gRPC, messaging, events.Order gọi Payment API hoặc publish OrderCreated event.
Fault isolationLỗi ở một service không nên làm sập toàn hệ thống.Payment timeout không được crash Order Service.

Monolith vs Microservice

MonolithMicroservice
Một deployable application.Nhiều service deploy độc lập.
Dễ bắt đầu, test, deploy khi hệ thống nhỏ.Operational complexity cao hơn.
Thường dùng shared database.Ưu tiên database per service.
Local transaction dễ hơn.Distributed consistency khó hơn.
Scale thường theo toàn bộ app.Mỗi service scale độc lập.
Quan trọng: Microservice không phải lúc nào cũng tốt hơn. Nếu team nhỏ, domain chưa rõ, hoặc vận hành chưa mature, modular monolith có thể tốt hơn distributed complexity.

14. Microservice nâng cao

Service Boundary và Bounded Context

Khó nhất của microservice không phải là tạo nhiều Spring Boot apps. Khó nhất là chia boundary đúng. Boundary tốt thường đi theo business capability và sở hữu data riêng.

Boundary tốt

High cohesion bên trong service, low coupling với service khác, own business rules và data.

Boundary xấu

Chia theo technical layer như User Controller Service, User Repository Service, Shared Database Service.

Database per Service

Order Service ── owns ── order_db Payment Service ── owns ── payment_db Inventory Service ── owns ── inventory_db Order Service không update trực tiếp payment_db. Payment Service không update trực tiếp order_db.

Distributed Transaction Problem

Trong monolith, một database transaction có thể update nhiều table. Trong microservices, data phân tán, nên một local transaction không thể update an toàn nhiều service.

Saga Pattern

Create Order ↓ Reserve Stock ↓ Charge Payment ↓ Confirm Order Nếu payment fail: ↓ Cancel Stock Reservation ↓ Cancel Order

Transactional Outbox Pattern

Transactional outbox giải quyết vấn đề update database và publish event atomically. Service ghi event vào outbox table trong cùng local DB transaction. Background publisher đọc outbox và publish ra broker. 

CREATE TABLE outbox_event (
    id UUID PRIMARY KEY,
    aggregate_type VARCHAR(100) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,
    event_type VARCHAR(100) NOT NULL,
    payload JSONB NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL,
    published_at TIMESTAMP NULL
);

Idempotency

Trong distributed system, client có thể retry và message có thể được deliver nhiều lần. Idempotency nghĩa là gọi lại cùng operation nhiều lần vẫn cho cùng kết quả cuối. 

POST /api/payments
Idempotency-Key: 0cfa0e5a-4e7d-43ab-b7b4-2e77c9e9f123

{
  "orderId": "ORD-1001",
  "amount": 100.00
}

Resilience Patterns

PatternMục đíchVí dụ
TimeoutTránh chờ mãi.Payment API timeout sau 2 giây.
RetryRecover từ temporary failure.Retry 3 lần cho network error, không retry validation error.
Circuit BreakerDừng gọi dependency đang lỗi tạm thời.Open circuit khi Payment Service failure rate cao.
BulkheadCô lập resource để tránh cascading failure.Thread pool riêng cho payment và inventory calls.
Rate LimitingBảo vệ service khỏi overload.Limit login API hoặc public search API.

Observability

PillarTrả lời câu hỏiVí dụ
LogsChuyện gì đã xảy ra?Structured JSON logs với requestId/correlationId.
MetricsXảy ra bao nhiêu lần, mức độ thế nào?Latency, error rate, CPU, memory, queue lag.
TracesThời gian mất ở service nào?Distributed tracing với traceId/spanId.

18. Ví dụ CI/CD cụ thể

Ví dụ 1: GitHub Actions cho Spring Boot + Docker + Kubernetes

name: order-service-ci-cd

on:
  pull_request:
    branches: [ "main" ]
  push:
    branches: [ "main" ]

env:
  IMAGE_NAME: ghcr.io/my-org/order-service
  JAVA_VERSION: "21"

jobs:
  build-test-scan:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Java
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: ${{ env.JAVA_VERSION }}
          cache: gradle

      - name: Build and test
        run: ./gradlew clean test

      - name: Build jar
        run: ./gradlew bootJar

      - name: Build Docker image
        run: |
          docker build \
            -t $IMAGE_NAME:${{ github.sha }} \
            -t $IMAGE_NAME:latest .

  deploy-staging:
    needs: build-test-scan
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    environment: staging

    steps:
      - name: Deploy to Kubernetes
        run: |
          kubectl set image deployment/order-service \
            order-service=$IMAGE_NAME:${{ github.sha }} \
            -n staging

          kubectl rollout status deployment/order-service -n staging

Ví dụ 2: Jenkins Declarative Pipeline

pipeline {
    agent any

    environment {
        IMAGE_NAME = 'registry.example.com/order-service'
        IMAGE_TAG = "${env.GIT_COMMIT}"
    }

    stages {
        stage('Build & Unit Test') {
            steps {
                sh './gradlew clean test'
            }
            post {
                always {
                    junit 'build/test-results/test/*.xml'
                }
            }
        }

        stage('SonarQube Analysis') {
            steps {
                withSonarQubeEnv('sonarqube') {
                    sh './gradlew sonar'
                }
            }
        }

        stage('Build Docker Image') {
            steps {
                sh "docker build -t ${IMAGE_NAME}:${IMAGE_TAG} ."
            }
        }

        stage('Deploy Staging') {
            when {
                branch 'main'
            }
            steps {
                sh "kubectl set image deployment/order-service order-service=${IMAGE_NAME}:${IMAGE_TAG} -n staging"
                sh "kubectl rollout status deployment/order-service -n staging"
            }
        }
    }
}

19. CI/CD cho SQL và Database Migration

Vì sao SQL migration quan trọng?

Application deployment và database schema changes phải được coordinate. Một SQL migration sai có thể làm production lỗi dù Java code đúng.

Flyway Migration Example

V1__create_order_table.sql

CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    order_no VARCHAR(50) NOT NULL UNIQUE,
    customer_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    total_amount NUMERIC(18, 2) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_orders_customer_id ON orders(customer_id);
CREATE INDEX idx_orders_status ON orders(status);

V2__add_payment_status.sql

ALTER TABLE orders
ADD COLUMN payment_status VARCHAR(30);

UPDATE orders
SET payment_status = 'PENDING'
WHERE payment_status IS NULL;

ALTER TABLE orders
ALTER COLUMN payment_status SET NOT NULL;
Cảnh báo production: Add NOT NULL column hoặc default vào table lớn có thể lock/rewrite data tùy DB. Với table lớn, nên dùng expand-contract migration qua nhiều release.

Expand-Contract Pattern

Release 1 - Expand: Add nullable column / new table / new index App ghi cả field cũ và mới nếu cần Release 2 - Migrate: Backfill data theo batch App đọc từ field mới Release 3 - Contract: Xóa column/table cũ sau khi chắc chắn không còn code dùng

SQL migration trong GitHub Actions

jobs:
  migrate-staging-db:
    runs-on: ubuntu-latest
    environment: staging

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Java
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"

      - name: Run Flyway migration
        env:
          FLYWAY_URL: jdbc:postgresql://${{ secrets.DB_HOST }}:5432/orderdb
          FLYWAY_USER: ${{ secrets.DB_USER }}
          FLYWAY_PASSWORD: ${{ secrets.DB_PASSWORD }}
        run: |
          ./gradlew flywayInfo
          ./gradlew flywayMigrate

Checklist review SQL migration

  • Migration có backward compatible với app version cũ không?
  • Có chạy an toàn trên production data volume không?
  • Có lock table quá lâu không?
  • Có index cho query pattern mới không?
  • Backfill có chạy theo batch nếu table lớn không?
  • Có rollback hoặc roll-forward strategy không?
  • Đã test ở staging với data gần production chưa?
  • Destructive changes có tách sang release sau chưa?
  • DB credentials có lưu trong CI secrets không?

21. Soft Skills cho Senior Backend Engineer

Communication

Senior engineer cần giải thích vấn đề kỹ thuật phức tạp cho dev, QA, PM, client và non-technical stakeholders. 

Context:
Payment API đang fail intermittent ở staging.

Impact:
Order creation đôi khi bị kẹt ở PENDING.

Root Cause:
External PSP timeout thấp hơn retry window của mình.

Solution:
Adjust timeout/retry policy, add idempotency key, improve error mapping.

Next Action:
Em sẽ chuẩn bị fix và thêm integration test cho timeout scenario.

Code Review

  • Check correctness và edge cases.
  • Check readability và maintainability.
  • Check transaction boundaries và error handling.
  • Check performance và database query impact.
  • Check security: validation, authorization, sensitive data.
  • Check tests: unit/integration cases meaningful.
  • Comment lịch sự và giải thích lý do.

Mentoring

Mentoring không chỉ là đưa answer. Đó là giúp người khác tự xây reasoning ability.

Handling Conflict

Good response:
"I understand why you prefer option A because it is faster to implement.
My concern is that it creates coupling between Order and Payment database.
Can we compare both options against delivery time, maintainability, and failure handling?"

Production Incident Communication

1. Acknowledge issue.
2. State impact.
3. Share current hypothesis.
4. Assign owner.
5. Give next update time.
6. After fix, write postmortem:
   - Timeline
   - Root cause
   - What worked
   - What failed
   - Prevention actions

22. Câu trả lời phỏng vấn — Vietnamese

Microservice

Microservice là architectural style chia hệ thống thành nhiều service nhỏ, deploy độc lập và align với business capability. Mỗi service nên own data riêng và expose behavior qua API hoặc events. Lợi ích là independent deployment, scalability và team autonomy, nhưng trade-off là operational complexity cao hơn, distributed transaction, network failure, data consistency và observability. Trong production, em quan tâm nhiều tới service boundary, database ownership, API versioning, resilience patterns như timeout/retry/circuit breaker, idempotency, saga, transactional outbox và monitoring bằng logs, metrics, traces.

DevOps / CI/CD

CI/CD là automation pipeline giúp verify và deliver software an toàn. Trong CI, mỗi change cần được build, test, scan và validate bằng quality gates. Trong CD, artifact được package thành Docker image, push lên registry, deploy vào environment như Kubernetes, smoke test và monitor. Với database changes, em ưu tiên versioned migration bằng Flyway hoặc Liquibase và dùng backward-compatible expand-contract migration. Senior engineer không chỉ biết deploy, mà cần hiểu rollback, health checks, secrets management, deployment strategies như rolling/blue-green/canary và observability sau release.

Agile / Scrum / Soft Skills

Agile là cách delivery value theo từng iteration và adapt dựa trên feedback. Scrum cung cấp roles, events và artifacts để hỗ trợ cách làm đó. Với vai trò senior engineer, em không chỉ coding mà còn clarify requirements, identify technical risks, break down stories, improve estimation, mentor teammates, review code, communicate blockers sớm và giúp team improve qua retrospective. Em cố gắng giải thích trade-off kỹ thuật rõ ràng cho cả technical và non-technical stakeholders, đồng thời ownership từ design đến production support.
