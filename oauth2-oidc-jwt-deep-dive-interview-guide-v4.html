Deep technical guide

OAuth 2.0 is an authorization framework — not an authentication protocol.

This document builds a complete mental model of OAuth 2.0 and OpenID Connect. The most important distinction is highlighted throughout the guide: OAuth 2.0 delegates authorization to access protected resources; it does not define how a client proves that a user has logged in. OpenID Connect adds the standardized authentication layer. The guide also explains why access tokens and refresh tokens must remain separate credentials with different consumers, exposure levels, lifetimes and security controls.

Core interview statement: OAuth 2.0 answers “What may this client access?” OpenID Connect answers “Who authenticated, and how can the client verify that authentication?” An access token calls an API. A refresh token is a more sensitive credential used only at the authorization server to obtain a new access token.

Foundation

1. The non-negotiable distinction: OAuth 2.0 is authorization, not authentication

Common interview mistake: “OAuth authenticates the user” is incomplete and often incorrect. An authorization server may authenticate a user as one internal step before issuing authorization, but the OAuth 2.0 framework does not define a standardized authentication result that the client can safely use as proof of login. That standardized identity layer is OpenID Connect.

1.1 Authentication and authorization solve different problems

Authentication — Who are you?

Authentication establishes an identity. It may use a password, passkey, OTP, TOTP, biometric, certificate, social identity provider or enterprise identity provider.

The result should let the relying application verify facts such as the authenticated subject, issuer, authentication time and assurance level.

OAuth-based standard: OpenID Connect, normally through an ID token and optionally the UserInfo endpoint.

Authorization — What may you do?

Authorization decides whether a client may access a protected resource. Examples: read a calendar, create an order, view a profile or initiate a payment.

The result is normally represented by an access token with restrictions such as scope, audience, subject, client, expiry and policy.

Framework: OAuth 2.0.

1.2 Why OAuth can show a login screen but still is not an authentication protocol

During Authorization Code Flow, the authorization server usually needs to know which user is granting access. It may therefore show a login screen and perform MFA. However, that login is between the user and the authorization server. OAuth 2.0 primarily standardizes the authorization request, authorization response and token issuance. It does not define an ID token, a standard subject claim for client login, nonce validation, authentication time or authentication assurance.

OAuth 2.0 view: User authenticates at Authorization Server ↓ Authorization Server evaluates consent and policy ↓ Client receives authorization code / access token ↓ Resource Server receives access token and checks permission OpenID Connect addition: Authorization Server also issues an ID token ↓ Client validates issuer, audience, signature, time and nonce ↓ Client obtains a standardized authentication result
Important nuance: OAuth does not forbid the authorization server from authenticating a user. It simply does not define OAuth access tokens as a reliable login result for the client. Do not build “Login with X” by reading arbitrary access-token fields or by calling a random profile API. Use OpenID Connect.

1.3 The problem OAuth solves

Without delegated authorization: User gives a third-party application the account password ↓ The application may receive broad, long-lived authority ↓ Password leakage compromises the account ↓ Revocation may require changing the password With OAuth 2.0: User authenticates directly with the Authorization Server ↓ The client receives limited, scoped, audience-bound, time-limited authorization ↓ The client calls only the intended protected API ↓ Authorization can be revoked without changing the user's password

1.4 Delegation is the key concept

The client normally does not receive the resource owner's password. Instead, it receives a credential that represents delegated authorization. The authorization server may limit that credential by:

  • Scope: which categories of operations are granted.
  • Audience/resource: which API may accept the token.
  • Subject: which user or workload the authorization relates to.
  • Client: which application received the grant.
  • Lifetime: how long the authorization credential is usable.
  • Consent and policy: what the user and organization approved.
  • Sender constraint: whether token use is bound to a key or certificate.

1.5 OAuth is not the complete business permission model

OAuth-level validation:
- token signature/introspection is valid
- issuer is trusted
- audience = orders-api
- scope contains orders.cancel

Business authorization:
- order belongs to the current tenant
- user owns the order or has support permission
- order status allows cancellation
- cancellation window is still open
- request does not violate fraud or compliance policy

A scope such as orders.cancel gives coarse permission. It does not prove that the caller may cancel every order. The resource server must still enforce object ownership, tenant boundaries and business rules.

How a senior engineer should answer

“OAuth 2.0 is an authorization framework, not an authentication protocol. Its main purpose is delegated access: a client obtains an access token and presents it to a resource server to access protected resources with limited permission. The authorization server may authenticate the user during the flow, because it needs to know who is granting access, but OAuth 2.0 does not standardize the authentication result that the client should consume as proof of login.

For user authentication, I use OpenID Connect on top of OAuth 2.0. OIDC adds an ID token, standard identity claims, nonce handling, discovery and validation rules. In implementation, I keep the responsibilities clear: the client validates the ID token for login, while the resource server validates the access token for API authorization. I never use an ID token as an API access token, and I never assume that a valid access token alone is a complete business authorization decision.”

3. Every token has one purpose — access and refresh tokens must remain separate

Design principle: Use separate credentials for separate trust boundaries. The access token is exposed to resource servers and sent on many API requests. The refresh token is restricted to the authorization server and is used much less often. Combining them would give one stolen credential both immediate API access and the ability to renew that access.

3.1 Access token

GET /api/orders/123 HTTP/1.1
Host: orders.example.com
Authorization: Bearer eyJ...

An access token represents authorization granted to a client. It is presented to the resource server, which validates the token and applies authorization policy. The client should normally treat the token as an opaque credential, even when its physical format is JWT.

3.2 Bearer token risk

Most access tokens are bearer credentials: whoever possesses one can usually use it. Because the access token travels with API requests, it may pass through clients, gateways, reverse proxies, application servers, observability systems and network boundaries. A short lifetime and narrow audience reduce the damage when it leaks.

3.3 JWT versus opaque access token

JWT access token

  • Resource server can validate signature and claims locally.
  • Good scalability and low request latency.
  • Already-issued tokens are harder to revoke immediately.
  • Claims are visible to anyone holding the token unless encrypted.

Opaque access token

  • Random-looking reference with server-side state.
  • Often checked through introspection or a local cache.
  • Central state can reflect revocation more quickly.
  • Creates availability, latency and caching trade-offs.

3.4 Refresh token

A refresh token is a credential presented only to the authorization server. Its purpose is not to call business APIs. It proves that the client still holds a previously issued grant and may request a new short-lived access token, subject to current policy.

Because a refresh token can extend a session, it normally requires stronger controls: secure storage, rotation, reuse detection, sender constraint where appropriate, idle and absolute expiry, revocation and device/session tracking.

3.5 ID token

{
  "iss": "https://id.example.com",
  "sub": "user-123",
  "aud": "web-client",
  "exp": 1784200000,
  "iat": 1784199700,
  "nonce": "n-0S6_WzA2Mj"
}
Do not use an ID token to call a business API. The ID token is issued to the OIDC client and its audience is normally the client ID. The API should receive an access token whose audience identifies that API.

3.6 Why not use one token for both access and refresh?

Access-token requirements

  • Sent frequently to resource servers.
  • Short-lived to limit breach impact.
  • Narrow audience and scopes.
  • Optimized for fast API validation.
  • May be visible to several infrastructure components.

Refresh-token requirements

  • Sent only to the authorization server.
  • Longer-lived to preserve the session.
  • Stored under stronger protection.
  • Supports rotation, reuse detection and revocation.
  • Never accepted by resource servers.

Reason 1 — The two credentials have conflicting lifetime requirements

An access token should expire quickly, for example after several minutes, because it is frequently transmitted and may be exposed. A refresh token needs a longer lifetime so the client can obtain a replacement without asking the user to authenticate repeatedly.

If one token is short-lived, it cannot provide a useful long-lived refresh session after it expires. If the same token is long-lived, every API that accepts it receives a long-lived bearer credential, greatly increasing the impact of leakage.

Reason 2 — A stolen access token would become self-renewing

Attacker steals the combined token ↓ Attacker calls the protected API immediately ↓ Before expiration, attacker sends the same token to /token ↓ Authorization Server issues a new token ↓ Attacker repeats the process and can maintain access indefinitely

This would make short access-token expiration much less effective. The attacker would not need to steal the protected refresh credential separately.

Reason 3 — Different consumers should not receive the same power

Resource servers need only enough information to decide whether an API call is authorized. They do not need the power to renew the user's session. If one token served both purposes, every resource server receiving it would be inside the refresh-token trust boundary. A compromise of any API, gateway or log pipeline could expose a session-renewal credential.

Reason 4 — Separation limits blast radius

When only an access token is stolen, the attacker is limited by its expiry, audience and scopes. When a refresh token is stolen, the incident is more serious, but the system can apply specialized controls such as rotation and reuse detection. Separation lets security teams identify which credential was compromised and apply the correct response.

Reason 5 — Rotation and reuse detection require stateful semantics

A refresh-token family can be rotated:

RT-1 is used → RT-1 becomes invalid → server returns RT-2 RT-1 is used again → possible theft detected → revoke the token family

Normal access-token validation does not have these semantics. An API may validate a JWT locally without contacting the authorization server. Combining the credentials would either force every API token to use refresh-token state or remove important replay detection.

Reason 6 — Separate scopes and audiences prevent misuse

An access token is usually audience-bound to an API, such as orders-api. A refresh token is audience-bound in practice to the authorization server's token endpoint. One token accepted by both creates token-substitution risk and weakens the rule that each credential has one intended consumer.

Reason 7 — Revocation and policy checks are different

When refreshing, the authorization server can re-evaluate the client, user session, consent, account status and organizational policy before issuing a new token. A resource server normally does not perform this full session-renewal evaluation on each API call.

3.7 Correct flow

Access token: Client ── access token ──> Resource Server validates audience, scopes and expiry Refresh token: Client ── refresh token ──> Authorization Server validates grant/session/rotation returns a new access token optionally returns a rotated refresh token

3.8 What happens after each token is stolen?

How a senior engineer should answer

“I would not use one token as both an access token and a refresh token because they operate across different trust boundaries and have conflicting security requirements. An access token is presented frequently to resource servers, so it should be short-lived, narrowly scoped and limited to a specific audience. A refresh token is presented only to the authorization server, is normally longer-lived and requires stronger storage, rotation, replay detection and revocation controls.

If the access token could also refresh itself, stealing one API token would give the attacker both immediate access and the ability to renew that access repeatedly. That would weaken the security value of short access-token expiration and expand the refresh-token trust boundary to every API, gateway or infrastructure component that sees the token.

By separating them, a stolen access token has a limited blast radius, while refresh-token theft can be detected through rotation and reuse detection. It also enforces token purpose: resource servers accept access tokens; only the authorization server accepts refresh tokens. This is an example of least privilege and separation of responsibilities, not merely a naming convention.”

JWT / JOSE

4. JWT deep dive — structure, claims, signing, encryption and private data

Core idea: JWT is a compact token format for carrying claims. JWT is not the same thing as OAuth 2.0, and JWT is not automatically an access token. OAuth defines authorization behavior; JWT defines a possible representation of claims. An OAuth access token may be a JWT or an opaque value. An ID token is normally a JWT, and JWT is also used in several other protocols.

4.1 What exactly is a JWT?

JWT means JSON Web Token. It is a compact, URL-safe representation of claims transferred between parties. A JWT can be protected by a digital signature or MAC through JWS, or encrypted through JWE.

Very important: The common three-part JWT that developers see is usually a signed JWS compact serialization. Its Header and Payload are Base64URL-encoded, not encrypted. Anybody who obtains the token can normally decode and read them without knowing the signing key.

4.2 The common three-part structure

    + "."

Header

Describes how the token is protected and may identify the signing key.

Payload

Contains claims: statements about a subject, client, issuer, authorization or token.

Signature

Protects integrity and allows the recipient to verify the expected signer or shared-key holder.

4.3 Base64URL is encoding, not encryption

Base64URL changes binary data into URL-safe text. It does not provide secrecy. A developer can decode the Header and Payload without a secret key: 

String[] parts = jwt.split("\\.");

String headerJson = new String(
        Base64.getUrlDecoder().decode(parts[0]),
        StandardCharsets.UTF_8
);

String payloadJson = new String(
        Base64.getUrlDecoder().decode(parts[1]),
        StandardCharsets.UTF_8
);
Do not confuse “cannot easily read at first glance” with encryption. Browser tools, command-line tools, libraries and even a few lines of Java can decode a normal signed JWT. Decoding does not prove that the token is valid. Claims must not be trusted until all cryptographic and semantic validation has succeeded.

4.4 Header in detail

{
  "alg": "RS256",
  "typ": "at+jwt",
  "kid": "signing-key-2026-07"
}
Header parameterMeaningSecurity note
alg Algorithm used to sign, MAC or encrypt the token. The verifier must use a server-side allow-list. Never trust the token to choose any algorithm it wants.
typ Explicit token type, for example JWT or at+jwt. Helps prevent one JWT type from being accepted in another context.
kid Key identifier used to select one key from a trusted key set. It is a selector, not a trust source. Do not build an arbitrary file path, SQL query or remote URL from it.
cty Content type, commonly used with nested JWT structures. Needed only in defined token profiles.
jku/x5u Locations related to keys or certificates. Dangerous if fetched from untrusted token input; may create SSRF or attacker-controlled key lookup.

Why alg must be allow-listed

The application configuration must decide which algorithms are accepted. It must not simply read alg from the untrusted header and dynamically accept it. This protects against algorithm-substitution and key-confusion problems. 

// Conceptual configuration:
accepted algorithms = { RS256 }

// Reject:
alg = none
alg = HS256 when this token profile requires RS256
alg = any algorithm not explicitly configured

{
  "iss": "https://id.example.com",
  "sub": "user-123",
  "aud": "orders-api",
  "exp": 1784200000,
  "nbf": 1784199600,

Each property is a claim: a statement made by the issuer. A claim is not trusted merely because it exists. The receiver trusts it only after validating the token and confirming that the issuer is authorized to make that claim for this token type and audience.

4.6 Registered claims

ClaimMeaningHow a resource server uses it

The registered claims are not all mandatory for every JWT. A specific profile defines which claims are required. For OAuth JWT access tokens, follow the access-token profile and authorization-server contract rather than inventing assumptions from the base JWT specification alone.

4.7 Public and private claims

Public claims

Claims registered in a public registry or defined with collision-resistant names. They improve interoperability across organizations.

Private claims

Application-specific claims agreed between issuer and consumer, such as tenant_id, department or permissions. “Private claim” means privately defined; it does not mean confidential.

Important vocabulary: A “private claim” is not encrypted private information. It is only a non-standard claim name used by cooperating applications.

4.8 Can the payload store private or sensitive information?

Technically, JSON can contain almost any data. Security-wise, a normal signed JWT payload should not contain secrets or unnecessary sensitive personal data. A signed JWT provides integrity, not confidentiality. Token holders, browser code, mobile applications, gateways, resource servers and any leaked logs may be able to read the payload.

DataStore in a normal signed JWT?Reason
User ID, tenant ID, client ID Usually acceptable Identifiers may be necessary for authorization, but still minimize and avoid externally meaningful identifiers when possible.
Scopes or compact permission indicators Often appropriate The resource server needs them, but avoid thousands of detailed permissions that create large, stale tokens.
Email or display name Only when required It is personal information and may leak through clients or logs. Prefer fetching profile data when it is not required on every request.
Address, phone number, date of birth Normally avoid Sensitive PII increases privacy and breach impact and is rarely needed for API authorization.
Password, PIN, OTP, TOTP secret Never These are authentication secrets. Signing does not hide them.
Client secret, private key, API key, refresh token Never A token must never carry another reusable secret that token holders can extract.
Full card number, CVV, bank credentials Never High-impact regulated data; CVV storage is especially prohibited in payment contexts.
Full medical, payroll or legal record Avoid JWTs are copied and transmitted broadly and are poor containers for large confidential records.

Practical rule

Before adding a claim, ask: 1. Does the intended recipient need this value on every request? 2. Can the API retrieve it from trusted server-side data instead? 3. Will it become stale before the token expires? 4. Is it safe if the user, client, proxy or log reader can see it? 5. Does adding it violate data-minimization, privacy or regulatory requirements? 6. Does this claim increase token size enough to affect headers, proxies or cookies?

If a claim is needed only by one API, issue an audience-specific token containing only the minimum necessary data. Do not create one large “identity bag” token and send it to every microservice.

4.9 Signing is not encryption

JWS — signed or MAC-protected content

Provides: integrity and signer/MAC verification.

Does not provide: confidentiality.

Common compact form: three segments.

JWE — encrypted content

Provides: confidentiality and authenticated encryption when correctly used.

Compact JWE normally has five segments.

It creates key-management and operational complexity.

Signed JWS compact form:
protectedHeader.payload.signature

Encrypted JWE compact form:
protectedHeader.encryptedKey.iv.ciphertext.authenticationTag

If confidentiality is required

Consider one of these options:

  • Do not put the information in the token. Store it server-side and use a minimal identifier.
  • Use an opaque reference token. The resource server obtains authorization data from trusted state or introspection.
  • Use JWE only when the protocol and operational model genuinely require encrypted JWT content.
JWE is not a reason to place unlimited sensitive data in tokens. The data can still appear after decryption in application memory, tracing, error logs or downstream systems. Encryption also needs correct recipient keys, rotation, algorithm configuration and failure handling.

4.10 Signature creation

For a signed JWS, the signing input is:

signingInput =
    BASE64URL(UTF8(protectedHeader))
    + "."
    + BASE64URL(payloadBytes)

signature = SIGN(signingInput, signingKey)

The verifier reconstructs the same signing input and verifies the signature with the correct key. Any change to the encoded Header or Payload should cause signature verification to fail.

4.11 HMAC versus asymmetric signatures

Algorithm familySigningVerificationTrade-off
HMAC, such as HS256 Shared secret Same shared secret Every verifier that knows the secret can also create tokens. Harder trust separation.
RSA, such as RS256/PS256 Private key Public key Resource servers can verify without being able to issue tokens. Larger keys/signatures.
Elliptic curve, such as ES256 Private key Public key Smaller keys/signatures, but implementation and ecosystem compatibility must be verified.
EdDSA, where supported by the profile Private key Public key Modern design, but support depends on the complete platform and token profile.

For a central authorization server and many resource servers, asymmetric signatures are often easier to separate safely: only the authorization server keeps the private signing key, while APIs receive public verification keys.

  • JWKS: JSON Web Key Set containing multiple JWKs.
  • kid: selects a candidate key from the issuer's already trusted JWKS.

Safe key rotation sequence

  1. Publish the new public key in JWKS.
  2. Begin signing newly issued tokens with the new private key.
  3. Keep the old public key available while old tokens may still be valid.
  4. Remove the old public key after the maximum token lifetime and safe overlap period.

4.14 JWT access token profile

When OAuth access tokens use JWT format, the issuer and resource server should follow an explicit profile. The profile defines claims, token type and validation expectations so that a resource server does not accept an arbitrary JWT from another purpose. 

{
  "typ": "at+jwt",
  "alg": "RS256"
}

Explicit typing and mutually exclusive validation rules reduce cross-JWT confusion—for example, accepting an ID token, logout token or client assertion where an API access token is required.

4.15 JWT size and stale-claim problems

  • Large tokens increase every HTTP request size.
  • They can exceed gateway, proxy, server or cookie header limits.
  • Large role/permission lists make authorization data difficult to manage.
  • Claims stay unchanged until a new token is issued, even if the database changes.
  • Long-lived tokens create a larger stale-authorization window.

For frequently changing authorization, use short-lived tokens, version/session checks, introspection or server-side policy lookup instead of placing the entire dynamic permission model inside the JWT.

4.16 Spring Security JWT validation example

@Bean
JwtDecoder jwtDecoder(
        @Value("${security.issuer}") String issuer,
        @Value("${security.audience}") String audience
) {
    NimbusJwtDecoder decoder =
            JwtDecoders.fromIssuerLocation(issuer);

    OAuth2TokenValidator<Jwt> issuerValidator =
            JwtValidators.createDefaultWithIssuer(issuer);

    OAuth2TokenValidator<Jwt> audienceValidator =
            jwt -> jwt.getAudience().contains(audience)
                    ? OAuth2TokenValidatorResult.success()
                    : OAuth2TokenValidatorResult.failure(
                            new OAuth2Error(
                                    "invalid_token",
                                    "Required audience is missing",
                                    null
                            )
                    );

    decoder.setJwtValidator(
            new DelegatingOAuth2TokenValidator<>(
                    issuerValidator,
                    audienceValidator
            )
    );

    return decoder;
}

The framework should perform cryptographic validation. Application code then maps only approved claims into authorities and applies object-level authorization.

4.17 What must never be logged

  • The complete JWT.
  • The Authorization header.
  • Refresh tokens, authorization codes or client secrets.
  • Decrypted JWE content.
  • Raw payload claims containing personal or security-sensitive information.

For diagnostics, log safe metadata such as trusted issuer, client ID, token type, a hashed subject, a hashed jti, validation failure category and correlation ID. Apply privacy controls even to metadata.

How a senior engineer should answer: Can JWT payload store private information?

“Technically, a JWT payload can contain arbitrary JSON claims, but I would not put secrets or unnecessary sensitive information in a normal signed JWT. The common three-segment token is a JWS: the Header and Payload are Base64URL-encoded and can be decoded by anyone who obtains the token. The signature protects integrity and proves the expected signer; it does not provide confidentiality. Also, a private claim is only an application-specific claim—it is not a confidential claim.

I keep token claims minimal and purpose-specific. Identifiers, audience, scope and compact tenant context may be appropriate when the resource server needs them. I avoid passwords, OTPs, private keys, API keys, refresh tokens, card data and detailed personal records. Even values such as email, phone number or date of birth should be included only when the intended recipient truly requires them and the privacy risk is accepted.

If confidentiality is required, my first choice is usually not to put the data in the token: I use a minimal identifier and retrieve protected data server-side. Depending on the architecture, an opaque reference token may be better. JWE can encrypt JWT content, but it adds key-management, rotation and operational complexity and does not remove data-minimization requirements.

Finally, I never trust decoded claims before validating the signature or encryption, issuer, audience, time, token type and profile-specific requirements. JWT is a data format, not a security decision by itself.”

4.5 What PKCE protects

An attacker who steals only the authorization code cannot exchange it without the verifier. The server compares the hash of the received verifier with the challenge stored for the authorization request.

4.6 What PKCE does not do

  • It does not authenticate the user.
  • It does not make a public client confidential.
  • It does not protect a stolen access token.
  • It does not replace exact redirect URI validation or TLS.

Grant selection

6. OAuth 2.0 grant types — complete deep dive

Core definition: An authorization grant is a credential representing authorization that the client can use to obtain an access token. The grant_type parameter tells the authorization server which grant mechanism the client is presenting at the token endpoint. Choosing a grant type means choosing who is granting authority, whether a user is involved, how the client proves possession of the grant, and which attacks the flow must resist.

6.1 Grant, grant type, response type and client authentication are different

Concept Meaning Example
Authorization grant The credential or mechanism representing authority to request an access token. Authorization code, client credentials, device code or JWT assertion.
grant_type A token-endpoint parameter identifying how the client is requesting a token. authorization_code, client_credentials, refresh_token.
response_type An authorization-endpoint parameter describing what response the client requests. response_type=code.
Client authentication method How a confidential client proves its own identity to the authorization server. client_secret_basic, private_key_jwt, mutual TLS.
Common interview confusion: private_key_jwt is normally a client-authentication method. urn:ietf:params:oauth:grant-type:jwt-bearer is a JWT assertion authorization grant. They can both use JWT, but they solve different problems.

6.2 Original grants and extension grants

The original OAuth 2.0 framework defined four authorization grant types: Authorization Code, Implicit, Resource Owner Password Credentials and Client Credentials. It also defined an extension mechanism. Later specifications added mechanisms such as Device Authorization, Token Exchange and assertion-based grants.

Modern security guidance changes which original grants should be selected:

MechanismModern statusMain reason
Authorization Code + PKCE Preferred user flow Tokens are issued from the token endpoint, and PKCE binds the code exchange to the initiating client instance.
Client Credentials Use for workload identity Correct when a confidential client acts as itself and no end-user delegation is required.
Refresh Token Use with strong protection Allows session continuation without exposing a long-lived credential to resource servers.
Device Authorization Use for constrained devices Moves user interaction to a second device with a usable browser and keyboard.
Token Exchange / Assertion grants Use for explicit advanced cases Supports federation, delegation, impersonation or exchange of an external assertion.
Implicit Do not select for new systems Access tokens are exposed in the authorization response and have higher leakage and replay risk.
Password / ROPC Must not be used The client directly handles the user's password and bypasses modern authentication flows.

6.3 How to select a grant type

Start | |-- Is a human user authorizing access? | | | |-- Yes | | | | | |-- Can the device use a browser or system user-agent? | | | | | | | |-- Yes → Authorization Code + PKCE | | | | | | | |-- No / difficult input → Device Authorization Grant | | | | | |-- Never collect the user's password with Password Grant | | | |-- No | | | |-- Is the workload acting as itself? | | | | | |-- Yes → Client Credentials | | | |-- Is it exchanging an existing user/service assertion | | for a new audience or security domain? | | | | | |-- Yes → Token Exchange or assertion grant | |-- Does the client already hold a valid refresh token? | |-- Yes → Refresh Token request
Do not choose a grant only from application shape. A backend is not automatically Client Credentials. If that backend is calling another service on behalf of a logged-in user, Client Credentials would replace the user's delegated identity with the backend's own identity. The business requirement determines the grant.

6.4 Authorization Code Grant with PKCE

This is the normal flow when a user participates. The client sends the user-agent to the authorization endpoint, receives a short-lived authorization code and exchanges the code at the token endpoint. A confidential client authenticates itself at the token endpoint. A public client cannot safely hold a static client secret and therefore uses its client identifier plus PKCE. PKCE and client authentication are complementary: one binds the code to the client instance; the other authenticates a confidential client.

Authorization code security properties

  • The code should be short-lived and one-time use.
  • The code must be bound to the client identifier.
  • The code must be bound to the registered redirect URI used in the request.
  • The code must be bound to the PKCE challenge.
  • The client validates state; an OIDC client also validates nonce.
  • Access and refresh tokens are returned from the token endpoint, not placed in the browser URL.

When to use

Suitable

  • Server-rendered web applications.
  • Backend-for-Frontend applications.
  • Single-page applications.
  • Mobile and desktop native applications using the system browser.
  • Login through OIDC.
  • User consent to access another system's API.

Important trade-offs

  • Requires browser redirects and callback handling.
  • Requires secure storage of verifier/state and possibly tokens.
  • Redirect URI and issuer configuration must be strict.
  • Native apps must prevent callback interception.
  • A BFF reduces browser token exposure but adds server/session complexity.

6.5 Client Credentials Grant

Client Credentials is used when a confidential client requests an access token under its own identity or under authority previously arranged with the authorization server. There is no end-user authorization interaction in this request.

Batch Job / Service | | Authenticate client + request scope v Authorization Server | | Access token: sub/client = workload identity v Protected API
POST /token
Authorization: Basic base64(client-id:client-secret)
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&scope=payment-reconciliation.read
{
  "access_token": "eyJ...",
  "token_type": "Bearer",
  "expires_in": 600,
  "scope": "payment-reconciliation.read"
}

What identity does the token represent?

Correct interpretation:
"The reconciliation-job client may read reconciliation data."

Incorrect interpretation:
"User Huy authorized this specific request."

The subject may identify the client, workload or service account depending on the issuer's profile. The resource server must not assume that every sub is a human user.

Typical use cases

  • Batch job calling an internal reporting API.
  • Scheduler triggering a maintenance service.
  • Backend service acting under its own business identity.
  • Daemon or machine process accessing pre-authorized resources.

When not to use it

  • When the downstream API must know the logged-in user.
  • When user consent or user-specific scopes are required.
  • When the application is a public client unable to protect a credential.
  • As a shortcut to bypass a proper delegated-user flow.
The OAuth 2.0 core specification limits Client Credentials to confidential clients. A refresh token is normally unnecessary and should generally not be returned because the client can authenticate and request another access token directly.

6.6 Refresh Token request

A refresh token lets a client obtain a new access token without repeating the full user authorization interaction. Strictly speaking, it is not one of the four original authorization grants, but the token endpoint uses grant_type=refresh_token. 

POST /token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token
&refresh_token=rt-current-family-member
&client_id=public-mobile-client
&scope=orders.read profile

A confidential client also authenticates itself. The requested scope must not contain permissions that were not originally granted. If scope is omitted, the request normally continues with the previously authorized scope according to server policy.

Refresh processing

The token must belong to the requesting client.
2

Not expired, revoked, reused or otherwise invalid.

User, client, consent, session and organization may have changed.

Real-world cases

  • Mobile application keeps a user session without login every ten minutes.
  • BFF renews an API token while the browser keeps only a session cookie.
  • Desktop application renews access using protected OS credential storage.
A refresh token must never be sent to a business resource server. Only the authorization server's token endpoint should accept it.

6.8 Token Exchange Grant

Token Exchange allows a client to present one security token and request another token from an authorization server acting as a Security Token Service. It supports controlled delegation, impersonation and conversion between security domains or audiences. 

POST /token
Authorization: <client authentication>
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=incoming-user-access-token
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&requested_token_type=urn:ietf:params:oauth:token-type:access_token
&audience=payment-service
&scope=payments.initiate

Important parameters

ParameterPurpose
subject_token The token representing the subject whose identity or authorization is being exchanged.
subject_token_type Identifies the type of the subject token.
actor_token Optional token representing an acting party operating for the subject.
requested_token_type Indicates the kind of token requested.
audience / resource Limits the intended recipient of the issued token.
scope Requests a reduced set of permissions under server policy.

Delegation versus impersonation

Impersonation

The issued token represents the subject, and the recipient may treat actions as performed by that subject. The acting service may not be visible unless claims/profile preserve it.

Delegation

The issued token represents a subject plus an actor operating on the subject's behalf. This supports audit chains such as user → order service → payment service.

Microservice example

User token audience = order-service ↓ Order Service must call Payment Service for the user ↓ Order Service authenticates to Authorization Server and exchanges the incoming token ↓ New token: audience = payment-service scope = payments.initiate subject = user actor = order-service ↓ Payment Service receives a reduced, correctly targeted token
Token Exchange is not simply “copy claims into a new JWT.” The authorization server must validate the incoming token, trust relationship, requested audience, actor, delegation policy and scope reduction before issuing a new token.

6.9 JWT Bearer assertion grant

An assertion-based grant allows a client to present a signed assertion as the authorization grant. A common example is the JWT Bearer Grant. 

POST /token

The JWT assertion commonly includes issuer, subject, audience, expiry and unique identifier claims. The authorization server validates the assertion's signature, trust relationship, audience, time window and replay controls before issuing an access token.

Typical uses

  • Enterprise federation where an external trusted authority issues an assertion.
  • Workload identity federation between cloud or security domains.
  • Exchanging an existing signed identity assertion for an OAuth access token.

6.10 Implicit Grant — legacy and unsafe for new designs

Implicit Grant returns an access token directly from the authorization endpoint through the user-agent, traditionally in the URL fragment. 

GET /authorize?
    response_type=token
    &client_id=legacy-spa
    &redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback
    &scope=orders.read
    &state=xyz
Browser authorization request ↓ Authorization Server returns access token in redirect response ↓ Browser/client JavaScript extracts token ↓ No separate code exchange at token endpoint

Why it was originally used

Older browser applications could not always call token endpoints conveniently and wanted fewer round trips. Modern browser capabilities and Authorization Code + PKCE remove that reason.

Why current guidance rejects it

  • Access token is exposed in the front-channel authorization response.
  • It is more vulnerable to leakage through browser and redirect handling.
  • It provides weaker protection against token injection and replay.
  • No authorization-code exchange exists for PKCE to protect.
  • Authorization Code + PKCE has a smaller and better-understood attack surface.
Do not “improve” Implicit Grant by adding a few custom checks. Use Authorization Code with PKCE instead.

6.11 Resource Owner Password Credentials Grant — must not be used

POST /token
Content-Type: application/x-www-form-urlencoded

grant_type=password
&username=huy@example.com
&password=user-password
&client_id=legacy-client

In this flow, the client directly receives and transmits the user's username and password. This contradicts the delegated model where the user authenticates directly with the authorization server.

Why it is unsafe

  • The client becomes part of the password trust boundary.
  • A compromised client can steal credentials, not only a limited token.
  • It trains users to enter identity-provider passwords into applications.
  • It cannot cleanly support federated login, passkeys, consent or complex authentication journeys.
  • It is not designed for modern MFA and step-up authentication.
  • The client can observe credentials with power beyond the requested OAuth scopes.

2
Introduce Authorization Code + PKCE
Use external browser/system user-agent as appropriate.

MFA, passkeys, federation and risk checks.
4

Measure usage and communicate cutover.

6.15 Grant-type interview questions

1. What is the difference between an authorization grant and an access token?

An authorization grant is the credential or mechanism the client presents to the authorization server to obtain an access token. The access token is the credential the client later presents to the resource server. For example, an authorization code is a grant; the token obtained by exchanging that code is an access token.

2. Why is Authorization Code + PKCE preferred for public clients?

A public client cannot safely keep a static secret. Authorization Code avoids placing the access token in the browser authorization response, while PKCE binds the code exchange to the client instance that created the verifier. A stolen code alone is therefore insufficient.

3. Does a confidential client still need PKCE?

Client authentication and PKCE protect different properties. Client authentication proves the registered confidential client. PKCE binds the individual authorization code to the request instance. Using both provides defense in depth and is appropriate in modern deployments.

4. Why is Client Credentials wrong for many user-driven microservice calls?

Client Credentials represents the service itself. If the downstream service needs to know which user authorized the action, replacing the user token with a client token loses delegation context. Use token relay only when audience and privilege are correct, or use Token Exchange for a reduced downstream token.

5. Is Refresh Token an authorization grant?

RFC 6749 defined four original authorization grant types, and refresh token was described separately. However, a refresh request uses the token endpoint parameter grant_type=refresh_token. In daily engineering discussion it is commonly grouped with grant types, but a precise interview answer should mention this distinction.

6. Why does Client Credentials usually not need a refresh token?

The confidential client can authenticate to the token endpoint and request another access token when needed. A refresh token adds another long-lived credential without providing much benefit. The core specification says a refresh token should not normally be included in this response.

7. What is the main difference between Device Flow and Authorization Code Flow?

Authorization Code Flow uses the same user-agent context to initiate authorization and receive the callback. Device Flow separates the input-constrained device from the browser where the user authenticates and approves. The device polls the token endpoint using a device code.

8. Token Exchange versus Client Credentials?

Client Credentials produces a token for the client itself. Token Exchange starts from an existing subject or actor token and can produce an audience-specific token representing delegation or impersonation. Use Token Exchange when downstream authorization must preserve or transform an existing security context.

9. JWT Bearer Grant versus JWT access token?

JWT Bearer Grant describes how a JWT assertion is presented to obtain an access token. A JWT access token describes the format of the token issued for API access. One is a grant mechanism; the other is a token representation.

10. What is the correct replacement for Password Grant?

Use Authorization Code + PKCE and let the user authenticate directly at the authorization server. This supports federation, passkeys, MFA, consent, risk-based authentication and future identity changes without giving the user's password to the client.

How a senior engineer should answer

“An OAuth grant type defines how a client presents authorization to the token endpoint. I choose it from the actor and trust model, not only from whether the application is frontend or backend. For a user-facing application, I normally use Authorization Code with PKCE. Public clients cannot protect a static secret, while confidential clients authenticate themselves and should still use PKCE to bind the authorization code to the request instance.

For service-to-service access where the service acts as itself, I use Client Credentials with a narrow audience, minimal scopes and a properly managed workload credential. I do not use it when a downstream API needs the end-user's delegated identity. In that situation I consider token relay or, preferably when available, Token Exchange to create an audience-specific reduced token with explicit delegation.

Refresh Token requests extend an existing grant and require stronger controls such as client binding, rotation, reuse detection, revocation and scope non-escalation. Device Authorization is suitable for input-constrained devices, while assertion grants and Token Exchange are for explicit federation and security-domain transitions.

I would not use Implicit Grant or Password Grant in a new design. Implicit exposes access tokens in the authorization response, and Password Grant puts the user's credentials inside the client trust boundary. A senior design answer should also cover exact redirect URIs, PKCE, token audience, client authentication, refresh-token protection and the fact that a grant type does not replace business authorization at the resource server.”

Interview

17. Basic and mid-level questions — answered with senior-level depth

A strong answer should give the definition, explain the security purpose, mention a practical example and state at least one limitation or common mistake.

1. What is OAuth 2.0?

Senior answer: OAuth 2.0 is an authorization framework for delegated access. It allows a client application to obtain limited permission to call a protected resource, either on behalf of a resource owner or on behalf of the client itself. Instead of sharing the user's password with the client, the authorization server issues an access token restricted by properties such as scope, audience, client, subject and lifetime.

For example, a calendar application may receive permission to read a user's calendar without receiving the user's Google password. OAuth does not define the application's complete business permission model, and it is not by itself a user authentication protocol.

2. Is OAuth 2.0 authentication or authorization?

Senior answer: OAuth 2.0 is authorization. It answers whether a client may access a protected resource. During the flow, the authorization server may authenticate the user, but OAuth does not define a standardized authentication result for the client.

For login, use OpenID Connect. OIDC adds the ID token and validation rules such as issuer, audience, signature, expiry and nonce. In a well-designed system, the client consumes the ID token for authentication, while the resource server consumes the access token for API authorization.

3. What are the four OAuth roles?

Senior answer: The resource owner controls the protected resource; the client requests access; the authorization server evaluates the grant and issues tokens; and the resource server hosts the protected API and validates access tokens. A common mistake is to assume the client is only a frontend. A backend application, mobile app, CLI or batch process can also be an OAuth client.

4. Why are access tokens and refresh tokens separate?

Senior answer: They have different consumers, lifetimes, exposure levels and security controls. The access token is sent frequently to resource servers and should be short-lived, scope-limited and audience-restricted. The refresh token is sent only to the authorization server, normally lives longer and must support stronger controls such as secure storage, rotation, reuse detection and revocation.

If one token performed both roles, stealing an API token would also let an attacker renew the session repeatedly. It would make short access-token expiry less useful and expose session-renewal power to every API component that receives the token. Separation reduces blast radius and enforces least privilege.

5. What is PKCE and what problem does it solve?

Senior answer: PKCE binds an authorization code to a high-entropy verifier created by the client instance. The client sends a SHA-256-based challenge in the authorization request and later sends the original verifier to the token endpoint. If an attacker intercepts only the authorization code, the attacker cannot exchange it without the verifier.

PKCE protects the code exchange. It does not authenticate the user, make a public client confidential, protect an already-stolen access token or replace TLS and exact redirect URI validation.

6. What is the difference between state, nonce and PKCE?

Senior answer: State correlates the authorization request with the callback and helps protect the client session against login CSRF. Nonce is an OIDC value included in the ID token, binding the authentication response to the request and reducing replay or token-injection risk. PKCE binds the authorization code to the client instance through the verifier/challenge pair.

They protect different parts of the flow. Using PKCE does not automatically remove the need for proper state and nonce handling.

7. What is a bearer token?

Senior answer: A bearer token can normally be used by whoever possesses it; the caller does not prove possession of a separate key. This makes token confidentiality critical. I protect bearer tokens with TLS, short lifetimes, secure storage, audience restriction and careful logging controls. For high-assurance scenarios, sender-constrained mechanisms such as DPoP or mTLS can reduce replay risk.

8. Is an access token always a JWT?

Senior answer: No. OAuth does not require one access-token format. It may be a JWT, an opaque reference token or another format agreed between the authorization server and resource server. JWT enables local validation and scale, but immediate revocation is harder. Opaque tokens support centralized activity checks through introspection, but add network and availability trade-offs.

9. What is the Client Credentials Grant?

Senior answer: Client Credentials is a machine-to-machine grant where the client authenticates to the authorization server and receives a token representing the client itself. It is appropriate for a batch job or backend service acting under its own identity.

It should not be described as a user token. If Service A uses Client Credentials to call Service B, B knows A is calling but does not automatically know which end user initiated the original request. For user delegation, consider token relay or token exchange.

10. Why should new systems not use Implicit Grant?

Senior answer: Implicit Grant returns an access token through the browser authorization response, which increases exposure to browser history, scripts, redirect handling and token-injection risks. It also lacks the protected code-exchange step provided by PKCE.

Authorization Code with PKCE is the modern replacement for browser and public clients because the front channel carries only a short-lived code and the token is obtained through the token endpoint.

11. Why must Password Grant not be used?

Senior answer: Password Grant requires the client to collect the resource owner's username and password. This breaks the delegated-security model, expands the credential attack surface and trains users to share passwords with applications. It also fits poorly with federation, MFA, passkeys, risk-based authentication and consent.

Use Authorization Code with PKCE for user-facing applications. Legacy migration pressure does not change the security model; it only means a controlled migration plan is needed.

12. What is OpenID Connect?

Senior answer: OpenID Connect is an identity layer built on OAuth 2.0. It defines how a client requests authentication using the openid scope and receives an ID token. It also defines standard claims, UserInfo, discovery and validation behavior.

The client validates the ID token's signature, issuer, audience, time and nonce. The stable external identity key should normally be the combination of issuer and subject, not email alone.

13. What is the difference between scope, role and claim?

Senior answer: A scope represents requested or granted authorization, usually from the client's perspective, such as orders.read. A role is an application or organizational grouping such as ADMIN or SUPPORT_AGENT. A claim is a statement contained in a token or response, such as subject, tenant, scope or authentication time.

These concepts may be mapped, but they are not identical. The resource server should translate trusted claims into local authorities through an explicit allow-list and still enforce business authorization.

14. What must a resource server validate?

Senior answer: For JWT, it should safely parse the token, enforce an algorithm allow-list, select a trusted key, verify the signature, validate issuer, audience, expiry and not-before time, and check token purpose and required authorization. For opaque tokens, it normally uses an authenticated introspection call or trusted local state.

Signature validation alone is insufficient. A correctly signed token issued for another API must still be rejected because its audience is wrong.

15. What is token introspection?

Senior answer: Introspection allows an authorized resource server to ask the authorization server whether a token is active and retrieve metadata such as subject, client, scope, audience and expiry. It is commonly used with opaque tokens and can provide faster visibility of revocation.

The trade-off is an additional network dependency. Caching improves latency and resilience but delays revocation visibility, so the cache duration must match the system's risk requirements.

16. What are the three parts of a signed JWT?

Senior answer: A common compact signed JWT has a protected Header, Payload and Signature. The Header declares protection metadata such as algorithm, token type and key identifier. The Payload contains claims. The Signature protects the encoded Header and Payload from modification and allows the receiver to verify the expected signer or MAC holder.

The Header and Payload are Base64URL-encoded, not encrypted. I therefore do not put secrets in them, and I do not trust decoded claims until signature and semantic validation have completed.

17. Can JWT payload contain private information?

Senior answer: It can technically contain arbitrary JSON, but a normal signed JWT does not provide confidentiality. Anyone holding it can usually decode the payload. I include only the minimum claims required by the intended recipient and avoid secrets, credentials, payment data and unnecessary PII.

If confidentiality is required, I first consider server-side data with a reference identifier or an opaque token. JWE is another option, but it adds key-management complexity and does not remove the need for data minimization.

18. What is the difference between signing and encryption?

Senior answer: Signing provides integrity and authentication of the signer: the receiver can detect modification and verify who signed the content. Encryption provides confidentiality: unauthorized parties should not read the content. A JWS is commonly signed but readable; JWE encrypts content. A system may use nested sign-and-encrypt structures when a defined profile requires both.

19. Is JWT the same as an access token?

Senior answer: No. JWT is a token format; an access token is an OAuth credential representing authorization. An access token may be JWT or opaque. JWT is also used for ID tokens, client assertions, logout tokens, DPoP proofs and other purposes. The receiver must validate the expected token type and profile so these JWTs cannot be substituted for one another.

20. What are JWK, JWKS and kid?

Senior answer: A JWK is a JSON representation of a cryptographic key. A JWKS is a set of JWKs published by a trusted issuer. The kid header helps select a candidate key from that trusted set. It does not establish trust by itself and must never trigger arbitrary untrusted key or URL lookup.

Senior interview

18. Senior questions — explain trade-offs, failure modes and production behavior

1. A JWT signature is valid. Why might you still reject the token?

Senior answer: A valid signature proves only that the JWT was signed by the corresponding key and was not modified. It does not prove that the token is appropriate for this API. I still validate the trusted issuer, audience, expiration, not-before time, allowed algorithm, expected token type and required scopes or claims.

I also consider key trust. A kid value must select among keys from a trusted issuer; it must not cause an arbitrary key lookup. Finally, valid token-level authorization does not replace tenant, ownership and business-rule checks.

2. How do you support immediate logout with JWT access tokens?

Senior answer: Self-contained JWT validation is intentionally decentralized, so an already-issued access token can normally remain valid until expiry even after the local session or refresh token is revoked. I first define the product requirement: does logout prevent renewal, or must it invalidate every API token immediately?

For common systems, I use short access-token TTL plus refresh-token revocation. For high-risk requirements, options include opaque reference tokens with introspection, a deny-list by token or session identifier, security-event propagation, or a gateway/session check. Each option adds state, latency and operational complexity.

3. How would you secure refresh tokens in a browser application?

Senior answer: I prefer a Backend-for-Frontend where OAuth tokens remain server-side and the browser receives only a Secure, HttpOnly, SameSite session cookie. The BFF must then implement CSRF, origin, cookie and session protections correctly.

If the SPA is a direct public client, I use Authorization Code + PKCE, refresh-token rotation with reuse detection or sender constraint, minimal scopes, idle and absolute expiration, and careful storage. I treat XSS as the primary threat because malicious JavaScript can either steal readable tokens or make authorized requests through the application.

4. How do you prevent access-token replay?

Senior answer: Basic controls are TLS, secure storage, short TTL, narrow scopes, audience restriction and preventing token leakage through URLs and logs. For high-assurance systems, I consider sender-constrained tokens such as DPoP or mTLS so possession of the token alone is not enough.

OAuth replay protection is not the same as business replay protection. A payment API also needs idempotency keys, duplicate-request detection and transaction-level controls even when the token is valid.

5. Why is audience validation critical in microservices?

Senior answer: Without audience validation, a valid token minted for Service A may be replayed at Service B. The signature and issuer can still be valid, so a generic “valid JWT” check will not stop the confused-deputy problem.

I prefer service- or resource-specific audiences and least-privilege scopes. When a downstream service needs a different token, token exchange or resource indicators can create a reduced, audience-specific credential instead of forwarding one broad token everywhere.

6. JWT or opaque token — which would you choose?

Senior answer: I choose based on risk, scale, latency, privacy and revocation requirements. JWT supports local validation, reduces authorization-server traffic and works well across distributed systems. Its trade-offs are claim exposure and delayed revocation for already-issued tokens.

Opaque tokens keep authorization state centralized and can reflect revocation quickly through introspection, but they create latency and availability dependencies. A hybrid design may use short-lived JWT access tokens with centrally managed refresh sessions.

7. How should signing-key rotation work?

Senior answer: Publish the new public key before issuing tokens signed by the new private key. Then begin signing new tokens with the new key while keeping the old public key available for at least the maximum remaining lifetime of old tokens plus safe clock skew.

Resource servers should cache JWKS, refresh on unknown key identifiers with rate limits and keep a last-known-good key set for resilience. Rotation should be tested operationally; it is not only a configuration task.

8. How should user identity be propagated to downstream services?

Senior answer: The main options are token relay, token exchange and a carefully designed trusted identity envelope. Relay is simple but exposes the same token downstream and may have the wrong audience or excessive privilege. Client Credentials represents the calling service, not the user.

Token exchange is often stronger because it can mint a downstream-specific token with reduced scope and explicit delegation. Regardless of the mechanism, downstream services still validate the token and enforce local object and tenant authorization.

9. What is an OAuth mix-up attack?

Senior answer: A mix-up attack affects a client configured with multiple authorization servers. The client may confuse which issuer produced an authorization response and send a code or credentials to the wrong endpoint.

I bind each flow to the expected issuer, validate issuer information in the response, use strict client and redirect configuration, and avoid ambiguous callback handling. Discovery and keys must also be bound to the trusted issuer.

10. Why are scopes insufficient for complete authorization?

Senior answer: Scopes are usually coarse capabilities such as orders.read. They do not answer whether this subject owns order 123, belongs to the same tenant, may access the customer's region, or may act while the order is in its current state.

I use scopes as one input to authorization, then enforce object ownership, tenant boundaries, roles, attributes and business invariants in the resource server. Database constraints and transaction controls may also be required.

11. What are PAR and RAR, and when would you use them?

Senior answer: Pushed Authorization Requests allow the client to send authorization parameters directly to the authorization server and use a short request URI in the browser redirect. This improves request integrity, privacy and support for large request data.

Rich Authorization Requests represent structured authorization details, such as payment amount, currency, payee and allowed action. I use them when simple scope strings are too broad for the business authorization being granted.

12. How do you design for multiple tenants or issuers?

Senior answer: I maintain an explicit allow-list of trusted issuers and bind each issuer to its metadata, keys, client configuration and expected audiences. I never use an arbitrary issuer or key URL from an unvalidated token to fetch trust material.

After cryptographic and issuer validation, I map the external subject to the correct tenant and still enforce cross-tenant object isolation. Multi-issuer support is a trust-configuration problem, not only a dynamic key lookup problem.

13. What is the difference between PKCE and DPoP?

Senior answer: PKCE protects the authorization-code exchange. It proves that the client instance exchanging the code holds the verifier corresponding to the original challenge. After the token is issued, PKCE does not protect that token from replay.

DPoP binds token use to a public/private key and requires a signed proof for token and API requests. It addresses sender constraint for access and potentially refresh tokens. The mechanisms protect different stages and can be used together.

14. How would you secure a payment-authorization flow?

Senior answer: I would use an audience-specific, least-privilege access token and consider structured authorization details to bind the authorization to amount, currency, payee and action. Sensitive payments may require recent strong authentication or step-up MFA and a sender-constrained token.

At the business layer, the API still validates amount and payee against the approved instruction, uses idempotency keys, prevents duplicate execution, records tamper-resistant audit data and applies fraud and transaction-limit policies.

15. What should an OAuth platform monitor?

Senior answer: I monitor failed authorization and token exchanges, invalid state or nonce, authorization-code reuse, refresh-token reuse, unexpected issuer/audience failures, excessive scope requests, client-authentication anomalies, revocation events, JWKS rotation failures and introspection latency.

I correlate events by safe identifiers such as client ID, issuer, subject hash, session ID or token family ID. I do not log raw access tokens, refresh tokens, authorization codes or client secrets. Monitoring must support incident response without creating a new credential-leak channel.

16. How do you prevent JWT algorithm-confusion attacks?

Senior answer: I configure an explicit algorithm allow-list for each token profile and key type. The verifier does not let the untrusted alg header choose an arbitrary verification strategy. I reject none and unexpected symmetric/asymmetric algorithms, use a mature library and keep access-token, ID-token and other JWT validation rules mutually exclusive.

17. Why should claims not be read before signature validation?

Senior answer: Anyone can construct a Base64URL Header and Payload containing arbitrary claims such as ADMIN, a victim subject or a trusted issuer. Before cryptographic and semantic validation, the content is only attacker-controlled input. It may be inspected only for safe parsing or routing under strict controls, never for an authorization decision.

18. How do you decide which claims belong in an access token?

Senior answer: I start from the intended resource server and include only claims needed on most requests that cannot be safely or efficiently obtained from trusted server-side data. I consider privacy, staleness, token size, audience isolation and whether the issuer is authoritative for the claim. I avoid turning the token into a replicated user database or complete permission graph.

19. When would you choose JWE instead of a signed JWT or opaque token?

Senior answer: I use JWE only when the protocol requires a self-contained token whose claims must remain confidential from intermediaries and the receiving parties can operate the encryption-key lifecycle safely. For many systems, a minimal opaque reference token is simpler and provides centralized control. JWE adds recipient-key distribution, rotation, algorithm and debugging complexity, so it needs a clear threat-model justification.

20. How do you handle authorization changes while a JWT is still valid?

Senior answer: A self-contained JWT is a snapshot. If a user's role changes, the token normally remains unchanged until replacement or expiry. I limit the stale window with short-lived access tokens. For urgent revocation or highly dynamic permissions, I add introspection, session/version checks, a deny-list, event propagation or server-side policy lookup. The choice is a trade-off between decentralization, latency, availability and revocation speed.

Model answer: The token has excessive audience and blast radius. Use resource indicators, service-specific audiences, least privilege and token exchange when useful.

Scenario 5 — Refresh token stolen

Model answer: Rotate on every use and track a token family. Reuse of an invalidated predecessor triggers family revocation and reauthentication. Sender constraint further reduces replay.
Production review

20. Production checklist

Authorization request

  • Code + PKCE S256.
  • Strict redirect URI.
  • State bound to session.
  • OIDC nonce.
  • Least-privilege scope.

Token issuance

  • Short access-token TTL.
  • Audience restriction.
  • Refresh rotation or sender constraint.
  • Secure client authentication.
  • No Implicit/Password Grant.

Resource server

  • Trusted issuer.
  • Algorithm allow-list.
  • Signature, issuer, audience and time.
  • Scope plus object policy.
  • No ID token as access token.

Operations

  • Test key rotation.
  • Document revocation/logout.
  • No token logging.
  • Monitor refresh reuse.
  • Incident revocation plan.

Browser/mobile

  • No embedded secret.
  • System browser for native apps.
  • Consider BFF.
  • Secure mobile storage.
  • Review XSS and CSRF separately.

Microservices

  • Distinguish user and service subject.
  • Specific audience.
  • Intentional token relay.
  • Consider token exchange.
  • Service-level authorization.
