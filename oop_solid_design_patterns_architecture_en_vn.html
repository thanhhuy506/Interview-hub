1. Big Picture

OOP gives basic modeling tools. SOLID gives maintainability principles. Design patterns solve repeated object-level design problems. Architecture patterns organize the whole application or system.

OOP → classes, objects, encapsulation, abstraction, inheritance, polymorphism SOLID → low coupling, high cohesion, testability, safe changes Design Patterns → reusable object-level solutions Architecture Patterns → boundaries, dependencies, layers, use cases, infrastructure separation

OOP

Model business concepts as objects with state and behavior.

SOLID

Reduce coupling and make code easier to test and change.

Design Patterns

Reusable solutions: Strategy, Factory, Adapter, Decorator, Observer, etc.

Architecture Patterns

System structure: Layered, Hexagonal, Clean Architecture, CQRS, DDD.

Senior mindset: Do not memorize pattern names only. Explain the problem, the pattern, trade-offs, and a real production use case.

2. OOP Basic → Advanced

What is OOP?

OOP is a programming paradigm that organizes software around objects. An object combines data and behavior. In Java, a class is a blueprint and an object is a runtime instance.

public class BankAccount {
    private final String accountNo;
    private BigDecimal balance;

    public BankAccount(String accountNo, BigDecimal initialBalance) {
        this.accountNo = accountNo;
        this.balance = initialBalance;
    }

    public void deposit(BigDecimal amount) {
        if (amount.compareTo(BigDecimal.ZERO) <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
        this.balance = this.balance.add(amount);
    }

    public BigDecimal getBalance() {
        return balance;
    }
}

Four Pillars of OOP

PillarMeaningJava ExampleWhy it matters
EncapsulationHide internal state and expose controlled behavior.private fields, methodsProtect invariants and avoid invalid state.
AbstractionExpose essential behavior and hide details.Interface, abstract classReduce coupling.
InheritanceCreate a type from another type.extendsReuse common behavior, but can create tight coupling.
PolymorphismSame contract, different implementations.Overriding, interface implementationRemoves if/else explosion.

Encapsulation is business protection

public class Order {
    private OrderStatus status;

    public void cancel() {
        if (status == OrderStatus.SHIPPED) {
            throw new IllegalStateException("Shipped order cannot be cancelled");
        }
        this.status = OrderStatus.CANCELLED;
    }
}

Real encapsulation means other classes cannot put the object into an invalid state.

Abstraction and Polymorphism

public interface PaymentGateway {
    PaymentResult charge(PaymentRequest request);
}

public class StripePaymentGateway implements PaymentGateway {

        return PaymentResult.success();
    }
}

public class OrderService {

    public OrderService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;

    public void checkout(Order order) {

Composition over Inheritance

Composition builds behavior by combining objects. It is usually more flexible than deep inheritance.

Inheritance: VipInternationalOrder extends InternationalOrder extends SpecialOrder extends Order Composition: Order has DiscountPolicy Order has ShippingPolicy Order has TaxPolicy
public class PricingService {
    private final DiscountPolicy discountPolicy;
    private final TaxPolicy taxPolicy;

    public PricingService(DiscountPolicy discountPolicy, TaxPolicy taxPolicy) {
        this.discountPolicy = discountPolicy;
        this.taxPolicy = taxPolicy;
    }

    public BigDecimal calculateFinalPrice(Order order) {
        BigDecimal discount = discountPolicy.calculateDiscount(order);
        BigDecimal tax = taxPolicy.calculateTax(order);
        return order.getTotalAmount().subtract(discount).add(tax);
    }
}

Advanced OOP Notes

  • Cohesion: a class/module should focus on one responsibility area.
  • Coupling: depend on abstractions and stable contracts, not concrete infrastructure.
  • Immutable objects: safer for multi-threading and easier reasoning.
  • Anemic domain model: object has only getters/setters and all business logic lives in services; often not ideal for rich domain.
  • God service: one service handles too many responsibilities.

3. SOLID Principles

SOLID helps create maintainable, testable, and change-friendly object-oriented code.

PrincipleMeaningCore Question
SRPSingle Responsibility PrincipleDoes this class have one main reason to change?
OCPOpen/Closed PrincipleCan we add behavior without modifying stable code?
LSPLiskov Substitution PrincipleCan subtype replace parent without breaking behavior?
ISPInterface Segregation PrincipleAre clients forced to depend on unused methods?
DIPDependency Inversion PrincipleDoes high-level logic depend on abstractions?

SRP — Single Responsibility Principle

A class should have one main responsibility. It does not mean only one method.

public class OrderService {
    private final OrderRepository orderRepository;
    private final PaymentService paymentService;
    private final EmailService emailService;

    public void placeOrder(OrderRequest request) {
        Order order = Order.create(request);
        paymentService.pay(order);
        orderRepository.save(order);
        emailService.sendOrderConfirmation(order);
    }
}

OCP — Open/Closed Principle

public interface PaymentMethod {
    PaymentResult pay(PaymentRequest request);
}

@Component("creditCard")
public class CreditCardPayment implements PaymentMethod {
    public PaymentResult pay(PaymentRequest request) {
        return PaymentResult.success();
    }
}

@Component("bankTransfer")
public class BankTransferPayment implements PaymentMethod {
    public PaymentResult pay(PaymentRequest request) {
        return PaymentResult.success();
    }
}

@Service
public class PaymentRouter {
    private final Map<String, PaymentMethod> paymentMethods;

    public PaymentRouter(Map<String, PaymentMethod> paymentMethods) {
        this.paymentMethods = paymentMethods;
    }

    public PaymentResult pay(String method, PaymentRequest request) {
        PaymentMethod paymentMethod = paymentMethods.get(method);
        if (paymentMethod == null) {
            throw new IllegalArgumentException("Unsupported payment method");
        }
        return paymentMethod.pay(request);
    }
}

LSP — Liskov Substitution Principle

Violation: subclass overrides a method and throws UnsupportedOperationException for behavior promised by parent.
public interface WithdrawableAccount {
    void withdraw(BigDecimal amount);
}

public class SavingAccount implements WithdrawableAccount {
    public void withdraw(BigDecimal amount) {
        // withdraw logic
    }
}

public class FixedDepositAccount {
    // no withdraw method because fixed deposit does not support it
}

ISP — Interface Segregation Principle

public interface Printable {
    void print(Document document);
}

public interface Scannable {
    void scan(Document document);
}

public class BasicPrinter implements Printable {
    public void print(Document document) {
        // print only
    }
}

DIP — Dependency Inversion Principle

public interface NotificationSender {
    void send(String recipient, String message);
}

public class EmailNotificationSender implements NotificationSender {
    public void send(String recipient, String message) {
        // send email
    }
}

public class UserRegistrationService {
    private final NotificationSender notificationSender;

    public UserRegistrationService(NotificationSender notificationSender) {
        this.notificationSender = notificationSender;
    }
}
Spring relation: Dependency Injection helps implement DIP by injecting abstractions into high-level services.

Factory Method

public interface NotificationSender {
    void send(String message);
}

public class NotificationSenderFactory {
    public NotificationSender create(String type) {
        return switch (type) {
            case "EMAIL" -> new EmailSender();

            default -> throw new IllegalArgumentException("Unsupported type");

Builder

public class User {
    private final String username;
    private final String email;
    private final boolean active;

    private User(Builder builder) {
        this.username = builder.username;
        this.email = builder.email;
        this.active = builder.active;
    }

    public static class Builder {
        private String username;
        private String email;
        private boolean active = true;

        public Builder username(String username) {
            this.username = username;
            return this;
        }

        public Builder email(String email) {
            this.email = email;
            return this;
        }

        public User build() {
            if (username == null || email == null) {
                throw new IllegalStateException("username and email are required");
            }
            return new User(this);
        }
    }
}

Adapter

Adapter converts an incompatible external interface into an interface expected by the application.

public interface PaymentGateway {
    PaymentResult charge(PaymentRequest request);
}

public class PspPaymentAdapter implements PaymentGateway {
    private final ExternalPspClient client;

    public PspPaymentAdapter(ExternalPspClient client) {
        this.client = client;
    }

    public PaymentResult charge(PaymentRequest request) {
        ExternalPspRequest externalRequest = mapToExternal(request);
        ExternalPspResponse response = client.makePayment(externalRequest);
        return mapToInternal(response);
    }
}

Decorator

public class LoggingPaymentGateway implements PaymentGateway {
    private final PaymentGateway delegate;

    public LoggingPaymentGateway(PaymentGateway delegate) {
        this.delegate = delegate;
    }

    public PaymentResult charge(PaymentRequest request) {
        long start = System.currentTimeMillis();
        try {
            return delegate.charge(request);
        } finally {
            System.out.println("Payment took " + (System.currentTimeMillis() - start) + "ms");
        }
    }
}

@Service
public class CheckoutFacade {

5. Architecture Design Patterns

Layered Architecture

Controller Layer ↓ Service Layer ↓ Repository Layer ↓ Database

Good for simple enterprise and CRUD applications. Risk: can become database-centric and anemic if all logic is in services and entities have no behavior.

Hexagonal Architecture / Ports and Adapters

Separates application core from external details. Domain and use cases depend on ports. Infrastructure implements adapters.

Inbound Adapter: REST Controller ↓ Inbound Port: CreateOrderUseCase ↓ Application Service / Domain Model ↓ Outbound Ports: PaymentPort, OrderRepositoryPort ↓ Outbound Adapters: JPA, WebClient, Kafka
public interface CreateOrderUseCase {
    OrderResult create(CreateOrderCommand command);
}

public interface PaymentPort {
    PaymentResult pay(Order order);
}

public class CreateOrderService implements CreateOrderUseCase {
    private final PaymentPort paymentPort;
    private final OrderRepositoryPort orderRepository;

    public OrderResult create(CreateOrderCommand command) {
        Order order = Order.create(command);
        paymentPort.pay(order);
        orderRepository.save(order);
        return OrderResult.from(order);
    }
}

Clean Architecture

Outer Layer: Controllers, DB, Web, Frameworks ↓ Interface Adapters: Presenters, Gateways, Repositories ↓ Use Cases: Application business rules ↓ Entities: Enterprise business rules

Dependencies point inward. Business rules should not depend on frameworks, database, or UI.

DDD Tactical Patterns

PatternMeaningExample
EntityObject with identity and lifecycle.Order, Customer, Account.
Value ObjectObject defined by value, usually immutable.Money, Address, Email.
AggregateConsistency boundary with aggregate root.Order aggregate contains OrderItems.
RepositoryAbstraction for retrieving/persisting aggregates.OrderRepository.
Domain ServiceDomain logic that does not belong naturally to one entity.TransferMoneyService.

CQRS

CQRS separates command/write model from query/read model.

public interface OrderCommandService {
    Long createOrder(CreateOrderCommand command);
    void cancelOrder(Long orderId);
}

public interface OrderQueryService {
    OrderDetailDto getOrderDetail(Long orderId);
    Page<OrderSummaryDto> searchOrders(OrderSearchCriteria criteria);
}

Event-Driven Architecture

Order Service publishes OrderCreated ↓ Inventory Service reserves stock Payment Service creates payment intent Email Service sends confirmation

Pattern Comparison

PatternBest ForTrade-off
LayeredSimple CRUD, common enterprise apps.Can become DB-centric.
HexagonalComplex business logic, integrations, testability.More interfaces and discipline.
Clean ArchitectureLong-lived business-critical systems.More structure upfront.
CQRSDifferent read/write models, optimized queries.More complexity.
Event-DrivenAsync workflows, decoupled services.Eventual consistency, harder debugging.

6. Common Interview Questions & Answers — English

Q1. What are the four pillars of OOP?

A: Encapsulation, abstraction, inheritance, and polymorphism. Encapsulation protects state, abstraction hides details behind contracts, inheritance models “is-a” relationships, and polymorphism allows different implementations through the same interface.

Q2. Why prefer composition over inheritance?

A: Inheritance creates tight coupling to the parent class. Composition is more flexible because behavior can be assembled from smaller components and replaced independently. In Spring, Strategy pattern and DI are common composition techniques.

Q3. Explain SOLID shortly.

A: SRP means one reason to change. OCP means open for extension but closed for modification. LSP means subclasses must be substitutable. ISP means clients should not depend on unused methods. DIP means high-level modules depend on abstractions, not details.

Q4. Which SOLID principle is related to Spring DI?

A: Dependency Inversion Principle. High-level services depend on interfaces, and Spring injects concrete implementations. This reduces coupling and improves testability.

Q5. Strategy vs Factory?

A: Factory is about object creation. Strategy is about interchangeable behavior or algorithms. A factory may locate or create strategies, but the intent is different.

Q6. Adapter vs Facade?

A: Adapter converts an incompatible interface to the expected interface. Facade simplifies a complex subsystem with a simpler API.

Q7. Which design patterns are common in Spring?

A: Singleton for beans, Proxy for AOP and transactions, Factory for bean creation, Strategy for business algorithms, Adapter for external APIs, Observer for events, Template Method for repeated flows, and Chain of Responsibility for filters/validators.

Q8. Layered vs Hexagonal Architecture?

A: Layered separates controller, service, repository, and database. Hexagonal separates core business logic from external adapters using ports. Hexagonal improves testability and protects business logic from frameworks but adds structure.

Q9. When would you use CQRS?

A: When read and write requirements are significantly different. Writes may need strict domain rules, while reads need optimized projections/search. CQRS adds complexity, so it should not be used for simple CRUD without need.

7. Tổng quan

OOP giúp model business bằng object. SOLID giúp code dễ maintain. Design patterns là giải pháp reusable cho vấn đề design thường gặp. Architecture patterns tổ chức cấu trúc toàn bộ application hoặc system.

OOP → class, object, encapsulation, abstraction, inheritance, polymorphism SOLID → low coupling, high cohesion, testability Design Patterns → giải pháp object-level reusable Architecture Patterns → boundary, dependency, layer, use case, infrastructure separation

8. OOP cơ bản → nâng cao

OOP là gì?

OOP là lập trình hướng đối tượng. Object kết hợp data và behavior. Trong Java, class là blueprint, object là instance runtime.

public class BankAccount {
    private final String accountNo;
    private BigDecimal balance;

    public BankAccount(String accountNo, BigDecimal initialBalance) {
        this.accountNo = accountNo;
        this.balance = initialBalance;
    }

    public void deposit(BigDecimal amount) {
        if (amount.compareTo(BigDecimal.ZERO) <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
        this.balance = this.balance.add(amount);
    }
}

Composition over Inheritance

Composition nghĩa là ghép behavior từ nhiều object thay vì kế thừa sâu. Trong business system, composition thường flexible hơn inheritance.

Inheritance: VipInternationalOrder extends InternationalOrder extends SpecialOrder extends Order Composition: Order has DiscountPolicy Order has ShippingPolicy Order has TaxPolicy

OOP nâng cao cần nhớ

  • Cohesion: class/module tập trung vào một nhóm responsibility rõ ràng.
  • Coupling: depend vào abstraction, không depend trực tiếp infrastructure.
  • Immutable object: dễ reasoning, an toàn hơn cho multi-thread.
  • Anemic domain model: entity chỉ có getter/setter, logic nằm hết trong service.
  • God service: một service làm quá nhiều responsibility.

9. SOLID Principles

SOLID là 5 nguyên tắc giúp code OOP maintainable, testable và dễ thay đổi hơn.

SRP

Một class nên có một responsibility chính. Không có nghĩa là chỉ được có một method.

12. Câu hỏi phỏng vấn phổ biến — Vietnamese

Q1. 4 tính chất OOP là gì?

A: Encapsulation, abstraction, inheritance, polymorphism. Encapsulation bảo vệ state và invariant. Abstraction ẩn detail sau contract. Inheritance mô hình hóa quan hệ “is-a”. Polymorphism cho phép nhiều implementation qua cùng interface.

Q2. Vì sao ưu tiên composition hơn inheritance?

A: Inheritance coupling chặt với parent class. Composition flexible hơn vì behavior được ghép từ component nhỏ và thay thế độc lập. Trong Spring, Strategy pattern và DI là cách dùng composition phổ biến.

Q3. Giải thích SOLID ngắn gọn.

A: SRP một lý do thay đổi. OCP mở rộng được mà ít sửa code cũ. LSP subclass thay parent không phá behavior. ISP không ép client depend method không dùng. DIP high-level module depend abstraction thay vì detail.

Q4. SOLID principle nào liên quan tới Spring DI?

A: DIP. Service depend interface, Spring inject implementation. Code giảm coupling và dễ test hơn.

Q5. Strategy khác Factory thế nào?

A: Factory lo tạo object. Strategy lo thay thế behavior/algorithm. Factory có thể tạo strategy, nhưng intent khác nhau.

Q6. Adapter khác Facade thế nào?

A: Adapter chuyển interface không tương thích thành interface app cần. Facade đơn giản hóa một subsystem phức tạp.

Q7. Pattern nào hay gặp trong Spring?

A: Singleton cho bean, Proxy cho AOP/transaction, Factory cho bean creation, Strategy cho business algorithm, Adapter cho external API, Observer cho event, Template Method cho processing flow, Chain of Responsibility cho filters/validators.

Q8. Layered khác Hexagonal thế nào?

A: Layered chia controller/service/repository/database, đơn giản nhưng dễ DB-centric. Hexagonal tách core business khỏi external adapters bằng ports, tăng testability nhưng cần structure và discipline hơn.

Q9. Khi nào dùng CQRS?

A: Khi read và write requirements khác biệt lớn. Write cần domain validation/consistency, read cần projection/search tối ưu. Không nên dùng cho CRUD đơn giản nếu không có nhu cầu thật.
