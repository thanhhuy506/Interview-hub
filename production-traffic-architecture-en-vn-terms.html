Production Architecture Deep Dive

DNS → CDN → WAF → Load Balancer → API Gateway

In a production system, user traffic normally does not go directly to an application server. It passes through multiple infrastructure layers. Each layer solves a different problem: locating the correct endpoint, reducing latency, protecting the application, distributing traffic, controlling APIs, routing to the correct service, and improving reliability.

1. What problem does each layer solve?

LayerMain responsibilityWithout itTypical production decision
DNS Resolve a domain name to an endpoint. The client does not know where to connect. Geo routing, failover routing, weighted routing.
CDN Serve cacheable content closer to users. Higher latency and more origin traffic. Cache static files, images, video, selected GET APIs.
WAF Inspect and filter Layer 7 HTTP traffic. Web attacks and bots reach the application directly. Managed rules, bot control, rate limiting.
Load Balancer Distribute requests across healthy backends. One server becomes a bottleneck or single point of failure. Round robin, least connections, weighted traffic.
API Gateway Centralize API policy and routing. Authentication, quotas, routing, and rate limits are duplicated across services. JWT validation, API versioning, request routing.

2. DNS — Domain Name System (hệ thống phân giải tên miền)

DNS does not forward the HTTP request itself. Its main job is to answer: “Which IP address or endpoint should this domain connect to?”

How DNS resolution works

Browser / OS cache

If the record is still cached and its TTL has not expired, the client can reuse it immediately.

Recursive Resolver (DNS resolver trung gian)

Usually provided by an ISP, company network, or public DNS provider.

Root → TLD → Authoritative DNS

The resolver walks the DNS hierarchy until it finds the Authoritative DNS (DNS có thẩm quyền) server that owns the record.

Return record + TTL

The result is cached according to TTL — Time To Live (thời gian bản ghi được phép cache).

Why do we need DNS?

Decoupling

Hide infrastructure changes

Servers and IP addresses can change while the public domain remains stable.

Routing

Choose a region or endpoint

DNS can route users by geography, weight, latency, or health.

Failover

Move traffic after failure

Health-aware DNS can route traffic away from an unhealthy region.

Common DNS production problems

ProblemWhy it happensImpactSolution
Slow propagation Old DNS records are still cached. Some users still reach the old endpoint. Lower TTL before migration, keep both environments running during the transition.
Provider outage The authoritative DNS provider becomes unavailable. Users cannot resolve the domain. Use secondary DNS, multi-provider DNS, or Anycast DNS.
Failover is too slow Long TTL and slow health detection. Traffic still reaches a failed region. Use health-based routing, reasonable TTLs, and a Global Load Balancer when faster failover is required.
Senior-level point: DNS failover is not instant because clients and resolvers may still cache old records. For critical systems, combine DNS with a Global Load Balancer (bộ cân bằng tải toàn cầu) or Anycast (nhiều server cùng quảng bá một IP để user đi tới điểm gần/khỏe nhất).

3. CDN — Content Delivery Network (mạng phân phối nội dung)

A CDN uses many Edge Servers (máy chủ biên đặt gần người dùng). If the requested content is already cached at the edge, the CDN returns it immediately without calling the origin.

Cache Hit

Fast path

User → CDN Edge → Response

The origin is not called.

Cache Miss

Origin path

User → CDN Edge → Origin → Cache → Response

The next request may be served from the edge.

Why use a CDN?

  • Reduce Latency (độ trễ).
  • Reduce Origin Load (tải lên server gốc).
  • Absorb large traffic spikes.
  • Reduce bandwidth usage at the origin.
  • Improve global user experience.

What should be cached?

ContentShould cache?ReasonRecommended strategy
Versioned JS/CSSYesImmutable by content hashVery long TTL + hashed file name
Images / videoYesStatic and largeEdge caching + compression
Public product detailOften yesRead-heavy, updates less frequentlyShort TTL + invalidation
Private user profileUsually no shared cachePersonalized dataPrivate cache or no-store
Payment / order creationNoState-changing requestBypass CDN cache

Important CDN failure cases

Stale Cache (cache cũ, dữ liệu không còn mới)

An admin updates a product, but the CDN still serves the old value.

Solution: cache invalidation, purge, versioned URLs, shorter TTL, or stale-while-revalidate.

Cache Stampede (nhiều request cùng cache miss rồi dồn xuống backend)

A hot cache entry expires and thousands of requests hit the origin at once.

Solution: request coalescing, TTL jitter, origin shield, soft TTL, stale-while-revalidate.

Wrong Cache Key (khóa cache thiết kế sai)

If important query parameters, headers, or cookies are not part of the cache key, users may receive incorrect data.

Solution: define the cache key explicitly and keep private responses out of shared caches.

Origin Overload

A CDN cannot cache every request. Personalized and write traffic still reaches the backend.

Solution: autoscaling, Redis, database scaling, queues, and rate limiting are still required.

Example cache policy

Static files:
Cache-Control: public, max-age=31536000, immutable

Public product API:
Cache-Control: public, max-age=30, stale-while-revalidate=60

Private user response:
Cache-Control: private, no-store

4. WAF — Web Application Firewall (tường lửa ứng dụng web)

A WAF inspects Layer 7 HTTP/HTTPS requests. It can inspect URLs, headers, query parameters, request bodies, IP reputation, and request behavior before traffic reaches the application.

Threat

SQL Injection (chèn câu lệnh SQL độc hại)

The attacker sends crafted input to manipulate database queries.

Threat

XSS — Cross-Site Scripting (chèn script độc hại vào trang web)

The attacker injects script content that later runs in another user's browser.

Threat

Bot Abuse (lạm dụng bằng bot tự động)

Bots may scrape data, brute-force accounts, or create huge request volumes.

WAF is defense-in-depth

Defense-in-depth (phòng thủ nhiều lớp) means you do not rely on one security layer. A WAF does not replace secure coding, input validation, authorization, parameterized queries, secrets management, dependency patching, or strong authentication.

Common WAF problems

ProblemMeaningSolution
False Positive (chặn nhầm request hợp lệ) A legitimate request is blocked. Start rules in count/log mode, tune exceptions by endpoint, monitor blocked traffic.
False Negative (không phát hiện request độc hại) A malicious request passes through. Use updated managed rules and keep validation inside the application.
Overly broad rule A large range of legitimate users is blocked. Scope the rule by route, country, IP, or request behavior.
Added latency Heavy inspection adds processing time. Remove unnecessary rules and carefully tune body inspection.

Rate Limiting (giới hạn số request trong một khoảng thời gian)

/login
- limit by account
- also limit by IP
- exponential backoff
- bot detection
- MFA / risk-based authentication

/search
- limit requests per IP or API key

/payment
- rate limiting
- idempotency key
- fraud/risk checks

5. Load Balancer (bộ cân bằng tải)

A Load Balancer distributes traffic across multiple instances, VMs, containers, or Kubernetes pods. Its main goal is to enable Horizontal Scaling (mở rộng bằng cách tăng số lượng instance) and prevent one machine from becoming a bottleneck.

Common algorithms

Round Robin (chia lần lượt)

Requests are distributed one by one across available backends.

Least Connections (ưu tiên server có ít kết nối hơn)

Traffic goes to the backend with fewer active connections.

Weighted Routing (phân phối theo trọng số)

Some instances receive more traffic than others, useful for different server sizes or canary rollout.

Health Checks (kiểm tra tình trạng service)

  • Liveness (service còn sống hay không): Is the process alive?
  • Readiness (service đã sẵn sàng nhận traffic chưa): Can it safely receive traffic now?
  • Dependency check: Does the application have the critical dependencies it needs?
Do not make readiness depend on every minor dependency. Otherwise, one small dependency failure can cause the Load Balancer to remove the entire application fleet.

Common Load Balancer problems

Uneven Load (tải phân phối không đều)

One server processes requests more slowly than the others.

Solution: least connections, latency-aware routing, autoscaling based on queue depth and latency.

Sticky Session (ghim một user vào một server)

A user's session is tied to one server, creating state and failover problems.

Solution: prefer stateless services or store session state in Redis, a database, or tokens.

Retry Storm (bão retry, nhiều tầng cùng retry làm traffic tăng mạnh)

The client, Load Balancer, Gateway, and service all retry during a failure.

Solution: retry budget, exponential backoff + jitter, timeouts, retry only idempotent operations.

Connection Draining (đợi request đang chạy hoàn tất trước khi gỡ instance)

During deployment, an instance is terminated while requests are still active.

Solution: deregistration delay, graceful shutdown, readiness false before termination.

6. API Gateway (cổng quản lý API)

An API Gateway sits in front of backend services and centralizes cross-cutting concerns such as authentication, routing, rate limiting, API versioning, quotas, and observability.

Security

Authentication (xác thực danh tính)

Validate JWTs, API keys, scopes, and claims before traffic reaches the service.

Routing

Path-based routing

/orders/* → Order Service
/users/* → User Service

Control

Quota (hạn mức sử dụng)

Control request volume by user, API key, customer, or tenant.

When is an API Gateway useful?

  • You have many public APIs or microservices.
  • You need centralized authentication and common policy enforcement.
  • You need API versioning and controlled deprecation.
  • You need rate limits or quotas per customer or tenant.
  • You want external clients to be isolated from the internal service topology.

Common Gateway problems

ProblemWhy it is dangerousSolution
Bottleneck (điểm nghẽn) All public API traffic passes through one layer. Keep it stateless, scale horizontally, deploy multi-zone, capacity test.
SPOF — Single Point of Failure (điểm lỗi duy nhất) If the Gateway fails, many APIs fail together. High availability, multiple zones, health checks, failover.
Business logic inside Gateway The Gateway becomes a large, hard-to-maintain application. Keep business logic in services. Keep only shared policies in the Gateway.
Timeout mismatch Client, Gateway, and service timeouts do not align. Design a timeout budget from outside to inside.
Large file upload WAF or Gateway may have request-body size limits. Use object storage and pre-signed URLs for large uploads.
Important: Authentication can be centralized at the Gateway, but sensitive Authorization (phân quyền) decisions should still be enforced by the service because business rules belong there.

7. Service Discovery (cơ chế khám phá service)

In a microservice system, service instances are dynamic. Containers restart, pods move to another node, autoscaling creates new instances, and old instances disappear. Because of that, one service should not hard-code the IP address of another service.

Core idea: Service Discovery answers the question: “Where is the healthy instance of Service B right now?”

Why do we need Service Discovery?

Dynamic infrastructure

Instances change constantly

In Kubernetes or autoscaling environments, IP addresses are temporary. A service instance can disappear and be recreated with a different IP.

Decoupling

No hard-coded endpoints

Service A should call a logical name such as order-service instead of a fixed IP like 10.0.1.24.

Resilience

Route only to healthy instances

Discovery systems usually work together with Health Checks (kiểm tra tình trạng service) to avoid dead instances.

Main components

ComponentMeaningResponsibility
Service Registry (sổ đăng ký service) A database of available service instances Stores service name, IP, port, health status, metadata
Service Registration (đăng ký service) An instance announces itself Example: Order Service starts and registers its endpoint
Health Check (kiểm tra trạng thái) Determines whether the instance is alive and ready Unhealthy instances are removed or ignored
Service Lookup (tra cứu service) A caller asks where the destination service is Returns one or more healthy endpoints

Client-Side Discovery (client tự tìm service)

In client-side discovery, the calling service queries the registry directly, gets a list of healthy instances, and chooses one instance itself. 

Service A
   |
   | query registry
   v
Service Registry
   |
   | returns:
   | 10.0.1.10:8080
   | 10.0.1.11:8080
   | 10.0.1.12:8080
   v
Service A chooses one instance
   |
   v
Service B

Advantages

  • One less network hop.
  • Client can implement custom load-balancing logic.
  • Fast when registry data is cached locally.

Disadvantages

  • Every client must understand discovery logic.
  • Client libraries can become language-specific.
  • More complexity is pushed into application code.

Server-Side Discovery (phía trung gian tìm service thay cho client)

In server-side discovery, the caller sends a request to a Load Balancer, proxy, API Gateway, or service mesh component. That infrastructure layer performs service lookup and forwards the request. 

Service A
   |
   v
Load Balancer / Proxy / Service Mesh
   |
   | lookup healthy backend
   v
Service Registry
   |
   v
Service B instance

Advantages

  • Application code is simpler.
  • Discovery logic is centralized in infrastructure.
  • Works better in polyglot systems with many languages.

Disadvantages

  • Adds an infrastructure dependency.
  • Proxy or Load Balancer must be highly available.
  • May add another network hop.

How Kubernetes handles Service Discovery

Kubernetes already provides built-in service discovery. Applications normally call a stable Service Name (tên service ổn định) instead of calling Pod IP addresses directly. 

order-service
     |
     | DNS lookup
     v
order-service.default.svc.cluster.local
     |
     v
Kubernetes Service
     |
     +--> Pod A: 10.244.1.20
     +--> Pod B: 10.244.2.18
     +--> Pod C: 10.244.3.11

Kubernetes DNS, usually powered by CoreDNS (DNS nội bộ của Kubernetes), resolves the service name. The Kubernetes Service provides a stable virtual endpoint and routes traffic to healthy Pods.

Senior-level point: In Kubernetes, you usually do not need Eureka just for basic service discovery. Kubernetes Service + CoreDNS already solve the core discovery problem. A separate registry is only useful when you have additional cross-platform or non-Kubernetes requirements.

Service Discovery vs Load Balancer

DimensionService DiscoveryLoad Balancer
Main question “Where are the available service instances?” “Which healthy instance should receive this request?”
Main responsibility Maintain and locate service endpoints Distribute traffic across endpoints
Can they work together? Yes. Discovery finds healthy instances, then the Load Balancer chooses one.

Common production problems

Stale Registry Data (registry giữ thông tin instance đã chết)

An instance disappears, but the registry still advertises it.

Solution: short health-check intervals, heartbeats, TTL-based registration, active health checking, and connection retry to another instance.

Registry Outage (service registry bị lỗi)

If every request depends on a live registry lookup, an outage can affect the entire system.

Solution: registry cluster, local caching, multiple replicas, graceful fallback.

Thundering Herd (nhiều client cùng lúc query registry)

Many services refresh discovery data at the same time.

Solution: local caching, jittered refresh intervals, push-based updates where supported.

Split Brain (các registry node có trạng thái không đồng nhất)

Different registry nodes disagree about which instances are healthy.

Solution: quorum-based consistency, leader election, strong operational monitoring.

Common technologies

TechnologyTypical useNotes
Kubernetes Service + CoreDNS Kubernetes-native discovery Recommended default inside Kubernetes clusters
Consul Service registry + health checking + multi-environment discovery Useful across VMs, containers, and multiple platforms
Netflix Eureka Application-level service registry Common in older Spring Cloud / Netflix OSS architectures
etcd Distributed key-value store Often used as infrastructure metadata store, including by Kubernetes internally
Service Mesh Proxy-based discovery, routing, mTLS, retries, observability Examples include Istio or Linkerd

9. TLS / HTTPS

TLS Termination (điểm giải mã kết nối HTTPS) can happen at the CDN, Load Balancer, or API Gateway.

Edge TLS Termination

User ↔ CDN/WAF uses HTTPS. The edge decrypts traffic for inspection or caching and then re-encrypts it to the origin.

mTLS — Mutual TLS (TLS xác thực hai chiều)

Both client and server validate certificates. This is common in service-to-service zero-trust environments.

10. Real Production Failure Cases

Case A — Flash sale traffic increases 50x

CDN absorbs cacheable traffic

Static files and public GET responses should not all hit the origin.

WAF and rate limiting block abuse

Bots should not consume the same backend capacity as real customers.

Load Balancer spreads requests

Backend instances scale horizontally.

Gateway enforces API quotas

Protect sensitive endpoints such as checkout and payment.

Services protect downstream dependencies

Use queues, caching, connection-pool limits, backpressure, and circuit breakers.

Case B — Admin updates a product, but users still see the old price

Stale data may exist at many layers: Browser Cache → CDN → API Cache → Redis → Database Replica.
  1. Invalidate or version cache entries by product ID.
  2. At checkout, re-read authoritative price and inventory.
  3. UI can display cached data, but the final transaction must validate fresh business data.
  4. If the price changed, return a clear conflict and let the user confirm again.

Case C — One slow dependency causes system-wide congestion

  • Set timeouts for every network hop.
  • Do not retry forever.
  • Use Exponential Backoff (tăng dần thời gian chờ giữa các lần retry).
  • Add Jitter (độ ngẫu nhiên trong thời gian retry để tránh nhiều request retry cùng lúc).
  • Use a Circuit Breaker (cơ chế tạm ngắt gọi tới dependency đang lỗi).
  • Use Bulkhead Isolation (cô lập tài nguyên để một dependency không làm nghẽn toàn hệ thống).

Case D — A new deployment causes 5xx errors

  • Readiness must pass before traffic is sent.
  • Use a Canary Deployment (triển khai thử cho một phần nhỏ traffic).
  • Monitor error rate, p95, p99, and saturation.
  • Automatically roll back when SLOs degrade.
  • Use connection draining before terminating old instances.

1. User opens:
   https://api.example.com/products/123
        |
2. DNS resolves api.example.com
        |
3. Client connects to CDN / edge
        |
4. CDN checks cache
   |-- cache hit  -> return immediately
   |
   '-- cache miss -> forward to origin path
        |
5. WAF inspects request
   |-- malicious -> BLOCK / RATE LIMIT
   '-- allowed   -> continue
        |
6. Load Balancer chooses a healthy entry point
        |
7. API Gateway:
   |-- validate JWT
   |-- check rate limit
   |-- apply route
   '-- /products/* -> Product Service
        |
8. Service Discovery:
   |-- resolve product-service
   '-- find healthy service instance
        |
9. Product Service:
   |-- local cache / Redis
   '-- database / read replica
        |
10. Response returns:
    Service -> Gateway -> LB -> WAF/CDN -> User
        |
11. CDN may cache the response if policy allows

13. Production Checklist

  • Reasonable DNS TTL and tested failover plan
  • Automatic TLS certificate renewal
  • Reviewed CDN cache key design
  • Content hash for static assets
  • Private data never placed in public shared cache
  • WAF rules tuned to reduce false positives
  • Rate limits for login, search, payment
  • Readiness-based Load Balancer health checks
  • Service Discovery has health-aware registration
  • Registry/DNS discovery has caching and failover
  • Stateless application where possible
  • Graceful shutdown and connection draining
  • Explicit timeout budget
  • Retry with backoff and jitter
  • Idempotency for create/payment operations
  • Autoscaling based on meaningful metrics
  • Canary or blue-green deployment
  • Centralized logs, metrics, and traces
  • Alerts based on SLOs, not only CPU
  • Realistic load testing

14. Senior Engineer Interview Answer

“When I deploy an application to production, I normally do not expose application servers directly to clients. I design the request path in layers, and each layer has a clear responsibility.

DNS resolves the public domain and can support regional routing or failover. A CDN reduces latency and origin traffic by serving cacheable content from edge locations. A WAF protects Layer 7 traffic from common web attacks and abuse. A Load Balancer distributes traffic across healthy instances so the application can scale horizontally. If the system has many APIs or microservices, an API Gateway centralizes authentication, rate limiting, routing, versioning, and API policies. Service Discovery allows services to find healthy instances dynamically instead of hard-coding IP addresses.

I also avoid over-engineering. A small application may only need DNS and a managed Load Balancer. CDN, WAF, and API Gateway should be introduced when there is a real requirement for performance, security, scale, or API governance.

The important part is not only knowing the components, but understanding their failure modes: DNS propagation, stale cache, cache stampede, WAF false positives, retry storms, sticky sessions, Gateway bottlenecks, incorrect health checks, and unsafe deployments.”
