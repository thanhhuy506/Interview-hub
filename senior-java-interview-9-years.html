1. Java Core & Collections

Internal implementation, contracts, complexity, and design decisions.

6 questions
Senior answer

HashMap stores entries in an array of buckets. When we call put(key, value), Java first calculates a spread hash from key.hashCode(), then finds the bucket index using (table.length - 1) & hash.

If the bucket is empty, the entry is inserted directly. If another entry already exists, HashMap compares the hash and then uses equals() to find the same logical key. A collision is stored in a linked list, and in Java 8+, a heavily-collided bucket may be converted into a red-black tree when the bucket reaches the treeification threshold and the table is large enough.

The average lookup complexity is O(1), but poor hash distribution can degrade performance. Resizing happens when the number of entries exceeds capacity × loadFactor. HashMap is not thread-safe; concurrent structural changes can cause lost updates and inconsistent results.

Important details

  • Default load factor: 0.75.
  • Treeification threshold: 8 entries.
  • Tree bins help reduce worst-case lookup toward O(log n).
  • Correct equals() and hashCode() are required.

Production perspective

  • Use immutable keys where possible.
  • Pre-size large maps to reduce resize overhead.
  • Use ConcurrentHashMap for shared mutable maps.
  • A bad custom hash function can create a performance hotspot.
Giải thích tiếng Việt: HashMap dùng mảng bucket. Hash quyết định bucket, còn equals() xác định đúng key. Collision được lưu bằng linked list hoặc red-black tree. Cần nhấn mạnh cơ chế resize, độ phức tạp và HashMap không thread-safe.

Senior answer

If two objects are equal according to equals(), they must return the same hash code. The reverse is not required because different objects may have the same hash code.

Collections such as HashMap and HashSet first use the hash code to locate a bucket, then use equals() to find the matching object. Overriding only one method breaks this lookup process and can produce duplicate logical keys or failed lookups. 

public final class CustomerKey {
    private final String tenantId;
    private final String customerId;

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;
        if (!(obj instanceof CustomerKey)) return false;
        CustomerKey other = (CustomerKey) obj;
        return Objects.equals(tenantId, other.tenantId)
            && Objects.equals(customerId, other.customerId);
    }

    @Override
    public int hashCode() {
        return Objects.hash(tenantId, customerId);
    }
}
Giải thích tiếng Việt: Hai object bằng nhau thì bắt buộc cùng hash code. Nếu override equals() mà không override hashCode(), HashMap có thể tìm sai bucket và không lấy được value.
Senior answer

I choose based on the dominant access pattern, not only Big-O notation. ArrayList provides O(1) random access, good CPU cache locality, and usually lower memory overhead. Appending is amortized O(1), although resizing occasionally copies the backing array.

LinkedList has O(n) random access and each element requires node pointers. Insertion is O(1) only after we already have the target node; finding that node is still O(n). In most business applications, ArrayList performs better. For queue or deque behavior, I usually choose ArrayDeque instead of LinkedList.

Giải thích tiếng Việt: Không nên chỉ nói LinkedList insert O(1). Muốn insert đúng vị trí vẫn phải duyệt O(n). ArrayList thường nhanh hơn do cache locality và ít object hơn.
Senior answer

The implementation depends on the data type and API. Object arrays are commonly sorted with a stable TimSort-style algorithm because preserving the order of equal elements is useful. Primitive arrays commonly use Dual-Pivot Quicksort because it performs well in memory and avoids object comparison overhead.

The important design point is that no single sorting algorithm is best for every input. Stability, memory usage, primitive versus object data, nearly-sorted input, and parallelism all influence the implementation choice.

Interview depth

  • Know stable vs unstable sorting.
  • Know average O(n log n).
  • Do not claim one algorithm is used everywhere.

Usage

  • Use a clear comparator.
  • A comparator must be consistent and transitive.
  • For huge data, database or external sorting may be better.
Giải thích tiếng Việt: Java chọn thuật toán khác nhau tùy object array hay primitive array. Senior answer nên nói về stability, memory và trade-off, không chỉ nhớ tên thuật toán.
Senior answer

Optional makes the absence of a return value explicit and encourages callers to handle it intentionally. It is useful as a method return type, especially for repository or lookup operations.

I avoid using Optional as an entity field, DTO field, or method parameter because it complicates serialization, frameworks, and method signatures. I also avoid calling get() without checking. Optional improves API clarity, but it is not a universal replacement for null.

Giải thích tiếng Việt: Optional phù hợp nhất cho return type để biểu diễn “có thể không có dữ liệu”. Không nên lạm dụng trong field, DTO hoặc parameter.
Senior answer

An immutable object cannot change after construction. I make the class final, fields private and final, initialize all state in the constructor, provide no mutating methods, and use defensive copies for mutable input or output objects.

Immutability simplifies reasoning, makes sharing across threads safer, prevents accidental state corruption, and works well for value objects and map keys. The trade-off is additional object allocation when values change.

Giải thích tiếng Việt: Immutable object không đổi state sau khi tạo. Nó giúp thread-safety và giảm side effect, nhưng mỗi lần thay đổi phải tạo object mới.

2. Multithreading & Concurrency

Visibility, atomicity, ordering, thread pools, and production race conditions.

7 questions
Senior answer

Code is thread-safe when multiple threads can execute it concurrently without violating its invariants or producing incorrect results. The main risk is shared mutable state. An operation such as count++ is not atomic; it contains read, calculate, and write steps that can interleave.

I first try to remove shared mutable state through immutability, local variables, partitioning, or message passing. If sharing is necessary, I use the smallest suitable coordination mechanism: atomics, concurrent collections, locks, synchronization, or database constraints.

Giải thích tiếng Việt: Thread-safe không có nghĩa là “có synchronized”. Cách tốt nhất thường là giảm shared mutable state trước, rồi mới chọn cơ chế đồng bộ phù hợp.
Senior answer

volatile provides visibility and ordering guarantees. A thread reading a volatile variable sees the most recently published write, and volatile access creates a happens-before relationship around that variable.

It does not make compound actions atomic. For example, counter++ remains unsafe because two threads can read the same value and overwrite each other. Volatile is suitable for status flags, configuration references, or single-writer publication. For compound state changes, I use an atomic type or locking. 

private volatile boolean shutdownRequested;

public void shutdown() {
    shutdownRequested = true;
}

public void runLoop() {
    while (!shutdownRequested) {
        doWork();
    }
}
Giải thích tiếng Việt: volatile bảo đảm thread khác nhìn thấy giá trị mới và hạn chế reordering, nhưng không bảo đảm atomicity cho thao tác nhiều bước như i++.
Senior answer

I use synchronized for simple critical sections because it is concise, automatically releases the monitor, and is easier to review. I use ReentrantLock when I need tryLock(), interruptible acquisition, multiple conditions, timed waits, or explicit fairness configuration.

The choice is not mainly about raw speed. Modern JVMs optimize synchronized well. The more important concerns are correctness, lock scope, contention, failure handling, and observability.

Giải thích tiếng Việt: synchronized phù hợp khi logic đơn giản. Lock dùng khi cần timeout, tryLock, interrupt hoặc nhiều Condition. Senior nên nhấn mạnh lock scope và contention.
Senior answer

Thread-pool sizing depends on workload, latency targets, downstream capacity, and blocking ratio. For CPU-bound work, a starting point is close to the number of CPU cores. For blocking I/O, a common estimate is: threads ≈ cores × (1 + wait time / compute time).

I do not apply the formula blindly. I also define a bounded queue, a rejection policy, meaningful thread names, metrics, and shutdown behavior. An unbounded queue can hide overload until latency and memory usage become dangerous. The pool must also respect limits of databases and remote services.

Configuration

  • corePoolSize
  • maximumPoolSize
  • bounded work queue
  • keepAliveTime
  • RejectedExecutionHandler

Monitor

  • active threads
  • queue size
  • task latency
  • rejection count
  • downstream saturation
Giải thích tiếng Việt: Không chỉ chọn core/max pool size. Cần bounded queue, rejection policy, metric và phải phù hợp với DB connection pool hoặc giới hạn downstream.
Senior answer

A deadlock happens when threads wait forever for locks held by each other. I prevent it by enforcing a consistent lock order, minimizing nested locks, keeping critical sections small, and using timed lock acquisition where appropriate.

In production, I inspect thread dumps and look for blocked threads and ownership cycles. I correlate the dump with request traces and lock-related metrics. The fix should remove the circular dependency, not only increase timeouts.

Giải thích tiếng Việt: Cách phòng ngừa phổ biến nhất là lock ordering thống nhất. Khi debug dùng thread dump để tìm thread BLOCKED và vòng chờ lock.
Senior answer

CompletableFuture represents a value that will be available later and allows us to build asynchronous pipelines. I use thenApply for transformation, thenCompose for dependent asynchronous calls, and thenCombine for independent calls.

The common problems are accidentally using the shared common pool, blocking with get() or join(), missing timeout handling, losing tracing context, and creating more parallel work than downstream systems can handle. In server applications, I normally use an explicitly configured executor and define exception and timeout behavior. 

CompletableFuture<Profile> profile =
    CompletableFuture.supplyAsync(() -> profileClient.load(userId), ioExecutor);

CompletableFuture<List<Order>> orders =
    CompletableFuture.supplyAsync(() -> orderClient.load(userId), ioExecutor);

return profile
    .thenCombine(orders, UserDashboard::new)
    .orTimeout(2, TimeUnit.SECONDS)
    .exceptionally(this::fallbackDashboard);
Giải thích tiếng Việt: CompletableFuture giúp chạy và kết hợp task bất đồng bộ. Cần tránh dùng common pool tùy tiện, tránh block, và phải có timeout/fallback.
Senior answer

ConcurrentHashMap allows concurrent reads and updates without locking the entire map. Modern implementations use volatile reads, CAS operations, and synchronized access at bucket level during structural changes.

Individual methods are thread-safe, but a sequence of methods may still have a race condition. I use atomic compound APIs such as putIfAbsent, compute, or computeIfAbsent instead of a separate check-then-act sequence. 

// Unsafe compound logic
if (!cache.containsKey(key)) {
    cache.put(key, loadValue(key));
}

// Atomic map operation
return cache.computeIfAbsent(key, this::loadValue);
Giải thích tiếng Việt: Mỗi method riêng lẻ thread-safe, nhưng chuỗi containsKey rồi put vẫn có race condition. Nên dùng atomic API như computeIfAbsent.

3. Spring Boot & Transaction Management

Proxy behavior, bean lifecycle, dependency design, and data consistency.

6 questions
Senior answer

Constructor injection makes mandatory dependencies explicit, allows fields to be final, supports immutability, and makes unit tests easy without starting Spring. It also prevents partially initialized objects.

A constructor with too many dependencies is useful design feedback. It often means the class has too many responsibilities and should be decomposed.

Giải thích tiếng Việt: Constructor injection giúp dependency bắt buộc rõ ràng, dễ test, dùng final field. Quá nhiều dependency cũng là dấu hiệu class vi phạm SRP.
Senior answer

In the common proxy-based Spring transaction model, self-invocation bypasses the proxy. Therefore, calling a transactional method through this.method() does not trigger new transactional advice such as starting a transaction or applying a different propagation level.

I usually move the transactional boundary to another Spring bean, redesign the service boundary, or place the annotation on the externally-invoked public method. Injecting the bean into itself is possible but normally makes the design harder to understand.

Giải thích tiếng Việt: Spring transaction thường chạy qua proxy. Gọi method trong cùng object không đi qua proxy nên annotation có thể không có hiệu lực.
Senior answer

REQUIRED joins the current transaction or creates one if none exists. It is the default and fits most business operations. REQUIRES_NEW suspends the outer transaction and starts an independent transaction.

For example, I may save a payment audit record in a new transaction so the failure evidence remains even if the main payment transaction rolls back. However, overusing REQUIRES_NEW consumes additional database connections and can create confusing partial commits.

Giải thích tiếng Việt: REQUIRED dùng chung transaction hiện tại. REQUIRES_NEW tạo transaction độc lập, phù hợp một số audit log nhưng có nguy cơ partial commit và tốn connection.
Senior answer

A circular dependency exists when bean A depends on bean B and bean B depends directly or indirectly on bean A. Constructor injection exposes the problem early because Spring cannot construct either object first.

I treat it as a design smell. Typical fixes are extracting a third service, introducing an event, moving orchestration to a higher-level component, or separating read and write responsibilities. @Lazy can break the cycle technically, but it should not be the default architectural fix.

Giải thích tiếng Việt: Circular dependency thường cho thấy responsibility bị trộn. Nên refactor boundary thay vì chỉ dùng @Lazy để che vấn đề.
Senior answer

When an entity is managed inside the persistence context, Hibernate keeps track of its original state. If the entity changes, Hibernate detects the difference and generates an update during flush. We do not always need to call save() again for a managed entity.

Flush synchronizes pending changes to the database, but it does not commit the transaction. It can happen before commit, before some queries, or when called explicitly. I use explicit flush only when I need database constraints or generated SQL to be executed at a specific point.

Giải thích tiếng Việt: Dirty checking tự phát hiện entity bị đổi trong persistence context. Flush đẩy SQL xuống DB nhưng chưa commit transaction.
Senior answer

N+1 happens when one query loads a list of parent entities and then N additional queries load related data for each parent. It often appears because lazy relationships are accessed inside a loop.

I first confirm it using SQL logs, tracing, or database metrics. Depending on the use case, I use a fetch join, entity graph, DTO projection, batch fetching, or a dedicated query. I avoid changing every relationship to EAGER because that creates different performance and memory problems.

Giải thích tiếng Việt: N+1 là 1 query lấy danh sách và N query lấy relation. Fix theo use case bằng fetch join, projection, entity graph hoặc batch fetching, không nên đổi tất cả thành EAGER.

4. Database, Indexing & Locking

B+Tree internals, isolation, execution plans, and data correctness.

6 questions
Senior answer

A B+Tree index is a balanced, multi-level structure optimized for storage pages. Internal nodes guide the search, while leaf nodes contain indexed keys and row references, usually ordered and linked for efficient range scans.

Because each node contains many keys, the tree has a small height, so the database needs only a few page reads for a lookup. B+Trees support equality, prefix, range, and ordered access well. The trade-off is additional storage and write overhead because inserts, updates, and deletes must maintain the index.

Giải thích tiếng Việt: B+Tree có fan-out lớn nên chiều cao thấp. Leaf node có thứ tự và liên kết, vì vậy vừa tìm equality tốt vừa scan range tốt.
Senior answer

I design a composite index from real query patterns. Column order matters because the index is organized from left to right. I usually place equality-filter columns first, then range or sorting columns, while also considering selectivity and index reuse.

For example, an index on (tenant_id, status, created_at) can support queries filtered by tenant, tenant plus status, and tenant plus status plus a created-at range. It normally cannot efficiently support a query filtering only by created_at. 

CREATE INDEX idx_order_tenant_status_created
ON orders (tenant_id, status, created_at DESC);
Giải thích tiếng Việt: Composite index phải dựa vào query. Quy tắc leftmost prefix rất quan trọng; thứ tự cột quyết định index dùng được cho điều kiện nào.
Senior answer

Isolation controls how concurrent transactions observe each other. Higher isolation reduces anomalies but may increase locking, retries, and latency.

Read Committed prevents dirty reads and is a common default. Repeatable Read gives a more stable view during a transaction, although exact behavior depends on the database implementation. Serializable provides the strongest isolation by making concurrent execution behave like a serial order, but it may abort transactions or reduce concurrency.

I choose isolation based on business invariants. For critical state transitions, I may combine normal isolation with optimistic locking, explicit row locks, or unique constraints instead of making every transaction serializable.

Giải thích tiếng Việt: Isolation càng cao thì consistency mạnh hơn nhưng concurrency thấp hơn hoặc retry nhiều hơn. Phải chọn theo business invariant, không chọn mức cao nhất cho mọi API.
Senior answer

Optimistic locking assumes conflicts are uncommon. A version column is checked during update, and if another transaction already changed the row, the update fails and the application can retry or return a conflict.

Pessimistic locking acquires a database lock, such as SELECT ... FOR UPDATE, before the change. It is useful when conflicts are frequent and the protected section is short, but it reduces concurrency and can contribute to deadlocks.

I normally prefer optimistic locking for user-driven updates and pessimistic locking for short, high-contention critical sections where retrying after expensive work would be risky.

Giải thích tiếng Việt: Optimistic dùng version và phù hợp khi conflict ít. Pessimistic khóa row trước, phù hợp critical section ngắn nhưng có thể gây wait và deadlock.
Senior answer

I start with evidence: query latency, frequency, rows returned, parameter values, lock wait, and execution plan. I compare estimated rows with actual rows using tools such as EXPLAIN ANALYZE.

I look for full scans on large tables, poor join order, incorrect cardinality estimates, repeated nested loops, sorting or spilling, missing indexes, non-sargable predicates, and over-fetching. Then I change one thing at a time and measure again. Sometimes the correct fix is query redesign, partitioning, caching, or reducing result size—not simply adding an index.

Giải thích tiếng Việt: Tối ưu query phải dựa vào execution plan và số liệu thật. Không nên thấy chậm là thêm index ngay.
Senior answer

An application-level “check then insert” is not enough because concurrent requests can both pass the check before either insert commits. A database unique constraint provides the final atomic guarantee.

I still validate in the application for a friendly error, but I treat the database constraint as the source of truth and handle the duplicate-key exception. This is especially important for idempotency keys, external transaction IDs, usernames, and payment references.

Giải thích tiếng Việt: Hai request đồng thời có thể cùng vượt qua bước check. Unique constraint mới là lớp bảo vệ atomic cuối cùng.

5. Synchronous, Asynchronous & Reactive

Execution models, backpressure, blocking boundaries, and use cases.

4 questions
Senior answer

Synchronous code waits for a result before continuing. It is simple to understand and is appropriate when the operation is fast, the dependency is local, or the caller truly needs an immediate result.

Asynchronous processing decouples the caller from completion. It is useful for long-running work, notifications, file processing, retries, and workflows that do not require an immediate response. However, asynchronous design introduces delivery guarantees, retry behavior, ordering, idempotency, monitoring, and eventual consistency concerns.

Giải thích tiếng Việt: Async không tự động tốt hơn sync. Async phù hợp khi caller không cần kết quả ngay, nhưng phải giải quyết retry, duplicate, ordering và monitoring.
Senior answer

Reactive programming helps systems handle many concurrent I/O operations with a small number of threads by using non-blocking APIs and event-driven execution. Reactor represents zero-or-one result with Mono and multiple results with Flux.

It is valuable for high-concurrency I/O gateways, streaming, and fan-out calls when the full stack is non-blocking. It is less useful for simple CRUD systems or when most dependencies are blocking. Mixing blocking calls into the event loop can remove the scalability benefit and cause severe latency.

Giải thích tiếng Việt: Reactive giúp xử lý nhiều I/O concurrent với ít thread. Chỉ có lợi khi toàn bộ chain gần như non-blocking; gọi JDBC hoặc block trên event loop sẽ gây nghẽn.
Senior answer

Backpressure is a mechanism that prevents a fast producer from overwhelming a slower consumer. In Reactive Streams, the consumer signals how many items it is ready to receive.

Without backpressure, queues grow, memory increases, and latency becomes unbounded. Depending on the business case, the system may buffer with a limit, drop items, keep only the latest item, slow the producer, or reject work.

Giải thích tiếng Việt: Backpressure kiểm soát tốc độ producer theo khả năng consumer. Mục tiêu là tránh queue tăng vô hạn và OOM.
Senior answer

I isolate unavoidable blocking work from the event-loop threads and schedule it on a bounded worker pool such as boundedElastic. I also limit concurrency and monitor queueing because moving blocking work to another scheduler does not remove the underlying capacity limit.

If the system is mostly blocking, I reconsider whether WebFlux is the correct architecture. A regular thread-per-request model may be simpler and more predictable. 

Mono.fromCallable(() -> legacyBlockingClient.load(id))
    .subscribeOn(Schedulers.boundedElastic())
    .timeout(Duration.ofSeconds(2));
Giải thích tiếng Việt: Chuyển blocking call sang boundedElastic chỉ cô lập nó khỏi event loop, không làm nó thành non-blocking. Cần limit concurrency và xem lại kiến trúc nếu blocking chiếm đa số.

6. Microservices & Loose Coupling

Boundaries, resilience, consistency, and operational trade-offs.

4 questions
Senior answer

Loose coupling means a service can evolve without requiring coordinated internal changes in many other services. I define boundaries around business capabilities, keep data ownership inside the service, and expose stable contracts rather than internal tables or domain objects.

I use versioned APIs or events, consumer-driven contract tests, backward-compatible schema evolution, idempotent consumers, and clear ownership. Sharing one database across services usually creates strong runtime and deployment coupling.

Giải thích tiếng Việt: Loose coupling đến từ boundary, data ownership và contract ổn định. Không nên để service khác truy cập trực tiếp table nội bộ.
Senior answer

A circuit breaker stops sending requests to a failing dependency after failures cross a configured threshold. In the open state, calls fail fast. After a wait period, the half-open state allows a small number of test requests. If they succeed, the circuit closes; otherwise, it opens again.

A circuit breaker must be combined with sensible timeouts, limited retries, bulkheads, and monitoring. Retrying every failure can amplify an outage. I retry only transient and idempotent operations, with exponential backoff and jitter.

Giải thích tiếng Việt: Circuit breaker fail-fast để không tiếp tục dồn request vào dependency đang lỗi. Phải đi cùng timeout, retry có giới hạn và bulkhead.
Senior answer

I avoid distributed ACID transactions when possible. Instead, I model the workflow as a saga with local transactions and compensating actions, or use orchestration when the workflow needs centralized visibility.

To publish events reliably after a database change, I use the transactional outbox pattern. The local transaction stores both business data and an outbox record, and a separate publisher sends the event. Consumers must be idempotent because at-least-once delivery can create duplicates.

Giải thích tiếng Việt: Microservice thường dùng eventual consistency. Outbox giúp tránh trường hợp DB commit nhưng event publish fail. Consumer phải idempotent.
Senior answer

I choose a modular monolith when the domain or team boundaries are still evolving, the scale does not require independent deployment, and operational simplicity is valuable. Strong internal modules can preserve boundaries without paying the network, deployment, observability, and consistency cost of microservices.

Microservices are justified when independent scaling, release cadence, ownership, fault isolation, or regulatory separation provides enough business value. They are not automatically more modern or more maintainable.

Giải thích tiếng Việt: Modular monolith thường phù hợp khi team nhỏ hoặc domain chưa ổn định. Microservice chỉ nên dùng khi lợi ích độc lập deploy/scale/ownership lớn hơn operational cost.

7. Senior System Design Scenarios

Real incidents and decisions expected from a 9-year backend engineer.

3 questions
Senior answer

I treat this as an idempotency and state-transition problem. The first protection is a unique idempotency key or provider transaction reference. Inside the database, I update the payment from PENDING to PROCESSING atomically using a version check or conditional update. Only the request that successfully changes the state may call the provider.

I also send an idempotency key to the provider if supported, persist request and response references, and make retries safe. A local Java lock is insufficient in a multi-instance deployment. Depending on the flow, I may use pessimistic row locking or a queue partitioned by payment ID. 

UPDATE payment
SET status = 'PROCESSING', version = version + 1
WHERE id = :id
  AND status = 'PENDING'
  AND version = :currentVersion;
Giải thích tiếng Việt: Không chỉ synchronized trong một JVM vì hệ thống có nhiều instance. Cần idempotency key, atomic state transition trong DB và hỗ trợ duplicate-safe ở provider.
Senior answer

For many read-heavy systems, I use cache-aside: read from cache, load from the database on a miss, then populate the cache. On a database update, I usually delete the cache entry after the transaction commits rather than updating both independently.

I accept a clearly-defined consistency window and use TTL as a safety net. For stronger guarantees, I may publish an invalidation event through an outbox. I also protect against cache penetration with validation or short-lived negative caching, and against cache stampede with request coalescing, locking, or randomized expiration.

Giải thích tiếng Việt: Cache-aside phổ biến: DB là source of truth, update DB xong thì invalidate cache. Cần xử lý penetration, stampede và thời gian dữ liệu có thể stale.
Senior answer

I first define the blast radius: which endpoints, tenants, regions, and time window are affected. I check recent deployments and configuration changes, then use metrics and traces to locate where time is spent: application CPU, GC pauses, thread pools, database connection pool, SQL latency, remote calls, locks, network, or queue backlog.

I compare current behavior with a known healthy baseline. If customer impact is high, I prioritize mitigation—rollback, disable a feature, scale a bottleneck, or reduce traffic—while preserving logs and evidence. After recovery, I perform root-cause analysis and add a preventive control such as an alert, load test, capacity limit, timeout, or safer deployment check.

First checks

  • Error rate and p95/p99 latency
  • Recent release or config change
  • CPU, heap, GC, thread count
  • DB pool and slow queries

Senior behavior

  • Mitigate before perfect diagnosis
  • Communicate impact clearly
  • Preserve evidence
  • Prevent recurrence
Giải thích tiếng Việt: Senior không đoán ngay nguyên nhân. Cần khoanh vùng, xem metric/trace, ưu tiên giảm impact, sau đó mới RCA và thêm biện pháp phòng ngừa.
