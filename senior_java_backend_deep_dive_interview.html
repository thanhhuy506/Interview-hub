0. Mindset for >= Mid Java Backend Interview

Với vị trí Senior Java Backend, interviewer thường không muốn nghe định nghĩa quá cơ bản. Họ muốn biết anh hiểu cơ chế, trade-off, production issue và cách chọn solution.

Context — Bám sát note

  • Java Core và Spring common topics được xem là nền tảng đã phải vững, không phải phần để trả lời nông.
  • Multiple threading là phần đặc biệt quan trọng vì backend service xử lý nhiều request đồng thời.
  • Advanced topics không chỉ để pass interview, mà còn giúp mình debug, optimize và design hệ thống tốt hơn.
  • Cách trả lời nên chuyển từ “definition-based” sang “context + mechanism + trade-off + real use case”.

Key concepts cần hiểu

Basic knowledge interviewer assumes

OOP, Collection, Exception, Stream API, Java memory, multithreading basics, Spring Boot, REST API, JPA, transaction, unit test.

Senior answer style

Explain problem → internal mechanism → benefit → trade-off → production example → caution.

Depth over quantity

Không cần học mọi topic quá rộng. Nhưng topic nào đã nói trong interview thì nên nói sâu và có ví dụ thật.

Common interview questions — trả lời như senior

At senior level, how do you answer technical questions differently from junior level?
Senior answer script
At senior level, I try not to answer only with a definition. I explain why the concept exists, how it works internally, what trade-offs it has, and how I apply it in production.

For example, if I explain HashMap, I do not only say it stores key-value pairs. I explain bucket, hashCode, equals, collision handling, treeification from Java 8, resizing, load factor, and why HashMap is not thread-safe.

This approach shows that I understand both API usage and production behavior.

1. Java Core — Especially Multithreading

Java Core là nền tảng. Nhưng với senior, multithreading là phần cần nắm sâu vì nhiều bug production xuất phát từ concurrency.

Context — Bám sát note

  • Java web application xử lý nhiều request cùng lúc.
  • Nhiều thread có thể cùng access shared data, cache, collection, counter, DB transaction hoặc external resource.
  • Nếu không hiểu thread safety, có thể tạo bug khó reproduce như race condition, deadlock, duplicate update, lost update, memory visibility issue.
  • Senior cần biết khi nào dùng synchronized, volatile, Lock, atomic classes, concurrent collections, thread pool, CompletableFuture.

Key concepts cần hiểu

Thread

Đơn vị thực thi nhỏ nhất trong process. Các thread trong cùng JVM share heap memory.

Race condition

Xảy ra khi nhiều thread cùng đọc/ghi shared mutable state và kết quả phụ thuộc thứ tự chạy.

Thread safety

Code/data structure vẫn đúng khi được access bởi nhiều thread cùng lúc.

synchronized

Dùng intrinsic lock để đảm bảo chỉ một thread vào critical section tại một thời điểm.

volatile

Đảm bảo visibility của biến giữa các thread, nhưng không đảm bảo atomicity cho compound operation như count++.

ExecutorService / Thread Pool

Tái sử dụng thread, kiểm soát concurrency và tránh tạo thread không giới hạn.

CompletableFuture

Hỗ trợ async computation, chaining, combining result và exception handling.

Common interview questions — trả lời như senior

What is thread safety?
Senior answer script
Thread safety means the code behaves correctly when accessed by multiple threads at the same time.

The main risk is shared mutable state. If multiple threads read and update the same data without proper synchronization, we may face race conditions or inconsistent data.

In production, I try to design services as stateless as possible. If shared state is required, I use proper synchronization, atomic classes, concurrent collections, database locking, or external coordination depending on the problem.
volatile vs synchronized?
Senior answer script
volatile guarantees visibility. When one thread updates a volatile variable, other threads can see the latest value.

However, volatile does not make compound operations atomic. For example, count++ has read, increment, and write steps, so volatile alone is not enough.

synchronized provides both visibility and mutual exclusion. It ensures only one thread can execute the critical section at a time.

I use volatile for simple flags, such as shutdown signals. I use synchronized, Lock, AtomicInteger, or concurrent data structures when I need atomic updates.
How do you design thread pool usage in production?
Senior answer script
I do not create unlimited threads manually. I use ExecutorService or framework-managed thread pools.

When designing a thread pool, I consider:
- task type: CPU-bound or I/O-bound
- core pool size
- max pool size
- queue size
- timeout
- rejection policy
- monitoring

For CPU-bound tasks, the pool size is usually close to the number of CPU cores. For I/O-bound tasks, we may use more threads because many threads wait for external systems.

A common production issue is thread pool exhaustion. If the queue is unbounded or timeout is missing, the service can become slow or even crash under load.
When would you use CompletableFuture?
Senior answer script
I use CompletableFuture when I have independent operations that can run in parallel.

For example, an API needs user information, order history, and reward points. If these calls are independent, I can call them concurrently and combine the result.

The benefit is lower response time. But as a senior engineer, I also need to handle timeout, exception, fallback, and custom executor carefully. Otherwise, async code can create hidden thread pool or error-handling problems.
Example code / script 
CompletableFuture<User> userFuture =
    CompletableFuture.supplyAsync(() -> userClient.getUser(userId), executor);

CompletableFuture<List<Order>> orderFuture =
    CompletableFuture.supplyAsync(() -> orderClient.getOrders(userId), executor);

UserProfile profile = userFuture
    .thenCombine(orderFuture, UserProfile::new)
    .orTimeout(2, TimeUnit.SECONDS)
    .exceptionally(ex -> UserProfile.empty())
    .join();

2. Spring Common Topics

Spring Boot common topics là phần interviewer mặc định anh phải nắm. Senior cần hiểu proxy, bean lifecycle, transaction, AOP, security và JPA behavior.

Context — Bám sát note

  • Hầu hết Java backend jobs dùng Spring Boot.
  • Câu hỏi không chỉ là annotation dùng để làm gì, mà còn là cơ chế Spring container/proxy hoạt động thế nào.
  • Các lỗi production hay gặp: transaction không rollback, self-invocation, lazy loading exception, circular dependency, bean scope misuse, N+1 query.

Key concepts cần hiểu

IoC

Spring container quản lý object creation, dependency injection và lifecycle thay vì code tự new object.

Dependency Injection

Inject dependency từ bên ngoài, giúp loose coupling và dễ unit test.

Bean scope

Quy định số lượng instance và vòng đời của bean: singleton, prototype, request, session...

AOP

Tách cross-cutting concerns như logging, security, transaction, audit khỏi business logic.

@Transactional

Quản lý DB transaction bằng Spring proxy/AOP.

Spring Data JPA

Abstraction trên JPA/Hibernate để làm việc với relational database qua entity/repository.

Common interview questions — trả lời như senior

What is IoC and why is it important?
Senior answer script
Inversion of Control means the responsibility of creating and managing objects is moved from application code to the Spring container.

Without IoC, classes create their dependencies manually using new. This creates tight coupling and makes testing harder.

With Spring, dependencies are injected from outside. The class depends on an abstraction or a dependency provided by the container. This improves loose coupling, testability, and maintainability.
How does @Transactional work internally?
Senior answer script
@Transactional works through Spring AOP proxy.

When a method annotated with @Transactional is called from outside the bean, Spring proxy intercepts the call, opens a transaction, executes the method, then commits or rolls back depending on the result.

Important points:
- By default, rollback happens for unchecked exceptions.
- Checked exceptions do not rollback unless configured.
- Self-invocation does not trigger the transactional proxy.
- Long transactions can cause DB locks and performance issues.
- Avoid external API calls inside a DB transaction when possible.
What is circular dependency and how do you fix it?
Senior answer script
Circular dependency happens when bean A depends on bean B and bean B depends on bean A.

This usually indicates a design smell because responsibilities may not be separated clearly.

Possible fixes:
- redesign the service boundary
- extract shared logic into another service
- use setter injection or @Lazy as temporary workaround
- publish domain events instead of direct dependency

As a senior, I prefer redesigning the dependency rather than just using @Lazy to hide the problem.
How do you handle global exception in Spring Boot?
Senior answer script
I use @RestControllerAdvice and @ExceptionHandler to centralize error handling.

This avoids repeating try-catch in every controller and gives frontend a consistent error response.

In production, I usually include errorCode, message, timestamp, path, and traceId. The traceId helps map API error to logs in distributed systems.
Example code / script 
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ApiError> handleNotFound(ResourceNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ApiError("NOT_FOUND", ex.getMessage()));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiError> handleGeneric(Exception ex) {
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(new ApiError("INTERNAL_ERROR", "Unexpected error"));
    }
}

3. Advanced Java Internals — Sorting & Hash Implementation Concept

Không nhất thiết phải implement algorithm từ đầu, nhưng nên hiểu Java sort/hash hoạt động conceptually để nói được performance và trade-off.

Context — Bám sát note

  • Sorting và hashing là nền tảng của Collection, DB indexing, cache key, partitioning và performance optimization.
  • Interviewer thường muốn biết anh hiểu concept chứ không bắt nhớ source code chi tiết.
  • Senior cần nói được complexity, stable sort, comparator issue, hash collision, equals/hashCode contract.

Key concepts cần hiểu

Sorting

Sắp xếp data theo comparator/order. Thường cost O(n log n).

TimSort

Java object sorting dùng TimSort conceptually, optimized cho data thực tế thường đã partially sorted và stable.

Dual-Pivot QuickSort

Primitive array sorting trong Java dùng optimized quicksort variant.

Hashing

Chuyển object/key thành hash value để lookup nhanh.

Collision

Nhiều key rơi vào cùng bucket.

equals/hashCode contract

Nếu two objects equal thì hashCode phải bằng nhau.

Common interview questions — trả lời như senior

How does Java sorting work conceptually?
Senior answer script
In Java, sorting depends on the data type.

For object arrays and collections, Java uses a stable sorting algorithm conceptually based on TimSort. It performs well with real-world partially sorted data.

For primitive arrays, Java uses optimized algorithms such as dual-pivot quicksort.

As a backend engineer, I care about:
- time complexity, usually O(n log n)
- comparator correctness
- memory usage
- whether sorting should happen in Java or in the database

For large datasets, I usually avoid loading everything into memory just to sort. I prefer database-level sorting with pagination and proper index.
How does HashMap work internally?
Senior answer script
HashMap stores key-value pairs using an array of buckets.

When we call put, it calculates hashCode of the key, maps it to a bucket index, and stores the entry there. When we call get, it calculates the hash again, finds the bucket, and uses equals to find the exact key.

If multiple keys go to the same bucket, collision happens. Before Java 8, collision was handled by linked list. From Java 8, when a bucket becomes too large and capacity is enough, it can be converted into a red-black tree, improving worst-case lookup from O(n) to O(log n).

Important production points:
- implement equals and hashCode correctly for custom keys
- avoid mutable keys
- HashMap is not thread-safe
- resizing is expensive
- bad hash distribution causes performance degradation.
Why did Java 8 change collision handling from linked list to red-black tree?
Senior answer script
Before Java 8, if many keys landed in the same bucket, HashMap had to scan a linked list. The worst-case lookup became O(n).

From Java 8, when the collision chain passes a threshold, the bucket can be treeified into a red-black tree. This improves lookup to O(log n) in worst-case collision scenarios.

This change protects HashMap performance when hash distribution is poor or when many collisions happen.
Example code / script 
Map<UserKey, UserProfile> cache = new HashMap<>();

// For custom key, equals() and hashCode() must be stable and correct.
// Avoid changing fields used in hashCode after putting the key into the map.

4. Database Advanced — B-Tree / Index / Query Plan

B-tree/index là topic rất đáng học sâu vì backend performance thường chết ở DB query chứ không phải Java code.

Context — Bám sát note

  • Database index giúp query nhanh hơn nhưng không miễn phí.
  • Senior cần biết index dùng để tối ưu read, nhưng ảnh hưởng insert/update/delete.
  • Nên hiểu B-tree/B+tree concept, composite index, leftmost prefix, execution plan, full table scan, index scan.

Key concepts cần hiểu

Index

Data structure giúp DB tìm row nhanh hơn thay vì scan toàn table.

B-Tree / B+Tree

Tree structure giữ key sorted, hỗ trợ equality search và range query hiệu quả.

Composite Index

Index trên nhiều column. Thứ tự column rất quan trọng.

Leftmost Prefix Rule

Index (a,b,c) thường hỗ trợ query theo a, a+b, a+b+c; không tối ưu cho chỉ b hoặc c.

Execution Plan

Kế hoạch DB chọn để chạy query: scan, join, sort, cost, row estimation.

Common interview questions — trả lời như senior

How does a database index work?
Senior answer script
A database index is a data structure that helps the database find rows faster.

Without an index, the database may perform a full table scan. With an index, it can traverse a B-tree or B+tree-like structure to locate matching rows more efficiently.

Indexes are useful for columns used in WHERE, JOIN, ORDER BY, and GROUP BY.

However, indexes are not free. They improve read performance but add overhead to insert, update, and delete because the index must also be maintained.

As a senior engineer, I do not add indexes blindly. I check real query patterns and execution plans first.
What is a composite index and why does column order matter?
Senior answer script
A composite index is an index on multiple columns.

Column order matters because of the leftmost prefix rule. For example, an index on (status, created_at) can help queries filtering by status, or by status and created_at together. But it may not help much for a query filtering only by created_at.

I design composite indexes based on the most common filters and sort order in real queries.
What is query execution plan?
Senior answer script
An execution plan shows how the database executes a SQL query.

It tells us whether the database uses an index scan, full table scan, nested loop join, hash join, sorting, and estimated cost.

When a query is slow, I check the execution plan to see:
- whether the right index is used
- how many rows are scanned
- whether sorting is expensive
- whether joins are efficient
- whether statistics are outdated

This is much better than guessing.
Example code / script 
CREATE INDEX idx_order_status_created
ON orders(status, created_at);

EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE status = 'PAID'
ORDER BY created_at DESC
LIMIT 50;

5. Database Isolation & Locking Mechanism

Isolation/locking là topic advance nhưng cực kỳ quan trọng trong hệ thống order, inventory, payment, banking, booking.

Context — Bám sát note

  • Nhiều request có thể update cùng một dữ liệu cùng lúc.
  • Nếu không hiểu isolation/locking, có thể gặp lost update, dirty read, overselling, duplicate payment, inconsistent report.
  • Senior cần biết ACID, isolation levels, optimistic lock, pessimistic lock, deadlock và transaction boundary.

Key concepts cần hiểu

ACID

Atomicity, Consistency, Isolation, Durability.

Dirty Read

Đọc data chưa commit từ transaction khác.

Non-repeatable Read

Cùng một row nhưng đọc hai lần ra kết quả khác nhau vì transaction khác đã commit update.

Phantom Read

Cùng một query nhưng lần sau xuất hiện thêm/mất row vì transaction khác insert/delete.

Optimistic Lock

Dùng version để detect conflict khi update.

Pessimistic Lock

Lock row trước để ngăn transaction khác update đồng thời.

Common interview questions — trả lời như senior

Explain transaction isolation levels.
Senior answer script
Isolation levels define how much one transaction is isolated from others.

Common levels:
- Read Uncommitted: may read uncommitted data, dirty read can happen.
- Read Committed: only reads committed data.
- Repeatable Read: reading the same row multiple times returns the same result.
- Serializable: strongest isolation, transactions behave like they run one by one.

The trade-off is consistency vs concurrency. Higher isolation gives stronger consistency but may reduce performance due to more locking.

In production, I choose isolation level based on business requirement, not always the highest level.
Optimistic locking vs pessimistic locking?
Senior answer script
Optimistic locking assumes conflicts are rare. It does not lock the row when reading. Instead, it uses a version column. When updating, it checks whether the version is still the same.

Pessimistic locking assumes conflicts are likely. It locks the row immediately so other transactions cannot update it until the lock is released.

I use optimistic locking for normal update flows where conflicts are rare. I use pessimistic locking when correctness is critical and conflicts are expected, for example inventory reservation under high concurrency.
How do you avoid overselling inventory?
Senior answer script
There are several approaches depending on scale and consistency requirements.

For simple systems, I can use database row lock with SELECT FOR UPDATE or JPA pessimistic lock.
For moderate systems, optimistic lock with retry can work.
For high-scale systems, I may use Redis atomic operation, message queue, reservation table, or inventory service with strong consistency boundary.

The key point is to make the stock deduction atomic and idempotent. We should also avoid long transactions and handle retry carefully.
Example code / script 
// Optimistic locking
@Version
private Long version;

// Pessimistic locking with JPA
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p from Product p where p.id = :id")
Product findForUpdate(@Param("id") Long id);

6. Sync / Async / Reactive Programming Use Cases

Không phải cứ async/reactive là tốt. Senior phải biết chọn model theo use case, complexity và failure handling.

Context — Bám sát note

  • Synchronous đơn giản, dễ debug, phù hợp flow cần kết quả ngay.
  • Asynchronous giúp giảm waiting time, decouple services, phù hợp notification/event/background processing.
  • Reactive phù hợp high-concurrency I/O-bound systems nhưng tăng complexity và yêu cầu non-blocking end-to-end.
  • Cần hiểu retry, timeout, fallback, idempotency, ordering, backpressure.

Key concepts cần hiểu

Synchronous

Caller chờ response rồi mới tiếp tục.

Asynchronous

Task chạy background/parallel, caller không cần chờ ngay.

Non-blocking I/O

Thread không bị block khi chờ external I/O.

Reactive

Event-driven non-blocking model, thường dùng Mono/Flux trong Spring WebFlux.

Backpressure

Cơ chế consumer báo producer giảm tốc khi xử lý không kịp.

Common interview questions — trả lời như senior

Synchronous vs asynchronous processing?
Senior answer script
Synchronous processing means the caller waits for the operation to finish. It is simple and suitable when the user needs the result immediately.

Asynchronous processing means the task can run in the background or in parallel. It is useful when the caller does not need immediate result.

For example, login and payment authorization are usually synchronous. Email notification, audit log, report generation, and event publishing can be asynchronous.

Async improves responsiveness and decoupling, but it introduces complexity: retry, idempotency, error handling, message ordering, and observability.
When would you use reactive programming?
Senior answer script
I use reactive programming when the system is I/O-heavy and needs to handle high concurrency with fewer threads.

Examples:
- API gateway
- streaming data
- calling multiple non-blocking external APIs
- real-time event processing

In Spring WebFlux, Mono represents zero or one item, and Flux represents zero to many items.

But reactive is not always better. It adds complexity and requires the full chain to be non-blocking. If we call blocking JDBC inside reactive flow, we lose the benefit.

For normal CRUD systems, Spring MVC is often simpler and good enough.
What mistakes should we avoid in async/reactive systems?
Senior answer script
Common mistakes include:
- no timeout
- no fallback
- using default common ForkJoinPool without control
- blocking call inside reactive pipeline
- no retry strategy
- non-idempotent consumer
- no correlation ID for tracing
- ignoring backpressure

Senior engineers should design async systems with failure in mind, not only happy path performance.
Example code / script 
Mono<UserProfile> profileMono =
    Mono.zip(userClient.getUser(userId), orderClient.getOrders(userId))
        .map(tuple -> new UserProfile(tuple.getT1(), tuple.getT2()))
        .timeout(Duration.ofSeconds(2))
        .onErrorResume(ex -> Mono.just(UserProfile.empty()));

7. Loose Coupling Design in Microservices

Loose coupling là mindset thiết kế microservice quan trọng: service nên phụ thuộc contract, không phụ thuộc internal database hoặc implementation của service khác.

Context — Bám sát note

  • Microservice không chỉ là tách project thành nhiều service.
  • Nếu service gọi trực tiếp DB của service khác, share entity quá nhiều, hoặc phụ thuộc implementation chi tiết, hệ thống vẫn bị tight coupling.
  • Loose coupling giúp service deploy độc lập, scale độc lập, thay đổi độc lập và giảm blast radius.
  • Nhưng loose coupling cũng cần observability, contract testing, API versioning, event design và failure handling.

Key concepts cần hiểu

Bounded Context

Ranh giới domain rõ ràng, mỗi service chịu trách nhiệm một business capability.

API Contract

Service giao tiếp qua contract ổn định: REST/gRPC/event schema.

Database per Service

Mỗi service sở hữu database/schema của nó, service khác không query trực tiếp.

Event-driven

Service publish event để service khác react mà không cần direct coupling.

Saga

Quản lý distributed transaction bằng local transaction + compensation.

Circuit Breaker

Ngăn cascading failure khi downstream service lỗi.

Common interview questions — trả lời như senior

What is loose coupling in microservices?
Senior answer script
Loose coupling means each service depends on stable contracts, not internal implementation.

A service should not directly access another service's database. It should communicate through API or events.

For example, Order Service should not update Payment Service database directly. It should call Payment API or publish an event like OrderCreated.

Loose coupling allows services to be developed, deployed, scaled, and changed independently. But it also requires good API versioning, contract testing, observability, and failure handling.
How do you define service boundaries?
Senior answer script
I define service boundaries based on business capability and data ownership, not only technical layers.

A good service should own its data and business rules. It should expose a clear contract to other services.

For example, User Service owns user profile and identity-related data. Order Service owns order lifecycle. Payment Service owns payment transaction and payment status.

If two services constantly need each other's internal data, the boundary may be wrong or we may need an event-driven read model.
How do you handle distributed transactions in microservices?
Senior answer script
In microservices, I usually avoid global transactions because they reduce scalability and increase coupling.

Common approaches are:
- Saga pattern
- Outbox pattern
- event-driven architecture
- compensation transaction
- idempotent consumer

For example, order creation can be split into local transactions:
1. Create order
2. Reserve inventory
3. Process payment
4. Confirm order

If payment fails, we release inventory and cancel the order through compensating actions.
What is circuit breaker and why is it useful?
Senior answer script
Circuit breaker prevents a service from repeatedly calling a failing dependency.

If the failure rate exceeds a threshold, the circuit opens and calls fail fast or return fallback. After some time, it becomes half-open to test whether the dependency recovered.

This prevents cascading failures. For example, if Payment Service is down, Order Service should not keep waiting for timeout and exhaust its threads.
Example code / script 
@CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
public PaymentResponse callPayment(PaymentRequest request) {
    return paymentClient.pay(request);
}

public PaymentResponse paymentFallback(PaymentRequest request, Throwable ex) {
    return PaymentResponse.pending("Payment service is temporarily unavailable");
}

  • Nên học sâu những phần liên quan trực tiếp tới Java backend: threading, Spring transaction, DB index/lock, microservice failure, async/event-driven.

Common interview questions — trả lời như senior

How should I prepare advanced topics for interview?
Senior answer script
I would not try to memorize every advanced topic superficially.

Instead, for each important topic, I prepare:
1. Why it exists
2. How it works conceptually
3. Trade-offs
4. Production use case
5. Common pitfalls
6. One example from my project or a realistic scenario

This helps me answer flexibly even when the interviewer changes the question slightly.
Which topics should a senior Java backend engineer prioritize?
Senior answer script
I would prioritize topics that directly affect production backend systems:
- Java multithreading and concurrency
- HashMap and collection internals
- Spring IoC, AOP, transaction, JPA
- SQL index, B-tree, execution plan
- DB isolation and locking
- sync vs async vs reactive
- loose coupling in microservices
- Kafka/event-driven communication
- observability: logs, metrics, traces

These topics are useful not only for interviews but also for real system design, debugging, and performance optimization.
