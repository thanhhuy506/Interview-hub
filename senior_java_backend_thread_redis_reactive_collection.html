1. Thread Safety, Multithreading, Thread Pool & Connection Pool

Senior Java Backend phải hiểu concurrency không chỉ ở keyword synchronized, mà còn ở thread model, shared state, pool sizing, DB connection pool, race condition, deadlock và production tuning.

Context — vì sao senior cần nắm?

  • Backend Java service xử lý nhiều request song song, nên thread-safety ảnh hưởng trực tiếp tới correctness.
  • Race condition thường không xuất hiện ở local test, nhưng có thể gây lỗi production rất khó debug.
  • Thread pool kiểm soát số lượng task chạy đồng thời; database connection pool kiểm soát số kết nối DB.
  • Nếu thread pool và connection pool sizing sai, service có thể bị latency cao, queue backlog, timeout hoặc connection starvation.

Key concepts

Thread-safe

Code/data structure vẫn hoạt động đúng khi nhiều thread access cùng lúc.

Thread-unsafe

Code có thể sai khi nhiều thread cùng access shared mutable state mà không có protection.

Multiple thread

Nhiều luồng thực thi song song trong cùng process, share heap memory.

Race condition

Kết quả phụ thuộc thứ tự chạy của thread khi cùng đọc/ghi shared data.

Thread pool

Tái sử dụng thread để giảm cost tạo thread và giới hạn concurrency.

Database connection pool

Pool giữ sẵn DB connections để reuse; giúp giảm cost mở connection và bảo vệ DB khỏi quá tải.

Deadlock

Hai hoặc nhiều thread chờ lock lẫn nhau và không thể tiếp tục.

Thread starvation

Task không được chạy vì thread bị chiếm lâu hoặc pool/queue bị nghẽn.

Common interview questions — senior answer

What is thread-safety?
Senior answer script
Thread-safety means the code behaves correctly when accessed by multiple threads at the same time.

The main risk is shared mutable state. If multiple threads read and update the same variable, object, collection, or cache without proper coordination, the result can be inconsistent.

In production, I try to design services as stateless as possible. If shared state is required, I use immutable objects, synchronization, locks, atomic classes, concurrent collections, or database-level locking depending on the problem.

For example, Spring service beans are singleton by default, so I avoid storing request-specific data in instance fields.
What is a race condition? Give a production example.
Senior answer script
A race condition happens when multiple threads access and modify shared data at the same time, and the final result depends on timing.

Example: two requests try to reserve the last item in stock at the same time. Both read stock = 1, both think the item is available, and both deduct it. The final result can become overselling.

To fix it, we need atomicity. Depending on the use case, we can use database row lock, optimistic locking with @Version, Redis atomic operation, synchronized block, or message-based serialization.

As a senior, I do not solve all race conditions with synchronized. I choose the correct boundary: JVM-level, DB-level, Redis-level, or business workflow-level.
How do you design a thread pool in production?
Senior answer script
I design a thread pool based on task type and system limits.

For CPU-bound tasks, the pool size is usually close to the number of CPU cores.
For I/O-bound tasks, we may use more threads because many threads spend time waiting for DB, network, or external APIs.

I also configure core pool size, max pool size, queue capacity, keep-alive time, rejection policy, timeout, and monitoring metrics.

A common production mistake is using an unbounded queue. Under load, tasks keep accumulating, memory increases, latency becomes high, and eventually the service becomes unstable.

For business-critical systems, I prefer explicit ThreadPoolExecutor instead of blindly using default async executors.
Thread pool vs database connection pool?
Senior answer script
Thread pool controls how many tasks can execute concurrently.

Database connection pool controls how many database connections are available.

They are related but not the same. If the thread pool is much larger than the DB connection pool, many threads may block waiting for DB connections. This wastes threads and increases latency.

For example, if a service has 200 worker threads but only 20 DB connections, many requests can be stuck waiting for a connection.

As a senior, I tune them together based on request traffic, DB capacity, query latency, external API latency, timeout settings, HikariCP metrics, and thread pool metrics.
How do you detect thread or connection pool issues in production?
Senior answer script
I check metrics and symptoms.

For thread pool, I check active thread count, queue size, task rejection count, execution time, blocked thread count, and thread dump.

For DB connection pool, I check active connections, idle connections, pending connection requests, connection timeout count, slow query logs, database CPU, and DB locks.

If many threads are waiting for DB connections, I check whether the pool is too small, queries are slow, transactions are too long, or connections are leaked.

Thread dumps and HikariCP metrics are very useful for this kind of issue.
Example code / config / script
// Explicit bounded thread pool
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    10,                         // core pool size
    50,                         // max pool size
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(500),
    new ThreadPoolExecutor.CallerRunsPolicy()
);

// HikariCP production properties example
spring.datasource.hikari.maximum-pool-size=20
spring.datasource.hikari.minimum-idle=5
spring.datasource.hikari.connection-timeout=3000
spring.datasource.hikari.idle-timeout=600000
spring.datasource.hikari.max-lifetime=1800000

2. Redis Deep Dive — Cache, Penetration, Read/Write Flow, Replication, Memory, Consistency, Lua

Redis không chỉ là cache. Senior cần hiểu cache strategy, failure cases, consistency, penetration/breakdown/avalanche, replication, memory eviction, Lua atomicity và production trade-off.

Context — vì sao senior cần nắm?

  • Redis thường dùng để giảm DB load, tăng response time, lưu session/token, rate limiting, distributed lock, idempotency key.
  • Cache design sai có thể gây stale data, DB overload, cache avalanche hoặc incorrect business behavior.
  • Redis chạy rất nhanh vì in-memory và single-threaded command execution model, nhưng vẫn cần hiểu memory, persistence, replication, failover.
  • Senior cần giải thích được read/write flow, consistency strategy và khi nào không nên cache.

Key concepts

Cache basics

Lưu dữ liệu truy cập thường xuyên vào Redis để giảm DB query và tăng tốc response.

Cache-aside

App đọc cache trước; miss thì đọc DB rồi set cache.

Cache penetration

Request liên tục query data không tồn tại, cache miss liên tục và đẩy load xuống DB.

Cache breakdown

Một hot key hết hạn, nhiều request cùng lúc đánh vào DB.

Cache avalanche

Nhiều key hết hạn cùng lúc hoặc Redis down, traffic dồn xuống DB.

Master–Replica

Master xử lý write, replica replicate data và có thể phục vụ read.

Read/write splitting

Write vào master, read từ replica để scale read workload, nhưng có replication lag.

Memory eviction

Redis remove key theo policy khi memory đầy, ví dụ allkeys-lru, volatile-ttl.

Cache consistency

Đảm bảo cache và DB không lệch quá mức chấp nhận được.

Lua scripting

Chạy nhiều Redis commands atomically trong một script.

Common interview questions — senior answer

How does Redis cache-aside read flow work?
Senior answer script
In cache-aside pattern, the application controls cache read and write.

Read flow:
1. Client calls API.
2. Application checks Redis by key.
3. If cache hit, return data immediately.
4. If cache miss, query database.
5. Store result in Redis with TTL.
6. Return data to client.

This pattern is simple and common, but we must handle cache penetration, hot key expiration, stale data, and serialization carefully.

I use cache-aside for data that is read frequently and can tolerate slight staleness, such as product detail, configuration, user profile summary, or token metadata.
What is cache penetration and how do you prevent it?
Senior answer script
Cache penetration happens when requests query data that does not exist. Since the data is not in cache and not in DB, every request goes through Redis to DB and causes unnecessary DB load.

Example: attackers or bad clients keep requesting random user IDs that do not exist.

Common solutions:
- cache null values with short TTL
- use Bloom filter to reject impossible keys before hitting DB
- validate request parameters early
- rate limit suspicious traffic
- protect APIs with authentication and throttling

For normal systems, caching null for a short TTL is simple and effective. For very large key spaces, Bloom filter is useful.
What is cache breakdown and how do you handle hot key expiration?
Senior answer script
Cache breakdown happens when a hot key expires and many requests hit the database at the same time to rebuild the cache.

Example: homepage product list or popular promotion detail expires during peak traffic.

Solutions:
- use mutex or distributed lock so only one request rebuilds cache
- use logical expiration and async refresh
- preload hot keys
- extend TTL with randomization
- never expire extremely hot keys, but refresh them asynchronously

The goal is to avoid many concurrent requests rebuilding the same cache value.
What is cache avalanche?
Senior answer script
Cache avalanche happens when many cache keys expire at the same time or Redis becomes unavailable, causing a large amount of traffic to hit the database.

Solutions:
- add random TTL jitter so keys do not expire together
- use Redis cluster or sentinel for high availability
- use local cache as fallback for critical hot data
- apply rate limiting and circuit breaker
- warm up cache before traffic peak
- degrade gracefully when cache is unavailable

Senior point: cache is a performance optimization, but the system should not blindly collapse when cache fails.
How do you design Redis read/write flow with master–replica and read/write splitting?
Senior answer script
In Redis master–replica setup, writes go to master. Replicas asynchronously copy data from master and can serve read traffic.

Read/write splitting helps scale read-heavy workloads. But because replication is asynchronous, there can be replication lag. After writing to master, reading immediately from replica may return old data.

For strong read-after-write consistency, I read from master immediately after write, or design the flow to tolerate eventual consistency.

For example, after updating user profile, the API response should use the updated value from DB or master path, not rely on replica that may lag.
How do you maintain cache consistency between Redis and database?
Senior answer script
Cache consistency is one of the most important Redis topics.

Common strategy:
1. Update database first.
2. Delete cache after DB commit.
3. Let next read rebuild cache.

Why delete instead of update cache? Because update cache can be error-prone if the cached object is computed from multiple tables or services.

Potential issue: if cache delete fails, stale data remains. To improve reliability, we can retry cache deletion, use message queue or outbox to delete cache asynchronously, use short TTL as safety net, or use double delete pattern in special cases.

For most business systems, DB is the source of truth and cache is temporary acceleration.
When would you use Redis Lua scripting?
Senior answer script
Redis executes Lua scripts atomically. This means no other Redis command runs in the middle of the script.

I use Lua when multiple Redis operations must be performed as one atomic operation.

Common use cases:
- rate limiting
- distributed lock release
- check-and-decrement stock
- idempotency key check and set
- token bucket algorithm

For example, when releasing a distributed lock, we should only delete the lock if the value belongs to the current owner. Lua makes this check-and-delete atomic.
Example code / config / script
// Cache-aside read flow
public ProductDto getProduct(Long id) {
    String key = "product:" + id;

    ProductDto cached = redisTemplate.opsForValue().get(key);
    if (cached != null) {
        return cached;
    }

    Product product = productRepository.findById(id)
        .orElseThrow(() -> new NotFoundException("Product not found"));

    ProductDto dto = ProductDto.from(product);
    redisTemplate.opsForValue().set(key, dto, Duration.ofMinutes(10));

    return dto;
}

// Lua script: safe distributed lock release
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end

3. Reactive Programming & Spring WebFlux

Reactive/WebFlux là advanced topic. Senior cần hiểu non-blocking model, event loop, Mono/Flux, backpressure, when-to-use, when-not-to-use và production pitfalls.

Context — vì sao senior cần nắm?

  • Reactive programming phù hợp với I/O-bound systems có nhiều concurrent requests.
  • WebFlux không tự động làm app nhanh hơn nếu bên trong vẫn dùng blocking JDBC hoặc blocking external calls.
  • Senior cần biết sự khác nhau giữa Spring MVC thread-per-request và WebFlux event-loop/non-blocking model.
  • Production reactive code cần timeout, error handling, backpressure, scheduler control và observability.

Key concepts

Reactive programming

Programming model xử lý data/event streams theo non-blocking style.

Spring WebFlux

Reactive web framework của Spring, dùng Reactor Netty và Project Reactor.

Mono

Reactive type đại diện cho 0 hoặc 1 item.

Flux

Reactive type đại diện cho 0 đến nhiều item.

Non-blocking I/O

Thread không bị block trong lúc chờ network/IO response.

Event loop

Một số ít thread xử lý nhiều connections/events.

Backpressure

Consumer báo producer giảm tốc khi xử lý không kịp.

Scheduler

Điều phối execution context trong Reactor, ví dụ boundedElastic cho blocking work nếu bắt buộc.

Common interview questions — senior answer

What is reactive programming?
Senior answer script
Reactive programming is a programming model for handling asynchronous data streams in a non-blocking way.

In Java Spring, WebFlux uses Project Reactor. Mono represents zero or one value, and Flux represents zero to many values.

The main benefit is efficient resource usage under high concurrency, especially for I/O-heavy systems such as API gateway, streaming, or services that call many external APIs.

But reactive is not always better. It adds complexity and requires the whole chain to be non-blocking. If we use blocking JDBC or blocking SDKs inside WebFlux, we can block event-loop threads and hurt performance.
Spring MVC vs Spring WebFlux?
Senior answer script
Spring MVC is based on the servlet model and usually follows thread-per-request. It is simple, mature, and good for typical CRUD applications.

Spring WebFlux is reactive and non-blocking. It can handle many concurrent I/O operations with fewer threads.

I choose Spring MVC when the application is mostly CRUD, uses blocking JDBC or JPA, and simplicity is more important.

I choose WebFlux when the application is I/O-heavy, needs high concurrency, uses non-blocking drivers such as R2DBC or WebClient, and the team is comfortable with reactive programming.
What are common mistakes in WebFlux?
Senior answer script
Common mistakes include:
- calling blocking code on event-loop threads
- using JPA or JDBC directly inside reactive pipeline
- calling block() in request flow
- missing timeout
- missing error handling
- overusing reactive for simple CRUD
- not understanding subscribe behavior
- using ThreadLocal context incorrectly

In production WebFlux, I always check whether dependencies are truly non-blocking. If I must call blocking code, I isolate it using boundedElastic, but I treat that as a compromise, not ideal design.
How do you handle errors in reactive flow?
Senior answer script
In Reactor, errors are part of the stream.

Common operators:
- onErrorReturn for static fallback
- onErrorResume for dynamic fallback
- onErrorMap to convert exception
- doOnError for logging side effect
- retryWhen for controlled retry
- timeout to avoid waiting forever

As a senior, I avoid unlimited retry. I define timeout, retry count, backoff, and fallback based on business requirement.
Example code / config / script
public Mono<UserProfile> getUserProfile(String userId) {
    Mono<User> userMono = userClient.getUser(userId);
    Mono<List<Order>> orderMono = orderClient.getOrders(userId);

    return Mono.zip(userMono, orderMono)
        .map(tuple -> new UserProfile(tuple.getT1(), tuple.getT2()))
        .timeout(Duration.ofSeconds(2))
        .onErrorResume(ex -> {
            log.warn("Failed to build user profile for {}", userId, ex);
            return Mono.just(UserProfile.empty(userId));
        });
}

// Avoid this in WebFlux request flow
User user = userClient.getUser(userId).block(); // blocks thread, bad in reactive flow

4. Java Collection Deep Dive

Collection không chỉ là API. Senior cần biết internal implementation, complexity, memory trade-off, concurrent behavior, equals/hashCode, iterator behavior và production pitfalls.

Context — vì sao senior cần nắm?

  • Collection xuất hiện trong hầu hết Java backend code.
  • Interview thường hỏi HashMap, ArrayList, LinkedList, ConcurrentHashMap, fail-fast/fail-safe, Set uniqueness, sorting.
  • Production bug thường đến từ dùng sai collection trong concurrent environment, mutable key, memory growth hoặc wrong equals/hashCode.
  • Senior cần chọn collection dựa trên access pattern, concurrency requirement và data size.

Key concepts

List

Ordered collection, cho phép duplicate. ArrayList là implementation phổ biến nhất.

Set

Không cho duplicate. HashSet dựa trên HashMap internally.

Map

Key-value structure. HashMap phổ biến nhưng không thread-safe.

ArrayList

Dynamic array, get(index) nhanh O(1), insert giữa list có thể shift elements.

LinkedList

Doubly linked list, random access chậm O(n), memory overhead cao hơn.

HashMap

Array of buckets, hashCode + equals, collision handling, treeification Java 8.

ConcurrentHashMap

Thread-safe map optimized for concurrent access.

CopyOnWriteArrayList

Thread-safe list phù hợp read-heavy, write ít vì mỗi write copy array mới.

Fail-fast iterator

Throw ConcurrentModificationException khi collection bị structural modification trong lúc iterate.

Fail-safe iterator

Không throw exception, thường iterate trên copy hoặc weakly consistent view.

Common interview questions — senior answer

How does HashMap work internally?
Senior answer script
HashMap stores key-value pairs using an array of buckets.

When we put a key, HashMap calculates the key's hashCode, applies a hash spreading function, maps it to a bucket index, and stores the entry.

When we get a value, it calculates the hash again, finds the bucket, and uses equals to compare the actual key.

If multiple keys map to the same bucket, collision happens. Before Java 8, collisions were handled by linked list. From Java 8, if the bucket becomes too large and capacity is enough, it can be converted into a red-black tree. This improves worst-case lookup from O(n) to O(log n).

Production cautions:
- HashMap is not thread-safe.
- Custom keys must implement equals and hashCode correctly.
- Avoid mutable keys.
- Bad hash distribution can degrade performance.
- Resizing can be expensive.
ArrayList vs LinkedList?
Senior answer script
ArrayList is backed by a dynamic array. It provides fast random access by index, O(1), and is usually cache-friendly.

LinkedList is backed by a doubly linked list. It has slower random access, O(n), because it must traverse nodes. It also uses more memory because each node stores references to previous and next nodes.

A common misconception is that LinkedList is always better for insertion and deletion. In reality, if we need to search the position first, traversal still costs O(n).

In most backend applications, ArrayList is the default choice. I use LinkedList only when there is a specific access pattern that justifies it.
HashMap vs ConcurrentHashMap?
Senior answer script
HashMap is not thread-safe. If multiple threads update it concurrently, data can become inconsistent.

ConcurrentHashMap is designed for concurrent access. It allows multiple threads to read and update safely with better performance than synchronizing the whole map.

In Java 8, ConcurrentHashMap uses CAS, synchronized blocks on bins, and internal control mechanisms to reduce lock contention.

However, thread-safe collection does not automatically make the whole business logic thread-safe. Compound actions may still need additional coordination.

For example, check-then-act logic can still be unsafe if not done atomically.
Fail-fast vs fail-safe iterator?
Senior answer script
Fail-fast iterators throw ConcurrentModificationException when the collection is structurally modified during iteration.

Examples:
- ArrayList
- HashMap
- HashSet

Fail-safe or weakly consistent iterators do not throw this exception. They may iterate over a copy or reflect some concurrent changes safely.

Examples:
- CopyOnWriteArrayList
- ConcurrentHashMap

In production, I choose based on concurrency pattern. CopyOnWriteArrayList is good for many reads and rare writes, such as listener lists. ConcurrentHashMap is better for concurrent key-value access.
How do you choose the right collection?
Senior answer script
I choose collection based on access pattern.

If I need ordered elements and fast index access, I use ArrayList.
If I need uniqueness, I use HashSet or TreeSet depending on ordering requirement.
If I need key-value lookup, I use HashMap.
If multiple threads access the map, I use ConcurrentHashMap.
If I need sorted keys, I use TreeMap.
If I need priority-based processing, I use PriorityQueue.
If I need read-heavy thread-safe list with rare writes, I use CopyOnWriteArrayList.

Senior point: do not choose collection only by habit. Choose based on lookup, insert/delete, ordering, uniqueness, concurrency, and memory.
Example code / config / script
// Safe compound operation with ConcurrentHashMap
ConcurrentHashMap<String, LongAdder> counters = new ConcurrentHashMap<>();

public void increment(String key) {
    counters.computeIfAbsent(key, k -> new LongAdder()).increment();
}

// Dangerous with normal HashMap under concurrency
Map<String, Integer> map = new HashMap<>();
map.put("count", map.getOrDefault("count", 0) + 1); // not thread-safe
