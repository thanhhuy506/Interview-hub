0. Big Picture: Synchronous, Asynchronous, and synchronized

Ba khái niệm dễ bị nhầm: synchronous/asynchronous là execution model; synchronized là Java keyword để lock critical section.

Context — why this matters

  • Trong interview, interviewer có thể hỏi synchronous vs asynchronous processing, hoặc hỏi synchronized keyword trong Java multithreading.
  • Senior cần phân biệt rõ: sync/async nói về cách flow chạy và chờ kết quả; synchronized nói về thread-safety và locking.
  • Backend production thường kết hợp cả ba: request/response synchronous, event processing asynchronous, và critical section có thể cần synchronized/lock.

Key concepts

Synchronous

Caller gửi request và chờ kết quả trả về rồi mới tiếp tục.

Asynchronous

Caller không cần chờ task hoàn thành ngay; task có thể chạy background hoặc xử lý qua callback/event/message.

synchronized

Java keyword dùng intrinsic monitor lock để bảo vệ shared mutable state khỏi race condition.

Blocking

Thread bị giữ lại trong lúc chờ I/O hoặc kết quả.

Non-blocking

Thread không bị giữ trong lúc chờ; thường dùng callback/event-loop/reactive model.

Concurrency

Nhiều task được xử lý overlap về thời gian, không nhất thiết chạy đúng cùng một lúc.

Parallelism

Nhiều task thực sự chạy cùng lúc trên nhiều CPU core.

Common interview questions

Synchronous, asynchronous, and synchronized khác nhau thế nào?
Senior answer script
Synchronous and asynchronous describe how an execution flow waits for a result.

Synchronous means the caller waits until the operation completes.
Asynchronous means the caller does not need to wait immediately. The task can run in the background, through another thread, message queue, callback, or event.

synchronized is different. It is a Java keyword used for thread-safety. It ensures only one thread can enter a critical section protected by the same lock at a time.

So:
- synchronous/asynchronous are about execution flow
- synchronized is about locking and shared data protection

For example, a REST API call to process payment is usually synchronous because the user needs the result immediately. Sending email after payment can be asynchronous. Updating a shared in-memory counter may need synchronized, AtomicInteger, or another thread-safe mechanism.
Code example
// Synchronous call: caller waits for result
PaymentResult result = paymentClient.pay(request);

// Asynchronous call: caller does not wait immediately
CompletableFuture.runAsync(() -> emailService.sendPaymentEmail(orderId));

// synchronized: protects shared mutable state
public synchronized void increment() {
    count++;
}

1. Synchronous Processing

Synchronous flow đơn giản, dễ hiểu, dễ debug. Caller chờ operation hoàn thành rồi mới tiếp tục.

Context — why this matters

  • Phù hợp khi business cần kết quả ngay, ví dụ login, payment authorization, validation, search API, read detail API.
  • Dễ implement và trace request hơn async.
  • Nhược điểm là caller bị block, latency phụ thuộc vào downstream service, dễ bị thread exhaustion nếu gọi external service chậm.

Key concepts

Request-response

Client gửi request và chờ response.

Blocking I/O

Thread chờ trong lúc database/external API trả kết quả.

Timeout

Bắt buộc cần timeout để tránh thread chờ vô hạn.

Circuit breaker

Ngăn gọi liên tục tới downstream service đang fail.

Bulkhead

Cô lập resource để một dependency chậm không làm sập toàn hệ thống.

Common interview questions

What is synchronous processing?
Senior answer script
Synchronous processing means the caller waits until the operation is completed and receives the result before moving to the next step.

It is simple and predictable. It is suitable when the user or upstream service needs the result immediately.

For example, login should usually be synchronous because the client needs a token immediately. Payment authorization is also usually synchronous because the user needs to know whether the payment succeeded or failed.

The trade-off is that the calling thread is blocked while waiting. If the downstream service or database is slow, the caller also becomes slow. Therefore, in production, synchronous calls must have timeout, retry policy, circuit breaker, and proper monitoring.
When should we use synchronous communication between services?
Senior answer script
I use synchronous communication when the result is required immediately to continue the business flow.

Examples:
- user login and token generation
- checking permission before accessing resource
- payment authorization
- validating inventory before confirming order
- fetching detail data for UI

However, I avoid chaining too many synchronous calls across microservices because it increases latency and coupling. If Service A calls B, B calls C, and C calls D synchronously, the whole request becomes slow and fragile.

For non-critical side effects, I prefer asynchronous processing.
What are common production risks of synchronous calls?
Senior answer script
Common risks include:
- high latency if downstream is slow
- thread pool exhaustion
- cascading failure
- retry storm
- tight coupling between services
- poor user experience if no timeout is configured

To reduce risk, I configure:
- connection timeout
- read timeout
- circuit breaker
- retry with backoff only for safe operations
- fallback if business allows
- monitoring for latency and error rate

A senior engineer should never call an external service synchronously without timeout.
Code example
// WebClient synchronous-style API should still have timeout.
public Mono<PaymentResult> pay(PaymentRequest request) {
    return webClient.post()
        .uri("/payments")
        .bodyValue(request)
        .retrieve()
        .bodyToMono(PaymentResult.class)
        .timeout(Duration.ofSeconds(3));
}

2. Asynchronous Processing

Asynchronous flow giúp decouple, giảm response time và xử lý background task. Nhưng cần quan tâm retry, idempotency, ordering và observability.

Context — why this matters

  • Phù hợp cho task không cần trả kết quả ngay: email, notification, audit log, report generation, data sync, event processing.
  • Có thể implement bằng CompletableFuture, @Async, message queue như Kafka/RabbitMQ/SQS, scheduled job hoặc reactive pipeline.
  • Async không làm hệ thống đơn giản hơn; nó chuyển complexity sang retry, duplicate message, failure handling, tracing.

Key concepts

Fire-and-forget

Gửi task đi và không chờ kết quả trực tiếp.

Callback

Xử lý tiếp khi task hoàn thành.

Future/CompletableFuture

Đại diện cho kết quả sẽ có trong tương lai.

Message queue

Tách producer và consumer bằng queue/topic.

At-least-once delivery

Message có thể được xử lý hơn một lần, nên consumer phải idempotent.

Idempotency

Cùng một request/message chạy nhiều lần vẫn cho kết quả cuối giống nhau.

Common interview questions

What is asynchronous processing?
Senior answer script
Asynchronous processing means the caller does not need to wait for the task to complete immediately.

The task can be processed in another thread, message queue, callback, or event-driven flow. This improves responsiveness and decouples systems.

For example, after an order is created, sending confirmation email, publishing audit log, or updating analytics can be asynchronous.

However, async processing introduces new challenges:
- retry
- duplicate processing
- message ordering
- idempotency
- error handling
- monitoring and tracing

So I use async when the business flow can tolerate eventual completion and does not require immediate result.
When should we use asynchronous communication?
Senior answer script
I use asynchronous communication when the caller does not need the result immediately or when I want to decouple services.

Good use cases:
- sending email or SMS
- audit logging
- notification
- report generation
- data synchronization
- event-driven microservices
- heavy background processing

For example, after creating an order, Order Service can publish OrderCreated event. Inventory Service, Notification Service, and Analytics Service can consume the event independently.

This reduces direct dependency between services and improves scalability.
What are the risks of asynchronous processing?
Senior answer script
The main risk is that the flow becomes eventually consistent and harder to debug.

Common risks:
- duplicate messages
- out-of-order messages
- lost messages if not configured properly
- retry storm
- poison messages
- no immediate error feedback to user
- difficult tracing across services

To handle this, I design:
- idempotent consumers
- retry topic and dead letter topic
- correlation ID
- proper offset/ack handling
- monitoring and alerting
- business status tracking

For example, if payment event is consumed twice, the consumer should check transactionId and avoid double processing.
CompletableFuture vs message queue?
Senior answer script
CompletableFuture is useful for asynchronous processing inside the same application process. It is good for parallelizing independent tasks during one request.

Message queue is used for asynchronous communication between services or for durable background processing.

CompletableFuture is not durable. If the application crashes, the task may be lost.
Message queue is durable if configured properly, so it is better for business-critical async workflows.

Example:
- Use CompletableFuture to call user-service and order-service in parallel.
- Use Kafka/SQS/RabbitMQ to process OrderCreated event asynchronously across services.
Code example
// CompletableFuture: async inside same service
CompletableFuture<User> userFuture =
    CompletableFuture.supplyAsync(() -> userClient.getUser(userId), executor);

CompletableFuture<List<Order>> orderFuture =
    CompletableFuture.supplyAsync(() -> orderClient.getOrders(userId), executor);

UserProfile profile = userFuture
    .thenCombine(orderFuture, UserProfile::new)
    .orTimeout(2, TimeUnit.SECONDS)
    .exceptionally(ex -> UserProfile.empty())
    .join();

// Message-driven async example
@KafkaListener(topics = "order-created")
public void handle(OrderCreatedEvent event) {
    if (processedEventRepository.exists(event.eventId())) {
        return; // idempotency
    }
    notificationService.sendOrderEmail(event.orderId());
    processedEventRepository.save(event.eventId());
}

3. Java synchronized Keyword

synchronized là Java locking mechanism để bảo vệ critical section. Nó giải quyết race condition nhưng có trade-off về performance và lock contention.

Context — why this matters

  • Spring service là singleton mặc định, nếu lưu shared mutable state trong field thì nhiều request/thread có thể cùng sửa data.
  • synchronized đảm bảo mutual exclusion và visibility.
  • Nhưng synchronized chỉ lock trong cùng JVM. Nó không giải quyết distributed race condition giữa nhiều instances/pods.
  • Trong microservices nhiều instance, cần DB lock, Redis atomic operation, distributed lock hoặc message serialization tùy use case.

Key concepts

Intrinsic lock / monitor lock

Mỗi Java object có monitor lock. synchronized dùng lock này.

Synchronized method

Lock toàn bộ method dựa trên this hoặc Class object nếu static method.

Synchronized block

Lock một block cụ thể, scope nhỏ hơn method.

Mutual exclusion

Chỉ một thread giữ lock và chạy critical section tại một thời điểm.

Visibility

Khi thread release lock, changes được visible cho thread khác acquire cùng lock.

Lock contention

Nhiều thread tranh lock làm giảm throughput.

Common interview questions

What is synchronized in Java?
Senior answer script
synchronized is a Java keyword used to control access to a critical section.

It ensures that only one thread can execute a synchronized block or method protected by the same lock at a time.

It provides two important guarantees:
1. Mutual exclusion: only one thread enters the critical section.
2. Visibility: changes made by one thread before releasing the lock are visible to another thread after acquiring the same lock.

I use synchronized for simple in-memory thread-safety problems. But I avoid using it for long-running operations or distributed coordination.
synchronized method vs synchronized block?
Senior answer script
A synchronized method locks the entire method.

For an instance method, it locks on this.
For a static method, it locks on the Class object.

A synchronized block locks only a specific block of code and can use a specific lock object.

I usually prefer synchronized block when I want a smaller lock scope. Smaller lock scope reduces contention and improves performance.

Senior point: never lock more code than necessary.
Can synchronized solve all concurrency problems?
Senior answer script
No.

synchronized only works inside the same JVM process. If the application runs on multiple instances or Kubernetes pods, each instance has its own memory and its own lock.

For distributed systems, synchronized cannot protect shared database records or shared Redis keys across instances.

For those cases, I use:
- database locking
- optimistic locking with @Version
- Redis atomic operation
- distributed lock with caution
- Kafka partition ordering
- single writer pattern

So synchronized is useful, but only for local JVM critical sections.
What are the drawbacks of synchronized?
Senior answer script
Drawbacks:
- lock contention can reduce throughput
- long synchronized blocks can block many threads
- risk of deadlock if multiple locks are acquired in inconsistent order
- not suitable for distributed locking
- harder to tune than some higher-level concurrency utilities

For counters, I prefer AtomicInteger or LongAdder.
For maps, I prefer ConcurrentHashMap.
For advanced locking, I may use ReentrantLock.
For database consistency, I use DB locking instead of JVM locking.
Code example
public class Counter {
    private int count = 0;

    // synchronized method: locks on this
    public synchronized void increment() {
        count++;
    }

    public synchronized int getCount() {
        return count;
    }
}

// Better for high-concurrency counter
public class SafeCounter {
    private final LongAdder counter = new LongAdder();

    public void increment() {
        counter.increment();
    }

    public long getCount() {
        return counter.sum();
    }
}

4. Synchronous vs Asynchronous vs Reactive

Senior cần biết chọn model đúng, không dùng async/reactive chỉ vì công nghệ mới.

Context — why this matters

  • Synchronous phù hợp request cần kết quả ngay.
  • Asynchronous phù hợp side-effect/background task/event-driven communication.
  • Reactive phù hợp high-concurrency I/O-bound system với non-blocking stack.
  • Sai lầm thường gặp là dùng reactive nhưng bên trong vẫn block, hoặc async nhưng không có retry/idempotency.

Key concepts

Synchronous

Simple, direct, immediate result, but blocking.

Asynchronous

Decoupled, background processing, eventual consistency.

Reactive

Non-blocking stream/event model, efficient for I/O-heavy high concurrency.

Eventual consistency

Data không nhất thiết consistent ngay lập tức nhưng sẽ consistent sau một khoảng thời gian.

Backpressure

Consumer kiểm soát tốc độ producer trong reactive stream.

Common interview questions

How do you choose between synchronous, asynchronous, and reactive?
Senior answer script
I choose based on business requirement and system characteristics.

If the caller needs the result immediately, I use synchronous processing.
Example: login, permission check, payment authorization.

If the task can happen later or should be decoupled, I use asynchronous processing.
Example: email, notification, audit log, event-driven integration.

If the system is I/O-heavy and needs to handle high concurrency with fewer threads, I consider reactive.
Example: API gateway, streaming, external API aggregation with non-blocking clients.

I do not choose async or reactive just because it is modern. I consider complexity, team skill, observability, failure handling, and whether the whole stack supports it.
Give a real order processing example using sync and async.
Senior answer script
In an order flow, I usually keep critical user-facing steps synchronous and non-critical side effects asynchronous.

Synchronous:
1. Validate request.
2. Check product availability.
3. Create order.
4. Authorize payment or return payment status.

Asynchronous:
1. Send confirmation email.
2. Publish OrderCreated event.
3. Update analytics.
4. Notify warehouse.
5. Generate invoice if it does not need immediate response.

This keeps the user response fast while still allowing downstream systems to process events independently.
Code example
// Synchronous critical flow
@PostMapping("/orders")
public ResponseEntity<OrderResponse> createOrder(@RequestBody OrderRequest request) {
    OrderResponse response = orderService.createOrder(request);
    return ResponseEntity.status(HttpStatus.CREATED).body(response);
}

// Async side effect after order created
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onOrderCreated(OrderCreatedEvent event) {
    eventPublisher.publish(event); // Kafka/SQS/RabbitMQ
}

Common interview questions

Senior answer: Explain synchronous and asynchronous processing.
Senior answer script
Synchronous processing means the caller waits for the operation to complete before continuing. It is simple and suitable when the result is required immediately, such as login, permission check, or payment authorization.

Asynchronous processing means the caller does not need to wait immediately. The task can be processed in another thread, message queue, event, or callback. It is suitable for email, notification, audit logging, report generation, and event-driven communication.

The trade-off is that asynchronous processing improves responsiveness and decoupling, but it introduces complexity: retry, duplicate handling, idempotency, ordering, failure tracking, and observability.

In production, I usually keep critical user-facing decisions synchronous and move non-critical side effects asynchronous. For example, in order creation, payment authorization can be synchronous, but email notification and analytics update can be asynchronous.

Also, synchronous/asynchronous should not be confused with Java synchronized. synchronized is a locking mechanism used to protect shared mutable state inside the same JVM. It does not solve distributed concurrency across multiple service instances.
