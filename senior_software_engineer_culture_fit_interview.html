Tell me about a conflict with a teammate. How did you resolve it?

Senior sample answer

In one project, another senior engineer and I disagreed about an integration design. He preferred synchronous communication because it was simpler. I preferred an asynchronous recovery flow because the external provider was sometimes slow and unstable.

I arranged a short design discussion instead of continuing the argument in code-review comments. We compared both options using response time, failure handling, maintenance cost, and business needs. We also built a small proof of concept.

We finally used a mixed design: synchronous processing for the normal flow and asynchronous retry for failed requests. The key point was that we focused on evidence and project requirements, not personal opinions.

How do you explain a complex issue to non-technical teammates?

Senior sample answer

I remove unnecessary technical terms and start with the business impact. For example, instead of saying, “The downstream API causes thread-pool exhaustion,” I say, “Our service is waiting too long for another system. Many requests are waiting at the same time, so new customers may also see delays.”

I explain what happened, who is affected, what we are doing now, and what the permanent solution will be. I may use a simple diagram or one real customer example.

At the end, I ask whether the explanation is clear and invite questions. My goal is not to show technical knowledge. My goal is to help the stakeholder make a correct decision.

What is your approach to giving feedback about code or a technical design?

Senior sample answer

My feedback focuses on the work, not the person. I normally explain what I noticed, why it may cause a problem, and what improvement I suggest.

For example: “This loop performs one database query for every record. With large data, it may cause an N+1 query problem. Could we load the required data in one query or use batch fetching?”

For small issues, a pull-request comment is enough. For an important design concern, I prefer a short discussion because written comments may create misunderstanding.

I also mention good parts of the implementation. Code review should improve code quality and help the engineer grow.

What is your opinion about pair programming and code reviews?

Senior sample answer

I support both, but I use them for the right situation.

Code review should be part of normal development. It helps find defects, share knowledge, improve readability, and maintain common standards. Reviewers should focus on correctness, security, performance, and maintainability—not personal formatting preferences.

Pair programming is useful for complex logic, production defects, security-sensitive code, onboarding, and unfamiliar technology. I do not think every simple task needs pair programming because it can be expensive.

The purpose is not to follow a process blindly. The purpose is to improve quality, reduce risk, and spread knowledge across the team.

Tell me about a time you convinced the team to use your technical solution.

Senior sample answer

In a microservice project, we needed to update our database and publish an event. The first proposal was to save the record and then directly send the message.

I explained a failure case: the database transaction could succeed, but message publishing could fail. The systems would then become inconsistent.

I proposed the transactional outbox pattern. The business change and outbox event would be stored in one database transaction. A separate worker would publish the event and retry safely.

I presented the failure scenarios and a small implementation example. After comparing reliability and complexity, the team accepted the approach for critical events.

How do you debug a complex problem with other engineers?

Senior sample answer

First, we agree on the exact symptom, impact, time range, and affected environment. Then we divide the investigation instead of having everyone check the same thing.

One engineer may check application logs, another the database, another infrastructure and network, and another recent deployments. We use the same request ID and timestamp and share findings in one channel.

For a major incident, one person coordinates actions and stakeholder updates. This prevents random changes and duplicated work.

After recovery, we document the root cause, contributing factors, recovery steps, and prevention actions. Collaborative debugging works best when facts and responsibilities are clear.

Problem-Solving & Critical Thinking

Tell me about a difficult technical issue you debugged.

Senior sample answer

In one project, some payment requests were processed more than once when users retried quickly or when the provider response was delayed.

The issue happened only under specific timing conditions. I added trace IDs and reviewed application logs, database updates, and provider requests. I found a race condition: two requests could read the same pending status before either transaction completed.

We introduced an idempotency key, a unique database constraint, and an atomic status update. We also added concurrency tests and monitoring for duplicate attempts.

The solution prevented duplicate processing and improved our ability to investigate similar cases. The lesson was that payment operations must be designed for retries and concurrent requests from the beginning.

How do you find the root cause of a performance problem?

Senior sample answer

I do not optimize based only on feeling. I begin with measurements.

I confirm the slow operation and expected response time. Then I check metrics and distributed traces to find which layer uses the most time. I review database execution plans and query counts, external API latency, thread and connection pools, CPU, memory, and garbage collection.

I reproduce the problem with realistic data or load, change one area, and measure again.

For example, an API may be slow because of an N+1 query, but it may also spend most of its time waiting for another service. Measurement prevents us from optimizing the wrong component.

How would you recover from serious technical debt?

Senior sample answer

First, I create a technical-debt inventory. I classify items by production risk, change frequency, defect rate, security impact, and development cost.

I prioritize debt that causes incidents, blocks important features, creates security risk, makes every change expensive, or has no test coverage.

I would not stop all feature work for a large rewrite unless the system was truly unsafe. I prefer incremental improvement: add tests, define clear boundaries, replace one component at a time, and measure progress.

Technical debt should be included in product planning because it has a business cost. It affects delivery speed, defect rate, operational effort, and the ability to respond to change.

When do you use a workaround instead of rebuilding correctly?

Senior sample answer

I consider urgency, customer impact, safety, reversibility, and long-term cost.

A workaround is acceptable when there is urgent production impact, the change is low risk, it can be removed easily, monitoring exists, and a follow-up task has an owner and deadline.

A workaround is not acceptable if it can create security problems, data corruption, or uncontrolled financial impact. For example, temporarily disabling a non-critical feature may be safer than performing a large redesign during an incident.

After the system is stable, we review the root cause and implement a proper solution. Temporary code should not silently become permanent architecture.

Have you designed a resilient or failover solution?

Senior sample answer

Yes. For integrations with unstable external systems, I have used timeouts, limited retries with backoff, circuit breakers, idempotency keys, queues, dead-letter queues, health checks, monitoring, and manual replay tools.

For example, when a provider is unavailable, the system should not send unlimited requests. A circuit breaker temporarily stops calls, while failed business operations are stored safely for later retry.

Retries must be designed carefully because they can create duplicate transactions. That is why idempotency and clear operation status are also required.

Resilience is a complete design. Adding one retry annotation without considering duplicates, overload, monitoring, and recovery is not enough.
