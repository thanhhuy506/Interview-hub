01 · Problem analysis

Phép tính đúng, nhưng execution model chưa tối ưuThe calculation is correct, but the execution model is not optimal

Con số 13,89 giờ chỉ đúng khi request sau phải chờ request trước hoàn tất. Cần phân biệt rõ latency, concurrency và throughput.

The 13.89-hour result is correct only when each request waits for the previous one. We must clearly distinguish latency, concurrency, and throughput.

Sequential baseline

Một request tại một thời điểmOne request at a time

50,000 × 1 second = 50,000 seconds
50,000 ÷ 3,600 = 13.89 hours

Throughput chỉ là 1 SMS/giây. CPU thường không bận; thread chủ yếu đang chờ network response.

Throughput is only one SMS per second. The CPU is usually not busy; the thread mostly waits for the network response.

Concurrent model

Nhiều request đang chờ cùng lúcMultiple in-flight requests

Capacity TPS ≈ Concurrency ÷ Latency
Effective TPS = min(Capacity TPS, Provider TPS)

Latency 1 giây và concurrency 100 tạo capacity khoảng 100 TPS. Nếu provider chỉ cho 60 TPS, effective throughput vẫn chỉ là 60 TPS.

One-second latency with concurrency 100 provides about 100 TPS capacity. If the provider allows only 60 TPS, effective throughput remains 60 TPS.

Điểm dễ nhầm: chunk size 500 không đồng nghĩa với 500 requests chạy song song. Chunk chỉ là đơn vị gom dữ liệu hoặc đơn vị task. Số request đồng thời được quyết định bởi thread pool, reactive concurrency, connection pool và rate limiter.
Common misunderstanding: a chunk size of 500 does not mean 500 requests run in parallel. A chunk is only a data or task boundary. Actual concurrent requests are controlled by the thread pool, reactive concurrency, connection pool, and rate limiter.

03B · Complete catalog

12 giải pháp có thể áp dụng12 possible solutions

Các solution bên dưới đi từ đơn giản đến production-grade. Một số là execution model, một số là infrastructure pattern; vì vậy production thường kết hợp nhiều solution thay vì chọn đúng một cái.

The solutions below range from basic to production-grade. Some are execution models while others are infrastructure patterns, so a production design normally combines several solutions rather than selecting only one.

Baseline

Sequential loop

Một thread gọi từng customer. Thời gian khoảng 13,89 giờ. Chỉ hợp với số lượng rất nhỏ hoặc script tạm thời.

One thread calls the provider for each customer. It takes about 13.89 hours. Suitable only for a very small volume or a temporary script.

Ưu: đơn giản. Nhược: chậm, recovery kém.

Pros: simple. Cons: slow and poor recovery.

Basic parallel

Fixed thread pool — one task/customer

Submit 50.000 tasks vào bounded executor; mỗi worker xử lý một customer. Load balancing tốt hơn chunk nhưng task/queue overhead cao hơn.

Submit 50,000 tasks to a bounded executor; each worker handles one customer. It balances work better than chunks but creates more task and queue overhead.

Ưu: tận dụng threads đều. Nhược: phải bound queue; chưa durable.

Pros: good worker utilization. Cons: requires a bounded queue and is not durable.

Your solution

Chunk + CompletableFuture / @Async

Đọc 500 records/lần, tạo 100 chunk tasks và chạy 10–20 chunks song song. Dễ kiểm soát memory và phù hợp application hiện có.

Read 500 records at a time, create 100 chunk tasks, and run 10–20 chunks concurrently. It controls memory and fits an existing application well.

Ưu: dễ triển khai. Nhược: một customer chậm có thể giữ cả chunk; restart cần checkpoint.

Pros: easy to implement. Cons: one slow customer can hold a chunk; restart requires checkpoints.

Avoid for this case

parallelStream()

Code ngắn nhưng mặc định dùng common ForkJoinPool, không thích hợp cho blocking external I/O và khó điều khiển rate, timeout, context.

The code is short, but it uses the common ForkJoinPool by default, is unsuitable for blocking external I/O, and makes rate, timeout, and context control harder.

Kết luận: không nên dùng cho campaign production.

Conclusion: avoid it for a production campaign.

Java 21

Virtual threads + Semaphore

Giữ blocking code dễ đọc nhưng chạy nhiều virtual threads. Vẫn bắt buộc dùng Semaphore/rate limiter; virtual threads không làm provider mạnh hơn.

Keep readable blocking code while running many virtual threads. A semaphore and rate limiter are still required; virtual threads do not increase provider capacity.

Ưu: code đơn giản, I/O scale tốt. Nhược: không cung cấp durability.

Pros: simple code and efficient I/O scaling. Cons: no durability.

Batch platform

Spring Batch chunk + partitioning

Reader–Processor–Writer, chunk transaction, JobRepository, restart và partitioning có sẵn. Rất tốt cho scheduled/offline batch.

Provides Reader–Processor–Writer, chunk transactions, JobRepository, restart, and partitioning. Very good for scheduled or offline batch work.

Ưu: checkpoint/restart mạnh. Nhược: cấu hình nặng hơn; external call vẫn cần idempotency.

Pros: strong checkpoint and restart. Cons: more configuration; external calls still need idempotency.

Non-blocking

WebFlux / Reactive pipeline

Dùng WebClient và bounded flatMap concurrency. Hiệu quả khi latency cao và hệ thống đã dùng reactive stack.

Use WebClient and bounded flatMap concurrency. Efficient when latency is high and the system already uses a reactive stack.

Ưu: nhiều in-flight I/O với ít threads. Nhược: complexity, chưa durable nếu đứng một mình.

Pros: many in-flight calls with few threads. Cons: added complexity and no durability by itself.

No broker

Database job table + SKIP LOCKED

Workers claim rows bằng FOR UPDATE SKIP LOCKED. Đây là durable queue đơn giản khi chưa thể vận hành Kafka/RabbitMQ/SQS.

Workers claim rows with FOR UPDATE SKIP LOCKED. This is a simple durable queue when Kafka, RabbitMQ, or SQS is unavailable.

Ưu: ít infrastructure. Nhược: polling và high throughput gây tải DB.

Pros: less infrastructure. Cons: polling and high throughput load the database.

Production standard

Message queue + distributed workers

Kafka/SQS/RabbitMQ lưu jobs; consumers scale ngang, retry, DLQ, backpressure và recovery rõ ràng.

Kafka, SQS, or RabbitMQ stores jobs; consumers provide horizontal scaling, retries, a DLQ, backpressure, and recovery.

Ưu: reliable và scalable. Nhược: thêm infrastructure, monitoring và eventual consistency.

Pros: reliable and scalable. Cons: additional infrastructure, monitoring, and eventual consistency.

Cloud native

SQS + Lambda / serverless fan-out

Queue trigger Lambda, concurrency và reserved concurrency được cấu hình. Phù hợp workload theo đợt trên AWS.

A queue triggers Lambda with configured concurrency and reserved concurrency. Suitable for bursty workloads on AWS.

Ưu: auto-scale, trả theo usage. Nhược: cold start, account limits, distributed rate limit phức tạp.

Pros: auto-scaling and pay-per-use. Cons: cold starts, account limits, and complex distributed rate limiting.

Check first

SMS provider bulk/campaign API

Gửi một batch gồm nhiều recipients hoặc upload campaign; provider tự fan-out, throttle và đôi khi cung cấp delivery report.

Submit a batch of recipients or upload a campaign; the provider performs fan-out, throttling, and sometimes delivery reporting.

Ưu: ít network calls và vận hành đơn giản nhất. Nhược: phụ thuộc tính năng, batch limit và SLA provider.

Pros: fewer network calls and the simplest operations. Cons: depends on provider features, batch limits, and SLA.

Best general design

Hybrid: chunk + outbox + queue + bounded workers

Chunk đọc customer, outbox chống mất message, queue giữ job, reactive/virtual-thread workers gọi provider dưới global rate limit.

Chunk customer reads, use an outbox to prevent message loss, retain jobs in a queue, and call the provider with reactive or virtual-thread workers under a global rate limit.

Ưu: tổng hợp reliability, throughput và recovery. Nhược: nhiều thành phần nhất.

Pros: combines reliability, throughput, and recovery. Cons: the most components.

04 · Deep dive

Chunk và async thực sự hoạt động như thế nào?How do chunking and async processing really work?

Đây là phần quan trọng khi interviewer hỏi sâu: “Tại sao chunk?”, “Tại sao không tạo 50.000 threads?”, hoặc “Chunk size có phải concurrency không?”.

This is the key section when an interviewer asks: “Why chunk?”, “Why not create 50,000 threads?”, or “Is chunk size the same as concurrency?”.

Chunk responsibility

Chunk kiểm soát data volumeChunking controls data volume

50,000 customers ÷ 500
= 100 chunks
  • Không query và giữ toàn bộ 50.000 records trong heap.
  • Giảm transaction size và dễ checkpoint theo page/chunk.
  • Mỗi chunk có thể trở thành một task hoặc chỉ là một page để tạo messages.
  • Chunk size không trực tiếp quyết định TPS.
  • Avoid querying and holding all 50,000 records in the heap.
  • Reduce transaction size and make page or chunk checkpoints easier.
  • Each chunk can be one task or merely a page used to create messages.
  • Chunk size does not directly determine TPS.
Async responsibility

Async tăng số I/O đang chạyAsync increases in-flight I/O

10 workers × 1 request/second
≈ 10 TPS → 83m 20s
  • Thread pool 10 nghĩa là tối đa khoảng 10 synchronous calls đồng thời.
  • Reactive không cần một platform thread cho mỗi request đang chờ.
  • Cả hai đều phải bounded; unbounded async gây OOM, 429 và connection exhaustion.
  • Concurrency không được vượt provider TPS hoặc HTTP pool capacity.
  • A pool of 10 threads permits about 10 synchronous calls at the same time.
  • Reactive processing does not need one platform thread per waiting request.
  • Both must be bounded; unbounded async causes OOM, 429 errors, and connection exhaustion.
  • Concurrency must not exceed provider TPS or HTTP pool capacity.
Ví dụ chính xác:Precise example: Có 100 chunks, mỗi chunk 500 customers và executor 10 threads. Tại một thời điểm chỉ 10 chunks chạy. Nếu mỗi thread loop tuần tự trong chunk, chỉ khoảng 10 SMS calls cùng lúc—not 5.000. Khi một chunk hoàn tất, thread lấy chunk tiếp theo. There are 100 chunks, 500 customers per chunk, and a 10-thread executor. Only 10 chunks run at one time. If each thread loops sequentially inside its chunk, there are only about 10 concurrent SMS calls—not 5,000. When one chunk finishes, its thread takes the next chunk.

Crash window

Provider success, app crashProvider succeeds, application crashes

  1. Provider nhận SMS và trả success.
  2. Application crash trước khi mark SENT.
  3. Queue redeliver message.
  4. Nếu provider hỗ trợ idempotency, cùng key sẽ không gửi lần hai.
  1. The provider accepts the SMS and returns success.
  2. The application crashes before marking SENT.
  3. The queue redelivers the message.
  4. If the provider supports idempotency, the same key prevents a second delivery.
Thực tế quan trọng: DB unique constraint chỉ ngăn application xử lý duplicate record; nó không loại bỏ hoàn toàn duplicate SMS trong crash window. Exactly-once end-to-end cần provider hỗ trợ idempotency hoặc API tra cứu trạng thái theo request key/provider message ID.
Important reality: a database unique constraint prevents duplicate application records, but it cannot completely remove duplicate SMS delivery in the crash window. End-to-end exactly-once behavior requires provider idempotency or a status lookup API using the request key or provider message ID.

CampaignService.java — page by 500, process at bounded concurrency
@Service
public class CampaignService {
    private static final int CHUNK_SIZE = 500;
    private final CustomerRepository customerRepository;
    private final SmsWorker smsWorker;
    private final Executor smsExecutor;

    public void sendCampaign(long campaignId) {
        List<CompletableFuture<Void>> futures = new ArrayList<>();
        int pageNumber = 0;
        Page<Customer> page;

        do {
            page = customerRepository.findTargets(
                PageRequest.of(pageNumber++, CHUNK_SIZE)
            );

            // Copy because Page content should not be reused or mutated.
            List<Customer> chunk = List.copyOf(page.getContent());

            futures.add(CompletableFuture.runAsync(
                () -> processChunk(campaignId, chunk),
                smsExecutor
            ));
        } while (page.hasNext());

        CompletableFuture.allOf(
            futures.toArray(new CompletableFuture[0])
        ).join();
    }

    private void processChunk(long campaignId, List<Customer> chunk) {
        // Sequential inside one chunk; parallelism comes from the executor.
        for (Customer customer : chunk) {
            smsWorker.send(campaignId, customer);
        }
    }
}

ReactiveSmsService.java — non-blocking with bounded concurrency
@Service
public class ReactiveSmsService {
    private static final int MAX_CONCURRENCY = 100;

    public Mono<Void> sendCampaign(
            long campaignId,
            Flux<Customer> customers) {

        return customers
            .flatMap(
                customer -> sendOne(campaignId, customer)
                    .onErrorResume(RetryableException.class,
                        ex -> saveForRetry(campaignId, customer, ex)),
                MAX_CONCURRENCY
            )
            .then();
    }

    private Mono<Void> sendOne(
            long campaignId, Customer customer) {
        String key = campaignId + ":" + customer.id();

        return acquireRateLimitPermit()
            .then(webClient.post()
                .uri("/messages")
                .header("Idempotency-Key", key)
                .bodyValue(toRequest(customer))
                .retrieve()
                .bodyToMono(SmsResponse.class))
            .flatMap(response -> markSent(key, response.messageId()));
    }
}
Lưu ý: flatMap(..., 100) giới hạn 100 subscriptions in-flight, nhưng nó không tự đảm bảo đúng 100 requests/second. Vẫn cần rate limiter vì nếu latency chỉ 100 ms, concurrency 100 có thể tạo capacity gần 1.000 TPS.
Note: flatMap(..., 100) limits in-flight subscriptions to 100, but it does not guarantee exactly 100 requests per second. A rate limiter is still required because, with 100 ms latency, concurrency 100 can provide nearly 1,000 TPS capacity.
SmsConsumer.java — atomic claim, rate limit, retry and DLQ
@KafkaListener(
    topics = "sms-notification",
    concurrency = "20"
)
public void consume(NotificationTask task) {
    // Atomic update: PENDING/RETRY -> PROCESSING.
    if (!notificationRepository.claim(task.id())) {
        return; // Already sent or owned by another worker.
    }

    String key = task.campaignId() + ":" + task.customerId();

    try {
        rateLimiter.acquirePermission();
        SmsResponse response = smsProvider.send(
            task.phoneNumber(), task.content(), key
        );
        notificationRepository.markSent(
            task.id(), response.providerMessageId()
        );
        // Queue acknowledgement happens only after SENT is persisted.
    } catch (RetryableProviderException ex) {
        notificationRepository.markRetry(task.id(), ex.getMessage());
        throw ex; // Broker retry with backoff.
    } catch (PermanentProviderException ex) {
        notificationRepository.markFailed(task.id(), ex.getMessage());
        deadLetterPublisher.publish(task, ex);
    }
}

Final recommendation

Ưu tiên Bulk API; nếu không có, dùng chunk + queue + bounded workers. Prefer a bulk API; otherwise use chunking + queue + bounded workers.

Nếu provider có Bulk Campaign API với tracking và idempotency tốt, hãy gửi theo provider batch limit vì đây thường là cách nhanh và đơn giản nhất. Nếu provider chỉ có single-message API, hãy đọc 500 records/lần; tạo notification record + outbox trong DB transaction; publish từng job vào Kafka/SQS/RabbitMQ; workers gửi theo global rate limit. If the provider offers a bulk campaign API with strong tracking and idempotency, submit recipients according to its batch limit because this is usually the fastest and simplest option. If only a single-message API exists, read 500 records at a time; create notification and outbox records in one database transaction; publish each job to Kafka, SQS, or RabbitMQ; and let workers send under a global rate limit. At 100 TPS, theoretical time is 500 seconds or 8 minutes 20 seconds; a practical estimate is about 9–12 minutes.

Vietnamese
“Nếu gửi tuần tự 50.000 SMS và mỗi provider call mất một giây, tổng thời gian sẽ khoảng 13,89 giờ. Tôi sẽ không tạo 50.000 threads. Tôi sẽ đọc customer theo chunk, ví dụ 500 records/lần, để kiểm soát memory và transaction size. Sau đó tôi tạo notification job và publish vào Kafka, RabbitMQ hoặc SQS.

Nhiều consumers xử lý các jobs song song, nhưng concurrency phải được giới hạn theo SMS provider TPS, HTTP connection pool và capacity của application. Ví dụ provider hỗ trợ 100 TPS thì thời gian lý thuyết là 50.000 chia 100, bằng 500 giây hay khoảng 8,3 phút.

Tôi cũng lưu trạng thái PENDING, PROCESSING, SENT, RETRY và FAILED; tạo idempotency key campaignId cộng customerId trước khi gọi provider; retry lỗi transient bằng exponential backoff và jitter; đưa message hết retry vào DLQ. Nếu cần tránh mất message giữa database và queue, tôi dùng transactional outbox. Tóm lại, chunk kiểm soát data volume, async workers tăng throughput, còn queue cung cấp durability, backpressure và recovery.”
English
“If we send 50,000 SMS messages sequentially and each provider call takes one second, the total time is about 13.89 hours. I would not create 50,000 threads. I would read customers in chunks, for example 500 records at a time, to control memory and transaction size. I would then create notification jobs and publish them to Kafka, RabbitMQ, or SQS.

Multiple consumers process the jobs concurrently, but concurrency must be bounded by the SMS provider’s TPS limit, the HTTP connection pool, and application capacity. For example, if the provider supports 100 TPS, the theoretical duration is 50,000 divided by 100, which is 500 seconds or about 8.3 minutes.

I would also persist PENDING, PROCESSING, SENT, RETRY, and FAILED states; create a deterministic idempotency key from the campaign ID and customer ID before calling the provider; retry transient failures with exponential backoff and jitter; and move exhausted messages to a dead-letter queue. To avoid losing messages between the database and the broker, I would use a transactional outbox. In summary, chunking controls data volume, async workers improve throughput, and the queue provides durability, backpressure, and recovery.”
11 · Follow-up questions

Các câu interviewer có thể hỏi tiếpLikely interviewer follow-up questions

Tại sao không chỉ dùng multithreading?Why not use only multithreading?
Thread pool giúp parallelism trong một process, nhưng không tự cung cấp durability, cross-instance scaling, message retention, replay hay DLQ. Queue giải quyết các phần đó.
A thread pool provides parallelism inside one process, but it does not provide durability, cross-instance scaling, message retention, replay, or a DLQ. A queue provides those capabilities.
Application restart sau khi gửi 30.000 thì sao?What happens if the app restarts after 30,000 messages?
Database biết records nào SENT; queue giữ jobs chưa ack; reconciliation chuyển PROCESSING quá lease timeout về RETRY. Workers tiếp tục mà không cần chạy lại toàn campaign.
The database identifies SENT records; the queue retains unacknowledged jobs; reconciliation moves PROCESSING records beyond their lease timeout to RETRY. Workers continue without restarting the whole campaign.
Chunk size 500 có phải tối ưu nhất?Is a chunk size of 500 always optimal?
Không. Đây là starting point. Tuning dựa trên row size, query latency, memory, transaction duration và database load. Chunk size gần như độc lập với provider TPS.
No. It is a starting point. Tune it using row size, query latency, memory, transaction duration, and database load. Chunk size is largely independent of provider TPS.
Có đảm bảo exactly once không?Can we guarantee exactly-once delivery?
Queue thường cho at-least-once. Ta đạt effectively-once bằng DB uniqueness, atomic claim và provider idempotency. Nếu provider không hỗ trợ idempotency, vẫn còn một duplicate window nhỏ khi app crash sau provider success.
Queues normally provide at-least-once delivery. We achieve effectively-once behavior through database uniqueness, atomic claim, and provider idempotency. Without provider idempotency, a small duplicate window remains after provider success and before database update.
Tại sao cần rate limiter nếu đã giới hạn threads?Why use a rate limiter if threads are already limited?
Concurrency giới hạn số request in-flight; rate limiter giới hạn số request bắt đầu trong một khoảng thời gian. Khi latency thay đổi hoặc có nhiều pods, hai con số không còn tương đương.
Concurrency limits in-flight requests; a rate limiter limits requests started during a time window. When latency changes or multiple pods run, the two numbers are no longer equivalent.
Kafka hay SQS/RabbitMQ?Kafka or SQS/RabbitMQ?
SQS phù hợp AWS managed task queue; RabbitMQ mạnh về routing/ack; Kafka phù hợp throughput lớn, replay và event platform. Chọn theo hệ sinh thái, ordering, retention và operational capability—not theo trend.
SQS is a good managed task queue on AWS; RabbitMQ offers strong routing and acknowledgement controls; Kafka suits high throughput, replay, and event platforms. Choose based on ecosystem, ordering, retention, and operational capability—not trends.
