Software Design Diagrams

A practical guide to the diagrams that software teams use to explain structure, behavior, data, deployment, security, and user experience.

How to read this page

The English is kept around IELTS 5.5–6.5 level. Important technical words include a short Vietnamese meaning.

BehaviorWhat happens next?

One key idea

A diagram is not “better” because it looks more complex. A good diagram answers one clear question for one clear audience.

Architecture = structure. Flow = process. Sequence = who talks to whom, and in what order.

Architecture Diagram

Architecture (kiến trúc) shows the major building blocks.

Very common

Use it when: you need to explain the system structure before going into detailed logic.

Example: “Our checkout request goes from the Web App to the API Gateway, then to Order, Payment, and Inventory services.”

C4 Model

C4 Model (mô hình 4 cấp kiến trúc) gives several levels of detail.

Best practice

Use it when: one architecture picture is either too simple or too detailed. C4 lets you zoom in step by step.

Sequence Diagram

Sequence (trình tự tương tác) shows messages in time order.

Very common

Use it when: debugging API calls, designing a new feature, or checking the order of service calls.

Flowchart / Activity Diagram

Flow (luồng xử lý) shows steps, decisions, and branches.

Very common

Flowchart: simple process or logic. Activity Diagram: better when the workflow has parallel work, joins, or more formal UML rules.

State Diagram

State (trạng thái) shows how one object changes over time.

Great for rules

Use it when: an object has strict lifecycle rules. Good examples are Order, Payment, Ticket, Document, or Account.

ERD — Entity Relationship Diagram

Entity (thực thể) and relationship (quan hệ) explain database structure.

Backend staple

Use it when: designing or discussing relational data. ERD focuses on entities, keys, and relationships.

Deployment Diagram

Deployment (triển khai) shows where software runs.

DevOps

Use it when: discussing servers, containers, clusters, cloud services, environments, and runtime connections.

Event Flow Diagram

Event-driven (hướng sự kiện) systems often need a clear event map.

Microservices

Use it when: services communicate through events, queues, topics, or a message broker.

User Flow

User flow (luồng người dùng) shows the path a user follows in the product.

Product / UX

Use it when: discussing screens, user tasks, navigation, onboarding, checkout, or product experience.

4. How to choose the right diagram

Start with the question you want to answer. Do not start with the drawing tool.

“What parts does the system have?”
→ Architecture / C4

Use for system structure and boundaries.

“Who talks to whom, and when?”
→ Sequence Diagram

Use for API calls and service interactions.

“What happens next?”
→ Flowchart / Activity

Use for logic and process steps.

“How does the status change?”
→ State Diagram

Use for lifecycle rules.

“How is data structured?”
→ ERD / Schema

Use for database and entity relationships.

“Where does data move?”
→ DFD / Data Lineage

Use for data processing and data movement.

“Where does the software run?”
→ Deployment / Infrastructure

Use for runtime, servers, cloud, and networks.

“Which events move between services?”
→ Event Flow

Use for queues, topics, and event-driven systems.

“How does the user move through the product?”
→ User Flow

Use for UX, screens, and product tasks.

Important: architecture style (phong cách kiến trúc) is not the same as a diagram type. Microservices, Clean Architecture, Hexagonal Architecture, Layered Architecture, and Event-Driven Architecture are design approaches. You can use several diagram types to explain them.

5. Database layer design for high-concurrency order systems

This section uses an e-commerce order system as a practical case. The main problem is keeping data correct while a promotion creates a very large traffic spike.

The main design goal

A database layer should give both correctness (tính đúng đắn dữ liệu) and good speed. For an order system, the hardest data is usually inventory, because many users may try to buy the same product at the same time.

Key idea: one million incoming requests should not become one million database writes at the same moment. The system should control traffic before it reaches the database.

Example scenario: promotion event

A flash sale starts at 20:00. A popular SKU has only 10,000 units, but millions of clients may refresh, add to cart, and press Buy during a short period. The system must avoid overselling (bán vượt tồn kho), remain responsive, and give users a clear result.

5.1 What a good database layer must protect

Consistency (tính nhất quán)Do not sell more items than the real stock.
Throughput (thông lượng)Process many operations per second without collapse.
Latency (độ trễ)Return useful feedback quickly.
Availability (tính sẵn sàng)Keep important functions working during failures.
Scalability (khả năng mở rộng)Grow capacity when users and data grow.
Recoverability (khả năng phục hồi)Recover safely after crashes, retries, or partial failures.

5.2 Basic data model for an order application

Core order and inventory entities

Keep business history separate from the current stock counter.

Database design

Reservation (giữ chỗ tồn kho): a temporary stock hold. It prevents another user from taking the same unit while payment or order confirmation is still in progress.

5.3 The classic inventory race condition

Race condition (điều kiện tranh chấp) happens when several requests read and change the same data at nearly the same time.

Unsafe pattern: Request A reads stock = 1. Request B also reads stock = 1. Both decide that the item is available. Both create an order. The system has sold 2 items while only 1 item existed.

Atomic conditional update

For a simple relational database, let the database check and reduce stock in one atomic write.

UPDATE inventory SET available = available - :qty WHERE sku_id = :sku AND available >= :qty;
  • If affected rows = 1 → stock was reserved/decreased.
  • If affected rows = 0 → not enough stock.

Strong default Good when contention is not extreme.

Optimistic locking (khóa lạc quan)

Store a version number. Update only if the version has not changed.

UPDATE inventory SET available = :new_value, version = version + 1 WHERE sku_id = :sku AND version = :old_version;

Good at medium contention Under a hot flash-sale SKU, many requests may retry and waste work.

Pessimistic locking (khóa bi quan)

Use a row lock such as SELECT ... FOR UPDATE before changing stock.

  • Easy to understand.
  • Strong consistency inside a short transaction.
  • But many buyers on one row become a long waiting line.

Poor for a very hot row Lock waits and deadlocks can grow quickly.

Serialized inventory worker

Send purchase attempts to a queue partitioned by SKU. One logical writer handles each SKU or partition in order.

  • Removes write races for the same hot key.
  • Creates clear backpressure.
  • Can process in small batches.

Strong for flash sales Requires queue, worker ownership, recovery, and monitoring.

5.4 Millions of requests: protect the database before the database

High-demand order architecture

The database is the final data store, not the first place that receives raw traffic.

Flash sale

Backpressure (kiểm soát áp lực ngược): when downstream capacity is full, the system slows, queues, or rejects new work instead of allowing every request to overload the database.

Filter traffic at the edge.

Use CDN, bot protection, authentication, request limits, and a waiting-room model when demand is far above supply.

Cache read-heavy data.

Product detail, promotion rules, images, and approximate availability can come from cache. Do not use an old cache value as the final decision for stock.

Use admission control (kiểm soát lượng request được nhận).

Only allow a safe amount of checkout work into the critical path. Fast rejection is often better than a 30-second timeout.

Partition the queue by SKU.

Requests for the same product go to the same logical owner. Different SKUs can still run in parallel.

Keep transactions short.

Update inventory and local order data quickly. Never keep a database lock open while calling an external payment provider.

Scale reads separately from writes.

Read replicas can serve product history, order history, or reports. Final inventory writes still need a clear source of truth.

5.5 Inventory reservation is usually better than “pay first, check later”

Recommended checkout flow

Reserve stock first, then complete payment, then confirm the sale.

Good UX + correctness
Why this helps UX: once stock is reserved, the user can receive a short countdown such as “Item reserved for 5 minutes.” They do not need to race other users during the payment form.

If payment fails or the timer ends, change the reservation to expired and return the quantity to available stock. This is a compensation (thao tác bù) step.

5.6 Do not keep one large transaction across services

Bad idea: lock the inventory row → call payment provider for several seconds → wait for network → update order → commit. This keeps a scarce database lock for too long and can block many other buyers.

A distributed order flow normally uses several short local transactions. The system keeps business state such as PENDING, RESERVED, PAID, CONFIRMED, or CANCELLED. This approach is often called a Saga (chuỗi giao dịch cục bộ có bước bù).

5.8 Idempotency: retries must not create duplicate orders

Mobile networks, proxies, and clients can retry the same request. An idempotent operation (thao tác lặp lại nhưng không tạo tác dụng phụ mới) gives the same business result when the same request is repeated.

POST /orders Idempotency-Key: checkout-user-123-attempt-456 UNIQUE(idempotency_key)

The first request creates the order. Later retries return the existing result instead of creating another order or charging the user twice.

5.9 Reliable events: database + message broker

A common failure is: the database commits an order, but publishing OrderCreated to the message broker fails. The Transactional Outbox (bảng sự kiện giao dịch) pattern solves this by writing the order and an outbox event in the same database transaction. A separate publisher sends the event later.

BEGIN; INSERT INTO orders (...); INSERT INTO outbox_events (type, payload) VALUES ('OrderCreated', ...); COMMIT;

Consumers should also be idempotent because the same message may be delivered more than once.

5.10 Hot SKU design: one product is different from many products

Sharding the database into 100 servers does not automatically solve one famous product with one shared stock counter. That SKU is a hot key (khóa dữ liệu có lượng truy cập cực cao).

Useful strategy: route the same SKU to the same queue partition or inventory owner, serialize only that SKU’s critical writes, and allow different SKUs to process in parallel. This keeps correctness without locking the whole database.

For extreme traffic, some systems keep a fast inventory counter in an in-memory store and update it with an atomic script. This can reduce database pressure, but the design must define durability, recovery, and reconciliation. A cache should not silently become the source of truth without a recovery plan.

5.12 Good user experience during extreme demand

1. Give a fast, honest status

“High demand — checking availability” is better than a long frozen spinner. If the system cannot safely accept more checkout work, fail fast with a clear message.

2. Use a waiting room when demand is much higher than stock

A controlled queue can improve fairness and protect backend capacity. Show position or progress when possible.

3. Reserve stock for a short time

After reservation succeeds, show a countdown. The user can complete payment without racing for stock every second.

4. Make retries safe

The user can press Retry after a network error without creating a second order or second charge.

5. Separate “request accepted” from “order confirmed”

For async flows, show states such as Processing, Reserved, Payment pending, Confirmed, or Sold out. Do not show success too early.

6. Give a useful sold-out path

Offer a waitlist, similar products, another store, or a notification option. A clear alternative is better than a generic error.

5.13 A practical reference architecture

Catalog path:

CDN / cache → Product API → read replica. This path is read-heavy and can scale widely.

Checkout admission:

Gateway → rate limit / waiting room → Order API. Only safe traffic enters the critical path.

Inventory allocation:

Queue partitioned by SKU → inventory worker → atomic database update / reservation.

Order transaction:

Create PENDING order + reservation + outbox event with short local transactions.

Payment:

Call external payment outside the database lock. Confirm or compensate later.

Async side effects:

Events drive email, analytics, shipping, loyalty points, and other non-critical work.

Observability:

Measure queue depth, reserve success rate, DB lock time, p95/p99 latency, DB connections, retry rate, sold-out rate, and payment reconciliation.

Design rule: keep the strict consistency area as small as possible. Inventory allocation needs strong control. Product images, descriptions, analytics, email, and many other tasks do not need to block the checkout transaction.

6. Caching layer design for e-commerce systems

Caching reduces repeated work and protects slower systems. The main skill is not only “put data in Redis”, but choosing what can be stale, what must be fresh, and what happens when the cache is missing or expires.

The main design goal

A cache (bộ nhớ đệm) stores data closer to the user or application so repeated reads can return faster. It should reduce load on databases, search engines, and external services.

Key idea: cache the data that is expensive to read or calculate, but do not let stale cached data make an unsafe business decision.

Example scenario: a hot product

A promotion starts at 20:00. One product page receives millions of views. Product information changes rarely, but price, promotion, cart, order status, and inventory have different update rates. They should not all use the same cache rule.

6.1 What caching can and cannot solve

Lower latency (giảm độ trễ)Serve common data without waiting for a slower database call.
Higher throughput (tăng thông lượng)More requests can be handled with the same backend capacity.
Database protection (bảo vệ cơ sở dữ liệu)Repeated reads do not reach the primary database every time.
Better resilience (khả năng chống lỗi tốt hơn)Some read paths can still return stale or fallback data during a backend problem.
Not a consistency solutionA cache alone does not solve overselling, duplicate payment, or transaction correctness.
Not free memoryCache capacity, eviction, hot keys, invalidation, and failure must be designed.

6.2 Common cache layers

Multi-layer cache architecture

Use the cheapest and closest layer first. Each layer protects the next one.

Common architecture

Browser / HTTP cache

Good for static assets and public GET responses. Use headers such as Cache-Control, ETag, and Last-Modified.

CDN / edge cache (cache biên)

Best for images, JavaScript, CSS, product pages, and public API responses that can be shared between users.

Local L1 cache (cache cục bộ trong service)

Very fast because it stays inside one application process. It is small and can become different between service instances.

Distributed L2 cache (cache phân tán)

Redis or Memcached can be shared by many application instances and can hold larger, common data sets.

6.5 Product data: cache by change frequency

One product page contains fields that change at different speeds. Do not put everything into one cache object with one TTL.

Split one product page into cache domains

Different data gets a different lifetime and invalidation rule.

Practical pattern

Example: product name and image may use a 1-hour or longer cache, while price may use minutes, and inventory shown on the page may be only an approximate “In stock / Low stock / Sold out” hint.

6.6 Shopping cart: frequent reads and writes

A cart is different from a product catalog. It is user-specific and changes often. A shared CDN cache is normally wrong for cart data.

Option A: Database is truth, Redis is cache

Use when the cart must survive cache loss and the database can handle the write rate.

GET cart:user:123 MISS → SELECT cart FROM DB → SET Redis WRITE → DB transaction → DEL/UPDATE Redis

Simple correctness More database writes.

Option B: Redis is the working cart store

Use Redis hashes or similar structures for fast add/remove/change operations. Persist or snapshot the cart if business rules require recovery.

HINCRBY cart:123 sku:ABC 1 HSET cart:123 updated_at ... EXPIRE cart:123 2592000

Important If Redis is the only copy, it is no longer “just cache”. Persistence, replication, backup, and recovery become part of the design.

Cart UX rule: use atomic cart operations, return the updated cart immediately, and keep a reasonable expiration such as days or weeks. Do not block each cart click on inventory reservation; validate or reserve stock later during checkout.

6.7 Orders: cache reads, not critical state transitions

Orders are durable business records. The database or event-sourced store should remain authoritative. Cache helps with frequent reads such as “My Orders” or order detail pages.

Create or update order in the database.

Commit the business state first, for example PENDING → PAID.

Publish an OrderUpdated event.

Use the outbox pattern when reliable event delivery is required.

Invalidate or update cache.

Delete order:{id} and related orders:user:{id}:* keys, or update them from the event.

Use short TTL as a safety net.

If an invalidation event is missed, the cache should still repair itself later.

Read-your-writes: immediately after a user pays, it is often better to return the new order state from the write response instead of reading a possibly stale cache again.

6.8 Inventory: cache can help reads, but final stock must be controlled

Inventory has high contention (tranh chấp). A cached value such as stock=7 can become wrong immediately after another user buys an item.

Use caseCan cache be used?Recommended behavior
Product page shows “In stock”YesUse short-lived or event-updated cache. Treat it as an availability hint.
Search result filters out sold-out itemsYesEventual consistency is usually acceptable.
User adds item to cartYes for a soft checkTell the user availability may change before checkout.
Checkout reserves 2 unitsNot with a normal stale cacheUse authoritative atomic DB update, serialized worker, or a carefully designed atomic inventory service.
Flash sale uses Redis atomic counterPossibleRedis becomes part of the inventory authority. Define durability, replication, idempotency, recovery, reconciliation, and DB synchronization.
Unsafe: GET inventory from cache → see 1 item → create order → later update DB. Under concurrency, many users can read the same cached value and oversell.

6.9 Cache invalidation strategies

Cache invalidation (làm mất hiệu lực dữ liệu cache) is the rule that removes or refreshes old data.

TTL expiration

Simple safety limit. Every key expires after a period.

  • Easy to operate.
  • Data can be stale until TTL ends.
  • Same TTL on many keys can cause a large expiry wave.

Invalidate on write

After DB commit, delete the cache key. The next read loads fresh data.

  • Good with cache-aside.
  • Prefer delete over “update DB then separately update many cache views” when there are many derived keys.

Event-driven invalidation

Publish events such as ProductUpdated or PriceChanged. Cache consumers delete or refresh related keys.

  • Works across many services.
  • Needs reliable events and idempotent consumers.

Versioned cache keys

Change the version in the key when content changes.

product:123:v17 promotion:summer-sale:v4

Old keys can expire naturally without blocking the new version.

6.10 Peak event: one product gets millions of requests exactly when TTL expires

This is the classic cache stampede (nhiều request cùng cache miss rồi dồn xuống backend), also called thundering herd (đám đông request dồn cùng lúc) or, for one hot key, cache breakdown (cache của hot key hết hạn gây quá tải).

Naive TTL failure: product key expires at 20:00:00 → one million requests see MISS → one million requests query the database → DB connection pool fills → latency grows → retries create more traffic → the whole service can collapse.

Safe hot-key refresh flow

Let one worker refresh while other users still receive a safe cached value.

Anti-stampede
Prewarm before the promotion.

Load known hot products, prices, promotion rules, and public page fragments into CDN and Redis before traffic starts.

Use soft TTL + hard TTL.

After soft TTL, data should be refreshed, but it can still be served for a short safe period until hard TTL. This avoids an empty cache window.

Allow only one refresh owner.

Use request coalescing / singleflight (gộp nhiều request miss thành một lần tải) or a short distributed lock. One request loads the DB; others do not.

Serve stale-while-revalidate.

For product title, image, description, or other safe fields, return the previous cached value while refresh runs.

Add TTL jitter.

Do not let thousands of related keys expire at the exact same second. Add a small random difference to each TTL.

Refresh hot keys early.

Refresh-ahead or probabilistic early refresh updates very popular keys before normal expiry.

Keep a fallback.

If DB refresh fails, continue to serve safe stale content for a limited period and protect the DB with circuit breakers and rate limits.

Example key state for a hot product value: product:123 soft_expire_at: 20:00:00 hard_expire_at: 20:05:00 20:00:01 request A: soft TTL expired acquire refresh lock load DB update cache with TTL + random jitter 20:00:01 requests B ... 1,000,000: do NOT call DB return old safe value, or wait a very short bounded time 20:00:02: new value is available for all requests

6.12 Negative caching and cache penetration

If a client repeatedly requests product:does-not-exist, a normal cache miss causes the database to be queried every time. Store a short “not found” result.

GET product:999999 MISS → DB: not found SET product:999999 = NOT_FOUND TTL 30s Next requests: cache returns NOT_FOUND database is protected

Use a short TTL because the object may be created later. For very large known ID sets, a Bloom filter (cấu trúc kiểm tra phần tử có khả năng tồn tại) can reject many impossible keys before they reach the database.

6.13 Cache key and TTL design

Good key structure

product:123:v17 price:sku-ABC:v8 cart:user-456 order:789 orders:user-456:page-1

Keys should be easy to understand, version, expire, and monitor.

Do not use one global TTL

Choose TTL from business risk and update frequency.

  • Images: hours/days with versioned URL
  • Product core: minutes/hours
  • Price/promotion: shorter + invalidation
  • Inventory hint: seconds or event-driven
  • Order status: short + event update

Add TTL jitter

base_ttl = 3600 jitter = random(0, 300) ttl = base_ttl + jitter

This spreads expiration times and reduces synchronized cache misses.

Do not cache huge objects blindly

Large values increase network cost, memory pressure, serialization time, and eviction. Cache the fields or computed view that the read path really needs.

6.14 Practical reference architecture for the e-commerce example

Product page:

Browser → CDN → Product API → L1 → Redis → Product DB. Product core has long TTL. Price/promotion use separate keys and events.

Shopping cart:

User-specific request → Cart API → Redis working store or DB + Redis cache. Use atomic operations and a long user-session TTL.

Order read:

Order API → short Redis cache → Order DB/read replica. Order write commits to DB first, then invalidates or updates cache through events.

Inventory display:

Product page can use cached availability hints. This path may be slightly stale.

Inventory reservation:

Bypass normal stale cache. Use atomic DB logic, queue/worker ownership, or a deliberately authoritative atomic inventory service.

Peak promotion:

Prewarm hot data, keep CDN edge cache active, use soft/hard TTL, singleflight refresh, TTL jitter, and protect all fallback paths with rate limits.

6.15 Quick decision guide

“Data is public, read-heavy, and changes rarely?”
→ CDN + long cache

Product content, images, static assets.

“Data is read-heavy but changes sometimes?”
→ Cache-Aside + TTL + invalidation

Product details, category, price, promotion.

“Data is user-specific and changes often?”
→ Redis working store or short cache

Shopping cart, session, temporary user state.

“Data is a durable business record?”
→ DB truth + cache reads

Order, payment, refund.

“Wrong stale value can oversell or lose money?”
→ Revalidate authoritative state

Inventory reservation, payment amount, coupon usage limits.

“One hot key may receive millions of reads?”
→ CDN + SWR + singleflight + prewarm

Never allow all expired-cache requests to fall through to the DB.

Design rule: a cache is a performance tool, not a permission to ignore correctness. Decide for every cached field: How stale may it be? Who is the source of truth? How is it invalidated? What happens on cache miss? What happens if the cache is down?

7. Technical vocabulary

Useful words that appear often in software design discussions.

Cache — fast temporary or near-compute storage used to avoid repeated expensive work. Bộ nhớ đệm.
Cache hit — requested data is found in cache. Cache có dữ liệu cần tìm.
Cache miss — requested data is not found in cache. Cache không có dữ liệu cần tìm.
TTL (Time To Live) — how long a cache entry can stay valid before expiration. Thời gian tồn tại của cache.
Eviction — removing cache entries, often because memory is full. Loại dữ liệu khỏi cache.
Cache invalidation — removing or marking old cached data as no longer valid. Làm mất hiệu lực dữ liệu cache.
Cache-Aside — the application checks cache, loads the database on miss, then fills the cache. Ứng dụng tự quản lý đọc/ghi cache.
Write-Through — update cache and durable storage before the write is reported as successful. Ghi qua cache đến nguồn dữ liệu.
Write-Behind — write to cache first and persist to durable storage later. Ghi cache trước, đồng bộ DB sau.
Refresh-Ahead — refresh popular cache data before normal expiration. Làm mới cache trước khi hết hạn.
Stale-While-Revalidate — serve an older safe value while a fresh value is loaded in the background. Trả dữ liệu cũ trong lúc làm mới.
Singleflight / Request coalescing — combine many identical cache misses into one backend request. Gộp nhiều cache miss thành một lần tải.
TTL jitter — add small random differences to expiration times. Làm lệch ngẫu nhiên thời gian hết hạn.
Cache stampede — many requests miss the same cache entry and hit the backend together. Nhiều request cache miss dồn xuống backend.
Cache avalanche — many cache keys expire in the same period and overload the backend. Nhiều key cache hết hạn cùng lúc.
Cache penetration — requests for missing data repeatedly pass through cache to the database. Request dữ liệu không tồn tại xuyên qua cache.
Negative caching — temporarily cache a “not found” result. Cache kết quả không tồn tại.
Concurrency — many operations happening at the same time. Xử lý đồng thời.
Contention — many operations competing for the same resource. Tranh chấp tài nguyên.
Race condition — wrong behavior caused by timing between concurrent operations. Điều kiện tranh chấp.
Atomic operation — an operation that acts as one indivisible change. Thao tác nguyên tử.
Transaction — a group of database changes that succeed or fail together. Giao dịch cơ sở dữ liệu.
Isolation — rules that control how concurrent transactions can see each other. Mức cô lập giao dịch.
Lock — a database mechanism that protects data during an operation. Khóa dữ liệu.
Optimistic locking — detect a conflict when writing and retry if needed. Khóa lạc quan.
Pessimistic locking — lock data before changing it. Khóa bi quan.
Reservation — a temporary hold on stock. Giữ chỗ tồn kho.
Idempotency — repeating the same request does not create a new side effect. Tính bất biến khi retry.
Backpressure — slowing or limiting new work when downstream systems are full. Kiểm soát áp lực ngược.
Load shedding — rejecting lower-value or excess work to protect the system. Loại bớt tải.
Hot key / hot row — one data key receiving much more traffic than others. Khóa / dòng dữ liệu nóng.
Partition — split data or work into smaller independent groups. Phân vùng.
Shard — one independent part of a horizontally split database. Mảnh cơ sở dữ liệu.
Read replica — a database copy mainly used for reads. Bản sao đọc.
Replication lag — delay before a replica receives the latest change. Độ trễ sao chép.
Saga — several local transactions with compensation when a later step fails. Chuỗi giao dịch cục bộ có bước bù.
Transactional Outbox — store an event with the database transaction, then publish it later. Mẫu outbox giao dịch.
Reconciliation — compare systems and repair inconsistent results. Đối soát và sửa lệch dữ liệu.
Thundering herd — many clients hit the same resource at once. Hiện tượng lượng lớn request dồn cùng lúc.
Architecture — overall system structure. Kiến trúc.
Component — a main part of a system. Thành phần.
Module — a separated part of code or functionality. Mô-đun.
Dependency — when one part needs another part. Sự phụ thuộc.
Interaction — communication between parts. Sự tương tác.
Sequence — order of actions or messages. Trình tự.
Workflow — a series of work steps. Quy trình công việc.
Branch — one possible path after a decision. Nhánh xử lý.
State — current condition or status of an object. Trạng thái.
Transition — movement from one state to another. Chuyển trạng thái.
Entity — a main data object, such as User or Order. Thực thể.
Relationship — connection between data entities. Mối quan hệ.
Schema — formal structure of a database. Lược đồ.
Data lineage — history of where data comes from and where it goes. Dòng nguồn gốc dữ liệu.
Deployment — putting software into an environment where it can run. Triển khai.
Infrastructure — servers, networks, cloud resources, and related technology. Hạ tầng.
Runtime — the environment while software is running. Môi trường chạy.
Event — a fact that something happened, such as OrderCreated. Sự kiện.
Publish / Consume — send an event / receive and process an event. Phát / nhận sự kiện.
Message broker — software that moves messages between services. Bộ trung gian thông điệp.
Authentication — proving who a user is. Xác thực.
Authorization — checking what a user can do. Phân quyền.
Trust boundary — a line between areas with different security trust levels. Ranh giới tin cậy.
Threat model — a model of possible security risks and attacks. Mô hình mối đe dọa.
