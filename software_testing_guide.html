Software Testing: Practical Guide

A practical guide to the main software testing types, including concepts, how to perform them, common tools, and how to apply them in a real project. The English uses simple vocabulary for easy interview and daily work use.

Overview Test Levels Functional Testing Unit Test Integration API Test E2E Regression Performance Security UAT Smoke Sanity Monkey Exploratory Compatibility Usability Recovery Automation Real Project Interview

1. What is Software Testing?

Software testing is the process of checking whether software works as expected and finding problems before or after release.

Main goals

  • Find bugs before users find them.
  • Check that the system meets business requirements.
  • Make sure old functions still work after new changes.
  • Check performance, security, reliability, and user experience.
  • Reduce production risk.
Important: Testing is not only "checking if the code works". A good testing strategy checks the system from different levels and different risks.

2. Big Picture

Requirement→ Test Plan→ Unit Test→ Integration Test→ API / E2E→ Performance / Security→ UAT→ Release

Different tests answer different questions:

QuestionUseful test
Does this small method work?Unit Test
Do several components work together?Integration Test
Does the API return the correct result?API Test
Can a user complete a business flow?End-to-End Test
Does the system meet the business requirement?Functional / UAT
Does the system handle high traffic?Performance Test
Is the system protected against common attacks?Security Test
Did a new change break old functions?Regression Test

3. Test Levels

There are four common levels in a software project.

LevelPurposeExampleTypical tools
UnitTest one small unit of code.Test a Java service method.JUnit, Mockito
IntegrationTest real communication between components.Service + PostgreSQL.Spring Boot Test, Testcontainers
System / E2ETest a complete user flow.Login → Buy → Pay → Order.Playwright, Cypress, Selenium
AcceptanceCheck business acceptance.Customer accepts a promotion flow.Manual test, Cucumber, UAT
A practical project normally uses all levels. The lower tests are usually faster, while higher-level tests give more confidence about the complete system.

4. Functional Testing

What the system does

Functional testing checks whether a function behaves according to the requirement. It focuses on business behavior rather than internal code structure.

Example

Requirement: "A customer gets 20% discount when the promotion is active."

  • Promotion is active → discount is 20%.
  • Promotion is expired → no discount.
  • Customer is not eligible → no discount.
  • Product is excluded → no discount.

How to perform it

  1. Read the requirement.
  2. Identify normal cases and edge cases.
  3. Create test scenarios and test cases.
  4. Prepare test data.
  5. Execute tests manually or with automation.
  6. Compare actual result with expected result.
  7. Report defects with steps, logs, and evidence.

Tools

Jira, TestRail, Xray, Zephyr, Postman, Playwright, Cypress, Selenium.

5. Unit Testing (UT)

Smallest test level

A unit test checks one small piece of code, normally one method or class, without depending on external systems.

Example: Java + JUnit

public BigDecimal calculateDiscount(BigDecimal price, int percent) {
    return price.multiply(
        BigDecimal.valueOf(100 - percent)
    ).divide(BigDecimal.valueOf(100));
}

@Test
void shouldCalculate20PercentDiscount() {
    var result = service.calculateDiscount(
        new BigDecimal("100"), 20
    );

    assertEquals(new BigDecimal("80.00"), result);
}

What should be tested?

  • Normal input.
  • Boundary values.
  • Invalid input.
  • Exception cases.
  • Business rules.

Tools

  • Java: JUnit 5, Mockito, AssertJ.
  • JavaScript / TypeScript: Jest, Vitest.
  • C#: xUnit, NUnit, Moq.
  • Python: pytest.
Do not make every unit test depend on a real database. Use mocks or test doubles for external dependencies when the goal is to test only the unit's logic.

Real project example

For a Spring Boot Promotion Service, unit tests can cover: PromotionService.calculateDiscount(), PromotionService.validatePromotion(), and PromotionService.isEligible().

6. Integration Testing

Components working together

Integration testing checks whether two or more components work correctly together. Unlike a pure unit test, it normally uses real infrastructure or a close test version.

Example

Promotion Service→ PostgreSQL→ Redis

Test cases can verify:

  • Data is correctly saved to PostgreSQL.
  • Data can be read back correctly.
  • Redis cache is updated correctly.
  • Transaction rollback works when an error occurs.

Useful tools

  • Spring Boot Test.
  • Testcontainers for PostgreSQL, Redis, Kafka, etc.
  • WireMock for external HTTP services.
  • Embedded Kafka or Testcontainers Kafka for event testing.

Example architecture

@Test
void shouldCreatePromotionAndSaveToDatabase() {
    // Call application service
    // Verify HTTP/API behavior
    // Check real test PostgreSQL
    // Verify saved data
}
Integration tests are slower than unit tests, but they give stronger confidence that the application works with real infrastructure.

7. API Testing

API testing checks REST, GraphQL, or other service APIs without using the full UI. It is very useful for backend and microservice projects.

Example

POST /api/promotions

Request:
{
  "name": "Summer Sale",
  "discount": 20
}

Expected:
HTTP 201 Created

Response:
{
  "promotionId": "P10001",
  "status": "ACTIVE"
}

What should be checked?

  • HTTP status code.
  • Response body.
  • Headers.
  • Authentication and authorization.
  • Validation errors.
  • Database side effects.
  • Response time.
  • Idempotency where required.

Tools

Postman, Newman, REST Assured, Karate, Swagger/OpenAPI.

Real project

For a microservice project, API tests are useful for checking: POST /orders, GET /orders/{id}, POST /payments, and error cases such as 400, 401, 403, 404, and 500.

8. End-to-End (E2E) Testing

E2E testing checks a complete business flow from the user's point of view. It may include frontend, backend, database, and external services.

Example: E-commerce

Login→ Search Product→ Add Cart→ Checkout→ Payment→ Order Created

Tools

Playwright, Cypress, Selenium.

When to use it

  • Important business flows.
  • Critical customer journeys.
  • Release smoke testing.
  • Regression testing for key UI flows.
Do not create thousands of E2E tests for every small rule. They are usually slower and more fragile. Put detailed business-rule tests at the unit/API level.

9. Regression Testing

Regression testing checks that existing functions still work after a change.

Example

A developer changes the payment calculation. The team should not only test the new payment logic. They should also check order creation, refund, invoice, notification, and other affected functions.

Typical process

  1. Identify the changed area.
  2. Identify related functions.
  3. Run focused regression tests.
  4. Run the full regression suite when needed.
  5. Review failures and decide whether they are bugs or expected changes.

Regression testing is a major reason why automated tests are valuable in CI/CD.

10. Performance Testing

Performance testing checks how the system behaves under different traffic and data loads.

TypeMeaningExample
Load TestExpected normal traffic.1,000 requests/sec.
Stress TestPush beyond normal capacity.10,000 requests/sec.
Spike TestSudden traffic increase.100 → 10,000 users in seconds.
Soak TestLong running load.2,000 users for 6 hours.

Example: Promotion Event

Imagine 1 million users open the same promotion at 12:00. A good performance test should check:

  • API response time.
  • CPU and memory.
  • Database connection pool.
  • Redis hit rate.
  • Kafka lag if events are used.
  • Error rate.
  • System recovery after traffic goes down.

Tools

JMeter, Gatling, k6, Locust.

Important metrics

  • Average latency.
  • P95 / P99 latency.
  • Requests per second (RPS).
  • Error rate.
  • CPU / memory.
  • Database query time.

11. Security Testing

Security testing checks whether the application protects data and prevents common attacks.

Common areas

  • Authentication.
  • Authorization.
  • SQL Injection.
  • XSS.
  • CSRF where relevant.
  • Broken access control.
  • Weak passwords and session handling.
  • Sensitive data exposure.
  • Dependency vulnerabilities.

Example

User A must not be able to call GET /orders/USER_B_ORDER and read User B's order. This is an authorization test, not only a normal functional test.

Tools

OWASP ZAP, Burp Suite, Snyk, Dependabot, SonarQube, Trivy.

12. UAT - User Acceptance Testing

UAT is performed to confirm that the product meets real business needs. It is usually done by business users, customers, product owners, or representatives.

Example

For a payment system, the business may verify:

  • Merchant can create a payment.
  • Customer can pay successfully.
  • Payment failure is shown correctly.
  • Refund works according to business rules.
  • Reports contain correct information.
Developers should support UAT, but UAT is not the same as a developer's unit test. The business decides whether the delivered behavior is acceptable.

13. Smoke Testing

Basic build health check

Smoke testing is a quick test to check whether a new build is stable enough for more detailed testing. It answers a simple question: "Is the application basically working?"

Example

After deploying a new build to the test environment, check:

  • Application starts successfully.
  • Login works.
  • Main page can be opened.
  • Important API is reachable.
  • Database connection works.
  • A basic transaction can be completed.

When to use it

Run smoke tests after a new deployment or build. If smoke testing fails, the team normally does not continue with the full test suite until the build is fixed.

Tools

Postman/Newman, Playwright, Cypress, Selenium, automated CI/CD scripts.

Think of it as: "Does this build work well enough to test further?"

14. Sanity Testing

Focused change check

Sanity testing is a focused test after a small change or bug fix. It checks whether the specific changed area works correctly and whether the change did not create an obvious problem around it.

Smoke vs Sanity

Smoke TestingSanity Testing
Checks overall build health.Checks a specific changed area.
Usually broad but shallow.Narrow but deeper.
Often done after deployment/build.Often done after a bug fix or small change.
"Can we start testing?""Does this specific change work?"

Example

A developer fixes a bug where a promotion was not applied when the order value was exactly $100.

  • Test order = $100.
  • Test order slightly below $100.
  • Test order slightly above $100.
  • Check that the promotion still works for normal orders.

This is a sanity check. We do not need to run the entire system regression suite for this first verification.

Tools

Postman, JUnit, REST Assured, Playwright, Cypress, manual test cases.

15. Monkey Testing

Random / unexpected actions

Monkey testing means giving random or unexpected input and actions to the system without following a fixed business scenario. The goal is to find crashes, unexpected behavior, or stability problems.

Example

For a mobile or web application, a test may:

  • Click buttons very quickly.
  • Open and close screens repeatedly.
  • Enter random values.
  • Use very long text.
  • Press back and refresh at unexpected times.
  • Change network connection during an operation.
  • Send many unexpected requests.

Example in a payment system

Imagine a user clicks the "Pay" button 20 times very quickly. The system should not create 20 payments for the same order. This type of unexpected behavior can reveal an idempotency or concurrency problem.

Tools

Android Monkey, Appium, random test scripts, property-based testing tools, fuzzing tools, and custom automation scripts.

Monkey testing is useful for finding unexpected problems, but it does not replace normal functional and business-rule testing.

16. Exploratory Testing

Learn + test at the same time

Exploratory testing means learning about the system while testing it. The tester does not follow only a fixed test script. They use experience and observation to find unusual problems.

Example

A tester receives a new checkout feature. Instead of only following prepared test cases, the tester tries:

  • Different browsers.
  • Very slow network.
  • Empty fields.
  • Special characters.
  • Multiple browser tabs.
  • Refresh during payment.
  • Back button during checkout.

When it is useful

  • New features.
  • Complex UI.
  • Areas with many unknown risks.
  • When requirements are not fully clear.
  • Before creating a complete automation suite.

Tools

Browser DevTools, Postman, Charles Proxy, Burp Suite, device emulators, and normal application tools.

17. Compatibility Testing

Compatibility testing checks whether the application works correctly in different environments.

Examples

  • Chrome, Firefox, Safari, Edge.
  • Windows, macOS, Android, iOS.
  • Different screen sizes.
  • Different database versions.
  • Different Java or framework versions when supported.
  • Different network conditions.

Real project example

For an Angular Business Portal, test important screens on Chrome, Edge, and Safari, and check common desktop resolutions. For a mobile application, test supported iPhone and Android versions.

Tools

BrowserStack, Sauce Labs, Selenium Grid, real devices, emulators.

18. Usability Testing

Usability testing checks whether users can understand and use the product easily. It focuses on user experience rather than only technical correctness.

Example

A payment error message says: ERR_PAYMENT_PROCESSOR_5001. Technically it may be correct, but it is not a good user message. A better message may be: Payment could not be completed. Please try again.

What to check

  • Is the screen easy to understand?
  • Can users find the main action?
  • Are error messages clear?
  • Are forms easy to complete?
  • Does the UI give useful feedback?
  • Is the flow too complicated?

Tools

Manual user testing, Figma prototypes, session recording tools, accessibility checkers, and browser DevTools.

19. Recovery Testing

Recovery testing checks whether the system can recover correctly after a failure. It is important for production systems and distributed systems.

Examples

  • Database goes down and comes back.
  • Redis becomes unavailable.
  • Kafka becomes temporarily unavailable.
  • Network connection is lost.
  • A service crashes during a transaction.
  • A pod is restarted during high traffic.

Example

During payment, the Payment Service crashes. After it comes back, the system should not create a duplicate payment and should be able to continue or safely recover the transaction.

Tools

Chaos testing tools, Kubernetes, Docker, Toxiproxy, LitmusChaos, Gremlin, monitoring tools such as Grafana and Prometheus.

For Senior-level system design, recovery testing is very important because production failures are normal. The goal is not "nothing will fail"; the goal is "the system can fail safely and recover."

20. Test Automation

Test automation means using software to execute tests automatically instead of doing all checks manually.

Good candidates for automation

  • Tests that run often.
  • Stable business rules.
  • Regression tests.
  • API tests.
  • Large data sets.
  • Critical business flows.

Less suitable candidates

  • One-time tests.
  • Frequently changing UI.
  • Exploratory testing.
  • Tests that require human judgment.

Test Pyramid

              /\
             /  \
            / E2E \       Few
           /------\
          /  API   \      Some
         /----------\
        / Integration \   More
       /--------------\
      /   Unit Tests   \  Many
     /------------------\

A healthy test strategy normally has many fast unit tests, a good number of integration and API tests, and a smaller number of important E2E tests.

21. How to Apply Testing in a Real Project

Example Project: Payment / Promotion Microservice

Angular UI→ API Gateway→ Promotion Service→ PostgreSQL
Promotion Service→ Redis
Promotion Service→ Kafka→ Notification Service

Step 1 - Unit Tests

Test business rules without real infrastructure.

  • Calculate discount.
  • Check promotion date.
  • Check customer eligibility.
  • Validate request.
  • Handle invalid input.

Step 2 - Integration Tests

Use Testcontainers to run real PostgreSQL / Redis / Kafka containers.

  • Save promotion to DB.
  • Read promotion from DB.
  • Read/write cache.
  • Publish Kafka event.
  • Verify transaction behavior.

Step 3 - API Tests

Test the service through HTTP.

  • POST promotion.
  • GET promotion.
  • Update promotion.
  • Delete promotion.
  • Authentication and authorization.
  • Validation and error responses.

Step 4 - E2E Tests

Test the critical user journey:

  1. Merchant logs in.
  2. Merchant creates promotion.
  3. Customer places an order.
  4. Promotion is applied.
  5. Payment is completed.
  6. Order is created.

Step 5 - Performance Tests

Simulate a promotion event where traffic suddenly becomes very high. Check P95/P99 latency, error rate, DB load, Redis behavior, and Kafka lag.

Step 6 - Security Tests

Check that only authorized merchants can manage their own promotions and that customer information cannot be accessed by another customer.

Step 7 - UAT

Business users execute real business scenarios and confirm that the feature matches the requirement.

22. Testing in CI/CD

Tests should be connected to the delivery pipeline so that bad code is detected early.

Developer Push→ Build→ Unit Test→ Integration Test→ API Test→ Deploy→ E2E / Smoke

Example GitHub Actions strategy

StageTestReason
Pull RequestUnit + static analysisFast feedback.
BuildUnit + integrationVerify code and infrastructure interaction.
Test EnvironmentAPI + E2EVerify complete behavior.
Before ReleaseRegression + securityReduce release risk.
ScheduledPerformance / security scansCheck non-functional risks.
The key idea is: fail fast. Run cheap and fast tests first. Do not wait until the final stage to discover a simple bug.

Expected ResultFinal price = $80.
PriorityHigh

Important test case categories

  • Positive case - valid input.
  • Negative case - invalid input.
  • Boundary case - minimum / maximum value.
  • Exception case - dependency or system failure.
  • Security case - unauthorized access.
  • Performance case - high traffic or large data.

24. Senior Developer Testing Mindset

A Senior Developer should not think only about "Does my code work?" A stronger question is:

"What can go wrong in production, and how can I prove that my system handles it?"

Example: Redis cache expiration

Suppose product data is cached in Redis with a TTL. The TTL expires during a large promotion event.

A basic developer may test:

  • Cache hit.
  • Cache miss.

A stronger production-focused test strategy also checks:

  • Many requests miss the cache at the same time.
  • Database receives too many requests.
  • Cache stampede protection.
  • Request timeout.
  • Retry behavior.
  • Circuit breaker behavior.
  • Fallback behavior.
  • System recovery after DB becomes healthy.

Possible solutions include distributed locking, request coalescing, TTL jitter, cache warming, rate limiting, circuit breakers, and read replicas.

26. Senior Interview Answer

Question: "What types of testing do you use in your project?"

"In my project, I normally use several levels of testing. First, we use unit tests to test business logic at the code level. Then we use integration tests to check the connection between the application and infrastructure such as PostgreSQL, Redis, or Kafka. For APIs, we use API tests to verify request, response, validation, authentication, and error cases. We also have a small number of E2E tests for critical business flows.

For non-functional requirements, we use performance testing to check high traffic and response time, and security testing to find common security problems. Before release, we run regression tests and support UAT with the business team.

I prefer to run fast tests first in CI/CD and keep the test pyramid balanced: many unit tests, enough integration and API tests, and fewer E2E tests. This gives us good coverage without making the pipeline too slow."

27. Key Takeaways

  • Unit Test: Does this small piece of code work?
  • Integration Test: Do components work together?
  • Functional Test: Does the feature meet the requirement?
  • API Test: Does the service API behave correctly?
  • E2E Test: Can the user complete the full business flow?
  • Regression Test: Did the change break something old?
  • Performance Test: Can the system handle the expected load?
  • Security Test: Can the system protect itself and its data?
  • UAT: Does the business accept the product?
  • Smoke: Is the new build stable enough for more testing?
  • Sanity: Does the specific change or bug fix work correctly?
  • Monkey: Can unexpected actions cause crashes or bad behavior?
  • Exploratory: What problems can we find beyond the prepared test cases?
  • Compatibility: Does it work in supported environments?
  • Usability: Can users understand and use it easily?
  • Recovery: Can the system recover safely after failure?
Senior mindset: Choose the right test at the right level. Do not test everything with E2E tests. Put detailed logic in unit tests, system interaction in integration tests, API behavior in API tests, and only critical business journeys in E2E tests.
