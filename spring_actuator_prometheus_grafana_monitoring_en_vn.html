Monitoring Spring Boot Applications with Actuator, Prometheus, Grafana and JVM Production Troubleshooting

Learn how to expose application/JVM metrics, scrape them with Prometheus, visualize them in Grafana, create alerts, and investigate production issues such as JVM OutOfMemoryError, high latency, high error rate, CPU spike, thread deadlock and DB connection pool exhaustion.

ActuatorMicrometerPrometheusGrafanaPromQLAlertsJVMOOMHeap DumpThread DumpGCKubernetesProduction

1. Big Picture

Production monitoring answers four questions: Is the application alive? Is it healthy? Is it fast? Is it consuming resources normally?

Spring Boot App ↓ exposes metrics via Actuator + Micrometer /actuator/health /actuator/prometheus ↓ scraped by Prometheus ↓ queried by PromQL Grafana dashboards + Alerts ↓ notify team Slack / Email / PagerDuty / Ops channel ↓ troubleshoot logs + metrics + traces + heap dump + thread dump

Actuator

Exposes production-ready endpoints: health, metrics, prometheus, info, loggers, env, threaddump, heapdump.

Micrometer

Application metrics facade used by Spring Boot to publish metrics to monitoring systems.

Prometheus

Pull-based time-series database. It scrapes metrics endpoints and stores numeric time-series.

Grafana

Visualization and alerting UI. It queries Prometheus and builds dashboards/alerts.

Senior mindset: Monitoring is not only dashboards. Good production monitoring needs metrics, logs, traces, alert rules, runbooks, ownership, and incident response.

2. Spring Boot Actuator

What is Actuator?

Spring Boot Actuator provides production-ready endpoints to monitor and manage a Spring Boot application through HTTP or JMX.

EndpointPurposeProduction Notes
/actuator/healthApplication health status.Expose safely. Often used by load balancer/Kubernetes probes.
/actuator/infoApplication build/version info.Useful for release verification.
/actuator/metricsAvailable metric names and details.Usually internal only.
/actuator/prometheusPrometheus scrape format.Expose to Prometheus only, not public internet.
/actuator/loggersView/change log levels.Powerful; protect strictly.
/actuator/threaddumpThread dump.Sensitive; internal/admin only.
/actuator/heapdumpHeap dump.Very sensitive and large; avoid public exposure.
/actuator/envEnvironment/config properties.May expose secrets. Do not expose publicly.

Minimal Actuator dependency

Gradle

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-actuator'
}

Maven

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

Expose safe endpoints

management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus,metrics
  endpoint:
    health:
      show-details: when_authorized
      probes:
        enabled: true
Production warning: Do not expose all endpoints publicly using include: *. Endpoints like env, heapdump, threaddump, loggers can leak sensitive information or affect runtime behavior.

Liveness and Readiness

For Kubernetes, liveness tells whether the app should be restarted; readiness tells whether the app can receive traffic.

management:
  endpoint:
    health:
      probes:
        enabled: true
  health:
    livenessstate:
      enabled: true
    readinessstate:
      enabled: true
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 20
  periodSeconds: 10

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 60
  periodSeconds: 20

3. Micrometer Metrics

Spring Boot uses Micrometer as a vendor-neutral metrics facade. Micrometer can export metrics to Prometheus, Datadog, New Relic and other monitoring systems.

Important default metrics

MetricMeaningUseful for
jvm_memory_used_bytesJVM memory used by area/id.Heap/non-heap monitoring, OOM prevention.
jvm_memory_max_bytesMax memory available.Memory utilization ratio.
jvm_gc_pause_secondsGC pause time.GC pressure and latency impact.
jvm_threads_live_threadsLive thread count.Thread leak detection.
process_cpu_usageProcess CPU usage.CPU pressure.
system_cpu_usageSystem CPU usage.Node/container pressure.
http_server_requests_seconds_countHTTP request count.Traffic rate, error rate.
http_server_requests_seconds_sumTotal request duration.Average latency.
hikaricp_connections_activeActive DB connections.DB pool exhaustion.
hikaricp_connections_pendingThreads waiting for DB connections.DB bottleneck.

Custom metrics example

@Service
public class PaymentService {
    private final Counter paymentSuccessCounter;
    private final Timer paymentTimer;

    public PaymentService(MeterRegistry registry) {
        this.paymentSuccessCounter = Counter.builder("payment_success_total")
            .description("Total successful payments")
            .tag("provider", "psp")
            .register(registry);

        this.paymentTimer = Timer.builder("payment_duration")
            .description("Payment processing duration")
            .register(registry);
    }

    public void pay() {
        paymentTimer.record(() -> {
            // call external payment provider
            paymentSuccessCounter.increment();
        });
    }
}
Metric cardinality warning: Do not use high-cardinality tags such as userId, email, orderId, requestId. They create too many time-series and can overload Prometheus.

    port: 8081

5. Prometheus and PromQL

Prometheus model

Prometheus scrapes metrics endpoints, stores time-series, and lets you query them using PromQL.

Metric sample: http_server_requests_seconds_count{application="order-service",method="GET",uri="/api/orders",status="200"} 12045 metric name: http_server_requests_seconds_count labels: application, method, uri, status value: 12045

Useful PromQL for Spring Boot

GoalPromQL
Request ratesum(rate(http_server_requests_seconds_count{application="order-service"}[5m]))
Error rate percentagesum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) / sum(rate(http_server_requests_seconds_count[5m])) * 100
Average latencysum(rate(http_server_requests_seconds_sum[5m])) / sum(rate(http_server_requests_seconds_count[5m]))
P95 latencyhistogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket[5m])) by (le, uri))
Heap usage ratiosum(jvm_memory_used_bytes{area="heap"}) / sum(jvm_memory_max_bytes{area="heap"}) * 100
GC pause ratesum(rate(jvm_gc_pause_seconds_sum[5m]))
Live threadsjvm_threads_live_threads
Active DB connectionshikaricp_connections_active
Pending DB connectionshikaricp_connections_pending

Prometheus scrape target status

In Prometheus UI, go to Status → Targets. The target should be UP. If target is DOWN, check network, port, metrics path, security, DNS and firewall.

Dashboard design advice

  • Start with golden signals: traffic, errors, latency, saturation.
  • Add JVM memory, GC, threads and DB connection pool panels.
  • Use environment/application labels to filter dashboard.
  • Do not create too many panels with high-cardinality labels.
  • Dashboard should support incident debugging, not just look nice.

7. Alerting

Prometheus alert rules

# alerts.yml
groups:
  - name: spring-boot-app-alerts
    rules:
      - alert: ApplicationDown
        expr: up{job="order-service"} == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Order service is down"
          description: "Prometheus cannot scrape order-service for more than 1 minute."

      - alert: HighErrorRate
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
          /
          sum(rate(http_server_requests_seconds_count[5m])) * 100 > 5
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "High 5xx error rate"
          description: "5xx error rate is above 5% for 5 minutes."

      - alert: HighHeapUsage
        expr: |
          sum(jvm_memory_used_bytes{area="heap"})
          /
          sum(jvm_memory_max_bytes{area="heap"}) * 100 > 85
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "High JVM heap usage"
          description: "Heap usage is above 85% for 10 minutes."

      - alert: DbPoolExhaustion
        expr: hikaricp_connections_pending > 0
        for: 3m
        labels:
          severity: critical
        annotations:
          summary: "DB connection pool has pending connections"
          description: "Threads are waiting for DB connections. Check slow queries or pool size."

Load alert rules in Prometheus

# prometheus.yml
global:
  scrape_interval: 15s

rule_files:
  - /etc/prometheus/alerts.yml

scrape_configs:
  - job_name: 'order-service'
    metrics_path: '/actuator/prometheus'
    static_configs:
      - targets: ['host.docker.internal:8081']

Alerting best practices

  • Alert on user impact: high error rate, high latency, app down, DB pool exhaustion.
  • Avoid noisy alerts for short temporary spikes.
  • Use for: duration to reduce noise.
  • Every alert should have a runbook or clear next action.
  • Separate warning and critical severity.
  • Test alert rules before production.

8. How to Check Production Java Application

Production check flow

Incident / alert fired ↓ 1. Check dashboard: UP, traffic, errors, latency, CPU, memory, GC, DB pool ↓ 2. Check logs by traceId/requestId/time window ↓ 3. Check recent deployment/config changes ↓ 4. Check dependency health: DB, Redis, Kafka, external APIs ↓ 5. Check JVM: heap, GC, threads, deadlocks ↓ 6. Mitigate: rollback, scale, restart, disable feature flag, increase pool carefully ↓ 7. Root cause analysis and postmortem

9. JVM OutOfMemoryError Troubleshooting

Common OOM types

OOM TypeMeaningCommon Causes
Java heap spaceHeap cannot allocate object.Memory leak, loading too much data, large cache, large file in memory.
GC overhead limit exceededJVM spends too much time in GC with little memory reclaimed.Heap nearly full, memory leak, excessive object allocation.
MetaspaceClass metadata memory exhausted.Classloader leak, dynamic class generation.
Direct buffer memoryOff-heap direct buffer exhausted.Netty/NIO buffer leak, too much direct memory.
Unable to create new native threadOS cannot create more threads.Thread leak, too many pools, OS limit, memory limit.

Enable heap dump on OOM

java \
  -Xms512m \
  -Xmx1024m \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/var/log/order-service/heapdump.hprof \
  -XX:+ExitOnOutOfMemoryError \
  -jar app.jar

Enable GC logging

# Java 17+
-Xlog:gc*,safepoint:file=/var/log/order-service/gc.log:time,uptime,level,tags:filecount=5,filesize=20M

OOM investigation steps

  1. Check Grafana heap trend. Is heap increasing and never dropping after GC?
  2. Check GC pause and frequency. Is JVM doing constant full GC?
  3. Check recent deployment, traffic spike, batch job, new cache, new endpoint.
  4. Collect heap dump if safe.
  5. Analyze heap dump with Eclipse MAT / VisualVM / YourKit.
  6. Look for dominator tree, biggest retained objects, duplicate strings, large maps/lists/caches.
  7. Check thread dump for blocked threads or too many threads.
  8. Mitigate: rollback, scale out, reduce traffic, disable feature, increase memory only if root cause known.

Typical OOM root causes in Spring apps

  • Loading millions of DB rows into memory instead of paging/streaming.
  • Unbounded cache using HashMap/ConcurrentHashMap.
  • Reading large files fully into byte array/string.
  • Too many pending async tasks.
  • WebClient/Netty direct memory leak or large buffers.
  • ThreadLocal leak.
  • Hibernate session holding too many managed entities in persistence context.
  • Large response aggregation in memory.

Code examples: bad vs better

Bad: load all rows

List<Order> orders = orderRepository.findAll();
for (Order order : orders) {
    export(order);
}

Better: paging

PageRequest pageRequest = PageRequest.of(0, 1000);
Page<Order> page;

do {
    page = orderRepository.findAll(pageRequest);
    page.getContent().forEach(this::export);
    pageRequest = pageRequest.next();
} while (page.hasNext());

Bad: unbounded cache

private final Map<String, UserProfile> cache = new ConcurrentHashMap<>();

public UserProfile get(String userId) {
    return cache.computeIfAbsent(userId, this::loadProfile);
}

Better: bounded cache

Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(30))
    .recordStats()
    .build(userId -> loadProfile(userId));

10. Error, Latency, CPU, Thread and DB Pool Troubleshooting

High 5xx error rate

CheckHow
Which endpoint?Grafana panel grouped by uri, status.
Which exception?Application logs with timestamp/traceId.
Recent change?Deployment version, config, DB migration.
Dependency failure?DB/Redis/Kafka/external API dashboards and logs.

High latency

  • Check P95/P99 latency by endpoint.
  • Check DB query time and connection pool pending count.
  • Check external API timeout/retry behavior.
  • Check GC pauses and CPU saturation.
  • Check thread pool queue and blocking calls.
  • Use distributed tracing to identify slow span.

High CPU

# Find Java process and hot threads
jps -lv
top -Hp <pid>

# Convert native thread id to hex
printf "%x\n" <thread-id>

# Find thread in dump
jcmd <pid> Thread.print | grep -A 30 <hex-thread-id>

Common causes: tight loop, excessive JSON serialization, regex issue, high GC, crypto/compression, too many requests, logging too much.

Thread deadlock / blocked threads

jcmd <pid> Thread.print > /tmp/thread-dump.txt
# Look for BLOCKED, WAITING, deadlock section, same lock monitor.

DB connection pool exhaustion

Symptoms: high hikaricp_connections_active, hikaricp_connections_pending > 0, slow requests, timeout waiting for connection.

  • Check slow SQL and missing indexes.
  • Check transaction too long.
  • Check connection leak.
  • Check pool size relative to DB max connections.
  • Check if external calls are executed inside DB transaction.
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      connection-timeout: 30000
      leak-detection-threshold: 60000
Senior note: Increasing DB pool size is not always the solution. It can overload the database. First check slow queries, long transactions and connection leaks.

11. Interview Q&A — English

Q1. What is Spring Boot Actuator?

A: Actuator provides production-ready endpoints for monitoring and managing Spring Boot applications. It exposes health, metrics, info, Prometheus metrics, loggers, thread dump and heap dump endpoints. In production, only safe endpoints should be exposed and sensitive endpoints must be protected.

Q2. How do you monitor a Spring Boot app with Prometheus and Grafana?

A: Add actuator and micrometer-registry-prometheus dependencies, expose /actuator/prometheus, configure Prometheus to scrape that endpoint, add Prometheus as a Grafana data source, create dashboards for traffic, errors, latency, JVM memory, GC, threads and DB pool, then configure alerts for high error rate, high latency, app down and high heap usage.

Q3. What is Micrometer?

A: Micrometer is a vendor-neutral application metrics facade. Spring Boot uses it to collect and export metrics to systems such as Prometheus, Datadog or New Relic. It is similar in spirit to SLF4J, but for metrics/observability.

Q4. What metrics are important for Java production monitoring?

A: The most important metrics are request rate, error rate, latency percentiles, JVM heap/non-heap usage, GC pause time, CPU usage, live thread count, DB connection pool active/pending connections, and dependency metrics such as Redis/Kafka/external API latency.

Q5. How do you troubleshoot JVM OutOfMemoryError in production?

A: First check heap usage and GC trend in Grafana. Then check logs for OOM type. If safe, collect heap dump and thread dump. Analyze heap dump with MAT or VisualVM to find retained objects and leak suspects. Check recent deployments, large queries, unbounded caches, large file processing, ThreadLocal leaks, and Hibernate persistence context. Mitigate with rollback, scaling, traffic reduction or memory increase only after understanding the cause.

Q6. What is the difference between liveness and readiness?

A: Liveness tells the platform whether the app is alive or should be restarted. Readiness tells whether the app is ready to receive traffic. A temporary dependency issue should usually make readiness fail, not necessarily liveness, otherwise the app may restart unnecessarily.

Q7. How do you alert effectively?

A: Alert on user impact and actionable symptoms: app down, high 5xx rate, high latency, DB pool exhaustion, high heap usage for a sustained period. Use a for-duration to avoid noise, set severity levels, and attach runbooks or next actions.

Q8. What should not be exposed publicly in Actuator?

A: Endpoints such as env, heapdump, threaddump, loggers and config-related endpoints should not be publicly exposed because they may leak secrets, sensitive data or allow runtime behavior changes. Prometheus endpoint should be reachable only from the monitoring network.

18. Alerting

groups:
  - name: spring-boot-app-alerts
    rules:
      - alert: ApplicationDown
        expr: up{job="order-service"} == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Order service is down"

      - alert: HighErrorRate
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
          /
          sum(rate(http_server_requests_seconds_count[5m])) * 100 > 5
        for: 5m
        labels:
          severity: warning

      - alert: HighHeapUsage
        expr: |
          sum(jvm_memory_used_bytes{area="heap"})
          /
          sum(jvm_memory_max_bytes{area="heap"}) * 100 > 85
        for: 10m
        labels:
          severity: warning

      - alert: DbPoolExhaustion
        expr: hikaricp_connections_pending > 0
        for: 3m
        labels:
          severity: critical
  • Alert theo user impact: app down, 5xx cao, latency cao, DB pool pending, heap cao.
  • Dùng for: để tránh noise do spike ngắn.
  • Mỗi alert nên có runbook/next action.
  • Phân loại warning/critical.

20. JVM OutOfMemoryError Troubleshooting

OOM TypeÝ nghĩaNguyên nhân phổ biến
Java heap spaceHeap không allocate được object.Memory leak, load quá nhiều data, cache quá lớn, file lớn trong memory.
GC overhead limit exceededJVM tốn nhiều thời gian GC nhưng reclaim ít.Heap gần full, leak, allocation quá nhiều.
MetaspaceClass metadata hết memory.Classloader leak, dynamic class generation.
Direct buffer memoryOff-heap direct buffer hết.Netty/NIO buffer leak, direct memory quá nhiều.
Unable to create new native threadOS không tạo được thread mới.Thread leak, quá nhiều pools, OS limit, memory limit.

Enable heap dump khi OOM

java \
  -Xms512m \
  -Xmx1024m \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/var/log/order-service/heapdump.hprof \
  -XX:+ExitOnOutOfMemoryError \
  -jar app.jar

GC logging Java 17+

-Xlog:gc*,safepoint:file=/var/log/order-service/gc.log:time,uptime,level,tags:filecount=5,filesize=20M

Các bước điều tra OOM

  1. Check heap trend trên Grafana: heap có tăng mãi và không giảm sau GC không?
  2. Check GC pause/frequency: có full GC liên tục không?
  3. Check deployment gần nhất, traffic spike, batch job, cache mới, endpoint mới.
  4. Nếu an toàn, lấy heap dump và thread dump.
  5. Analyze heap dump bằng Eclipse MAT / VisualVM / YourKit.
  6. Xem dominator tree, retained objects lớn nhất, large Map/List/cache.
  7. Mitigate: rollback, scale out, giảm traffic, disable feature, tăng memory chỉ khi hiểu nguyên nhân.

Root causes thường gặp

  • Load hàng triệu rows vào memory thay vì paging/streaming.
  • Unbounded cache dùng HashMap/ConcurrentHashMap.
  • Read file lớn toàn bộ vào byte array/string.
  • Quá nhiều async tasks pending.
  • ThreadLocal leak.
  • Hibernate persistence context giữ quá nhiều managed entities.
  • Aggregate response quá lớn trong memory.

21. Errors / Latency / CPU / DB Pool

High 5xx error rate

  • Endpoint nào lỗi? Group by uri, status.
  • Exception gì? Check logs theo timestamp/traceId.
  • Có deploy/config/DB migration mới không?
  • Dependency nào fail? DB/Redis/Kafka/external API.

High latency

  • Check P95/P99 latency theo endpoint.
  • Check DB query time và Hikari pending connections.
  • Check external API timeout/retry.
  • Check GC pauses và CPU.
  • Check thread pool queue/blocking calls.
  • Dùng distributed tracing để tìm span chậm.

High CPU

jps -lv
top -Hp <pid>
printf "%x\n" <thread-id>
jcmd <pid> Thread.print | grep -A 30 <hex-thread-id>

DB pool exhaustion

Triệu chứng: hikaricp_connections_active cao, hikaricp_connections_pending > 0, request chậm, timeout đợi connection.

  • Check slow SQL và missing indexes.
  • Check transaction quá dài.
  • Check connection leak.
  • Check pool size so với DB max connections.
  • Không gọi external API lâu bên trong DB transaction.

22. Câu hỏi phỏng vấn — Vietnamese

Q1. Spring Boot Actuator là gì?

A: Actuator cung cấp production-ready endpoints để monitor và manage Spring Boot application như health, metrics, info, prometheus, loggers, threaddump, heapdump. Production chỉ nên expose endpoint an toàn và protect endpoint nhạy cảm.

Q2. Monitor Spring Boot bằng Prometheus/Grafana như thế nào?

A: Add actuator và micrometer-registry-prometheus, expose /actuator/prometheus, cấu hình Prometheus scrape endpoint này, add Prometheus datasource vào Grafana, tạo dashboard cho traffic, errors, latency, JVM memory, GC, threads, DB pool, sau đó tạo alerts cho app down, error rate cao, latency cao, heap cao.

Q3. Micrometer là gì?

A: Micrometer là vendor-neutral metrics facade. Spring Boot dùng Micrometer để collect/export metrics sang Prometheus, Datadog, New Relic... Có thể hiểu giống SLF4J nhưng cho metrics/observability.

Q4. Metrics quan trọng cho Java production?

A: Request rate, error rate, latency percentiles, JVM heap/non-heap, GC pause, CPU, live threads, DB connection pool active/pending, Redis/Kafka/external API latency/error.

Q5. Troubleshoot OutOfMemoryError thế nào?

A: Check heap/GC trend trên Grafana, check log OOM type, lấy heap dump/thread dump nếu an toàn, analyze bằng MAT/VisualVM để tìm retained objects/leak suspects, check recent deployment, large query, unbounded cache, large file, ThreadLocal leak, Hibernate persistence context. Mitigate bằng rollback/scale/disable feature/tăng memory sau khi hiểu nguyên nhân.

Q6. Liveness khác readiness?

A: Liveness cho platform biết app còn sống hay cần restart. Readiness cho biết app có sẵn sàng nhận traffic không. Dependency temporary issue thường nên làm readiness fail, không nhất thiết liveness fail, để tránh restart không cần thiết.

Q7. Alert thế nào cho hiệu quả?

A: Alert theo user impact và actionable symptoms: app down, 5xx cao, latency cao, DB pool exhaustion, heap cao kéo dài. Dùng for-duration để tránh noise, có severity và runbook/next action.

Q8. Endpoint Actuator nào không nên public?

A: env, heapdump, threaddump, loggers, config-related endpoints không nên public vì có thể leak secrets/sensitive data hoặc thay đổi runtime behavior. Prometheus endpoint chỉ nên cho monitoring network access.

Quick Senior Checklist

  • Expose only required Actuator endpoints.
  • Use Micrometer Prometheus registry.
  • Prometheus scrapes /actuator/prometheus.
  • Grafana queries Prometheus and visualizes golden signals.
  • Monitor traffic, errors, latency, saturation.
  • Monitor JVM heap, GC pause, threads, CPU.
  • Monitor DB pool active/pending connections.
  • Create actionable alerts with runbooks.
  • Enable heap dump on OOM and GC logs.
  • Use heap dump/thread dump carefully in production.
  • For incidents, check dashboard → logs → recent changes → dependencies → JVM.
