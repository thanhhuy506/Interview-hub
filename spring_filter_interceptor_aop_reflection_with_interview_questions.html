Spring request lifecycle - practical engineering guide

Filter vs Interceptor vs Spring AOP vs Java Reflection

Understand where each mechanism runs, what it can see, when to use it, and how a request moves from HTTP into Spring MVC and then through Spring proxies to the Service layer.

HTTP / Servlet layer

3. Servlet Filter

Use a Filter when the concern belongs to the whole HTTP request rather than a specific Controller method. In Spring Boot, OncePerRequestFilter is the common base class.

Best use cases

Request ID / correlation ID

HTTP access logging and total request timing

Security headers and CORS-related infrastructure

Authentication filters inside Spring Security

Request/response wrappers

@Component
public class RequestTimingFilter
        extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain chain)
            throws ServletException, IOException {

        long start = System.nanoTime();
        try {
            chain.doFilter(request, response);
        } finally {
            long ms = (System.nanoTime() - start) / 1_000_000;
            log.info("{} {} -> {} in {} ms",
                request.getMethod(),
                request.getRequestURI(),
                response.getStatus(),
                ms);
        }
    }
}

More Filter code examples

Case 1 - Request ID with MDCAttach one correlation ID to every log line in the request.
@Component
public class RequestIdFilter
        extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain chain)
            throws ServletException, IOException {

        String requestId = request.getHeader("X-Request-Id");
        if (requestId == null || requestId.isBlank()) {
            requestId = UUID.randomUUID().toString();
        }

        MDC.put("requestId", requestId);
        response.setHeader("X-Request-Id", requestId);

        try {
            chain.doFilter(request, response);
        } finally {
            MDC.remove("requestId");
        }
    }
}
Production value: easier tracing across Controller, Service and downstream logs.
Case 2 - Reject a request before MVCA Filter can stop processing before a Controller is selected.

Spring MVC layer

4. HandlerInterceptor

Use an Interceptor when you care about the selected Spring MVC handler. It can inspect HandlerMethod, which gives you the Controller class, method and annotations.

@Component
public class LoggingInterceptor
        implements HandlerInterceptor {

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler) {

        if (handler instanceof HandlerMethod hm) {
            log.info("Calling {}.{}",
                hm.getBeanType().getSimpleName(),
                hm.getMethod().getName());
        }
        return true;
    }

    @Override
    public void afterCompletion(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler,
            Exception ex) {
        log.info("MVC request completed");
    }
}

Lifecycle

preHandle()Before Controller invocation. Return false to stop the handler.
postHandle()After a normal Controller return and before view rendering is fully complete.
afterCompletion()After request completion. Good for cleanup and final timing.

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface InternalEndpoint {}

@Override
public boolean preHandle(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler) throws IOException {

    if (!(handler instanceof HandlerMethod hm)) {
        return true;
    }

    InternalEndpoint marker =
        hm.getMethodAnnotation(InternalEndpoint.class);

    if (marker != null && !isInternalNetwork(request)) {
        response.sendError(HttpServletResponse.SC_FORBIDDEN);
        return false;
    }

    return true;
}
For complex authorization, prefer Spring Security method or request authorization. This example shows the Interceptor capability.
Java runtime mechanism

5. Java Reflection - more than method.invoke()

Reflection allows Java code to discover structure at runtime instead of hard-coding every class and method at compile time. Frameworks use this heavily for metadata-driven behavior.

Class metadataClass, Method, Field
->
Inspectname, type, annotations
->
Decideframework behavior
->
Invoke / mapruntime action

Key difference from AOP: Reflection gives you runtime inspection and invocation primitives. AOP gives you automatic before/after/around behavior around selected Spring bean calls.

Reflection example 1 - inspect methods and annotations

Define runtime metadataA custom annotation survives into runtime because of RUNTIME retention.
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Auditable {
    String action();
}

public class PaymentService {

    @Auditable(action = "PAYMENT")
    public void pay() {
        System.out.println("pay");
    }
}
Discover annotation dynamicallyNo direct call to PaymentService.pay() is required to read the metadata.
Method method =
    PaymentService.class.getMethod("pay");

if (method.isAnnotationPresent(Auditable.class)) {
    Auditable annotation =
        method.getAnnotation(Auditable.class);

    System.out.println(annotation.action());
}

Reflection example 2 - create objects from constructors

Frameworks often need to create an object when they only know its class at runtime. This is one idea behind DI containers, serializers and plugin loaders.

Class<?> type = Class.forName(

Reflection example 3 - a tiny generic object-to-map serializer

This demonstrates why Reflection is useful for generic libraries: the same code can work with many classes without knowing their fields in advance.

public Map<String, Object> toMap(Object object)
        throws IllegalAccessException {

    Map<String, Object> result = new HashMap<>();

    for (Field field :
            object.getClass().getDeclaredFields()) {

        field.setAccessible(true);
        Object value = field.get(object);
        result.put(field.getName(), value);
    }

    return result;
}

What happens

1. Read the runtime class.

2. Discover all declared fields.

3. Read each value dynamically.

4. Build a generic representation.

Real serializers are much more complex: inheritance, records, access rules, cycles, modules, dates and custom adapters all matter.

Reflection example 4 - generic Map to POJO mapper

Populate fields dynamicallyThis is educational; production mapping libraries handle conversion and validation more safely.
public <T> T fromMap(
        Map<String, Object> values,
        Class<T> type) throws Exception {

    T object = type.getDeclaredConstructor().newInstance();

    for (Map.Entry<String, Object> entry : values.entrySet()) {
        try {
            Field field = type.getDeclaredField(entry.getKey());
            field.setAccessible(true);
            field.set(object, entry.getValue());
        } catch (NoSuchFieldException ignored) {
            // Ignore unknown properties in this demo.
        }
    }

    return object;
}

Reflection example 6 - mini dependency injection concept

Marker annotationA simplified field injection example.
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
public @interface Inject {}

public class OrderService {
    @Inject
    private PaymentService paymentService;
}
Container logicInspect fields, find @Inject, then assign dependencies.
public void inject(Object bean,
        Map<Class<?>, Object> registry) throws Exception {

    for (Field field : bean.getClass().getDeclaredFields()) {
        if (!field.isAnnotationPresent(Inject.class)) {
            continue;
        }

        Object dependency = registry.get(field.getType());
        field.setAccessible(true);
        field.set(bean, dependency);
    }
}

This is only a teaching example. Spring's real dependency injection supports scopes, proxies, qualifiers, constructors, lifecycle callbacks, circular dependency handling and much more.

AOP example 1 - execution time with a custom annotation

UsageOnly annotated methods are measured.
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface TrackExecutionTime {}

@Service
public class OrderService {

    @TrackExecutionTime
    public Order createOrder() {
        return processOrder();
    }
}
Aspect@Around gives access to before, after, result and exception paths.
@Aspect
@Component
public class TimingAspect {

    @Around("@annotation(TrackExecutionTime)")
    public Object measure(ProceedingJoinPoint jp)
            throws Throwable {

        long start = System.nanoTime();
        try {
            return jp.proceed();
        } finally {
            long ms = (System.nanoTime() - start) / 1_000_000;
            log.info("{} took {} ms",
                jp.getSignature().toShortString(), ms);
        }
    }
}

AOP example 2 - audit business actions

Business methodThe Service declares intent, not logging implementation.
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface AuditAction {
    String value();
}

@AuditAction("CANCEL_ORDER")
public void cancelOrder(Long orderId) {
    repository.cancel(orderId);
}
Audit aspectRecord success and failure centrally.
@Around("@annotation(auditAction)")
public Object audit(
        ProceedingJoinPoint jp,
        AuditAction auditAction) throws Throwable {

    try {
        Object result = jp.proceed();
        auditService.record(
            auditAction.value(), "SUCCESS"
        );
        return result;
    } catch (Throwable ex) {
        auditService.record(
            auditAction.value(), "FAILED"
        );
        throw ex;
    }
}
Do not blindly log full method arguments. They may contain passwords, tokens, personal data or large payloads.

AOP example 3 - custom method authorization

AnnotationExpress a policy close to the protected method.
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface RequireRole {
    String value();
}

@RequireRole("ADMIN")
public void deleteUser(Long userId) {
    repository.deleteById(userId);
}
Before adviceReject before business logic executes.
@Before("@annotation(requireRole)")
public void authorize(RequireRole requireRole) {

    String currentRole = securityContext.currentRole();

    if (!requireRole.value().equals(currentRole)) {
        throw new AccessDeniedException("Forbidden");
    }
}
In production, Spring Security method authorization such as @PreAuthorize is usually preferable to inventing a parallel security system.

AOP example 5 - retry wrapper

Educational @Around retryShows control of target invocation. In real systems prefer a mature resilience library where appropriate.
@Around("@annotation(RetryableOperation)")
public Object retry(ProceedingJoinPoint jp)
        throws Throwable {

    int maxAttempts = 3;
    Throwable last = null;

    for (int attempt = 1; attempt <= maxAttempts; attempt++) {
        try {
            return jp.proceed();
        } catch (TransientException ex) {
            last = ex;
            if (attempt == maxAttempts) {
                break;
            }
            Thread.sleep(100L * attempt);
        }
    }

    throw last;
}
Retries are safe only for operations designed to be retried. Consider idempotency, transaction boundaries, timeout budgets and backoff.

Senior interview notes

7. Common mistakes and design rules

Do not use Filter for Service logic

A Filter only knows the HTTP request/response boundary. If you need behavior around OrderService.createOrder(), AOP is the more natural layer.

Do not use Interceptor as a universal AOP replacement

An Interceptor only participates in Spring MVC requests. Scheduled jobs, message consumers and internal bean calls do not pass through it.

Do not use Reflection when a normal interface is enough

Reflection trades compile-time safety for runtime flexibility. Keep it mainly in generic infrastructure, framework and extension code.

Do not forget AOP proxy boundaries

Self-invocation, non-Spring-created objects and some method visibility/finality choices can prevent proxy advice from behaving as expected.

Logging caution: Filter, Interceptor and AOP can all accidentally leak secrets if they log full headers, tokens, passwords, request bodies or method arguments. Production logging should mask sensitive fields and control payload size.

Q1. How do you log before and after entering a Controller, besides Spring AOP?

Recommended answer: use a Spring MVC HandlerInterceptor. preHandle() runs before the selected Controller method. postHandle() runs after the Controller returns normally, and afterCompletion() runs when MVC request processing is complete. If I need logging around the entire HTTP request instead of specifically around Controller execution, I use a Servlet Filter or OncePerRequestFilter.

Controller logging with HandlerInterceptorBest when you need the exact Controller class and method.
@Component
public class ControllerLoggingInterceptor
        implements HandlerInterceptor {

    private static final String START_TIME = "startTime";

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler) {

        request.setAttribute(
            START_TIME,
            System.currentTimeMillis()
        );

        if (handler instanceof HandlerMethod hm) {
            log.info("Before Controller: {}.{}",
                hm.getBeanType().getSimpleName(),
                hm.getMethod().getName());
        }

        return true;
    }

    @Override
    public void postHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler,
            ModelAndView modelAndView) {

        if (handler instanceof HandlerMethod hm) {
            log.info("Controller returned normally: {}.{}",
                hm.getBeanType().getSimpleName(),
                hm.getMethod().getName());
        }
    }

    @Override
    public void afterCompletion(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler,
            Exception ex) {

        Long start = (Long) request.getAttribute(START_TIME);

        if (start != null) {
            long duration =
                System.currentTimeMillis() - start;

            log.info("MVC request completed: status={}, duration={}ms",
                response.getStatus(), duration);
        }

        if (ex != null) {
            log.error("Unhandled MVC exception", ex);
        }
    }
}
Register the InterceptorSelect which endpoint paths should be intercepted.
@Configuration
public class WebConfig implements WebMvcConfigurer {

    private final ControllerLoggingInterceptor interceptor;

    public WebConfig(
            ControllerLoggingInterceptor interceptor) {
        this.interceptor = interceptor;
    }

    @Override
    public void addInterceptors(
            InterceptorRegistry registry) {

        registry.addInterceptor(interceptor)
            .addPathPatterns("/api/**")
            .excludePathPatterns(
                "/api/health",
                "/api/login"
            );
    }
}
Why this is better than a Filter for Controller-specific logging: handler can be a HandlerMethod, so you can read the Controller class, Java method and its annotations.
Alternative: whole HTTP request logging with FilterUse this when Controller identity is not the main requirement.
@Component
public class HttpLoggingFilter
        extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain chain)
            throws ServletException, IOException {

        long start = System.currentTimeMillis();

        log.info("HTTP before: {} {}",
            request.getMethod(),
            request.getRequestURI());

        try {
            chain.doFilter(request, response);
        } finally {
            log.info("HTTP after: status={}, duration={}ms",
                response.getStatus(),
                System.currentTimeMillis() - start);
        }
    }
}

Interview detail: postHandle() is for a normal Controller return. For final timing/cleanup, prefer afterCompletion(). Also remember that an exception may be handled by Spring's exception resolvers, so the Exception ex argument is not a complete substitute for centralized exception logging.

Recommended answer: a Filter belongs to the Servlet layer and wraps the HTTP request before it enters Spring MVC. An Interceptor can enforce Controller-aware rules, but it should not be treated as a replacement for the core Spring Security filter chain.

10. 30-second interview summary

Filter works at the Servlet level and is ideal for HTTP-wide concerns such as authentication, CORS, headers, request IDs and access logging. HandlerInterceptor works inside Spring MVC after Spring has resolved the handler, so it can identify the exact Controller class and method. Spring AOP works around Spring bean method calls through proxies, so it is suitable for transactions, auditing, timing, caching and other cross-cutting concerns. Java Reflection is different: it is a runtime mechanism for inspecting and invoking classes, methods, fields, constructors and annotations dynamically.

Rule of thumb: Filter = HTTP request | Interceptor = Controller | AOP = Spring bean method | Reflection = runtime inspection.
