1. Mental model: what does propagation answer?

English

Propagation answers one core question:

“When this method is called, should it join the current transaction, create a new one, create a savepoint, or run without a transaction?”

Tiếng Việt

Propagation trả lời một câu hỏi cốt lõi:

“Khi method này được gọi, nó sẽ join transaction hiện tại, tạo transaction mới, tạo savepoint hay chạy không transaction?”

REQUIRED = dùng chung · NESTED = dùng chung + savepoint · REQUIRES_NEW = transaction riêng

2. Default propagation in Spring

English

The default propagation of @Transactional is Propagation.REQUIRED.

Tiếng Việt

Propagation mặc định của @Transactional là Propagation.REQUIRED.

@Transactional
public void process() {
    ...
}

// Conceptually:
@Transactional(propagation = Propagation.REQUIRED)
public void process() {
    ...
}
If a transaction already exists, REQUIRED joins it. If none exists, Spring creates one.Nếu đã có transaction, REQUIRED join vào đó. Nếu chưa có, Spring tạo transaction mới.

3. REQUIRED — same transaction

@Service
public class OrderService {

    private final PaymentService paymentService;
    private final OrderRepository orderRepository;
    private final AuditRepository auditRepository;

        orderRepository.save(new Order("ORDER-001", "CREATED"));

        // B
        paymentService.processPayment();

        // C
        auditRepository.save(new Audit("ORDER-001", "DONE"));
    }
}

@Service
public class PaymentService {

    @Transactional // REQUIRED
    public void processPayment() {
        paymentRepository.save(new Payment("ORDER-001", 100_000L));

Although there are two @Transactional annotations, there is still normally only one physical transaction: T1.

4. REQUIRED + try/catch — why A and C can still be rolled back

English

This is one of the most important Spring Transaction traps.

Many developers look at the Java code below and think:

A succeeds
B fails
catch B exception
C still runs
=> A and C should commit

But that conclusion can be wrong when B uses Propagation.REQUIRED.

Tiếng Việt

Đây là một trong những trap quan trọng nhất của Spring Transaction.

Nhiều developer nhìn đoạn code dưới đây và nghĩ:

A thành công
B fail
catch exception của B
C vẫn chạy
=> A và C sẽ commit

Nhưng kết luận đó có thể sai nếu B dùng Propagation.REQUIRED.

4.1 Code that looks safe but is not

@Service
public class OrderService {

    private final PaymentService paymentService;
    private final OrderRepository orderRepository;
    private final AuditRepository auditRepository;

    @Transactional
    public void processOrder() {

        // A
        orderRepository.save(
            new Order("ORDER-002", "CREATED")
        );

        try {
            // B
            paymentService.processPayment();
        } catch (Exception e) {
            // Developer thinks:
            // "I caught B's exception, so T1 is fine."
            log.warn("Payment failed, continue flow", e);
        }

        // C
        auditRepository.save(
            new Audit("ORDER-002", "DONE")
        );
    }
}
@Service
public class PaymentService {

    @Transactional // REQUIRED by default
    public void processPayment() {

        paymentRepository.save(
            new Payment("ORDER-002", 100_000L)
        );

        throw new RuntimeException("Payment failed");
    }
}

4.2 The key point: B is NOT a separate transaction

English

Because processPayment() also uses REQUIRED, it joins the already existing transaction T1.

So A, B and C are all working inside the same physical transaction.

Tiếng Việt

Vì processPayment() cũng dùng REQUIRED, nó join vào transaction T1 đang tồn tại.

Do đó A, B và C thực chất đều chạy trong cùng một physical transaction.

4.3 What the Spring proxy/interceptor does when B throws RuntimeException

English

The important part is not only that B throws an exception. The important part is that the exception crosses B's transactional proxy boundary.

Spring's transaction interceptor sees that B ended with a rollback-causing exception. But B does not own an independent physical transaction; it is participating in T1.

Therefore the shared transaction can be marked:

rollbackOnly = true
Tiếng Việt

Điểm quan trọng không chỉ là B throw exception. Quan trọng là exception đi ra khỏi transactional proxy boundary của B.

Transaction interceptor của Spring thấy B kết thúc bằng một exception thuộc rollback rule. Nhưng B không có physical transaction riêng; B đang tham gia T1.

Vì vậy transaction dùng chung có thể bị mark:

4.4 Then why does the outer catch still work?

English

Because there are two separate concerns:

1. Java control flow
The outer try/catch catches the exception, so Java continues to execute C.

2. Transaction state
The transaction may already be marked rollback-only by Spring.

Tiếng Việt

Vì có hai vấn đề hoàn toàn khác nhau:

1. Java control flow
try/catch phía ngoài bắt được exception nên Java vẫn chạy tiếp C.

2. Transaction state
Transaction có thể đã bị Spring mark rollback-only.

C executing successfully does NOT mean C will be committed. C chạy thành công KHÔNG có nghĩa là C sẽ được commit.

4.5 What happens when processOrder() returns?

English

After processOrder() returns normally, the outer transaction interceptor attempts to commit T1.

But it discovers that T1 has already been marked rollback-only.

So Spring cannot safely commit the transaction and rolls it back.

Tiếng Việt

Sau khi processOrder() return bình thường, transaction interceptor phía ngoài cố commit T1.

Nhưng lúc này nó phát hiện T1 đã bị mark rollback-only.

Spring không thể commit transaction đó nên rollback toàn bộ.

4.6 Why UnexpectedRollbackException appears

English

From the outer method's point of view, everything looked successful because the exception was caught and the method returned normally.

But Spring knows the transaction was already doomed. To avoid silently pretending that the commit succeeded, Spring can throw:

UnexpectedRollbackException
Tiếng Việt

Từ góc nhìn của outer method, mọi thứ trông có vẻ ổn vì exception đã được catch và method return bình thường.

Nhưng Spring biết transaction này đã bị đánh dấu phải rollback. Để tránh việc giả vờ rằng commit thành công, Spring có thể throw:

UnexpectedRollbackException
Interpretation: “Your code returned normally, but the transaction could not actually be committed because an inner participant had already marked it for rollback.” Hiểu đơn giản: “Code của bạn return bình thường, nhưng transaction thật sự không thể commit vì một inner participant đã đánh dấu nó phải rollback.”

4.8 The mental model you should remember

try/catch handles the exception, not the transaction.

REQUIRED means B joins T1.
B fails through its transactional proxy.
Spring may mark T1 rollback-only.
Outer catch lets Java continue.
C can execute.
Final commit still fails because T1 is already rollback-only. try/catch xử lý exception, không xử lý trạng thái transaction.

REQUIRED nghĩa là B join T1.
B fail khi đi qua transactional proxy của nó.
Spring có thể mark T1 rollback-only.
Outer catch làm Java chạy tiếp.
C vẫn có thể execute.
Nhưng commit cuối vẫn fail vì T1 đã rollback-only.

4.9 Expected result comparison

Scenario Scenario A B C
REQUIRED + B succeeds REQUIRED + B thành công ✅ Commit ✅ Commit ✅ Commit
REQUIRED + B fails, no catch REQUIRED + B fail, không catch ❌ Rollback ❌ Rollback — Not executed
REQUIRED + B fails, outer catches REQUIRED + B fail, outer catch ❌ Usually rollback with T1 ❌ Rollback ❌ May execute, but rollback at the end
This is exactly why “A stays, B rolls back, C continues” is not a normal REQUIRED use case. You need a different transaction boundary such as NESTED/savepoint or REQUIRES_NEW, depending on the business requirement. Đây chính là lý do “A giữ lại, B rollback, C tiếp tục” không phải case phù hợp với REQUIRED thông thường. Bạn cần transaction boundary khác như NESTED/savepoint hoặc REQUIRES_NEW tùy business requirement.

5. NESTED — “A stays, B rolls back, C continues”

English

NESTED is conceptually a savepoint inside the outer transaction.

Tiếng Việt

NESTED về mặt ý tưởng là một savepoint nằm trong outer transaction.

@Service
public class OrderService {

    private final PaymentService paymentService;

    @Transactional
    public void processOrder() {

        // A
        orderRepository.save(new Order("ORDER-003", "CREATED"));

        try {
            // B
            paymentService.processPaymentNested();
        } catch (Exception e) {
            log.warn("B failed, continue outer transaction", e);
        }

        // C
        auditRepository.save(new Audit("ORDER-003", "DONE"));
    }
}
@Service
public class PaymentService {

    @Transactional(propagation = Propagation.NESTED)
    public void processPaymentNested() {

        paymentRepository.save(
            new Payment("ORDER-003", 100_000L)
        );

        throw new RuntimeException("Payment failed");
    }
}

SAVEPOINT S1

B -> INSERT payment
B -> fails

ROLLBACK TO S1
|
+-- undo B only

catch

C -> INSERT audit

COMMIT T1

C ✅
NESTED is still part of T1. If T1 later rolls back, A and C also roll back.NESTED vẫn thuộc T1. Nếu T1 rollback về sau thì A và C cũng rollback.

6. REQUIRES_NEW — independent transaction T2

@Service
public class PaymentService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void processPaymentInNewTransaction() {

        paymentRepository.save(
            new Payment("ORDER-004", 100_000L)
        );

        throw new RuntimeException("Payment failed");
    }
}
@Transactional
public void processOrder() {

    // T1
    orderRepository.save(new Order("ORDER-004", "CREATED")); // A

    try {
        // suspend T1, create T2
        paymentService.processPaymentInNewTransaction(); // B
    } catch (Exception e) {
        log.warn("B failed in T2");
    }

    // resume T1
    auditRepository.save(new Audit("ORDER-004", "DONE")); // C
}

7. Plain JDBC SAVEPOINT — the mechanism directly

public void processWithSavepoint(DataSource dataSource) throws SQLException {

    try (Connection connection = dataSource.getConnection()) {

        connection.setAutoCommit(false);

        try {
            // A
            try (PreparedStatement ps = connection.prepareStatement(
                    "INSERT INTO orders(order_code, status) VALUES (?, ?)")) {
                ps.setString(1, "ORDER-006");
                ps.setString(2, "CREATED");
                ps.executeUpdate();
            }

            Savepoint beforeB = connection.setSavepoint("BEFORE_B");

            try {
                // B
                try (PreparedStatement ps = connection.prepareStatement(
                        "INSERT INTO payments(order_code, amount) VALUES (?, ?)")) {
                    ps.setString(1, "ORDER-006");
                    ps.setLong(2, 100_000L);
                    ps.executeUpdate();
                }

                throw new RuntimeException("B failed");

            } catch (Exception bError) {
                // rollback only B
                connection.rollback(beforeB);
            }

            // C
            try (PreparedStatement ps = connection.prepareStatement(
                    "INSERT INTO audit_log(order_code, message) VALUES (?, ?)")) {
                ps.setString(1, "ORDER-006");
                ps.setString(2, "DONE");
                ps.executeUpdate();
            }

            connection.commit(); // A + C

        } catch (Exception e) {
            connection.rollback(); // rollback everything
            throw e;
        }
    }
}

Result:

8. Spring Proxy trap — self invocation

Wrong / dangerous

@Service
public class OrderService {

    @Transactional
    public void processOrder() {
        saveOrder();

        this.processPayment(); // self invocation

        saveAudit();
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void processPayment() {
        // You expect T2 here
    }
}
Caller
  |
Spring Proxy
  |
processOrder()
  |
  +-- this.processPayment()
         |
         X bypasses proxy interception

Better

@Service
public class OrderService {

    private final PaymentService paymentService;

    @Transactional
    public void processOrder() {
        saveOrder();

        paymentService.processPayment(); // through another bean proxy

        saveAudit();
    }
}

@Service
public class PaymentService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void processPayment() {
        ...
    }
}
Transaction propagation is proxy-based in the common Spring setup. Same-class calls are a classic interview and production trap.Propagation thường dựa trên proxy trong Spring. Gọi method cùng class là lỗi kinh điển ở interview và production.

10. Spring Data JPA / Hibernate caveats

English

Do not assume NESTED always behaves like plain JDBC savepoints in every JPA setup. Support depends on the transaction manager and underlying resources.

For a JPA-heavy system, verify the actual transaction manager before relying on NESTED behavior.

Tiếng Việt

Không nên mặc định NESTED luôn hoạt động y hệt JDBC savepoint trong mọi cấu hình JPA. Support phụ thuộc transaction manager và resource phía dưới.

Với hệ thống dùng JPA nhiều, hãy kiểm tra transaction manager thật sự trước khi dựa vào NESTED.

If B truly needs an independent transaction boundary, REQUIRES_NEW is often clearer conceptually.Nếu B thật sự cần transaction boundary độc lập, REQUIRES_NEW thường dễ hiểu hơn về mặt kiến trúc.

11. Repository.save(), flush(), and commit are not the same

@Transactional
public void processOrder() {

    orderRepository.save(order);
    paymentRepository.save(payment);
    auditRepository.save(audit);
}
English

Three repository calls do not mean three transactions. They participate in the transaction defined by the service boundary.

save != commit. flush != commit. Flush synchronizes pending SQL to the DB, but the transaction can still roll back later.

Tiếng Việt

Ba repository call không có nghĩa là ba transaction. Chúng tham gia transaction do service boundary quyết định.

save != commit. flush != commit. Flush có thể đẩy SQL xuống DB nhưng transaction vẫn có thể rollback về sau.

Case B — Why not overuse REQUIRES_NEW?

English

The outer transaction may already hold one DB connection. The inner REQUIRES_NEW usually needs another connection. At high concurrency, this can pressure the connection pool and create lock interactions.

Tiếng Việt

Outer transaction có thể đang giữ một DB connection. Inner REQUIRES_NEW thường cần thêm connection khác. Khi concurrency cao, điều này có thể gây áp lực connection pool và lock interaction.

Case C — Service layer as transaction boundary

Default design principle: put transactions around a meaningful business use case, not around every repository call.Nguyên tắc thiết kế: đặt transaction quanh business use case có ý nghĩa, không phải quanh từng repository call.

13. Integration test idea

@SpringBootTest
class OrderServiceIntegrationTest {

    @Autowired OrderService orderService;
    @Autowired OrderRepository orderRepository;
    @Autowired PaymentRepository paymentRepository;
    @Autowired AuditRepository auditRepository;

    @Test
    void nested_should_keep_A_and_C_but_rollback_B() {

        orderService.processOrder();

        assertThat(
            orderRepository.findByOrderCode("ORDER-003")
        ).isPresent();

        assertThat(
            paymentRepository.findByOrderCode("ORDER-003")
        ).isEmpty();

        assertThat(
            auditRepository.findByOrderCode("ORDER-003")
        ).isPresent();
    }
}

17. Senior interview answer

English

Question: What is the default propagation in Spring, and how would you implement “A stays, B rolls back, C continues”?

Answer: The default propagation of @Transactional is REQUIRED. If a transaction already exists, the called method joins it; otherwise Spring starts a new one. Therefore, if A, B, and C all participate in the same REQUIRED transaction, a failure in B may mark the shared transaction rollback-only, so simply catching B's exception may not be enough.

If the requirement is partial rollback inside the same outer transaction, NESTED/savepoint is the conceptual match when the transaction manager supports it. If B must be independent from A and C, REQUIRES_NEW is more appropriate because it suspends T1 and creates a separate T2. I would also verify proxy boundaries, actual transaction manager support, connection-pool impact, and integration-test behavior before choosing.

Tiếng Việt

Câu hỏi: Propagation mặc định trong Spring là gì, và xử lý requirement “A giữ lại, B rollback, C tiếp tục” như thế nào?

Trả lời: Propagation mặc định của @Transactional là REQUIRED. Nếu đã có transaction thì method được gọi join vào transaction đó; nếu chưa có thì Spring tạo mới. Vì vậy nếu A, B, C cùng tham gia một REQUIRED transaction, lỗi ở B có thể mark transaction dùng chung thành rollback-only, nên chỉ catch exception của B chưa chắc đủ.

Nếu requirement là rollback một phần trong cùng outer transaction thì NESTED/savepoint là lựa chọn đúng về mặt ý tưởng khi transaction manager hỗ trợ. Nếu B phải độc lập với A và C thì REQUIRES_NEW phù hợp hơn vì nó suspend T1 và tạo T2 riêng. Ngoài ra cần kiểm tra proxy boundary, transaction manager thực tế, ảnh hưởng connection pool và integration test.

18. Senior-level traps & follow-up questions

Q1. Catch exception rồi tại sao vẫn rollback?

Because catch changes Java control flow, but it does not necessarily clear the transaction rollback-only state.

Vì catch chỉ thay đổi luồng Java, không nhất thiết xóa rollback-only.

Q2. REQUIRES_NEW có luôn tốt hơn NESTED không?

No. NESTED means partial rollback within one outer transaction. REQUIRES_NEW means an independent transaction.

Không. NESTED là rollback một phần trong outer transaction; REQUIRES_NEW là transaction độc lập.

Q3. REQUIRES_NEW có downside gì?

It may require another DB connection and create more transaction/locking pressure under concurrency.

Nó có thể cần thêm DB connection và tăng áp lực transaction/locking khi concurrency cao.

Q4. repository.save() có commit ngay không?

Normally no. Commit is controlled by the transaction boundary.

Thông thường không. Commit được quyết định bởi transaction boundary.

Q5. flush() có phải commit không?

No. Flush synchronizes pending changes, but the transaction may still roll back later.

Không. Flush đồng bộ pending changes, nhưng transaction vẫn có thể rollback.

Q6. Transaction nên đặt ở đâu?

Usually around a meaningful application/service use case that coordinates several repository/domain operations.

Thường nên đặt quanh một application/service use case có ý nghĩa, nơi điều phối nhiều repository/domain operation.

Q7. Nếu B cần gọi external API thì sao?

A DB transaction cannot roll back a remote API call. For cross-system consistency, consider idempotency, outbox, saga, compensation, retries, and event-driven patterns instead of relying only on local DB transactions.

DB transaction không thể rollback một external API call. Với consistency xuyên hệ thống, cần cân nhắc idempotency, outbox, saga, compensation, retry và event-driven thay vì chỉ dựa vào local DB transaction.

19.8 Senior Java interview — concise answer

English

The default propagation of Spring @Transactional is REQUIRED. If a caller already has a transaction, the callee joins it; otherwise Spring creates a new one. Because outer and inner REQUIRED scopes usually participate in the same physical transaction, an inner failure can mark the shared transaction rollback-only. Therefore simply catching the exception does not guarantee that A and C will commit.

If the requirement is to roll back only B but keep A and continue C, I need another transaction boundary. I can use savepoint/NESTED if the transaction manager supports it, or REQUIRES_NEW if B must run in a completely independent transaction.

Tiếng Việt

Default propagation của Spring @Transactional là REQUIRED. Nếu caller đã có transaction thì method được gọi join vào transaction đó; nếu chưa có thì Spring tạo transaction mới. Vì outer và inner REQUIRED thường cùng tham gia một physical transaction, failure ở inner scope có thể mark transaction dùng chung thành rollback-only. Do đó chỉ catch exception không đảm bảo A và C sẽ commit.

Nếu requirement là rollback riêng B nhưng giữ A và tiếp tục C, tôi cần transaction boundary khác. Có thể dùng savepoint/NESTED nếu transaction manager hỗ trợ, hoặc REQUIRES_NEW nếu B cần transaction hoàn toàn độc lập.
