SQL Live Coding Interview Handbook

A practical collection of common SQL interview problems with clear answers, expected output, step-by-step reasoning, alternative solutions, common mistakes, and production performance notes.

How to use this handbook

In a live coding interview, the interviewer is usually evaluating more than whether your final query works. They also evaluate how you think, how you clarify assumptions, and whether you understand correctness and performance.

1. Clarify

Ask what duplicate means, how ties should be handled, whether NULL values exist, and which SQL dialect is used.

2. Build incrementally

Start with a correct simple query, then improve it with window functions or indexes when needed.

3. Explain trade-offs

Explain why you use JOIN, EXISTS, GROUP BY, ROW_NUMBER, RANK, or a CTE.

Dialect note: Most queries use ANSI-style SQL and work with small changes in PostgreSQL, MySQL 8+, SQL Server, and Oracle. Some functions such as DATE_TRUNC, INTERVAL, and percentile functions vary by database.

1Find the second highest salary

Window FunctionRanking

Question

Return the second highest distinct salary from the employees table.

Recommended answer
SELECT salary
FROM (
    SELECT
        salary,
        DENSE_RANK() OVER (ORDER BY salary DESC) AS salary_rank
    FROM employees
) x
WHERE salary_rank = 2;

Why DENSE_RANK?

Suppose salaries are: 

10000
10000
9000
8000

The second highest distinct salary is 9000. DENSE_RANK() gives both 10000 rows rank 1, then 9000 rank 2.

Alternative

SELECT MAX(salary) AS second_highest_salary
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
Always clarify whether the interviewer means the second row or the second distinct salary.

2Find the highest-paid employee in each department

PartitionTie Handling

Answer preserving ties
SELECT employee_id, employee_name, department_id, salary
FROM (
    SELECT
        e.*,
        DENSE_RANK() OVER (
            PARTITION BY department_id
            ORDER BY salary DESC
        ) AS salary_rank
    FROM employees e
) x
WHERE salary_rank = 1;

Why not ROW_NUMBER?

ROW_NUMBER() returns only one employee when two employees have the same highest salary. DENSE_RANK() returns all tied employees.

Alternative using GROUP BY

SELECT e.*
FROM employees e
JOIN (
    SELECT department_id, MAX(salary) AS max_salary
    FROM employees
    GROUP BY department_id
) m
  ON m.department_id = e.department_id
 AND m.max_salary = e.salary;

3Find duplicate records

Assume an employee is considered duplicated when employee_name and department_id are the same.

SELECT
    employee_name,
    department_id,
    COUNT(*) AS duplicate_count
FROM employees
GROUP BY employee_name, department_id
HAVING COUNT(*) > 1;
Reasoning: GROUP BY creates one group for each business key. HAVING filters groups after aggregation.
Common mistake: using WHERE COUNT(*) > 1. Aggregate functions belong in HAVING, not WHERE.

4Delete duplicate rows while keeping one

PostgreSQL / SQL Server style
WITH ranked AS (
    SELECT
        employee_id,
        ROW_NUMBER() OVER (
            PARTITION BY employee_name, department_id
            ORDER BY employee_id
        ) AS rn
    FROM employees
)
DELETE FROM employees
WHERE employee_id IN (
    SELECT employee_id
    FROM ranked
    WHERE rn > 1
);

How it works

  1. Partition rows by the duplicate business key.
  2. Give the first row number 1.
  3. Delete rows numbered 2, 3, 4, ...
In production, first run the CTE as a SELECT and verify the rows before executing the DELETE.

5Find customers who have never placed an order

Preferred answer using NOT EXISTS
SELECT c.customer_id, c.customer_name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);

Alternative using LEFT JOIN

SELECT c.customer_id, c.customer_name
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;

Why NOT EXISTS is often a strong answer

It expresses the business intent directly: “return a customer for whom no matching order exists.” It also avoids common NULL problems associated with NOT IN.

6Find the best-selling product

Assume “best-selling” means highest total quantity sold.

SELECT
    p.product_id,
    p.product_name,
    SUM(oi.quantity) AS total_quantity
FROM order_items oi
JOIN products p
  ON p.product_id = oi.product_id
GROUP BY p.product_id, p.product_name
ORDER BY total_quantity DESC
FETCH FIRST 1 ROW ONLY;
PostgreSQL/MySQL commonly use LIMIT 1. SQL Server commonly uses TOP 1.

Interview clarification

Ask whether “best-selling” means highest quantity, highest revenue, or highest number of distinct orders. These are different metrics.

7Find the top 3 products by revenue in each category

WITH product_revenue AS (
    SELECT
        p.category_id,
        p.product_id,
        p.product_name,
        SUM(oi.quantity * oi.unit_price) AS revenue
    FROM order_items oi
    JOIN products p
      ON p.product_id = oi.product_id
    GROUP BY
        p.category_id,
        p.product_id,
        p.product_name
),
ranked AS (
    SELECT
        pr.*,
        DENSE_RANK() OVER (
            PARTITION BY category_id
            ORDER BY revenue DESC
        ) AS revenue_rank
    FROM product_revenue pr
)
SELECT *
FROM ranked
WHERE revenue_rank <= 3
ORDER BY category_id, revenue_rank;

Why this is a classic interview problem

It tests whether you understand the pattern: aggregate first → rank inside each group → filter the rank.

8Calculate monthly revenue

PostgreSQL
SELECT
    DATE_TRUNC('month', order_date) AS month,
    SUM(total_amount) AS revenue
FROM orders
WHERE status = 'COMPLETED'
GROUP BY DATE_TRUNC('month', order_date)
ORDER BY month;

Important details

  • Clarify which statuses count as revenue.
  • Clarify timezone if orders are stored in UTC.
  • Clarify whether refunds should reduce revenue.

9Find customers who purchased on consecutive days

WITH daily_orders AS (
    SELECT DISTINCT
        customer_id,
        CAST(order_date AS DATE) AS order_day
    FROM orders
),
with_previous AS (
    SELECT
        customer_id,
        order_day,
        LAG(order_day) OVER (
            PARTITION BY customer_id
            ORDER BY order_day
        ) AS previous_day
    FROM daily_orders
)
SELECT DISTINCT customer_id
FROM with_previous
WHERE order_day = previous_day + INTERVAL '1 day';

Why DISTINCT first?

A customer may create several orders on the same date. We want to compare distinct calendar days, not individual order rows.

10Calculate a running total

SELECT
    order_date,
    total_amount,
    SUM(total_amount) OVER (
        ORDER BY order_date, order_id
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_total
FROM orders
WHERE status = 'COMPLETED';

Key idea

A window aggregate calculates values across related rows without collapsing them into one row as GROUP BY does.

Add a deterministic tie-breaker such as order_id when multiple orders can share the same timestamp.

11Calculate each product's percentage of total revenue

WITH product_revenue AS (
    SELECT
        product_id,
        SUM(quantity * unit_price) AS revenue
    FROM order_items
    GROUP BY product_id
)
SELECT
    product_id,
    revenue,
    revenue * 100.0 / SUM(revenue) OVER () AS revenue_percentage
FROM product_revenue
ORDER BY revenue DESC;

Why 100.0?

In some databases, using an integer can produce integer division. A decimal literal makes the intent explicit.

12Find the Nth highest salary

For example, return the 4th highest distinct salary.

SELECT salary
FROM (
    SELECT
        salary,
        DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
    FROM employees
) x
WHERE rnk = 4;

For a dynamic N, pass N as a parameter rather than building SQL by string concatenation.

13Find employees earning above their department average

Window function solution
SELECT employee_id, employee_name, department_id, salary
FROM (
    SELECT
        e.*,
        AVG(salary) OVER (
            PARTITION BY department_id
        ) AS department_avg_salary
    FROM employees e
) x
WHERE salary > department_avg_salary;

Alternative

SELECT e.*
FROM employees e
JOIN (
    SELECT department_id, AVG(salary) AS avg_salary
    FROM employees
    GROUP BY department_id
) a
  ON a.department_id = e.department_id
WHERE e.salary > a.avg_salary;

14Return the latest order for each customer

SELECT *
FROM (
    SELECT
        o.*,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY order_date DESC, order_id DESC
        ) AS rn
    FROM orders o
) x
WHERE rn = 1;

Why ROW_NUMBER?

We want exactly one row per customer. The second ordering column makes the result deterministic when timestamps are equal.

15Find each customer's first and last order date

SELECT
    customer_id,
    MIN(order_date) AS first_order_date,
    MAX(order_date) AS last_order_date
FROM orders
GROUP BY customer_id;

Follow-up: return the full first-order row

SELECT *
FROM (
    SELECT
        o.*,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY order_date, order_id
        ) AS rn
    FROM orders o
) x
WHERE rn = 1;

16Calculate the number of days between consecutive orders

SELECT
    customer_id,
    order_id,
    order_date,
    LAG(order_date) OVER (
        PARTITION BY customer_id
        ORDER BY order_date, order_id
    ) AS previous_order_date,
    order_date
      - LAG(order_date) OVER (
            PARTITION BY customer_id
            ORDER BY order_date, order_id
        ) AS gap
FROM orders;

LAG() is the natural choice when a row needs information from the previous row in the same group.

17Find missing IDs in a sequence

Example existing IDs: 1, 2, 3, 5, 6, 9. Return missing values such as 4, 7, 8.

PostgreSQL example
SELECT gs AS missing_id
FROM generate_series(
    (SELECT MIN(order_id) FROM orders),
    (SELECT MAX(order_id) FROM orders)
) gs
LEFT JOIN orders o
  ON o.order_id = gs
WHERE o.order_id IS NULL;
In databases without generate_series, use a numbers table or recursive CTE.

18Use conditional aggregation to create a pivot-like report

Return completed, cancelled, and pending order counts per customer.

SELECT
    customer_id,
    SUM(CASE WHEN status = 'COMPLETED' THEN 1 ELSE 0 END) AS completed_orders,
    SUM(CASE WHEN status = 'CANCELLED' THEN 1 ELSE 0 END) AS cancelled_orders,
    SUM(CASE WHEN status = 'PENDING' THEN 1 ELSE 0 END) AS pending_orders
FROM orders
GROUP BY customer_id;

Interview concept

Conditional aggregation is often simpler and more portable than database-specific PIVOT syntax.

19Find customers who bought from every category

SELECT o.customer_id
FROM orders o
JOIN order_items oi
  ON oi.order_id = o.order_id
JOIN products p
  ON p.product_id = oi.product_id
GROUP BY o.customer_id
HAVING COUNT(DISTINCT p.category_id)
     = (SELECT COUNT(*) FROM categories);

What this tests

This is a form of relational division: finding entities related to all members of another set.

20Find the median salary

PostgreSQL / Oracle-style ordered-set aggregate
SELECT
    PERCENTILE_CONT(0.5)
    WITHIN GROUP (ORDER BY salary) AS median_salary
FROM employees;

Window-function fallback

WITH ranked AS (
    SELECT
        salary,
        ROW_NUMBER() OVER (ORDER BY salary) AS rn,
        COUNT(*) OVER () AS cnt
    FROM employees
)
SELECT AVG(salary) AS median_salary
FROM ranked
WHERE rn IN (
    (cnt + 1) / 2,
    (cnt + 2) / 2
);

21Find the longest consecutive activity streak

This is the classic gaps and islands problem.

PostgreSQL example
WITH days AS (
    SELECT DISTINCT
        customer_id,
        CAST(order_date AS DATE) AS activity_day
    FROM orders
),
grouped AS (
    SELECT
        customer_id,
        activity_day,
        activity_day
          - ROW_NUMBER() OVER (
                PARTITION BY customer_id
                ORDER BY activity_day
            ) * INTERVAL '1 day' AS grp
    FROM days
),
streaks AS (
    SELECT
        customer_id,
        MIN(activity_day) AS start_day,
        MAX(activity_day) AS end_day,
        COUNT(*) AS streak_length
    FROM grouped
    GROUP BY customer_id, grp
)
SELECT *
FROM streaks
ORDER BY streak_length DESC;

Why the trick works

For consecutive dates, both the date and row number increase by one. Subtracting the row-number offset creates the same grouping key for dates in the same streak.

22Sessionize user activity

Create a new session when the gap between events is more than 30 minutes.

WITH events AS (
    SELECT
        customer_id,
        order_date AS event_time,
        LAG(order_date) OVER (
            PARTITION BY customer_id
            ORDER BY order_date
        ) AS previous_time
    FROM orders
),
flags AS (
    SELECT
        *,
        CASE
            WHEN previous_time IS NULL
              OR event_time - previous_time > INTERVAL '30 minutes'
            THEN 1 ELSE 0
        END AS new_session
    FROM events
)
SELECT
    *,
    SUM(new_session) OVER (
        PARTITION BY customer_id
        ORDER BY event_time
        ROWS UNBOUNDED PRECEDING
    ) AS session_id
FROM flags;

23Calculate a 7-day moving average of daily revenue

WITH daily AS (
    SELECT
        CAST(order_date AS DATE) AS order_day,
        SUM(total_amount) AS daily_revenue
    FROM orders
    WHERE status = 'COMPLETED'
    GROUP BY CAST(order_date AS DATE)
)
SELECT
    order_day,
    daily_revenue,
    AVG(daily_revenue) OVER (
        ORDER BY order_day
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS revenue_7d_avg
FROM daily
ORDER BY order_day;
This calculates seven rows, not necessarily seven calendar days if some dates have no rows. For strict calendar-day logic, join to a calendar table first.

24Calculate next-day user retention

Suppose we treat a customer's first order date as the signup/activation date. Return the percentage of customers who also ordered on the following day. 

WITH first_day AS (
    SELECT
        customer_id,
        MIN(CAST(order_date AS DATE)) AS cohort_day
    FROM orders
    GROUP BY customer_id
),
returned AS (
    SELECT DISTINCT
        f.customer_id
    FROM first_day f
    JOIN orders o
      ON o.customer_id = f.customer_id
     AND CAST(o.order_date AS DATE)
         = f.cohort_day + INTERVAL '1 day'
)
SELECT
    100.0 * COUNT(r.customer_id)
    / COUNT(f.customer_id) AS next_day_retention_pct
FROM first_day f
LEFT JOIN returned r
  ON r.customer_id = f.customer_id;

25Detect overlapping time intervals

Assume bookings have start_time and end_time. Find pairs that overlap.

SELECT
    a.booking_id AS booking_a,
    b.booking_id AS booking_b
FROM bookings a
JOIN bookings b
  ON a.resource_id = b.resource_id
 AND a.booking_id < b.booking_id
 AND a.start_time < b.end_time
 AND b.start_time < a.end_time;

Core overlap rule

A overlaps B when:

A.start < B.end
AND
B.start < A.end

This form handles interval overlap more reliably than trying to enumerate many separate cases.

Common live-coding mistakes

1. Using WHERE instead of HAVING

-- Wrong
SELECT department_id, COUNT(*)
FROM employees
WHERE COUNT(*) > 5
GROUP BY department_id;

-- Correct
SELECT department_id, COUNT(*)
FROM employees
GROUP BY department_id
HAVING COUNT(*) > 5;

2. Using NOT IN with possible NULL values

-- Risky if subquery may return NULL
WHERE customer_id NOT IN (
    SELECT customer_id FROM orders
)

-- Safer
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
);

3. Choosing the wrong ranking function

FunctionTiesExample ranks for 100,100,90
ROW_NUMBERBreaks ties1, 2, 3
RANKSame rank, leaves gaps1, 1, 3
DENSE_RANKSame rank, no gaps1, 1, 2

4. Forgetting tie-breaking columns

If two orders share the same order_date, ORDER BY order_date DESC may not be deterministic. Add order_id DESC.

5. Multiplying rows accidentally with joins

A one-to-many join can duplicate parent rows. Before aggregating, understand the cardinality of every join.

6. Filtering a LEFT JOIN in WHERE

-- This can effectively turn the LEFT JOIN into INNER JOIN
SELECT *
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.customer_id
WHERE o.status = 'COMPLETED';

-- Keep unmatched customers:
SELECT *
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.customer_id
 AND o.status = 'COMPLETED';

Performance and indexing — what senior candidates should mention

1. Index join and filter columns

CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);

CREATE INDEX idx_order_items_product
ON order_items(product_id);

Index design depends on filter selectivity, sort order, query shape, write volume, and database engine.

2. Avoid functions on indexed columns when possible

-- Can make index use harder
WHERE DATE(order_date) = DATE '2026-08-26'

-- Usually friendlier to a range index
WHERE order_date >= TIMESTAMP '2026-08-26 00:00:00'
  AND order_date <  TIMESTAMP '2026-08-27 00:00:00';

3. Do not optimize before correctness

In an interview, first produce a correct query. Then discuss indexes, execution plan, large-table behavior, partitioning, and materialization if the interviewer asks about scale.

4. Read the execution plan

Look for:

  • Full table scans on large tables.
  • Bad row-estimation.
  • Large sorts.
  • Nested-loop joins over huge data sets.
  • Hash spills to disk.
  • Missing or unused indexes.
A senior-level answer often includes: “I would verify the query with EXPLAIN or EXPLAIN ANALYZE before deciding which optimization is actually needed.”
