SQL Query Performance: Indexing vs Partitioning

A practical, interview-ready guide to query tuning with WHERE, JOIN, ORDER BY and GROUP BY, B-tree indexes, low-cardinality columns, SARGable predicates, function-based indexes, partition pruning, composite index design, and production troubleshooting.

English guide • Key technical terms translated to Vietnamese

1. The Performance Mental Model

A fast query is usually a query that makes the database do less work.

Read fewer rows→ Read fewer pages→ Sort less data→ Join less data→ Return only what is needed

Most SQL performance problems come from one or more of these costs:

I/O

Disk / buffer reads

The database scans too many data pages. I/O = thao tác đọc/ghi dữ liệu.

CPU

Compute work

Sorting, hashing, expression evaluation, grouping, decompression, JSON parsing, etc.

WAIT

Concurrency waits

Locks, latches, network, connection pool, remote storage, and overloaded resources.

Senior mindset: Do not ask “Which index should I add?” first. Ask “Why is this query expensive?” Then verify with the execution plan, actual row counts, statistics, and I/O.

2. How to Improve SQL Query Performance — Practical Theory

The most common performance wins do not come from one magic keyword. They come from reducing the amount of data the database must read, join, sort, group, and return. Start with the access pattern and execution plan, then optimize the SQL clauses that create the most work.

The most-used techniques in real projects: make WHERE predicates SARGable, create indexes that match the actual access pattern, join on the correct keys with compatible data types, return only required columns, avoid unnecessary large sorts/aggregations, keep optimizer statistics healthy, and validate every change with the actual execution plan and I/O metrics.

2.2 Optimize WHERE: usually the first SQL-level win

The WHERE clause determines which rows survive. A good filter is not only logically correct; it should also allow the optimizer to use an efficient access path such as an index seek/range scan or partition pruning.

Rule A — Keep predicates SARGable

SARGable (điều kiện có thể dùng index để tìm kiếm hiệu quả) means the database can use the search argument directly against an index instead of transforming every stored value first.

Less efficient

SELECT id, total_amount
FROM orders
WHERE DATE(created_at) = DATE '2026-08-27';

The function may have to be evaluated for many rows, and a normal index on created_at may not be usable as a direct range search.

Usually better

SELECT id, total_amount
FROM orders
WHERE created_at >= TIMESTAMP '2026-08-27 00:00:00'
  AND created_at <  TIMESTAMP '2026-08-28 00:00:00';

This expresses the condition as an index-friendly range.

Rule B — Avoid implicit conversion on indexed/join columns

-- Risky when order_id is numeric
WHERE order_id = '10001'

-- Better: use the correct parameter/data type
WHERE order_id = 10001

An implicit conversion (chuyển kiểu ngầm định) can force the database to convert values, distort cardinality estimates, or make an index harder to use. The exact behavior is database-specific, but matching types is the safest design.

Rule C — Understand selectivity, not just “column has an index”

-- If 90% of orders are ACTIVE, this may still scan a lot of data
SELECT id
FROM orders
WHERE status = 'ACTIVE';

Selectivity (độ chọn lọc) describes how much the predicate reduces the data. An index is especially useful when the predicate returns a small fraction of the table. A low-cardinality value such as status can still be useful in a composite/filtered/partial index when the queried value is rare or when combined with more selective columns.

Rule D — Prefix search can use a B-tree more naturally than contains search

-- Commonly index-friendly
WHERE customer_name LIKE 'Nguyen%'

-- A normal B-tree usually cannot seek efficiently from the left edge
WHERE customer_name LIKE '%Nguyen%'

For contains/full-text search, consider database-specific full-text, trigram, inverted, or search-engine solutions rather than forcing a regular B-tree to solve the wrong problem.

Rule E — Be careful with large OR conditions

WHERE customer_id = :customerId
   OR merchant_id = :merchantId

Some optimizers can combine indexes efficiently; others may choose a broad scan depending on statistics and data distribution. For difficult cases, compare the plan with an equivalent UNION ALL strategy, while preventing duplicates if the branches can overlap. Do not rewrite mechanically—measure both forms.

Rule F — Filter by the partition key when partition pruning is part of the design

SELECT id, customer_id, total_amount
FROM orders
WHERE created_at >= :fromDate
  AND created_at <  :toDate
  AND customer_id = :customerId;

If orders is partitioned by created_at, the time predicate may eliminate most partitions. The remaining customer_id predicate can then use an index inside those partitions. This is the classic partition pruning + index combination.

2.3 Optimize SELECT: read and transfer only what you need

Avoid unnecessary wide reads

SELECT *
FROM orders
WHERE customer_id = :customerId;

Prefer explicit projection

SELECT id, status, total_amount, created_at
FROM orders
WHERE customer_id = :customerId;

Why this matters:

  • Fewer columns can mean fewer data pages and less network traffic.
  • Narrow rows reduce memory pressure during sorts, hashes, and joins.
  • A narrow projection may allow a covering/index-only scan (đọc đủ dữ liệu trực tiếp từ index), depending on the engine and visibility/storage rules.
  • SELECT * creates unnecessary coupling when table columns change.

2.4 Optimize JOIN: control row multiplication

A join becomes expensive when the database must repeatedly search a large table, when join keys are not indexed appropriately, or when the relationship unexpectedly multiplies rows.

Rule A — Join on real keys with compatible data types

SELECT o.id, o.total_amount, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= :fromDate;

customers.id is normally a primary/unique indexed key. An index on orders.customer_id is often useful for lookup/join patterns, referential operations, and queries starting from customers—but whether it is used for this exact query depends on row counts and the chosen join algorithm.

Rule B — Do not apply functions/casts to join keys unless intentionally indexed

-- Risky
JOIN users u
  ON LOWER(u.email) = LOWER(o.customer_email)

-- Better data model when possible
JOIN users u
  ON u.normalized_email = o.normalized_customer_email

Normalize values at write time when appropriate, or use a supported expression/function-based index. Recomputing expressions on both sides of a large join can increase CPU and block normal index access.

Rule C — Reduce rows before an expensive many-to-many-like join

-- Example: limit orders to the relevant time range before joining large detail data
SELECT o.id, SUM(oi.quantity * oi.unit_price) AS amount
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.created_at >= :fromDate
  AND o.created_at <  :toDate
GROUP BY o.id;

Modern optimizers often push safe filters down automatically, so written SQL order is not the same as execution order. The important point is to provide selective predicates and correct join relationships so the optimizer can keep the intermediate result set (tập dữ liệu trung gian) small.

Rule D — Detect accidental row explosion

-- Dangerous if the real relationship is missing a condition
FROM orders o
JOIN payments p ON p.customer_id = o.customer_id

If one customer has 100 orders and 20 payments, this can produce 2,000 joined rows for that customer. If the intended relationship is payment-to-order, join by p.order_id = o.id. Using DISTINCT later to hide duplicate rows is usually a design smell and adds another expensive operation.

Rule E — Understand the main join algorithms

Join typeUsually good forPerformance concern
Nested Loop (lặp lồng)Small outer result + fast indexed lookup on the inner side.Terrible if the outer side is unexpectedly huge and each row triggers expensive lookup work.
Hash Join (join bằng bảng băm)Large equality joins when scanning inputs is reasonable.Needs memory; a large hash table can spill to disk.
Merge Join (join trên dữ liệu có thứ tự)Large inputs already sorted/indexed by join keys.Sorting inputs can be expensive if order is not available.
Senior point: Do not force “index join” everywhere. If 40% of a 500M-row table is needed, a sequential scan + hash join can be more efficient than millions of random index lookups.

2.5 Optimize ORDER BY: avoid sorting millions of rows

ORDER BY can require a full sort. Sorting is CPU- and memory-intensive; when memory is insufficient, the engine can spill to disk (tràn dữ liệu tạm xuống disk).

Best case — Let an index produce rows in the required order

SELECT id, total_amount, created_at
FROM orders
WHERE customer_id = :customerId
ORDER BY created_at DESC
FETCH FIRST 20 ROWS ONLY;

A useful index pattern is often:

CREATE INDEX idx_orders_customer_created
ON orders (customer_id, created_at DESC);

The engine can seek to one customer and read the newest rows in index order, possibly stopping after 20 rows instead of sorting the customer's full history. Exact syntax and index direction behavior vary by engine.

Make ORDER BY deterministic for pagination

ORDER BY created_at DESC, id DESC

If multiple rows have the same created_at, adding a unique tie-breaker such as id makes page ordering stable.

Avoid deep OFFSET pagination for large result sets

-- Expensive at deep pages: engine may still process/skip many rows
ORDER BY created_at DESC, id DESC
OFFSET 500000 ROWS FETCH NEXT 20 ROWS ONLY;

-- Keyset/seek pagination
WHERE (created_at, id) < (:lastCreatedAt, :lastId)
ORDER BY created_at DESC, id DESC
FETCH FIRST 20 ROWS ONLY;

Keyset pagination (phân trang theo khóa/mốc cuối) scales much better for deep navigation when the access pattern fits it.

2.6 Optimize GROUP BY: aggregate the smallest useful dataset

GROUP BY may use sorting or hashing. Both get expensive when the input is huge or group cardinality is high.

Rule A — Use WHERE for row filtering before aggregation; use HAVING for aggregate filtering

SELECT customer_id, SUM(total_amount) AS revenue
FROM orders
WHERE created_at >= :fromDate
  AND created_at <  :toDate
GROUP BY customer_id
HAVING SUM(total_amount) > 10000;

WHERE removes source rows before grouping. HAVING filters groups after aggregate results exist. A non-aggregate condition that can safely be placed in WHERE should generally not wait until HAVING.

Rule B — Pre-aggregate before joining when it reduces data substantially

WITH order_totals AS (
  SELECT order_id,
         SUM(quantity * unit_price) AS item_total
  FROM order_items
  GROUP BY order_id
)
SELECT o.customer_id, SUM(t.item_total) AS revenue
FROM orders o
JOIN order_totals t ON t.order_id = o.id
WHERE o.created_at >= :fromDate
GROUP BY o.customer_id;

This can be beneficial when aggregation dramatically reduces the detail table before later operations. But CTE/materialization behavior differs by database and version, so inspect the actual plan rather than assuming the written form is faster.

Rule C — Indexes can help GROUP BY, but not always

An index whose leading order matches the grouping keys can sometimes support ordered/stream aggregation and reduce sorting. However, for large analytical scans, a hash aggregate over a sequential scan may still be cheaper. The correct plan depends on the amount of data, grouping cardinality, memory, and storage layout.

Rule D — Do not group wide expressions repeatedly if you can model them better

-- Repeated expression work
GROUP BY DATE(created_at), LOWER(country_code)

For frequent reporting dimensions, consider generated/normalized columns, expression indexes, summary tables, or materialized views where supported and justified.

2.7 Use DISTINCT carefully

SELECT DISTINCT c.id, c.name
FROM customers c
JOIN orders o ON o.customer_id = c.id;

DISTINCT often requires sorting or hashing. If your real requirement is “customers that have at least one order,” a semi-join form is clearer:

SELECT c.id, c.name
FROM customers c
WHERE EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.id
);

Modern optimizers may transform multiple equivalent forms to the same plan, so EXISTS is not universally “faster.” The key advantage here is semantic clarity: stop caring about duplicate matching rows when existence is all you need.

2.8 Should we use subqueries?

Yes. A subquery (truy vấn con) is not inherently slow. In many cases it is the clearest and most correct way to express the requirement, and modern optimizers can transform a subquery into a semi-join, anti-join, hash join, or another efficient execution strategy. The important question is not “subquery or JOIN?” but how much work does the chosen form cause the database to perform?

Senior rule: Use a subquery when it expresses the business condition clearly and produces an efficient plan. Avoid a subquery when it causes repeated work, prevents useful predicate pushdown, returns an unnecessarily large intermediate result, or hides a better set-based access pattern.

2.8.1 Good case — use EXISTS when you only need to know whether a related row exists

Suppose the requirement is: “Return customers who have at least one paid order.” You do not need the order rows themselves.

SELECT c.id, c.name
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
      AND o.status = 'PAID'
);

This expresses a semi-join (phép nối chỉ kiểm tra sự tồn tại). Conceptually, the database can stop searching for a customer after it finds the first matching order. A useful index may be:

orders(customer_id, status)

A less clear alternative is to join all matching orders and then remove duplicates:

SELECT DISTINCT c.id, c.name
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'PAID';

The second form can create many duplicate customer rows before DISTINCT removes them. Optimizers may still produce similar plans, but EXISTS communicates the intent better: I care about existence, not the number of matching child rows.

2.8.2 Good case — use NOT EXISTS for “find rows that have no matching child”

SELECT c.id, c.name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
);

This is an anti-join (phép nối tìm bản ghi không có bản ghi đối ứng). It is usually a clean way to express “customers who never ordered.”

Be careful with NOT IN: if the subquery can return NULL, SQL three-valued logic may produce unexpected results. NOT EXISTS is often safer for this business meaning.

2.8.3 IN vs EXISTS: do not memorize “EXISTS is always faster”

-- IN
SELECT *
FROM customers
WHERE id IN (
    SELECT customer_id
    FROM vip_customers
);

-- EXISTS
SELECT c.*
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM vip_customers v
    WHERE v.customer_id = c.id
);

Many database optimizers can transform both forms into a similar semi-join. Performance depends on table sizes, indexes, statistics, null semantics, correlation, and the optimizer. Use the form that expresses the requirement correctly, then verify the actual plan.

SituationUsually clearer choiceReason
Check whether at least one related row existsEXISTSDirectly expresses existence and avoids thinking about duplicate child rows.
Compare with a small literal/set resultINReadable and concise, for example status IN ('PAID','DONE').
Find rows that have no matchNOT EXISTSClear anti-join semantics and avoids NOT IN + NULL surprises.
Need columns from the related tableJOINYou actually need data from both relations, not only an existence check.

2.8.4 Dangerous case — correlated subquery executed for many outer rows

A correlated subquery (subquery phụ thuộc vào từng dòng của query bên ngoài) references columns from the outer query.

SELECT c.id,
       c.name,
       (SELECT MAX(o.created_at)
        FROM orders o
        WHERE o.customer_id = c.id) AS last_order_at
FROM customers c;

Conceptually, this can look like:

Read customer 1 → find MAX(order)
Read customer 2 → find MAX(order)
Read customer 3 → find MAX(order)
...
Read customer 5,000,000 → find MAX(order)

If the optimizer cannot decorrelate the subquery and there is no efficient index, this becomes millions of repeated lookups. With an index such as (customer_id, created_at DESC), each lookup may be cheap; without it, the pattern can be very expensive.

A set-based rewrite may be better when a large portion of customers is needed:

SELECT c.id,
       c.name,
       x.last_order_at
FROM customers c
LEFT JOIN (
    SELECT customer_id, MAX(created_at) AS last_order_at
    FROM orders
    GROUP BY customer_id
) x ON x.customer_id = c.id;

But this rewrite is not automatically faster. If you only request 20 customers and there is an excellent index, 20 targeted lookups may be cheaper than aggregating the entire orders table. Always compare the amount of work.

2.8.5 Scalar subqueries in the SELECT list: convenient, but watch repeated work

SELECT o.id,
       o.total_amount,
       (SELECT c.name
        FROM customers c
        WHERE c.id = o.customer_id) AS customer_name
FROM orders o
WHERE o.created_at >= :fromDate;

If the outer query returns a very large number of orders, this can conceptually create one customer lookup per order. A normal join is usually easier to reason about and gives the optimizer an obvious set relationship:

SELECT o.id,
       o.total_amount,
       c.name AS customer_name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= :fromDate;

Again, many optimizers can rewrite the scalar subquery, but in code review I would inspect the execution plan rather than assuming that rewrite always happens.

2.8.6 Derived-table subquery in FROM: useful when pre-aggregation significantly reduces rows

SELECT c.region,
       SUM(x.revenue) AS revenue
FROM customers c
JOIN (
    SELECT customer_id,
           SUM(total_amount) AS revenue
    FROM orders
    WHERE created_at >= :fromDate
      AND created_at <  :toDate
    GROUP BY customer_id
) x ON x.customer_id = c.id
GROUP BY c.region;

This can be useful because the detail orders rows are aggregated before the later join. If 100 million order rows become 2 million customer summaries, the following join may process far less data.

However, some optimizers can push filters and rearrange joins even if you write the SQL differently. The derived table is useful when it improves correctness/readability or encourages a desirable reduction in intermediate rows—not because “subquery is faster.”

2.8.7 CTE vs subquery: readability first, then verify materialization behavior

WITH customer_revenue AS (
    SELECT customer_id,
           SUM(total_amount) AS revenue
    FROM orders
    WHERE created_at >= :fromDate
    GROUP BY customer_id
)
SELECT c.id, c.name, r.revenue
FROM customers c
JOIN customer_revenue r ON r.customer_id = c.id;

A CTE (Common Table Expression / biểu thức bảng chung) often improves readability and makes complex queries easier to maintain. But do not assume it is automatically faster or slower than an inline subquery. Depending on the database and version, the optimizer may:

  • Inline it (gộp CTE vào query chính).
  • Materialize it (tạo kết quả trung gian rồi đọc lại).
  • Push predicates into it or keep it as an optimization boundary.

If the CTE is referenced multiple times, materialization may save repeated computation in some engines; in other cases it can create unnecessary I/O. Check the execution plan for your database/version.

2.8.8 Subquery and partition/index behavior

A subquery does not remove the need to think about indexes or partitions. Each query block still has its own access path.

SELECT *
FROM orders o
WHERE o.created_at >= '2026-08-01'
  AND o.created_at <  '2026-09-01'
  AND EXISTS (
      SELECT 1
      FROM payments p
      WHERE p.order_id = o.id
        AND p.status = 'SUCCESS'
  );

If orders is partitioned by created_at, the outer date predicate may enable partition pruning. The EXISTS lookup may then benefit from an index such as:

payments(order_id, status)

So one efficient plan can combine:

Partition pruning on orders→ Read August rows only→ Indexed EXISTS lookup on payments→ Return matching orders

2.8.10 Interview answer — “Should we use subqueries?”

Yes. I do not treat subqueries as inherently slow. I choose them when they clearly express the requirement, especially for existence checks, anti-joins, isolated aggregation, or readable query decomposition. What I watch for is repeated execution, especially correlated or scalar subqueries over a large outer result. I also check whether predicates can be pushed down, whether indexes support the correlation key, whether partition pruning still happens, and how many rows each query block processes. Modern optimizers can rewrite many subqueries into joins or semi-joins, so I compare actual execution plans rather than using a rule such as “JOIN is always faster.” If a correlated subquery performs millions of lookups, I may rewrite it as a set-based JOIN or pre-aggregation, but only after comparing the real I/O and row counts.

2.9 Keep statistics accurate

Statistics (thống kê phân bố dữ liệu) tell the optimizer how many rows it expects predicates and joins to produce. Bad estimates lead to bad plans.

Estimated rows: 100
Actual rows:    8,000,000

This gap can cause:

  • Nested-loop joins chosen where a hash join would be better.
  • Insufficient memory for sort/hash operations.
  • Indexes chosen for predicates that are actually not selective.
  • Wrong join order or access path.

Use the database's statistics maintenance mechanism (ANALYZE, auto statistics, update statistics, histogram features, etc.) according to the engine you use.

2.10 Design indexes for the query pattern, not one column at a time

SELECT id, total_amount, created_at
FROM orders
WHERE merchant_id = :merchantId
  AND status = :status
  AND created_at >= :fromDate
ORDER BY created_at DESC;

A candidate composite index could be:

(merchant_id, status, created_at DESC)

Why? Equality predicates can narrow the search first, then the time column supports the range and ordering. But index design depends on the complete workload: data distribution, optional filters, read/write ratio, existing indexes, and database-specific optimizer rules.

Do not over-index: every additional index consumes storage and must be maintained by INSERT, UPDATE, and DELETE. Remove redundant or unused indexes only after validating workload and operational requirements.

2.11 Use partitioning for data elimination and manageability—not as a replacement for indexing

orders partitioned by month on created_at

Query time range
      ↓
Partition pruning
      ↓
Only August partition remains
      ↓
Index(customer_id, created_at)
      ↓
Find a small customer subset

Partitioning is especially useful for very large time-series/history/fact tables, retention operations, bulk maintenance, and pruning. If a query still needs only a tiny subset inside the selected partition, an index may still be essential.

2.14 A reliable query-tuning workflow

  1. Capture the real SQL and real parameter pattern. Performance can differ dramatically by parameter value and data skew.
  2. Measure a baseline. Record latency, CPU, logical reads, rows returned, and concurrency conditions.
  3. Read the actual execution plan. Find the operators consuming the most time/I/O and compare estimated vs actual rows.
  4. Check WHERE. Is it selective? SARGable? Does it include the partition key when pruning is expected? Are data types compatible?
  5. Check indexes. Does an index match the combined predicate/order pattern? Is the optimizer reading far more rows than it returns?
  6. Check joins. Are relationships correct? Do intermediate row counts explode? Are nested-loop lookups repeated millions of times?
  7. Check ORDER BY/GROUP BY. Is a large sort/hash spilling to disk? Can the input be reduced first?
  8. Check projection and pagination. Remove unnecessary columns and avoid deep OFFSET where possible.
  9. Check statistics and data skew. Fix estimation problems before forcing plans.
  10. Re-test under realistic load. A query that is fast for one user can still fail under 5,000 concurrent requests.

2.15 Senior interview answer: “How do you improve a slow SQL query?”

I do not start by adding indexes blindly. First, I reproduce the slow query with representative parameters and inspect the actual execution plan, elapsed time, CPU, and logical reads. I compare estimated rows with actual rows to find cardinality-estimation problems. Then I check whether the WHERE predicates are selective and SARGable, whether functions or implicit casts prevent efficient index access, and whether partition pruning is happening when expected. Next I inspect the indexes against the complete access pattern, especially equality predicates, range predicates, join keys, and ORDER BY. I check joins for row explosion or repeated nested-loop lookups, and I check ORDER BY and GROUP BY for large sorts, hash aggregates, or disk spills. I remove unnecessary SELECT * columns and avoid deep OFFSET pagination. If estimates are wrong, I investigate statistics and data skew. Finally, I rerun the plan and measure again under realistic concurrency. If the workload itself is inappropriate for OLTP—such as repeated expensive analytics—I consider caching, read replicas, materialized summaries, a warehouse, or another specialized data store.

3. Execution Plan: Your First Diagnostic Tool

An execution plan shows how the optimizer decided to execute the SQL. Exact operator names differ by PostgreSQL, MySQL, SQL Server, and Oracle, but the principles are similar.

Good signals

  • Index seek/range scan for selective predicates
  • Partition pruning
  • Reasonable estimated vs actual rows
  • Small intermediate result sets
  • No large spill to disk

Warning signals

  • Full scan on a huge table
  • Millions of rows read to return 10 rows
  • Repeated key lookups
  • Large sort/hash memory spill
  • Implicit conversion on indexed columns
-- PostgreSQL example
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, customer_id, total_amount
FROM orders
WHERE customer_id = 1001
  AND created_at >= DATE '2026-08-01';

In production, be careful with execution options that actually run the statement, especially for UPDATE/DELETE statements.

4. Index Explained Deeply

An index is an additional data structure that helps the database locate rows faster than scanning every row.

The most common general-purpose index is a B-tree (cây cân bằng dùng để tìm kiếm theo thứ tự). Conceptually, it stores indexed key values in sorted order and points to rows or row locations.

CREATE INDEX idx_orders_customer_created
ON orders (customer_id, created_at);

For a query like:

SELECT id, total_amount
FROM orders
WHERE customer_id = 1001
  AND created_at >= '2026-08-01';

the database can navigate directly to the area of the index containing customer_id = 1001, then scan only the relevant created_at range.

Why indexes are not free

BenefitCost
Faster selective readsExtra disk/storage space
Faster JOIN lookupsINSERT/UPDATE/DELETE must maintain indexes
Can avoid sortingMore cache pressure / memory footprint
Can enforce uniquenessToo many indexes increase write latency
Important: An index does not automatically make a query faster. If a query returns a very large percentage of the table, a sequential/full scan can be cheaper.

5. When Should You Use an Index?

Indexes are most valuable when a column or column combination is frequently used to locate a small, selective subset of rows.

Good candidates

  • Columns frequently used in WHERE filters.
  • Foreign keys used in joins.
  • Columns used for uniqueness, such as email or external_id.
  • Columns frequently used in ORDER BY when the index order matches the query.
  • Columns used together often in a stable query pattern → composite index.
  • High-read, low-write tables where read latency matters more than write cost.

Bad or weak candidates

  • Columns rarely filtered or joined.
  • Very small tables where scanning is already cheap.
  • Columns updated extremely frequently unless the read benefit is strong.
  • Low-cardinality columns used alone and returning a large percentage of rows.
  • Redundant indexes that duplicate the same left-prefix pattern.

6. Low-Cardinality Columns: flag, status, type = 1/2/3/4

Cardinality (độ đa dạng giá trị) means how many distinct values exist in a column. A boolean flag has very low cardinality: usually only 2 distinct values.

Question: Is it useful to create an index on a flag or status column with only 2–4 values?
Answer: Sometimes, but not automatically. The key issue is not only the number of distinct values. The real question is: How many rows does this predicate return?

Case A — Usually not useful

Assume 10 million orders:

status = 'ACTIVE'   → 8,500,000 rows
status = 'CLOSED'   → 1,400,000 rows
status = 'ERROR'    →   100,000 rows

An index on status alone may not help much for ACTIVE because the database still needs to visit most of the table.

Case B — Can be useful because distribution is skewed

Data skew (phân bố dữ liệu lệch) matters. Even though status has only three values, ERROR is only 1% of rows. An index may be useful for queries filtering ERROR.

SELECT id, created_at
FROM orders
WHERE status = 'ERROR';

Case C — Partial / filtered index is often better

-- PostgreSQL partial index example
CREATE INDEX idx_orders_error_created
ON orders (created_at)
WHERE status = 'ERROR';

This keeps the index smaller because it contains only ERROR rows.

Case D — Low-cardinality column inside a composite index

CREATE INDEX idx_orders_tenant_status_created
ON orders (tenant_id, status, created_at);

This can be effective when tenant_id first reduces the search space strongly, then status and created_at narrow it further.

Interview-quality statement: “I would not reject an index only because the column has low cardinality. I would check selectivity, data distribution, query frequency, row width, clustering, and whether a partial/composite/bitmap index is more appropriate. On OLTP systems, a simple B-tree on a 50/50 boolean flag is often weak. On some analytical databases or Oracle, bitmap indexes can be effective for low-cardinality read-heavy workloads, but they are usually a poor fit for high-concurrency OLTP writes.”

7. What Happens When a Function Is Applied to an Indexed Column?

The critical concept is SARGable (điều kiện có thể tận dụng cấu trúc index để tìm kiếm). A predicate is SARGable when the optimizer can use the indexed value directly to locate a range of matching keys.

Non-SARGable example

CREATE INDEX idx_orders_created_at ON orders(created_at);

-- Often prevents normal B-tree range usage
SELECT *
FROM orders
WHERE DATE(created_at) = DATE '2026-08-27';

The function is applied to every candidate value, so the database may not be able to navigate directly to the indexed date range.

Better: rewrite as a range

SELECT *
FROM orders
WHERE created_at >= TIMESTAMP '2026-08-27 00:00:00'
  AND created_at <  TIMESTAMP '2026-08-28 00:00:00';

This usually allows a normal range scan on the index.

Other common non-SARGable patterns

-- Function
WHERE LOWER(email) = 'alice@example.com'

-- Arithmetic
WHERE amount * 1.1 > 1000

-- Leading wildcard
WHERE name LIKE '%smith'

-- Implicit type conversion can also block or reduce index use
WHERE numeric_id = '12345'

Solution: expression / function-based index

-- PostgreSQL expression index
CREATE INDEX idx_users_lower_email
ON users (LOWER(email));

SELECT *
FROM users
WHERE LOWER(email) = 'alice@example.com';
Nuance: “Function on indexed column = index is never used” is too absolute. A database can still use an expression/function-based index, generated column index, or optimizer transformation. The correct senior answer is: a function can make a normal index predicate non-SARGable unless the database has a matching expression index or can safely rewrite the predicate.

8. Composite Index, Leftmost Prefix & Covering

A composite index (index nhiều cột) contains multiple columns in a defined order.

CREATE INDEX idx_orders_customer_status_created
ON orders (customer_id, status, created_at);

Typical B-tree behavior

PredicateUsefulnessWhy
customer_id = ?GoodUses the leftmost indexed column.
customer_id = ? AND status = ?Very goodUses first two columns.
customer_id = ? AND status = ? AND created_at >= ?Excellent patternEquality columns first, then range column.
status = ?Often weak / cannot fully seekSkips leftmost customer_id.
created_at >= ?Often weakSkips earlier keys.

Column-order rule of thumb

Common OLTP pattern:

equality columns → range column → optional columns used for order/covering

But do not blindly sort columns by “highest cardinality first”. Column order should be based on the real predicate, join, sort, grouping, and selectivity pattern.

Covering index

A covering index (index chứa đủ dữ liệu để trả kết quả mà không cần đọc row chính) can satisfy a query from the index alone or mostly from it.

-- Syntax differs by database
CREATE INDEX idx_orders_customer_created_cover
ON orders (customer_id, created_at)
INCLUDE (status, total_amount);
Trade-off: Covering indexes reduce row lookups, but wider indexes cost more memory, storage, and write maintenance.

9. Partitioning Explained Deeply

Partitioning divides one logical table into multiple smaller physical/logical pieces based on a partition key.

Typical strategies:

Range partition

Example: partition by month on created_at. Best for time-series/history/retention.

List partition

Example: partition by region or business type.

Hash partition

Distribute rows more evenly across partitions using a hash of a key.

Example: monthly order partitions

orders
├── orders_2026_06
├── orders_2026_07
├── orders_2026_08
└── orders_2026_09

Query:

SELECT customer_id, total_amount
FROM orders
WHERE created_at >= '2026-08-01'
  AND created_at <  '2026-09-01';

If the database can infer the target partition, it performs partition pruning (loại bỏ các partition không liên quan) and reads only orders_2026_08.

Partitioning benefits

  • Skip irrelevant partitions when the query filters by partition key.
  • Make retention easier: drop/detach an old partition instead of deleting billions of rows.
  • Smaller indexes per partition can be easier to maintain.
  • Can improve maintenance, archiving, vacuuming, backups, loading, and data lifecycle operations depending on DB engine.
  • Can isolate very large datasets into more manageable pieces.

What partitioning does NOT automatically solve

  • It does not automatically make every query faster.
  • If you do not filter by the partition key, the database may scan many or all partitions.
  • It does not replace good indexes inside partitions.
  • Too many partitions can increase planning/metadata/maintenance overhead.
  • Poor partition-key choice can create hotspots or uneven distribution.

Short interview answer: “Indexing and partitioning solve different levels of the problem. Partitioning reduces the search domain by pruning partitions; indexing then locates the matching rows efficiently inside the remaining partition(s). In large OLTP/OLAP systems, we often use both.”

11. Do We Still Need Indexes on Partitioned Tables?

Question: If a table is already partitioned, do I still need indexes?
Usually yes, if queries need selective lookup inside the remaining partitions. Partition pruning only says which partitions to inspect. It does not necessarily tell the engine which exact rows inside the partition match.

Example

Table is partitioned monthly by created_at. A single monthly partition still contains 50 million orders.

SELECT id, total_amount
FROM orders
WHERE created_at >= '2026-08-01'
  AND created_at <  '2026-09-01'
  AND customer_id = 1001;

Partitioning can eliminate all months except August. An index inside the August partition such as (customer_id, created_at) can then find the customer's rows quickly.

Should the partition key also be included in the index?

Answer: It depends on query pattern and database design.

CaseRecommendationReasoning
Query always includes partition key and then filters another selective keyIndex may start with the selective key, e.g. (customer_id, created_at)Partition pruning already reduced scope; customer_id may be the most useful search key inside the partition.
Query uses partition key as a range inside a large partitionIncluding partition key can still helpIt narrows the range inside the partition and can help ordering.
Uniqueness constraint spans partitionsDB-specific ruleSome engines require partition key to be part of a unique/local index; others support global uniqueness differently.
Query does not include partition keyIndex may still help, but engine may touch many partitionsWithout pruning, each partition may need to be searched; global indexes can change this behavior in engines that support them.

Local index vs Global index

Terminology and capability are database-specific:

  • Local index (index gắn theo từng partition): each partition has its own aligned index structure. Good manageability; pruning and index access work together naturally.
  • Global index (index bao phủ nhiều/all partition): one logical index spans partition boundaries. Useful for lookups not using the partition key, but maintenance can be more complex and support differs by engine.
Do not overgeneralize across databases: PostgreSQL, Oracle, SQL Server, and MySQL differ significantly in unique constraints, local/global indexing, automatic child-partition indexes, and partitioned-index syntax. In interviews, state the general principle first, then mention that exact implementation is engine-specific.

12. Common Query Patterns & Better Designs

Pattern 1 — Avoid SELECT *

-- Weak
SELECT * FROM orders WHERE customer_id = 1001;

-- Better
SELECT id, status, total_amount
FROM orders
WHERE customer_id = 1001;

Reading fewer columns reduces I/O, network transfer, memory, and sometimes enables a covering index.

Pattern 2 — Keyset pagination instead of deep OFFSET

-- Can become expensive for deep pages
SELECT id, created_at
FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 500000;

-- Better seek/keyset pagination
SELECT id, created_at
FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;

Pattern 3 — Avoid unnecessary DISTINCT

DISTINCT can force a sort/hash. If duplicates come from a bad join, fix the join instead of using DISTINCT as a patch.

Pattern 4 — Pre-filter before large joins

SELECT o.id, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= CURRENT_DATE - INTERVAL '7 days';

Make sure the date predicate and join key have useful access paths and statistics.

Pattern 5 — Avoid leading wildcard when possible

WHERE name LIKE '%abc%'

A standard B-tree is generally poor for leading-wildcard substring search. Depending on database and requirements, consider trigram/full-text/search-engine solutions.

Pattern 6 — Avoid implicit conversion

-- Suppose order_id is BIGINT
WHERE order_id = '10001'

Some engines can convert safely, others may cast the column or make estimates less accurate. Use consistent data types across parameters, joins, and foreign keys.

13. Production Pitfalls: Index & Partition Problems

Too many indexes

Writes become slower because every INSERT/UPDATE/DELETE maintains multiple index trees. Bulk loads and vacuum/maintenance can also cost more.

Redundant indexes

(customer_id) may be redundant if (customer_id, created_at) already serves the same workload, though exact usefulness depends on size and engine.

Wrong composite order

An index exists but the query cannot exploit its leading columns efficiently.

Stale statistics

The optimizer chooses a poor plan because it predicts 10 rows but actually gets 10 million.

Partition key missing

No pruning: the engine touches many partitions. This can make a partitioned table slower than expected.

Too many tiny partitions

Planning, metadata, file handles, maintenance, and operational complexity can increase.

Hot partition

All current writes land in one partition, so partitioning alone does not remove a write hotspot.

Function / cast hides index

The indexed column is transformed, making the predicate non-SARGable.

Case: “The index exists, but database still does a full scan”

Possible reasons:

  1. The predicate returns too many rows.
  2. Statistics are stale or cardinality estimate is wrong.
  3. The query uses a function/cast or mismatched data type.
  4. The composite index column order does not match the query.
  5. The table is small, so scanning is cheaper.
  6. Random row lookups are more expensive than sequential I/O.
  7. The optimizer expects most needed pages are already in cache or makes another cost-based choice.

14. Senior-Level Interview Questions & Answers

Q1. What are the first things you check when a SQL query is slow?
I first reproduce the query with realistic parameters and inspect the execution plan. I look at actual versus estimated row counts, rows read versus rows returned, expensive scans, join strategy, sorting/hashing, memory spills, and wait time. Then I verify indexes, statistics, predicate SARGability, data distribution, and whether the query is reading much more data than necessary. I measure again after each change rather than assuming an index will fix the issue.
Q2. When should you create an index?
I create an index when a frequent access pattern needs to find a relatively small subset of rows, support a join, avoid an expensive sort, or enforce uniqueness. I consider read frequency, selectivity, update frequency, table size, existing indexes, and whether a composite or partial index is better than a single-column index. I also validate the improvement from the execution plan and runtime metrics.
Q3. Should we index a flag or status column with only values 1, 2, 3, 4?
It depends on selectivity and distribution. A B-tree index on a 50/50 boolean column is often not useful because each value returns too many rows. But if one value is rare, such as ERROR = 0.1%, the index can be useful. A partial/filtered index can be even better. In read-heavy analytical workloads, bitmap indexing can also be relevant depending on the database, but it is normally not a good OLTP choice under heavy concurrent writes.
Q4. If I apply a function to an indexed column, is the index still used?
A normal B-tree index may no longer be usable for a direct seek because the predicate becomes non-SARGable. For example, DATE(created_at) = ? is usually worse than a timestamp range on created_at. However, a matching expression/function-based index or optimizer rewrite can still make index access possible. So the correct answer is database- and expression-dependent, not an absolute “no”.
Q5. What is the difference between an index and a partition?
An index is a search structure used to locate rows quickly. Partitioning divides a large table into separate chunks. Partition pruning can remove entire chunks from the query, while an index can then locate rows efficiently inside the remaining chunk. They solve different problems and often work together rather than replacing each other.
Q6. If a table is partitioned, should we still index it?
Usually yes. Partition pruning narrows which partitions are relevant, but a remaining partition may still contain millions of rows. We still need appropriate indexes for selective filters, joins, sorting, and uniqueness. The exact local/global index design depends on the database engine and query pattern.
Q7. Must the partition key be included in the index?
Not always. If pruning already isolates one partition and the real lookup key is customer_id, an index starting with customer_id may be better. But including the partition key can still help range filtering or ordering, and some database engines require the partition key in certain local unique indexes or constraints. I decide from the query pattern and engine rules, not from a universal rule.
Q8. Why can the optimizer ignore an index?
Because using the index can cost more than scanning. If the predicate returns a large percentage of the table, an index may cause many random row lookups. Other reasons include stale statistics, wrong cardinality estimates, non-SARGable predicates, implicit conversion, low selectivity, unsuitable composite order, or simply a small table.
Q9. How do you choose the order of columns in a composite index?
I start from the real query shape. Equality predicates are commonly placed before range predicates, and I consider join columns, ordering, grouping, selectivity, and whether the index can cover the query. I do not blindly put the highest-cardinality column first. The best order is the one that supports the most important access path with acceptable write cost.
Q10. When would you choose partitioning?
I consider partitioning for very large tables where data has a natural partition key such as time, tenant, or region, and where pruning, retention, archiving, loading, or operational maintenance becomes important. For example, monthly range partitions are strong for large event or order-history tables because old data can be dropped by partition and time-bounded queries can scan only relevant months.
Q11. Should we use a subquery, or should we always rewrite it as a JOIN?
I do not rewrite a subquery just because it is a subquery. EXISTS and NOT EXISTS are often the clearest form for semi-join and anti-join requirements, and many optimizers transform them into efficient join strategies. I become concerned when a correlated or scalar subquery is executed repeatedly for a large outer result. Then I check whether the correlation key is indexed, whether the optimizer decorrelates it, and whether a set-based JOIN or pre-aggregation reduces total work. The decision is based on the actual execution plan, rows processed, logical reads, and semantics—not on a rule that JOIN is always faster.

15. Scenario-Based SQL, Index & Partition Interview Questions

These scenarios are designed to show reasoning depth. A strong answer should not stop at “add an index” or “use partitioning.” Explain what work the database is doing, what the optimizer can eliminate, how selective the remaining predicates are, and how you would validate the decision with an execution plan.

Senior reasoning framework: Query shape → partition pruning → rows remaining → predicate selectivity → possible index access → table/heap lookups → sort/join cost → write overhead → execution plan validation. Đây là chuỗi suy luận nên nói ra khi trả lời phỏng vấn.

Scenario 1 — The query already uses the partition key. Do we still need an index?

Situation

A table contains 1 billion orders and is partitioned monthly by created_at. A query always filters one month and one customer:

SELECT id, total_amount, status
FROM orders
WHERE created_at >= '2026-08-01'
  AND created_at <  '2026-09-01'
  AND customer_id = 12345;
Yes, an index can still be very useful. Partition pruning and indexing reduce work at different levels. The date predicate may prune 120 monthly partitions down to one August partition, but that remaining partition could still contain 30 million rows. An index such as (customer_id, created_at) or a local index on customer_id can then locate the customer's rows inside that partition instead of scanning all 30 million rows. I would add or keep the index only if the customer predicate is selective enough and the query is important enough to justify the write/storage cost.
Key distinction: Partition pruning answers “which partition should I search?” The index answers “where are the matching rows inside that partition?”

What I would verify: the execution plan should show partition pruning first, then an index seek/range scan inside the surviving partition. I would compare rows read vs rows returned and logical I/O before and after the index.

Scenario 2 — The query filters only the partition key. Is another index always useful?

Situation
SELECT *
FROM audit_log
WHERE created_at >= '2026-08-01'
  AND created_at <  '2026-09-01';
Not necessarily. If the table is partitioned monthly and the query needs almost every row in the August partition, scanning that partition can be cheaper than traversing an index and then performing millions of row lookups. An index helps most when the predicate is selective. If the partition contains 100 million rows but the query asks for only a five-minute range, then an index on created_at can still be useful because the predicate is much narrower than the partition granularity.

Senior point: do not equate “index exists” with “index must be used.” The optimizer chooses the lowest estimated cost. A sequential/partition scan can be the correct plan when a large percentage of the partition is required.

Scenario 3 — The table is partitioned by date. Must the date column also be the first column of the index?

Situation

Partitions are monthly by created_at. The main query is:

SELECT id, status
FROM orders
WHERE created_at >= :from
  AND created_at <  :to
  AND customer_id = :customerId;
No universal rule says the partition key must be first in the index. If the date predicate already prunes the query to one or a few partitions, customer_id may be the better leading index column because it is the real selective lookup key inside each remaining partition. (customer_id, created_at) is often more useful than (created_at, customer_id) when customer_id is equality-filtered and created_at is a range. However, ordering, additional query patterns, uniqueness rules, and database-specific local-index requirements can change the design.
Do not memorize: “partition key must be in every index.” Instead say: “I design the index from the access path after pruning and from the database engine's constraint rules.”

Scenario 4 — The query does not contain the partition key but has an index on another column

Situation

orders is partitioned monthly by created_at, and every partition has a local index on customer_id:

SELECT *
FROM orders
WHERE customer_id = 12345;
The local index can still reduce row scanning inside each partition, but without a date predicate the database may have to probe the customer_id index in every partition. If there are 120 partitions, that can mean 120 index probes plus result merging. Some engines support global indexes that span partitions, but they introduce their own maintenance trade-offs. If this query is frequent and latency-sensitive, I would reconsider the access pattern, add a bounded date predicate when semantically possible, use a supported global index, or rethink the partitioning/data model.

Deep point: an index does not automatically restore partition pruning. Partition pruning depends on predicates the optimizer can map to the partition key.

Scenario 5 — Should we index a status column with values 1, 2, 3, 4?

Situation
SELECT id, created_at
FROM payment
WHERE status = 4;
I would first inspect the data distribution, not only the number of distinct values. If each status represents roughly 25% of the table, a normal B-tree index on status alone may be weak because the query still touches a huge number of rows. But if status = 4 represents only 0.1% of rows, the same low-cardinality column becomes highly selective for that value. A filtered/partial index such as “only rows where status = 4” can be even better when the engine supports it. A composite index such as (status, created_at) can also be effective for operational queries like “failed payments in the last hour.”
Vocabulary: low cardinality ít giá trị khác nhau is not identical to low selectivity độ chọn lọc thấp. Distribution matters.

Scenario 6 — A function is applied to an indexed column

Situation
-- created_at has a normal B-tree index
SELECT *
FROM orders
WHERE DATE(created_at) = '2026-08-27';
This often makes the predicate non-SARGable for the normal index because the database must evaluate DATE(created_at) rather than search directly for a range of raw created_at values. I would usually rewrite it as created_at >= '2026-08-27 00:00:00' AND created_at < '2026-08-28 00:00:00'. A matching expression/function-based index is another option if the database supports it and the expression is a real access pattern.

Important nuance: some optimizers can rewrite certain expressions automatically, so I verify the actual plan instead of claiming that functions always disable indexes.

Scenario 7 — The index exists but an implicit type conversion prevents efficient access

Situation

An indexed column and the bound parameter have different types.

-- customer_code is VARCHAR and indexed
WHERE customer_code = 123456
Depending on the database and conversion direction, the engine may convert the indexed column for every row, which can make the predicate non-SARGable or distort cardinality estimates. The fix is to bind parameters with the same data type and length/precision as the column whenever possible. I also check collation/character-set conversions because those can create similar problems.

Scenario 8 — Why does LIKE 'abc%' behave differently from LIKE '%abc%'?

A B-tree index is ordered from the beginning of the key. A prefix search such as name LIKE 'abc%' can often become a bounded index range. A leading wildcard such as name LIKE '%abc%' does not reveal where in the B-tree the matching values begin, so a normal B-tree is usually not enough. For substring search I would consider engine-specific full-text, trigram, inverted-index, or search-engine solutions rather than forcing a normal B-tree.

Scenario 9 — Which composite index order is better?

Situation
SELECT id, amount
FROM payment
WHERE merchant_id = :merchant
  AND status = 'FAILED'
  AND created_at >= :from
  AND created_at <  :to
ORDER BY created_at DESC;
A strong candidate is an index that starts with equality predicates and places the range/order column later, for example (merchant_id, status, created_at DESC). This lets the engine narrow by merchant and status, then scan the desired time range in order. But I would not choose the order from a slogan alone: I check which predicates are always present, their distribution, how many merchants exist, whether status is skewed, whether other queries reuse the index, and whether the engine can satisfy the ORDER BY without a sort.

Scenario 10 — We have an index on (a, b, c). Can a query on only b and c use it?

With a conventional B-tree, the strongest access path normally begins from the leftmost prefix, so predicates only on b and c usually cannot seek as efficiently as predicates beginning with a. Some engines have skip-scan or other optimizer techniques, but I do not design critical queries assuming those will save a mismatched index. If queries frequently start from b, they usually need a different index whose leading columns match that access pattern.

Scenario 11 — Can an index speed up ORDER BY ... LIMIT even if the filter is not very selective?

Situation
SELECT id, created_at
FROM notification
WHERE user_id = :userId
ORDER BY created_at DESC
LIMIT 20;
Yes. An index such as (user_id, created_at DESC) can seek to the user's key range and return the first 20 rows already ordered, avoiding a large sort and avoiding reading the user's entire history. This is an example where index value is not only about filtering; it can also provide order and support an efficient top-N access path.

Scenario 12 — Should we make every read query a covering index?

No. A covering index can avoid extra table/heap lookups and reduce I/O, but every included/key column makes the index wider. Wider indexes consume more storage and memory, reduce cache density, and make INSERT/UPDATE/DELETE more expensive. I use covering indexes for important high-frequency queries where avoiding row lookups produces measurable value. I avoid copying many large or volatile columns into indexes just to eliminate a small lookup cost.

Scenario 13 — An index exists but the optimizer still chooses a full scan

I would not force the index immediately. I first ask whether a scan is actually cheaper. If the predicate returns 40% of a table, a sequential scan may use fewer random I/Os than millions of index-to-table lookups. I also check stale statistics, cardinality misestimation, non-SARGable predicates, implicit conversions, composite-key mismatch, cached-plan/parameter sensitivity, and whether the table is small. The correct fix comes from the actual plan and runtime metrics, not from the fact that an index exists.

Scenario 14 — We added many indexes and reads improved, but writes became slow

That is an expected trade-off. Every INSERT may need entries inserted into multiple index trees; UPDATEs to indexed columns may modify several indexes; DELETEs remove index entries; and page splits or maintenance can add I/O. I would identify unused and overlapping indexes, consolidate indexes when one composite index can serve multiple important queries, avoid indexing every column independently, and measure write amplification. Index design is workload design, not a read-only decision.

Scenario 15 — Is creating many very small partitions always better?

No. Over-partitioning can increase metadata, planning time, open-file/object overhead, maintenance complexity, and the number of partition/index probes. The partition granularity should match data volume, query time windows, retention operations, and engine capabilities. If most queries read one month, daily partitions may be unnecessary unless the monthly partition is too large or operational requirements justify daily lifecycle management.

Scenario 16 — Current-day partition is overloaded. Does partitioning solve the concurrency problem?

Not automatically. Time partitioning often sends all current writes to the newest partition, creating a hot partition partition bị dồn tải. Partitioning is mainly a data-organization and pruning mechanism; it is not the same as sharding traffic across independent database nodes. Depending on the workload, solutions can include hash subpartitioning, distributed sharding, reducing index contention, batching, queueing, or changing the write key design. I would first identify whether the bottleneck is page/latch contention, locks, storage throughput, CPU, or a single database node.

Scenario 17 — Two huge partitioned tables are joined. Is partitioning enough to make the join fast?

Situation
SELECT ...
FROM orders o
JOIN payments p ON p.order_id = o.id
WHERE o.created_at >= :from
  AND o.created_at <  :to;
Not by itself. Pruning orders helps, but the database still needs an efficient way to find matching payments. An index on the join key such as payments(order_id) can be critical. Some engines can perform partition-wise joins when both tables are compatibly partitioned on related keys, but that is an optimization with engine-specific requirements. I would examine both sides of the plan, join order, join algorithm, row estimates, and whether both tables can be reduced before the join.

Scenario 18 — Unique constraints on a partitioned table

This is database-specific and is a good place to show depth. Local unique indexes can only guarantee uniqueness within each partition unless the partitioning scheme and engine rules allow a global guarantee. Some databases therefore require the partition key to be part of a partitioned unique constraint; others provide global indexes with different maintenance costs. I would explicitly check the target engine's rules rather than assume that a local unique index guarantees uniqueness across all partitions.

Scenario 19 — Updating the partition key

Situation
UPDATE orders
SET created_at = '2026-09-01'
WHERE id = 1001;
If created_at is the partition key and the row moves from the August partition to the September partition, the operation can behave more like a delete from one partition plus an insert into another, subject to engine behavior. That can be much more expensive than updating a non-partition key and can affect indexes, logging, locking, and replication. A good partition key is therefore usually stable.

Scenario 20 — The execution plan shows both partition pruning and index scan, but the query is still slow

Then I move beyond “does it use the index?” and inspect the real cost. The query may still return millions of rows, perform millions of table lookups, sort a large result, spill hash/sort data to disk, wait on locks, hit cold storage pages, or spend most time transferring data over the network. I compare actual vs estimated rows, rows read vs returned, buffer/physical I/O, sort/hash spill, wait events, and result size. “Uses index” is not a performance guarantee.
Strong interview statement: “I do not optimize for an execution-plan label like Index Scan. I optimize for total work: rows/pages read, CPU, waits, memory, and end-to-end latency.”

Scenario 21 — A global customer search is frequent, but the table is time-partitioned

Situation
SELECT *
FROM transactions
WHERE customer_id = :customerId
ORDER BY created_at DESC
LIMIT 100;
A time-partitioned layout is excellent for time-bounded analytics and retention, but this query is customer-oriented and may have to search many partitions. I would first ask whether the business can supply a time bound. If not, options include a supported global index, a separate customer-centric lookup table/materialized projection, a different partitioning strategy, or a search/read model designed for this access pattern. This illustrates an important principle: partition keys should come from dominant access patterns and lifecycle requirements, not only from table size.

Scenario 22 — Count or aggregate over most of the table

Situation
SELECT status, COUNT(*)
FROM orders
WHERE created_at >= '2026-01-01'
GROUP BY status;
If the query legitimately needs a very large fraction of the year's data, a normal OLTP index may not remove much work. Partition pruning can remove older years, but the database may still need to scan many rows and aggregate them. For frequent analytical workloads I would consider pre-aggregation, materialized views, columnar storage, a reporting replica/warehouse, or partition-level summary tables rather than endlessly adding B-tree indexes to an OLTP table.

Scenario 23 — Deep pagination becomes slower on later pages

Situation
SELECT id, created_at
FROM orders
WHERE customer_id = :customerId
ORDER BY created_at DESC, id DESC
LIMIT 50 OFFSET 500000;
Even with a good index, the engine may still walk or discard roughly 500,000 earlier rows before returning the next 50. I prefer keyset/seek pagination when possible, using the last seen (created_at, id) as the next boundary. An index such as (customer_id, created_at DESC, id DESC) then supports a direct continuation from the previous page.

Scenario 24 — Should indexes be rebuilt after every large insert?

Normally no. Database indexes are maintained transactionally as rows are inserted, updated, and deleted. Rebuilding an index after every load would usually be wasteful. What may need attention is engine-specific maintenance such as statistics refresh, vacuum/analyze, page fragmentation/bloat, or bulk-load strategies. I separate the concepts of index contents from optimizer statistics: the index can be structurally up to date while statistics are stale.

Scenario 25 — Partitioning or sharding?

Partitioning splits one logical table into partitions managed by a database engine and is primarily useful for pruning, lifecycle management, and large-table operations. Sharding distributes data across separate database nodes or clusters to scale storage/write throughput horizontally and introduces routing, cross-shard query, rebalancing, and consistency problems. Partitioning can exist inside each shard. I would not promise horizontal scalability merely because a table is partitioned.

Scenario 26 — A correlated subquery is slow. Should we always replace it with a JOIN?

Situation
SELECT c.id,
       (SELECT MAX(o.created_at)
        FROM orders o
        WHERE o.customer_id = c.id) AS last_order_at
FROM customers c
WHERE c.region = 'APAC';
Not automatically. First I check how many APAC customers are returned and whether orders(customer_id, created_at DESC) exists. If the outer result contains only a few hundred customers, indexed correlated lookups can be very efficient. If it contains millions of customers, repeated lookups may become expensive, and a set-based aggregation such as GROUP BY customer_id followed by a JOIN may reduce total work. I also check whether the optimizer has already decorrelated the subquery into a join-like plan. The correct answer depends on the number of outer rows, selectivity, index support, data distribution, and actual execution plan.
Deep point: “Correlated subquery” describes SQL syntax. It does not guarantee a row-by-row runtime plan. The optimizer may transform it. Always reason from the physical plan, not only the written query.

16. Final Query Tuning Checklist

  • Execution plan: Do I know where the time and I/O are spent?
  • Rows read: Am I scanning millions of rows to return only a few?
  • SARGability: Did I apply a function, calculation, or cast to an indexed column?
  • Index selectivity: Does the predicate narrow to a small enough subset?
  • Composite order: Does index order match equality/range/join/sort usage?
  • Low-cardinality: Is the rare-value distribution enough to make the index useful?
  • Statistics: Are optimizer statistics current and representative?
  • Partition pruning: Does the query include a predicate that allows pruning?
  • Index inside partitions: Is the remaining partition still too large to scan?
  • Write trade-off: Will the new index significantly hurt INSERT/UPDATE/DELETE?
  • Pagination: Can OFFSET be replaced with keyset pagination?
  • Data returned: Can I avoid SELECT *?
  • Architecture: Should this workload live in OLTP DB, or use cache/search/warehouse/read replica?

One-Minute Summary

Index

Use it to locate rows quickly when a query is selective. Watch out for write overhead, low selectivity, non-SARGable predicates, and bad composite order.

Partition

Use it to manage and prune very large datasets. It is strongest when queries include the partition key and when retention/maintenance is important.

Low-cardinality status

Not automatically bad. A rare value, partial index, composite index, or analytical bitmap index can still be effective.

Function on indexed column

Often makes a normal index predicate non-SARGable. Rewrite as a range or use a matching function/expression index.

Partition + Index

Common best practice: prune partitions first, then use an index to find rows inside the remaining partitions.

Senior answer style

Always say “it depends on selectivity, query pattern, distribution, database engine, and measured execution plan” rather than giving absolute rules.
